    권한 구조와 관리자 화면에 들어가는 방법이다.

    A-01권한 체계

    무엇을 하나

    역할은 user와 admin 두 가지다. 화면 문구의 「운영자」는 admin 권한을 뜻한다.

    구분 할 수 있는 일 판정
    user 질의·양식 채우기·알람 수신(권한 존만)·노이즈 관제 조회 사용자 토큰 + DB 조회 권한
    admin user 기능 전부 + 관리자 대시보드·관리자 노이즈 관제·관리 API 사용자 토큰의 DB 역할이 admin
    break-glass 운영자 admin과 같다 /admin/login으로 받은 운영자 토큰(.env의 부트스트랩 계정)

    AUTH_ENABLED=false(개발 모드)면 모든 요청이 익명으로 통과하고 Admin 링크도 항상 보인다.

    사용 방법

    1. 운영 환경은 AUTH_ENABLED=true로 둔다. 이때 ADMIN_USERNAME·ADMIN_PASSWORD·ADMIN_JWT_SECRET·AUTH_JWT_SECRET이 없으면 서버가 기동을 거부한다.
    2. 최초 기동 시 활성 관리자가 0명이면 부트스트랩 계정이 admin 사용자로 한 번 만들어진다.
    3. 다른 사용자를 관리자로 만들려면 사용자 관리에서 역할을 admin으로 바꾼다.

    화면 요소

    화면 캡처가 없다. 권한 판정은 서버에서 하며, 화면의 링크 숨김은 편의 기능일 뿐이다.

    주의·제약

    • 화면 HTML(대시보드·매뉴얼 포함)은 서버에서 막지 않는다. 데이터와 조작은 API가 권한을 검사한다.
    • 관리자(admin)는 「조회 가능 DB」 목록과 관계없이 전체 DB를 조회할 수 있다.

    A-02관리자 화면에 들어가는 두 가지 길

    무엇을 하나

    1. admin 사용자로 로그인 → 메인 화면 머리글의 Admin 링크(새 탭)

    2. 2비밀번호
    3. 3사용자 화면으로 돌아가기

    • 운영자 토큰은 사용자 토큰과 다른 시크릿으로 서명된다(ADMIN_JWT_SECRET). 두 시크릿을 같게 두지 않는다.

    A-07등급과 반영 시점

    무엇을 하나

    항목마다 반영 시점 배지와 등급이 있다.

    반영 시점 뜻
    즉시 저장하면 바로 반영
    리로드 저장 후 설정 리로드를 누르면 재시작 없이 반영
    재시작 서버를 재시작해야 반영
    등급 뜻 예

    • OS 환경변수로 같은 키가 주입돼 있으면 .env를 지워도 그 값이 쓰인다(A-12).

    A-09저장과 변경 확인

    무엇을 하나

    저장을 누르면 바뀐 항목을 전·후 값으로 보여 주는 확인 창이 뜬다. 확인하면 .env에 기록된다.

    사용 방법

    1. 값을 고친다. 그룹 제목에 「미저장 N건」이 표시된다.
    2. 저장을 누른다.
    3. 확인 창에서 전(붉은 줄)·후(초록 줄) 값과 반영 시점 배지를 확인하고 저장, 아니면 취소를 누른다.
    4. 결과 알림에서 재시작 필요 항목, 무시된 항목, DB 준비도 경고를 확인한다.

    1. 1저장(확정)
    2. 2취소

    • 시크릿 항목은 저장해도 반영되지 않는다(무시된 항목으로 알린다).
    • 저장만으로는 「리로드」·「재시작」 항목이 반영되지 않는다.

    A-10설정 리로드

    무엇을 하나

    설정 리로드는 서버를 재시작하지 않고 「리로드」 항목을 반영한다. 설정을 새로 읽고, 운영 검사를 다시 하고, 실행 그래프를 다시 만든 뒤 한 번에 교체한다.

    사용 방법

    1. 저장을 마친 뒤 설정 리로드를 누른다.
    2. 결과 알림을 확인한다. 실패하면 기존 설정이 그대로 유지된다.

    화면 요소

    1. 3설정 리로드

    A-45침묵(Silence) 규칙

    무엇을 하나

    침묵(Silence)은 기간을 정해 특정 서버·알람·자원 패턴의 통보를 멈추는 규칙이다. 억제 기록은 그대로 남는다.

    사용 방법

    1. 관리 탭 침묵(Silence)에서 서버·알람·자원 패턴(글롭, 예: svr-web-*), 심각도 상한, 지속 시간, 사유를 입력한다.
    2. 침묵 추가를 누른다.
    3. 목록에서 해제로 끝낸다. 만료·해제분 포함을 체크하면 지난 규칙도 보인다.
    4. 결정 추적 창의 이 패턴 침묵을 누르면 그 알람의 값이 입력란에 채워진다.

    주의·제약

    • 심각도 3은 어떤 규칙으로도 침묵되지 않는다.
    • 만료 없는 침묵은 만들 수 없다. 지속 시간 상한은 기본 7일(NOISE_SILENCE_MAX_DURATION_SECONDS)이다.
    • 침묵 기능(NOISE_SILENCE_ENABLED)이 꺼져 있으면 규칙을 만들어도 적용되지 않고, 화면 위에 그 사실이 표시된다.
    • 규칙 추가·해제는 감사 로그에 남는다.

    2. 판단 결과는 logs/alarm_decisions.jsonl(NOISE_DECISION_STORE_PATH)에 알람마다 한 줄씩 쌓인다. 화면에서는 노이즈 관제의 결정 이력·결정 추적으로 본다.
    3. 개별 알람이 어떻게 판단됐는지는 A-60의 단계 표와 결정 추적의 판단 경로를 맞춰 본다.

    주의·제약

    • 게이트가 꺼져 있으면 분석만 하고 최소 심각도(ALARM_MIN_SEVERITY) 이상 알람을 모두 통보한다. 노이즈 관제 화면에도 판단이 쌓이지 않는다.
    • 지문 중복으로 걸러진 재발은 판단 레코드가 아니라 type="recurrence" 레코드로만 남는다. 발생 건수를 셀 때 둘을 합친다.
    • 게이트가 켜진 상태에서 1 ≤ 심각도 < ALARM_MIN_SEVERITY 알람은 판단 전에 기록 없이 버려진다. 주의(1) 알람까지 보려면 ALARM_MIN_SEVERITY=1로 둔다.

    A-61보조 신호 — LLM·통계·운영자 피드백

    무엇을 하나

    판단에 보조 입력으로 들어가는 LLM·통계 신호와 운영자 피드백이 어디서 어떻게 쓰이는지 정리한다. 모두 결정 기록의 신호 스냅샷에 남는다.

    신호 방식 판단에 들어가는 곳 켜는 설정(코드 기본)
    알람 분석(요약·원인·패턴·is_routine) LLM 1회 호출 9단계 승격·강등 게이트 흐름에 항상 포함
    액션가능성(llm_actionability) 같은 LLM 호출에 운영자 피드백 예시를 넣어 판단(추가 호출 없음) 9단계 승격·강등 NOISE_ENABLE_LLM_ACTIONABILITY(false)
    AI 심각도 상향 메시지형 알람의 등급을 LLM이 올리기만 함 1단계 실효 심각도 = max(폴스타, AI) NOISE_ENABLE_AI_SEVERITY_BOOST(false)
    동적 baseline Holt-Winters(선택 시 STL) 잔차 z-score → 상향 후보 위 AI 상향 경로로 반영 NOISE_DYNAMIC_BASELINE_ENABLED 그리고 NOISE_ENABLE_AI_SEVERITY_BOOST · STL은 NOISE_ANOMALY_STL_ENABLED
    agentic 보강 오케스트레이터 LLM이 읽기 전용 도구로 신호 수집 심각도 상향만 NOISE_ENABLE_AGENTIC_ENRICHER(false)
    주석 LLM 분류 운영자 손글 주석(계획작업·해소)을 LLM이 분류, 실패 시 정규식 7.7단계 NOISE_ANNOTATION_LLM_CLASSIFICATION_ENABLED(false)
    변경 근접 알람 직전 창(3600초)의 변경 이력과 자원 매칭 9단계 승격만 NOISE_CHANGE_CORRELATION_ENABLED(false)
    임베딩 근접 중복 로컬 임베딩 코사인 유사도 주석 전용(판정 무관) NOISE_SEMANTIC_DEDUP_ANNOTATION_ENABLED(false)

    운영자 피드백이 반영되는 경로(알람 카드의 유효·노이즈):

    1. 라벨이 logs/alarm_feedback.jsonl(NOISE_FEEDBACK_STORE_PATH)에 한 줄 쌓인다.
    2. 다음에 같은 알람명이 오면 과거 라벨 중 알람명이 같은 것만 후보로 고르고, 자원명 일치 +2점·패턴 일치 +1점, 동점이면 최신 순으로 최대 NOISE_ACTIONABILITY_FEWSHOT_COUNT(3)건을 프롬프트에 넣는다.
    3. LLM이 actionable 또는 noise를 낸다. 예시가 없으면 의견도 없다.
    4. 9단계에서 actionable은 승격, noise는 조건부 강등으로 소비된다.

    사용 방법

    1. 피드백 반영을 쓰려면 NOISE_ENABLE_NOISE_GATE·NOISE_ENABLE_LLM_ACTIONABILITY·NOISE_FEEDBACK_STORE_ENABLED를 모두 켠다. 앞의 둘 중 하나라도 꺼져 있으면 피드백 API가 503(「피드백 비활성」)을 돌려준다. 저장소 설정이 꺼져 있으면 요청은 받아도 라벨이 저장되지 않는다.
    2. 반영 여부는 결정 추적 신호 스냅샷의 LLM 액션가능성 값과 사유의 「승격:」·「강등:」 문구로 확인한다.
    3. 쌓인 라벨은 알람 피드백 요약에서 본다. 같은 알람에 유효·노이즈가 엇갈리면 최신 라벨이 우선한다.

    화면 요소

    화면 캡처가 없다. A-39 알람 피드백 그림을 본다.

    주의·제약

    • 피드백은 명령이 아니라 자문이다. 최대 1단계, 다음 알람부터이며, 승격 신호가 하나라도 있으면 노이즈 라벨은 무시된다. 심각도 3에는 닿지 않는다.
    • 조회 키는 알람명이다. 서버별로 따로 학습되지 않고, 누른 횟수에 가중치도 없다.
    • 억제(SUPPRESS)된 알람은 카드가 뜨지 않아 피드백을 달 수 없다. 잘못 억제된 알람은 결정 이력이나 억제 포함(감사) 표시 레벨로 찾는다.
    • LLM을 부르는 기능은 알람 유입량만큼 호출이 는다. 운영 LLM이 과금 경로라면 켜기 전에 승인을 받는다.

    A-54실행 경로(사다리) 확인

    무엇을 하나

    질의 처리 방식(실행 경로)은 기동할 때 한 번 정해지고 기동 로그 한 줄로 확인한다.

    1. 기동 로그에서 오케스트레이션 사다리 확정: tier=… 줄을 찾는다.

    • 플래그를 비워 두면 다른 설정(활성 DB 등)에 따라 경로가 자동으로 정해진다. 운영에서는 값을 명시한다.

    문제 해결

    관리자 화면에 들어가지 못한다(로그인·403)

    증상 원인 대응
    /admin을 열면 메인 화면(/)으로 돌아간다 로그인한 계정의 역할이 user다. 대시보드는 진입 시 관리자 API를 한 번 호출해 확인하고, 403이면 안내 없이 메인 화면으로 보낸다(src/static/js/admin.js verifyToken). 다른 관리자가 A-30에서 역할을 admin으로 바꾼다. 역할은 요청마다 DB에서 다시 읽으므로 재발급 없이 다음 진입부터 반영된다.
    /admin을 열면 로그인 화면(/login?next=/admin)으로 간다 토큰이 없거나 만료·무효(401)다. 로그인하면 대시보드로 돌아온다. 사용자 토큰이 만료된 경우에는 메인 화면(/)을 먼저 열어 다시 로그인한 뒤 Admin 링크로 들어간다(메인 화면은 만료 토큰을 지우고 로그인 화면으로 보낸다).
    /admin/login에서 「ID 또는 비밀번호가 올바르지 않습니다.」 이 화면은 .env의 부트스트랩 계정(ADMIN_USERNAME·ADMIN_PASSWORD)만 확인한다. 사용자 DB의 계정은 여기서 로그인되지 않는다. 평소에는 /login으로 로그인한 뒤 Admin 링크로 들어간다(A-02).
    관리 API가 「관리자 권한이 필요합니다.」(403) 사용자 토큰은 유효하지만 역할이 admin이 아니다(src/api/dependencies.py require_admin_user). 관리자 노이즈 관제의 실시간 피드도 같은 문구로 거부한다. 위 첫 행과 같다.
    「보호된 root 계정의 역할·상태는 변경할 수 없습니다.」 등(403) 보호 root 계정은 역할·상태 변경, PW초기화, 삭제가 막혀 있다(src/api/routes/admin.py). 의도된 동작이다. 부서·알림그룹 같은 다른 항목은 바꿀 수 있다.

    설정 리로드가 실패한다

    리로드는 실패하면 기존 설정과 실행 그래프를 그대로 유지한다(src/api/routes/admin.py reload_settings). 실패 알림은 5초 뒤 사라지므로 바로 읽는다. 서버 로그에도 같은 사유가 남는다.

    표시 문구 원인 대응
    저장되지 않은 변경이 있습니다 — 먼저 저장한 뒤 리로드하세요. 화면에 미저장 편집이 남아 있다. 요청은 서버로 가지 않았다. 저장하거나 편집을 되돌린 뒤 다시 누른다.
    설정 로드에 실패했습니다 — 기존 설정이 유지됩니다: (사유) 저장된 .env를 설정으로 읽지 못했다(형식 오류 등). 400. 사유에 나온 키의 값을 고친다. 목록·사전 값은 JSON 배열·객체 형식으로 적는다.
    운영 모드 필수 설정 검증에 실패했습니다 — 기존 설정이 유지됩니다: (사유) AUTH_ENABLED=true인데 필수 크레덴셜·시크릿이 비었다. 기동 시와 같은 검사다. 400. 사유에 나열된 키(ADMIN_USERNAME/ADMIN_PASSWORD, ADMIN_JWT_SECRET, AUTH_JWT_SECRET)를 .env/.encenv에 채운다.
    그래프 재빌드에 실패했습니다 — 기존 설정이 유지됩니다: (사유) 새 설정으로 실행 그래프를 만들지 못했다. 500. 사유와 서버 로그를 보고 바꾼 설정을 되돌리거나 고친다.
    서버와의 통신에 실패했습니다. 응답을 받지 못했다. 서버 상태를 확인한다.

    리로드는 성공했지만 일부가 반영되지 않은 경우도 있다.

    • 「설정을 리로드했습니다 — N건 반영, M건은 서버 재시작이 필요합니다.」와 함께 「다음 항목은 서버 재시작 후 반영됩니다: …」 배너가 뜬다. 나열된 키는 재시작해야 반영된다(A-07).
    • 알람 워커가 켜져 있고 LLM_*·DBHUB_*·ACTIVE_DB_IDS가 바뀌었으면 「알람 워커는 재시작 전까지 이전 LLM/DB 설정으로 동작합니다: …」가 덧붙는다. 질의 경로만 새 값으로 바뀐 상태다.

    저장 후 「활성화 준비도 경고」가 뜬다

    ACTIVE_DB_IDS에 새로 넣은 DB가 있으면 저장 직후 그 DB의 준비도를 판정하고, 필수 조건을 채우지 못한 DB를 알린다(A-09). 저장은 이미 끝났으며 경고가 저장을 막지 않는다.

    표시 문구 뜻 대응
    ⚠ 활성화 준비도 경고 — 저장은 완료되었습니다. 아래 DB는 「DB 구조」 탭에서 필수 항목을 채우세요. 제목 줄이다. 아래에 DB마다 「(DB) — 필수 미충족 N건: 항목 (사유) · …」가 나온다. 4장 DB 구조에서 그 DB의 준비도 항목을 확인하고 채운다(A-16, A-19).
    준비도를 판정하지 못했습니다: 준비도 판정 시간 초과(20초) 판정이 상한 20초 안에 끝나지 않았다. 「DB 구조」 탭에서 그 DB의 준비도를 직접 확인한다.
    준비도를 판정하지 못했습니다: 준비도 판정 실패: (오류) 판정 중 오류가 났다. 서버 로그의 같은 사유를 확인하고 「DB 구조」 탭에서 준비도를 확인한다.
    • 판정은 실행 중인 프로세스의 설정으로 한다. 레지스트리를 새로 고쳤다면 재시작 전까지는 옛 등록 기준으로 판정된다.
    • 이 경고는 감사 로그의 설정 변경 기록에도 함께 남는다.
    • 이미 활성이던 DB는 다시 판정하지 않는다. 기존 DB의 상태는 「DB 구조」 탭의 준비도 열로 본다.
