## 1. 결론 요약

**전면 전환은 부적합하다. 이 프로젝트는 이미 반대 방향(LLM → 정규식)으로 여러 번 실측 후 되돌린 이력이 코드 주석에 남아 있다** (§4.3). 정규식 210곳 중:

|---|---|---|

**추가 발견 2 — 정규식 이전의 결함**: HITL 승인 파서가 fail-open(기본값 `approve` — 오탐 시 미승인 SQL 실행, §8-1). 전환 논의 전에 수정해야 한다.

## 4. 카테고리 A 상세 — 사용자 질의 해석 12곳

### 4.1 핵심 실측: LLM은 이미 같은 정보를 뽑고 있는데 그 결과가 버려진다

`src/prompts/input_parser.py`는 LLM에게 `time_range`(L42,54)·`limit`(L45,55)·`aggregation`을 명시 요구하고 `src/nodes/input_parser.py:232-234/329-331`이 `parsed_requirements`에 세팅한다. 그러나 다운스트림 소비 전수 grep 결과:

- **`limit` 소비처 0건** — 실제 LIMIT은 전부 정규식 `resolve_query_limit`이 결정.
- **`time_range`는 SQL 생성 경로 소비 0건** — 소비처는 `output_generator.py:232`(0건 안내 문구)·`result_organizer.py:296`뿐. 실제 기간 필터는 정규식 `resolve_stat_month_range`가 결정.

즉 A 카테고리는 "LLM과 중복"이 아니라 **"LLM 경로를 대체·폐기"한 구조**다. 전환 검토의 출발점은 "정규식을 LLM으로 바꾸자"가 아니라 "이미 있는 LLM 산출물을 왜 안 쓰는가"이다.

### 4.3 A1~A9를 LLM으로 되돌리면 안 되는 실측 근거 (코드 주석에 남은 이력)

- `semantic_compiler.py:646-647` — "SMQ가 명시 요청 차원을 누락하는 **비결정 보정용**(2026-07-21 gp-009)". `:675-677` — 같은 질의에서 "동시선택→단독선택→미선택"으로 흔들린 3회 관측 기록.
- `semantic_compiler.py:768-770` — "프롬프트 단서만으로는 LLM이 패턴 B로 과포획(월별 4725행→1820행 붕괴), **프롬프트 보강 후에도 재발** → 결정적 게이트로 폴백 강제".
- `query_gen_common.py:83-87` — "LLM이 `BETWEEN 직전월 AND 이번달`처럼 진행 중인 달까지 재계산 → 코드가 해석한 월을 강제"(D-076 후속4).
- `multi_db_executor.py:629-631` — "프롬프트로 '제안'하면 LLM이 프로필 few-shot과 경쟁해 무시·변형 → 코드가 직접 조립해 LLM 우회"(D-068 2차 정정).

A1~A9의 LLM 재위임은 D-068/D-076/D-099의 실측 근거를 무효화하며 CLAUDE.md "LLM 비결정성 대응" 원칙과 정면 충돌한다. **단, Plan 67 트랙 S(단계적 도출 루프)와는 충돌하지 않는다** — 루프에서 LLM은 `resolve_time_range` 등 **결정적 도구를 호출**할 뿐 해석 자체를 재계산하지 않는다(도구 내부 로직이 이 정규식들이다).

### 4.4 A1~A6 권고: 2단 폴백 (전환이 아니라 회복)

정규식 1순위 유지 + 미매칭 시 §4.1의 폐기되던 `parsed_requirements["time_range"]`/`["limit"]` 폴백. "지난 반년"·"백 건" 같은 미커버 표현을 회복하면서 결정성 유지, **신규 LLM 호출 0건**(D-127 무관). 폴백 발동은 로그로 계측(정규식 미커버율의 실측 데이터가 됨).
