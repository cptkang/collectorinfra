# Redis 기반 동의어(유사어) 관리의 적정성 분석 및 개선점

> 대상: `collectorinfra` — Polestar 인프라 모니터링 DB 자연어→SQL 에이전트의 유사어 사전
> 작성일: 2026-07-13
> 관련: `docs/text2sql_quality_research.md`(Text-to-SQL 문헌 조사), D-012(매핑-우선), D-019(Redis 캐시), D-051(유사어 보완 상한), D-035(결정적+LLM)
> 범위: (1) 현행 동의어 관리 구현 정밀 분석, (2) Text-to-SQL 문헌 대비 적정성 판정, (3) 개선점(IP-1~IP-5)

## 0. 요약

동의어(유사어) 사전은 **한국어 질의어를 실제 DB 스키마 요소(컬럼·resource_type·EAV 속성명)로 연결하는 도메인 지식 계층**이다. 이는 Text-to-SQL 문헌에서 BIRD가 강조하는 *external knowledge evidence* 및 CHASE-SQL의 *Value Retrieval* 철학과 정확히 같은 목적을 가진다. 즉 **접근 방향 자체는 문헌에 부합하고 적정하다.**

그러나 구현 세부를 문헌 SOTA와 대조하면 세 가지 한계가 드러난다:

1. **매칭이 "정규화 후 정확 문자열 일치"에 한정** — 형태소·의역·부분어 변형("메모리 사용률"↔"메모리 이용률"↔"MEM 점유율")을 잡지 못한다. 문헌(DAIL-SQL 스켈레톤 유사도, 임베딩 기반 선택)은 의미 유사도를 쓴다. 현재 Redis(`redis:7-alpine`)에 RediSearch/벡터 모듈이 없어 의미 검색 인프라도 부재.
2. **동의어 ≠ 값 검색(Value Retrieval)** — 사전은 "용어→컬럼/타입"을 매핑하지만, WHERE 절 리터럴에 쓸 **실제 DB 셀 값**을 체계적으로 검색·주입하지 않는다. `resource_type_synonyms`/`column_values`가 부분적으로 보완하나, 키워드/LSH 인덱싱된 라이브 값 검색은 아니다.
3. **기여도 측정 부재** — 유사어 적중률·EX(실행정확도) 기여를 계측하지 않아, 사전 확장이 실제 품질을 올리는지 검증 불가(→ R1 평가 하네스와 결합 필요).

결론: **현행 방식은 폐쇄망·읽기전용·결정적(D-035) 제약 하에서 적정하며 유지할 가치가 있다.** 다만 매칭을 정확일치→유연/의미 매칭으로 승격하고(IP-1/IP-2), 값 검색으로 확장하며(IP-3), 적중률을 계측(IP-4)하면 품질을 유의미하게 끌어올릴 수 있다.

## 1. 현행 동의어 관리 구현 분석

### 1.1 저장 구조 (Redis)

`src/schema_cache/redis_cache.py`의 키 정의:

| Redis 키 | 자료형 | 내용 |
|----------|--------|------|
| `synonyms:global` | Hash | `{table.column: JSON([유사어…])}` — 전 DB 공용 컬럼 유사어 |
| `synonyms:resource_types` | Hash | `{resource_type값: JSON([한국어 표현…])}` (예: `server.Server`↔서버) |
| `synonyms:eav_names` | Hash | `{EAV 속성명: JSON([한국어 표현…])}` (예: `Hostname`↔호스트명) |
| `synonyms:column_values` | Hash | `{table.column: JSON([값 유사어…])}` |
| `{db_id}:synonyms` | Hash | DB별 매핑 피드백(사용자 등록/LLM 추론 결과) |

- **파일 시드**: `src/schema_cache/synonym_loader.py`가 `config/global_synonyms.yaml`을 로드해 위 글로벌 키에 저장(merge/overwrite 모드). mtime 기반 재로드.
- **DB 초기화 시 글로벌 보존**: `redis_cache.py`의 초기화 로직은 DB별 데이터만 지우고 `synonyms:global` 등 글로벌 사전은 보존한다.

### 1.2 생성·등록 경로 (Human-in-the-loop + LLM)

`src/document/field_mapper.py::perform_3step_mapping`의 매핑 소스는 3종(+EAV):
1. **hint** — 양식/질의의 명시적 힌트
2. **synonym** — 사전 정확일치 매칭
3. **llm_synonym / llm_inferred** — LLM이 발견/추론한 매핑

- LLM이 추론한 매핑은 `_build_pending_registrations`로 **등록 후보**가 되고, 사용자가 `synonym_registrar`(`"전체 등록"`/`"1,3 등록"`/`"건너뛰기"`)로 승인한 것만 Redis에 영구 등록된다(D-012 매핑-우선 전략).
- 즉 사전은 **LLM 발견 → 사람 확인 → 학습 축적** 루프로 성장한다. 이는 문헌의 external-knowledge 큐레이션과 정합하며, 환각 유입을 사람 게이트로 차단한다.

### 1.3 매칭 로직 (핵심)

`src/document/field_mapper.py::_synonym_match`:

```python
field_no_space = field_lower.replace(" ", "")
for col_key, words in synonyms.items():
    for word in words:
        word_norm = normalize_field_name(word).lower()
        if word_norm == field_lower or word_norm.replace(" ", "") == field_no_space:
            return col_key          # ← 정규화 후 "정확 동등" 만 인정
    # 컬럼명 자체도 정확일치 시도
```

→ **정규화(소문자·공백제거) 후 완전 동등**일 때만 매칭. 편집거리·부분문자열·의미 유사도·한글 자모 변형은 인정하지 않는다.

### 1.4 프롬프트 주입 및 스케일 가드

- `query_generator`/`schema_analyzer`는 스키마 텍스트 컬럼 줄에 `[유사: w1, w2, …]`(최대 5개)를 붙이고, `RESOURCE_TYPE`/`EAV 속성명` 참조 섹션을 프롬프트에 추가한다.
- **스케일 문제와 D-051 가드**: 유사어가 전 테이블×컬럼 규모로 누적된 DB(polestar_b0, 실측 407테이블)에서 유사어 테이블을 무조건 `allowed_tables`에 전량 편입하면 system prompt가 104K > FabriX 한도 95K로 폭증한 이력이 있다. 이에 `schema_analyzer._synonym_tables_matching_query`는 **이번 질의에 실제 등장한 유사어의 테이블만** 게이트하고 상한(`_MAX_SYNONYM_SUPPLEMENT_TABLES=15`)을 두며, 빈 문자열·1글자 유사어는 오매칭 방지를 위해 제외(길이≥2만 인정)한다.
- `src/utils/synonym_usage.py::extract_synonym_usage`는 생성된 SQL을 사전과 역대조해 "LLM이 실제로 사용한 유사어"를 UI에 표시(계측이 아니라 표시 용도).

## 2. Text-to-SQL 문헌 대비 적정성 판정

| 문헌 관점 | 문헌 권고 | 현행 동의어 관리 | 판정 |
|-----------|-----------|------------------|------|
| **외부지식 주입** | BIRD: 도메인 힌트·값 매핑·유사어 정의가 EX에 직접 기여 | 유사어 사전으로 명시적 주입 | ✅ **적정** — 방향·목적 일치 |
| **엔티티/스키마 링킹** | 질의어↔스키마 요소 연결 | 용어→컬럼/타입/EAV명 매핑 | ✅ 적정(연결 대상) / ⚠️ 매칭방식 취약 |
| **매칭 알고리즘** | 의미 유사도(임베딩·스켈레톤), 최소한 퍼지 | **정규화 후 정확일치만** | ⚠️ **개선 필요** |
| **값 검색(Value Retrieval)** | CHASE-SQL 1단계: WHERE 리터럴용 실제 DB 값 검색 | 부분적(resource_type·column_values), 라이브 값 인덱싱 없음 | ⚠️ **개선 여지** |
| **큐레이션·거버넌스** | 사람 검증된 evidence 우선 | LLM 발견 + 사람 승인 루프(D-012) | ✅ **우수** |
| **결정성** | 재현 가능성 | 결정적 룩업(D-035 정합) | ✅ 적정 |
| **측정** | Spider/BIRD EX로 기여 검증 | 미계측 | ⚠️ **개선 필요** |

**종합 판정**: 동의어 관리의 **존재 이유와 거버넌스(사람 승인·결정성·폐쇄망 적합)는 문헌 기준으로 적정하고 오히려 모범적**이다. 취약점은 오직 **매칭 정밀도(정확일치 한정)·값 검색 미흡·측정 부재**에 국한된다. 즉 "폐기/교체"가 아니라 "매칭·계측 계층의 보강" 문제다.

## 3. 개선점 (IP-1 ~ IP-5)

### IP-1. 유연 매칭 도입 (정확일치 → 정규화·자모·부분어) — *저비용, 인프라 무변경*
- **문제**: `_synonym_match`가 완전 동등만 인정 → "메모리 사용률"은 잡지만 "메모리 이용률/점유율", "MEM 사용률", 오탈자를 놓친다.
- **개선**: (a) 한글 자모 분해(초성·NFC 정규화) 후 비교, (b) 편집거리(Levenshtein) 임계 기반 근사일치, (c) 토큰/부분어 포함 매칭(단, 빈문자열·1글자 제외 기존 가드 유지). 오매칭 억제를 위해 **매칭 신뢰도 점수**를 부여하고 임계 이하는 후보로만 제시.
- **효과**: 표현 변형 커버리지↑, 미등록 재질문↓. Redis/모델 변경 불필요.
- **리스크**: 과잉매칭 → 신뢰도 임계와 D-051식 상한으로 통제. **회귀 없는 옵트인 플래그** 권장.

### IP-2. 선택적 의미(임베딩) 검색 — *중비용, 폐쇄망 오프라인 임베딩*
- **문제**: 정확/퍼지로도 못 잡는 의역·동의개념("가동률"↔"이용률"↔"사용률").
- **개선**: 유사어·컬럼 설명을 **오프라인 사전계산 임베딩**으로 벡터화하여 질의어 top-k 근접검색. 현행 `redis:7-alpine`은 벡터 미지원 → 두 경로: (a) Redis Stack/RediSearch 도입, (b) **인프로세스 벡터 인덱스**(FAISS/numpy 코사인)로 Redis 무변경 유지. 폐쇄망에서는 사내 임베딩 모델 또는 사전계산 벡터를 반입.
- **효과**: 커버리지 최대. **비용**: 임베딩 모델 반입·인덱스 관리.
- **권고**: IP-1 이후, 측정으로 정확/퍼지의 한계가 확인될 때 도입(과설계 방지).

### IP-3. 동의어 → 값 검색(Value Retrieval) 승격 — *R5와 통합*
- **문제**: WHERE 리터럴(`resource_type='server.Server'`, EAV `NAME='Hostname'`)이 사전에 없으면 환각(Plan 25에서 관찰된 미존재 resource_type 생성).
- **개선**: 안정·유한한 폴스타 값집합(distinct `resource_type`, EAV `NAME` 값)을 주기적으로 인덱싱해 질의 키워드로 검색·주입. 기존 `synonyms:column_values`를 **실측 값 검색**으로 승격하고 캐시.
- **효과**: 필터 리터럴 환각 직접 억제. `docs/text2sql_quality_research.md`의 R5와 동일 작업 — **함께 구현**.

### IP-4. 유사어 적중률 계측 (R1 하네스 연동) — *선행 권장*
- **문제**: 사전 확장이 EX를 올리는지 데이터가 없다.
- **개선**: 질의별 (유사어 히트 수, 소스=hint/synonym/llm, 매칭 신뢰도, 최종 SQL 성공 여부)를 로깅. R1 EX 하네스에 **"유사어 on/off" A/B 축**을 추가해 기여도를 정량화.
- **효과**: IP-1~IP-3의 도입 판단을 근거 기반으로 전환. `extract_synonym_usage`(현재 UI 표시)를 계측 소스로 재활용.

### IP-5. 사전 위생·거버넌스 (신뢰도·감쇠·우선순위) — *저비용*
- **문제**: 사전이 커질수록 프롬프트 토큰·오매칭 리스크↑(D-051이 이미 완화 중).
- **개선**: 각 유사어에 (등록출처, 사용횟수, 최종사용일, 신뢰도) 메타 부여 → (a) 프롬프트 주입 시 **사용빈도·신뢰도 상위만** 선별, (b) 장기 미사용 항목 감쇠/정리, (c) 충돌(동일 용어가 여러 컬럼에 매핑) 시 우선순위 규칙.
- **효과**: 스케일 안정성·정밀도 동시 확보. 기존 상한(15) 가드의 상위 정책화.

## 4. 권고 순서

| 단계 | 항목 | 근거 | 비용 |
|------|------|------|------|
| 선행 | IP-4 계측(R1 연동) | 개선 검증 수단 | 낮음 |
| 1 | IP-1 유연 매칭 + IP-5 위생 | 저비용·즉효, 인프라 무변경 | 낮음 |
| 2 | IP-3 값 검색(R5 통합) | 환각 직접 억제 | 중간 |
| 3 | IP-2 의미 검색 | 잔여 의역 커버(측정 후 판단) | 중~높음 |

**핵심 메시지**: 동의어 관리는 **적정한 설계이며 유지**한다. 개선은 "매칭 정밀도 + 값 검색 + 측정" 세 축의 보강이며, 대부분 Redis·모델 교체 없이 애플리케이션 계층에서 옵트인·무회귀로 가능하다. IP-2(의미 검색)만 인프라 판단(Redis Stack vs 인프로세스 인덱스)이 필요하므로 측정(IP-4) 후 결정한다.
