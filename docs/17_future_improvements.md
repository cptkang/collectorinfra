# 추후 개선 사항 (Future Improvements)

이 문서는 **당장 구현하지 않지만 언젠가 개선해야 할 항목**을 구조적으로 축적하는 백로그입니다.
기능 요건이 새로 발생하거나, "지금은 하지 않기로" 결정한 개선점이 생길 때마다 이 문서에 항목을 추가합니다.

- **결정(D-NNN)과의 관계**: 확정된 설계·의사결정은 [`02_decision.md`](02_decision.md)에 기록합니다.
  이 문서는 "아직 결정/구현하지 않은 개선 후보"를 다룹니다. 어떤 항목을 실제로 구현하기로 확정하면,
  해당 결정을 `02_decision.md`에 `D-NNN`으로 추가하고, 여기 항목의 **상태**를 `구현됨(→ D-NNN)`으로 갱신합니다.
- **Known Mistakes와의 관계**: 재발 방지용 실수 이력은 `CLAUDE.md`의 "Known Mistakes"에 기록합니다.
  이 문서는 실수가 아니라 **개선 여지**를 다룹니다.

---

## 사용 방법 (작성·갱신 규칙)

새 항목을 추가할 때는 아래 규칙을 따릅니다.

1. **ID 부여**: `FI-NNN` (Future Improvement) 형식. 아래 "변경 이력" 표와 각 항목 헤더를 모두 확인하여
   현재 최댓값 + 1을 부여합니다. (ID 재사용·충돌 금지 — Known Mistakes 2026-06-25 교훈)
2. **분류(Category)**: 아래 "분류 체계"의 태그 중 하나 이상을 부여합니다. 없으면 새 태그를 분류 체계에 추가합니다.
3. **템플릿 준수**: 아래 "항목 템플릿"의 필드를 모두 채웁니다. 근거·트레이드오프를 비워두지 않습니다.
4. **우선순위·상태 갱신**: 상황이 바뀌면(관련 요건 발생, 부분 구현, 폐기) 해당 항목의 상태·우선순위를 갱신하고
   "변경 이력"에 한 줄 남깁니다.
5. **구현 확정 시**: `02_decision.md`에 `D-NNN`을 추가하고, 이 문서 항목 상태를 `구현됨(→ D-NNN)`으로 바꿉니다.
   항목 본문은 삭제하지 않고 이력으로 남깁니다(왜 이 개선이 필요했는지의 맥락 보존).

### 상태 값

| 상태 | 의미 |
|------|------|
| `제안됨` | 개선 후보로 기록만 됨. 착수 미정 |
| `검토중` | 설계/트레이드오프 논의 진행 중 |
| `보류` | 의도적으로 미루기로 결정(트리거 조건 충족 시 재개) |
| `구현됨(→ D-NNN)` | 구현 완료. 확정 결정은 `02_decision.md` 참조 |
| `폐기` | 더 이상 필요 없음(사유 기록) |

### 우선순위 값

`높음` / `중간` / `낮음` — "사용자 영향 × 발생 빈도 × 리스크"로 판단. 판단 근거를 항목 본문에 남깁니다.

## FI-001. 오케스트레이터 런타임 동적 폴백 / 자동 복귀

| 항목 | 내용 |
|------|------|
| **분류** | 가용성/복원력 |
| **상태** | 제안됨 |
| **우선순위** | 중간 |
| **제안일** | 2026-07-01 |
| **관련 결정/코드** | D-037(빌드 시 1회 결정적 백엔드 선택), [`src/graph.py:321`](../src/graph.py#L321), [`src/orchestration/deep_agent.py:66`](../src/orchestration/deep_agent.py#L66), [`src/orchestration/deep_agent.py:212`](../src/orchestration/deep_agent.py#L212) |
| **트리거 조건** | vLLM 오케스트레이터(트랙 B)를 운영 상시 경로로 승격할 때 / 운영 중 vLLM 단절로 인한 요청 실패가 실제로 관측될 때 |

### 문제 / 현재 동작

deepagents 오케스트레이터(vLLM tool-calling, 트랙 B) 백엔드 선택은 **그래프 빌드 시(앱 기동 시) 1회만** 판정되어
프로세스 수명 동안 고정된다(D-037, "결정적"). 이로 인해:

- **기동 시 폴백은 있음**: 기동 시점에 vLLM이 미가용이면 `vllm_healthy()`가 False → `semantic_router`로 폴백([`deep_agent.py:66-80`](../src/orchestration/deep_agent.py#L66-L80)). 앱은 정상 기동한다.
- **런타임 폴백은 없음**: 기동 후 잘 돌던 중 vLLM 연결이 끊기면, `deep_agent` 노드의 [`agent.ainvoke`](../src/orchestration/deep_agent.py#L212)가 연결 예외를 그대로 전파 → 해당 요청은 500/에러로 실패한다(자동으로 semantic으로 강등되지 않음). 이 줄은 try/except로 감싸여 있지 않다(빌드 실패만 [`deep_agent.py:201`](../src/orchestration/deep_agent.py#L201)에서 처리).
- **자동 복구는 없음**: 반대로 기동 시 vLLM이 죽어 semantic으로 고정된 경우, 이후 vLLM이 살아나도 트랙 B로 전환되지 않는다. 관리자 설정 변경도 `load_config.cache_clear()`만 하고 그래프를 재빌드하지 않으므로, 결국 **프로세스 재시작**이 유일한 전환 경로다.

> 참고: 폐쇄망 활성 런타임 경로는 트랙 A(`enable_deepagent_orchestration`, FabriX 워커 사용)이며 vLLM에 의존하지 않는다.
> 본 항목은 vLLM을 쓰는 트랙 B를 상시 운영으로 올릴 때 특히 중요해진다.

### 개선 목표

1. 기동 시 오케스트레이터 우선 선택(현행 유지).
2. **런타임 중 오케스트레이터 통신 불가 시 semantic_router로 자동 폴백**(요청 실패 대신 강등 처리).
3. **통신 복구 시 자동으로 오케스트레이터로 복귀**(프로세스 재시작 불필요).

### 후보 접근

1. **A안 — 노드 내 try/except 폴백(경량)**
   - 오케스트레이션 노드에서 vLLM 호출을 감싸고, 연결 예외 시 그 요청만 semantic 로직으로 인라인 강등.
   - **복귀 자동**: 매 요청이 오케스트레이터를 먼저 시도하므로 vLLM 복구 시 자연 복귀.
   - 단점: 장애 구간에 매 요청이 vLLM 타임아웃을 1회 물고 폴백 → 짧은 TTL 헬스 캐시로 완화.
2. **B안 — 조건부 엣지 + 백그라운드 헬스 폴러(구조적)**
   - 두 경로를 그래프에 모두 등록하고, `field_mapper` 뒤 라우터가 공유 헬스 플래그(N초마다 백그라운드 갱신)를 읽어 분기.
   - 폴백·복귀 모두 플래그로 구동, 요청당 타임아웃 부담 없음.
   - 단점: lifespan에 백그라운드 태스크 수명관리 추가, 부품 증가.

### 트레이드오프 / 주의

- **D-037 충돌**: 현재 결정은 "빌드 시 1회 판정으로 백엔드 확정(결정적)"을 **의도적으로** 채택했다. 본 개선은 이 결정성을 런타임 동적성으로 바꾸는 것이므로, 착수 시 **D-037을 갱신(또는 신규 D-NNN 발행)** 해야 한다. 임의 진행 금지 — 사용자 확인 필수(CLAUDE.md 결정 충돌 규칙).
- 헬스 판정 진동(flapping) 방지: 폴백↔복귀가 짧은 간격으로 반복되지 않도록 히스테리시스(연속 N회 성공/실패) 고려.
- 관측성: 폴백·복귀 전환은 반드시 로그(전환 사유·시각)로 남겨 "조용한 강등"이 되지 않게 한다.
