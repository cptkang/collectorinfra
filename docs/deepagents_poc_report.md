## 1. 결과 — 무엇이 동작하는가

PoC 대상은 사다리 1단 `deep_agent`다: 오케스트레이터가 tool-calling으로 제어하고, 도구 내부는 기존 워커 파이프라인이 실행하며, 최종 자연어 응답도 워커(`result_aggregator`)가 만든다.

| 성공기준(`plans/49` §1.3) | 판정 | 근거 |
|---|---|---|
| 1. tool_calls 왕복 안정 | **충족(MLX)** | 대역 프로브 도구 호출 36건에서 파싱 실패 0. 시나리오별 도구 순서 3/3 일치 |
| 2. `write_todos`·`task` 구동 | **미관측** | 대역 24건·실 DB 4건 모두 내장 도구 호출 0. 동적 재계획은 ReAct 순차 도구 호출로 이뤄진다 |
| 3. registry 도구 노출·내부 실행 | **충족** | 도구 7종 노출(계획 5종 + `query_live_processes`·`inspect_host`), 내부는 워커 파이프라인 |
| 4. 결과 조건부 재계획 | **충족** | 패턴 ③ 대역 3/3(있음→후속 실행 · 없음→미실행 · 0건→재조회). 패턴 ② 실 DB 충족 |
| 5. 최종 응답 워커 생성 | **충족** | 오케스트레이터 자유 서술이 최종 응답으로 나간 경우 0/28. 일반 안내도 워커 `general_inference` 산출 |
| 6. 가용성 기반 백엔드 선택 | **기동 시 충족 / 런타임 미구현** | 정상→`deep_agent` · 오케스트레이터 사망→`intent_orchestration`(2단 on) · 플래그 off→`intent_orchestration` · 사망+2단 off→`semantic_router`. 런타임 장애는 §2 참조 |
| 7. 폐쇄망 도입 조건 문서화·검증 | **부분 충족** | 본 보고서로 문서화. wheel 반입·내부망 vLLM 실검증은 미완(§3) |

**실 DB 종단 4건**(`build_graph()` 1단 확정 그래프 + MCP 9099 로컬 샌드박스, 오류·타임아웃 0)

| ID | 질의 형태 | 도구 호출 | 소요 |
|---|---|---|---|
| E1 | 단순 집계("서버 수") | `data_query` 1회 | 104초 |
| E2 | 독립 2조회("CPU 상위 3 + 메모리 상위 3") | `data_query` 2회 — **병렬** | 245초 |
| E3 | 결과 의존 2단("심각 알람 서버 → 그 서버들의 IP·OS") | `alarm_query` → `data_query` — **순차**, 선행 결과가 후속 SQL 스코프로 주입(D-095) | 228초 |
| E4 | 일반 안내 | 도메인 조회 도구 0회, 워커 `general_inference`로 위임 | 48초 |

E3가 이 구조의 핵심을 보여준다. 오케스트레이터는 "알람 서버를 먼저 찾고 그 서버들을 조회한다"는 **순서만** 정하고, 대상 서버 집합을 프롬프트로 전달하지 않는다. 코드가 선행 결과에서 식별 값을 뽑아 후속 SQL에 `HAVING … hostname IN ('svweb001','svbatch009')`로 **결정적으로** 주입한다. LLM이 서버 목록을 옮겨 적다 흘리는 실패 모드가 구조적으로 없다.

### 1.1 PoC에서 찾아 고친 결함 (D-234)

조회는 전부 성공했는데 **최종 응답에서만 데이터가 사라지는** 침묵 손실 3종이 실측됐다. 세 건 모두 모델 무관·결정적이라 내부망 FabriX·vLLM 조합에서도 그대로 발생했을 것이다.

| ID | 증상 | 원인 | 수정 |
|---|---|---|---|
| B-1 | 독립 2조회 중 한쪽 결과 소실 | 병합 표를 행수 최소 조회의 서버 집합으로 절단(동률이면 첫 조회) | 절단은 `base_keys ⊆ 다른 조회 키 합집합`일 때만. 공통 서버 0이면 결정적 병합 포기 → LLM 합성 폴백 |
| B-1a | 후속 조회 컬럼이 표에 남고 값만 공란 | 병합 키가 원시 값이라 `server_name='SV-WEB-001'`과 `hostname='svweb001'`이 다른 서버로 갈림 | 병합 키를 정규화 값으로(`_identity_key` — 소문자 + `[\s_.-]` 제거) |
| B-2 | 병렬 도구 호출 중 한쪽 결과가 덮어써짐 | 호출 순번을 collector 길이로 계산 — collector는 도구가 **끝날 때** 늘어난다 | `build_tools`가 도구 묶음마다 만든 공유 `itertools.count`에서 **시작 시점**에 채번 |

수정 전후 같은 질의 대조(로컬 MLX):

- **E2** — 수정 전 "메모리 사용률 상위 서버는 조회된 데이터에 포함되어 있지 않습니다"(SQL 2건은 모두 성공) → 수정 후 `cpus_avg`·`memory_avg` 3행 전부.
- **E3** — 수정 전 `OSType` 공란("OS 정보는 데이터에 포함되지 않았습니다") → 수정 후 `Linux`·`AIX`.

**교훈**: 이 구조는 도구 결과를 오케스트레이터의 문맥이 아니라 **별도 수집기(collector)** 에 모아 워커가 재정리한다. 그래서 "SQL이 성공했다"와 "사용자가 그 데이터를 본다" 사이에 코드 경로가 하나 더 있고, 그 경로의 결함은 **로그만 봐서는 보이지 않는다**(조회 성공 로그가 모두 남는다). PoC 단계에서 최종 응답 본문을 실데이터와 대조하지 않았다면 놓쳤을 결함이다.

## 2. 한계 — 무엇이 확인되지 않았거나 동작하지 않는가

### 2.1 계획과 다른 실측

- **`write_todos`·`task`가 쓰이지 않는다.** `create_deep_agent`는 내장 도구 8종(`write_todos`·`task`·파일시스템 6종)을 자동 장착하고, 오케스트레이터에 노출된 도구 정의 20,415자 중 **92%(18,814자)가 내장**이다(도메인 7종은 1,601자). 실사용은 0회다. 동적 재계획은 내장 계획 도구가 아니라 ReAct 순차 도구 호출로 성립했다. 즉 **이 도입의 실익은 "deepagents의 계획 미들웨어"가 아니라 "tool-calling 루프"** 다.
- **오케스트레이터가 `sub_query`에 SQL을 넣는다.** 36건 중 30건이 자연어가 아니라 **존재하지 않는 테이블로 지은 SQL**이었다(예: `SELECT … FROM servers WHERE …` — 폴스타에 `servers` 테이블 없음). 도구 인자 스키마에 설명이 없는 것이 원인으로 보인다(`{"sub_query": {"type": "string"}}`). 워커가 실 스키마로 재생성해 조회 자체는 성공하지만, 설계 전제(§4.2 "자연어 지시")와 다르다.
- **런타임 graceful fallback이 없다.** 기동 후 오케스트레이터가 죽으면 `openai.APIConnectionError`가 그대로 전파된다(2.1초). 백엔드 선택은 **기동 시 1회**뿐이다. 이는 의도된 상태다 — 조용히 하위 단으로 내려가는 것은 저장소의 침묵적 폴백 금지 원칙과 충돌하므로, 구현하려면 "무엇을 어떻게 알릴지"를 포함한 결정이 선행한다.

### 2.2 검증 범위 밖

- **단일 환경**이다. 워커·오케스트레이터 두 평면 모두 같은 로컬 MLX 서버(9B 4bit)를 썼다. 운영 조합(워커 FabriX + 오케스트레이터 vLLM)은 검증되지 않았다.
- **로컬 샌드박스 DB**다. PostgreSQL 단일 소스이고 DB2 방언·멀티 존·대용량은 포함되지 않았다.
- **D-234 ②(겹침 0 → 합성 폴백) 경로는 실 DB에서 타지 않았다.** 샌드박스에서 CPU 상위 3과 메모리 상위 3이 같은 서버 집합이라 겹침이 3/3이었다. 이 경로는 단위 테스트로만 검증됐다.
- **응답 절단이 남아 있다.** `finish_reason=length`(`LLM_MLX_MAX_TOKENS=4096`) 경고가 종단 실행마다 관측된다. 잘린 응답이 그대로 다음 단계로 넘어간다. MLX 설정 문제이지만, 운영 모델에서도 도구 정의 18KB + 대화 누적이 컨텍스트를 압박할 수 있다.
- **폐쇄망 도입 조건 자체가 미검증**이다 — §3.

## 3. 운영 권고

### 3.1 위치 — 부가 경로로 둔다

2026-09-17 사용자 기준으로 **기본 실행 경로는 사다리 3단 `semantic_router`**이고 `deep_agent`는 부가 경로다(D-225). 본 PoC 결과는 이 배치를 뒷받침한다:

- 실익은 tool-calling 루프이지 계획 미들웨어가 아니다(§2.1). 같은 효과를 LangGraph 네이티브로 얻는 경로가 `plans/103`로 계획돼 있다.
- 도구 정의의 92%가 실사용 0인 내장 도구다 — 컨텍스트 비용 대비 이득이 낮다.
- 반면 **결과 의존 체인(E3)과 병렬 조회(E2)는 실제로 동작**한다. 폐기 대상이 아니다(D-225 ② — D-161 승격-폐기 동반의 명시 예외).

### 3.2 내부망 도입 전 반드시 확인할 것

순서대로 게이트를 통과시킨다. 앞 게이트가 깨지면 뒤는 의미가 없다.

1. **wheel 반입·설치** — `deepagents`·`langchain`·`langchain-core>=1.4.7`(+전이) 3플랫폼 wheel을 격리 venv에 설치하고 기존 회귀를 돌린다. 현 실측 설치본은 `deepagents 0.6.10` · `langchain-core 1.6.1` · `langgraph 1.2.11`이다(`plans/49` §3.1 표는 작성 시점 값이라 갱신 대상).
2. **vLLM tool-calling 신뢰도(R-B2)** — 선정 모델에 `--enable-auto-tool-choice`와 모델별 `--tool-call-parser`를 붙이고, Qwen3 계열이면 **thinking 모드와 tool-calling의 상호작용**을 확정한다. 병렬·연속 tool_calls를 부하 상태에서 실측한다. MLX에서 파싱 실패 0이었다는 사실은 vLLM 파서 설정의 대체 증거가 되지 않는다.
3. **§2.1의 두 관찰이 내부망에서도 재현되는지** — ①`sub_query`에 SQL이 들어오는지 ②내장 도구가 실제로 쓰이는지. 재현되면 도구 인자 설명 보강·내장 도구 축소를 검토한다. **단, 둘 다 프롬프트 접두를 바꾸므로 KV 캐시 무효화 비용을 함께 판단한다**(78 P14) — 접두가 흔들리면 이후 전 턴의 캐시가 무효가 된다.
4. **최종 응답 본문 대조** — 조회 성공 로그가 아니라 **사용자에게 나간 표의 전 컬럼**을 실데이터와 맞춰 본다. §1.1의 결함 3종이 전부 이 대조에서만 드러났다.

### 3.3 운영 시 주의

- **플래그는 기동 시 1회 해석된다.** `ENABLE_DEEPAGENTS_PACKAGE`·`ENABLE_INTENT_ORCHESTRATION`·`ENABLE_SEMANTIC_ROUTING`의 조합으로 사다리 단이 확정되며, 확정 결과는 기동 로그 1줄(`record_ladder_resolution`)로만 판독된다. 뒤 두 개는 tri-state라 미입력 시 `ACTIVE_DB_IDS` 등록 상태에 따라 달라진다 — **고정하려면 `.env`에 명시한다**.
- **오케스트레이터 장애는 사용자에게 오류로 드러난다**(§2.1). 이를 바꾸려면 결정이 선행한다.
- **`deep_agent`와 `semantic_router`는 병합·집계 코드를 공유한다.** D-234 수정도 1·2단 공용 경로에 들어갔다. 한쪽 경로만 보고 병합 동작을 판단하지 말 것.
- **컨텍스트 예산**을 확보한다. 도구 정의만 20KB다. 운영 모델의 컨텍스트 길이와 `max_tokens`를 도구 정의 + 대화 누적 + 결과 요약 기준으로 잡는다.

산출물: `reports/deepagent_mlx_20260917/` (프로브·종단 스크립트 + 결과 JSON).

두 스크립트 모두 **비과금 루프백 확인 뒤에만** LLM을 호출한다: 워커·오케스트레이터 두 평면이 `mlx`이고 base_url이 `http://127.0.0.1:`로 시작하며 `external_planes`가 비어 있어야 하고, Gemini 키 3종은 OS env 빈 값으로 덮는다(D-127 — 과금 외부 API는 사용자 승인 없이 호출 금지). 사다리가 `tier=deep_agent`가 아니면 거부한다.

공유 MLX 서버를 쓸 때는 `mlx_polite_gate()`가 (a) 다른 클라이언트가 붙어 있으면 대기 (b) 1토큰 생성으로 생존 확인을 한다. 2026-09-17 16:20 동시 요청 2건 처리 중 `[METAL] Insufficient Memory`로 서버 생성 스레드가 죽고 `/health`만 200을 반환하는 좀비 상태가 된 사고가 있었다 — **동시성 1로 직렬 실행한다**.
