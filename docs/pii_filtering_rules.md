# PII 필터링 규칙

> **출처**: 「11. 개인정보 필터 가이드」(그룹 공동 생성형 AI 가이드, 2026-08-05 확보본).
> 코드 이식본은 `src/security/pii_filter.py`의 `PII_RULES` — 이 문서와 반드시 동기 갱신한다.
> FabriX 커넥터 경유 호출은 LLM 사용 여부와 무관하게 **질문(프롬프트)·답변(응답)·문서 업로드
> 전부** 이 필터가 적용되며, 9개 유형 모두 처리 정책이 "차단"이다(이름은 미차단).

아래 정규표현식과 일치하는 문자열은 개인정보(PII)로 판단하여 필터링한다.

## 1. 주민등록번호

- 룰 ID: `848`
- 탐지 예시:
  - `8809161111111`
  - `880916-1111111`
  - `880229 2111111`

```regex
(?<!\d)(?:(?:[5-9]\d)(0[1-9]|1[0-2])(0[1-9]|[12]\d|3[01])[- ]?[12]\d{6}|(?:[0-4]\d)(0[1-9]|1[0-2])(0[1-9]|[12]\d|3[01])[- ]?[34]\d{6})(?!\d)
````

## 2. 법인등록번호

* 룰 ID: `854`
* 탐지 예시:

  * `180213-2111111`

```regex
(?<!\d)(?:(1[1-9]|2[0-8])(0[1-3]|1[1-5]|4[1-9]|5[0-9]|6[0-2])(1[1-5]|2[1-2]|3[1-9]|4[0-9]|5[0-5]|6|7|8[1-6])(?:[-\s]\d{7}))(?!\d)
```

## 3. 외국인등록번호

* 룰 ID: `849`
* 탐지 예시:

  * `121210-5234567`
  * `121210 5234567`

```regex
(?<!\d)\d{2}(?:0[1-9]|1[0-2])(?:0[1-9]|[12]\d|3[01])[- ]?[5678]\d{6}(?!\d)
```

## 4. 운전면허번호

* 룰 ID: `850`
* 탐지 예시:

  * `12-11-222222-33`
  * `서울 12 121058 50`
  * `11 12-121058-50`

```regex
(?<!\d)(?:(?:서울|부산|경기|강원|충북|충남|전북|전남|경북|경남|제주|대구|인천|광주|대전|울산|1[1-9]|2[0-8])[- ]?\d{2}[- ]\d{6}[- ]\d{2}|(?:서울|부산|경기|강원|충북|충남|전북|전남|경북|경남|제주|대구|인천|광주|대전|울산|1[1-9]|2[0-8])[- ]\d{10})(?!\d)
```

## 5. 여권번호

* 룰 ID: `842`
* 탐지 예시:

  * `D24689033`
  * `M15687911`

```regex
(?<!\d)(?:[MSROD]\d{8}|[MSROD]\d{3}[A-Z]\d{4})(?!\d)
```

## 6. 핸드폰번호 (2026-08-05 개정)

* 룰 ID: `855`
* 탐지 예시:

  * `01012345678`
  * `010 1234 5678`
  * `010-1234-5678`
  * `010.1234.5678`
* 구분자(하이픈·점·공백)는 두 위치에 **동일하게** 사용된 형식만 탐지한다
  (백레퍼런스). 혼합 형식(`010-12345678`)은 비탐지.

```regex
(?<!\d)(?:010([-.\s]?)\d{4}\1\d{4}|01[16789]([-.\s]?)\d{3,4}\2\d{4})(?!\d)
```

## 7. 계좌번호 (2026-08-05 개정)

* 룰 ID: `851`
* 탐지 예시:

  * `6565-01-02-233123`
  * `6471 01 02 233123`
* 공식 주석(가이드):

  * 핸드폰번호를 계좌번호로 사용하는 경우 (중복) 필터될 수 있다.
  * 2-2-3-5 자리 패턴은 탐지되지 않는다.
  * 알파벳 하나가 맨 앞에 붙은 접수번호 형태는 제외한다.
* 총 숫자 10~14자리, 동일 구분자(하이픈 또는 공백) 3그룹 이상.
* ⚠ 가이드 PDF에서 원문 정규식이 일부 절단되어 아래는 **예시·예외 기준 재구성본**이다
  — 폐쇄망 실측(차단 덤프·pii_probe)으로 격차 발견 시 보정할 것.

```regex
(?<![A-Za-z0-9])(?<!\d[- ])(?!\d{2}(?P<a>[- ])\d{2}(?P=a)\d{3}(?P=a)\d{5}(?!\d))(?!\d{4}(?P<d>[- ])\d{2}(?P=d)\d{2}(?!(?P=d)\d)(?!\d))(?=(?:\d[- ]?){10,14}(?![- ]?\d))\d{2,6}(?P<s>[- ])\d{2,6}(?P=s)\d{1,8}(?:(?P=s)\d{1,8})*(?!\d)
```

* 날짜형(`YYYY-MM-DD`, 뒤에 동일 구분자 그룹이 더 없을 때)은 제외한다 — 타임스탬프
  (`2026-08-05 12:30:45`) 오탐 방지(서버 원문의 날짜·시각 제외 단편 대응).

### ⚠ 인프라 데이터에서 계좌번호 룰에 걸리는 형태 (D-152 후속3 — 육안 진단용 카탈로그)

"계좌번호 차단인데 계좌 유사값이 없다"고 보일 때 실제로 걸리는 형태들
(전부 로컬 이식 룰로 재현 확인, PostgreSQL 공동존 데이터 포함):

| 형태 | 예시 | 비고 |
|------|------|------|
| **유선 전화번호** | `02-1234-5678`, `031-123-4567` | 핸드폰 룰(855)은 010/01x만 — **유선·팩스는 계좌 룰(851)로 차단** (담당자 연락처 컬럼의 맹점) |
| 팩스·평생번호 | `0505-123-4567` | 11자리 |
| 회선·자산·계약 코드 | `12-3456-789012` | 동일 구분자 3그룹+, 10~14자리 |
| IP 하이픈 표기 | `192-168-10-115` | 11자리 매칭 (`192-168-0-11`은 9자리라 비매칭) |
| 공백 구분 코드 | `6471 01 02 233123` | 공백도 구분자 |
| DB2 타임스탬프 | `2026-08-05-14.30.45.123456` | 하이픈 4그룹 10자리 (b0) |

비매칭 확인: 9자리 이하, 1자리 그룹 포함(`10-0-17763-1234`), 16진수 혼입(MAC),
파이프/콤마 구분, 단일 알파벳 접두(`A6565-…`), 2-2-3-5 패턴.

### ⚠ 계좌번호 룰의 날짜·타임스탬프 광폭 매칭 (D-152 후속3)

* **DB2 타임스탬프**(`2026-08-05-14.30.45.123456`)는 하이픈 4그룹 10자리라
  이 룰(재구성본 포함)에 **그대로 매칭**된다 — b0 샘플의 dtime류 값이 "계좌번호
  차단인데 계좌 유사 문자열 부재" 증상의 유력 원인.
* 서버 원문의 날짜 제외 단편은 2자리 연도(`YY-MM-DD`)형만 커버 — 4자리 연도는
  제외되지 않는다. 자릿수 창이 비숫자 관통(`\D*`, 구룰 방식)이라면
  `"2026-06-17 02:30:45", "id": 123` 같은 숫자 많은 라인의 일반 타임스탬프도
  창을 채워 매칭될 수 있다(의심 — 이등분 재현으로 확정).
* **ISO 타임스탬프의 날짜부(`2023-07-14T17:48:31.267000` → `2023-07-14`) 매칭 분석
  (2026-08-06, 공동존 라이브 의심 검출 대응)**: 가이드에서 온전히 보이는 코어 단편
  `\d{2,6}([- ])\d{2,6}\1\d{1,8}(?:\1\d{1,8})*`만으로 실행하면 날짜부가 **매칭**된다
  (그룹 구조 최소 자릿수 = 2+2+1 = 5). 구룰의 명시적 `{10,14}` 최소 창이 개정본에
  유지됐는지가 절단부에 가려 미확인 — 단 ①개정본에 2자리 연도형 날짜 제외가 굳이
  존재(= 최소 창이 낮아 짧은 날짜형이 걸리기 때문으로 해석)하고 ②4자리 연도는 그
  제외를 벗어나며 ③공동존 차단 덤프에서 다른 계좌 유사값이 부재했으므로, **날짜부
  매칭 가능성이 높다**. 확정은 해당 라인 1개짜리 파일로 pii_probe 1회 호출.
* **실측(2026-08-06)**: ISO 타임스탬프 **단독 라인은 통과** — "날짜부 단독 매칭"은
  기각. 남는 가설은 **조합/총량 의존**(자릿수 창을 여러 값이 함께 채우는 형태 —
  구룰의 `(?=(?:\D*\d){10,14}\D*$)` 방식이면 정확히 이 동작) 또는 별도 재료.
  pii_probe가 이등분에서 "양쪽 절반 모두 통과"를 만나면 **ddmin(델타 디버깅)으로
  자동 전환**해 함께 있어야 차단되는 최소 라인 집합을 특정한다(D-152 후속4).

## 서버측 탐지 내역 무추정 확인 경로 — filter_log_id

클라이언트 응답에는 **탐지 문자열이 실리지 않는다**(FabriX는 유형 policy_id +
`filter_log_id`까지만, catched_text는 APIM 경로 전용). 추정 없이 "무엇이 걸렸는지"를
확인하는 공식 경로:

1. `[PII-FILTER]` 로그의 `filter_log_id`(서버측 필터 로그 레코드 ID)를 확보 —
   차단 시 로그에 "서버측 탐지 내역 조회: … filter_log_id=NNNN" 안내가 함께 출력된다.
2. FabriX 테넌트 관리 콘솔의 필터 로그 메뉴(또는 테넌트 관리자/SDS 운영 문의)에서
   해당 ID로 조회 — 탐지 룰·대상 텍스트가 서버측 기록에 남는다.
3. filter_log_id 미제공 변형(SUCCESS+안내문)이면 서버 조회 불가 —
   `scripts/pii_probe.py`(이등분→ddmin) 재현이 유일한 결정적 방법.

## 도구: 임의 정규식 오프라인 검증 — scripts/pii_regex_check.py

프로젝트 무관(표준 라이브러리만, 파일 하나 복사로 동작). 공개/최신 필터 정규식을
덤프 등 임의 파일에 적용해 걸리는 값을 즉시 확인한다 — **서버 룰이 문서와 다르다고
판정됐을 때(표적 대조 0건), AI팀에서 받은 현행 정규식이나 후보 정규식을 검증하는 용도.**

```
python scripts/pii_regex_check.py "(?<!\d)\d{4}([-\s])\d{4}\1\d{4}\1\d{4}(?!\d)" logs/pii_block/xxx.log
→ 필터링 1 : 1234-1231-5432-4234
  필터링 2 : 1234 2342 4352 6345
```

여러 룰 일괄: `--pattern-file rules.txt` (줄당 `이름 ::: 정규식`, `#` 주석).
옵션: `--line-no`(라인 번호) `--context N`(앞뒤 문맥) `--whole`(파일 전체 매칭)
`--unique`(중복 제거) `--max N`. 종료 코드: 매칭 0(있음)/1(없음)/2(오류) — grep 관례.
검증 완료된 정규식은 이 문서와 `PII_RULES`에 반영한다(동기 갱신 원칙).
* 대응: 진단(`diagnose_blocked_prompt`)이 "[의심]" 티어로 날짜형을 보고하고,
  `SECURITY_PII_SCRUB_SUSPECT_DATES=true` 시 스크럽이 날짜 구분자를 점으로 치환해
  무해화한다(`2026-06-17 02:30:45` → `2026.06.17.02:30:45` — 값·자릿수 보존,
  서버 룰 구분자 클래스 `[- ]` 회피). 오프라인 스캔:
  `python scripts/pii_probe.py <덤프> --scan-only`.

## 8. 카드번호

* 룰 ID: `852`
* 탐지 예시:

  * `1234-5678-7854-1234`
  * `1234 5678 7854 1234`
* 네 자리 숫자 그룹 사이에는 동일한 구분자를 사용해야 한다.

```regex
(?<!\d)\d{4}([-\s])\d{4}\1\d{4}\1\d{4}(?!\d)
```

## 9. 이메일 주소 (2026-08-05 개정)

* 룰 ID: `853`
* 탐지 예시:

  * `abcd123@google.co.kr`
  * `edd123@naver.com`
* 로컬파트 말미가 리터럴 `\n`(역슬래시+n)이면 제외한다(개정본 룩비하인드).
* 필터링 제외 도메인(종전 가이드 유지분 — 개정본에서 해당 위치 절단, 실측 검증 필요):

  * `kbonecloud.com`
  * `kbfg.com`

```regex
[A-Za-z0-9]+(?:[._%+-][A-Za-z0-9]+)*(?<!\\n)@(?!(?:kbonecloud\.com|kbfg\.com)\b)[A-Za-z0-9]+(?:-[A-Za-z0-9]+)*(?:\.[A-Za-z0-9]+(?:-[A-Za-z0-9]+)*)+
```

## 판정 기준

입력 내용에서 위 정규표현식과 일치하는 문자열이 발견되면 다음 PII 유형 중 하나로 판정한다.

* 주민등록번호 / 법인등록번호 / 외국인등록번호 / 운전면허번호 / 여권번호
* 핸드폰번호 / 계좌번호 / 카드번호 / 이메일 주소

정규표현식과 일치하지 않거나 명시된 제외 조건에 해당하면 해당 PII 유형으로 판단하지 않는다.
"이름"은 탐지 대상이지만 처리 정책이 미차단(-)이다.

## 차단 응답 형태 (실측 shape)

**FabriX 커넥터** — 차단 시:

* `status: "FILTER_INVALID"`, `content: "The content was blocked by the filter"`,
  `filter_block_reason: {ko, en, policy_id, message, result_code: "FR-400", filter_log_id}`
* 스트림 모드는 **순차 반환되는 data의 content 각각에 대해** 필터 검사한다.
  차단 청크는 스트림 중간에 FILTER_INVALID로 도착할 수 있다.
* ⚠ **통과 라인에도** `filter_block_reason`이 실린다(`result_code: "FR-200"`,
  `message: "The content was passed"`, `policy_id: null`) — reason 객체의 존재만으로
  차단을 판정하면 안 된다. FR-400/policy_id/"blocked" 문구로만 판정한다
  (코드: `pii_filter._normalize_reasons`).

**APIM** (프로 에이전트 내부 모델 호출 경로) — 차단 시:

```
{'detail': "Error code: 400 - {'error': '민감정보 감지됨: ', 'rule_name': '핸드폰번호', 'catched_text': '010-1234-5678'}"}
```

`rule_name`·`catched_text`가 직접 실리므로 그대로 원인 특정에 사용한다
(코드: `pii_filter._apim_reasons`).
