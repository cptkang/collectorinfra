## D-193. MCP SSE 세션 종료 — 정리는 **연 태스크에서, 각각 독립적으로**

- **결정일**: 2026-08-31 | **상태**: 확정 (정리 경로 수정 완료 · 트리거 경로는 운영 로그 실측 대기) | **번호**: `## D-` 헤더 최댓값 **D-192** · 「변경 이력」 표 최댓값 **D-192** · 「채번 이력」 표 예약(D-105·115·134·158·163~168·176) 대조 → **D-193**(등재 직전 재실측).
- **배경(사용자 보고)**: 은행존(`polestar_b0`·DB2) 복합 질의 실행 중 콘솔에 `mcp.client.sse: Error in sse_reader` → `anyio.BrokenResourceError` 트레이스백이 뜬다.
- **★ 실측이 좁힌 범위 — 이 트레이스백은 "지금 도는 질의"가 아니라 "이미 끝난 세션"의 잔여다**: 로컬 MCP 서버로 경로별 재현(2026-08-31).
  - 정상 `connect → health_check → disconnect` 반복 · `execute_sql` 호출 타임아웃 취소 후 종료 · 호출 대기 중 태스크 취소 → **전부 재현되지 않음**. 즉 상시 경로의 결함이 아니다.
  - `connect()`와 `disconnect()`가 **서로 다른 asyncio Task**에서 일어날 때만 재현. `sse_client`가 여는 anyio task group은 진입/탈출 태스크가 같아야 하고, 어긋나면 `RuntimeError: Attempted to exit cancel scope in a different task than it was entered in`이 난다.
  - 그 `RuntimeError`가 **`disconnect()`의 단일 `try`를 탈출시켜 `sse_context.__aexit__`를 아예 건너뛰게** 만든다 → SSE 연결과 `sse_reader` 태스크가 **좀비로 남고**, 이후 그 세션으로 서버 메시지가 오면 이미 닫힌 `read_stream`에 쓰면서 `BrokenResourceError`가 터진다. 사용자 트레이스백과 프레임까지 일치(`sse.py` `sse_reader` → `memory.py` `send` → `send_nowait`).
- **결정**:
  - **`disconnect()`는 session·sse를 각각 독립 `try`로 닫는다.** 한 try에 묶으면 앞의 실패가 뒤의 정리를 삼킨다 — "독립 신호 수집은 개별 try/except"(Known Mistakes)와 같은 계열이고, 여기서는 그 대가가 **파일 디스크립터·태스크 누수**다.
  - **취소는 삼키지 않는다.** session 종료가 `CancelledError`로 끊겨도 sse는 마저 닫고, 취소는 정리 후 재전파한다.
  - **`connect()`가 취소되면 반쯤 열린 컨텍스트를 그 자리에서 정리한다.** 종전에는 `except asyncio.TimeoutError`만 정리했고 `CancelledError`는 `BaseException`이라 어디에도 걸리지 않아 상위 `get_db_client`의 `finally`로 넘어갔다 — **정리 태스크가 갈리는 바로 그 조건**이다. connect를 연 태스크에서 닫고 취소를 재전파한다.
- **대안 기각**: **`asyncio.shield`로 정리 완주 보장** — shield는 정리를 별도 태스크로 옮기므로 cancel scope 위반을 **오히려 유발**한다 · **MCP 세션을 전용 태스크에 가두는 구조 변경**(근본책) — 클라이언트 수명 모델을 갈아엎는 별건이고, 현 결함은 정리 경로 두 곳으로 막힌다 · **에러 로그 억제** — 증상만 가리고 연결 누수는 남는다.
- **주의**: ①**이 트레이스백은 진행 중 질의를 직접 실패시키지 않는다** — 깨지는 것은 이미 `disconnect()`된 세션이고, 질의마다 클라이언트를 새로 만든다. **화면 실측(2026-08-31 17:29)이 이를 뒷받침한다**: 같은 질의가 오류 메시지 없이 *"작업 실행 [대기]"* 상태로 **35분간 매달려 있었다** — 세션이 깨져 실패한 모습이 아니라 **끊기지 않은** 모습이다. 화면이 멈춘 원인은 이 결정의 범위 밖이며, `/query/stream`이 **이벤트 간 타임아웃만 갖고 전체 실행 타임아웃이 없는 것**(비스트리밍 `/query`·스트리밍 폴백 `ainvoke` 경로에는 있다 — `query.py:1198` vs `:1021`·`:1353`)으로 따로 추적 중이다. ②실제 운영에서 두 호출의 태스크가 갈리는 지점은 **아직 특정하지 못했다** — 재현은 조건을 인위적으로 만든 것이다. 판별 신호는 `MCP 서버 연결 종료 중 에러: Attempted to exit cancel scope…`(수정 후에는 `MCP session 컨텍스트 종료 실패: RuntimeError: …`) warning의 유무다. ③`mcp_call_timeout`은 결정 기록(D-014)의 60s가 아니라 **운영 `.env` 실측 600s**다 — 60s 전제로 타임아웃을 추정하면 틀린다.
