## D-221. 재측정 실험 전제조건 — **분할 실행(`--segment`·`--resume-failed`) · LLM 비용 측정 불가의 고정 고지 · 사다리 강등 경고 · 장비명 few-shot 4종 교정** (plans/94 §15.3·§17 W1-c · plans/98 CU-17 · D-218 후속)

- **결정일**: 2026-09-16 | **상태**: 확정 (구현 완료 · W1 전건 랜딩) | **번호**: `## D-` 헤더 최댓값 **D-220** · 「변경 이력」 표 최댓값 **D-220** · 「채번 이력」 표 예약(D-105·115·134·158·163~168·176·195·210·212·214·**219**=`plans/97`) 대조 → **D-221**(등재 직전 재실측 2026-09-16)
- **배경**: 사용자 지시 *"추가 실험을 진행하기 위한 구현계획까지 구현을 진행하라."* 다음 실험은 전 시나리오 재측정(W2)이고, 그것이 **성립하려면** 세 가지가 먼저 필요하다 — ①8시간대 run 의 실패 반경을 줄일 분할 수단 ②직전 run 의 무효 103턴을 복구할 경로 ③측정하지 못한 축을 "0"이 아니라 "못 쟀다"로 읽히게 하는 고지.
- **결정**: ①**`--segment N`** — 시나리오 N건마다 **토큰만** 재발급. 경계는 **시나리오 경계**이고 서버 재기동·체크포인트 분리·`raw.jsonl` 분할·중간 teardown 을 하지 않는다(§15.4 보존 5가지). cold 묶음은 `_execution_order` 정렬 덕에 자동으로 첫 세그먼트에 남는다. **토큰을 쓰지 않는 프로파일(모의·인증 off)은 갱신을 시도하지 않는다** — 세그먼트마다 나는 허위 경고가 진짜 경고를 덮는다 ②**`--resume-failed RUN_ID`** — 원본을 **읽기만** 하고 새 run_id 로 무효·오류 **시나리오**를 다시 돈다(`meta.rerun_of`·`meta.rerun_selection`). 판정은 **`row_is_invalid`** 로 한다 ③**세그먼트 크기 기준은 시나리오 수**(예상 소요 아님) ④**O-b 는 "불가"로 확정** — `llm_calls`·`tokens` 는 감사 로그에서 가져올 수 없고, 그 사유를 `bottleneck.md` 에 고정 문구로 싣는다 ⑤**O-c** — 정본 단(`deep_agent`)이 아닌 단으로 측정됐으면 리포트 **최상단 경고**. **미관측(`tier` 없음·`mock`)은 강등으로 세지 않는다** ⑥**CU-17** — `"특정 서버의 CPU 리소스를 조회해줘"` few-shot 이 **네 프로필 전부** `WHERE parent.hostname = '서버명'` 이던 것을 `parent.name` 으로(b0 는 OR 3분기) 교정.
- **근거**:
  - **X-2 의 원래 명분은 이미 소진됐다** — `--segment` 는 "세그먼트마다 토큰을 새로 잡는 것"이 목적이었는데 **D-218 T-b(수명 80% 경과 시 턴 경계 선제 갱신)가 시간 기준으로 이미 막는다.** 남은 값은 실패 반경 축소·진행 가시성·명시적 재개점이라 **여전히 유용하지만 만료 방어 수단은 아니다.** 그래서 크기 기준도 시간이 아니라 개수다.
  - **세그먼트 크기를 소요로 자르면 거짓 정밀도가 된다** — 러너가 가진 유일한 추정은 `estimate()` 의 상한이고 재료는 **군 목표치**와 `ASSUMED_LLM_CALLS_PER_TURN`(가정치)다. 직전 run 은 **16개 군 전건이 목표 미달**이라 그 추정은 체계적으로 틀린다. 대신 **군별 턴당 소요 편차(R1 181초 ~ R2 73초 = 2.5배)** 를 실행 가이드에 실어, 균등 소요가 필요하면 `--group` 을 쓰도록 안내한다.
  - **X-3 이 `row_is_invalid` 를 써야 하는 이유** — run 20260915-131903 의 103턴은 T-c 이전 적재라 `func_verdict` 가 `error`/`fail` 이다. `invalid` 만 보면 **복구 대상이 통째로 0건**이 되어 기능이 무의미해진다. 그 실물 형태를 재현한 픽스처로 검증했다(구 형식 3건 + 신 형식 1건 + 비인증 오류 1건 → 5건 선택, 성공·불합격 제외).
  - **X-3 이 턴이 아니라 시나리오 단위인 이유** — 새 run 은 `raw.jsonl` 이 비어 재개 스킵이 걸리지 않고, 멀티턴은 1턴부터 새 thread 로 가야 승계가 성립한다. 계획서의 *"무효·오류 **턴만** 돈다"* 는 새 run 에서는 성립하지 않는 표현이다.
  - **O-b 가 불가인 근거 네 지점**(실측) — ①`audit_logger` 이벤트 5종(`query_execution`·`user_request`·`drm_decrypt`·`silence_change`·`host_investigation`)에 LLM 이 없다 ②`src/llm.py` 가 `usage_metadata` 를 수집하지 않는다 ③`AgentState.llm_calls`(`state.py:58`)는 **선언만 있고 기록부가 0곳**이며 초기화도 없다 ④`done` 페이로드에 호출 수·토큰 키가 없다. 제품 관측성 갭이고 소유는 `plans/56` 이다.
  - **CU-17** — CU-1 이 강제 지시를 넣어도 **같은 프로필의 few-shot 이 반대를 보이면 그쪽이 이긴다**(`CLAUDE.md` 「프롬프트 강제가 few-shot 과 경쟁하면 반복 실패」). 질문이 *"특정 서버"* 인데 필터가 `hostname` 이고 플레이스홀더가 `'서버명'` 이라, P-1 을 네 프로필에서 동시에 재생산하는 교본이었다.
- **대안(기각)**: 세그먼트를 예상 소요로 자르기(위 근거 — 추정이 틀린다) · 세그먼트마다 서버 재기동(§3.5 전제 파괴 · cold 근사 무효) · `--resume-failed` 가 원본 run 을 덮어쓰기(무엇이 무효였는지가 사라져 복구 자체를 검증할 수 없다) · `func_verdict == "invalid"` 로만 복구 대상 판정(이번 사고의 103턴이 빠진다) · `llm_calls` 를 스트림 이벤트로 추정해 채우기(추정치를 넣으면 리포트가 "쟀다"고 말한다) · 미관측 `tier` 를 강등으로 경고(상시 경고는 읽히지 않는다)
