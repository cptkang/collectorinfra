- **배경**: `plans/114` §2.3 실측 — 폐쇄망 run `20260922-112010`에서 타임아웃 95턴 중 **55턴이 SQL 실행을 끝낸 뒤** 서술(LLM) 단계에서 죽었고, 그중 **41턴은 답변 앞부분(p50 588자)을 이미 스트리밍한 뒤**였다. 전체 경과 상한 가드가 오류만 내고 상태에 있는 행을 쓰지 않았다. 사용자는 데이터를 보다가 오류를 받았고, 조회 비용(A-01은 757건 48초)은 전부 버려졌다.
- **결정**:
  ① **행이 있으면 오류 대신 답한다** — 상한 도달 시 체크포인트(스트림은 추적분 우선)에서 행을 건져 **LLM 없이 결정적 표**(상위 20행)로 응답한다. 첫 줄에 *"서술 생성이 시간 상한을 넘어 표로 대신합니다"* 사유를 싣고(침묵적 강등 금지), 전체 행은 기존 CSV 내려받기로 준다. **행이 없으면 종전 504·오류 이벤트 그대로**다.
  ② **상태값은 `partial`** — `completed`로 두면 기록기(D-248 `_turn_status`)와 하네스가 "서술이 빠진 답"을 구별할 수 없다. 응답 모델과 스트림 `done`이 같은 값을 싣는다.
  ③ **스트림은 `done`으로 낸다** — 오류 이벤트는 `TurnRecorder.stream`이 기록하지 않아 그 턴이 이력에서 사라진다.
  ④ **진입점 4곳 대칭**(비스트림·스트림 × 텍스트·파일 · D-066). 파일 경로도 같다 — 양식을 못 채웠어도 조회한 행은 준다.
  ⑤ **사다리 단 대칭** — 3단·단일 경로는 `query_results`→`organized_data.rows`, 2단은 `task_results`의 **마지막으로 행을 낸 작업**을 쓰고 몇 건 중 어느 것인지 본문에 밝힌다(작업마다 컬럼이 달라 이어 붙이면 표가 깨진다).
  ⑥ **판정은 `timeout`과 같은 제거 사유**(D-241 사유 3종 유지 · 어휘를 늘리지 않는다). 그대로 두면 ⓐ`status: completed`를 기대하는 카탈로그 124턴이 전부 기능 불합격이고 ⓑ제품이 빨라지지 않았는데 타임아웃률만 내려가 관문(`plans/114` M-2 ②)이 은폐된다. 러너 행 `status` 칸이 정본이고 리포트·벤치 두 규칙이 대칭으로 읽는다.
