- **배경(사용자 지시)**: *"웹 UI의 LLM 응답 출력창에서 응답시간이 오래 걸릴 경우 커서만 깜박이고 있어 진행 중인지 중단됐는지 알 수 없다 — gemini/chatgpt처럼 처리 진행 사항을 커서 아래에 표현하라"* + *"88번 계획을 참조하여 복합 질의 UI 개선도 고려하라"*.
- **★ 실측이 드러낸 것 — 위젯 하나가 아니라 세 겹 + 계약 부재**: ①`_known_nodes`(SSE 화이트리스트)에 사다리 1단 정본 `deep_agent`가 없어 운영 경로(`.env` `ENABLE_DEEPAGENTS_PACKAGE=true`)에서 `field_mapper` 이후 최종 토큰까지 이벤트 0건 ②에이전트 내부 도구 루프·서브에이전트 핸들러는 노드가 아니라 원래 침묵 ③프론트가 SSE 연결 직후 단계 칩 말풍선을 제거해(`removeProcessingMessage` → `createStreamingMessage`) 이후 `updateProcessingStage`가 대상 DOM 없이 무동작 ④살아 있음 신호가 없어 무이벤트 상한(`.env` `API_QUERY_TIMEOUT=240`, 코드 기본값 60 아님 — D-193)까지 "진행 중"과 "죽음"이 구별되지 않음. 복합 질의(`plans/88`)는 2단 작업 목록이 **전 레벨 종료 후 1회**만 오고, 88이 도입한 `status="skipped"`는 패널에서 "대기"로 오표기될 상태였다.
- **결정**:
  1. **SSE 이벤트 2종 추가**(기존 6종 불변): `heartbeat{elapsed_ms,last_activity_ms}`(무이벤트 구간 주기 발행) · `progress{kind:"tool"|"step"|"task", name, phase, node, timestamp_ms, label?, task?}`(`on_tool_start/end`·`on_custom_event` 변환). 서버는 원시 이름만 내고 라벨은 클라이언트가 붙인다. 구 클라이언트는 미지 type을 무시함을 실측.
  2. **큐 기반 제너레이터** `_graph_event_stream`(텍스트·파일 SSE 2곳 공통 헬퍼): 생산자 태스크 + `asyncio.Queue`. **`wait_for(__anext__)` 재호출 금지**(취소된 `__anext__`는 비동기 제너레이터를 깨뜨린다). 무이벤트 연속 시간 ≥ `effective_timeout`이면 기존 `error` 문구 후 종료 — D-066 후속의 의미 보존. 생산자 취소는 `finally`에서 걸되 완료 대기는 `_PRODUCER_CANCEL_GRACE_SEC`(1s)로 유한 — **원격 D-198 F2(검출·취소 분리)의 취지와 정합**. 원격의 `_next_event_or_timeout` 헬퍼는 `test_stream_guard.py`가 임포트하므로 정의 유지(호출부 없음).
  3. **화이트리스트 보정** `_STREAM_KNOWN_NODES`(모듈 상수 · 2곳 공용): `deep_agent`·`fault_diagnosis`·`cache_management` 추가 — D-039 화이트리스트 결정의 누락 정정(플래그 무관).
  4. **복합 질의 단계 이벤트** `src/orchestration/task_progress.py::emit_task_progress` — 2단 레벨 루프(시작·종료·게이트 건너뜀)와 1단 `_run_subagent_tool`(시작·게이트 건너뜀·종료)이 **같은 함수**를 부른다(대칭은 소스 grep 테스트로 고정). 페이로드 필드명은 D-203 `DependencyVerdict`/`skip_result`와 **동일**(`status·reason·scope_col·scope_size·truncated_count`) — 실행 중 표시(89)와 사후 경과 블록(88 R-5)이 같은 값에서 나온다는 불변식. 부모 run이 없으면(단위 테스트·CLI) `RuntimeError`를 삼킨다. `deep_agent` 재개(D-093)·최종 합성 직전에 `step` 마일스톤.
  5. **웹 UI 상태 영역** `#streamingStatus`(커서 바로 아래, `role=status aria-live=polite`): 활동 문구 + 클라이언트 1s 경과 타이머 + 스피너. 상태 기계 `waiting → active(node/tool/task) → streaming(첫 token) → done | stalled(무신호 15s = 하트비트 5s×3, 하트비트 수신 시 복귀) | interrupted/error(영역 제거)`. 단계 칩은 지우지 않고 **이관**(`createStreamingMessage` → `removeProcessingMessage` 순서 역전), `agent` 칩은 1·2단 노드에서만 **지연 생성**(3·4단 UI 불변). 문구 우선순위 task > tool > node. 완료 시 **한 줄 요약으로 접음**("완료 · N단계 · 12.3s", 단계 목록은 클릭 펼침 — 본문의 순차 처리 경과 블록이 정본이라 중복 회피). 오른쪽 패널에는 도구·단계 하위 행(`node_complete` 재렌더 시 보존), `renderTaskList`에 `reason`/절단 표기(`reason`이 있으면 상태값과 무관하게 "건너뜀" 우선).
  6. **설정** `API_SSE_PROGRESS_EVENTS`(**기본 on** — `plans/80` §5.4-③의 명시 예외: 부가 이벤트·구 클라 무시·off면 증상이 운영에 그대로 남음, config 주석에 근거) · `API_SSE_HEARTBEAT_INTERVAL_SEC=5`(0이면 없음). off면 기존 이벤트 바이트 열 동일(테스트 고정).
