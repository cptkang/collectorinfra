## D-340. 워커 LLM에 `vllm` provider 추가 — 사내 vLLM을 `ChatOpenAI` 그대로 부른다 · 워커 비과금 집합에 `vllm` 편입 (D-222 ③ 부분 개정)

> **번호 변경(2026-10-19)**: 구 **D-337** — `origin/main` 병합 시 원격 D-337(구조 리팩터 규약)·D-338(인증 저장소 fail-closed)·D-339(로그 비밀값 가림)와 겹쳐 최댓값+1로 재채번했다.

- **결정일**: 2026-10-16 | **상태**: 확정 · 구현(커밋 없음 · 기본 off = `LLM_PROVIDER` 기본값 `ollama` 그대로)
- **배경**: vLLM은 오케스트레이터 평면(`ORCHESTRATOR_PROVIDER`)에서만 고를 수 있었고, 워커(`LLM_PROVIDER`)는 `ollama`·`fabrix`·`gemini`·`mlx`뿐이었다. API 규격이 같은 `mlx`에 vLLM 주소를 넣는 우회는 가능하지만, mlx 경로는 로컬 MLX를 전제로 한 처리(구조화 출력 `MD_JSON` 고정 · 모델 무관 thinking 토글 · `max_completion_tokens` 상시 전송 · 루프백 전제 preflight · 로그 라벨 MLX)를 싣고 있어 운영 용도로 맞지 않는다(D-222 대안 기각 「위장」과 같은 이유). 사용자 지시: *"응 워커에 vllm provider 추가해"*(2026-10-16).
- **결정**:
  ① `LLMConfig.provider`에 `vllm` 추가. 전용 필드 `LLM_VLLM_{BASE_URL,MODEL,API_KEY,TIMEOUT(300),VERIFY_SSL(true),ENABLE_THINKING(false)}` — provider가 `vllm`이 아니면 읽히지 않는다. 오케스트레이터 vLLM(`ORCHESTRATOR_*`)과는 별개 값이다(같은 서버여도 양쪽에 적는다)
  ② 팩토리 `_create_vllm`은 **`ChatOpenAI` 그대로**(서브클래스 아님) — 구조화 출력이 `MODE_TOOLS`(D-169)로 간다. 오케스트레이터 vLLM 경로와 같은 규칙: Qwen 이름 가드로만 `chat_template_kwargs.enable_thinking` 부착(D-042) · `verify_ssl=false`면 httpx 검증 해제(D-060) · `max_retries=0`(D-268 부기) · `max_tokens` 미전송. 오케스트레이터와 달리 `stream_chunk_timeout`=`LLM_VLLM_TIMEOUT`(워커는 SSE 토큰 스트리밍을 쓴다 — D-222 부기 결함 A)
  ③ `LLM_VLLM_BASE_URL`·`LLM_VLLM_MODEL` 중 하나라도 비면 `ValueError`(그래프 조립에서 기동 실패). `LLM_MODEL`로 조용히 폴백하지 않는다
  ④ **워커 비과금 집합 {`fabrix`,`ollama`,`mlx`,`vllm`}** — 오케스트레이터 `vllm`과 같은 취급(사내 서빙 · 외부 송신 0). 정의는 종전대로 `scripts/scenario/preflight.py` `WORKER_INTERNAL_PROVIDERS` 1곳
- **행동 변화(명시)**: `LLM_PROVIDER=vllm`은 종전 config 검증 실패였다. 하네스 과금 판정 `external_planes("vllm", …)`은 종전 외부(`LLM_PROVIDER=vllm`)였고 이제 비과금이다 — 종전 단언 `test_과금_판정의_단일_정의[vllm-vllm]`을 `[]`로 갱신했다.
- **근거**: mlx 경로 차이 실측(`src/llm.py` `_create_mlx` · `src/clients/instructor_adapter.py` `_NATIVE_TOOL_CALLING_CLASSES`) · instructor TOOLS 모드는 강제 함수 지정(named `tool_choice`)이라 vLLM 기본 기동으로 동작한다 · 구조화 출력은 opt-in(`STRUCTURED_OUTPUT_BACKEND` 기본 `none`)이고 실패 시 `None` → 기존 경로 폴백.
- **대안(기각)**: `LLM_PROVIDER=mlx` + vLLM 주소(위 배경) · 오케스트레이터 설정(`ORCHESTRATOR_*`) 공유(평면별로 다른 서버·모델을 쓸 수 없고, 1단 off 운영에서도 오케스트레이터 키를 채워야 한다) · `LLM_MODEL` 재사용(기본값 `llama3.1:8b`가 조용히 실려 404)
- **구현**: `src/config/llm.py`(Literal + 필드 6 · 2026-10-19 config 패키지화 병합으로 이동) · `src/llm.py`(`_create_vllm`) · `src/schema_cache/admin_base.py`(`provider_info` vllm 모델 · 병합으로 이동) · `scripts/scenario/preflight.py`(집합) · 문구 `scripts/scenario/__main__.py`·`scripts/apm_bench/driver.py`·`docs/35_demo_script_guide.md` · `src/api/settings_catalog.py`(`RELOADABLE_KEYS` +5 · 시크릿 `LLM_VLLM_API_KEY`) · `config/settings_help/llm.yaml`(provider 선택지 + 6항목) · `.env.example`·`.encenv.example` · `docs/03_setup_guide.md` §7.5 · `CLAUDE.md`·`AGENTS.md` Tech Stack · 관리자 매뉴얼 A-55 · 테스트 `tests/test_llm_vllm.py` 신규 14건, `test_settings_catalog.py`(필드 420→426 · enum · 시크릿)·`test_preflight.py` 갱신
- **주의**: ①실 vLLM 서버 호출은 하지 않았다(로컬에 vLLM 없음) — 요청 본문은 httpx MockTransport로만 검증. 내부망 첫 기동 때 `GET /v1/models`의 `id`와 `LLM_VLLM_MODEL` 일치, 대표 질의 1건을 확인한다 ②`tool_choice=auto`를 쓰는 경로(`src/nodes/column_deriver.py` `bind_tools`)는 서버가 `--enable-auto-tool-choice --tool-call-parser <계열>`로 떠 있어야 한다 — 아니면 그 노드가 폴백으로 강등된다 ③`finish_reason=length` 경고는 mlx 경로만 있다(D-222 주의 ① 갭이 vllm 워커에도 그대로) ④`WORKER_PROVIDER_OVERRIDE`(테스트 전용)에는 넣지 않았다 ⑤preflight·벤치의 MLX 전용 점검(도달·1토큰 생성)은 vllm 워커에 적용되지 않는다
