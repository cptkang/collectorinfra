## D-187. 응답 표 렌더 안전망(GFM 구분선 정규화) + 양식 저장 값 패널(항목별 삭제 버튼)
- **결정일**: 2026-08-26 | **상태**: 구현 완료(개발망 테스트 통과) — 폐쇄망 실기 검증 대기
- **배경(라이브 실측 2026-08-26, 금감원 CPU 양식)**: ①응답 표가 가끔 마크다운 원문(`| 비고 | … |` / `|-----|`)으로 노출. 프론트는 marked.js GFM이며 **구분선 행 셀 수 ≠ 헤더 셀 수면 표로 인식하지 않는다** — 19열 양식에서 LLM이 셀 수를 자주 틀림. ②같은 표의 칼럼 순서가 뒤섞임(평균 M+5, M+1, Peak M …) — 행 dict 키 순서(=SQL SELECT=양식 헤더 순)는 정상이고 엑셀도 정상, LLM이 표 작성 시 재배열. ③'?' 조회로 저장 값은 보이지만 삭제는 텍스트 명령("<필드명> 기억 삭제")뿐 — 복합 필드명 입력 부담, FIX-23이 기록한 "커버리지 밖 문구에서 LLM이 삭제했다고 환각" 위험.
- **결정**: ①`output_generator._normalize_markdown_tables` — 표 블록(2행이 구분선인 블록만, 코드 펜스 내부 제외)의 구분선을 헤더 셀 수로 재생성하고 본문 행은 부족분 패딩·초과분 절단(GFM이 초과 셀을 버리는 동작과 동일). **내용(누락 칼럼·순서)은 고치지 않는다** — 렌더만 보장. `_generate_text_response` 반환 직전(연도 가드 앞) 전 경로 적용. ②칼럼 순서(버그 ②)는 **이번 범위에서 제외** — 사전 검토에서 "폼필 표 결정적 생성(B)"은 정상 런에서도 스트리밍·강조·경로 간 일관성을 잃어 비용 대비 과하다고 판단(사용자 확인). 대안 "검증 후에만 교체"(LLM 표 헤더가 기대 칼럼과 집합·순서 일치하면 유지, 아니면 그 블록만 결정적 표로 교체)를 후보로 남긴다 — 발생 빈도를 로그로 잰 뒤 결정. ③저장 값 패널: `intent_planner`의 '?'/조회 단락이 `form_memory_panel {signature, display_name, entries:[{field,label,action,value}]}`(단일 출처 `build_form_memory_panel`)를 task에 동봉 → `subagents` direct 반환 → `result_aggregator` 단일 task 승격 → API 응답 필드(`QueryResponse.form_memory_panel`, SSE done 포함, 텍스트·파일 라우트 10곳) → 프론트 `renderFormMemoryPanel`(체크박스 + [선택 삭제]/[전체 삭제·confirm]) → **`form_memory_delete {signature, fields|null, all}` 구조화 요청** → 라우트 `_form_memory_delete_or_none`이 **파이프라인·LLM 없이** `delete_form_memory_entries` 호출(존 역질문 pre-gate와 같은 위치, /query·/query/stream 대칭) → 남은 항목으로 패널 재구성(진부화 방지), 0건이면 "이미 삭제됨" 안내. **signature는 세션 `last_form_signature`와 일치할 때만 수행**(임의 시그니처로 타 양식 이력 삭제 차단).
- **트레이드오프(사전 검토)**: ①정규화는 렌더 실패만 막고 빠진 칼럼은 그대로(A-1), 셀이 밀린 행의 정렬 왜곡은 GFM 렌더와 동일(A-3), 스트리밍 중간 노출은 최종 보정에서만 회복(A-4). ③패널은 진부화(다른 턴 삭제 후 옛 패널 재사용)를 "0건 안내"로 흡수, 전체 삭제는 confirm. 이력 저장소가 사용자 스코프가 아닌 양식 시그니처 스코프(공용)라는 기존 설계는 불변 — 버튼이 삭제를 쉽게 하는 만큼 추후 사용자 스코프 도입 시 재검토. 텍스트 삭제 명령은 그대로 유지(패널은 추가 경로).
