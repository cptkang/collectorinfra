## D-194. FabriX 하이퍼파라미터 프로파일 — KBGenAI `llmConfig` 전송 + 호출 목적별 2단 프로파일

- **결정일**: 2026-08-31 | **상태**: 확정 (구현 완료 · **폐쇄망 실측 완료 2026-08-31**) | **번호**: 원 채번 **D-189**(당시 등재 최댓값 D-188 기준) → **2026-09-01 `multiintent` 병합 시 D-194 재부여** — 원격이 같은 날 D-189를 L3 접근 경로 확정(D-117 ① 개정)에 선점.
- **배경(사용자 지시)**: 팀장 분석 — FabriX API 호출에 temperature·top_k 등 하이퍼파라미터 조정 기능이 없다. 코드 실측으로 확정: 운영 경로 `KBGenAIChat._get_payload`는 `modelId/contents/isStream/…/systemPrompt`만 전송(샘플링 파라미터 필드 자체가 없어 **FabriX 서버 기본값**으로 동작), 폴백 `FabriXAPIClient`는 temperature 0.0 하드코딩·설정 수단 없음. FabriX 가이드에서 body `"llmConfig": {"temperature": <float>, "top_k": <int>, "top_p": <float>}` 규약 확보. 요구: **SQL 생성은 낮게, 사용자 응답 합성은 높게** — 호출 지점별 차등.
- **결정**:
  - **2단 프로파일**: `LLM_FABRIX_LLM_CONFIG`(결정적 경로 기본 — SQL 생성·분류 등 전 중간 호출) / `LLM_FABRIX_ANSWER_LLM_CONFIG`(최종 사용자 응답 합성 전용, 빈 값이면 기본 프로파일 폴백). `create_llm(config, purpose="deterministic"|"answer")`로 선택하며 기본값이 deterministic이라 **기존 호출처 ~25곳 무변경**.
  - **answer 적용 지점 = D-009 `USER_RESPONSE_TAG` 부여 3곳과 동일 경계**: `output_generator`(단일 DB) · `result_aggregator` 최종 합성(멀티 DB) · `general_inference`. **D-062 중간 합성(`stream_user_response=False`)은 최종 합성의 재료이므로 결정적 프로파일 유지**(output_generator에서 플래그로 분기).
  - **미설정 시 `llmConfig` 필드 자체를 생략** — D-194 이전 페이로드와 바이트 동일, 서버 기본 동작 보존(옵트인 배포 가능).
  - **config 필드는 JSON 객체 "문자열"**(dict 타입 아님): dict 필드는 `.env`의 빈 값(`KEY=`)이 config 로드 전체를 깨뜨린다(폐쇄망 `.env` 관례상 빈 키 상존). 대신 `field_validator`가 기동 시점에 JSON 유효성을 검증해 오탈자를 명확히 실패시킨다(침묵 폴백 금지). 설정 카탈로그(D-129)에도 string 타입으로 안전 직렬화.
  - 폴백 `FabriXAPIClient`(OpenAI 호환)는 `llmConfig`가 KBGenAI 전용 규약이므로 프로파일의 **temperature만 매핑**.
  - `purpose`는 str — 향후 노드 단위 프로파일 확장(예: "sql") 시 시그니처 변경 없이 키만 추가.
- **대안 기각**: **dict 타입 config 필드** — 빈 env 값 파손 리스크(상기) · **per-call `.bind(llm_config=…)`** — `_generate/_agenerate/_stream/_astream` 4경로 kwargs 배선 + 노드 호출부 전파가 과대, 생성 시점 주입으로 충분 · **프로파일 dict 일반화**(`LLM_FABRIX_PROFILES`) — 현 요구는 2단으로 충분, purpose str로 확장 여지만 유지.
- **폐쇄망 실측(2026-08-31, 사용자 수행)**: ①에이전트 경유 일반·인프라·폼필 질의 각 1건 — llmConfig 전송 상태에서 **무오류 정상 응답**(수용 확인, 400/EL1008E류 거부 없음). ②기반 API 직접 호출로 temperature 0.0 vs 1.0 반복 비교 — 사람 체감 차이는 크지 않았으나 **LLM 판정으로는 변동성 차이 뚜렷** → 적용으로 판정. top_k/top_p 개별 실측은 미수행(temperature와 같은 llmConfig 필드라 동일 규약 추정).
- **주의**: ①응답 temperature 상승은 표 형식·수치 변동성을 키운다 — D-187 표 정규화·D-186 연도 가드가 후단에 있으나 **0.3~0.5에서 시작 권장**. ②알람 워커는 기동 캡처 config라 LLM_* 리로드 비대칭(기존 규약 그대로). ③적용 판정의 근거가 사람 체감이 아닌 LLM 판정이므로, 운영 중 응답 다양성이 기대와 다르면 동일 프롬프트 반복 비교(§실측 프로토콜)를 재수행할 것.
- **검증**: 신규 `tests/test_clients/test_fabrix_llm_config.py` **16건**(validator 유효/오탈자/비객체 · purpose→프로파일 해석·폴백 · create_llm 배선(KBGenAI/OpenAI 호환) · 페이로드 llmConfig 포함/**미설정 시 키 부재**/스트림/bind_tools 보존). 갱신: `test_llm_gemini.py` 3건(시그니처·`purpose="deterministic"` 전달) · 설정 카탈로그 카운터 309→**311**. `tests/test_nodes`+`test_orchestration` **424 passed** · `arch_check --ci` exit 0 · 기준선 대비 신규 실패 0(worktree 실측 — instructor_adapter 7건·`.env` 부재 3건·gemini 패키지 1건은 사전 존재).
