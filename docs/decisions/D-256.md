## D-256. 알람 **AI 분석이 실패해도 알람을 삼키지 않는다** — 원문 알람과 결정적 값으로 결과를 만들어 발송 판단·통보·결정 기록을 이어 간다 (사용자 지시 2026-09-27 · `plans/116` §11.8.3 ⑦ · D-035 취지 복구)

- **결정일**: 2026-09-27 | **상태**: 확정·구현(사용자 지시 — *"오류를 수정하라."*) | **번호**: 등재 직전 `## D-` 헤더(최대 D-255)·변경 이력 표·안내 줄(「다음 D-256」) 확인
- **결함**: 분석 LLM 호출·JSON 해석·필수 키 누락이 실패하면 `alarm_analyzer_node`가 `{"error": …}`만 돌려, 발송 판단(`notification_gate`)과 통보(`alarm_notifier`)가 빈 결과로 끝났다. **심각도 3을 포함해** 결정·통보·결정 기록이 없고 dead-letter에도 가지 않았으며(정상 종료로 ACK), 재발 거르기가 분석 전에 창을 열어 같은 알람의 반복도 최대 4시간(기본값) 판단 없이 걸러졌다. 게이트 켬·끔 모두 해당. 남는 흔적은 로그 한 줄뿐이었다. 이 동작을 정한 결정·고정 테스트는 없었다(매뉴얼 작성 중 검증 에이전트 2개가 코드로 확정 · 작성자가 세 곳 재확인).
- **결정**:
  ① 분석이 실패하면 **원문 알람으로 만든 결과**(`_fallback_result`)를 돌려준다 — 심각도 라벨은 이벤트 값, 요약 「AI 분석에 실패해 원문 알람으로 판단했습니다: 알람명 (서버 · 자원)」, 추정 원인에는 **예외 종류만**(예외 문구에 접속 정보가 섞일 수 있다 — 상세는 로그), `result.error = "analysis_failed: <예외 종류>"`. LLM 산출 필드(패턴 해석·일상 반복·액션가능성·LLM 상향 후보)는 비워 정책 계층이 「판단 없음」으로 다룬다.
  ② **결정적 상향은 유지** — 시그니처 스캔·동적 baseline 상향을 공용 함수(`_apply_severity_boost`)로 분리해 실패 경로에서도 적용한다(LLM 없이 계산되는 값이다).
  ③ 발송 판단은 평소대로 결정하고, 결정 기록 `stage_evidence.analysis = "AI 분석 실패 — 원문 알람으로 판단"`을 남긴다(관제 화면 결정 추적에서 구별).
  ④ 범위 밖 그대로: LLM 클라이언트 생성·프롬프트 조립 단계 예외는 분석 호출 전이라 종전대로 「알람 처리 실패」 로그 + `alarm:dead` 보관.
- **플래그**: 두지 않는다 — 결함 수정이며 새 기능이 아니다(`plans/80` §5.4-③ 「기본 off」 원칙의 대상 아님). 성공 경로의 출력은 비트 동일하다.
- **검증**: 회귀 테스트 `noise_gate/tests/test_analyzer_failure_fallback.py` 4건(예외·비 JSON 응답 폴백 · 실패 시 시그니처 상향 유지 · 유지보수 중 심각도 3 → PAGE + 결정 기록 `analysis`) — **수정 전 코드에서 4건 모두 실패, 수정 후 통과**. `noise_gate/tests` 전체 1,361 통과(남은 실패 2건은 수정 전부터 있던 프로세스 API 클라이언트 테스트 · redis·prometheus_client를 임시로 얹고 UTF-8 모드로 실행) · `arch_check --ci`·`overfit_check --ci` exit 0.
- **매뉴얼(D-255)**: 사용자 U-44·U-45, 관리자 A-44·A-59·A-60·A-61의 옛 동작 문장 18곳을 새 동작으로 고쳤다(`plans/116` §11.7).
- **대안**: (a) 심각도 3이면 분석 없이 바로 PAGE — 심각도 1·2 알람은 여전히 삼켜져 기각. (b) 예외를 다시 던져 dead-letter로 — 통보가 여전히 없고 재처리 도구도 없어 기각.
