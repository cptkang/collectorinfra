## D-357. MCP 서버 동시성 — 다중 프로세스(다중 워커) 미채택 · DB2 연결 풀 기본 on · 소스별 프로세스 분리는 측정 판정 뒤

- **결정일**: 2026-11-02 | **상태**: 확정 · 구현 전(`plans/206`) | **번호**: 등재 직전 `ls docs/decisions/` 최댓값 D-356 확인
- **배경**: 사용자 제기(2026-11-02) *"mcp agent를 멀티 코어 프로세스로 구현하여 동시성을 높일 수 있는지 검토하라."* 실측(`plans/206` §1): `mcp_server`는 프로세스 1개·루프 1개지만 DB 대기는 이미 동시(asyncpg·aiomysql 풀 · DB2 `to_thread`)이고, 요청 1건의 루프 CPU는 최악 49ms(10,000행 정규화+직렬화)로 APM 게이트웨이(D-356 · 응답 1건 600ms)보다 한 자릿수 이상 작다. 동시 수를 묶는 것은 D-347 ③ 소스별 상한(풀 크기 5 · DB2 4)이다. DB2만 요청마다 `ibm_db.connect`한다.
- **결정**:
  ① **다중 워커·stateless 전환 미채택** — SSE 세션이 프로세스 메모리라 다중 워커에서 `POST /messages`가 끊기고, 소스별 상한이 워커 수만큼 곱해져 조회 대상 부하가 N배가 된다(D-347 ③ 위반 · 상한을 나누면 이득 0). stateless streamable-http(mcp 1.29.1 지원 실측)는 호출자 3곳·HolmesGPT 설정 전환 비용에 상한 곱셈 문제가 그대로라 같은 사유로 미채택.
  ② **DB2 연결 풀 · 기본 on** — PostgreSQL·MariaDB와 같은 풀 방식으로 맞춘다. 소스별 풀 최대 = `effective_max_concurrent()`(DB2 기본 4 — D-347 ③ 상한과 같아 연결 수·부하 한도 불변) · 지연 생성(기동 불변) · 꺼낼 때 `active`·유휴 수명(`pool_idle_seconds` 300) 검사 · 실행 예외 연결은 폐기. 소스 키 `pool_enabled` 기본 **true**, `false` = 현행 요청별 연결(비트 동일).
  ③ **소스별 프로세스 분리는 측정 판정 뒤** — 코어 포화가 폐쇄망 측정(`plans/206` W0)으로 확인되면 소스 하나 = 프로세스 하나로 배치하고(상한 합 불변) 본체·sre_agent에 소스별 URL 맵(기본 빈 값 = 현행)을 단다. 판정 결과는 이 파일에 부기한다.
- **기본 off 원칙 예외(D-162)**: ②는 사용자 결정(2026-11-02 「기본값을 처음부터 켜라」). 되돌리기는 소스별 `pool_enabled = false`.
- **근거**: `plans/206` §1 실측(루프 CPU 비용 · 현 상한 · DB2 요청별 연결 · mcp 1.29.1 전송 지원).
- **구현**: `plans/206` W1(DB2 풀) · W0(폐쇄망 측정) · W2(소스별 프로세스 — 판정 시) · W3(보류).
- **주의**: ① 로컬 venv에 `ibm_db`가 없다 — W1 착수 전 폐쇄망에서 연결 핸들의 스레드 간 순차 사용·`active`/`free_stmt` 시그니처·`pconnect` 동작을 실측한다. ② 기본 on이라 기존 DB2 소스는 배포 즉시 풀로 동작한다 — 첫 배포 때 접속 비용 전후 비교와 DB2 측 연결 수를 DBA와 확인한다. ③ DB2 세션 읽기 전용 속성은 이 결정 밖(보안 동작 변경 — 별도 계획 · D-337 ⑥).
