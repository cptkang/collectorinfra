## D-242. 스트림 실패는 **경위와 함께 말풍선에 남기고, 다시 할지는 사용자가 정한다** · 일반 질의 상한 `API_QUERY_TIMEOUT` 기본 60→120초 (사용자 지시 2026-09-21)

- **결정일**: 2026-09-21 | **상태**: 확정 (구현 완료 · 운영 반영 시점은 사용자 결정) | **번호**: 등재 직전 실측 2026-09-21 — `## D-` 헤더 최댓값 **D-241** · 「변경 이력」 표 최댓값 **D-241** · 「채번 이력」 표 예약에 242 없음 → **D-242**(D-241 사용 세션과 사전 조율)
- **배경**: 폐쇄망 웹 실측(2026-09-21) — 은행존 *"지난달 메모리 사용률 평균 80% 초과 서버"* 질의가 존 선택 뒤 **빈 말풍선 "완료 · 1단계 · 60.6s"**로 끝났다. 원인 셋: ①프로필 few-shot 「서버별 월간 … 성능 통계」 예시(폴스타 프로필 4종)가 삭제 리소스 필터를 `hi` 서브쿼리 안에만 둬, LLM이 서브쿼리를 빼고 따라 쓰자 필터가 사라짐 → 결정적 가드(D-104 계열) 검증 실패 → 재생성 1회(약 20초) ②`query_timeout` 60초 초과 ③`error` 이벤트를 8초 토스트로만 띄우고 말풍선은 "완료"로 접어 **실패가 성공처럼** 남음. 사용자 지시: *"타임아웃값은 120초로 바꾸고 설정값에서 설정할 수 있도록 하라. 웹화면에 오류가 어떻게 났는지 보여줘야 한다. 오류를 보고 재시도를 할지는 사용자의 판단에 맡긴다."*
- **결정**:
  - ①**일반 질의 상한 기본 120초** — `ServerConfig.query_timeout` 60→120(`API_QUERY_TIMEOUT`). 관리자 설정 화면 항목은 이미 있었다(`settings_catalog.RELOADABLE_KEYS` — 저장 후 「설정 리로드」로 재시작 없이 반영). **`.env`에 값이 명시돼 있으면 코드 기본값은 적용되지 않는다** — 운영 반영은 운영 `.env` 또는 관리자 설정 화면에서 값을 바꿔야 한다(실측: 이 개발 맥 `.env`=900 · 폐쇄망 run `20260918-182507`은 199턴이 60초에 걸림 — 폐쇄망 `.env` 값은 미확인)
  - ②**실패 경위 계약** — SSE `error` 이벤트는 **`message`를 바꾸지 않고** 경위 필드를 더한다: `code`(`timeout`·`exception`) · `elapsed_ms` · `limit_sec` · `stage`(진행 중이던 가장 안쪽 단계) · `last_error`(마지막으로 기록된 단계 실패 사유) · `steps`(최근 30단계 — `kind`·`name`·`label`·`status`·`ms`·`detail`) · `steps_dropped`. 두 스트림 라우트 대칭. 수집은 `src/api/stream_failure.py` `StreamTrace`가 **라우트가 이미 받는 신호**(노드 시작·종료 · 도구·단계·작업 `progress`)에서 한다 — 새 이벤트 발행 없음. 단계 실패 사유는 `emit_step(..., detail=)`로 싣는다(`_run_single_db_pipeline` 검증·실행 종료). `progress` 단계 이벤트의 `detail`은 **있을 때만** 붙는다
  - ③**화면** — 실패는 말풍선 안에 사유 · 시간(상한·경과) · 멈춘 단계 · 앞선 실패 · 접이식 진행 경위 · 「다시 시도」 버튼으로 남는다(텍스트·파일 스트림 대칭 · HTTP 오류 응답과 연결 단절 포함). "완료" 요약을 만들지 않는다
  - ④**재시도는 사용자가 정한다** — 자동 재시도 없음. **종전의 연결 단절(TypeError) 시 비스트리밍 `/query` 자동 재실행을 없앴다**(서버가 첫 요청을 계속 처리 중이면 중복 실행이 된다). 「다시 시도」는 같은 인자(질의·선택 존·파일)로 한 번 다시 보낸다 — 누르면 비활성화, 처리 중이면 거절
- **근거**: 사용자 지시. 상한만 올리면 원인은 여전히 한 줄 문구 뒤에 숨는다(`settings_help` `API_QUERY_TIMEOUT` example: *"실패 원인이 '전체 시간 초과'로만 남아 어느 단계가 느렸는지 알 수 없다"*). `message` 불변은 하네스가 문구로 타임아웃을 분류하기 때문이다(D-218 · D-241 `timeout` 사유 도출)
- **대안(기각)**: 서버·클라이언트 자동 재시도(중복 실행 · 사용자 판단 배제) · 클라이언트가 받은 이벤트로 경위 재구성(검증 실패 사유·상한값을 모른다 — 서버가 정본) · 경위를 매 단계 별도 이벤트로 송출(`progress`가 이미 있다 — 실패 시 1회 요약이면 충분) · `.env`만 변경(미추적 파일 — 확정 설정은 코드 기본값)
- **구현**: `src/config.py`(`query_timeout`) · `.env.example` · `config/settings_help/infrastructure.yaml`·`llm.yaml`(기본값 문구) · `src/api/stream_failure.py`(신규) · `src/api/routes/query.py`(`_stream_error_payload` · 두 스트림 생성기의 관측 호출 · `_progress_sse_payload` `detail`) · `src/utils/progress_events.py`(`emit_step` `detail`) · `src/orchestration/subagents.py`(검증·실행 종료 사유) · `src/static/js/app.js`(`failureStepLabel`·`renderStreamFailure`·`markStreamFailed` · 두 스트림 함수의 실패 경로) · `src/static/css/style.css` · 테스트 `tests/test_api/test_query_stream_progress.py`(경위 3건 · 두 라우트) · `tests/test_orchestration/test_handler_milestones.py`(사유 1건) · `tests/test_api/test_ui_stream_status.py`(`TestStreamErrorInBubble` 6건)
- **주의**: ①**측정 기준선 축이 바뀐다** — `plans/110` 재테스트·벤치 구간 캠페인은 상한이 다른 run의 지연·타임아웃 수를 직접 비교하지 말 것(실효값은 설정 에코로 확인) ②운영 `.env` 명시값이 코드 기본값을 이긴다(①) ③`last_error`는 "마지막으로 기록된 실패"다 — 이후 단계가 통과했어도 남는다(경위로 읽을 것) ④1단(`deep_agent`) 경로의 도구 내부 단계는 `pipeline.*` 마일스톤에만 의존한다 — 마일스톤이 없는 핸들러 안에서 멈추면 `stage`는 바깥 작업·도구까지만 가리킨다 ⑤원인 ①의 few-shot 교정(4종 바깥 WHERE에 `r`·`svr` 필터 추가 · 조인 구조 안내 5항)은 같은 사건의 별도 수정이다(`docs/18` 2026-09-21 행)
