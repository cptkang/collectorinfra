## D-344. SRE 조사 플레이북 APM 호출 지연 교정 — 해소 소스 한정 · X-View 사전 확인(기본 10 · 기본 off 예외) · APM 전용 호출 상한 (`plans/190`)

- **결정일**: 2026-10-20 | **상태**: 확정 · 구현(`plans/190` W0~W5 · 커밋 없음 · 폐쇄망 재측정 대기) | **번호**: 2026-10-20 색인 예약 행 → 같은 날 본문 등재(등재 직전 `ls docs/decisions/` 최댓값 D-343 확인)
- **배경**: 폐쇄망 실측(2026-10-20) — 플레이북 APM 스텝이 매번 20초 타임아웃으로 실패했다. 게이트웨이 감사에서 도구 1건 `elapsed_ms` 469,979~656,449 · 소스당 `api_calls` 121 · 스필 35건이 X-View(`/api/transaction/time`). 같은 `instance_name`이 b0·cm_prd에 하나씩(서로 다른 서버) 있었다. 파생으로 조사 감사 accepted 348 중 `stuck_watchdog` 126. 원인 ① 플레이북이 `instance_name`만 넘겨 게이트웨이 `resolve_instance_name`이 고른 소스 전부에서 동명 인스턴스를 찾는다 — **다른 존의 다른 서버 데이터가 섞이는 정합성 결함**이기도 하다. ② 기간 모드 `apm_app_health`가 X-View를 1분 조각 상한 없이 부른다(`apm_core.xview`). ③ APM 호출이 사전수집 상한(20초)을 공유하고, 클라이언트가 포기해도 게이트웨이는 끝까지 돈다.
- **결정**:
  ① **해소 소스 한정** — 대상 확정(S0 `apm_instance_map(query=…)` · 호스트 확장 · 역방향 S0′ `apm_instance_map(hostname=…)`) 결과 행의 `source_id`를 `ctx.targets` 각 dict에 보존한다. 같은 이름이라도 소스가 다르면 대상 행을 나눈다. 플레이북의 모든 APM 호출 인자는 공용 헬퍼 `_apm_args` 한 곳에서 조립하며, `source_ids`를 받는 도구(W0 실측 13종 — 허용 목록 `APM_SOURCE_IDS_TOOLS`)에 `source_ids=[해당 소스]`를 싣는다. 소스가 미확정이면 종전 인자 그대로 + 브리핑 한계 「APM 소스 미확정 — 전 소스 조회」(탐색 호출은 한계 없음). 업무 동료 확장은 좁히지 않고, 나온 행마다 자기 소스로 이후 호출한다.
  ② **X-View 사전 확인** — 설정 `apm_xview_confirm_over: int | None = 10`. 기간 모드 `apm_app_health` 호출 전부에 게이트웨이 옵트인 인자 `xview_confirm_over`로 싣는다(None·0 이하 = 미전송 · 종전 비트 동일). `status: confirm_required`면 X-View를 다시 부르지 않는다. 이미 시 단위 비교를 부르는 스텝(S1)은 그 통계를 그대로 싣고, 아니면(S0·S0′) `apm_period_compare`를 시 경계 기준 직전 같은 길이 구간과 1회 비교한다. 대체마저 실패하면 `missing`으로 둔다. 모든 경우 한계 「X-View 사전 확인 초과(예상 N회 > 상한 M) — 구간 p95·에러율 생략, 시 단위 통계로 대체」를 남긴다. **p95 근거가 없으므로 해당 대상 판정은 「판정 불가」(None)다** — 시 단위 통계로 재판정하지 않고, 「정상」으로 강등하지도 않는다(계획 §3.2 ①의 「시 단위 통계로 판정」을 보수적으로 해석 · D-341 ③ 결정적 판정 · 침묵 강등 금지).
  ③ **APM 전용 호출 상한** — `apm_tool_timeout_seconds: float | None = None`. None·0 이하 = 종전 `evidence_prefetch_timeout_seconds`(비트 동일). 폴스타 배치 호출자는 영향 없음.
  ④ **운영 정렬 규칙(문서)** — 본체 `NOISE_INVESTIGATION_FOLLOWUP_TIMEOUT_SECONDS`(후속 대기)는 sre_agent `INVESTIGATION_TIMEOUT_SECONDS`(조사 예산)보다 커야 한다. 권장값 = 워치독 임계 `max(600, 2×INVESTIGATION_TIMEOUT_SECONDS)`. 두 `.env.example`에 주석으로 남긴다. 값은 바꾸지 않는다.
- **기본 off 원칙 예외(②)**: off로 두면 보고된 정체(도구 1건 8~11분 → 조사 포화 → 워치독 대량 발생)가 그대로 남는다. D-296 부기 ⓓ 「플래그 없음」 선례를 따랐다. 게이트웨이 쪽은 옵트인 인자라 다른 호출자 영향이 0이다. **D-296 ④ 「자체 상한 없음」과의 관계**: 게이트웨이는 조회 범위를 줄이지 않는다(불변). 무인 자동 조사에는 고를 사용자가 없으므로, 호출자가 상한을 선택하고 축소 사실을 한계로 노출한다 — 본체 1·2단 `XVIEW_CONFIRM_OVER = 60` + 되묻기와 같은 계약의 무인 판이다. 되돌리기는 `APM_XVIEW_CONFIRM_OVER=0`.
- **근거**: 폐쇄망 2026-10-20 감사·스필·ASGI 예외 실측(`plans/190` §1). W0 게이트웨이 시그니처 실측(`plans/190` §2.6) — `source_ids` 13종 · `apm_transaction_profile`은 단수 `source_id` · `xview_confirm_over`는 `apm_app_health`뿐. confirm 봉투는 표준 `ok()` 봉투 + `status`·`expected_xview_calls`·`expected_api_calls`·`xview_confirm_over`·`instance_count`·`estimate`이고, `error` 키가 없다.
- **구현**: `sre_agent/sre_agent/application/playbook_steps.py`(`_apm_args`·`APM_SOURCE_IDS_TOOLS`·`APM_XVIEW_CONFIRM_TOOLS`·`_confirm_fallback`·`_prior_window_compare_call`·`_target_labels`·`RunScope.target_entries`·`StepContext.target_sources/limits`) · `playbook_runner.py`(`run_playbook(xview_confirm_over=)` · 스텝 한계 → `PlaybookRun.notes` → 브리핑 한계) · `investigation_dispatcher.py`(`_collect_playbook` 배선 1줄) · `settings.py` · `infrastructure/mcp_tool_client.py`(`_apm_timeout_seconds`) · `sre_agent/.env.example` · 루트 `.env.example`(주석). 테스트 `sre_agent/tests/test_plan190_{apm_scope,apm_timeout,verify}.py`.
- **주의**: ① **스텝 대기 상한 30초**(`playbook_runner.DEFAULT_STEP_TIMEOUT_S` · 설정 키 없음)가 APM 호출 상한 위에 있다. `APM_TOOL_TIMEOUT_SECONDS`를 30보다 크게 두면 스텝은 30초에 missing이 되고 호출만 백그라운드에서 끝까지 돈다. 그래서 권장값은 30이다. 더 긴 값이 필요하면 스텝 대기 상한을 설정으로 여는 일이 먼저다(후속). ② 같은 이름의 두 번째 대상은 표·대상별 키에 `이름@소스`로 적는다. 알람 인스턴스(첫 행)는 이름 그대로라 판독 조회는 종전과 같다. ③ 클라이언트 포기 시 게이트웨이 작업 취소 전파는 이 결정 밖이다(게이트웨이 계약 변경 — `plans/190` §7). ④ 알람 행 선택은 종전대로 첫 정확 일치 행이다. 페이로드 `meta.hints.source_id`로 고르는 방법은 후속 후보로 남긴다.
