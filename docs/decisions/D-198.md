## D-198. SSE 무한대기 이중 가드 — FabriX 호출 총 소요 상한 + 스트림 가드의 검출·취소 분리

- **결정일**: 2026-09-07 | **상태**: 확정 (구현 완료 · 폐쇄망 검증 대기) | **번호**: 원 채번 **D-195** → **2026-09-09 `test_update` 병합 시 D-198 재부여**(팀장 로컬 작업이 D-195 점유 — 「채번 이력」 표 참조)
- **배경**: `docs/29` 성능테스트 B군에서 새 세션·존 역질문 재개 턴의 SSE 질의가 무한대기(1시간+, 12건 중 4건 발현). 진단 계측(`scripts/diag_server.py` — asyncio 태스크 await 사슬 주기 덤프 + `scripts/health_probe.ps1` 외부 헬스 프로브 + `scripts/stack_dump_summary.py`)으로 원인 사슬을 실측 확정했다: ①FabriX 호출이 응답 없이 무기한(`_run_agent`가 `chat_models.agenerate`에 8분+ 고정. 연결이 **유지된 채** 하트비트(`STATUS`/`SYNC`)만 오면 httpx `timeout`은 read 1회당 간격이라 라인마다 리셋 — 연결이 끊겼다면 즉시 예외로 끝났다) ②SSE 가드(`wait_for` 60s)는 발화했으나 **내부 취소 완료 대기에 갇힘**(`event_generator`가 wait_for 프레임에 8분+ 고정) → TimeoutError 미도달 → 에러 이벤트도 미송출 → 무한 깜빡임. ALARM_ENABLED·디버거·BaseHTTPMiddleware 가설은 전부 실측 기각(이벤트 루프·프로브 정상, agen이 yield가 아닌 wait_for에 정지).
- **결정**:
  - **F1 총 소요 상한**: `KBGenAIChat.total_timeout`(기본 300s, `LLM_FABRIX_TOTAL_TIMEOUT`) 신설. `_agenerate`는 `wait_for` 래핑(httpx는 취소에 즉시 반응하므로 취소 완료 대기가 갇히지 않음), `_astream`/`_stream`은 라인 루프에 벽시계 데드라인. 발화 시 경과·수신 라인 수·마지막 `event_status`를 ERROR 로그로 남긴다(FabriX 측 상태 판정 증거 확보).
  - **F2 검출·취소 분리**: 스트림 이벤트 fetch를 `wait_for` → `asyncio.wait(timeout=…)` 패턴(`_next_event_or_timeout` 헬퍼, 텍스트·파일 SSE 2곳)으로. 타임아웃 시 내부 태스크에 취소만 걸고 **완료를 기다리지 않은 채** 에러 이벤트 송출 후 응답 종료. 잔여(유령) 태스크의 수명은 F1이 보장 — **두 수정은 세트로 배포**.
- **대안 기각**: 이벤트 루프에 총 예산(경과 시간) 체크 추가 — 체크 도달 자체가 fetch 반환에 의존해 같은 wedge에 걸린다 · AuditMiddleware 순수 ASGI 전환 — 실측 결과 미들웨어는 무관.
- **주의**: ①비스트림 `/query`의 `wait_for(ainvoke)` 4곳은 이론상 같은 wedge 가능 — 발현 미관측이라 후속 ②ollama·구 `fabrix_client`·gemini는 총상한 미적용(프로바이더 전환 시 재발 가능, 후속) ③read 침묵 구간에서는 스트림 총상한이 read 타임아웃만큼 늦게 발화할 수 있음 ④진단 스크립트 3종은 scripts/에 존치(재발 시 재사용).
- **관련**: D-066(이벤트 fetch 타임아웃 원 결정 — 본 결정이 그 한계를 교정) · D-121(존 재개 턴 타임박스) · D-193(MCP SSE 세션 정리 — 인접 계열) · Known Mistakes(장시간 실행 경로 전체 타임아웃 가드).
