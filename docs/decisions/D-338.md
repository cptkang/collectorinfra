## D-338. 인증 활성인데 사용자 저장소가 없으면 fail-closed(503) — 토큰 payload만으로 통과시키지 않는다 · break-glass는 유지

- **결정일**: 2026-10-17 | **상태**: 확정 · 구현(`plans/186` L4 · 커밋 없음)
- **결정**: `AUTH_ENABLED=true`인데 `app.state.user_repo`가 None이면 사용자 토큰 의존성 3곳(`src/api/dependencies.py` `get_current_user`·`resolve_stream_user`·`require_user`)은 유효 토큰이어도 **503 고정 문구**(「인증 서비스를 사용할 수 없습니다. 관리자에게 문의하세요.」 — 로그인 503과 같은 문구) + warning 로그(요청 경로만)로 거부한다. 판정 순서: 인증 비활성 → `ANONYMOUS_USER`(종전) · 토큰 없음 → 종전(None·401) · 무효 토큰 → 401 · 유효 토큰 + 저장소 부재 → 503. 운영자 break-glass(`_try_break_glass_admin` — admin 시크릿·`type=admin`·`sub` 필수)는 `require_admin_user`·운영자 스트림이 먼저 보므로 저장소 장애에도 진입로로 남는다.
- **근거**: 종전에는 저장소가 없으면 토큰 payload만 믿고 `allowed_db_ids=None`·`allowed_sources=None`(전 DB·전 소스 허용)·is_active 미조회로 통과시켜, 인증 DB 장애가 곧 사용자별 인가 해제였다(fail-open). `plans/184` L1 감사에서 이 폴백이 인가 강등 경로로 드러났다(docs/18 2026-10-17). 메인 판정(사용자 지시 「확인할 사항은 직접 확인하고 진행」 2026-10-17) = fail-closed.
- **구현**: `src/api/dependencies.py` `AUTH_STORE_UNAVAILABLE_DETAIL`·`_auth_store_unavailable` · `src/api/server.py` `_init_auth_db` 풀 생성 전 실패 + 인증 활성 경고 문구 정정(「사용자 요청은 503으로 거부됩니다(운영자 break-glass만 진입)」) · 프론트 `src/static/js/app.js`(503이면 로그인 리다이렉트·알림 구독 없이 문구만 — 무한 재연결 방지) · `src/static/js/admin.js`(503이면 토큰 유지 — break-glass 토큰 삭제 방지) · 매뉴얼 user.md·admin.md. 단언 `tests/test_api/test_plan186_auth_fail_closed.py`.
- **주의**: 사용자 알림 SSE(`src/api/routes/alarm.py`)는 break-glass를 받지 않는다(기존 · 의도된 제한 — 운영자 스트림은 `noise_dashboard`가 break-glass 선행). 인증 활성에서 `user_repo`가 None이 되는 것은 풀 생성 **전** 실패·미설정뿐이다 — 풀 생성 뒤 부분 실패는 184 L1(안 A)대로 원복하지 않는다. 테스트가 인증 활성 + 저장소 없는 앱으로 payload 통과에 기대던 픽스처는 가짜 저장소를 주입하도록 고쳤다(`plans/186` §3).
- **관련**: D-026(사용자 인증) · D-069(통합 RBAC · break-glass) · D-070(사용자/운영자 시크릿 분리) · D-232(인가 거부) · D-337 ⑥(행동 변경 분리)
