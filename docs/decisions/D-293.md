  ① **데이터 소스 유사어 정본 = 레지스트리**(N-1) — 비DB 시스템은 `solutions[].aliases`(제니퍼 = 「제니퍼」·「JENNIFER」·「APM」 · 문서 = 「전산관리매뉴얼」·「본부매뉴얼」·「전산관리규정」·「설계문서」 · Prometheus = 「프로메테우스」·「Prometheus」), DB 시스템은 종전 `databases[].aliases`(자산관리 = 「ITAM」·「자산관리」 등). 추가·수정은 이 YAML 한 곳에서 한다. 위치·환경·제품 표면어와 겹치는 이름은 소스 유사어에서 제외한다(위치어 보강 D-065 몫). 같은 이름이 두 시스템을 가리키지 않는다(테스트 고정). 일반어(「모니터링」·「서버」)는 넣지 않는다.
  ② **원문 결정적 보강**(N-1) — 입력 파서가 원문의 소스 이름·유사어를 `target_db_hints`에 더한다(D-065 위치어 보강과 같은 방식 · 라틴 이름은 단어 경계·대소문자 무시 `term_in_text`). D-004 부기(등록 표면어 인식은 의도 분류가 아님 · D-281 ⑦) 적용 — 원문 키워드로 소스를 **고르는** 규칙(「WAS」 → APM 등)은 만들지 않는다. 소스 유사어는 직전 턴 DB 승계 차단 신호에도 합류한다.
  ③ **계획 출구 고정**(N-2 · 2단) — 조회 담당(`data_query`·`alarm_query`·`process_query`) task가 가리키는 지목(단일 task = 원문 전체 · 복합 = task 질의에 이름이 남은 것)이 ⓐ 활성 DB 시스템 없이 활성 비DB 시스템 하나면 그 처리기로 고정(보기는 처리기가 정함) ⓑ **전부 비활성이면 조회하지 않고 안내만 하는 task**(`direct_response` · 사용자가 쓴 표현만 · 「다른 데이터 소스의 값으로 대신 답하지 않았습니다」 — D-264) ⓒ 그 밖(활성 DB 지목 섞임·지목 없음)은 그대로. 개념 설명(`general_inference`)·계획 고정 `db_ids` task는 건드리지 않는다. **활성 판정은 시스템 단위**다 — 폴스타 한 존 DB가 비활성이어도 폴스타에 활성 DB가 있으면 활성(존 사이 처분은 종전 위치 규칙 D-246·TP-1.11a 노트 — 로컬 샌드박스의 「김포」 질의는 종전대로 답한다).
  ④ **SQL 처리기 가드**(1·2단 공용 `run_data_query_pipeline`) — task 질의에 이름이 남은 지목 중 활성 DB 시스템이 없으면 조회하지 않고 안내(분류 LLM 0회). 1단(비SQL 처리기 비노출 — G-5)·재계획 후속의 침묵 대체를 막는다. 비활성 비DB 지목이 활성 소스 지목과 섞인 턴은 종전 사유 노트(TP-1.11a)에 합류한다.
  ⑤ **소스 불가 종결**(N-3 · G-4) — 비SQL 처리기(`apm_query`·`doc_query`) 실패 · 명시 소스 안내로 끝난 task는 재계획 평가에서 빼고, 나머지가 없거나 전부 성공이면 평가 LLM 없이 끝낸다. **권한 거부는 넣지 않았다** — G-4 질문 문구에는 있었으나 「일부만 거부된 복합 계획은 LLM이 평가한다」(D-251 ⑤ · `plans/119` N-2 · 테스트 고정)와 충돌하고, 그 충돌을 게이트에서 묻지 않았다(전체 회귀에서 발견 — 이 축소는 사용자 확인 대상).
