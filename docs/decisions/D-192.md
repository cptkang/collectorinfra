## D-192. 알람 → 질의 프롬프트 인계 — **추천은 검증된 형태만, 전송은 확인 뒤에**

- **결정일**: 2026-08-31 | **상태**: 확정 (구현 완료 · `plans/86` · `CAPABILITY-MAP-86.md`) | **번호**: `## D-` 헤더 최댓값 **D-191** · 「변경 이력」 표 최댓값 **D-191** · 「채번 이력」 표 예약(D-105·115·134·158·163~168·176) 대조 → **D-192**(등재 직전 재실측). *(작성 착수 시 191로 잡았으나 같은 날 병렬 작업이 D-191을 선점해 옮겼다 — 채번은 계획 시점이 아니라 **쓰기 직전**에 확정해야 한다는 D-161 부기의 재확인.)*
- **배경(사용자 지시)**: *"이벤트 알람에서 나타난 내용을 바로 프롬프트로 조회할 수 있는 기능을 추가하라. … 'fgisidd0'를 클릭하면 … `fgisidd0 서버의 1달 평균 메모리 사용률과 증가율을 보여줘` 라는 프롬프트를 생성하여 '질의응답' 페이지에서 조회를 자동으로 … 프롬프트는 '권고 조치'나 '패턴 분석'에서 … 추천하여 생성하도록."*
- **★ 실측이 옮긴 무게중심 — 문제는 UI가 아니라 답변 가능성이었다**: 요청은 클릭·전송 배선처럼 읽히지만, 배선은 이미 다 있었다(`setActiveView`·`promptEl`·`handleSend`·closure 바인딩 선례). 실제 난점은 **생성한 질의를 파이프라인이 답하는가**였다.
  - *"1달 평균 메모리 사용률"* → **답한다**(골드셋 `gp.yaml:214`·`:345`에 동형).
  - *"증가율"* → **지시대로는 답하지 못한다.** 급증 조립기가 **파일시스템 전용**(`spike_sql.py:35` `_FILESYSTEM_TYPE`)·**월 단위만**(`:34`)·**절대 임계 명시 필수**(`query_generator.py:590` — 없으면 *"급증 조립 미진입"* 후 LLM 폴백)다. 예시를 문자 그대로 구현하면 **첫 클릭부터 비결정 경로로 샌다**.
  - 그래서 이 결정의 중심은 **추천 문구를 "검증된 형태"로 제한**하는 데 있다. 추천은 창작이 아니라 **골드셋 동형의 재사용**이다.
- **결정**:
  - **축 판정 키는 `resource_type`이다.** `alarm_name`은 자유 한국어라 단독 키로 못 쓴다 — 실측 값에 *"내부Cloud ○○○님의 Cloud PC 사양변경 승인바랍니다"* 같은 것이 섞인다. 축별 매핑은 골드셋 동형이 있는 문구만 담고, **`server.Network`는 동형이 없어 일부러 비워 뒀다**(T7 실측 후 편입 — 테스트로 부재를 고정).
  - **급증형 문구에 임계·차분을 박는다**(*"지난달 대비 10%p 이상 상승하고 80% 이상"*). 이 수치가 없으면 조립기가 진입하지 않고, 진입하지 않은 사실은 **화면에 드러나지 않는다**.
  - **★ 전송은 확인 뒤에**(G-2 사용자 확정). 지시는 *"자동으로 조회"* 였고 계획서 권고도 자동 전송이었으나, 사용자가 **확인 후 전송**을 택했다. 결과적으로 **D-183의 "채우기만"과 충돌하지 않는다** — 입력창에 채운 뒤 `[이대로 조회] / [수정]` 바를 띄우고, 조회는 `handleSend()` **단일 진입점**을 탄다. 진행 중이면 조회 버튼이 비활성이다(연타 = 중복 과금).
  - **두 경로의 계약을 이름으로 갈라 둔다** — `reuseHistoryQuery`(이력 재사용, 확인 바 없음·D-183)와 `stageAlarmPrompt`(알람 인계, 확인 바 있음). 각 함수 주석이 서로를 참조한다: **한쪽을 보고 다른 쪽을 "일관성 있게" 고치는 회귀**를 막기 위해서다. 테스트가 `reuseHistoryQuery`에 전송·확인 바 호출이 없음을 고정한다.
  - **진입은 둘 다**(G-1). 헤더 서버명(지시의 예시)은 추천이 있을 때만 `<button>`이 되고 — 누를 것이 없는데 눌리게 보이면 클릭이 무반응으로 끝난다 — 하단 칩(최대 3개)은 상시 노출한다. `is_routine=true`면 섹션을 **접어 둔다**: 노이즈 게이트가 "일상"이라 판정한 알람에 조회를 권하는 것은 UI가 게이트의 판단을 뒤집는 일이다.
  - **프롬프트 전문은 속성이 아니라 DOM으로 다룬다.** 전문에는 서버명(외부 데이터)이 들어가는데 `escapeHtml`은 **따옴표를 이스케이프하지 않는다**(`div.textContent → innerHTML`) — `data-*`에 넣으면 마크업이 깨진다. 칩은 `createElement` + `textContent`/`title` + closure 캡처다(D-049·D-177의 인라인 `onclick` 금지 선례와 같은 계열).
  - **LLM 추천은 보강이지 대체가 아니다**(G-4 = Phase 1+2). `POST /alarm/suggest-prompt`는 **기본 off**이고, 프론트는 **결정적 추천이 0건일 때만** 호출하며, capabilities가 꺼졌다고 알려주면 아예 부르지 않는다(알람마다 503을 때리지 않게). 실패·파싱 실패·**대상 서버명 누락**은 `200 + suggestion:null` — 추천이 없다고 알람 카드가 깨지면 안 된다. 존 RBAC은 피드백·ack와 같은 규약(`_assert_zone_access`)이다: 다른 존 알람 내용을 LLM에 실어 보내지 못하게 한다.
- **대안 기각**: **자동 전송**(계획서 원 권고) — 사용자가 확인 후 전송을 택함 · **예시 문구 그대로("증가율" 포함)** — 결정적 경로 부재로 첫 클릭이 LLM 폴백 · **`spike_sql`을 메모리·CPU로 확장** — 근본 해결이나 골드셋 추가·방언 재검증이 따르는 별건 · **LLM이 모든 추천을 생성** — 골드셋 대조가 없어 답변 가능성이 보장되지 않는다 · **`alarm_name` 키워드 매칭** — 자유 문자열이라 오분류.
- **주의**: ①LLM 산출 질의는 **파이프라인이 답한다는 보장이 없다** — 기본 off·결정적이 빌 때만·확인 후 전송 3중으로 막지만 성질 자체는 남는다. ②LLM 추천이 뒤늦게 도착하면 섹션만 끼워 넣고 **헤더는 버튼으로 바뀌지 않는다**(트리거는 결정적 추천의 진입). ③`server.Network` 축은 T7 전까지 추천이 없다 — 기능 부재가 아니라 **검증 대기**다. ④신규 설정 키가 카탈로그 3계약을 건드렸다(SECTION 분류·필드 수 309→310·`config/settings_help/` 큐레이션) — **자기 델타만** 메웠다.
