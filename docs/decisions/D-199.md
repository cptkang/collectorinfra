## D-199. EAV 단위 문자열 숫자 캐스트의 GB 기준 환산 정규화

- **결정일**: 2026-09-07 | **상태**: 확정 (구현 완료 · 폐쇄망 검증 대기) | **번호**: 원 채번 **D-196** → **2026-09-09 `test_update` 병합 시 D-199 재부여**(팀장 로컬 작업이 D-196 점유 — 「채번 이력」 표 참조)
- **배경**: docs/29 B-11("메모리 사이즈 상위 3대")에서 GP/YD 실행 에러 `invalid input syntax for type numeric: "14.9 GB"` 실측. 메모리·디스크류 EAV 값(`TotalSize` 등)은 단위 접미 문자열이며, **실측 단위 분포는 세 존 모두 TB/GB/MB 혼재**(B0: TB 26,073·GB 21,783·MB 21 / GP: GB 10,449·TB 1,455·MB 43 / YD: GB 4,796·TB 743·MB 1 — 단위 없는 값 0건). LLM은 `REPLACE(…, 'GB', '')` 임기응변을 생성하기도 하나 GB만 처리해 TB에서 깨진다(B0 executed_sql 실측). 로컬 픽스처(`testdata/pg`)는 순수 숫자 MB라 **운영 shape와 달라 테스트가 이 결함을 잡지 못했다**.
- **결정**: `normalize_eav_unit_casts`(query_gen_common) — EAV 값 컬럼이 포함된 NUMERIC/DECIMAL 캐스트를 **GB 기준 환산 CASE**(TB×1024 · GB · MB÷1024 · KB÷1048576 · 무단위=원값)로 결정적 교체. D-160(정수→NUMERIC) 뒤에 체인하며 단일(query_generator)·멀티(multi_db_executor 결정적 선택+LLM 경로) 3곳 대칭 배선. **단위 제거만 하는 안은 기각** — 혼재 분포에서 900 MB > 14.9 GB로 정렬되는 침묵 오류가 된다.
- **구현 원칙**: CASE·LIKE·SUBSTR·LENGTH·TRIM·NULLIF·UPPER·CAST만 사용한 **방언 중립 + 검증기 안전 식** — 1차 구현의 REPLACE 함수가 sql_guard 금지 키워드(MySQL `REPLACE INTO` 차단용)와 충돌해 검증기 거부·재생성 루프를 유발한 폐쇄망 실측(2026-09-07, docs/18 등재) 후 **위치 기반(값 끝 2글자) 단위 제거**로 확정. LLM의 `REPLACE(X,'GB','')` 임기응변은 가드가 X로 벗겨 검증기 통과 SQL로 정규화. 값 컬럼 무관 캐스트 불변 · 재적용 멱등(마커 검사) · 괄호 불균형 무변경(하방 안전) — D-160과 동일 골격. **가드 산출물의 `SQLGuard.detect_forbidden_keywords` 통과를 테스트로 고정.**
- **주의**: ①무단위 값은 GB로 간주하지 않고 원값 캐스트(vcore '4.0' 등 스케일 불변 — 운영 3존은 단위 없는 값이 0건이라 미해당) ②B0 B-11의 "0건" 응답은 캐스트와 별개의 조인/모델링 문제일 수 있음 — 가드 배포 후 재실측으로 분리 판정 ③픽스처 shape 불일치는 별도 개선 항목(운영 shape 픽스처 추가).
- **관련**: D-160(EAV 정수 캐스트 — 같은 가드 계열·같은 배선 지점) · D-068(고정 스키마 쿼리 결정적 조립 원칙) · Known Mistakes(LLM 비결정성 — 결정적 가드 후처리).
- **부기(2026-09-30 · `plans/123` S-1b — 정규식 단위 삭제도 벗긴다)**: run `20260923-103638` R4-10(「메모리 64GB 넘는 서버」)이 반복 3회 중 2회 198건 · 1회 197건이었다. 198건 두 번은 LLM이 `CAST(regexp_replace(cc.stringvalue_short, '[^0-9\.]', '', 'g') AS DECIMAL)`를 만들었고 가드가 **숫자만 남은 식**을 CASE 피연산자로 써 단위 분기가 전부 죽었다 — 「965.5 MB」가 ELSE(무단위 원값)로 965.5가 돼 64 초과에 섞였다. 197건 반복은 원값에 CASE를 걸었다. 세 반복 모두 「넘는」을 `> 64`로 옮겼으므로 차이는 초과/이상 해석이 아니라 이 결함이다. 교정: `_unwrap_llm_unit_replace`가 `REGEXP_REPLACE(X, '<패턴>', ''[, '<플래그>'])` 중 **패턴이 단위 접미를 지우는 것**(표본 `1.5 TB`·`14.9 GB`·`965.5 MB`·`512 KB`에 파이썬 `re`로 적용해 단위가 사라지면)도 X로 벗긴다 — 컴파일되지 않는 패턴·단위를 남기는 패턴·삭제가 아닌 치환은 무변경(하방 안전). 신규 플래그 0 · 단일·멀티 3곳 배선 그대로 · 테스트 `tests/test_utils/test_eav_unit_cast.py::TestRegexpUnitStrip` 4건(시작 커밋 worktree에서 2건 적색 확인). 측정은 run R5(123 S 트랙).
