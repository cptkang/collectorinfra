## D-003. 3중 읽기 전용 방어
- **결정일**: 2026-03 (초기 설계) | **상태**: 확정 — 절대 변경 불가
- **결정**: 읽기 전용을 3개 레이어에서 동시 강제 — (1) DBHub `readonly=true`, (2) query_validator에서 DML/DDL 키워드 차단(INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE/GRANT/REVOKE), (3) query_generator 프롬프트에 "SELECT 문만 생성" 명시.
- **근거**: 다층 방어, LLM은 프롬프트 무시 가능하므로 프로그래밍적 검증 필수.
- **주의**: 이 결정은 변경하지 않는다. 어떤 요건이 추가돼도 쓰기 기능 허용 절대 금지.
- **부기(2026-09-29 · 사용자 확정 "권고")**: 이 결정은 DB 접근(질의·조사 평면)의 읽기 전용이다. 제니퍼 연동 L2(WAS 조치 실행 — 덤프 채취 · PLC 상한 조정 · 인스턴스 재기동)는 DB 쓰기가 없으므로 D-003의 **범위 밖**이며 **예외가 아니다** — 그 실행 평면은 **D-195 ③**이 별도 통제한다.
- **부기(2026-10-14 · `plans/163` W1 S1 — 강화 사실 기록 · 결정 본문 불변)**: (1) 「DB 계층 readonly」의 실체를 MCP 서버(`mcp_server/`) 한 지점으로 모았다 — ① 검사기 `validate_readonly`를 금지 목록에서 **문장 유형 허용 목록**(단일 문장 · `SELECT`/`WITH…SELECT` 시작 · `INTO`·행 잠금 절·부작용 함수 금지 · PG·DB2·MariaDB 세 방언으로 주석·리터럴을 각각 읽은 본문 모두 통과)으로 강화 ② 검사 위치를 `DBPoolManager.execute`(+`health_check`)로 옮겨 폴스타 도구·스키마 헬퍼·exporter·`execute_sql`이 모두 받는다(설정 없는 소스는 차단) ③ 세션 읽기 전용 — PG `default_transaction_read_only=on`·MariaDB `transaction_read_only=1`(되돌릴 수 있는 보조 수단) · DB2는 드라이버 미설치로 미적용(계정 권한 의존) ④ 스키마 헬퍼 `table_name` 보간 SQL 주입 수정(식별자 형태 검사 + 따옴표 이중화). **본질은 SELECT 권한만 가진 접속 계정**이며 운영 계정 권한은 폐쇄망 확인 항목이다. 소스 `readonly=false` 스위치는 현행 유지.
- **부기(2026-10-19 · 폐쇄망 실측 교정)**: MariaDB 세션 읽기 전용 변수는 11.1부터 `transaction_read_only`, 그 전(10.x)은 `tx_read_only`만 있다 — 운영 ITAM이 10.x라 풀 초기화가 1193(`Unknown system variable`)으로 실패해 itam 전체가 offline이었다(로컬 샌드박스는 `mariadb:11.4`라 미검출). `mcp_server/db.py` `_create_mariadb_readonly_pool`이 `transaction_read_only` → `tx_read_only` 순으로 시도하고, 1193 외 오류·두 이름 모두 미지원이면 그대로 실패한다(읽기 전용 없이 여는 강등 없음). 결정 본문 불변.
