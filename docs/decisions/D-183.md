## D-183. 질의 프롬프트 이력 — **목록은 브라우저, 감사는 라우트**

- **결정일**: 2026-08-29 | **상태**: 확정 (구현 완료 · `plans/84` · `CAPABILITY-MAP-84.md`) | **번호**: 등재 최댓값 D-182 → **D-183**
- **배경(사용자 지시)**: *"질의했던 프롬프트 내용을 별도로 저장하여 목록을 볼 수 있게 하고 싶다."*
- **★ 실측이 드러낸 것 — 결손은 하나가 아니라 둘이었다**:
  - **사용자 쪽**: `promptHistory`가 **메모리 배열**(`app.js:250`)이라 새로고침하면 사라지고, ↑↓ 탐색 말고 목록 UI가 없다.
  - **운영자 쪽**: `AuditService.log_user_request`(`audit_service.py:126`)가 **정의만 있고 호출부 0건**이었다. 그래서 관리자 "감사 로그" 탭이 읽는 DB `audit_logs`에 질의가 **한 건도** 없었다(파일 감사 `logs/audit-*.jsonl`에는 `input_parser.py:157`이 남기고 있었다). **없는 것은 저장이 아니라 조회 경로였다.** 감사 탭의 이벤트 필터에는 "질의 요청"(`user_request`) 선택지가 **이미 있었다** — UI는 준비돼 있고 데이터만 없던 상태.
  - 두 결손은 소비자·수명·조회 경로가 달라 **두 모듈로 분리**했다(`query-history-ui` ∥ `query-audit-path`, 의존 0).
- **결정**:
  - **목록은 브라우저에 둔다**(사용자 확정 G-1). 근거는 취향이 아니라 실측이다 — `.env`·`.encenv` 어디에도 `AUTH_ENABLED`가 없어 기본 `false`(`config.py:457`)이고, `require_user`가 `ANONYMOUS_USER`를 돌려준다(`dependencies.py:238`). **서버에 두면 전원이 `anonymous` 한 명으로 뭉쳐 남의 질의가 내 목록에 섞인다.** D-178·D-180의 "개인 선호는 브라우저" 전례와 같은 계열.
  - **저장 항목은 질의문과 시각뿐**(G-2). SQL·결과·DB 식별자는 저장하지 않는다.
  - **세 번째 뷰 탭**(G-3). D-182가 만든 탭 배선을 재사용하되, `setActiveView`의 **하드코딩 toggle을 뷰 등록표로 일반화**했다 — 탭이 늘 때마다 뷰 하나가 조용히 안 숨는 회귀를 막는다. **스크롤 복원 분기도 `else` → `view === "chat"`으로 좁혔다**: 그대로 뒀으면 이력 탭으로 *갈* 때 채팅 복원이 돌았다.
  - **목록 클릭은 입력창에 채우기만 한다 — 전송하지 않는다.** 옛 질의가 지금도 유효하다는 보장이 없고(존 개명·서버 폐기), 오전송은 되돌릴 수 없다(`plans/75` §2.2의 disabled 버튼과 같은 취지). 테스트로 고정.
  - **기록 지점을 늘리지 않는다.** `handleSend`가 전송의 단일 진입점(버튼·Enter·웰컴 힌트·파일 업로드)이라 거기 한 줄이면 모든 경로가 덮인다. 상한 200건 · 같은 질의는 제거 후 최신 재삽입(도배 방지) · 모든 저장소 접근은 try/catch(**사생활 모드에서 localStorage는 던진다** — 목록이 비는 것은 허용해도 질의 전송이 막히는 것은 허용하지 않는다).
  - **★ 감사의 주체를 노드에서 라우트로 옮긴다.** `AuditService.log`는 **JSONL과 DB에 둘 다 쓰므로**(`audit_service.py:43`·`:51`, 기본 둘 다 on) 라우트에 그냥 주입하면 `input_parser`의 기록과 겹쳐 **파일에 같은 질의가 두 번** 남는다. 그러면 그 파일로 하는 모든 집계(`plans/82` §5.1의 918건 비용 실측 등)가 오염된다. 그래서 **노드의 호출을 제거하고 진입점 4개**(`/query`·`/query/stream`·`/query/file`·`/query/file/stream`)**에 대칭 주입**했다. 노드는 애초에 `app.state`에 닿지 못해 `client_ip`·`session_id`를 영원히 채울 수 없다 — 호출부가 비어 있던 것 자체가 이 계층 문제의 흔적으로 보인다.
  - **CLI 감사는 이설로 보존한다.** `main.py:71`이 `graph.ainvoke`를 직접 부르는 CLI 경로가 있어, 노드에서 빼면 그 경로의 감사가 사라진다. 파일 감사 호출을 CLI 진입부로 옮겨 **API·CLI 어느 쪽이든 1건**이 되게 했다.
  - **인증 상태는 데이터에 근거해 표기한다.** 감사 탭에 `anonymous` 행이 **실제로 있을 때만** 안내를 띄운다 — 정적 문구를 박아두면 인증을 켠 뒤 거짓말이 된다(D-179의 경계 표시 방식).
- **대안 기각**: **서버 이력 테이블 신설** — 인증이 꺼진 채로는 사용자 구분이 불가능하다(G-1) · **라우트 주입 + 노드 유지** — 파일 이중 기록 · **`audit_repo.log_event` 직접 호출** — 중복은 없으나 `AuditService`의 형식 통일·`client_ip`를 우회 · **`AUTH_ENABLED=true` 동반 전환** — 운영 영향(로그인 강제·계정 시딩)이 커서 별건.
- **구현 중 발견 1건 — 죽은 스타일과의 이름 충돌**: `.history-item`이 `style.css:3536`(`.query-history` 계열)에 **이미 있었다**. 사용처는 0건인 옛 잔재인데 파일 뒤쪽이라 내 규칙을 이겨(배경·라운드·`margin-bottom`) 행 모양이 의도와 다르게 렌더됐다 — **headless Chrome 렌더로 잡았고**, 정적 테스트로는 잡히지 않았을 종류다. 옛 규칙은 이 작업의 범위가 아니라 **지우지 않고**, 내 클래스를 `.history-row` 계열로 개명한 뒤 사유를 주석으로 남겼다.
- **주의**: ①**기기 간 동기화가 없다**(G-1의 알려진 한계 — D-178과 같은 성질). ②공용 PC 대응은 마스킹이 아니라 **"모두 지우기"의 존재**다. ③인증을 켜기 전까지 DB 이력의 `user_id`는 전부 `anonymous`다 — **버그가 아니라 설정 상태**. ④알람 뷰와 골격이 같아 CSS 셀렉터를 공유하되(`.alarm-view, .history-view`) 목록 행만 분리했다.
- **검증**: 신규 테스트 **17건**(`test_ui_query_history.py` 9 · `test_query_audit_path.py` 8 — 탭 3개 고정 · 인증 게이트 · 저장소 상한·가드 · **기록 지점 단일성** · **재사용 경로에 전송 호출 없음** · 뷰 등록표 · **진입점 4개 대칭** · 노드 무기록 · CLI 기록 · DB 1행 · 감사 실패 무해). **정리 1건**: 처음 넣었던 서빙 테스트는 한 세션에 앱 lifespan을 한 번 더 띄워 **종료 정리 경합으로 간헐 실패**했다(실패 지점이 단언이 아니라 `TestClient.__exit__`라 신호가 아니다) — 같은 파일을 이미 D-182의 서빙 테스트가 보므로 **중복을 제거**했다. `node --check` 2파일 · `arch_check --ci` exit 0 · `test_nodes` **774 passed**(노드 감사 제거 회귀 0) · 격리 worktree 기준선(`36 failed / 4794 passed / 24 errors`) 대비 **신규 실패 0 · 오류 집합 완전 동일**(현재 `27 failed / 5252 passed / 24 errors` — 감소분은 트리의 다른 미커밋 작업 몫). 라이트·다크·모바일(414px) 렌더 확인 — **모바일에서 탭 3개는 넘치지 않는다**(헤더는 요소가 넷이라 `flex-wrap`으로 방어).

### D-183 개정 — 세 번째 탭에서 **접이식 왼쪽 사이드바**로 (2026-08-31)

- **배경(사용자 지시)**: *"질의 이력을 왼쪽창에 열었다 닫았다 할 수 있는 UI로."* G-3(세 번째 탭)의 변경이다.
- **왜 탭이 아니라 사이드바가 맞는가**: 탭은 **본문을 교체**하므로 이력을 보는 동안 채팅이 사라진다. 그런데 이력의 쓰임은 "옛 질의를 골라 다시 묻는 것"이라 **채팅과 동시에 보여야** 한 동작이 끊기지 않는다. 탭 전환 → 항목 클릭 → 채팅 탭 복귀의 3단계가 클릭 하나로 줄었다(그래서 `reuseHistoryQuery`의 `setActiveView("chat")` 호출도 없앴다 — 사이드바는 채팅 뷰 안에 있어 애초에 채팅 화면이다).
- **오른쪽 진행 패널과 대칭으로 만든다.** 같은 grid의 한 열이고, 접으면 44px 손잡이만 남으며(진행 패널은 42px), 화살표는 "누르면 일어날 일"을 가리킨다. 새 상호작용 관용구를 만들지 않는 것이 학습 비용이 가장 싸다.
- **★ 두 패널은 독립적으로 접힌다 — 조합 넷을 모두 정의했다**(`260px 1fr 380px` / `260px 1fr 42px` / `44px 1fr 380px` / `44px 1fr 42px`). 하나라도 빠지면 그 조합에서 grid 열 수가 어긋나 레이아웃이 무너진다. 1024px 이하도 같은 넷, 640px 이하는 두 패널 모두 숨김(진행 패널 전례). **테스트로 고정**.
- **기본은 접힘, 편 상태는 브라우저가 기억한다**(`query_history_panel_open`). 기본 접힘이라 첫 방문 화면이 종전 2열과 같아 **회귀가 0**이고, 저장소가 막힌 환경의 기본값도 접힘이다(`isHistoryPanelOpen`의 catch가 `false`). 진행 패널은 상태를 기억하지 않지만, 이력은 D-178·D-180의 "개인 선호는 브라우저"를 따른다 — 이력 자체가 이미 localStorage를 쓰므로 추가 비용이 없다.
- **좁은 열에 맞춰 행 구조를 바꿨다**: 한 줄(시각+질의문+버튼)에서 **두 줄**(질의문 2줄까지 + 시각·버튼)로. 동작 버튼은 hover·포커스에서만 나타난다 — 260px에서 상시 노출은 질의문 자리를 뺏는다.
- **부수 정리**: 뷰 탭이 **둘로 돌아왔고**(질의응답·이벤트 알람), `viewRegistry`에서 `history`가 빠졌으며(사이드바는 본문을 교체하지 않는다), 알람 뷰와 공유하던 CSS 셀렉터(`.alarm-view, .history-view`)도 **골격이 달라져 분리**했다. 인증 게이트는 별도 항목이 필요 없어졌다 — 사이드바가 `.chat-layout` 안에 있어 기존 `body.auth-pending > .chat-layout`에 함께 걸린다(**테스트로 고정** — 밖으로 나가면 로그인 전 노출이 되살아난다).
- **D-248 부분 개정(2026-09-22)**: G-1(목록은 브라우저)을 **대화(질의+응답)에 한해** 서버 앱 DB로 옮겼다 — 소유 키는 로그인 사용자 user_id, 익명은 브라우저 식별자(`X-Client-Id`)라 G-1의 "남의 질의가 섞인다"는 막힌다. 질의 목록(G-2)은 사이드바 "질의" 모드로 그대로다. 이 개정본의 "편 상태는 브라우저가 기억한다"는 선언 순서 결함으로 동작하지 않았고 D-248에서 교정했다.
