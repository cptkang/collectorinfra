## D-356. APM 게이트웨이 조회 가속 — 도구 안 독립 호출 동시 실행 · 큰 응답 파싱·자격증명 검사 프로세스 풀 · 기본 on

- **결정일**: 2026-11-02 | **상태**: 확정 · 구현(`plans/205` W1~W4 · 커밋 없음 · 폐쇄망 재측정 대기) · 부기 1(① 헬퍼 재사용·X-View 직렬·기본 폭 2 — R-1) | **번호**: 등재 직전 `ls docs/decisions/` 최댓값 D-355 확인
- **배경**: 사용자 제기(2026-11-02) *"apm gateway가 api 조회 시 시간이 오래 걸린다. 1코어에서 동작하니 행이 걸리는 것으로 보인다."* 실측(`plans/205` §1): ① 여러 건 조회 경로가 루프 안에서 API를 한 건씩 기다린다(I/O 직렬) ② 응답 파싱·`scrub_detail`은 GIL을 쥐는 순수 파이썬이라 `to_thread`로도 1코어다 — 6.5MiB 응답 1건 약 0.64s, 8건 순차 5.0s → 프로세스 풀(4) 1.45s.
- **결정**:
  ① **도구 안 독립 호출 동시 실행** — 순서에 종속되지 않는 호출(도메인·인스턴스·지표·단위·`targets` 항목)을 순서 보존 헬퍼(`gather_ordered`)로 동시에 보낸다. 결과 처리(행·`[한계]`·호출 수 신고)는 입력 순서대로 해 봉투가 순차와 같다. 동시 상한 `APM_FANOUT_CONCURRENCY`(기본 4 · 1 = 현행 순차). 종속 호출(표기 후보 순차 · 페이지 넘김)은 바꾸지 않는다.
  ② **큰 응답 파싱+자격증명 검사는 프로세스 풀** — 임계(`APM_PARSE_PROCESS_MIN_BYTES` 기본 256KiB) 이상 본문은 spawn 프로세스 풀(`APM_PARSE_WORKERS` 기본 `min(4, CPU-1)` · 0 = 현행 `to_thread`)에서 파싱과 검사를 **함께** 하고 가린 결과만 돌려받는다(D-296 ③ 경계 불변). 풀 장애는 WARNING 후 그 호출만 스레드 경로 + 풀 재생성.
  ③ **상한은 기존 장치** — 모든 호출은 클라이언트의 자리(D-347 ③ · 8) → 속도 제어(초당 5) → HTTP를 지난다. 새 상한을 더하거나 기존 상한을 올리지 않는다.
  ④ **uvicorn 다중 워커는 채택하지 않는다** — MCP SSE 세션이 프로세스 메모리라 깨지고, 소스별 상한이 워커 수만큼 늘어나며(D-347 ③ 위반), 폴러·캐시·작업 관리자가 나뉜다.
  ⑤ **다중 사용자 공정 동시성**(사용자 요구 2026-11-02) — 소스별 자리·초당 상한은 게이트웨이 전체 공용이므로, 호출자 키(주체 + `owner` — 본체는 `user:<sub>`)별로 나눈다: 같은 우선순위 안에서는 자리를 가장 적게 쥔 호출자 먼저 · 호출자별 동시 상한 `JENNIFER_MAX_INFLIGHT_PER_CALLER`(기본 자리//2 = 4 · poller 제외) · owner별 실행 작업 상한 `APM_JOB_MAX_CONCURRENT_PER_OWNER`(기본 2) · 둘 다 일 보존(기다리는 다른 호출자가 없으면 상한을 넘겨 받는다) · 대기 시간 가시화(`slot_wait_ms`·`throttle_wait_ms`). 우선순위(poller > interactive > background)·에이징은 불변. 기본 on · 0 = 종전 순서 비트 동일. 자리·초당 상한 코드 기본값은 바꾸지 않는다(D-347 ③ · 운영 `.env` 조정).
- **기본 off 원칙 예외(D-162)**: 사용자 결정(2026-11-02 「기본값은 켜둔 상태로」). 되돌리기는 `APM_FANOUT_CONCURRENCY=1` · `APM_PARSE_WORKERS=0` · `JENNIFER_MAX_INFLIGHT_PER_CALLER=0` · `APM_JOB_MAX_CONCURRENT_PER_OWNER=0` — 현행과 비트 동일. 결과 봉투는 순차와 같게 테스트로 고정한다.
- **근거**: `plans/205` §1 실측(합성 응답 파싱·검사 비용 · 풀 대비 · 순차 루프 전수).
- **구현**: `plans/205` W1(풀) · W2(도구 안 동시) · W3(배치 항목 동시) · W3b(다중 사용자 공정 동시성) · W4(기록·측정).
- **주의**: ① 동시 실행으로 소스당 대기 요청이 자리(8)를 넘을 수 있다 — 제니퍼가 느리면 자리 대기 초과(`SOURCE_UNAVAILABLE`)가 새로 날 수 있다(`plans/205` R-1). 검증에서 나면 기본 동시값을 낮추고 이 파일에 부기한다. ② 초당 5건 상한은 그대로라 호출 N건은 최소 N/5초다. ③ 워커 수만큼 RSS가 는다 — 폐쇄망 배포 뒤 측정(`plans/205` §6).
- **관련**: D-347 ③ · D-296 ③④ · D-344 · D-162 · D-274 ③ · D-303 · `plans/205`
- **부기 1(2026-11-02 · 구현 · 사용자 결정 「충돌 1 = A · 충돌 2 = X-View 직렬」)**: 착수 시 계획서(16ea44fa 작성)가 그 뒤 병합된 D-358 ②와 겹쳐 두 가지를 사용자 결정으로 정했다. (a) **헬퍼 재사용** — 새 `fanout.py`/`gather_ordered`를 만들지 않고 D-358의 `application/parallel.py` `gather_bounded`·`sources.gather_per_source`를 쓴다. 폭 = `JenniferSource.width` = min(`APM_FANOUT_CONCURRENCY`, 소스 자리 `JENNIFER_MAX_INFLIGHT_PER_SOURCE`) — D-358 기존 4곳(인스턴스 명단 적재·`apm_core.realtime/hourly`·실시간 순위)도 이 폭을 따른다(D-358 부기). (b) **X-View 루프 직렬 유지**(D-358 ② · D-344) — `apm_core.xview` 바깥 루프·`instance_tools._business_trace` 2단은 병렬 대상에서 뺐고, 안쪽에서 X-View를 부르는 `apm_change_impact`(`_impact_side`)도 보류했다. (c) **기본 폭 4 → 2(R-1)** — 실 축척 가짜 전송(지연 3s·5s · 자리 8 · 초당 5 · timeout 30s) 실측: 도구 단독(작업 4 × 독립 12)은 폭 4에서 자리 대기 초과 0(최대 대기 9.4s)이지만, 배치 조합(작업 4 × `targets` 6 × 도구 안)은 폭 4에서 초과 6건(최대 30.0s · 하위 봉투 부분 실패) · 폭 2에서 0건(최대 9.4s)이고 소요는 같았다(48.3s 대 52.3s — 속도 상한이 지배). 계획 R-1 규칙대로 기본 2(= 자리 8 // 작업 동시 4)로 낮췄다. 자리 8·초당 5는 그대로다(D-347 ③). (d) 동시 실행 중 클라이언트가 HTTP마다 신고하는 자격증명 메모·가린 칸은 항목별로 모아 **입력 순서로** 다시 신고한다(`parallel._OrderedNotes`). 계약 위반(`CONTRACT_VIOLATION`)은 첫 위반에서 아직 시작하지 않은 호출을 보내지 않는다(`gather_bounded(stop=)` — 폭 1은 종전 직렬과 호출 수까지 같다). `gather_per_source`는 소스별 세마포어를 단 1단 `gather_bounded`로 평탄화해 메모가 소스를 섞은 입력에서도 전역 입력 순서를 지킨다. 그래서 감사·예상 시간이 쓰는 **신고 폭**은 종전 max(소스별 폭)에서 sum(min(폭, 소스별 항목 수))로 바뀌었다 — 실제 동시 호출 수와 같고, 소스 하나일 때는 종전과 같다. (e) ⑤ 공정 분배는 「유효 순위 → 같은 순위 안 상한 미도달 → 적게 쥔 호출자 → 먼저 온 순서」로 순위를 먼저 둔다. 대기 가시화는 작업 기록·감사 `waits=slot_ms:합/최대,throttle_ms:합/최대`, 혼잡 현황은 `gateway_health`의 `congestion`(소스별 숫자만 — 호출자 키 미노출). (f) 측정: 클라이언트 단위 루프 지연(6MiB 4건) 인라인 207ms → 풀 22ms. 도구 전체 경로(20,000건 응답)는 파싱 뒤 도구의 행 조립이 루프를 잡아 최대 지연이 풀 켬·끔 모두 0.65~0.8s다 — 동시 경로 소요는 6.9s → 5.0s로 준다(`apm_gateway/scripts/bench_parallel.py`). 행 조립의 루프 점유는 이 결정 밖의 잔여다.
