## D-297. DB별 한글 식별자 허용 정책 — **D-104(생성 SQL 한글 토큰 잔존 차단) 개정 · 레지스트리 DB 항목 `allow_hangul_identifiers`(기본 false = 현행 비트 동일) · 허용 DB도 스키마 실재 이름·SQL 안 선언 별칭만 통과 · MariaDB 백틱 인용 인정 · MariaDB 큰따옴표 컬럼(침묵 오답) 검증 오류 · 단일·멀티·도구·자산 검증기 대칭 · 설정 조각 자동 제안** (사용자 지시 2026-10-06 *"ITAM의 경우 DB 칼럼명을 한글로 구성하였음을 확인하였음. 따라서 각 DB 설정에 따라 한글로 된 SQL을 허용할 것인지에 대한 여부를 설정하는 기능을 추가해야 함."* · 게이트 G-1~G-6 확정 · `plans/137`)

- **결정일**: 2026-10-06 | **상태**: **확정 · 구현 완료(`9e85556`)** — 폐쇄망 ITAM 1차 검증에서 한글 컬럼 SQL 실행 확인(2026-10-06) · 후속 교정 D-305
- **배경**: D-104(2026-07-22 「변경 이력」 — 원 D-087 · 본문 절 없음)는 LLM이 생성 SQL 구조 영역에 남긴 자연어 조각(「해당」·「현재」)이 DB 구문 오류를 내는 비결정 결함을 막으려고, 따옴표 밖 한글이 있으면 검증 실패로 재생성을 유도했다. 폴스타는 영문 컬럼이라 문제가 없었으나 ITAM(MariaDB · D-214)은 **물리 컬럼명이 한글**이다(사용자 확인 — 테이블명은 영문 `TCDMS…`). 이대로면 ITAM 질의는 전부 이 가드에 걸린다. 조사 중 두 결함을 더 확인했다: ① 가드가 MariaDB 백틱 인용(`` `자산명` ``)을 인용으로 보지 않아 정상 SQL도 거부한다 ② 운영 ITAM `sql_mode`(사용자 전달 `STRICT_TRANS_TABLES, NO_AUTO_CREATE_USER, NO_ENGINE_SUBSTITUTION` — `ANSI_QUOTES` 없음)에서 큰따옴표는 문자열 리터럴이라 `SELECT "자산명"`은 글자를, `WHERE "자산상태" = '운영'`은 0행을 오류 없이 돌려준다(`testdata/itam/README.md` 리허설 실측). 종전 재생성 문구(*"따옴표 안 … 외의 한글은 제거"*)는 LLM을 바로 그 형태로 유도한다.
- **결정**:
  ① **설정 = `config/db_registry.yaml` DB 항목 `allow_hangul_identifiers`**(G-2) — `DBEntry` 필드 · 미선언 false. 본체 앱의 레지스트리 1파일만 바꾸고 재기동한다(앱은 레지스트리를 쓰지 않는다 · R11). `.env`·MCP 서버·게이트웨이는 무관하다(MCP 읽기 전용 검증에는 한글 차단이 없다). ITAM만 true.
  ② **허용 범위 = 스키마 대조**(G-1 ⓐ) — 허용 DB에서 따옴표 밖 한글 토큰(한글 포함 식별자 단위)은 검증기가 이미 받는 `schema_info`(이번 질의 관련 테이블 — LLM 프롬프트와 같은 근거)의 테이블·컬럼명이거나 같은 SQL에서 선언한 별칭(`AS 별칭` · FROM/JOIN 테이블 별칭)일 때만 통과한다. 대조는 NFC 정규화 + 대소문자 무시 정확 일치. 그 밖의 한글은 D-104대로 거부·재생성(문구: 「스키마에 없는 한글」 + MariaDB면 백틱 안내). 대조할 스키마가 없으면 검사를 건너뛰고 경고를 남긴다(침묵 강등 금지). 전면 허용 모드는 두지 않는다.
  ③ **허용 off DB는 현행 비트 동일**(G-4) — 토큰 단위·판정·문구 불변. 폴스타 계열은 고려하지 않는다(영문 컬럼 확정).
  ④ **MariaDB·MySQL은 백틱을 인용으로 인정한다**(정책 무관 결함 교정).
  ⑤ **MariaDB·MySQL에서 스키마 이름을 큰따옴표로 감싸면 검증 오류**(G-3 ⓐ · G-6 운영 `ANSI_QUOTES` off) — 자동 교정 없음. `AS "…"` 결과 별칭 자리·문자열 리터럴·주석은 제외(폼필 한글 별칭 강제와 공존). 정책과 무관하게 MariaDB 전체(영문 컬럼도 같은 침묵 오답).
  ⑥ **경로 대칭**(D-066) — 단일 `query_validator`·멀티 `_validate_sql`(간이·full)·도구 `validate_sql_draft`·자산 생성 검증기(`asset_sql_checker` — `SqlChecker`에 `db_id` 인자 추가)가 같은 코어 함수(`check_hangul_tokens` · `check_double_quoted_identifiers`)와 같은 해석기(`hangul_identifiers_allowed`)를 쓴다. 공용 코어는 db_id를 모르고 정책 값만 받는다(D-088/D-089).
  ⑦ **「DB 구조」 O-8 설정 조각이 자동 제안**한다 — 수집 스냅샷에 한글 컬럼이 있으면 `allow_hangul_identifiers: true`와 근거 주석(한글 컬럼 수)을 싣는다(결정적 · LLM 0).
- **개정**: **D-104** — 「따옴표 밖 한글 = 거부」를 「허용 off DB는 그대로 · 허용 DB는 스키마 실재 이름·선언 별칭 통과」로 개정. MariaDB 백틱 인정·큰따옴표 가드는 추가.
- **근거**: 사용자 결정(G-1~G-6). 실측 — HEAD `d1f4b2a` 함수 직접 호출(백틱 오탐 · `취득_금액2` 토큰 분할 · `"자산명"` 통과) · DDL 파서(D-292)는 한글·백틱 컬럼을 정상 해석 · `schema_info`는 단일 `schema_to_dict(full_schema, relevant)`·멀티 `_gate_schema_tables` 사본 · 운영 `sql_mode` 사용자 전달.
- **주의**: ① 캐시가 오래돼 새 한글 컬럼이 빠져 있으면 그 컬럼도 거부된다 — 기존 컬럼 존재 검사와 같은 한계(「DB 구조」 재수집으로 해소). ② 따옴표 없는 암시적 별칭(`SELECT 자산명 자산이름`)은 선언 별칭으로 인식하지 않아 거부 → 재생성(AS 사용). ③ 백틱 참조(`` `t`.`자산명` ``)는 컬럼 존재 검사를 거치지 않는다(종전부터 · 잔여). ④ `||`(PIPES_AS_CONCAT 없음 → OR)·FabriX PII 필터의 한글 컬럼명 차단 여부는 `plans/95` W-6·폐쇄망 실측 소관.
- **대안(기각)**: 허용 DB 전면 허용(자연어 조각 재발 — G-1 ⓑ) · `.env` DB 목록(DB 단위 성질이 두 곳으로 갈림 — G-2 ⓑ) · 큰따옴표 자동 교정(리터럴/식별자 의도 추측 — G-3 ⓑ) · 토큰 단위 변경을 전 DB에 적용(G-4 — 폴스타 비고려 지시).
- **부기 (2026-10-08 · `plans/146` W1 · 게이트 G-1 (b))**: 주의 ③ 잔여(백틱 참조의 컬럼 존재 검사 누락)를 승격했다 — 내부망 3회차 ITAM-108·110 첫 시도가 `tcdmsif80`에 없는 컬럼으로 DB 1054까지 갔다(한글 검사는 선별 스키마 어느 테이블에든 있는 이름이면 통과). ① 백틱 엔진(MariaDB·MySQL)은 `validate_sql` 5·6단계를 `check_catalog_references`로 대체한다 — 백틱 테이블·별칭·한정/비한정 컬럼을 읽고, 비한정 컬럼(백틱·무백틱 한글)은 참조 테이블(하나면 그 테이블 · 여럿이면 합집합)과 대조한다(파생 테이블·CTE가 있으면 비한정 대조 생략). ② 실존 판정은 선별 스키마가 아니라 **조회 대상 전체 카탈로그**(`schema_info["_catalog_columns"]` — 선별 직전 전체 스키마 ∩ `allowed_tables` · 이름만)로 한다. 선별 밖이어도 실존하는 허용 테이블·컬럼은 통과(재시도 없음), 없는 컬럼은 그 테이블 실제 컬럼 이름 목록(상한 80)을 실은 오류, 조회 대상 밖 테이블은 종전 「존재하지 않는 테이블 참조」. 카탈로그는 정의 기반 선별 + 검증기가 백틱 엔진으로 판정할 때만 싣는다(단일 `schema_analyzer`는 `active_db_engine` 기준 · 멀티 `_analyze_schema`) — 한글 검사(②)의 대조 집합에도 같이 들어간다. ③ 단일·멀티(`_validate_sql_simple`·full) 대칭(D-066) · PostgreSQL·DB2 바이트 동일 · 선별 로직 불변(G-2 (c) — 선별 보강은 4회차 「선별 밖 테이블 사용 턴」 재계수 뒤 판단). **잔여**: 3·4단 단일 그래프는 `query_validator._engine_or_fallback`이 엔진을 postgresql로 가정해 이 검사가 돌지 않는다(`plans/103` 3단 동등성 소관 · 기준 2단은 동작) · 하위 질의 안 별칭·3단 한정·비단어 백틱 식별자는 검사하지 않는다(놓칠 뿐 오탐 없음).
- **부기 (2026-10-08 · `plans/149` W3 · 게이트 G-4 (b))**: 내부망 4회차 ITAM-115·117·118이 **이름 칸**에 등호를 걸어 0행이 났고 재생성은 0회였다(K4 부분 일치 규칙 반입 뒤에도 3턴 중 0턴 준수 — D-004 취지대로 결정적 신호로 옮긴다). ① 실행 SQL이 0행이고 WHERE에 이름 칸의 문자열 등호·`IN`이 있으면 「이 칸은 핵심어 `LIKE '%핵심어%'` 부분 일치로 다시 써라(컬럼 설명이 사용 범위를 제한하면 그 설명을 따른다)」 힌트를 재시도 사유로 실어 **1회만** 재생성한다. 재생성도 0행이면 그대로 0행을 답한다(결과 확장·숨김 없음). ② 이름 칸은 그 DB의 설명 정본(`config/knowledge/{db_id}/column_descriptions.yaml`)이 「부분 일치」로 표시한 칸이다 — 런타임 Redis 설명이 아니라 정본 파일을 읽는다(정본은 Redis에 없는 키만 채운다). 코드에 칸 이름 목록·엔진 분기 없음 · 신규 플래그 없음 · 정본이 없는 폴스타 계열은 비트 동일. 「부분 일치」 낱말 포함만 보므로 부정문도 표시가 된다(정본 작성자 주의). ITAM 표시 칸 5개: `tcdmsif72`의 `그룹경로내용`·`구성항목설명내용`·`용도내용` · `tcdmsif52.업무명` · `tcdmsgt82.어플리케이션명`. ③ 판정 함수 하나(`src/nodes/name_match_retry.py`)를 2단 task 루프(`_run_single_db_pipeline`)와 그래프 경로(`result_organizer` → `route_after_organization`)가 함께 쓴다(D-066 대칭). 기존 재시도 예산 안에서 성공한 0행 실행이 첫 1건일 때만 발동한다. 2단은 재생성이 실행 성공 없이 끝나면(검증 예산·마감 등) 재생성 전 0행 답으로 되돌린다. 그래프 경로는 남은 재시도 2회 이상일 때만 발동한다(되돌림에 상태 필드가 필요해서 — 발동 뒤 연속 2회 실패하면 실패 응답인 잔여는 xfail로 고정). **잔여**: 그래프 경로 후속 턴은 스레드 누적 실행 기록 때문에 덜 발동한다(수용) · `multi_db_executor`는 대상 밖 · 큰따옴표 문자열 리터럴(`= "값"`)·역순 비교는 미탐(수용) · 2단 되돌림 때 재생성 단계의 검증 실패 이벤트는 이미 스트림에 나가 있다.
