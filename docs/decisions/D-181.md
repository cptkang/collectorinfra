## D-181. `mcp` 패키지 `<2` 상한 고정 — 2.x의 FastMCP 제거로 `mcp_server` 임포트 파손
- **결정일**: 2026-08-28 | **상태**: 확정 (조치 완료) | **번호**: 등재 최댓값 D-180 → **D-181**(등재 직전 `## D-` 헤더·「변경 이력」·「채번 이력」 표 재확인 — D-176은 `plans/82` 예약이라 건너뜀).
- **증상(2026-08-28 실측)**: 루트 `.venv`의 `mcp`가 **2.1.1**로 올라가면서(설치 시각 10:33) `mcp_server`가 **임포트 단계에서 죽었다** — `ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x, where FastMCP was renamed to MCPServer`. 영향 파일은 `server.py`·`tools.py`·`polestar_tools.py`·`promql_tools.py` 4종(전부 `from mcp.server.fastmcp import …`).
- **★ 더 위험했던 2차 증상 — 조용한 skip**: `mcp_server/tests/test_promql_tools.py`는 모듈 상단이 `try: import … except ImportError: HAS_MCP=False` + `pytestmark = skipif`라 **53건이 전부 skip되면서 "통과"처럼 보였다.** 전체 스위트 실행에서는 앞선 모듈이 `mcp.server.fastmcp`를 먼저 채워 수집이 통과해 더 눈에 띄지 않았다(단일 파일 지정 실행에서만 수집 오류로 드러남 — `tests/test_dbhub_integration.py`). **임포트 가드 skip은 "환경 부재"와 "환경 파손"을 구별하지 못한다**는 것이 이 건의 교훈이다.
- **결정**: **`mcp<2` 상한을 `pyproject.toml`(루트)·`mcp_server/pyproject.toml` 양쪽에 고정**하고, 루트 `.venv`를 **1.29.1**(1.x 최신)로 되돌린다. `sre_agent/.venv`는 1.25.0으로 이미 1.x라 무변경(별도 venv — D-118).
- **근거(다운그레이드가 안전한 방향임을 실측)**: ①`claude-agent-sdk 0.1.48`의 요구는 `mcp>=0.1.0`으로 **상한이 없다** — 1.x로 충족되고, 실제 사용 API도 `mcp.server.Server`·`mcp.types`로 1.x 이래 불변. ②본체가 쓰는 `mcp.client.sse.sse_client`(`src/dbhub/client.py:91`·`noise_gate/infrastructure/sre_agent_client.py:79`)는 **1.x·2.x 양쪽에 존재**해 어느 방향이든 무해. ③따라서 **깨지는 쪽은 서버 프레임워크(FastMCP) 하나뿐**이고, 그 소비자는 전부 이 저장소 코드다.
- **대안 기각**: **`MCPServer` API 마이그레이션** — `server.py`의 lifespan·`build_asgi_app`(SSE + Bearer 미들웨어)·도구 등록 데코레이터 4파일이 동시에 바뀌고, `mcp_server`는 실 데이터 접근 경계(D-119)라 회귀 비용이 크다. 상한 고정이 **코드 변경 0**으로 같은 결과를 낸다. 2.x 이점을 실제로 필요로 할 때 별건으로 계획한다. **아무 조치 없이 두기** — 조용한 skip 때문에 회귀 감시가 무력화된 채로 남는다(기각).
- **검증(2026-08-28)**: `pip install 'mcp<2'` → **1.29.1**. `pip check` 깨진 요구 0. 임포트 5종 전부 OK(`mcp_server.server`·`mcp_server.promql_tools`·`claude_agent_sdk`·`src.dbhub.client`·`noise_gate.infrastructure.sre_agent_client`). **`mcp_server` 183 passed / 2 skipped**(직전: 대량 skip) · **`test_promql_tools.py` 52 passed / 1 skipped**(직전: 53 skipped) · **`tests/test_dbhub_integration.py` 60 passed**(직전: 수집 오류) · 본체 전체 회귀 기준선 대비 신규 실패 0.
- **잔여 위험**: 상한은 `pyproject.toml`에만 있고 **이미 설치된 `collectorinfra` dist-info에는 옛 무제약 메타데이터가 남아 있다** — `pip install -e .` 재실행 시 갱신된다. 상한을 푸는 것은 `MCPServer` 마이그레이션과 **같은 커밋에서만** 해야 한다.
- **관련**: D-119(PromQL 도구가 이 프레임워크 위에 있다 — 파손 시 Prometheus 경로 전체 정지) · D-118(별도 venv라 `sre_agent`는 무영향) · `docs/27_prometheus_integration_guide.md` §4.3.
- **부기(2026-09-22 · 루트 `uv.lock` 재생성 — `plans/92` v3 R-11 · 사용자 지시 *"고치지 않은 것들을 권고에 맞게 모두 수정하라"*)**: 상한은 `pyproject.toml`에 들어갔지만 **루트 `uv.lock`은 D-181 이전 상태로 남아 있었다**. requires-dist가 `{ name = "mcp" }`(지정자 없음)였고, 잠긴 버전은 **`mcp` 2.1.1**이었다(최종 갱신 2026-08-31 `1868330`). `uv lock --check`가 "needs to be updated"로 실패했다. 이 상태로 `uv sync --frozen`을 하면 이 결정이 막은 파손(`mcp.server.fastmcp` 부재)이 재현된다. **조치**: `uv lock`(uv 0.11.3 · 기존 잠금 우선 · `--upgrade` 없음). 버전 변화는 **`mcp` 2.1.1 → 1.30.0 · `httpx-sse` 0.4.3 추가 · `mcp-types`·`opentelemetry-api` 제거** 4건뿐이다(183 패키지 해소). 나머지 diff는 uv 버전 차이로 생긴 **도달 불가 분기 마커 정리**다(`torch` → `cuda-toolkit`은 `sys_platform == 'linux'`에서만 요구되므로 그 아래 `nvidia-*`의 win32 조건이 빠짐 등). 설치 결과는 같다. 재생성 뒤 `uv lock --check` 통과 · requires-dist `{ name = "mcp", specifier = "<2" }`. **1.30.0 호환 실측**: 저장소 밖 스크래치 venv 2개(Python 3.13 · Windows · `ibm-db` 미설치)에서 `mcp_server` 전체 스위트를 같은 조건으로 돌렸다. 결과는 **1.30.0 = 245 passed / 7 skipped / 2 failed**, **1.29.1 = 246 passed / 7 skipped / 1 failed**다. 실패는 두 버전 모두 `tests/test_sql_log.py`의 동시 쓰기 테스트뿐이다(`test_concurrent_processes_do_not_interleave` 상시 · `test_concurrent_appends_do_not_interleave` 간헐). `sql_log.py`는 `mcp`를 임포트하지 않고 `O_APPEND` 원자성에 기대는데, 이 성질이 Windows에서 성립하지 않아 생기는 **플랫폼 실패**다. 해당 파일만 버전별로 4회씩 반복하면 둘 다 매번 1 failed / 7 passed였다. 따라서 **1.30.0 전환에 따른 회귀는 0**이다. 개발 기준 환경(맥)의 venv 재동기화 후 재확인은 권장 사항으로 남긴다.

### D-181 후속 — `mcp_server/.env.example` 오버라이드 커버리지 (2026-08-28)

- **발견**: D-181 조사 중 `docs/27` 작성을 위해 오버라이드 표면을 전수 대조한 결과, `_apply_env_overrides`가 읽는 **키 14종 중 9종이 `.env.example`에 미문서화**였다. 그중 **`MCP_BEARER_TOKEN`(전송 인증 — 미설정이면 무인증으로 뜬다)**·**`EXPOSE_EXECUTE_SQL`/`EXPOSE_RAW_PROMQL`(D-122가 배치별로 다른 값을 요구하는 게이트)**·`PROMETHEUS_URL`(미설정 시 PromQL 전건 실패)이 포함된다. 보안 값은 애초에 TOML에 쓸 수 없어 **`.env.example`에만 있을 수 있는 키**인데 그게 비어 있었다.
- **부수 발견 2건**: ①**유령 키** `ITAM_CONNECTION` — `config/db_registry.yaml`에 `itam` DB가 등록돼 있으나 `config.toml`에 `[[sources]] name="itam"`이 없어 **값을 채워도 조용히 무시**된다(오류도 로그도 없음). ②**운영 존 3종 미문서화** — `polestar_cm_gp`·`polestar_cm_yd`는 실제 `mcp_server/.env`가 쓰고 있는데 예제에 없어 **현행 설정을 예제만 보고 재현할 수 없었다**.
- **조치**: 누락 9키를 배치별 권장값 주석과 함께 추가(본체 파이프라인 배치 vs 조사 배치 — D-122). 존 3종(`gp`·`yd`·`b0`) 연결 키 추가. `ITAM_CONNECTION`은 **삭제하되 사유를 주석으로 남긴다** — itam은 오타가 아니라 레지스트리에 실재하는 계획 DB이므로, 제거가 아니라 *"소스를 먼저 추가해야 효력을 갖는다"*를 명시하는 편이 정확하다.
- **재발 방지가 본체**: 키를 한 번 채우는 것만으로는 다음에 키가 늘 때 같은 공백이 다시 생긴다. `mcp_server/tests/test_env_example_coverage.py`(8건)가 **`_apply_env_overrides`의 소스에서 키를 직접 추출**해 `.env.example`과 대조한다 — 목록을 테스트에 **복제하지 않는 것이 핵심**(복제본이 곧 다음 누락 지점이다. 본체 `settings_catalog` 전수 회귀와 같은 발상 — D-129). 역방향(유령 연결 키)과 **추출기 자가 검증**(정규식이 빈 집합을 뽑으면 커버리지 단언이 공허하게 통과한다)도 함께 고정했다.
- **이 테스트는 `mcp`에 의존하지 않는다** — `config.py`가 `mcp`를 임포트하지 않으므로 임포트 가드가 없다. D-181 본체 사고(가드 skip이 파손을 숨김)와 같은 방식으로는 무력화되지 않는다.
- **작성 중 잡은 오류 1건**: `_load_toml`이 dict를 돌려준다고 가정했으나 실제 반환형은 `AppServerConfig`였다(테스트가 즉시 검출 — 실측 우선 원칙 재확인).
- **검증**: `mcp_server` 183 → **191 passed / 2 skipped**. 오버라이드 키 14/14 문서화 · 유령 연결 키 0.
- **회귀 귀속 확정(2026-08-28)**: 클린 HEAD worktree에 **`.env`·`.encenv`·`.cache`를 복사해 환경을 동일화**한 뒤 대조 — 기준선 **36 failed / 4794 passed / 25 errors** vs 현재 공유 트리 **35 failed / 4960 passed / 25 errors**. **신규 실패 0 · 신규 오류 0**(오류 집합 완전 동일), 오히려 실패 1건 해소(`test_t1_catalog_covers_all_env_file_keys`)·통과 +166. **주의**: 같은 날 아침의 `34 failed / 24 errors`는 환경이 다른 실행이라 **비교 기준이 될 수 없다** — 그 수치와의 `+1/+1` 차이는 회귀가 아니라 기준선 오용이었다(docs/18 「worktree 환경 동일화」 항목의 반대 방향 사례).
