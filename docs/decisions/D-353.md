## D-353. 장애 조사 실행 병렬화 — 플레이북 의존 기반 스케줄링 · 스텝 안 축 동시 · HolmesGPT 턴당 다중 도구 지침 (전부 옵트인 · D-341 실행기 조항 개정)

- **결정일**: 2026-10-30 | **상태**: 확정 · 구현(`plans/200` W0~W5 · 플래그 전부 기본 off · 커밋 없음) | **번호**: 2026-10-30 색인 예약 행(당초 D-351) → 같은 날 본문 등재 → **D-353으로 재채번**(origin/main에 D-351(노이즈 관제 결정 이력 솔루션·존 칸) 선푸시 · 병행 세션 collectorinfra-da가 D-352 선점 · 이 작업 트리 색인에는 원격 D-351 행 없음 — 병합 시 해결)
- **배경**: 사용자 제기(2026-10-30) — 「플레이북 조사 항목이 순차로 진행되고 HolmesGPT 도구 호출도 순차라 분석이 느리다」. 분석(`plans/200` §1) 결과 병렬은 이미 다섯 겹(플레이북 ∥ HolmesGPT · 같은 단계 스텝 4 · 배치 4 · 소견 LLM 4 · holmes 응답 단위 16스레드)이며, 느린 원인은 ① `plan_stages`가 YAML 연속 구간으로 단계 장벽을 만들어 의존 없는 스텝도 기다림 ② S5·S7 두 독립 축 직렬 ③ 지침의 순서형 문구가 턴당 1호출을 유도 ④ 측정 부재였다.
- **결정**:
  ① **Q1 — D-341 실행기 조항 개정**: 「YAML 순서의 연속 구간을 단계로 묶어 같은 단계만 병렬」에 더해 **「의존이 모두 끝난 스텝부터 실행」**(DAG)을 옵트인으로 둔다(`SRE_PLAYBOOK_DAG_SCHEDULING_ENABLED` 기본 false = 종전 단계 실행과 비트 동일). 의존 = when 스텝 참조 ∪ when 판독의 입력 액션(`READING_INPUTS`) ∪ `ctx.prior` 입력(`PRIOR_INPUTS`) ∪ 앞선 대상 확정 스텝 — 모두 YAML상 앞 스텝만(그래서 YAML 순서가 늘 유효한 위상 순서 · 슬롯 1 = YAML 순서 실행).
  ② **Q2 — 결정성**: DAG에서 when 평가·`prior`·단계 끝 해석의 「앞 단계 결과」 줄·「왜」 문장은 **조상 스텝 결과로 한정**한다. 단계 끝 해석의 **판독 스냅숏**은 해석 기준(`narration_basis` = 조상 ∪ 그 스텝이 담당하는 판독의 입력 액션을 맡은 YAML 앞 스텝)으로 정한다 — 자기 판독이 off와 같게(예: host.cpu S2 `cpu_owner`가 비조상 S4 결과를 씀). 기준이 아직 끝나지 않았으면 **실행은 미루지 않고 단계 끝 처리 묶음(결과 한 줄·step_end·부분 브리핑·소견 제출)만** 미뤄, 기준이 정착하면 YAML 순서로 처리하고 수집 직후 남은 묶음을 모두 처리(flush)한다. scope는 조상 중 YAML 마지막 대상 확정 결과(없으면 초기 scope). 결과 조립(섹션·호출 목록)은 YAML 순서.
  ③ **Q3**: 스텝 동시 수 `SRE_PLAYBOOK_MAX_WORKERS` 기본 4(1~8 · 단계 실행·DAG 공통 · 종전 `DEFAULT_MAX_WORKERS`와 같음). 실제 상한은 전역 도구 동시 상한(D-347 ②).
  ④ **Q4**: X-View 1분 조각 동시화(`plans/200` I-6)는 착수하지 않는다 — 소스당 5/s 상한이 같아 이득 불확실 · 내부망 측정 뒤 별도 계획.
  ⑤ **스텝 안 축 동시**: S5 관련 알람(폴스타 알람 · APM 이벤트)·S7 최근 변경(APM 변경 · 폴스타 변경 이력)의 두 축 호출만 동시에(`SRE_PLAYBOOK_AXIS_CONCURRENCY_ENABLED` 기본 false). 호출 기록·도구 결과 순서는 고정 축 순서. 켜면 실행 기록의 `tool_start`가 두 축 먼저 나란히, `tool_end`가 뒤에 나온다(개수 동일).
  ⑥ **HolmesGPT 지침 변형**: 순서형 문구(「①…⑥ 순서」·「먼저 확보하라」·「먼저 판정」·「이 순서로 확인하되」)를 「대상 확정 → 서로 의존하지 않는 조회는 한 턴에 함께 요청」형으로 바꾼 변형을 옵트인으로(`SRE_GUIDANCE_PARALLEL_TOOLS_ENABLED` 기본 false = 지침 바이트 동일 · vLLM KV 캐시 접두 보존 · D-343). 진짜 의존(대상 확정 → 조회 · ref → 상세)과 안전 문구는 남긴다. holmes 패키지는 고치지 않는다.
  ⑦ **측정**: 조사 `done` instrumentation에 가산 키 `tool_batch_sizes`·`max_tools_per_turn`·`turns_n`(HolmesGPT 턴) · 플레이북 경로 `stage_wall_s`·`collect_s`·`opinion_wait_s`·`synthesis_s`·`deep_dive_wait_s`. 오프라인 하네스 `sre_agent/scripts/investigation_bench/playbook_timeline.py`(녹화 픽스처 + 지연 주입 · LLM 가짜).
  ⑧ **불변**: D-347 부하 상한(전역 도구 8 · 배치 4 · apm in-flight 8 · 시간당 예산 20)과 D-341 ㊹ 시간 사슬 값은 바꾸지 않는다. 투기 실행·가설별 다중 HolmesGPT는 하지 않는다(`plans/200` §6).
- **근거**: `plans/200` §1(코드 실측) · 오프라인 하네스(도구 0.5s·LLM 1s 지연 · 3회): 플레이북 수집 벽시계 off → DAG on — was.latency `case3_cpu_loop` 4.04~4.09s → 3.53~3.58s · `case1_jdbc_acquire` 4.05~4.08 → 3.54~3.57 · host.cpu 4.05~4.10 → 3.03~3.07 · host.process 4.55~4.60 → 3.55~3.57. 해석 지연 교정 후 재측정(2회): 실행 기록 off host.cpu 3.06 · host.process 3.55 · `case3_cpu_loop` 3.54 / 실행 기록 on 3.08 · 3.60 · 3.60(끝 flush 0.03~0.06s). 판독 입력을 실행 의존에 넣는 안은 was.latency 단축을 0(4.04s)으로 만들어 기각했다. 축 동시 단독(지연 0.2s): S5 415→216ms · S7 422→213ms. 축 동시는 DAG 위에서 추가 효과가 거의 없다(S5·S7이 임계 경로 S0r→S2→S3a→S3b 밖). 녹화 픽스처 12건 × {DAG, DAG+축}에서 최종 결과(섹션·판독·가설 순위·notes·호출 목록)가 off와 같다.

- **주의**: 조사 전체 완료는 HolmesGPT 종료(최대 600s)에 묶이므로 플레이북 단축은 주로 부분 브리핑·플레이북 섹션이 먼저 보이는 시각을 앞당긴다. DAG에서 슬롯을 기다리다 예산이 끝난 스텝은 「스텝 미시작」(missing)이 아니라 `skipped(budget)`다(on 경로만). 지침 변형의 효과는 모델 순응도에 달려 내부망 vLLM에서 `max_tools_per_turn` off/on으로 판단하고, 개선이 없으면 off로 남긴다. 로컬 MLX 확인은 이 체크아웃의 두 평면이 mlx가 아니어서(워커 ollama · 오케스트레이터 vllm) 내부망으로 이월했다.
