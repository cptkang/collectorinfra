- **배경**: 사용자 지시 원문(순서대로) ① *"제니퍼 연동은 sre_agent처럼 별도의 소스로 구분하여 구현하도록 계획이 되어 있냐?"* ② *"데이터 소스이긴 하지만 WAS의 상태를 조회하거나 분석하는 등의 노이즈 캔슬링이나 장애 진단, 분석 등에서 사용될 데이터 소스이다. 제니퍼 연동기능은 별도의 패키지 형식으로 분리하는 것에 대해 검토하라."* ③ (검토 보고 뒤) *"권고에 맞게 계획을 수정하라."* 실측: `plans/87` v2.2까지는 제니퍼를 `mcp_server`의 세 번째 소스로 편입했다(D-119 ① "별도 서버가 아니라 이 경계의 확장"). 그러나 제니퍼 연동은 얇은 조회 래퍼가 아니다 — 인스턴스↔hostname 정합 · WAS 시그니처 결정적 판정 · 이벤트 폴링·정규화 · OpenMetrics 노출을 모두 갖고, 소비자가 셋(`noise_gate`·`sre_agent`·`src`)이다. D-119가 C안(별도 Prometheus MCP 서버)을 기각한 사유 *"얇은 래퍼에 패키지·프로세스·인증 과중"*은 이 성격에 해당하지 않는다. 또 제니퍼 토큰 하나가 쓰기·제어 API까지 연다(`plans/87` §0.4 · §1.3-3).
- **결정**:
  ① **D-119 ① 개정** — "향후 관측 소스 추가도 별도 서버가 아니라 이 경계의 확장으로 편입한다" → **"도메인 판정 로직이나 별도 자격증명을 가진 관측 소스는 독립 게이트웨이 패키지(자체 MCP 서버)로 둘 수 있다. 얇은 조회 래퍼는 종전대로 `mcp_server`로 확장한다."** D-119 ②~⑤(Prometheus 도구 일원화 · hostname 서버측 조립 · 자격증명·타임아웃 서버측 · 지침 일원화)는 유지한다. ④의 "감사 한 곳"은 게이트웨이 소스에 한해 "같은 감사 형식 + 조사 id·thread_id 전파"로 완화된다. ⑥은 제니퍼 배포 환경에서 `sre_agent` MCP 엔드포인트가 둘이 되는 결과만 생긴다.
  ② **제니퍼 적용 — 최상위 패키지 `apm_gateway/`**(D-139 신규 최상위 패키지 · `sre_agent`(D-118)·`mcp_server`와 같은 격) — 자체 `pyproject.toml` · 자체 cwd · 루트 venv 공유(`mcp_server` 전례 · 둘 다 ≥3.11) · 2단 중첩(D-139 ③ — 자체 cwd라 무해) · 독립 프로세스(자체 MCP 서버 · 정적 Bearer D-125). 내부 계층: `domain/`(WAS 시그니처 결정적 판정 · 이벤트 모델 · 레벨 매핑) · `adapters/jennifer/`(Open API 클라이언트 · GET·경로 허용목록 코드 상수 — 벤더 리터럴 격리) · `application/`(인스턴스↔hostname 정합 · 축약·마스킹 · 이벤트 폴러) · `interface/`(MCP 서버 `apm_*` 도구 · Bearer · 감사 · (J7) `/metrics/apm`). `tests/`·`scripts/`·`testdata/`(recorded JSON)를 소유한다(D-139). 패키지명은 도구 표면 `apm_*`·레지스트리 솔루션 `apm`과 맞춘다.
  ③ **경계 불변식** — `apm_gateway` ↔ `src`·`noise_gate`·`sre_agent`·`mcp_server` 양방향 import 0. 통신은 MCP · Redis Stream(`alarm:raw`) · HTTP 스크레이프 계약만. `sre_agent/tests/test_boundary.py` 방식의 불변식 테스트가 J1 수용 기준이다.
  ④ **이벤트 생산자** — 제니퍼 이벤트 폴러는 게이트웨이 안에 둔다. 게이트웨이가 `alarm:raw` 생산자가 된다(`noise_gate/alarm_server/base_receiver.py:44` XADD와 같은 형식). `plans/87` G-4의 폴링 경로 선택(① `mcp_server` 경유 / ② 직접 호출 — 자격증명 2곳)은 **해소**된다. 어댑터 push(2단계)의 착수 여부·방식은 미결로 남는다.
  ⑤ **WAS 판정 단일 정의** — WAS 시그니처의 결정적 판정은 게이트웨이 `domain/`에 두고, `noise_gate`(`app_impact` 승격)와 `sre_agent`(severity)가 MCP 결과로 함께 쓴다(D-035). 알람 kind 분류(`classify_alarm_kind`의 apm 선판정 — `plans/87` R-16)는 `noise_gate`에, 조사 지침·`ANCHORED_TOOLS`·권고 표는 `sre_agent`에 남긴다.
  ⑥ **폴스타 정합 브릿지** — 게이트웨이는 폴스타 DB 자격증명을 갖지 않는다. `was_object` 조회는 게이트웨이가 `mcp_server`를 MCP로 호출해 수행한다(TTL 캐시). 의존은 게이트웨이 → `mcp_server` 한 방향이다. 필요하면 `mcp_server`에 폴스타 고수준 도구 1종을 추가한다(`plans/87` J1).
  ⑦ **소비자 연결(예정)** — `sre_agent` `_build_mcp_servers()`에 `"apm"` 항목 + `AgentSettings.apm_mcp_url`·`apm_mcp_token`(holmes `Config.mcp_servers`는 dict — D-119 실측) · `noise_gate` 신규 MCP 클라이언트(`noise_gate/infrastructure/sre_agent_client.py` 전례) · `src` 2단 처리기의 두 번째 MCP 엔드포인트(`plans/121` 처리기 계약 · 현행 `DBHubConfig.server_url`은 하나) · Prometheus는 `/metrics/apm` 스크레이프.
  ⑧ **옮기지 않는 것** — L2 실행기(`remediation/` · `plans/87` G-7) — 게이트웨이는 읽기 전용이고 실행 자격증명을 갖지 않는다.
- **근거**: ①토큰 격리 — 쓰기·제어 API까지 여는 제니퍼 토큰을 폴스타 DB 자격증명과 다른 프로세스에 둔다 ②장애 격리 — 제니퍼 API 지연·폴링·캐시가 폴스타 조회 프로세스에 영향을 주지 않는다 ③선택 배포 — 제니퍼가 없는 환경에는 패키지를 배포하지 않는다 ④WAS 판정 단일 정의 — `plans/87` R-16의 `classify_alarm_kind` 이중 정의 같은 문제의 재발 방지 ⑤코드 0건이라 지금은 문서 비용만 든다.
- **`plans/87` §2.8 대안 ③ 기각 사유의 재해석**: (b) 토큰이 클라이언트 헤더로 넘어감 · (c) 허용목록·감사 부재 · (d) P4 통제 밖은 셋 다 **"제니퍼 공식 MCP 직결"**에만 해당하고 자체 게이트웨이에는 해당하지 않는다. (a) D-119 ① 위반은 이 결정으로 해소된다. 공식 MCP 직결 기각과 `plans/87` **G-8(공식 MCP 미채택)·G-1(API 위주)은 유지**한다 — 새 안은 "우리가 만든 게이트웨이가 Open API를 직접 호출"하는 것이다.
- **비용·완화**: 감사가 두 프로세스로 나뉜다(D-119 ④ 약화) → 같은 감사 형식 + 조사 id·thread_id를 호출 인자로 전파 · 운영 대상 1세트 추가(프로세스·포트·Bearer·헬스체크) → 제니퍼가 있는 환경에만 배포 · Bearer 미들웨어(`mcp_server/mcp_server/server.py:31` 약 40행)·반환 계약 복제(소규모) · OpenMetrics 직렬화기(`om_exposition.py` 321행)는 복제/공용 추출을 J7 착수 시 결정 · 게이트웨이 → `mcp_server` 1 hop → 캐시로 흡수 · `arch_check`·`overfit_check` 스캔 편입 여부는 구현 시 결정(벤더 리터럴은 `adapters/jennifer/`에 격리) · `CLAUDE.md` 「저장소 지도」·「패키지 경계」 표 갱신은 **패키지를 실제로 만드는 J1의 산출물**(이 결정 시점에는 수정하지 않는다).
