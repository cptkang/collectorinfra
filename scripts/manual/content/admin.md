이 매뉴얼은 Infra Query Agent를 **설정·운영하는 관리자**용 안내서다. 사용자 화면의 기능은 [사용자 매뉴얼](/manual/user)에서 다루고, 여기서는 반복하지 않는다.

- 1~10장은 웹 화면(관리자 대시보드·노이즈 관제)과 화면 없는 관리 API를 다룬다.
- 11장(운영)은 요약과 기준 문서 링크만 둔다. 절차의 정본은 저장소 `docs/`다.
- 화면 캡처는 테스트 환경에서 찍었다. DB 목록·설정값은 설치 환경마다 다르다.

## 1. 관리자 개요

권한 구조와 관리자 화면에 들어가는 방법이다.

### A-01
::: what
역할은 **user**와 **admin** 두 가지다. 화면 문구의 「운영자」는 admin 권한을 뜻한다.

| 구분 | 할 수 있는 일 | 판정 |
|---|---|---|
| user | 질의·양식 채우기·알람 수신(권한 존만)·노이즈 관제 조회 | 사용자 토큰 + DB 조회 권한 |
| admin | user 기능 전부 + 관리자 대시보드·관리자 노이즈 관제·관리 API | 사용자 토큰의 DB 역할이 admin |
| break-glass 운영자 | admin과 같다 | `/admin/login`으로 받은 운영자 토큰(`.env`의 부트스트랩 계정) |

`AUTH_ENABLED=false`(개발 모드)면 모든 요청이 익명으로 통과하고 Admin 링크도 항상 보인다.
:::
::: how
1. 운영 환경은 `AUTH_ENABLED=true`로 둔다. 이때 `ADMIN_USERNAME`·`ADMIN_PASSWORD`·`ADMIN_JWT_SECRET`·`AUTH_JWT_SECRET`이 없으면 서버가 기동을 거부한다.
2. 최초 기동 시 활성 관리자가 0명이면 부트스트랩 계정이 admin 사용자로 한 번 만들어진다.
3. 다른 사용자를 관리자로 만들려면 [사용자 관리](#a-30)에서 역할을 admin으로 바꾼다.
:::
::: ui -
화면 캡처가 없다. 권한 판정은 서버에서 하며, 화면의 링크 숨김은 편의 기능일 뿐이다.
:::
::: caution
- 화면 HTML(대시보드·매뉴얼 포함)은 서버에서 막지 않는다. 데이터와 조작은 API가 권한을 검사한다.
- 관리자(admin)는 「조회 가능 DB」 목록과 관계없이 전체 DB를 조회할 수 있다.
:::
::: related
- [A-02 관리자 화면에 들어가는 두 가지 길](#a-02)
- [A-30 역할·상태·알림그룹](#a-30)
:::

### A-02
::: what
관리자 대시보드(`/admin`)에 들어가는 길은 둘이다.

1. **admin 사용자로 로그인** → 메인 화면 머리글의 **Admin** 링크(새 탭)
2. **break-glass 운영자 로그인** → `/admin/login`에서 `.env` 부트스트랩 계정으로 로그인
:::
::: how
1. 평소에는 1번을 쓴다. 감사 로그에 실제 사용자 ID가 남는다.
2. 사용자 DB에 문제가 있어 로그인할 수 없을 때만 2번을 쓴다.
:::
::: ui admin-login 운영자 로그인(break-glass)
1. 운영자 ID
2. 비밀번호
3. 사용자 화면으로 돌아가기
:::
::: caution
- 운영자 토큰은 사용자 토큰과 다른 시크릿으로 서명된다(`ADMIN_JWT_SECRET`). 두 시크릿을 같게 두지 않는다.
- 토큰이 없이 `/admin`을 열면 로그인 화면으로, 권한이 없으면(403) 메인 화면으로 돌려보낸다.
:::
::: related
- [A-01 권한 체계](#a-01)
:::

## 2. 환경변수 설정

`.env` 설정을 화면에서 조회·수정한다. 목록은 코드의 설정 정의에서 자동으로 만들어지므로 새 설정도 코드 수정 없이 여기에 나타난다.

### A-04
::: what
설정은 그룹(LLM, 오케스트레이터, 시멘틱 라우터 …)별로 접혀 있다. 검색과 필터로 원하는 항목을 찾는다.
:::
::: how
1. 검색창에 설정 키(`LLM_PROVIDER`)나 설명의 낱말을 적는다.
2. 필터로 좁힌다.
   - **전체**
   - **변경됨(미저장)**: 화면에서 고쳤지만 아직 저장하지 않은 항목
   - **기본값과 다름**: `.env`에 기본값과 다른 값이 있는 항목
   - **리로드 반영**: 저장 후 「설정 리로드」로 반영되는 항목
   - **재시작 필요**: 서버를 재시작해야 반영되는 항목
3. 그룹 제목을 눌러 펴고 접는다.
:::
::: ui settings-list 환경변수 설정
1. 검색
2. 모두 펼치기
3. 설정 리로드
4. 저장
:::
::: caution
- 이 화면은 본체 서버의 설정만 다룬다. `mcp_server/.env`·`mcp_server/config.toml`, `sre_agent/.env`는 각 프로세스가 따로 읽으므로 파일을 직접 고치고 그 프로세스를 재기동한다(화면 아래 「이 화면 범위 밖 설정」).
:::
::: related
- [A-07 등급과 반영 시점](#a-07)
:::

### A-05
::: what
기본 화면은 자주 바꾸는 설정만 보여 준다. 나머지는 체크로 드러낸다.
:::
::: how
1. **고급 설정 표시**: 기본값을 쓰는 것이 원칙인 내부 상수급(C등급) 설정까지 보인다.
2. **미소비 필드 표시**: 코드에 정의는 있으나 현재 어디서도 읽지 않는 설정까지 보인다.
3. **모두 펼치기**: 모든 그룹을 편다.
:::
::: ui settings-list 환경변수 설정
2. 모두 펼치기
:::
::: caution
- 미소비 필드는 값을 바꿔도 동작에 영향이 없다. 정리 대상인지 판단하는 용도로만 본다.
:::
::: related
- [A-04 설정 목록·검색·필터](#a-04)

### A-06
::: what
항목 옆 **?** 를 누르면 오른쪽에 상세 설명이 열린다. 무엇을 제어하는지, 값마다 어떻게 동작하는지, 운영에서 쓰는 값이 무엇인지 나온다.
:::
::: how
1. 항목의 **?** 를 누른다.
2. 오른쪽 패널에서 「운영 설명」, 현재값·기본값, 값에 따른 동작을 읽는다.
3. **×**로 닫는다.
:::
::: ui settings-help 설정 상세 설명
:::
::: caution
- 상세 설명이 준비된 항목만 내용이 나온다. 원천은 저장소 `config/settings_help/*.yaml`(21개 그룹)이며, 이 매뉴얼은 그 내용을 옮기지 않는다.

### A-07
::: what
항목마다 **반영 시점** 배지와 **등급**이 있다.

| 반영 시점 | 뜻 |
|---|---|
| 즉시 | 저장하면 바로 반영 |
| 리로드 | 저장 후 **설정 리로드**를 누르면 재시작 없이 반영 |
| 재시작 | 서버를 재시작해야 반영 |

| 등급 | 뜻 | 예 |
|---|---|---|
| A | 설치마다 정해야 하는 환경 결속값(주소·포트·프로바이더·활성 DB) | `LLM_PROVIDER`, `ACTIVE_DB_IDS` |
| B | 운영 중 조정하는 레버 | 시간 초과, 재시도 예산 |
| C | 내부 상수급 — 기본값을 쓴다(기본 화면에서 숨김) | 저장 경로, 보관 일수 |
:::
::: how
1. 바꾸기 전에 배지로 반영 시점을 확인한다.
2. 「재시작」 항목은 저장 후 서버 재시작 계획을 세운다.
:::
::: ui settings-group 펼친 그룹 — 항목별 반영 시점 배지
:::
::: caution
- 설정은 기동할 때 한 번 해석된다. 요청 처리 중에 값을 바꾸는 경로는 없다.
:::

### A-08
::: what
항목의 **기본값으로**를 누르면 `.env`에서 그 줄을 지우고 코드 기본값을 쓰게 한다.

:::
::: caution
- OS 환경변수로 같은 키가 주입돼 있으면 `.env`를 지워도 그 값이 쓰인다([A-12](#a-12)).

::: related
- [A-09 저장과 변경 확인](#a-09)

### A-09
::: what
**저장**을 누르면 바뀐 항목을 전·후 값으로 보여 주는 확인 창이 뜬다. 확인하면 `.env`에 기록된다.
:::
::: how
1. 값을 고친다. 그룹 제목에 「미저장 N건」이 표시된다.
2. **저장**을 누른다.
3. 확인 창에서 전(붉은 줄)·후(초록 줄) 값과 반영 시점 배지를 확인하고 **저장**, 아니면 **취소**를 누른다.
4. 결과 알림에서 재시작 필요 항목, 무시된 항목, DB 준비도 경고를 확인한다.
:::
::: ui settings-diff 변경 확인 창
1. 저장(확정)
2. 취소
:::
::: caution
- 시크릿 항목은 저장해도 반영되지 않는다(무시된 항목으로 알린다).
- 저장만으로는 「리로드」·「재시작」 항목이 반영되지 않는다.
:::
::: related
- [A-10 설정 리로드](#a-10)

### A-10
::: what
**설정 리로드**는 서버를 재시작하지 않고 「리로드」 항목을 반영한다. 설정을 새로 읽고, 운영 검사를 다시 하고, 실행 그래프를 다시 만든 뒤 한 번에 교체한다.
:::
::: how
1. 저장을 마친 뒤 **설정 리로드**를 누른다.
2. 결과 알림을 확인한다. 실패하면 기존 설정이 그대로 유지된다.
:::
::: ui settings-list 환경변수 설정
3. 설정 리로드
:::
::: caution
- 리로드 중 들어온 질의는 이전 설정으로 끝까지 처리된다.
- 「재시작」 항목은 리로드로 반영되지 않는다.
:::
::: related
- [A-07 등급과 반영 시점](#a-07)

### A-11
::: what
비밀번호·API 키 같은 **시크릿**은 `.encenv`에서 관리한다. 화면에는 🔒 **.encenv 관리** 표시와 설정 여부(설정됨·미설정)만 나오고 값은 보이지 않는다.
:::
::: how
1. 시크릿을 바꾸려면 서버의 `.encenv` 파일을 직접 고친다.
2. 서버를 재시작하거나 리로드한다.
:::
::: ui -
화면 캡처가 없다. [A-06](#a-06) 그림의 `LLM_OLLAMA_API_KEY` 줄이 시크릿 항목의 표시다.
:::
::: caution
- 화면에서 시크릿을 입력해도 저장되지 않는다. `.encenv` 파일은 저장소에 커밋하지 않는다.
:::
::: related
- [A-09 저장과 변경 확인](#a-09)
:::

### A-12
::: what
같은 키가 OS 환경변수나 `.encenv`에도 있으면 그 값이 `.env`보다 우선한다. 화면은 이 경우 **덮인 값**임을 표시하고 실제로 적용 중인 값(실효값)을 함께 보여 준다.
:::
::: how
1. 항목 상태에서 「OS 환경변수가 덮음」 같은 표시를 확인한다.
2. 화면에서 바꿔도 반영되지 않으면, 서버 기동 스크립트나 서비스 설정의 환경변수를 확인한다.
:::
::: ui -
화면 캡처가 없다. 덮인 항목이 있을 때만 나타나는 표시다.
:::
::: caution
- 서버 작업 디렉터리가 프로젝트 루트와 다르면 화면이 고치는 `.env`와 서버가 읽는 `.env`가 다를 수 있다. 이때 화면 위에 경고가 뜬다.
:::

## 4. DB 구조

질의에 쓰는 DB 구조 정보(프로필)를 관리한다. **질의 경로는 DB 구조를 분석하지 않는다.** 구조 분석·승인·버전 관리는 이 탭에서만 한다.

### A-16
::: what
MCP 서버에 연결된 소스를 레지스트리·`ACTIVE_DB_IDS`와 대조해 표로 보여 준다.

| 열 | 뜻 |
|---|---|
| 연결 | MCP 소스로 보이는지 |
| 등록·활성 | 레지스트리 등록 여부, 활성 DB 여부 |
| 불일치 | MCP·레지스트리·활성 목록 사이의 어긋남 |
| 구조 정보 | 수동 프로필·승인본 유무 |
| 준비도 | 필수·권장 조건 충족 수 |
:::
::: how
1. **DB 구조** 탭을 연다.
2. **새로고침**으로 다시 읽는다.
3. 행의 **상세**·**신규 연동**으로 들어간다.
:::
::: ui dbs-list 소스 목록
:::
::: caution
- 이 화면은 레지스트리·`.env`·MCP 설정 파일을 직접 쓰지 않는다. 필요한 조각을 내려받아 사람이 반영한다([A-26](#a-26)).
- `DB_BACKEND=direct`면 MCP 소스 목록을 조회할 수 없어 연결 칸이 「확인 못 함」으로 나온다.
:::
::: related
- [A-17 소스 상세](#a-17)
:::

### A-19
::: what
새 DB를 질의 대상으로 쓰기까지의 9단계(O-1~O-9)를 순서대로 실행한다.

| 단계 | 내용 |
|---|---|
| O-1 | 발견·연결 확인 |
| O-2 | 스키마 수집·캐시 등록 |
| O-3 | 설명 범위(테이블) 선정 |
| O-4 | 컬럼 설명·유사어 초안(LLM) |
| O-5 | DB 설명 초안(LLM) |
| O-6 | 구조 분석·승인 |
| O-7 | 부속 등록(시드·값 인덱스) |
| O-8 | 설정 조각 내보내기 |
| O-9 | 마무리 점검 |
:::
::: how
1. 목록에서 **신규 연동**을 누른다.
2. 위쪽 요약에서 필수·권장 미충족 항목을 확인한다.
3. 단계마다 **실행**·**초안 생성**을 누르고, 초안은 해당 영역으로 이동해 검토·적용한다.
4. O-8에서 조각을 내려받아 레지스트리·`.env`에 반영하고 앱을 재기동한다.
:::
::: ui dbs-register 신규 연동 등록 단계
:::
::: caution
- O-4·O-5는 LLM을 호출한다. 예상 호출 수가 화면에 표시되므로 확인하고 실행한다.
- 환경(MCP 주소)이 캐시를 만든 환경과 다르면 C7 경고가 나온다. 다른 환경의 캐시로 등록하지 않는다.
:::
::: related

### A-59
::: what
노이즈 캔슬링의 처리 흐름과 **누가 판단하는지**를 정리한다. 요지는 **판단은 결정적 규칙이 하고, LLM과 통계는 보조 입력만 낸다**는 것이다. 학습된 머신러닝 모델은 쓰지 않는다(도입 계획은 저장소 `plans/117`).

```
폴스타 알람 → 알람 수신부(TCP 9100) → Redis Stream alarm:raw
  → AlarmWorker(본체 프로세스)
     ① 지문 중복 제거·재통보 창, 최소 심각도 필터      규칙
     ② 컨텍스트 수집: 이력 통계·프로세스·중요도·유지보수·토폴로지·변경   조회·통계
     ③ 알람 분석: 요약·원인·패턴·일상 반복 여부            LLM(자문)
     ④ (옵션) agentic 보강: 읽기 전용 도구로 추가 신호      LLM(상향만)
     ⑤ 발송 판단: 4-티어 결정 + 결정 기록                  결정적 규칙
     ⑥ 통보: PAGE 쪽지 / TICKET 일배치+카드 / DASHBOARD 카드 / SUPPRESS 기록만
```

| 주체 | 하는 일 | 할 수 없는 일 |
|---|---|---|
| 결정적 규칙(`noise_gate/domain/notification_policy.py`) | 티어 결정 전부 | — |
| LLM | 요약·원인 서술, 일상 반복 판단, 피드백 기반 액션가능성 의견, 메시지 알람 심각도 상향 | 티어 결정, 심각도 하향, 심각도 3 억제 |
| 통계(Holt-Winters·STL·Nagios 플래핑·Jaccard 군집) | 이상 점수, 플래핑·상관 여부 같은 신호 산출 | 단독 억제 결정(규칙이 신호를 소비) |
| 임베딩 | 근접 중복 주석 | 판정·지문 변경 |
:::
::: how
1. 게이트가 켜져 있는지 [환경변수 설정](#a-04)의 노이즈 게이트 그룹에서 `NOISE_ENABLE_NOISE_GATE`를 확인한다(코드 기본 `false`).
2. 판단 결과는 `logs/alarm_decisions.jsonl`(`NOISE_DECISION_STORE_PATH`)에 알람마다 한 줄씩 쌓인다. 화면에서는 [노이즈 관제](#a-42)의 결정 이력·결정 추적으로 본다.
3. 개별 알람이 어떻게 판단됐는지는 [A-60](#a-60)의 단계 표와 결정 추적의 판단 경로를 맞춰 본다.
:::
::: ui -
화면 캡처가 없다. [A-42](#a-42) 그림의 퍼널과 결정 이력을 본다.
:::
::: caution
- **게이트가 꺼져 있으면** 분석만 하고 최소 심각도(`ALARM_MIN_SEVERITY`) 이상 알람을 모두 통보한다. 노이즈 관제 화면에도 판단이 쌓이지 않는다.
- 지문 중복으로 걸러진 재발은 판단 레코드가 아니라 `type="recurrence"` 레코드로만 남는다. 발생 건수를 셀 때 둘을 합친다.
- 게이트가 켜진 상태에서 `1 ≤ 심각도 < ALARM_MIN_SEVERITY` 알람은 판단 전에 **기록 없이** 버려진다. 주의(1) 알람까지 보려면 `ALARM_MIN_SEVERITY=1`로 둔다.
:::

- [A-60 결정 단계와 우선순위 매트릭스](#a-60)

### A-60
::: what
발송 판단은 아래 단계를 **위에서부터** 평가하고, 먼저 확정된 단계가 결과가 된다. 「관제 표시명」은 퍼널·결정 추적에 나오는 이름이다.

| 순서 | 관제 표시명 | 조건 | 결과 | 켜는 설정(코드 기본) |
|---|---|---|---|---|
| (워커) | — | 같은 지문(DB·서버·알람명·자원명)이 재통보 창 안에 다시 옴 | 판단 없이 재발 기록 | `NOISE_REPEAT_INTERVAL_SECONDS`=14400 · 심각도 3은 `NOISE_SEV3_REPEAT_INTERVAL_SECONDS` |
| 0.5 | 비운영 알람 | 알람 마커 없음 + 승인·안내·공지 마커 있음 | SUPPRESS | `NOISE_NON_ALARM_FILTER_ENABLED`(false) |
| 3 | 심각도3 단락 | 실효 심각도 3 | **PAGE** | 항상 |
| 4 | 자가복구 상관 · 독립 해소 | 해소 알람. 창 안에 짝 발생이 있으면 자가복구 | SUPPRESS(독립 해소는 설정에 따라 DASHBOARD) | `NOISE_SELF_HEAL_WINDOW_SECONDS`=300 · `NOISE_RESOLVED_TO_DASHBOARD`(false) |
| 5 | 수집 실패 보수화 | 중요도·유지보수 신호 수집 실패 + 심각도 ≥1 | **PAGE** | 항상 |
| 6 | 유지보수 | 폴스타 유지보수 모드 | SUPPRESS | 항상 |
| 6.2 | 침묵 규칙 | [침묵 규칙](#a-45) 매칭 | SUPPRESS | `NOISE_SILENCE_ENABLED`(false) |
| 6.4 | 의존성 연쇄 | 부모(또는 다홉 조상) 자원 비정상 | SUPPRESS, 다홉에서 근본원인 미통보면 DASHBOARD | `NOISE_DEPENDENCY_SUPPRESSION`(false) · `NOISE_MULTI_HOP_CASCADE_ENABLED`(false) |
| 6.5 | 인히비션 | 같은 서버에 더 높은 심각도 발생 중 | SUPPRESS | `NOISE_INHIBITION_ENABLED`(false) |
| 6 | 플래핑 | 상태 진동(가중 상태변화율, 임계 low 5 / high 20) + 심각도 ≤ 억제 상한 | SUPPRESS | `NOISE_FLAPPING_ENABLED`(false) |
| 7 | 스톰 | 같은 서버에 창(60초) 안 다발(5건 초과) | 대표 외 SUPPRESS | `NOISE_STORM_GROUPING_ENABLED`(false) |
| 7.5 | 크로스-호스트 상관 | 서버를 넘어 유사 알람 군집(Jaccard ≥ 0.5, 120초) | 대표 외 SUPPRESS | `NOISE_CROSS_HOST_CORRELATION_ENABLED`(false) |
| 7.7 | 계획-무해 주석 | 계획작업 주석 **그리고** 해소·상관·변경 근접 중 하나 | DASHBOARD | `NOISE_ANNOTATION_PLANNED_SUPPRESS`(false) |
| 8~9 | 우선순위 매트릭스 | 위 단계에 걸리지 않음 | 매트릭스 + 보조 조정 | 항상 |

**8단계 매트릭스**(실효 심각도 × 중요도):

| | 중요도 높음 | 보통 | 낮음 |
|---|---|---|---|
| 심각도 2(경고) | PAGE | TICKET | DASHBOARD |
| 심각도 1(주의) | TICKET | DASHBOARD | DASHBOARD |

중요도는 폴스타 `IMPORTANCE_ID`를 `NOISE_IMPORTANCE_VALUE_MAP_CSV`로 높음·보통·낮음에 대응시키며, 대응이 없으면 **보통**이다. 정의되지 않은 심각도는 보수적으로 PAGE다.

**9단계 보조 조정** — 신호를 승격·강등 목록으로 모은 뒤 **승격이 하나라도 있으면 1단계 승격(강등 무시)**, 승격 없이 강등만 있으면 1단계 강등(하한 SUPPRESS).

| 방향 | 신호 | 조건 |
|---|---|---|
| 승격 | 폴스타 통보 정책 `notify` | — |
| 승격 | LLM `is_routine=false`(평소와 다른 패턴) | — |
| 승격 | LLM 액션가능성 `actionable` | `NOISE_ENABLE_LLM_ACTIONABILITY` |
| 승격 | 변경 근접(알람 직전 변경 이력) | `NOISE_CHANGE_CORRELATION_ENABLED` |
| 강등 | 폴스타 비통보 정책 `suppress` | — |
| 강등 | LLM `is_routine=true`(일상 반복) | 실효 심각도 ≤ `NOISE_SUPPRESS_MAX_SEVERITY`(2) |
| 강등 | LLM 액션가능성 `noise` | 위 조건 + `NOISE_ENABLE_LLM_ACTIONABILITY` |
:::
::: how
1. 결정 추적의 **판단 경로**에서 결과를 정한 단계를 찾고, 이 표의 같은 표시명 행에서 조건과 설정을 확인한다.
2. 매트릭스 단계면 사유가 `매트릭스(심각도N×중요도X) → 기본 티어 · 승격/강등: … → 최종 티어` 형식이다. 기본 티어와 승격·강등 사유가 결정 추적의 근거에 따로 남는다.
3. 설정 값은 [정책 조회](#a-46)에서 보고, 바꿀 때는 [환경변수 설정](#a-04)에서 고친다.
:::
::: ui -
화면 캡처가 없다. [A-46](#a-46) 정책 그림의 매트릭스와 [A-42](#a-42) 그림의 퍼널을 본다.
:::
::: caution
- **심각도 3은 3단계에서 끝나므로 침묵·의존성·스톰·피드백 어떤 것도 닿지 않는다.** 예외는 0.5단계(비운영 알람)뿐이며, 이는 승인·안내 문구처럼 알람 마커가 전혀 없는 메시지에만 적용된다.
- 억제 계열 단계는 대부분 코드 기본 off다. 켤 때는 [운영 판단 요령](#a-47)대로 억제율 변화를 먼저 본다 — 재현율 우선 원칙.
- 9단계 이동은 항상 **1단계**다. PAGE를 한 번에 SUPPRESS로 내리는 경로는 없다.
:::

### A-61
::: what
판단에 **보조 입력**으로 들어가는 LLM·통계 신호와 운영자 피드백이 어디서 어떻게 쓰이는지 정리한다. 모두 결정 기록의 신호 스냅샷에 남는다.

| 신호 | 방식 | 판단에 들어가는 곳 | 켜는 설정(코드 기본) |
|---|---|---|---|
| 알람 분석(요약·원인·패턴·`is_routine`) | LLM 1회 호출 | 9단계 승격·강등 | 게이트 흐름에 항상 포함 |
| 액션가능성(`llm_actionability`) | 같은 LLM 호출에 운영자 피드백 예시를 넣어 판단(추가 호출 없음) | 9단계 승격·강등 | `NOISE_ENABLE_LLM_ACTIONABILITY`(false) |
| AI 심각도 상향 | 메시지형 알람의 등급을 LLM이 **올리기만** 함 | 1단계 실효 심각도 = max(폴스타, AI) | `NOISE_ENABLE_AI_SEVERITY_BOOST`(false) |
| 동적 baseline | Holt-Winters(선택 시 STL) 잔차 z-score → 상향 후보 | 위 AI 상향 경로로 반영 | `NOISE_DYNAMIC_BASELINE_ENABLED` **그리고** `NOISE_ENABLE_AI_SEVERITY_BOOST` · STL은 `NOISE_ANOMALY_STL_ENABLED` |
| agentic 보강 | 오케스트레이터 LLM이 읽기 전용 도구로 신호 수집 | 심각도 상향만 | `NOISE_ENABLE_AGENTIC_ENRICHER`(false) |
| 주석 LLM 분류 | 운영자 손글 주석(계획작업·해소)을 LLM이 분류, 실패 시 정규식 | 7.7단계 | `NOISE_ANNOTATION_LLM_CLASSIFICATION_ENABLED`(false) |
| 변경 근접 | 알람 직전 창(3600초)의 변경 이력과 자원 매칭 | 9단계 **승격만** | `NOISE_CHANGE_CORRELATION_ENABLED`(false) |
| 임베딩 근접 중복 | 로컬 임베딩 코사인 유사도 | **주석 전용**(판정 무관) | `NOISE_SEMANTIC_DEDUP_ANNOTATION_ENABLED`(false) |

**운영자 피드백이 반영되는 경로**(알람 카드의 **유효**·**노이즈**):

1. 라벨이 `logs/alarm_feedback.jsonl`(`NOISE_FEEDBACK_STORE_PATH`)에 한 줄 쌓인다.
2. 다음에 같은 **알람명**이 오면 과거 라벨 중 알람명이 같은 것만 후보로 고르고, 자원명 일치 +2점·패턴 일치 +1점, 동점이면 최신 순으로 최대 `NOISE_ACTIONABILITY_FEWSHOT_COUNT`(3)건을 프롬프트에 넣는다.
3. LLM이 `actionable` 또는 `noise`를 낸다. 예시가 없으면 의견도 없다.
4. 9단계에서 `actionable`은 승격, `noise`는 조건부 강등으로 소비된다.
:::
::: how
1. 피드백 반영을 쓰려면 `NOISE_ENABLE_NOISE_GATE`·`NOISE_ENABLE_LLM_ACTIONABILITY`·`NOISE_FEEDBACK_STORE_ENABLED`를 모두 켠다. 앞의 둘 중 하나라도 꺼져 있으면 피드백 API가 503(「피드백 비활성」)을 돌려준다. 저장소 설정이 꺼져 있으면 요청은 받아도 라벨이 저장되지 않는다.
2. 반영 여부는 결정 추적 **신호 스냅샷**의 **LLM 액션가능성** 값과 사유의 「승격:」·「강등:」 문구로 확인한다.
3. 쌓인 라벨은 [알람 피드백 요약](#a-39)에서 본다. 같은 알람에 유효·노이즈가 엇갈리면 최신 라벨이 우선한다.
:::
::: ui -
화면 캡처가 없다. [A-39](#a-39) 알람 피드백 그림을 본다.
:::
::: caution
- 피드백은 **명령이 아니라 자문**이다. 최대 1단계, 다음 알람부터이며, 승격 신호가 하나라도 있으면 노이즈 라벨은 무시된다. 심각도 3에는 닿지 않는다.
- 조회 키는 알람명이다. 서버별로 따로 학습되지 않고, 누른 횟수에 가중치도 없다.
- **억제(SUPPRESS)된 알람은 카드가 뜨지 않아 피드백을 달 수 없다.** 잘못 억제된 알람은 결정 이력이나 억제 포함(감사) 표시 레벨로 찾는다.
- LLM을 부르는 기능은 알람 유입량만큼 호출이 는다. 운영 LLM이 과금 경로라면 켜기 전에 승인을 받는다.
:::

#### 설정 키 색인

환경변수 설정 화면의 상세 설명은 저장소 `config/settings_help/` 아래 21개 파일에서 온다. 아래 표는 **어느 파일이 어떤 설정을 다루는지**만 적는다. 항목별 설명·권장값은 설정 화면에서 그 항목의 **?** 패널로 본다([A-06](#a-06)). 이 매뉴얼에 옮겨 적지 않는다 — 설명의 정본을 한 곳에 두기 위해서다.

| 파일 | 다루는 설정 |
|---|---|
| `general.yaml` | 실행 경로 선택 플래그, SQL 승인, DB 백엔드, 로그 레벨, 구조화 출력, 전역 기본 테마, 대화 체크포인트·보존 |
| `llm.yaml` | 워커 LLM 공급자 선택과 공급자별 주소·모델·키·시간 제한(`LLM_*`) |
| `orchestrator.yaml` | 오케스트레이터(제어 평면) 모델의 공급자·주소·시간 제한·토큰 예산(`ORCHESTRATOR_*`) |
| `router.yaml` | 시멘틱 라우터 2단 분류·신뢰도·조기 종료(`ROUTER_*`) |
| `intent_frame.yaml` | 의도 프레임 기록과 정규 질의 모드·소비자, 재작성 게이트·검증 |
| `text2sql.yaml` | SQL 생성 방식 — 시맨틱 조립, 후보 생성·선택, 관련 테이블 게이트, 0건 진단, 단계적 컬럼 도출, 질의 이력 예시(`TEXT2SQL_*`) |
| `query.yaml` | 기본 LIMIT, 충분성 임계, 재시도 예산, 양식 기억 보존 일수(`QUERY_*`) |
| `composite.yaml` | 복합 질의·호스트 조사 — 대상 수·동시성·시간 제한, 가용성 사전 판정, 존 순회, 범위 역질문, 순차 실행 계약(`COMPOSITE_*`) |
| `multi_db.yaml` | 활성 DB 목록(`ACTIVE_DB_IDS`)과 존 그룹 상호배타(`ZONE_GROUP_EXCLUSIVE`) |
| `synonym.yaml` | 유사어 매칭 — 퍼지·값 검색·의미 매칭(임베딩 백엔드), 거버넌스·감쇠(`SYNONYM_*`) |
| `infrastructure.yaml` | MCP 서버 접속(`DBHUB_*`), API 서버 포트·CORS·질의 시간 제한·SSE(`API_*`), Redis(`REDIS_*`), 스키마 캐시(`SCHEMA_CACHE_*`) |
| `auth.yaml` | 사용자 인증(`AUTH_*` — 로그인 필수 여부, 토큰 만료, 잠금 횟수·시간, 비밀번호 길이, 기본 DB 권한), 운영자 부트스트랩 계정(`ADMIN_*`), 호스트 조사 인가 |
| `security.yaml` | 민감 컬럼 마스킹, IP·이메일 마스킹, PII 필터 로그·차단 덤프(`SECURITY_*`) |
| `audit.yaml` | 감사 로그 파일·DB 기록, 보존 일수, 보안 경고 조건(로그인 실패·대량 결과·야간)(`AUDIT_*`) |
| `observability_polestar.yaml` | 실행 SQL 로그, 실행 트레이스, `/metrics` 공개(`OBS_*`), 폴스타 REST 실시간 사용률(`POLESTAR_REST_*`) |
| `alarm.yaml` | 알람 워커 기동, 최소 심각도, Redis 스트림·중복 제거, 이력 근거, 프로세스·Prometheus 보강, 통보 채널·웹훅, 서버 식별(`ALARM_*`) |
| `noise_gate_core.yaml` | 노이즈 게이트 전체 스위치, 억제 상한 심각도, 반복·자가 복구·플래핑·폭주·연쇄 억제, 중요도 매핑, 결정 저장, 침묵 |
| `noise_gate_correlation.yaml` | 서버 간 상관 묶음, 동적 기준선·이상 탐지, 변경 작업 상관, 임베딩 유사 주석 |
| `noise_gate_investigation.yaml` | 장애 조사 자동 의뢰·후속 조사, 원인 보강(에이전트형), 주석 수집·분류, 비운영 알람 필터 |
| `noise_gate_notify.yaml` | 억제율 메타경보, AI 심각도 승격, 업무 시간, 티켓 묶음 큐, 메시지 보강(L1·L3), SSE 브리지, 사건 계측, 액션가능성 판단·피드백 저장 |
| `workb_drm.yaml` | 사내 메신저 쪽지 발송(`WORKB_*`)과 업로드 문서 DRM 복호화(`DRM_*`) |

- 서버는 21개 파일을 키 이름으로 합쳐 읽는다. 그래서 설정 화면의 그룹 구분은 설정 정의를 따르고, 이 파일 구분과 꼭 같지는 않다(`src/api/settings_help.py` `curated_index`). 키를 찾을 때는 설정 화면 검색을 쓴다.
- 파일 하나가 깨져 읽히지 않아도 설정 화면은 열린다. 그 파일의 키는 자동 설명으로 바뀌고 서버 로그에 「설정 도움말 로드 실패」가 남는다.
- 파일에 설명이 없는 키도 화면에 나온다. 이때는 설정 정의에서 자동으로 만든 일반 설명이 대신 표시된다(`general.yaml` 머리 주석).
- `mcp_server/`·`sre_agent/` 쪽 설정은 이 색인에 없다. 각 프로세스의 설정 파일을 직접 고친다([A-04](#a-04)).

#### 문제 해결

**관리자 화면에 들어가지 못한다(로그인·403)**

| 증상 | 원인 | 대응 |
|---|---|---|
| `/admin`을 열면 메인 화면(`/`)으로 돌아간다 | 로그인한 계정의 역할이 user다. 대시보드는 진입 시 관리자 API를 한 번 호출해 확인하고, 403이면 안내 없이 메인 화면으로 보낸다(`src/static/js/admin.js` `verifyToken`). | 다른 관리자가 [A-30](#a-30)에서 역할을 admin으로 바꾼다. 역할은 요청마다 DB에서 다시 읽으므로 재발급 없이 다음 진입부터 반영된다. |
| `/admin`을 열면 로그인 화면(`/login?next=/admin`)으로 간다 | 토큰이 없거나 만료·무효(401)다. | 로그인하면 대시보드로 돌아온다. 사용자 토큰이 만료된 경우에는 메인 화면(`/`)을 먼저 열어 다시 로그인한 뒤 Admin 링크로 들어간다(메인 화면은 만료 토큰을 지우고 로그인 화면으로 보낸다). |
| `/admin/login`에서 「ID 또는 비밀번호가 올바르지 않습니다.」 | 이 화면은 `.env`의 부트스트랩 계정(`ADMIN_USERNAME`·`ADMIN_PASSWORD`)만 확인한다. 사용자 DB의 계정은 여기서 로그인되지 않는다. | 평소에는 `/login`으로 로그인한 뒤 Admin 링크로 들어간다([A-02](#a-02)). |
| 관리 API가 「관리자 권한이 필요합니다.」(403) | 사용자 토큰은 유효하지만 역할이 admin이 아니다(`src/api/dependencies.py` `require_admin_user`). 관리자 노이즈 관제의 실시간 피드도 같은 문구로 거부한다. | 위 첫 행과 같다. |
| 「보호된 root 계정의 역할·상태는 변경할 수 없습니다.」 등(403) | 보호 root 계정은 역할·상태 변경, PW초기화, 삭제가 막혀 있다(`src/api/routes/admin.py`). | 의도된 동작이다. 부서·알림그룹 같은 다른 항목은 바꿀 수 있다. |

**설정 리로드가 실패한다**

리로드는 실패하면 **기존 설정과 실행 그래프를 그대로 유지**한다(`src/api/routes/admin.py` `reload_settings`). 실패 알림은 5초 뒤 사라지므로 바로 읽는다. 서버 로그에도 같은 사유가 남는다.

| 표시 문구 | 원인 | 대응 |
|---|---|---|
| 저장되지 않은 변경이 있습니다 — 먼저 저장한 뒤 리로드하세요. | 화면에 미저장 편집이 남아 있다. 요청은 서버로 가지 않았다. | 저장하거나 편집을 되돌린 뒤 다시 누른다. |
| 설정 로드에 실패했습니다 — 기존 설정이 유지됩니다: (사유) | 저장된 `.env`를 설정으로 읽지 못했다(형식 오류 등). 400. | 사유에 나온 키의 값을 고친다. 목록·사전 값은 JSON 배열·객체 형식으로 적는다. |
| 운영 모드 필수 설정 검증에 실패했습니다 — 기존 설정이 유지됩니다: (사유) | `AUTH_ENABLED=true`인데 필수 크레덴셜·시크릿이 비었다. 기동 시와 같은 검사다. 400. | 사유에 나열된 키(`ADMIN_USERNAME`/`ADMIN_PASSWORD`, `ADMIN_JWT_SECRET`, `AUTH_JWT_SECRET`)를 `.env`/`.encenv`에 채운다. |
| 그래프 재빌드에 실패했습니다 — 기존 설정이 유지됩니다: (사유) | 새 설정으로 실행 그래프를 만들지 못했다. 500. | 사유와 서버 로그를 보고 바꾼 설정을 되돌리거나 고친다. |
| 서버와의 통신에 실패했습니다. | 응답을 받지 못했다. | 서버 상태를 확인한다. |

리로드는 성공했지만 일부가 반영되지 않은 경우도 있다.

- 「설정을 리로드했습니다 — N건 반영, M건은 서버 재시작이 필요합니다.」와 함께 「다음 항목은 서버 재시작 후 반영됩니다: …」 배너가 뜬다. 나열된 키는 재시작해야 반영된다([A-07](#a-07)).
- 알람 워커가 켜져 있고 `LLM_*`·`DBHUB_*`·`ACTIVE_DB_IDS`가 바뀌었으면 「알람 워커는 재시작 전까지 이전 LLM/DB 설정으로 동작합니다: …」가 덧붙는다. 질의 경로만 새 값으로 바뀐 상태다.

**저장 후 「활성화 준비도 경고」가 뜬다**

`ACTIVE_DB_IDS`에 **새로 넣은** DB가 있으면 저장 직후 그 DB의 준비도를 판정하고, 필수 조건을 채우지 못한 DB를 알린다([A-09](#a-09)). 저장은 이미 끝났으며 경고가 저장을 막지 않는다.

| 표시 문구 | 뜻 | 대응 |
|---|---|---|
| ⚠ 활성화 준비도 경고 — 저장은 완료되었습니다. 아래 DB는 「DB 구조」 탭에서 필수 항목을 채우세요. | 제목 줄이다. 아래에 DB마다 「(DB) — 필수 미충족 N건: 항목 (사유) · …」가 나온다. | [4장 DB 구조](#ch-4)에서 그 DB의 준비도 항목을 확인하고 채운다([A-16](#a-16), [A-19](#a-19)). |
| 준비도를 판정하지 못했습니다: 준비도 판정 시간 초과(20초) | 판정이 상한 20초 안에 끝나지 않았다. | 「DB 구조」 탭에서 그 DB의 준비도를 직접 확인한다. |
| 준비도를 판정하지 못했습니다: 준비도 판정 실패: (오류) | 판정 중 오류가 났다. | 서버 로그의 같은 사유를 확인하고 「DB 구조」 탭에서 준비도를 확인한다. |

- 판정은 **실행 중인 프로세스의 설정**으로 한다. 레지스트리를 새로 고쳤다면 재시작 전까지는 옛 등록 기준으로 판정된다.
- 이 경고는 감사 로그의 설정 변경 기록에도 함께 남는다.
- 이미 활성이던 DB는 다시 판정하지 않는다. 기존 DB의 상태는 「DB 구조」 탭의 준비도 열로 본다.
