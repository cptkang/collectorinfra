# Plan 86 실행 계획 — 알람 → 질의 프롬프트 인계

> `plans/86` · `CAPABILITY-MAP-86.md` · D-192 · 사용자 확정 G-1~G-4(2026-08-31)

## 구현 순서와 그 이유

```
T1 builder(순수 함수 + 테스트)  ← 검증 가능한 기준선을 먼저 세운다
      ↓
T2 UI 마크업·CSS                ← builder 출력이 있어야 렌더할 대상이 있다
      ↓
T3 인계 배선(확인 후 전송)       ← 마크업이 있어야 클릭 대상이 있다
      ↓
T4 LLM 추천 라우트(기본 off)     ← 결정적 폴백 기준선이 서 있어야 폴백이 정의된다
      ↓
T5 프론트 LLM 연동(0건일 때만)
      ↓
T6 문서(D-192 등재 · INDEX · 계획서 상태)
```

**병렬 불가**: 전 단계가 다음 단계의 입력이다. T4는 T1~T3와 파일이 겹치지 않아(서버측)
논리적으로는 병렬 가능하지만, 폴백 계약이 T1에서 확정되므로 순차로 둔다.

## 검증 체크포인트

| 이후 | 확인 |
|---|---|
| T1 | 축별 문구 단언 테스트 통과 · 함수 원문 추출 실행 검증(D-190 방식) |
| T3 | `reuseHistoryQuery` 불변 · `handleSend` 단일 진입점 · 확인 바 동작 |
| T4 | 503(기본 off) · 403(존) · LLM 실패 graceful · arch/overfit 0 |
| T6 | 채번 3곳 재확인 후 D-192 등재 |

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| **추천 문구를 파이프라인이 못 푼다**(최대 리스크) | 골드셋 동형만 채택. `server.Network`는 검증 전까지 매핑에서 **제외** |
| 자동 전송 오작동 | G-2가 **확인 후 전송**으로 확정 — 자동 전송 경로를 만들지 않는다 |
| D-190 필터와 간섭 | 칩은 카드 표시 여부를 바꾸지 않는다. 회귀 테스트로 고정 |
| LLM 라우트가 카드 렌더를 깨뜨림 | 실패는 200+null. 프론트는 결정적 추천이 0건일 때만 호출 |
| 과금 | 기본 off · 결정적이 빌 때만 호출 · 실 LLM 호출은 건별 승인(D-127) |
| 브라우저 렌더 미확인 | 확장·playwright 모두 미연결 — 원문 추출 실행 검증으로 대체하고 **미확인 사실을 보고** |
