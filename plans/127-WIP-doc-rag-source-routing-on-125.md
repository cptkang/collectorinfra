- **문서 기준 시점**: 문서 값은 작성 시점 기준이다(126 §4.7a 5). 현재값(L1~L3)과 **자동 비교하지 않는다** — 텍스트와 수치는 결정적으로 대조할 수 없다(125 Q-6은 「이미 조회된 같은 속성」끼리만). 둘이 함께 나오면 코드가 시점 고지 1줄을 붙인다(§4.7).

### 4.2 레지스트리 등재 형식 (G-5)

**권고 (a)**: `config/db_registry.yaml` `solutions`에 **껍데기 항목** `doc`을 둔다.

```yaml
  - code: doc
    label: 사내 문서(규정·설계 근거)
    order: 40
    backend: rest            # FabriX Retrieval Connector(httpx POST)
    family: fabrix_rag       # 고유 family(공유 금지 — 121 TP-9.2 로더 검증)
```

- ① **보기 파생**: 로더가 `config/rag_collections.yaml`의 `enabled: true` 문서군마다 보기 1건을 만든다 — `id = doc.<collection_id>` · `label = title` · `capability` = 문서군 → 영역 대응(정본 YAML에 `capability:` 1필드 추가 — `answer_domains`는 한국어 자유어라 영역 코드로 쓰지 않는다) · `required_input` 없음 · `first_hop` 해당 없음. 설명·형제 차이·표면어는 **복사하지 않는다**(분해 절이 렌더 시 YAML에서 읽는다). `ViewSpec`(`registry.py:62-84`)은 `tool`(MCP 도구)을 전제하므로 **도구 없는 보기**를 허용하도록 넓힌다(파서가 `backend` 값을 검증하지 않는 것도 함께 — `registry.py:522-535` · 125 리뷰).
- ② **민감 문서군(`sensitive: true`)은 보기에 넣지 않는다**(1차) — 분해 프롬프트는 전역(기동 시 1회)이라 권한 밖 사용자의 계획에도 이름이 실린다(125 §15.4 ① · D-264 ②). 민감 문서군의 채팅 도달은 후속 게이트. 지금 두 문서군은 모두 `sensitive: false`(`config/rag_collections.yaml:27,47`).
- ③ **활성 판정의 일반화**: 125의 활성 = 「보기 표 있음 ∧ MCP 엔드포인트 설정」(`apm_query.py:87-89`)이고 관리 후보의 활성은 `dbhub.active_source_codes()`(MCP 엔드포인트)다. 문서의 활성은 MCP가 아니라 `RagConfig`에서 오므로 **시스템별 활성 판정 함수 표**(시스템 코드 → 판정 함수)로 일반화한다 — 125 소유 코드라 **125 소유자 리뷰**를 받는다.
- 결과: `non_db_systems()`(`registry.py:340-348` — `backend != sql`이고 DB family를 공유하지 않는 솔루션)에 `doc`이 잡혀 존·실행 그룹·라우터 소유 안내 행에서 빠지고, 관리자 「조회 가능 소스」 후보에 나타난다(G-8).
- 대안 (b) 레지스트리 밖 병렬 목록(`rag_collections.yaml`만) — 125 소유 판정·인가 후보·카탈로그(121 TP-9.1)가 문서를 모른다. (c) `rag_collections.yaml`을 레지스트리로 이관 — 126 §4.1a의 의미/접속 분리는 유지되지만 D-284 ③의 정본 위치를 바꾼다.

### 4.4 분해 프롬프트 절 · 문서군 선택 · 우선순위 (G-6 · G-7)

- **절**(활성일 때만 삽입 · 125 A-5 방식 — `_APM_AGENT_ANCHOR` 앞): 담당 한 줄 + 보기 표 `<doc_view_rows>`(문서군 id · 제목 · `description` 첫 문장 · `sibling_note` — 전부 `rag_collections.yaml`에서 렌더) + 경계 예시 4줄(§4.1 이름 충돌) + 「문서 task는 다른 task의 입력이 되지 않는다 — `depends_on`·`input_from`을 걸지 말 것」.
- **문서군 선택 = `views`**: 분해 호출 안에서 LLM이 고른다(추가 LLM 0 · D-004 — 구조화 출력). 목록 밖 id는 버린다. 지금의 정제 함수 `_sanitize_task_views`(`intent_planner.py:896-908`)는 **`apm_query` 전용이고 다른 담당의 `views`를 떼어 낸다** — 조건부 처리기마다 자기 어휘로 정제하도록 일반화한다(§4.3 ① 결합 모듈이 처리기별 정제 함수를 함께 돌려준다).
- **G-6 — `views`가 비었을 때**: 권고 (a) **보기에 오른 문서군 전부(상한 `RAG_MAX_COLLECTIONS_PER_TURN` = 2)를 검색하고 해석 한 줄에 「두 문서군 모두 찾았습니다」를 코드가 고지**한다 — 리랭커가 하나라 전역 정렬이 성립하고(126 §4.8) 비용 상한이 2건으로 고정이다. 126 §4.6 「미지정 = 오류」는 **사람이 지정하는 시험 표면**의 규칙(암묵적 전체 검색 금지)이고, 채팅 경로는 시스템이 고르고 그 사실을 고지하므로 같은 위험(사람이 모르는 채 비용·혼입)이 없다. (b) 역질문(부록 D-6 원안 — 턴 +1). (c) 문서군 `surface_terms`의 결정적 인식으로 확정(125 B-2 명시 소스 기계 — R7 뒤).
- **G-7 — 우선순위**: 권고 (a) **우선순위 표 본문(`src/prompts/intent_planner.py:29-51`)은 건드리지 않고 삽입 절만** 둔다(125 APM 선례 · 비활성 바이트 불변이 쉽고 활성 델타가 「삽입」 하나로 설명된다). 경계 골드(§7)에서 「알람 대응 절차」가 `alarm_query`로 가는 오유입이 관측되면 (c) 알람 줄에 좁은 음성 조건 1줄(「절차·기준·규정 자체를 묻는 것은 `doc_query`」 — **활성일 때만 렌더**)을 더한다. (b) 부록 D-3의 「cache 다음 2순위」 표 삽입은 기존 4클래스 정확도를 흔들 수 있어(부록 D-3 이관 위험 ③) 측정 없이 택하지 않는다.

### 4.6 인가 (G-8 · D-232)

- **두 층**: ① 소스 축 — 이 사용자가 문서 소스를 쓸 수 있나(125 A-7 `allowed_sources`) ② 문서군 축 — 어느 문서군을 열어 주나(126 `sensitive`). 둘은 대체 관계가 아니다(126 §4.10 「두 층이 함께 필요」와 같은 논리).
- **G-8 권고 (a)**: 문서를 소스 축에 **편입**한다. 관리자가 「사용자 관리 → 조회 가능 소스」에서 사람별로 열고 닫을 수 있고(후보 = `non_db_systems()` — 등재만으로 나타난다 · 활성 표시는 §4.2 ③ 일반화 뒤), 기존 사용자(NULL)는 전체 허용이다. **대가**: 신규 가입자는 `AUTH_DEFAULT_ALLOWED_SOURCES`(빈 값 = 없음)를 따르므로 **문서 질의가 기본으로 막힌다** — 126 G-2 권고(비민감 = 전원 허용)와 다르다. 전원 개방이 목적이면 운영자가 `AUTH_DEFAULT_ALLOWED_SOURCES`에 `doc`을 넣는다(APM과 독립 — 목록이다). (b) 소스 축 밖 — 비민감 전원 허용 유지(126 G-2) · 관리자가 사람별로 막을 수단이 없다.
- **D-285 ① 문구**: 대상이 「DB 없는 **관측** 소스」로 적혀 있다. (a)면 「DB 없는 소스(관측 소스 + 문서 소스)」로 부기가 필요하다(§10).
- **민감 문서군**: 1차 채팅 경로에서는 보기에 없으므로(§4.2 ②) 문서군 축 인가는 **이중 방어**다(보기 밖 id는 `sanitize`에서 이미 버려진다).
- **거부 문구**: 소스 축 거부는 125 문구(소스 이름 없음) 그대로 · 문서군 축 거부는 문서군 제목을 싣지 않는다(D-264 ②).
- **「관리자」 정의가 두 축에서 다르다**(§2 #25): 소스 축(`db_authz.is_admin`)은 `admin`만, 문서군 축(`doc_qa/authz._is_admin`)은 `admin`·`operator`를 전체 허용으로 본다. 결과적으로 `operator` 역할은 소스 축에서는 일반 사용자 규칙(자기 `allowed_sources`)을, 문서군 축에서는 관리자 규칙(민감 문서군 포함)을 받는다. 1차 채팅 경로는 민감 문서군을 보기에 올리지 않으므로(§4.2 ②) 실제 차이는 없지만, **민감 문서군을 채팅에 열기 전에 한 정의로 맞춘다**(126 엔진 변경 — 126 소유자 합의 · D-232 「관리자 전체 허용」 정의를 따르는 쪽이 권고).
- **계획 요약 노출**: `plan_summary.tasks[].agent`·`views`에 `doc_query`·`doc.*`가 권한 밖 사용자 턴에도 실릴 수 있다 — 125 §15.4 ①과 같은 질문이므로 **그 결론을 따른다**(이 계획에서 따로 정하지 않는다).

### 4.7 조합 — 문서 + 다른 소스는 병렬로만 (G-10 · 121 TP-10 경계)

- **간선 없음**: 문서 결과는 엔터티 식별자를 주지 않고(`key_facets_out=()`), 문서 내용에서 서버를 뽑는 것은 결정적이지 않다(질의 시점 LLM 엔터티 추출 = 125 §4.11 「채택하지 않는 것」). 따라서 **문서 task는 `depends_on`·`input_from`의 양쪽 어디에도 서지 않는다**. 분해가 걸면 코드가 끊고 경과 노트 1줄(「문서 답은 다른 조회의 입력으로 쓰지 않았습니다」)을 단다.
- **병렬 조합**(예: 「규정상 CPU 임계 기준과 지금 그 기준을 넘는 서버」 → `doc_query` ∥ `data_query`): 두 답이 **따로** 나온다. 「규정의 기준값으로 조회 조건을 만든다」는 연쇄는 하지 않는다 — 사용자가 기준값을 명시하면 그 값으로 조회한다.
- **응답 형식**
  - C 트랙 전(현행 2단 `composite_answer="steps"`): 단계별 답 중 하나로 문서 답(본문 + 참고 문서)이 들어간다(`result_aggregator.py:1154-1157`).
  - **125 C 트랙 랜딩 뒤**(R7 묶음): 125 §4.9 골격 ③ 엔터티 표 · ④ 연결 장부 · ⑤ 불일치 각주 **다음에 ⑤′ 「문서 근거」 절**(문서 답 + 참고 문서)을 둔다. **문서 절은 ⑥ LLM 요약의 입력에 넣지 않는다**(121 G-25 — 요약 입력은 표 사실 목록만 · 문서 본문이 요약에 섞이면 수치와 규정 서술의 출처가 흐려진다). ② 소스 상태 행에 문서 한 줄(`문서 3건` · `0건` · `색인 갱신됨(관리자 조치)` · `사용 불가(사유)` · `권한 밖`).
  - **시점 고지**(코드): 문서 절과 현재값 표가 함께 나오면 「문서 내용은 작성 시점 기준이며 위 조회 결과(현재값)와 다를 수 있습니다」 1줄.
- **121 TP-10과의 경계**: TP-10(키 패싯·브리지·바인드 조인)은 **엔터티 연쇄**다. 문서는 그 대상이 아니다 — 이 계획은 연쇄를 만들지 않고, 121에 넘길 것도 없다(126 §1.2 「문서 + DB 혼합 = 121 TP-10」 행은 이 결론으로 대체).

### 4.8 재계획 · LLM 예산 (G-12)

- **재계획 프롬프트**: `src/prompts/replanner.py:34` 규칙 6(안내성 답 = 완결 · 중복 후속 금지)에 `doc_query`를 같은 성질로 더한다 — **문서 활성일 때만 렌더**(비활성 바이트 불변). 문서 0건·`stale_id`는 재시도로 회복되지 않는다(126 §4.2 1 · §4.7 — 표현을 바꿔 보라는 안내가 답이다).
- **재계획 코드의 중복 방지**(`replanner.py:266-275`)는 「후속이 **모두 `general_inference`**면 종료」다 — 「후속이 모두 `doc_query`이고 같은 턴에 이미 `doc_query`가 완료됨」도 같은 종료 대상으로 넓힌다(문서 재검색은 같은 답을 되풀이한다).
- **재계획 프롬프트의 담당 목록**(`src/prompts/replanner.py:19-25`)에는 조건부 처리기가 없고 어휘로만 허용된다(`replanner.py:319-324` · 삽입 없음 `:387`) — 이것은 125 B-7(R7 묶음)의 몫이다. 이 계획은 B-7의 렌더 단일화가 랜딩하면 그 위에 문서 줄을 얹는다(따로 만들지 않는다).
- **G-12 — 문서 전용 계획의 재계획 LLM**: 현행 `_all_tasks_succeeded` 조건 6(`replanner.py:936-985`)은 행 결과가 하나도 없으면 LLM 평가로 간다 → 문서 전용 질문은 분해 1 + 서술 1 + **재계획 1**. 권고 (a) **task가 전부 `doc_query`이고 전부 완료면 결정적 종료**(LLM 0 — 문서 답은 완결 · 재계획이 만들 수 있는 후속은 같은 문서 재검색이거나 `general_inference` 보충뿐이다) · 섞인 계획은 현행 그대로. 이 변경은 **문서 task가 있을 때만** 발동하므로 비활성 배포 동작 불변이다. (b) 현행 유지(LLM 평가 — 지연 +1회).
- **예산**: 문서 전용 = LLM 2회(G-12 (a)) · 근거 0건이면 1회(분해만). 126 §4.11의 검색 상한(12초 + 총 20초)이 턴 마감 안에서 계산된다(126 §4.2 3 · D-268). **지연 목표는 기준선 없이 정하지 않는다**(§7) — CLAUDE.md 목표 「단순 < 10초 · 복합 < 30초」 중 어디에 넣을지는 MLX·내부망 기준선 뒤.

### 4.9 멀티턴 · 스트리밍 · UI · 상태 (부록 D-5 재평가)

- **`AgentState` 필드 0 · 그래프 노드 0**: 문서 결과는 task 결과로만 흐른다(125와 같음). 요청 스코프 초기화 문제(체크포인터 델타 병합)가 **새로 생기지 않는다**.
- **멀티턴**: 분해 프롬프트의 기존 「후속 턴 — 지시어 해소」 규칙(`src/prompts/intent_planner.py` 「## 후속 턴」)이 「그 문서」를 직전 답의 문서 제목으로 풀어 `sub_query`에 넣는다(추적 — 직전 답 본문에 「참고 문서」 제목이 있으므로). 제목이 lexical 경로에 유리하다(126 §4.9). 인용 경량 요약 승계(부록 D-5)는 **후속**(골드에서 실패가 관측되면).
- **스트리밍**: 2단 최종 응답은 루트 직속 `result_aggregator`가 내므로 SSE `done` 규칙이 그대로 성립한다(103 §4.1 P0-3 실측). **엔진 서술은 이미 스트리밍된다** — `answer_from_documents`가 `astream_text(…, tags=[USER_RESPONSE_TAG])`로 서술을 부르고(`service.py:394`) 스트리밍 라우트는 그 태그의 토큰을 전달한다(`query.py:2629`). 즉 채팅 경로에 붙는 순간 서술 토큰이 먼저 흐르고, **인용 블록은 스트리밍 뒤 `done`의 최종 응답에만** 있다(v1 초안의 「토큰 스트리밍 없음」은 틀렸다 — v1.1 정정). 2단 `general_inference`가 같은 모양(처리기 실행 중 태그 토큰 · `general_inference.py:301-305`)이라 화면 처리는 선례가 있다(추적). 확인할 것: ①단독 턴 — 스트리밍 본문과 `done` 최종 응답(본문 + 참고 문서)이 화면에서 한 번만 보이는가 ②**복합 턴** — 결과 합류기의 토큰 억제는 `output_generator`에만 걸리므로(`result_aggregator.py:143-145`) 문서 서술 토큰이 다른 단계 답보다 먼저 흐를 수 있다(추정) → §6.1 테스트 · 필요하면 복합 턴에서는 문서 서술 태그를 끄는 호출 인자를 엔진에 더한다(엔진 변경이므로 126 소유자 합의). 진행 이벤트(D-204 task)는 처리기 이름으로 나가므로 **UI 라벨** `doc_query: "문서 검색"`을 `app.js:469-479`에 더한다(캐시 버전 올림). 같은 표에 **`apm_query` 라벨이 없다** — 125에 통지(§13).
