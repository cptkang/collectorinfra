## 1. D-142 — Excel 멀티로우 병합 헤더 결합

### 1.1 설계 원칙

- **수정 지점은 parser 단일**: `excel_parser.py`가 결합된 복합 필드명 + 올바른 열 좌표를
  `header_cells`로 내보내면, field_mapper(`extract_field_names`)와 excel_writer
  (`col_assignments` 채우기)는 **무변경**으로 동작한다(둘 다 `header_cells`의
  `{col, value}`만 소비 — `excel_writer.py:199-224` 실측).
- **보수적 게이트**: 기존 단일 헤더 템플릿의 동작을 절대 바꾸지 않는다. 아래 결합 조건을
  모두 만족할 때만 2행 결합을 발동한다.

### 1.2 알고리즘

`_detect_header_row()`를 `_detect_header_block()`으로 확장:

1. 기존 휴리스틱으로 최다-셀 행 `R`을 찾는다(현행 유지).
2. **결합 후보 판정** — 다음을 모두 만족하면 `(R-1, R)` 또는 `(R, R+1)` 2행 블록으로 결합:
   - 인접 행에 `_MIN_HEADER_CELLS` 이상의 비어있지 않은 셀이 있고,
   - 두 행에 정확히 걸친 **세로 병합**(예: B5:B6)이 존재하고(**필수 증거**),
   - 두 행이 모두 데이터 행이 아니다(수치 값 비율 50% 초과 행이면 결합 중단).
   - **[구현 중 실측 확정 2026-07-27]** 초안의 "가로 병합 + 하위 값 2개" 단독 증거는
     **폐기**: `sample/취합 예시2.xlsx` 3행(부분 그룹 행 "자원현황"/"모니터링 Tool" —
     가로 병합만 있고 세로 병합 없음)이 4행 헤더와 오결합되어 기존 회귀 테스트
     3건(`tests/test_query_to_excel_mapping.py`)이 깨지는 것을 클린 worktree 기준선
     대조로 확인. 두 행을 구조적으로 묶는 세로 병합을 필수로 요구하면 금감원 3종
     (세로 병합 4~7개 보유)은 결합되고 취합 예시2는 현행 유지된다.
     **한계(의도적)**: 세로 병합이 하나도 없는 순수 그룹+서브 2행 헤더는 결합되지
     않는다(현행과 동일하게 서브 행만 헤더) — 실물 수요 확인 시 게이트 완화를 별도 검토.
3. **열별 복합 필드명 생성 규칙** (상단 행 값 `top`, 하단 행 값 `bot`):
   - 세로 병합(B5:B6) 또는 `bot` 없음 → `top` 단독 (예: `제조사(모델명)`, `호스트명`, `비고`)
   - 가로 병합 하위 열 → `top` 앵커 값 전파 + 구분자 결합: `f"{top}|{bot}"`
     (예: `월중평균사용률(최근 6개월간)|M+2`, `접근통제 및 추가인증|적용 솔루션명`)
   - 둘 다 값 존재·비병합(A5 `구분`/A6 `분류`) → `f"{top}|{bot}"` (`구분|분류`)
   - `top` 없음·`bot`만 존재 → `bot` 단독
   - 구분자는 `|` 고정(정규화 `normalize_field_name`이 유지하는 문자 — 구현 시 실측 확인,
     충돌 시 공백으로 대체). 병합 앵커 값 조회는 `ws.merged_cells.ranges`의 최상좌 셀 사용.
4. **[구현 시 변경]** `header_row`는 블록 **하단** 행으로 반환한다(초안의 "상단 행"에서 변경).
   근거 실측: 모든 소비처(`excel_parser._analyze_sheet:79`, `excel_csv_converter:110`)가
   `data_start_row = header_row + 1` 계약으로 계산하므로, 하단 행 반환이 **소비처 무변경**으로
   올바른 데이터 시작 행(양식 3종 모두 7행)을 보장한다. excel_writer는 `header_cells`/
   `data_start_row`만 소비함을 grep 실측. 블록 범위는 `sheet_info.header_block_rows`
   (예: `[5, 6]`, 단일 헤더는 `[N]`)로 별도 노출한다.

### 1.3 하위 호환

- 결합 조건 미충족(단일 헤더) 시 현행과 **완전 동일 출력**. 기존 테스트
  `test_header_detection_non_first_row`(`tests/test_document/test_excel_parser.py:83`) 등
  전부 통과가 게이트.
- `headers`/`header_cells` 키 구조는 유지(값만 복합명). `header_row` 의미가 "블록 상단"으로
  바뀌는 소비처가 있는지 `grep -rn "header_row"`로 전수 확인 후 배선(Known Mistakes:
  호출부 배선 실측).
- **[실측 2026-07-27] 소비처 2경로 확인**: `_detect_header_row`는 폼필 경로
  (`input_parser.py:396` → `parse_excel_template`)뿐 아니라 **데이터 파일 CSV 변환 경로**
  (`src/document/excel_csv_converter.py:103` 직접 호출 + `:154` 폴백)도 공유한다.
  한쪽만 블록 결합을 적용하면 같은 파일이 경로별로 다르게 해석되는 비대칭(Known Mistakes

## 2. D-143 — 월별 가로 피벗(M~M+5) 결정적 조립

### 2.1 왜 결정적 조립인가

Known Mistakes 원칙 그대로: "스키마·조인이 고정된 폼필 피벗은 코드가 runnable SQL을 직접
조립(LLM 우회)". 프로필 few-shot(월별 GROUP BY 세로 전개, `polestar_cm_yd.yaml:459-506`)과
프롬프트 강제가 경쟁하는 전형적 형태이므로 LLM에 맡기지 않는다. D-067(이중 조립 엔진 금지)에
따라 **새 조립기를 만들지 않고 `build_multi_resource_pivot_sql`에 모드를 추가**한다.

### 2.2 조립기 확장 (`src/db_adapters/polestar/assembler.py`)

**[구현 시 인터페이스 확정 2026-07-28]** 초안의 `month_pivot: list[str]`(월 목록) 대신
**`month_measures: list[tuple[alias, resource_type, val_col, YYYYMM]]`**(measure 완전 전개)로
확정. 근거: alias 명명 규칙을 조립기에 숨기지 않고 호출부(§2.3 인식기)가 템플릿 칼럼과 1:1로
직접 통제 — 조립기는 명명 무지(agnostic) 상태를 유지해 과적합을 차단(D-145 정합). 조인 월
필터는 measure들의 (최소, 최대) 범위로 자동 산출하며 `stat_month`보다 우선한다.
월 형식은 `\d{6}` 검증(위반 시 ValueError — 결정적 호출부 버그 조기 검출).

초안 설계(참고용 — 전개 형태는 동일):

- `month_pivot`가 주어지면 metric SELECT 라인을 월×집계로 전개한다. 리소스 타입 `rt`,
  월 인덱스 `k`(0-based), 월 `mm`에 대해:
  ```sql
  MAX(CASE WHEN c.resource_type='server.Cpus' AND s.stat_date='202602' THEN s.avg_val END) AS cpu_m0_avg,
  MAX(CASE WHEN c.resource_type='server.Cpus' AND s.stat_date='202602' THEN s.max_val END) AS cpu_m0_peak,
  ...
  ```
  - `MAX(CASE …)`는 config×metric 이중 조인의 행 복제에 **불변**(동일 값 중복이므로) —
    기존 조립기의 불변식(docstring `:247-248`)과 동일 논리.
  - **alias는 라틴 소문자 고정**(`cpu_m0_avg` … `mem_m5_peak`): DB2 결과 칼럼 라틴
    소문자화(Known Mistakes 멀티 엔진 방언) 대응. PostgreSQL/DB2 공통 안전.
  - metric join 조건은 기존 `BETWEEN month_pivot[0] AND month_pivot[-1]`을 재사용(`:283-285`).
  - D-086 값 타당성 게이트(`avg_val/max_val BETWEEN 0 AND 1000`)는 CASE 내부 조건에 유지.
- `month_pivot=None`이면 **기존 경로와 바이트 동일 SQL**(회귀 계약:
  `test_multi_resource_pivot.py` 기존 케이스 전부 무수정 통과).
- 기존 계약 "stat_date는 GROUP BY에 넣지 않는다"(`:386-387`)는 **유지**된다 — 월 전개는
  GROUP BY가 아니라 SELECT의 CASE 피벗으로 한다(서버당 1행 불변식 보존).

### 2.3 양식 인식 → month_pivot 발동 (결정적 인식기)

field_mapper/query_generator 파티셔닝(`src/nodes/query_generator.py:196-225`, `:807-846`)에
결정적 전처리를 추가한다:

1. 복합 필드명이 패턴 `^(?P<group>.+(평균|peak|피크|최고|최대).*사용률.*)\|(?P<sub>M(\+\d+)?|\d{1,2}월|\d{4}[-./]\d{1,2})$`
   (대소문자 무시)에 부합하는 열 집합을 **month-series 필드**로 분류한다.
   - group에 `평균` 포함 → `avg_val`, `peak/피크/최고/최대` 포함 → `max_val`.
   - 리소스 타입은 양식 제목·사용자 질의·시트명에서 기존 `classify_metric_field`
     (`assembler.py:66-80`)의 명사 사전(cpu/메모리/mem/디스크)으로 판정. 판정 불가 시
     이 양식을 month-pivot 대상에서 제외하고 기존 경로로 폴백(과적합 방지 — plans/63 원칙,
     금감원 전용 하드코딩 금지).
2. 서브 헤더 해석:
   - `M+k` 상대 표기: 그룹 라벨의 "최근 N개월" 또는 사용자 질의의 기간을
     `resolve_stat_month_range()`(`query_gen_common.py:35-66`)로 해석해 시작월을 M으로.
     기간 언급이 전혀 없으면 **기본값(사용자 확정 2026-07-27): 기준월은 M+5이며
     M+5 = 실행일 기준 지난달(마지막 완결 월)**. 예: 실행일이 7월이면 M+5=6월,
     M=1월(1~6월 데이터). 사용자가 기준월을 명시하면(예: "기준월 3월") 그것이 M+5.
   - `1월`/`2026-02` 절대 표기: 그대로 YYYYMM 매핑(연도 없으면 최근 12개월 내 최신 해당월).
3. `column_mapping`에 복합 필드 → alias(`cpu_m0_avg` 등)를 **코드가 직접 기입**하고
   (LLM·유사어 경로 우회), month_pivot 목록과 함께 조립기에 전달한다.
4. **단일/멀티 경로 대칭(필수)**: 이 전처리·조립 호출이 `query_generator`(단일 DB)와
   `multi_db_executor`/`semantic_compiler`(멀티 DB) **양쪽에 실제 주입되는지 실측**한다
   (Known Mistakes: 한쪽만 고치는 비대칭이 반복 원인). 조립 함수 자체는 공용이므로
   발동 지점만 대칭 배선하면 된다.

### 2.4 기준월 명시 응답 (감사자료 오기재 방지)

M이 어느 달인지 양식에 적히지 않으므로, 폼필 응답 본문에 **실제 사용한 월 매핑을 반드시
명시**한다: 예) `M=2026년 2월, M+5=2026년 7월 (마지막 완결 월 기준 최근 6개월)`.
가능하면 산출 Excel의 `비고` 열이 아닌 **응답 텍스트**에만 기재(양식 원본 불가침 원칙 —
비고 열 기재 여부는 사용자 결정 사항, §5 미결).

## 4. D-145 — 양식 특화 매핑의 스코프 격리 (과적합 방지 핵심 원칙)

**문제의식(사용자 제기 2026-07-27)**: 본 양식을 위해 `처리능력→메모리 용량` 같은 매핑을
전역 유사어·프로필에 등록하면 **다른 양식·일반 질의까지 오염**된다. 실제로 CPU 양식의
`처리능력(TPMC)`이 메모리 용량으로 오매핑되는 즉각적 반례가 같은 취합자료 안에 존재한다.

**원칙(D-145)**: 특정 양식의 문맥에서만 성립하는 매핑은 **요청 스코프의 결정 규칙**
(파싱된 템플릿 컨텍스트 → column_mapping 직접 기입, 요청 종료 시 소멸)으로만 구현한다.
전역 상태(Redis 유사어, 프로필 `synonyms:`, EAV attribute synonyms)에는 등록하지 않는다.
plans/63(과적합 분리)·Known Mistakes(유사어 자동 등록 오염 자기강화 루프)의 연장이다.

### 4.1 요청 스코프 규칙 (전역 등록 없음)

| 필드 | 결정 규칙 (모두 §2.3 인식기 내부, 요청 스코프) | 근거 문맥 |
|------|-----------------------------------------------|-----------|
| `처리능력` | 시트 리소스 판정(제목 "주기억장치/메모리"→server.Memory) **AND** 단위 토큰 `(GB)` → 메모리 총 용량(EAV). 단위가 `(TPMC)` 등 미수집 지표면 미지원 분류 | 시트 제목 + 같은 헤더 블록의 단위 행 |
| `호스트명` | `cmm_resource.hostname` **직접 컬럼**(사용자 확정: 금감원 제출은 실제 호스트명 기준) — 신규 규칙이 아니라 기존 프로필 가이드(`polestar_cm_yd.yaml:171` "명시적으로 '호스트명'일 때만 hostname") 그대로. **오버라이드 금지 + 회귀 테스트로 계약 고정**만 수행 | 헤더 문언 자체 |
| `OS(버전정보포함)` | `OSType` + `OSVerson` 두 값 조회 후 **코드에서 결합**(SQL `\|\|` 결합 대신 — DB2/PG 방언 및 NULL 결합 회피) | 헤더 문언의 "(버전정보포함)" |
| `서버명` | `cmm_resource.name`(등록명) — 기존 가이드와 일치, 확인만 | 기존 규칙 |

### 4.2 전역(프로필)에 넣어도 되는 것의 기준

- **DB 스키마의 보편적 사실**(예: "OSVerson은 오탈자 반영")만 프로필에 남긴다.
- "이 양식에서 이 칼럼은 이것"류 지식은 전부 §4.1 스코프 규칙 또는 (누적 시) 별도
  양식 프로파일 계층으로 격리한다 — 본 계획에서는 규칙이 4건뿐이므로 **양식 프로파일
  레지스트리(YAML)는 도입하지 않는다**(YAGNI). 유사 양식 특화 규칙이 3종 이상 누적되는
  시점에 `config/form_profiles/` 도입을 별도 계획으로 검토한다(양식 지문(fingerprint)
  = 제목 텍스트 + 헤더 시그니처 매칭 방식).
- **유사어 Redis 자동 등록 경로에는 어떤 것도 넣지 않는다**(Known Mistakes: 오염
  자기강화 루프 — 쓰기 지점 결정적 차단 유지).

### Phase 3.12 — `c.category` 근본 원인 확정 및 교정 (2026-07-30, FIX-15)

**사용자 캐시 실측으로 확정**: category는 환각·캐시 오염이 아니라 **`cmm_resource_type`에

직접 칼럼 매핑은 피벗에서 제외**(조립기의 암묵 전제 "regular=entity 직접 칼럼"을 입력
검증으로 명문화). 제외된 `구분`은 공란+D-144 사유로 귀결(Q4 확정과 정합 — 구분은 1차

| R6 | **NULL 월의 해석 모호성** | 특정 월 데이터 부재 시 해당 칼럼 NULL → 공란. "수집 전 기간"인지 "수집 실패"인지 양식만으론 구분 불가 | D-144 사유 구조에서 "값 없음(데이터 부재)" 분류 + 생성 SQL 로그 연동(D-050: null은 SQL 오류일 수도 — 진단 시 생성 SQL 먼저) |
| R7 | **테스트·유지보수 비용** | 파서 분기 증가, 방언별 스냅샷, e2e 픽스처 3종 — 테스트 자산 증가 | 픽스처를 실물 양식 사본으로 고정해 회귀 계약화(G4 해소가 곧 자산). 스냅샷은 조립기 단위로 국소화 |
| R8 | **`구분|분류` 등 복합명 UX** | 사유 노출 시 사용자에게 낯선 `A|B` 표기 노출 | 응답 표시용으로는 `A > B` 또는 "A의 B"로 변환하는 표시 계층 처리(내부 키만 `|`) |
| R9 | **CSV 변환 경로 동반 변경** | `_detect_header_row`를 excel_csv_converter(데이터 파일 업로드)도 공유 — 블록 결합이 데이터 파일의 CSV 헤더명·data_start_row를 바꿀 수 있음 | 두 경로 대칭 적용(§1.3) + converter 회귀 테스트. 2단 헤더 데이터 파일은 복합명이 오히려 LLM 매핑에 유리(개선 방향의 변경). 단일 헤더 파일은 게이트 미충족으로 무영향 |

## 9. 명시적 비범위 (본 계획에서 하지 않는 것)

- Word(`{{placeholder}}`) 멀티로우 표 헤더 — Excel 안정화 후 별도 계획.
- 3단 이상 헤더(2행 초과 블록) — 실물 수요 확인 전 미지원(게이트 조건이 자연 차단).
- TPMC·접근통제 등 미수집 도메인의 신규 수집 — 수집 체계 밖(에이전트 범위 아님).
- 유사어 자동 등록 확대 — Known Mistakes(오염 자기강화) 금지 유지.
- **서버 목록 `구분` 자동 채움(Q4)** — 자원 상위 그룹 조회는 2차에 "일반 필드 능력 +
  사용자 지시 발동"으로 검토(§5 Q4). 양식→트리구조 자동 매핑은 하지 않는다.
- **양식 프로파일 레지스트리(`config/form_profiles/`)** — 스코프 규칙이 3종 양식군 이상
  누적될 때 별도 계획으로 도입 검토(§4.2). 지금은 YAGNI.
