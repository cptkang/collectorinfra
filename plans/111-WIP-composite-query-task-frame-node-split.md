### 0.1 실측 한 줄

### 0.2 "노드로 나누면 빨라지는가"에 대한 답

**복합 질의에서만.** 이 run에서 2단은 단일 질의에도 분해·오케스트레이션·합성 노드를 전부 태웠고, 타임아웃 199턴 중 131턴이 그 2단 전용 노드(`result_aggregator` 95 · `replanner` 36) 안에서 죽었다(`plans/108` §1.2).
따라서 이 문서의 노드 분리는 **"단일 의도는 결정적 1 task로 바로 흘리고, 복합일 때만 계획·팬아웃을 태운다"**(103 §3.1 G-5와 같은 방향)를 전제로 한다. 새로 만드는 노드는 전부 **결정적**(LLM 0회)이다.

### 2.3 재계획이 "재시도 장치"로 쓰이고 있다

재계획이 발동한 28턴의 **t1 결과**:

| t1 결과 | 턴 | 재계획이 한 일 | 결과 |
|---|---:|---|---|
| SQL 생성이 **산문을 냄**(`SQL 구조에 자연어(한글) 토큰이 남아 있습니다: …드릴, 수, 있습니다`) → 검증 실패 | **15** | 같은 질의를 조금 바꿔 t2 추가 — 일부는 **SQL 자체를 `sub_query`로 씀**(`UPDATE alarm_config SET threshold = 80` · `SELECT * FROM servers WHERE cpu_usage > 90 AND cpu_usage < 10`) | 대부분 60초 벽 |
| **0행** | 7 | "대소문자 무시·부분 일치로" 등 조건 완화 t2 | 동일 |
| 성공했는데 추가 단계 | 6 | 집계·분석 후속 t2 | §2.2 과분해 |

- 산문 15건 중 **9건이 §2.4의 알람 오분류**다 — `data_query` 템플릿은 알람 테이블이 `allowed_tables`에서 빠지므로(`plans/108` §1.5) LLM이 "알람 테이블이 없다"는 산문을 낸다.
- `replanner._filter_futile_retries`(`replanner.py:115`)가 있어도 **표현만 바꾼 형제 task**는 걸러지지 않는다.
- **노드 관점**: 재시도 예산은 이미 task 안에 있다(`query_validator → query_generator` 회귀 · `QUERY_MAX_RETRY_COUNT` 3). 재계획이 그 위에 **task 파이프라인 전체를 한 번 더** 태우므로 턴 지연이 두 배가 된다. 산문 응답은 `plans/108` CU-A2(조기 종결 + 사유 노출 · 랜딩)가 task 안에서 끝내는 경로를 이미 만들었다.

### 2.4 결정적 교정의 우회 — 존 선택 재진입 경로 (108 §1.5의 원인 세분)

- **실측**: t1이 `data_query`인데 `has_alarm_signal(sub_query)`가 참이고 선행 의존이 없는 턴 **27건**. **27건 전부 `db_ids`가 고정**(존 선택)돼 있고 20건이 재진입 턴(그래프 턴 ≥ 2)이다. 그중 10건이 재계획, 9건이 t1 산문 검증 실패.
- **원인**: `intent_planner`의 사전 처리 ②.5(`intent_planner.py:321-329`)가 존 선택(`selected_db_ids`)이 있으면 **`_single_task_plan("data_query", …)`를 바로 반환**한다. 알람 교정 `_coerce_alarm_intent`는 LLM 분해 경로(`:375`)에만 걸려 있어 이 분기를 지나지 않는다. 2단에서 `routing_intent`는 task 라벨에서만 오므로(`subagents.py:784`) 알람 의도가 그대로 사라진다.
- `plans/108` §1.5는 이 소실을 "단일 `data_query` 폴백(33회 + LLM 실패 3회)"으로 집계했다. 이 문서는 그중 **존 선택 재진입이 지배적 원인**임을 더한다. 108 **G-2**(2단 전용 결함 `CU-B1` 보류)는 그대로 유효하다 — 여기서 뽑는 것은 **3단 설계 교훈**이다(§4 D-1).
- **3단에도 같은 모양의 위험이 있다**: 103 §3.1은 "단일 의도면 `plan`이 결정적으로 1 task를 만든다"이고 G-3은 교정 함수를 "계획 경로에만" 둔다. **사전 처리 분기(①~③.7)가 계획 노드 안에서 조기 반환하면 교정을 우회하는 구조가 그대로 옮겨진다.**

### 2.5 task 질의문(`sub_query`) 재작성 오염 — 복합에서 집중된다

`sub_query` 578건 중 원문과 다른 것 265건. 원문 대비 표면 대조(숫자 · 한정어 15종 · 따옴표 리터럴/SQL 키워드):

| 항목 | 단일 계획 | 복합 계획 | 예 |
|---|---:|---:|---|
| 숫자 탈락 | 1 | **10** | "은행존 서버 목록 보여주고, 그중 CPU **90%** 넘는 건…" → t1 "은행존 서버 목록 조회" |
| 한정어 탈락 | 0 | **11** | "김포 서버 목록과 여의도 서버 목록을 **각각**" → "김포 서버 목록 조회" |
| 한정어 추가 | 17 | **14** | "CPU 사용률이 높은 서버…프로세스를 분석" → "…**상위 10개** 프로세스…**평균**…" |

- **탈락은 정상 분배일 수 있다** — "90%"가 t1에서 빠지고 t2에만 있는 것은 옳다. 판정은 **task 합집합이 원문 슬롯을 덮는가**로 해야 한다(§5.3). 합집합 기준으로도 깨지는 사례: SYN-I-04 계열(t1이 "8개 이상"을 잃고 t2가 "선행 결과에 **없는** 서버"로 의미를 뒤집음).
- **추가(발명)는 분배로 설명되지 않는다** — `'critical'`은 폴스타에 없는 값이고(심각 = `alarmseverity = 3`), `SELECT … WHERE`는 SQL 생성 프롬프트에 원문 대신 들어간다. 107 §2.4가 기록한 오염 부류가 **복합 계획에서 가장 짙다**.

**그래서 정하는 것**
1. **기본값은 off 로 둔다**(G-1 확정은 계약의 방향이지 켜는 시점이 아니다).
2. 켜기 전에 **조각 출력을 모델이 지키게 만드는 것이 선행**이다 — 구조화 출력 강제·예시 보강, 또는 **위반 시 즉시 폴백하지 말고 한 번 더 조르는 재요청**(현행은 1회 위반 = 즉시 폴백). 이것이 없으면 계약은 소형 모델에서 "분해 끄기"와 같아진다.

**이 수치의 한계**
- 8건·2회차다. 항목 1건 차이는 유의하지 않다.
- **지연으로 결론내지 않는다**(D-240 ④) — 노트북 공유 MLX 이고, on 의 지연 증가에는 `cx-04` 의 재계획 3회가 섞여 있다.
- 채점은 **마지막 task 의 SQL** 로 한다 — 재계획이 task 를 덧붙이면 답이 아닌 SQL 이 채점된다(`cx-04`). M-1 이 적은 "최종 답 결과집합 채점"은 아직 하네스에 없다(잔여).
- 3단 참조 1회는 대조군이 아니다 — 4건이 검증 소진·실행 실패로 미채점이고(`core_config_prop`·`cmm_metric_stat_m` 미존재 판정, `server` 실행 실패) 샌드박스 스키마 인식 문제와 섞여 있다.
- 원자료(arm 별 json·로그)는 세션 스크래치패드에 남겼고 저장소에는 넣지 않았다(`results/`·`reports/` 는 `5ffe0d3` 부터 추적 제외).

## 5. 복합 질의 프롬프트 재작성 — 107의 확장

### 5.1 분해 출력 계약: `sub_query` 자유문 → **task 프레임**

현행 `_llm_decompose`(`intent_planner.py:682`)는 task마다 `agent`·`sub_query`(자연문)·`depends_on`/`input_from`을 낸다. 바꾼다:

```yaml
tasks:
  - task_id: t1
    agent: data_query            # 교정 대상(D-1)
    slots:                       # 원문 프레임(107 IntentFrame)의 부분집합 — 값은 원문 근거가 있어야 한다
      targets.zone: [bankjon]
      metrics: [서버]
    output: rows                 # rows | file | chart
  - task_id: t2
    agent: alarm_query
    slots:
      filters: [{field: cpu_usage, op: ">", value: 90, evidence: "CPU 90% 넘는"}]
    relation: {input_from: t1, kind: filter_by_prior}   # filter_by_prior | anti_join | compare | branch_on
```

- **값을 새로 만들지 못하게** 슬롯마다 `evidence`(원문 부분 문자열)를 요구한다 — `'critical'` 같은 발명은 근거 문자열이 원문에 없어 D-1에서 탈락한다(§2.5).
- `sub_query`는 **계획 LLM의 출력에서 뺀다.** task 텍스트는 D-2가 슬롯에서 찍는다(107 G-1.5 "자유 서술 재작성 신설 금지"의 복합 판).

### 5.2 task 프롬프트 렌더 — R1-01 예

```
[확정된 해석 — t2 / 2]
- 의도: alarm_query
- 조건: CPU 사용률 > 90 (원문: "CPU 90% 넘는")
- 대상 서버: 선행 결과(t1)의 서버 — 결과 행에서 식별자를 받는다
※ '대상' 줄은 이미 확정된 조회 대상이다. SQL의 WHERE 조건으로 쓰지 않는다.
[사용자 원문]
은행존 서버 목록 보여주고, 그중 CPU 90% 넘는 건 알람 이력도 같이 알려줘
```

- 원문은 **버리지 않는다**(107 P-5 병기). 다른 task의 조건이 번지는 위험은 "이 task의 조건" 블록이 원문보다 **앞에서 범위를 못 박는 것**으로 막는다 — 107 W3가 복합을 제외했던 이유(전체 프레임을 실으면 task 스코프가 무력화된다)는 **task 프레임만 싣는 것**으로 해소된다.
- 선행 결과 스코프는 **식별자 값을 프롬프트에 나열하지 않는다** — 값은 결정적 스코프 주입(D-086·D-095)이 SQL에 넣는다. 프롬프트에는 참조만 둔다(§2.5 "숫자 추가" 부류 차단).

### 5.3 결정적 검증(D-1 `normalize`가 수행)

| 검사 | 불합격 예 | 처리 |
|---|---|---|
| **합집합 커버** — task 슬롯 합집합 ⊇ 원문 프레임의 발화 출처 슬롯 | SYN-I-04 t1이 "8개 이상"을 잃고 t2가 부정으로 뒤집음 | 단일 task 폴백 + 사유 |
| **발명 금지** — 모든 슬롯 값의 `evidence`가 원문 부분 문자열 | `alarm_severity='critical'` | 해당 task 폐기 → 폴백 |
| **SQL 금지** — task 슬롯·렌더 결과에 SQL 키워드 문장 없음 | `UPDATE …` · `SELECT … WHERE` | 폴백 |
| **DAG** — 기존 `validate_plan_dag` | 순환·미지 참조 | 기존 되먹임 1회 → 폴백 |

검증은 107 `verify_rewrite`(재작성 대조)와 **같은 함수 계열**로 둔다 — 단일은 "재작성문 ⊇ 프레임", 복합은 "task 합집합 ⊇ 프레임"이다.

### 5.4 나눌지 말지 — 분해 계약에 넣는 규칙

§2.2의 경계를 **계획 프롬프트의 규칙과 D-1의 검증**으로 옮긴다. 판정 입력은 원문 문자열이 아니라 **구조화 슬롯**이다(D-004 — 원문 키워드 분류 신설 0).

| 나눈다 | 나누지 않는다 |
|---|---|
| 에이전트가 바뀐다 — 알람·지표·실시간 프로세스·점검(R1-05) | 같은 DB 안의 필터·안티조인·집계 비교(SYN-I-04 · R4-02) |
| 산출물이 둘이다 — 파일 + 표(R1-03) | 같은 결과의 가공(평균·정렬·상위 N) |
| 실행 그룹(존)이 갈리고 사용자가 "각각·존별로"를 요구한다(R1-02) — 기존 D-143 후속3 실행 그룹과 합류 | 사용자가 한 결과를 원하는 멀티 DB(멀티 DB 실행기가 처리) |
| 앞 결과가 뒤 **조건을 고른다**(R1-07 "차이가 큰 쪽") | 앞 결과가 뒤 **대상만 좁힌다**면 한 SQL의 서브쿼리가 먼저 — 단, 에이전트가 다르면 나눈다(SYN-H-04: 알람→지표) |

ⓑ **G-5와 D-1의 관계** — 랜딩 시점(2026-09-21)의 D-1은 **플래그가 켜졌을 때만** 2단 ②.5 우회를 닫았다. **2026-09-22 D-250 ⑤가 이를 개정했다** — 교정은 플래그에서 분리돼 2단에 항상 적용된다(구현 소유 `plans/114` T-1 · **2026-09-23 랜딩**). 조각 계약(`spans`) 쪽은 그대로 플래그 뒤에 있고 기본 off다.

ⓒ **C-4 D-2의 구현 범위(범위 축소 · 되돌리는 비용 작음)** — `task_prompt`는 task 질의를 조각으로 찍고 SQL 생성 입력을 task 범위로 좁힌다. 선행 결과 값은 task 질의에 나열하지 않는다 — 선행 결과를 받는 task는 고정 접두(`선행 결과 대상 중`)만 갖고, 값은 D-086 스코프 블록(`build_prior_rows_block`)이 SQL 프롬프트에 결정적으로 넣는다(그 블록이 이미 건수·값을 싣는다).
**§5.2의 107 `render_canonical_block` 병기 블록(원문 함께 싣기)은 적용하지 않았다.** 이유: 병기 채널(107 W3 `get_prompt_query`)은 단일 DB `query_generator`에만 있고 멀티 DB `multi_db_executor`에는 없다 — 단일 경로에만 실으면 **단일/멀티 비대칭**(Known Mistakes 「단일/멀티 경로 대칭」)이 새로 생긴다. 107 W3 채널을 멀티 경로까지 넓힐 때 함께 한다(잔여 · 107 소유).

ⓓ **C-4·C-5는 3단 전용이다** — 2단 `intent_planner`·`replanner`·`agent_orchestrator` 동작은 바뀌지 않았다(G-5 · 108 G-2). **단, D-1 교정의 플래그 분리(D-250 ⑤ · `plans/114` T-1)가 2026-09-23 랜딩돼 2단은 이제 플래그와 무관하게 알람·프로세스 교정을 받는다** — 조각 계약(`_apply_task_frames`)은 그대로 플래그 뒤이므로 이 문단의 나머지는 유효하다(§8 G-5). 2단 모듈에서 바뀐 것은 **함수 추출뿐**이다(`agent_orchestrator._task_verdict`·`_postcheck_result` · `subagents._pack_pipeline_result` · 동작 동일 — 기존 테스트 전건 통과). 3단 루프는 **계획이 필요한 데이터·알람 질의만** 탄다 — 단일 의도는 현행 직결 체인 그대로다(§0.2 · 103 G-5).

- **2단 핫픽스는 권하지 않는다** — §2.4 ②.5 우회는 한 줄 교정(`_coerce_alarm_intent`를 ②.5 반환 전에 적용)으로 닫히지만 108 **G-2**(2단 전용 결함 보류 · 사용자 확정)와 충돌한다. 3단 설계에 교훈으로만 반영한다(D-1). 사용자가 달리 정하면 G-5.
