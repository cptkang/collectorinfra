## 1. 배경과 이 계획의 범위

사용자 지시(2026-08-26): *"논문을 보면 시멘틱 라우팅 시 label only 기반으로 출력할 때 성능이
향상되었다. 이 프로젝트의 시멘틱 라우팅 성능 향상을 위해 개선 계획을 작성하라."*

논문은 동일 평가셋(250질의·7클래스)에서 **분류 지시문**과 **출력 형식** 두 요인을 분리 측정했다.
그 결과를 이 프로젝트에 이식할 수 있는지 판단하고 구현 계획을 세운다.

> **먼저 짚을 것 — 지시의 전제를 논문 데이터로 정정한다(§2.2).**
> label-only는 **모델 규모에 따라 효과가 정반대**이며, 논문이 지목한 성능 향상의 주역은
> **label-only가 아니라 개선된 분류 지시문**이다. 이 구분이 적용 방안 전체를 가른다.

### 1.1 불변식 — **멀티 DB 선택은 계속 제공한다** (v6 · 사용자 확정)

> 사용자 확정(2026-08-26): *"멀티 DB 선택은 기능을 제공해야 한다."*

현행 라우터는 하나의 질의에 대해 **여러 DB를 동시에 선택**하고 각 DB별 조회 내용을
`sub_query_context`로 분리한다(`prompts/semantic_router.py:38-60`).

```json
{"intent": "data_query", "databases": [
   {"db_id": "cloud_portal",  "sub_query_context": "VM 정보 조회", ...},
   {"db_id": "polestar_b0",   "sub_query_context": "서버 사양 조회", ...}]}
```

**이 능력은 본 계획의 어떤 트랙으로도 축소되지 않는다.** 아래를 계획 전체의 불변식으로 둔다.

| 불변식 | 검증 |
|---|---|
| 하나의 질의가 **N개 DB를 선택**할 수 있다 | 멀티 DB 골든셋 케이스가 단일 선택으로 축소되지 않음 |
| DB별 **`sub_query_context` 분리**가 유지된다 | 분리 실패 시 회귀로 판정 |
| 위치·환경 정보는 **DB 라우팅에만** 쓰이고 `sub_query_context`에 섞이지 않는다(`:43-46`) | 기존 규칙 유지 |

#### 이 불변식이 트랙 D(label-only)를 사실상 배제한다 ★

**순수 label-only는 라벨 하나만 출력하므로 `databases` 배열을 표현할 수 없다.**
멀티 DB를 제공해야 한다면 선택지는 둘뿐이다.

| 경로 | 멀티 DB | 판정 |
|---|---|---|
| **C-0 ① 라벨 선행 하이브리드** — `data_query\n{"databases":[…]}` | **✔ 배열 유지** | **채택** — 첫 토큰=라벨(신뢰도 확보) + 멀티 DB 보존 |
| **트랙 B 2단 분리** — 1단계 intent만 label-only, 2단계 DB는 JSON | **✔ 2단계가 배열** | **label-only 이득의 유일 경로**(v7 · B-0 ④). 대가는 호출 2회·컨텍스트 대역폭(B-2) |
| **트랙 D 순수 label-only** | **✘ 표현 불가** | **배제**(v6) — 불변식과 정면 충돌 |

> **귀결**: **트랙 D는 "조건부 검토"에서 "불변식 위배로 배제"로 바뀐다.**
> 논문의 label-only 이득(9B +11.2%p)은 **C-0 ①이 첫 토큰을 라벨로 만드는 것으로 부분 취득**한다 —
> 신뢰도(logprob) 이득은 그대로 얻고, 출력 형식만 하이브리드로 남긴다.
> **다만 "형식이 짧아져서 얻는 이득"이 있었다면 그 부분은 포기**한다(§2.5 혼입 때문에 얼마인지
> 분리되지 않으며, 멀티 DB가 그보다 우선한다).

| Model | baseline instr.<br>+ JSON | revised instr.<br>+ JSON | baseline instr.<br>+ label-only | revised instr.<br>+ label-only | **지시문 효과**(%p) |

1. **지시문 효과는 모든 모델에서 일관되게 양수**다(+9.2 ~ +17.6%p). 모델 규모와 무관하다.

> *"For this task the **classification instruction, not parameter scale**, governed classification accuracy."*
> *"revising the classification instruction was **more effective than increasing model capacity**"*
> — 개선 지시문 하에서는 **1.5B(87.1%)가 9B(84.0%)를 앞섰다.**

### 2.5 ⚠ 논문이 스스로 밝힌 혼입(confounding)

> *"In this implementation the output format and the confidence source are **set by a single switch and
> therefore vary together**: JSON denotes structured output with self-reported confidence, and label-only
> denotes bare-label output with first-token log-probability confidence."*

**즉 label-only의 측정 효과에는 logprob confidence의 효과가 섞여 있다.**
본 계획은 이 둘을 **분리 가능한 스위치로 구현**해 이 혼입을 재현하지 않는다(§5 트랙 C).

> **v4 정정 — 완전 독립은 불가능하다.** 논문이 둘을 한 스위치로 묶은 것은 구현 편의가 아니라
> **신뢰도가 첫 생성 토큰에서 나오므로 그 토큰이 라벨이어야 한다는 제약** 때문이다. 정확히는
> **"제약이 있는 분리"** — 측정은 분리하되, 신뢰도 산출이 출력 구조에 요구사항을 건다(§5 **C-0**).

## 3. 현행 실측 — 이 프로젝트의 라우터

> 2026-08-26 코드 실측.

| 항목 | 현재 상태 | 근거 |
|---|---|---|

| 분류 범위 | **intent + 대상 DB 동시 분류** | `_llm_classify` docstring — *"LLM을 사용하여 질의의 **대상 DB를 분류**한다"*, 반환 `list[dict]` |
| 신뢰도 | 자기보고 계열(임계 비교) | `MIN_RELEVANCE_SCORE` 기반 |
| few-shot 예시 | **JSON 예시 19개** — `alarm_query` **7개(37%)** 편중 | `prompts/semantic_router.py` 실측 §3.5④ |
| 운영 LLM | **FabriX (KBGenAI 모드)** — 사용자 확인(2026-08-26). `.env`의 `LLM_PROVIDER=gemini`는 개발값 | `src/llm.py:246-277` |
| 폐쇄망 운영 예정 | vLLM **Qwen3.5-9B** 오케스트레이터 | D-037 |

### 3.1 이식을 가로막는 세 가지 차이

**① intent 단독이 아니라 intent + DB 동시 분류다** ★ 최대 제약
논문은 intent 하나만 출력하므로 label-only가 성립한다. 이 프로젝트는 **한 번의 호출로 intent와
대상 DB를 함께 결정**한다. **단일 라벨로는 DB 선택 정보를 표현할 수 없다.**
→ v3까지는 *"label-only를 쓰려면 분류를 두 단계로 나눠야 한다"*(트랙 B)고 보았으나,
**v4에서 완화됐다**: **라벨 선행 하이브리드**(`data_query\n{"databases":[…]}`)를 쓰면
동시 분류를 유지한 채 첫 토큰을 라벨로 만들 수 있다(§5 **C-0 ①**). 트랙 B는 **선택지**가 된다.

**② 모델 계열이 다르다**
논문은 로컬 Qwen/Gemma(0.5B~9B)를 측정했고, 현재 운영은 **FabriX(KBGenAI)** 다.
**Table 13의 규모별 결론을 그대로 이식할 수 없다** — FabriX 서빙 모델이 9B급으로 거동한다는 보장이 없고,
Gemma3-1B가 label collapse를 보인 사실은 **계열 차이도 변수임**을 시사한다.
→ **이 프로젝트에서 재측정하기 전에는 label-only를 켜지 않는다.**

**③ logprob은 현행 경로에서 원천 불가다 — 확정**(v13 정정 · 종전 "미확인")
논문의 confidence 이득은 vLLM `top_logprobs`에 의존한다(`NWAgent_bench/.../entropy_utils.py`:
`confidence_top1_from_logprobs`). **실측 결과 운영 LLM은 Gemini가 아니라 FabriX이며 KBGenAI
모드다**(`src/llm.py::_create_fabrix` — `fabrix_client_key`가 있으면 `KBGenAIChat`).
그 프로토콜은 요청 `{modelId, contents, systemPrompt, …}` · 응답 `{status, content}`(텍스트)로
**logprobs를 실을 자리 자체가 없다**. 미측정이 아니라 **구조적 부재**다.
→ **트랙 C 전체를 라우터 평면 이동 후로 이월**한다(§8 ②). 재개 최단 경로는 **라우터를 제어 평면으로
이동**하는 것이며 사용자 판단 사항이다(§8 ⑪).
**추가(v4)**: 가용성만으로는 부족하다 — **첫 생성 토큰이 라벨이어야** 그 logprob이 의도 신뢰도가 된다.
현행 JSON 선행 프롬프트에서는 첫 토큰이 구조 토큰이라 **읽어도 무의미**하다(§5 C-0).

### 3.2 신뢰도 현황 — **자기보고 값으로 후보를 잘라내고 있다** (v2 추가 실측)

> 사용자 지시(2026-08-26): *"logprob 신뢰도는 성능 향상보다 **분류한 의도의 신뢰도를 측정하는
> 측면**에서 활용해야 한다."* 이 관점으로 현행을 다시 보니 **문제가 성능이 아니라 판정에 있다.**

| 항목 | 실측 |
|---|---|
| `relevance_score`의 출처 | **LLM이 JSON에 직접 써넣는 자기보고 값** — `prompts/semantic_router.py:89` *"relevance_score는 0.0~1.0 사이의 관련도 점수"* |
| few-shot이 보여주는 값 | **0.8 · 0.9 · 0.95 · 1.0** (`:116·126·136·148·159`) — 낮은 값 예시가 **사실상 없다** |
| 임계 | `MIN_RELEVANCE_SCORE = 0.3` (`routing/semantic_router.py:42`) |
| 사용처 | 라우팅 대상 필터(`:276`) · **2단 경로에서도 동일 필터**(`subagents.py:166`) |

**여기서 나오는 문제:**

1. **논문이 측정한 바로 그 자기보고 방식**이다 — 7개 모델 전부 **과신**(gap +0.066 ~ +0.947).
   과신하는 값으로 후보를 거르면 **관련 없는 DB도 통과**한다.
2. **few-shot이 0.8~1.0만 보여준다.** 모델은 예시를 따르므로 출력이 그 대역에 몰릴 개연성이 높고,
   그렇다면 **임계 0.3은 거의 아무것도 걸러내지 못한다** — 게이트가 형식적으로만 존재하게 된다.
   → **v3에서 이보다 강한 근거를 찾았다**: 프롬프트가 **모델에게 0.3 미만을 스스로 버리라고 지시**한다
   (규칙 5). 추론이 아니라 **명시된 지시**이므로 게이트 no-op은 개연성이 아니라 **설계상 귀결**이다(§3.5①).
3. 즉 **현행 신뢰도는 "얼마나 확신하는가"를 재는 눈금이 아니라, 프롬프트가 시킨 대로 채워지는
   자리표시자에 가깝다.** 이 상태에서는 저신뢰 질의를 식별할 수단이 없다.

> **파생 판단**: 그러므로 logprob의 값어치는 정확도 +몇 %p가 아니라, **판정 가능한 눈금을 처음으로
> 갖는 것**이다. 트랙 C를 그 관점으로 재정의한다(§5 트랙 C).

### 3.4 반대로, **지시문 개선은 즉시 적용 가능하고 이 프로젝트에 특히 유효할 가능성이 높다**

논문이 지목한 개선 항목 ①(정답 분포와 모순되는 예시 제거)은 이 프로젝트의 알려진 문제와 겹친다:

- Known Mistakes: *"프롬프트 강제가 프로필 few-shot 예시와 경쟁해 반복 실패"* — **예시가 지시문을
  이긴 사례**가 이 저장소에 기록되어 있다.

→ **트랙 A(지시문 개선)가 1순위인 이유**다.

### 3.5 프롬프트 전수 감사 (v3 · `src/prompts/semantic_router.py` 367줄 실측)

트랙 A를 실행 가능하게 하려면 "감사하라"가 아니라 **감사 결과**가 있어야 한다. 아래가 그 결과다.

#### 발견 ① — **저신뢰가 구조적으로 표현될 수 없다** ★ 가장 중요

프롬프트 「판단 규칙」이 모델에게 **저신뢰 항목을 스스로 버리라고 지시**한다.

```
4. 확실한 매칭이면 0.8 이상, 가능성 있는 매칭이면 0.5~0.8, 약한 연관이면 0.3~0.5를 부여합니다.
5. 0.3 미만의 관련도를 가진 DB는 포함하지 마세요.          ← :91
```

그리고 코드는 그 뒤에서 **같은 임계로 다시 거른다**:

```python
MIN_RELEVANCE_SCORE = 0.3                                    # routing/semantic_router.py:42
targets = [r for r in llm_results if r["relevance_score"] >= MIN_RELEVANCE_SCORE]   # :276
```

**결과: 모델이 지시를 따르면 0.3 미만이 출력에 없으므로, 코드 게이트에 걸리는 항목이 원천적으로
존재하지 않는다 — 게이트가 구조적으로 no-op이다.**

더 나쁜 것은 **걸러진 정보가 복구 불가**라는 점이다. 모델이 "이 DB는 0.2쯤 관련 있다"고 판단해도
그 신호는 출력에 실리지 않으므로, **시스템은 저신뢰 상황이 있었다는 사실 자체를 알 수 없다.**

> **트랙 C의 전제가 여기서 나온다**: 신뢰도 소스를 logprob으로 바꾸더라도, **규칙 5가 남아 있으면
> 저신뢰 후보가 애초에 출력되지 않는다.** 신뢰도 소스 교체와 **무관한 구조적 차단**이므로
> **규칙 5 제거가 트랙 C의 선행 조건**이다(§5 트랙 C-1).

#### 발견 ② — 예시가 고신뢰 대역만 보여준다

| `relevance_score` | 예시 개수 |
|---|---|
| 1.0 | 3 |
| 0.95 | 5 |
| 0.9 | 5 |
| 0.8 | 1 |
| **0.5~0.8**(규칙 4의 "가능성 있는") | **0** |
| **0.3~0.5**(규칙 4의 "약한 연관") | **0** |

**규칙 4가 정의한 3개 대역 중 상위 하나만 예시가 있다.** 모델은 지시문보다 예시를 따르므로
(Known Mistakes에 기록된 이 저장소의 반복 실패 양상), 중·저 대역은 사실상 학습 신호가 없다.

#### 발견 ③ — 클래스 정의와 실제 클래스가 불일치한다

| | 개수 | 내용 |
|---|---|---|
| 「출력 형식」 절의 정의(`:81-83`) | **3** | `data_query` · `alarm_query` · `cache_management` |
| 전용 판단 절(`## ` 헤더) | **5** | 알람(`:94`) · DB 설명(`:219`) · 캐시 관리(`:225`) · 일반 추론(`:264`) · 장애 진단(`:339`) |
| few-shot 예시 등장 | **5** | + `general_inference` · `fault_diagnosis` |
| ~~`synonym_registration`~~ | 0회 언급 | **오판 정정(v10)** — LLM 산출 intent가 아니다. `routing/semantic_router.py:90-107`이 `parsed_requirements`를 보고 **결정적으로 라우팅**한다(멀티턴 승인 흐름). 프롬프트에 없는 것이 **정상** |

**정의부(3)와 전용 절(5)·예시(5)의 불일치는 실재**하며 이것이 A-3의 대상이다.
(`synonym_registration` 항목은 v10에서 오판으로 정정 — 위 표 각주.)

#### 발견 ④ — `alarm_query` 편중

| 클래스 | few-shot 예시 | 비중 |
|---|---:|---|
| **`alarm_query`** | **7** | **37%** |
| `data_query` | 4 | 21% |
| `general_inference` | 3 | 16% |
| `cache_management` | 3 | 16% |
| `fault_diagnosis` | 2 | 11% |
| `synonym_registration` | **0** | — |

게다가 `alarm_query`만 **전용 패턴 목록 절**(`:94-107`, 7개 패턴 카테고리)을 갖는다.
다른 클래스에는 그런 절이 없다. **한 클래스에 지시와 예시가 동시에 몰린 비대칭**이며,
`plans/63`(과적합 분리)이 다루는 문제와 같은 형태다.

#### 발견 ⑤ — 우선순위 선언과 배치가 어긋난다

`fault_diagnosis` 절은 **"— 최우선 검토"** 라고 표기돼 있으나 위치는 **파일 맨 끝(`:339`)** 이다.
「intent 판단 우선순위」 절은 `:253`에 있어 그보다 앞선다. 즉 **우선순위 규칙이 선언된 뒤에
"최우선" 클래스가 등장**한다. 긴 프롬프트에서 위치는 주의 배분에 영향을 주며(§2.4 U자형 어텐션
논의와 같은 계열), 최소한 **선언과 배치를 일치**시켜야 한다.

#### 발견 ⑥ — `unknown`이 없다

논문이 unknown recall 개선의 직접 원인으로 지목한 **"모호한 질의를 `unknown`으로 분류하는 예시"**
가 없을 뿐 아니라, **`unknown`에 해당하는 클래스 자체가 없다.**
현행에서 모호한 질의는 `general_inference`(DB 미접근 일반 응답)로 흡수되는데, 이는
**"분류 불가"와 의미가 다르다**(§8 미해결 ①).

### 3.6 응답 **처리** 실측 (v12 · `src/routing/semantic_router.py` — Instructor 검토 중 발견)

§3.5는 **프롬프트**를 감사했다. 이 절은 **응답을 받은 뒤의 처리**를 감사한다.
두 결함 모두 **어느 계획서에도 등재돼 있지 않았다**(근거: `docs/instructor_intent_extraction_review.md` §3).

#### 발견 ⑦ — `intent`가 알려진 클래스 집합과 대조되지 않는다 (**F1**)

```python
# src/routing/semantic_router.py:439
intent = parsed.get("intent", "data_query")
```

이후 가드는 **하나뿐이다** — `fault_diagnosis` → `data_query` 강등(`:248`, Plan 64 CW-B 옵트인 보호).
**나머지 전 범위에 허용 집합 검증이 없다.** 하류는 `if intent == "cache_management"` /
`== "general_inference"` 동등 비교이므로, LLM이 오타·환각 intent(예: `"프로세스조회"`,
`"alarm_qeury"`)를 내면 **어느 분기에도 걸리지 않고 조용히 DB 조회 경로로 낙하**한다.

**A-1과 결합하면 노출이 커진다** — A-1이 "낮아도 그대로 값을 부여하라"로 모델의 자기 검열을
없앴으므로, 저신뢰 상황에서 모델이 **경계 밖 라벨**을 낼 여지도 함께 늘었다.

#### 발견 ⑧ — 한 항목의 형식 오류가 **분류 전체**를 폐기한다 (**F2**)

```python
# src/routing/semantic_router.py:452
"relevance_score": float(db_entry.get("relevance_score", 0.5)),
```

`float()`가 raw로 걸려 있다. LLM이 `"높음"`·`"0.9 (높음)"`·`"0.9점"`을 반환하면 `ValueError`가
나고, 호출부(`:225` `except Exception`)가 이를 삼켜 **`llm_results` 전체를 버리고
`active_db_ids[0]` 단일 폴백**으로 간다.

> **왜 지금 중요한가**: **멀티 DB 선택(§1.1 불변식)이 조용히 단일 선택으로 축소되는 경로**다.
> §8 ⑩이 *"임계를 올리면 멀티 DB가 축소된다"* 를 경고하는데, **여기는 임계와 무관하게
> 값 하나의 형식만으로 축소가 일어난다.** 게다가 A-1로 후보 수가 늘어 **노출 표면이 커졌다.**

**부수 발견** — 무효 `db_id`는 `if db_id in valid_db_ids`(`:449`)로 **로그 없이 탈락**한다.
전부 무효면 *"라우팅 결과 없음"* 경고만 남아 **"모델이 못 골랐다"와 "모델이 환각했다"가 구분되지
않는다**(침묵 폴백 금지 규약 저촉).

으로만 쓴다(`process_query`가 이미 그 방식으로 쓰고 있다 — 첫 턴 db_id 재도출 결정적 폴백).

#### B-1. 설계

1. **1단계: intent 분류**(라벨 하나) → **2단계: DB 선택**(intent 확정 후 후보 축소)
2. **문맥 손실 방지**: 위치 힌트(`_LOCATION_DB_HINTS`)·`db_descriptions`·사용자 DB 직접 지정 규칙을
   2단계에 전달한다. 특히 **"사용자가 DB를 직접 지정"**(`:24-36`)은 intent와 무관하게 작동해야 하므로
   **1단계 이전에 결정적으로 선처리**하는 편이 안전하다.
3. **멀티 DB 질의 처리**: 현행은 한 번에 여러 DB를 선택하고 `sub_query_context`를 분리한다(`:38-60`).
   2단계에서도 **다중 선택과 sub_query 분리를 유지**해야 한다 — 단일 선택으로 축소하면 회귀다.
4. **하위 호환**: 기존 단일 호출 경로를 플래그로 보존(`ROUTER_TWO_STAGE_ENABLED`, 기본 off).
   off면 비트 동일(회귀 0).
5. **신뢰도 2축 산출**(②): intent 신뢰도와 DB 신뢰도를 각각 기록한다. 임계도 각각 정한다(C-4).

#### B-2. 트레이드오프 재분석 — **오류 전파는 차이가 아니다**(v8 정정)

> **v5~v7 서술은 틀렸다(사용자 지적 2026-08-26).** *"단일 호출은 intent와 DB를 동시에 고려하므로
> 상호 보정이 일어난다"* 고 썼으나, **성립하지 않는다.**

**근거 — 단일 호출도 이미 순차적이다.** 현행 출력 스키마는 `intent`가 `databases`보다
**먼저** 나온다(`prompts/semantic_router.py:67-70`):

```json
{"intent": "data_query",          ← 먼저 생성·확정
 "databases": [ … ]}              ← 확정된 intent를 조건으로 생성
```

LLM은 autoregressive이므로 **`databases`를 만들 때 `intent`는 이미 확정된 토큰**이고,
**되짚어 고칠 수 없다.** v6에서 채택한 라벨 선행 하이브리드(`data_query\n{"databases":[…]}`)도
순서가 같다. → **어느 형식이든 intent → DB 순서이므로 오류 전파 구조는 동일하다.**

**그러면 실제 차이는 무엇인가.** 둘이고, 방향이 반대다.

| 축 | 단일 호출 | 2단 분리 | 유불리 |
|---|---|---|---|
| **컨텍스트 대역폭** | DB 생성 시 **프롬프트 전체와 내부 표현**을 그대로 참조(알람 패턴 목록·클래스 정의 등) | 2단계는 **"intent 라벨"이라는 요약만** 전달받음 | **분리가 불리** |
| **조기 차단** | 다 생성된 뒤에야 신뢰도를 안다 | **1단계 신뢰도를 보고 2단계 진입 전에 멈출 수 있다** | **분리가 유리** |

**따라서 B-2는 "오류 전파"가 아니라 "컨텍스트 대역폭 손실"의 문제다.**

- **완화**: 2단계 프롬프트에 intent 라벨만이 아니라 **1단계가 참조한 판단 근거**(해당 intent의
  클래스 정의·관련 패턴)를 함께 전달한다. 전량이 아니라 **해당 intent에 해당하는 절만** 넣으면
  프롬프트 축소(B-0 ③) 이득을 유지하면서 대역폭 손실을 줄인다.
- **측정**: 단일 경로와 2단 경로의 **분류 불일치 사례를 개별 분석**해 손실이 실제로 발생하는지 본다
  (B 수용 기준에 이미 있음).

#### B-2-1. 조기 차단은 **비용 판단도 바꾼다**

v7까지 *"D-004 때문에 2단계도 LLM이므로 호출 2회 확정"* 이라고 했으나, 조기 차단을 넣으면
**"항상 2회"가 아니다**:

```
1단계 intent 분류 (LLM)
   ├─ 신뢰도 ≥ 임계 → 2단계 DB 선택 (LLM)        … 2회
   └─ 신뢰도 <  임계 → 되묻기 · 중단              … 1회 (2단계 호출 없음)
```

저신뢰 질의는 **어차피 결과를 쓸 수 없으므로** 2단계 호출이 낭비다. 분리하면 그 낭비를 **미리**
막는다 — 단일 호출은 이미 다 생성한 뒤에 버린다.

> **순 효과**: 분리의 대가는 v7까지 생각한 것보다 **작다**. 남는 실질 대가는
> **① 컨텍스트 대역폭 손실**(완화 가능) **② 정상 경로의 호출 2회**(조기 차단으로 일부 상쇄)
> **③ KV 캐시 접두부 분기**(B-3)뿐이다.


#### B-3. 비용

호출 1회 → 2회. **지연·토큰 증가분을 측정**해 ②의 이득과 비교한다
(`plans/78` P12 — 비싼 경로는 근거가 있을 때만). KV 캐시 관점에서도 **프롬프트 접두부가 둘로
갈라지므로** 캐시 재사용 특성이 달라진다(`plans/78` §3.4.3③ 계열 — 측정 항목에 포함).

**수용 기준**
- 2단 경로가 단일 경로와 **동일 분류 결과**를 내는 비율 측정(불일치 사례는 개별 분석).
- **멀티 DB 선택·`sub_query_context` 분리가 보존**된다(단일 선택 축소 = 회귀).
- 사용자 DB 직접 지정이 **intent와 무관하게** 반영된다.
- intent·DB **신뢰도가 각각 산출**되고 임계가 각각 적용된다.
- **조기 차단이 동작한다** — 1단계 저신뢰 시 2단계 호출 없이 중단·되묻기(B-2-1).
- **컨텍스트 대역폭 손실 측정** — 단일 경로와 불일치한 사례를 개별 분석해, 2단계가 못 본 근거
  때문인지 확인한다(B-2 완화책 적용 전후 대조).
- 지연·토큰·KV 캐시 영향 계측치가 남는다. 플래그 off 시 회귀 0.


### 트랙 C — **의도 신뢰도 측정·판정 인프라** (v2 재정의) · D-169

> ## ⛔ 이월 확정 (v13 배너)
> **사유**: 운영 LLM이 FabriX **KBGenAI 모드**라 응답 스펙에 logprobs 자리가 **원천적으로 없다**
> (§3.1 ③ · §8 ②). 가용성 미측정이 아니라 구조적 부재다.
> **재개 조건**: 라우터 평면 이동, 또는 **라우터를 제어 평면(vLLM)으로 이동**(§8 ⑪ — 최단 경로 · 사용자 판단).
> **아래 C-0~C-4 설계는 보존한다** — 재개 시 그대로 재사용하며, 순서 서술("A와 병행 · D보다 선행")도
> **재개 시점 기준**으로 읽는다. 재개 시 계약 C-C가 발효되고 감사 스키마에 신뢰도 필드가 추가된다
> (`plans/80` C-B ②).

> **목적 정정(사용자 지시 2026-08-26)**: logprob는 **정확도를 올리는 레버가 아니라, 분류한 의도의
> 신뢰도를 재는 눈금**이다. 따라서 성공 기준도 정확도(%p)가 아니라 **calibration 품질과 저신뢰
> 처리의 실효성**이다.
>
> **순서도 바뀐다**: 트랙 C는 A/B/D의 **경쟁자가 아니라 전제**다 — 신뢰도를 못 재면 A·B·D의 효과도
> 판정할 수 없다(`plans/78` **P13** 측정이 최적화보다 먼저). **A와 병행, D보다 선행**한다.

#### C-0. **프롬프트 구조 요구 — 첫 토큰이 라벨이어야 한다** (v4 신설) ★

> **사용자 지적(2026-08-26)**: *"logprob를 기반으로 처리하려면 템플릿 프롬프트도 같이 수정되어야
> 하지 않냐?"* — **맞다. v3까지 검토되지 않았고, 이는 트랙 C의 성립 조건이다.**

**왜 프롬프트를 건드려야 하는가.** logprob 신뢰도는 **첫 생성 토큰**에서 나온다.
벤치마크 구현이 이를 명시한다:

```python
# NWAgent_bench/.../semantic_router_graph.py:403
response.response_metadata["logprobs"]["content"][0]["top_logprobs"]
#                                              ↑ 첫 번째 생성 토큰
```

테스트 픽스처의 토큰은 `("routing", ln 0.7) · ("manual", ln 0.2) · …` — **첫 토큰이 곧 라벨**이다.

**현행 프롬프트에서는 성립하지 않는다.** `:64` *"반드시 아래 JSON 형식으로만 응답하세요"* 이므로
첫 생성 토큰은 ` ``` ` 또는 `{` 또는 `"` 같은 **구조 토큰**이다. 그 top-1 확률은
**"JSON을 시작할 확신"이지 "`data_query`라는 확신"이 아니다.**
→ 그대로 logprob을 읽으면 **의도와 무관한 수치를 신뢰도라 부르게 된다.**

> **v2 서술 정정**: "형식(D)과 신뢰도(C)는 **독립 스위치**"라고 했으나, **완전 독립은 불가능**하다.
> 논문이 둘을 한 스위치로 묶은 것은 구현 편의가 아니라 **첫 토큰이 라벨이어야 한다는 제약** 때문이다.
> 정확히는 **"제약이 있는 분리"** — 혼입은 피하되, 신뢰도 산출은 출력 구조에 요구사항을 건다.

**선택지 — 첫 토큰을 라벨로 만드는 방법**

| # | 방식 | intent+DB 동시 분류 유지 | 트랙 B 필요 | 비고 |
|---|---|---|---|---|
| **①** | **라벨 선행 하이브리드** — `data_query\n{"databases":[…]}` 형태로 **라벨을 먼저, JSON을 뒤에** | **✔ 유지** | **불요** | 첫 토큰=라벨 확보 + DB 정보 보존. **유력안** |
| ② | 2단 호출 — intent는 label-only 별도 호출 | 분리됨 | **필요** | 호출 2회 비용(트랙 B-4) |
| ③ | 토큰 위치 특정 — JSON 안 `intent` 값 토큰을 찾아 그 logprob 사용 | ✔ 유지 | 불요 | 토크나이저·포맷 변화에 **취약**. 구조 토큰 스킵 로직 필요 |
| ④ | **제약 디코딩** — 첫 토큰을 라벨 집합으로 제한(logit bias·guided decoding) | ✔ 유지 | 불요 | 분포가 곧 라벨 분포. `plans/78` **P14**(Manus 로짓 마스킹)와 같은 발상. vLLM 한정 |

**권고: ①을 기본안, ④를 vLLM 경로의 강화안으로 둔다.**
①은 프롬프트 「출력 형식」 절 수정만으로 성립하고, **트랙 B(2단 분리)를 선행 조건에서 뗀다** —
v3까지 "label-only는 트랙 B가 선행"이라 했는데, ①을 쓰면 **트랙 C는 트랙 B 없이도 가능**하다.

**부수 이득 — 분포 기반 불확실성**: `top_logprobs`는 K개를 주므로 **라벨 후보 간 분포**를 얻는다.
벤치마크가 `shannon_entropy_from_logprobs`로 엔트로피를 계산하는 이유다(단순 top-1이 아니다).
이 분포는 **C-3 ④ collapse 감지**에 직접 쓰인다 — 특정 라벨에 확률이 쏠리는지 한 번의 호출로 보인다.

**프롬프트 측 변경 항목(트랙 A와 함께 적용)**

- 「출력 형식」 절: **라벨 선행** 구조로 교체(①)
- **모든 few-shot 예시의 출력부를 같은 구조로 갱신** — 예시가 지시문을 이기므로(Known Mistakes),
  형식 변경 시 예시를 남겨두면 모델은 옛 형식을 따른다
- 파싱부 대응: `_llm_classify` 응답 파서가 **선행 라벨 + JSON**을 함께 처리해야 한다
- **라벨 토큰화 확인**: 라벨이 **단일 토큰으로 쪼개지는지** 실측한다. `data_query`가 여러 토큰으로
  나뉘면 첫 토큰(`data`)만으로는 `data_query`/`data_...` 구분이 안 될 수 있다 —
  필요하면 **라벨 명을 토크나이저 친화적으로 조정**한다(논문의 "이름을 모델 관례에 맞춤"과 같은 계열)

#### C-1. 신뢰도 소스 확보

> **선행 조건 두 가지** ★: **① C-0(프롬프트 구조 — 첫 토큰이 라벨)** · **② 트랙 A-1(규칙 5 제거)**.
> 전자는 신뢰도를 *읽을 수* 있게 하고, 후자는 저신뢰 후보가 *출력되게* 한다. 둘 다 프롬프트 수정이다.
>
> **A-1 상세**: 프롬프트가 모델에게 저신뢰 항목을 버리게 하는 한,
> **신뢰도 소스를 무엇으로 바꾸든 저신뢰 후보가 출력되지 않는다**(§3.5①). A-1은 신뢰도 소스와
> 무관한 **구조적 차단**이므로 트랙 C의 어떤 항목보다 먼저다.

1. ~~가용성 실측 선행~~ → **v11: 실측 완료 · 결론 확정**. 운영 LLM은 **FabriX KBGenAI 모드**이고
   요청·응답 스펙에 logprobs 자리가 없어 **원천 불가**다(§3.1③ · §8 ②). → **트랙 C 전체를 vLLM
   전환 후로 이월**한다. 그때까지 **자기보고의 신뢰 불가 사실(§3.2)은 그대로 남으므로**,
   현행 경로에서 신뢰도가 필요하면 대체 지표(자기일관성 샘플링 분산)를 별도 검토한다.
   **가장 빠른 재개 경로는 라우터를 제어 평면(vLLM)으로 옮기는 것**이다(§8 ⑪ — 사용자 확인 사항).
2. **출력 형식과 분리된 플래그**: `ROUTER_CONFIDENCE_SOURCE = self_report | logprob`.
   논문의 혼입(§2.5)을 재현하지 않는다 — 형식(트랙 D)과 신뢰도(트랙 C)는 **독립 스위치**.
3. intent와 DB 각각의 신뢰도를 구분해 산출한다(트랙 B의 2단 분리와 정합 — 같은 값 하나로
   두 판단을 덮지 않는다).

#### C-2. 측정 — calibration을 지표로 삼는다

| 지표 | 의미 | 현행 대비 |
|---|---|---|
| **confidence-accuracy gap** | 신뢰도가 실제 정확도를 얼마나 벗어나는가 | 논문: 자기보고 **전 모델 과신**(+0.066~+0.947) / logprob 9B **−0.007** |
| **ECE**(구간별 기대 보정 오차) | 신뢰도 구간마다 실제 정확도가 맞는가 | 신규 |
| **신뢰도 분포** | 값이 특정 대역(0.8~1.0)에 몰리는가 | §3.2 문제의 직접 관측 |
| **예측 분포** | 소수 클래스로 집중되는가(**collapse**) | 신규 |

**핵심 관측 항목**: 현행 자기보고 값이 실제로 0.8~1.0에 몰려 **임계 0.3이 무력한지**를 먼저
데이터로 확인한다(§3.2는 프롬프트로부터의 추론이므로 **실측으로 확정**해야 한다).

#### C-3. 활용 — 신뢰도로 무엇을 할 것인가 ★ 이 트랙의 실질

측정만으로는 값이 없다. **판정에 연결**해야 한다. 네 가지 용도로 쓴다.

| 용도 | 동작 | 재사용 자산 |
|---|---|---|
| **① 저신뢰 → 되묻기** | 임계 미만이면 분류를 밀어붙이지 않고 **사용자에게 선택지를 되묻는다** | **`build_zone_clarification` · `status="clarification"`**(§3.3) — 신규 UI 불필요 |
| **② 저신뢰 → 비싼·위험 경로 차단** | 저신뢰 상태로 `sre_agent` 위임·실호스트 조사에 진입시키지 않는다 | `plans/78` **P12** · W3-2 경로 선택 |
| **③ 관측 기록** | 요청별 신뢰도·분포를 감사에 남겨 **라우팅 품질 추세**를 본다. 지시문 변경(트랙 A)의 효과 판정 근거 | `plans/78` W6 감사 스키마 |
| **④ collapse 감지** | 신뢰도가 높은데 예측이 소수 클래스에 몰리면 이상으로 판정 | D-035 결정적 가드 |

> **④가 필요한 이유**: 논문에서 붕괴한 모델은 **logprob으로도 과신을 유지**했다(Gemma3-1B +0.648).
> 즉 **신뢰도만으로 안전을 판정하면 안 된다** — 분포 감시를 결정적으로 병행한다.

#### C-4. 임계 재설계 (기존 값을 그대로 쓰지 않는다)

- `MIN_RELEVANCE_SCORE = 0.3`은 **자기보고 스케일 기준**이다. logprob 확률은 분포가 전혀 다르므로
  **그대로 쓰면 게이트가 의미를 잃는다**(현행이 이미 그런 상태일 가능성 — §3.2).
- 임계는 **측정된 calibration 곡선에서 도출**한다(예: 목표 정밀도를 만족하는 최소 신뢰도).
- 임계 변경은 `semantic_router.py:276`과 `subagents.py:166` **양쪽에 대칭 적용**한다
  (Known Mistakes — 한쪽만 고치는 비대칭).

**수용 기준**
- 신뢰도 소스가 **형식과 독립적으로** 전환된다(혼입 없음).
- gap·ECE·신뢰도 분포·예측 분포가 **산출되고 감사에 기록**된다.
- **현행 자기보고 값의 분포가 실측으로 문서화**된다(임계 무력 여부 확정).
- 저신뢰 시 **되묻기가 동작**하고, 저신뢰 상태로 비싼 경로에 진입하지 않는다.
- collapse 감지가 동작한다(신뢰도 높음 + 분포 집중 = 경보).
- 임계 재설계 근거가 곡선과 함께 남는다.

#### E-1. `intent` 허용 집합 대조 (§3.6 발견 ⑦ · **F1**)

- 라우터가 산출한 `intent`를 **알려진 클래스 집합과 대조**하고, 미상이면 `data_query`로 강등한다.
- **강등은 반드시 로그로 남긴다** — 현행 `fault_diagnosis` 강등(`:248`)과 같은 형태.
- 허용 집합은 **프롬프트의 클래스 정의와 단일 출처를 공유**해야 한다(A-3이 정의 집합을
  일원화했으므로, 코드가 그 집합을 사본으로 다시 적으면 D-053 위반이자 드리프트 원천이다).
- **옵트인 상호작용 주의**: `fault_diagnosis`는 `fault_diagnosis_enabled`에 종속된 조건부
  클래스다(plan 80 계약 **C-A**). 허용 집합도 **플래그에 따라 달라져야** 한다 —
  off일 때 허용 집합에 넣으면 CW-B 옵트인 계약이 깨진다.

**수용 기준**: 미상 intent가 `data_query`로 강등되고 **사유가 기록된다** ·
`fault_diagnosis_enabled` off에서 `fault_diagnosis`가 허용 집합에 **없다** ·
허용 집합이 프롬프트 클래스 정의와 **동기화됨을 단언**(사본 금지).

#### E-2. `relevance_score` 변환 실패의 **항목 단위 격리** (§3.6 발견 ⑧ · **F2**)

- `float()` 실패를 **해당 DB 항목에서만** 처리하고 **나머지 후보는 살린다**.
  현행처럼 분류 전체를 버리고 단일 DB로 폴백하지 않는다.
- 탈락 항목은 **사유를 남긴다**(침묵 폴백 금지). 무효 `db_id` 탈락(부수 발견)도 동일.
- **폴백 값을 임의로 부여하지 않는다** — 형식 오류는 "관련도 0.5"가 아니라 **판정 불가**다.
  임의 기본값은 게이트를 통과시켜 버린다.

**수용 기준**: 한 항목이 `"높음"`이어도 **나머지 DB가 후보로 생존**한다(멀티 DB 불변식 §1.1
회귀 테스트) · 탈락 사유가 구조화되어 남는다 · 전체 폴백 경로는 **LLM 호출 자체가 실패했을 때만**
탄다.

> 커스텀 핸들러 등록으로 제거 가능함을 실측**했기 때문이다(E-3.2). 리스크를 감수하고 진행하는 것이

##### E-3.2 ★ 핵심 설계 — 프롬프트 주입을 **한국어로 대체**한다 (v13 신규 실측)

v12가 보류 사유로 든 것은 `Mode.MD_JSON`이 한국어 프롬프트 뒤에 **영어 스키마 블록**을 붙이고
**추가 user 메시지**("Return the correct JSON response within a ```json codeblock…")를 덧붙인다는
점이었다. 트랙 A가 고정한 few-shot 구조와 경쟁할 수 있기 때문이다.

**그런데 이 문구는 레지스트리에 등록된 핸들러 클래스의 것이고, 교체가 가능하다.**

```python
@register_mode_handler(Provider.OPENAI, Mode.MD_JSON)
class KoreanMDJSONHandler(OpenAIMDJSONHandler):
    def prepare_request(self, response_model, kwargs):
        ...  # 한국어 지시문 + 스키마만 system 말미에 덧붙인다
```

**실측 결과**(probe): 영어 블록 **완전 소멸**(`"genius expert" in messages → False`) ·
**추가 user 메시지도 없음**(우리가 안 붙이므로) · **파싱·되먹임 재질의는 상속되어 그대로 동작** ·
한국어 system 프롬프트는 보존되고 그 **말미에만** 스키마가 붙는다.

**이로써 v12 보류 사유 1이 소멸한다.** 남는 것은 **스키마 블록 자체의 토큰 비용**뿐이며,
이는 정적이라 **KV 캐시 접두를 깨지 않는다**(P14 정합).

> **재질의문도 한국어화된다 — v14 실측 완료**(종전 미검증 항목 해소). `handle_reask`를 같은
> 클래스에서 오버라이드해 확인했다:
>
> ```
> [user] 직전 응답이 스키마 검증에 실패했습니다. 아래 오류를 고쳐 ```json 블록으로 다시 출력하세요.
>        ### 검증 오류
>        - `confidence`: Input should be a valid number (받은 값: '높음')
> ```
>
> 영어 잔존 **0**(`"Correct your JSON"`·`"genius expert"` 모두 False). 마침 **F2의 실패 형태
> (`relevance_score: "높음"`)를 그대로 잡았다** — §3.6 발견 ⑧이 가정한 시나리오가 실제로 검출된다.
>
> **단, 오류 본문은 pydantic이 생성한 영어 문장**(`Input should be a valid number`)이다. 이는
> instructor가 아니라 pydantic 소관이며, 필드 경로·받은 값이 함께 실려 모델이 교정하기에 충분하다고
> 판단해 **번역하지 않는다**(과도한 가공은 오류 정보를 잃는다). 착수 후 교정률이 낮으면 재검토.

##### E-3.3 구조 — 어댑터 한 겹 (프로토콜 재구현 없음)

```
AsyncInstructor(client=None, mode=…)
  └ create = instructor.patch(_lc_create, mode=…)      ← patch 필수(raw 콜러블이면 파싱 안 됨)
      └ _lc_create(messages=[dict], **kw)
          ├ dict → LangChain 메시지 (is_kbgenai면 System 다음 빈 AIMessage)
          ├ await llm.ainvoke(...)        ← 기존 KBGenAIChat / FabriXAPIClient / ChatOpenAI 그대로
          └ AIMessage.content → coerce_content_text → OpenAI 응답 shape로 감싸기
```

- 페이로드·인증·**PII 훅**(`log_filter_block_if_any`)·`remove_llm_junk`·SSE는 **기존 클라이언트가 계속 담당**한다.
- **부수 이득**: `is_kbgenai` 분기가 어댑터 한 곳으로 모인다(현재 8곳 산재 · Plan 69 P2 정합).
- **필수**: `coerce_content_text` 재사용 — 실 모델이 content를 **콘텐츠 블록 리스트**로 반환하는
  사례가 실측돼 있다(`utils/json_extract.py` 주석 · 2026-08-04 E1). 어댑터가 `str` 가정 시 여기서 깨진다.

**모드 자동 선택** — 평면에 따라 갈린다:

| LLM | 모드 | 근거 |
|---|---|---|
| `KBGenAIChat` · `FabriXAPIClient` | **`Mode.MD_JSON`**(한국어 핸들러) | 네이티브 tool-calling 부재(78 §4.7.5-②) |
| `ChatOpenAI`(vLLM) | **`Mode.TOOLS`** | 네이티브 지원 → 스키마 주입 자체가 불요 |

> **J-9 정합**: 평면 이동이 결정되면 **어댑터 분기만 바뀌고 소비처는 그대로**다. 이 구조가
> 평면 이동을 **선행조건에서 최적화 항목으로** 강등시킨다 — E-3은 더 이상 J-9를 기다리지 않는다.

> **⚠ E-3b 후에도 E-1·E-2를 제거하지 않는다.** 플래그 off(=Instructor 미사용) 경로가
> 상시 존재하고, 그 경로에는 여전히 F1·F2가 있다.

**E-3c 편입 근거(v14 · 사용자 결정)** — 어댑터가 생기면 한계비용이 작고, 이 표면에 실측 결함이 있다:

- 재시도는 있으나(`:218`·`:318` 각 2회) **고정 힌트 한 문장**이고 판정도 `query_targets` 존재 여부뿐이다.
  검증 오류 되먹임으로 바꾸면 **같은 호출 횟수로 품질이 오른다**(비용 증가 없음).
- 출력 12필드를 **`setdefault`로 사후 보정**한다 — 타입 계약이 없어 잘못된 타입이 그대로 통과한다.
- **⚠ 두 함수가 비대칭이다**: `_parse_natural_language`는 `synonym_registration` 기본값을 넣는데
  `_parse_natural_language_with_csv`는 **넣지 않는다**(`:328~336` 실측). CSV 경로에만 키가 없다.
  **공유 스키마 하나로 이 비대칭이 구조적으로 해소된다** — E-3c의 부수 이득이자,
  Known Mistakes *"단일/멀티 경로 대칭"* 의 직접 사례다.
- **주의**: 12필드 스키마는 라우터보다 **토큰이 크다**. `Optional` 필드 설명을 과하게 붙이지 말 것.

##### E-3.6 플래그 · 폴백 · 수용 기준

```
STRUCTURED_OUTPUT_BACKEND=none      # none | instructor   (기본 none = 현행 비트동일)
STRUCTURED_OUTPUT_MAX_RETRIES=1     # 총 2회 호출. 응답시간 목표(단순 <10s) 준수
```

- **기동 시 1회 해석**(P14) — 요청 시점에 바꾸면 프롬프트 접두가 흔들려 KV 캐시가 무효화된다.
- **폴백**: `InstructorRetryException` 발생 시 기존 폴백 경로를 타되 **사유를 구조화해 응답에
  노출**한다(`failed_attempts` 요약). **침묵 폴백 금지** — 이것이 F4 해소의 본체다.
- **재시도 예산**: 라우터는 지연에 민감하므로 `max_retries=1`로 시작하고, **실측 후** 조정한다.

**수용 기준**
1. `STRUCTURED_OUTPUT_BACKEND=none`에서 **프롬프트·동작이 현행과 비트동일**(회귀 0 단언).
2. `instructor` **미설치 상태에서 앱이 기동**되고, 플래그가 켜져 있어도 graceful 강등 + 로그.
3. 어댑터가 **콘텐츠 블록 리스트** content를 처리한다(`coerce_content_text` 경유 단언).
4. `is_kbgenai` 빈 `AIMessage` 규약이 어댑터에서 적용된다(KBGenAI 대역 단언).
5. **한국어 핸들러 단언** — 전송 메시지에 `"genius expert"`·`"Correct your JSON"`이 **둘 다 없다** ·
   스키마 블록이 한국어 지시문과 함께 system **말미**에 온다 · 재질의 메시지가 한국어이고
   **실패 필드 경로와 받은 값이 포함**된다(E-3.2에서 실측 확인 — 회귀 방지용 고정 단언).
6. 검증 실패 시 **`ValidationError` 내용이 재질의 메시지에 실린다**(대역 LLM으로 단언).
7. 소진 시 **사유가 응답에 노출**된다(침묵 폴백 금지).
8. `python scripts/arch_check.py --ci` **exit 0**.
9. E-3b 한정: **멀티 DB 예시가 `RouterDecision`으로 왕복**해도 보존된다(§1.1 불변식).
10. E-3c 한정: **두 함수가 같은 스키마를 쓴다**는 단언(`_parse_natural_language` ·
    `_parse_natural_language_with_csv`). 현행 `synonym_registration` 기본값 비대칭이 해소됨을 확인한다.

> **D-127 경계**: 위 1~9는 **전부 대역(fake `create`)으로 검증 가능**하며 실 LLM 호출이 필요 없다.
> **분류 정확도·지연·토큰 변화 측정만** D-127 건별 승인 대상이다.

### 6.4 회귀·안전 — **blast radius가 크다**

- **프롬프트 변경은 예시와 함께**한다 — 형식만 바꾸고 예시를 두면 모델은 옛 형식을 따른다
  (Known Mistakes: 예시가 지시문을 이긴다).
- **A-1은 단독 적용 금지** — 후보 수가 늘고 게이트가 처음 작동하므로 **C-4 임계 재검토와 묶는다**.
  > **⚠ v10 — 이 규율이 이미 깨졌다.** 2026-08-26 실측 결과 A-1은 적용됐고 C-4는 미착수다.
  > 프롬프트는 저신뢰를 출력하는데 `MIN_RELEVANCE_SCORE=0.3`이 그대로라 **게이트가 처음으로
  > 실동작**한다. 시정 전에는 이후 측정이 전부 미조정 기준선 위에 쌓인다 — **`plans/80` §3**.

- **롤백**: 플래그 off → 즉시 현행 복귀. 프롬프트는 파일이므로 git revert.
- **과금 게이트**(D-127): **실 LLM(FabriX 또는 대체 provider) 호출** 벤치마크는 **건별 사용자 승인 + `RUN_E2E=1`**.

## 7. 검증 설계 — 벤치마크 이식

논문의 실험 설계를 이 프로젝트 골든셋에 이식한다. **핵심은 2요인 분해 구조**다.

| 조건 | 지시문 | 출력 형식 | 신뢰도 |
|---|---|---|---|
| C0 (현행 기준선) | 현행 | JSON | 자기보고 |
| C1 | **개선** | JSON | 자기보고 |
| C2 | 현행 | **라벨 선행 하이브리드** | logprob |
| C3 | **개선** | **라벨 선행 하이브리드** | logprob |

- **C1 − C0 = 지시문 효과**, **C2 − C0 = 형식+신뢰도 효과**(혼입 — 트랙 C로 추가 분해)
- 통제: temperature 0 · seed 고정 · 동일 골든셋 · 동일 모델
- **각 조건은 정확히 한 요인만 바꾼다** — 논문이 지키지 못한 분리를 여기서는 지킨다
- 산출: 클래스별 정확도·recall · confidence-accuracy gap · **예측 분포**(collapse 감지) · 지연

> **과금 게이트**: **실 LLM 호출**은 **D-127에 따라 건별 사용자 승인 + `RUN_E2E=1` 옵트인**이다.
> 벤치마크 실행 전 승인을 받는다.
