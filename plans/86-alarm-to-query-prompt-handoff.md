## 0. 요약 — 이 계획이 실제로 푸는 문제

요청은 "클릭하면 프롬프트가 생성되어 자동 조회된다" 한 줄이지만, 실측하면 **난이도가 서로 다른 세
조각**으로 갈라진다.

| 조각 | 난이도 | 근거 |
|---|---|---|
| **① 카드 → 질의응답 인계(배선)** | 낮음 | 필요한 것이 전부 이미 있다 — `setActiveView("chat")`(`app.js:2758`) · `promptEl` · `handleSend()`(`app.js:655`). 알람 카드의 closure 바인딩 패턴도 ack·피드백이 선례다(`bindAlarmFeedback`, `app.js:3211`) |
| **② 프롬프트 생성(무엇을 물을 것인가)** | **중간** | 재료는 SSE payload에 이미 전부 실려 있다(§4.1). 문제는 *생성 방식* — 결정적 템플릿이냐 LLM 추천이냐 |
| **③ 생성한 질의를 파이프라인이 실제로 답하는가** | **높음 — 이 계획의 진짜 리스크** | 사용자 예시의 *"1달 평균 메모리 사용률"* 은 답한다(골드셋에 있다). **"증가율"은 현재 결정적 경로가 없다** — 급증 조립기가 **파일시스템 전용·월 단위·절대 임계 명시 필수**다(§4.3) |

**따라서 이 계획의 중심은 UI가 아니라 ③이다.** 클릭 한 번에 파이프라인이 못 푸는 질의를 자동
전송하면, 사용자는 "기능이 됐다"가 아니라 **"에이전트가 내 알람에 답을 못 한다"**를 경험한다.
그래서 §3의 설계는 **추천 프롬프트를 "파이프라인이 답할 수 있다고 확인된 형태"로 제한**하는 데
대부분을 쓴다.

## 1. 요청 해석 — 갈라지는 지점 2곳

### 1.1 "클릭"의 대상이 무엇인가

사용자 문장에는 두 개가 함께 들어 있다.

- (a) *"'fgisidd0'를 **클릭**하면"* → **카드 헤더의 서버명**을 누르는 것
- (b) *"'권고 조치'나 '패턴 분석'에서 … 프롬프트를 **추천**하여"* → 분석 결과를 근거로 한 **추천 목록**

(a)만 만들면 "서버명 클릭 = 고정 템플릿 1개"가 되어 (b)의 *추천*이 사라지고, (b)만 만들면 예시로 든
서버명 클릭이 안 된다. **둘은 배타적이지 않다** — (a)는 진입, (b)는 선택지다. 본 계획은 둘 다
넣되 역할을 나눈다(§3.2, G-1로 확정 요청).

### 1.2 "자동으로 조회" — 어디까지가 자동인가

**D-183이 정면으로 반대 방향을 확정해 두었다**:

> *"목록 클릭은 입력창에 **채우기만** 한다 — 전송하지 않는다. 옛 질의가 지금도 유효하다는 보장이
> 없고(존 개명·서버 폐기), **오전송은 되돌릴 수 없다**."* (`docs/02_decision.md` D-183)

본 요청은 명시적으로 *"조회를 자동으로"* 를 요구하므로 **기존 결정과 충돌한다**. 다만 두 상황의
성질은 다르다 — 아래 표가 §5.1의 근거다.

| | D-183(질의 이력 재사용) | 본 요청(알람 인계) |
|---|---|---|
| 질의의 나이 | 며칠~몇 주 전 | **방금 도착한 알람** |
| 대상 유효성 | 존 개명·서버 폐기로 무효화 가능 | 알람이 방금 왔다 = **그 서버는 지금 살아 있다** |
| 사용자 의도 | "이런 걸 물었었지" 회고 | **"이 알람을 지금 파악하겠다"** |
| 문구의 출처 | 사용자가 과거에 쓴 문장 | **시스템이 방금 생성한 문장** |

마지막 행이 중요하다 — **시스템이 만든 문장을 사용자가 읽지도 않고 전송**하는 것이 자동 조회다.
그래서 §3.3은 "자동 전송하되 **보내기 전에 무엇을 보내는지 보이고 되돌릴 수 있게** 한다"로 설계한다.

## 2. 현재 상태 실측

### 2.1 알람 카드가 실제로 들고 있는 필드

SSE 티어 payload 정본 — `noise_gate/application/nodes/alarm_notifier.py:586~617` (`_tier_sse_payload`),
incident open payload는 `:707~750`에서 같은 필드 집합에 식별자만 더한다.

| 분류 | 필드 | 프롬프트 생성에서의 쓰임 |
|---|---|---|
| 대상 식별 | `hostname` · `server_name` · `server_identity{name,ip_address,os_type,zone_label,…}` · `db_id` · `ip_address` | **질의의 주어**. 등록명 우선(`server_identity.name` → `server_name` → `hostname`)은 카드 헤더와 같은 규칙(`app.js:3021`) |
| 알람 정체 | `alarm_name`(자유 한국어) · **`resource_type`** · `resource_name` · `severity_label` · `alarm_time` · `alarm_status` | **자원 축 판정의 키는 `resource_type`**(§2.2) |
| 분석 결과 | `summary` · `probable_cause` · **`recommended_action`** · **`pattern_type`** · `is_routine` · **`pattern_analysis`** · `pre_classification` | 사용자가 지목한 추천 근거 2종이 여기 있다 |

**⚠ 경로별 비대칭 1건**: `history_stats`(패턴 근거 표)와 `process_snapshot`은 **SSE 티어 payload에
없다**. 프론트는 `data.history_stats`를 렌더하고 있고(`app.js:3117`), 이 값은 API 경로
(`src/api/routes/alarm.py:304`·`:624`)에서만 채워진다. **추천 로직이 `history_stats`에 의존하면
경로에 따라 조용히 빈 추천이 나온다** — §3.1은 이 필드에 의존하지 않는다.

### 2.2 자원 축 판정 키 — `resource_type`이 유일하게 구조화돼 있다

실측 분포(`noise_gate/tests/` 전수 grep):

`alarm_name`은 자유 문자열이다 — `"CPU 임계 초과"` · `"CPU 사용률"` · `"디스크 사용률"` ·
`"메모리 사용률"` · `"로그 패턴 감지"` · `"내부Cloud ○○○님의 Cloud PC 사양변경 승인바랍니다"`.

`Memory사용률`은 `alarm_name`, 축 판정은 `resource_type == "server.Memory"`가 한다.

## 3. 설계

### 3.1 M1 — 프롬프트 생성기 (결정적 템플릿 우선)

**결정적 조립을 기본으로 한다.** 근거는 취향이 아니라 CLAUDE.md의 명문 원칙이다 —
*"LLM 분류·매핑 출력에 정합성을 의존하지 말 것. 스키마·조인이 고정된 쿼리는 코드가 직접 조립"*.
여기서는 SQL이 아니라 **질의문**을 조립하지만 실패 양식이 같다: LLM이 만든 추천 프롬프트는
파이프라인이 못 푸는 형태로 흘러가도 **아무도 그것을 검증하지 않는다**.

**축 매핑표**(`resource_type` → 추천 질의군). 각 항목은 §4.3의 "답할 수 있는가" 판정을 통과한
것만 넣는다.

| 축 (`resource_type`) | 추천 프롬프트 (초안) | 파이프라인 근거 |
|---|---|---|
| `server.Cpus` | `{서버} 서버의 지난 1개월 평균·최대 CPU 사용률을 보여줘` | 골드셋 `gp.yaml:214`·`:345` |
| `server.Memory` | `{서버} 서버의 지난 1개월 평균·최대 메모리 사용률을 보여줘` | 골드셋 `gp.yaml:214` |
| `server.Disks` / `server.FileSystems` | `{서버} 서버의 파일시스템별 사용률을 보여줘` / **급증형**: `{서버} 서버에서 지난달 대비 사용률이 10%p 이상 상승하고 80% 이상인 파일시스템을 보여줘` | 급증은 `spike_sql.py`가 결정적 조립 — **절대 임계·차분을 문구에 넣어야 진입한다**(§4.3) |
| `server.Network` | `{서버} 서버의 지난 1개월 네트워크 트래픽 통계를 보여줘` | `cmm_metric_stat_m` 계열 — **검증 필요(§6 T2)** |
| `server.LogMonitor` | `{서버} 서버의 최근 3개월 알람 발생 이력을 보여줘` | 골드셋 `gp.yaml:400` 인접 형태 |
| `server.Server`(가용성) | `{서버} 서버의 가용성 상태와 IP를 조회해줘` | 골드셋 `gp.yaml:177` **동일 형태** |
| 미매핑 / `management.*` · `platform.*` | **추천을 만들지 않는다**(칩 미표시) | 근거 없는 추천보다 없는 편이 낫다 |

공통 추가 축(자원과 무관하게 항상 1개):
- `{서버} 서버의 사양과 OS 정보를 조회해줘` — 골드셋 `gp.yaml:131` 동일 형태. **대상을 모를 때의
  안전한 첫 질의**다.

**`{서버}` 치환 규칙**: 카드 헤더와 동일하게 `server_identity.name` → `server_name` → `hostname`.
헤더가 보여준 이름과 프롬프트의 이름이 다르면 사용자는 다른 서버를 조회한 것으로 읽는다.

**⚠ 사용자 예시 문구를 그대로 쓰지 않는 이유**: *"1달 평균 메모리 사용률과 **증가율**"* 에서
증가율은 §4.3이 보이듯 **메모리에 대해서는 결정적 경로가 없다**. 예시를 문자 그대로 구현하면
첫 클릭부터 LLM 폴백으로 새는 질의가 나간다. G-3에서 확정을 요청한다.

**모듈 위치**: `src/static/js/app.js` 내 신규 함수군(`buildAlarmPrompts(data)`)으로 시작한다.
매핑표에 `server.Memory` 같은 **폴스타 리터럴**이 들어가는데, 이는 `overfit_check`의 공용 계층
스캔(`PUBLIC_LAYER_DIRS` = `src/utils`·`src/nodes`·`src/prompts`·…)에 걸리는 종류다. 다만 게이트는
`rglob("*.py")`만 훑으므로 **JS는 대상이 아니다**. 향후 서버측으로 옮긴다면 `src/db_adapters/polestar/`
(스캔 제외 목록) 또는 `config/` YAML에 두어야 한다(D-089 · §5.3).

### 3.2 M2 — 카드 UI (진입 2종)

**(a) 헤더 요소 클릭 — 사용자 예시 경로.** 카드 헤더의 서버명(`.alarm-server`)을 클릭 가능한
요소로 만든다. 클릭하면 **그 서버 축의 추천 목록을 펼친다**(즉시 전송하지 않는다 — §3.3).

- 접근성: `<span>`이 아니라 `<button class="alarm-prompt-trigger">`로 감싼다(키보드 도달·`aria-label`).
- 시각: 밑줄 점선 + hover 강조. **링크처럼 보이되 링크가 아님**을 유지(페이지 이동이 아니다).

**(b) 추천 프롬프트 칩 — 사용자가 지목한 "권고 조치·패턴 분석 기반" 경로.** 카드 하단
(`.alarm-feedback-section` **위**)에 `.alarm-prompt-section`을 둔다.

```
이 알람을 조회해 볼까요?
[ 1개월 메모리 사용률 ]  [ 서버 사양·OS ]  [ 최근 알람 이력 ]     ← 최대 3개
```

- **최대 3개**. 그 이상은 고르는 비용이 조회 비용을 넘는다.
- 칩 라벨은 **짧은 요지**, `title`(툴팁)에 **전송될 프롬프트 전문**을 넣는다 — 무엇이 나갈지
  보이지 않는 자동 전송은 만들지 않는다.
- `pattern_type`이 `"급증"`이면 급증형 추천을 **1순위**로 올린다(패턴 분석 반영).
- `is_routine === true`(일상적 반복)면 칩을 **접어 둔다** — 노이즈 캔슬링이 "일상"이라 판정한 알람에
  조회를 권하는 것은 게이트의 판단을 UI가 뒤집는 것이다.

### 3.3 M3 — 인계 정책 (D-183과의 조정)

**3단 중 하나를 G-2로 확정 요청한다.**

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **A. 채우기만** (D-183 그대로) | 탭 전환 + 입력창 채움 + 포커스. 사용자가 Enter | 기존 결정과 무모순 · 오전송 0 | 사용자 요구(*"자동으로 조회"*)를 **충족하지 못함** |
| **B. 자동 전송 + 되돌리기** *(권고)* | 탭 전환 + 채움 + **즉시 `handleSend()`**. 전송 직후 스트림 상단에 `이 질의는 알람 카드에서 자동 생성되었습니다 [중단]` 배너 | 요구 충족 · `stopStreaming()`이 이미 있다(`app.js:657`) | 과금 경로가 클릭 1회로 열린다 |
| **C. 확인 후 전송** | 채운 뒤 입력창 위에 `[이대로 조회] [수정]` | 오전송 0 + 요구 근사 | 클릭이 2회 — "자동"이 아니다 |

**권고는 B**다. 근거: ①`handleSend`는 이미 진행 중 재클릭 시 `stopStreaming()`으로 중단된다 —
**되돌릴 수 없다는 D-183의 전제가 이 경로에서는 성립하지 않는다** ②알람은 방금 도착했으므로
대상 유효성 문제(§1.2)가 없다 ③프롬프트는 §3.1의 **폐쇄된 템플릿 집합**에서만 나오므로 "무엇이
나갈지 모른다"가 아니다.

**B를 택할 경우 D-183을 개정하지 않는다** — 그 결정은 *질의 이력 재사용*에 대한 것이고, 본
경로는 별개 진입점이다. D-192에 **"자동 전송은 시스템 생성 프롬프트에 한한다"**는 경계를 명시한다.

### 3.4 M4 — LLM 추천 보강 (옵트인 · 후순위)

결정적 매핑이 커버하지 못하는 축(`management.*`·`platform.*`·미매핑 `alarm_name`)에 한해,
`recommended_action`·`pattern_analysis`를 근거로 LLM이 **질의 1개**를 제안한다.

- **기본 off**(`ALARM_PROMPT_LLM_SUGGEST_ENABLED=false`) — 신규 플래그 기본 off = 현행 비트 동일
  (`plans/80` §5.4-③).
- 켜져도 **자동 전송 금지**(안 A로 강등) — LLM 생성 문구는 폐쇄 집합이 아니다.
- 서버 라우트 신설이 필요하므로 **본 계획의 Phase 2**로 분리한다. Phase 1은 프론트 전용.

## 4. 답변 가능성 실측 — 이 계획의 핵심 근거

### 4.1 재료는 충분한가 → **충분하다**

§2.1의 payload에 대상·자원·분석이 모두 있다. `history_stats` 비대칭(§2.1 ⚠)만 피하면 된다.

### 4.2 "1달 평균 사용률" → **답한다**

골드셋에 동일 형태가 있다.
- `testdata/text2sql_gold/gp.yaml:214` — *"전체 서버들의 CPU, 메모리 용량 및 사용률(평균·최대)
  리스트를 조회해줘. 사용률은 지난달 1개월 통계 기준으로."*
- `:255` — *"지난 3개월간 전체 서버별 월간 CPU, 메모리, 파일시스템, 디스크 IO 성능 통계"*
- `:345` — *"김포 폴스타 전체 서버를 통틀은 지난달 평균 CPU 사용률"*

서버 1대로 좁히는 형태(`:131`·`:196`)도 골드셋에 있다. **조합이 새로울 뿐 두 축 모두 검증돼 있다.**

### 4.3 "증가율" → **조건부다. 사용자 예시대로는 안 된다**

급증 조립기 실측(`src/db_adapters/polestar/spike_sql.py`):

| 제약 | 값 | 출처 |
|---|---|---|
| 대상 자원 | **파일시스템 전용** | `_FILESYSTEM_TYPE = "server.FileSystems"` (`:35`) |
| 기간 단위 | **월만** | `_METRIC_TABLE = "cmm_metric_stat_m"` (`:34`) — *"주 단위는 보존기간 미확인"* |
| 진입 조건 | 급증 어휘 **AND 절대 임계 명시** | `query_generator.py:590` — 절대 임계 없으면 *"급증 조립 미진입"* 로그 후 **LLM 경로로 폴백** |
| 게이트 | `spike_condition_enabled` | `query_generator.py:566` |

즉 *"메모리 **증가율**"* 은 ①자원 축이 파일시스템이 아니고 ②임계 문구도 없어 **결정적 경로에
진입하지 못하고 LLM 폴백**된다. 폴백이 곧 실패는 아니지만, **추천 기능의 첫 인상을 비결정 경로에
맡기는 설계**가 된다.

**대응 3안**(G-3):
1. **(권고)** 메모리·CPU 추천에서 "증가율"을 빼고 `평균·최대 사용률`로 한다 — 검증된 형태만 추천
2. 파일시스템 축에서만 급증형 추천을 낸다(문구에 임계·차분을 넣어 결정적 진입 보장) — **1과 병행 가능**
3. `spike_sql`을 메모리·CPU로 확장한다 — **별건 작업**(`_FILESYSTEM_TYPE` 일반화 + 골드셋 추가).
   본 계획의 범위 밖이며, 하려면 별도 계획서가 필요하다

### 4.4 전제 검증이 필요한 것 (§6 T2에서 처리)

- 네트워크 축 질의(`server.Network`)가 실제로 답하는지 — 골드셋에 없다
- 로그 축(`server.LogMonitor`) 알람의 자연스러운 후속 질의가 무엇인지 — 알람 이력 조회로 대체 가능한지

## 5. 결정과 긴장

### 5.1 D-183과의 관계 — 개정이 아니라 **경계 추가**

§1.2·§3.3의 근거로, D-183의 "채우기만"은 **질의 이력 재사용 경로에 유지**하고, 본 경로는
"시스템 생성 프롬프트에 한해 자동 전송"으로 **경계를 나눈다**. 두 규칙이 한 파일에 공존하므로
`reuseHistoryQuery`(채우기만)와 `runAlarmPrompt`(전송)를 **이름으로 구분**하고, 각 함수 주석에
서로를 참조해 둔다 — 나중에 한쪽을 보고 다른 쪽을 "일관성 있게" 고치는 회귀를 막는다.

### 5.2 과금 경로가 열린다

클릭 1회 = LLM 파이프라인 1회 실행이다. 운영 실측(`.env`)은 `LLM_PROVIDER=gemini`이므로
**실제 과금**이다(D-127). 방어:
- 칩 3개 상한(§3.2) · `is_routine` 알람은 접어 둠
- 전송 직후 중단 배너(§3.3 B) — `stopStreaming()` 재사용
- **연타 방지**: 전송 후 그 카드의 칩을 일시 비활성(진행 중 재클릭은 중단으로 흡수)

### 5.3 리터럴 위치

`server.Memory` 등 폴스타 자원 타입이 매핑표에 들어간다. Phase 1(프론트 JS)은 `overfit_check`
스캔 대상이 아니다(`rglob("*.py")`). **Phase 2에서 서버로 옮길 때는** `src/db_adapters/polestar/`
(EXCLUDE) 또는 `config/` YAML이어야 한다 — `src/utils`·`src/nodes`에 두면 게이트가 막는다.

### 5.4 알려진 한계 (구현 후에도 남는 것)

- 추천은 **폐쇄 집합**이다 — 매핑 밖 알람은 추천이 없다(의도된 동작, §3.1)
- 존/DB 스코프: 프롬프트에 `db_id`를 넣지 않는다. 서버명만으로 라우팅이 되는지는 **T2에서 확인**하고,
  안 되면 존 표면어(`config/db_registry.yaml`의 위치 표면어)를 문구에 넣는다
- 알람 뷰는 세션 한정이므로(D-182 ①) 새로고침 후에는 추천도 사라진다 — 기능 성질상 정상
