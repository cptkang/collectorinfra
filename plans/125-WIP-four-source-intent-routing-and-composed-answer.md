## 0. 요약

### 0.1 결론

| 질문 | 답 | 근거 |
|---|---|---|
| 지금 4소스를 조합한 응답이 되나 | **안 된다.** 2단에서 1급으로 조회되는 것은 **폴스타 3존 DB와 폴스타 REST뿐**이다. ITAM은 SQL로 닿지만 활성은 로컬뿐이다. **Prometheus와 제니퍼는 본체에 처리기가 0건이다.** 제니퍼 게이트웨이(`apm_*` 도구 8종)는 있지만 소비자는 `sre_agent`·`noise_gate`뿐이다 | §2.1 |

### 0.2 권고 한 줄

**4소스를 계층(애플리케이션 · 호스트 · 자산)으로 나눠 속성마다 권위 소스를 정본에 적는다. 제니퍼를 2단 1급 처리기로 편입한다(LLM은 보기만 고름). 계층 사이 식별자는 각 간선의 소유자(게이트웨이·폴스타·키 브리지)가 결정적으로 옮긴다. 응답은 구동 집합 기준 엔터티 표에 소스별 출처·상태·불일치를 코드가 붙여 그린다.**
순서: M(측정) → B(결함) → A(제니퍼) ∥ E(연결) → C(조합 응답) → V(검증). 각 단계는 D-251 ⑦의 기준선 → 수정 → 재측정을 따른다.

## 1. 배경과 범위

### 1.1 사용자 서술 → 계층 모델

| 계층 | 질문 예 | 소스 | 접근 경로(현행) |
|---|---|---|---|
| **L3 애플리케이션·미들웨어** | "김포 WAS 응답시간" · "힙 사용률 높은 인스턴스" · "지금 걸려 있는 서비스" · "WAS 에러 이벤트" | **제니퍼** | `apm_gateway` MCP(127.0.0.1:9096 · `apm_*` 8종) |
| **L2 호스트·OS** | CPU·메모리·디스크 사용률(통계·실시간) · OS 구성 · 프로세스 · 알람 | **폴스타**(3존 DB + REST) · **Prometheus**(PromQL·OpenMetrics) | `mcp_server`(`execute_sql` · 고수준 도구 · `prom_*`·`om_*`) · 폴스타 REST 직접 |
| **L1 자산·조직** | 장비·자산 분류 · 계약·지원 종료 · 담당자·담당 부점 · 설치 소프트웨어 | **ITAM** | `mcp_server`(MariaDB `itam`) |

**계층 사이 연결**: L3 인스턴스 → (`hostName` — 게이트웨이 정합) → L2 호스트(`hostname` ↔ `server_name` — 폴스타) → (`sevrHostName`·`iPCtnt` — 키 브리지) → L1 자산. L2 안에서 Prometheus는 `nodename = server_name`으로 붙는다(D-119 ③).

### 1.2 용어

121 §1.1 용어를 그대로 쓴다(답변 영역 · 소스 카탈로그 · 엔터티 집합 · 키 패싯 · 키 브리지 · 바인드 조인 · 출처). 이 계획이 더하는 용어:

| 용어 | 뜻 |
|---|---|
| **계층**(layer) | L3 애플리케이션 · L2 호스트 · L1 자산. 답변 영역의 상위 묶음이다. 소스가 아니다 |
| **권위 소스**(authoritative source) | 속성 하나에 대해 정본으로 쓰는 소스. 121의 `role: canonical`과 같다 |
| **보기**(view) | 비SQL 처리기 안에서 호출할 고정 도구·템플릿 id. 예: `apm.app_health` · `prom.cpu_usage`. **LLM이 고르는 유일한 비SQL 인자**다 |
| **간선**(edge) | 한 계층·시스템의 식별자를 다른 계층·시스템 식별자로 옮기는 결정적 대응. 간선마다 **소유자**가 있다(§4.5) |
| **패싯 변환 단계** | 후속 단계가 요구하는 키 패싯을 선행 단계가 주지 못할 때 코드가 삽입하는 조회 단계. LLM 0회 |
| **연결 장부** | 구동 집합의 키마다 `연결(high/medium)` · `미연결` · `모호` · `조회 안 함(사유)`을 기록한 표 |
| **구동 집합**(driving set) | 조합 응답의 행이 되는 엔터티 집합. 보통 첫 선별 단계의 결과다 |
| **소스 상태 행** | 응답 머리의 소스별 한 줄: `조회 n건` · `0건` · `조회 안 함(사유)` · `사용 불가(사유)` |
| **불일치 각주** | 같은 엔터티·같은 속성에 대해 **이미 조회된** 두 소스 값이 정규화 뒤에도 다를 때 코드가 붙이는 각주 |

### 2.2 소스가 정해지는 지점

1. **분해 LLM은 처리기와 `sub_query`만 고른다.** 프롬프트가 *"대상 DB는 선택하지 마세요"*라고 지시한다(`src/prompts/intent_planner.py:58` ✔).
2. **처리기가 곧 소스 종류다.** SQL은 `data_query`/`alarm_query`, REST는 `process_query`, MCP 고수준 도구는 `host_inspect`다. 레지스트리 `solutions[].backend`로 실행자를 고르는 코드는 없다(`src/routing/execution_groups.py:77` · 소비는 관측 지표뿐).
3. **DB는 task 안에서 고른다.** `classify_dbs`(LLM)가 **활성 SQL DB 중에서** 고르고, 그 뒤 결정적 보정(힌트 고정 → 승계 → 소유 제한 → 존 역질문 → 인가)이 붙는다(`subagents.py:1386-1529`).
4. **답변 영역 슬롯은 있지만 꺼져 있다.** `OwnershipTaskSpec.capability`는 소유 플래그(`ROUTER_CAPABILITY_OWNERSHIP_ENABLED` 기본 off)일 때만 분해 출력에 실린다(`src/orchestration/schemas.py:87-96` ✔).
5. **소유 판정은 DB 항목만 순회한다.** `system_of`·`capability_owners`가 `databases`만 돈다. 그래서 DB가 없는 시스템(Prometheus·제니퍼)은 `solutions`에 선언해도 소유자가 될 수 없다(`src/routing/registry.py:249-276` ✔).
6. **처리기 계약 필드는 선언돼 있지만 소비처가 테스트뿐이다.** `backend`·`required_inputs`·`key_facets_out`·`max_bind_values`·`bind_block`·`concurrency`·`timeout_sec`(`subagents.py:137-180` ✔ · 121 TP-2.1a).

## 3. 문헌·산업 근거

### 3.1 재사용하는 기존 조사(재조사하지 않음)

- **`plans/121` §3.12~3.16 · 원칙 P-11~P-20**:
  - 소스 카탈로그는 정본에서 파생하고 형제 소스와의 차이를 중심으로 쓴다(Metadata Reasoner · DBCopilot).
  - LLM은 영역만, 소스 결정은 소유표로 코드가 한다(Information Manifold · PRACTIQ).
  - 단계 하나 = 소스 하나, 키만 전달한다(Symphony · CAESURA).
  - 결정적 정규화 + 승인 매핑표를 쓴다(Peeters et al. EDBT 2025 · ComEM).
  - 바인드 조인은 배치 + 장부로 한다(FedX · Garlic).
  - 비SQL 질의는 화이트리스트 템플릿으로 한다(PromCopilot — 기본 프롬프트 PromQL 정답 2.6~5.2%).
  - 부분 답변 + 남은 작업(Bonnet & Tomasic).
  - 시간창은 한 번 해석한다.
  - 정본 단일 사용 · 자동 융합 금지(Truth Finding — 데이터 항목 70%에 값이 둘 이상).
- **`plans/87` §4**: LLM 장애 진단 에이전트 · 트레이스 기반 RCA · WAS 도메인 지식.

이 계획은 위 원칙을 전부 유지한다. 아래는 **121이 다루지 않은 네 주제**, 곧 ① 이종 지식 소스 라우팅 ② 조합 응답의 출처·상충 ③ 도메인·엔터티 모델 ④ 운영 에이전트와 상용 어시스턴트의 다중 소스 처리를 새로 조사한 결과다.

→ **업계 공통점**:
- ① 엔터티와 관계는 **적재·수집 시점**에 만든다. 이름 불일치는 **사람이 쓴 별칭**으로 메운다.
- ② 소스 사용 조건을 **선언**하고, 도구 목록을 **줄여서** 준다.
- ③ 질의는 **템플릿·카탈로그 → 생성·검증** 순이다.
- ④ 출처는 **질의·시간 범위·소스** 단위로 단다.
- **벤더 정량 수치는 전부 방법론 비공개**라 설계 근거로 쓰지 않는다.

### 3.7 조사에서 확인한 공백

- **APM ↔ 호스트 ↔ CMDB/ITAM을 엔터티로 이어 응답을 조합하는 LLM 연구가 없다.** CMDB 그래프 추론은 DM-5 한 편뿐이고, 제조 CMDB에 관측 데이터 결합도 없다.
- **모니터링 도구 간 호스트명·인스턴스명 불일치 해소 연구가 없다.** 근거는 벤더 문서뿐이다. 표준(OTel)도 관계 선언을 지원하지 않는다고 적고 있다.
- **소스 선택 정확도·출처 정확도를 1급 지표로 둔 운영 벤치가 없다.** 대리 지표로 OP-3(데이터소스 일치)과 Cloud-OpsBench(preprint — 결과 정확도 0.76인데 필수 증거 확보는 0.38)가 있다.
- **정형 표·수치 결과를 합친 응답의 행 단위 출처·수치 상충 처리 연구가 희소하다**(지식 충돌 연구는 텍스트 기반이다).
- **시맨틱 레이어(dbt·Cube·LookML) 효과의 동료심사 근거가 없다.** preprint와 벤더 블로그뿐이다(dbt: "SL의 실패는 오류 메시지로, text-to-SQL의 실패는 그럴듯한 오답으로 나타난다" — 벤더 자기 평가).
- **VM·베어메탈 OS · DB2 · 국산 APM 평가 환경과 한국어 운영 질의 데이터가 없다.** 벤더도 한국어 공백이 있다.
- **"도메인별 전문 에이전트 vs 단일 계획기" 통제 비교 실험이 드물다**(OP-5 간접 근거뿐).

→ 121 §3.15와 같은 결론이다. **LLM 자유도를 줄이고 결정적 표·규칙·장부에 기대며, 효과는 자체 4소스 골드(M-1)로만 판정한다.**

  - 제니퍼 "이벤트"와 폴스타 "알람"은 **다른 영역**이다. 둘 다 원할 때("그 서버 알람과 WAS 이벤트")는 두 단계가 된다.

- **담당자(`asset_owner`)**: 95 G-9로 **마스킹 없이 노출**하기로 확정돼 있다(`config/db_registry.yaml:319` ✔). 전자금융감독규정 제14조의 책임자명부와도 관련된 정보다(산업 자료 · 원문 미대조). 연락처 칼럼이 추가되면 FabriX PII 규칙(유선 전화는 계좌 룰로 차단)에 걸리니 표시 전에 확인한다(`docs/pii_filtering_rules.md:116`).

### 4.2 제니퍼 보기(view) 표 — 영역 → 도구 · 필수 입력 · 창 상한

| 보기 id | 영역 | 게이트웨이 도구 | 필수 입력 | 창 · 상한 | 첫 홉 가능 |
|---|---|---|---|---|---|
| `apm.instances` | `was_instance` | `apm_instance_map` | 없음(전체) 또는 hostname | 전체 ≤ 200 | **예** |
| `apm.app_health` | `was_performance` | `apm_app_health` | hostname | 구간 ≤ 10분 · `reference_time` | 아니오(대상 필요) → 대상이 없으면 `apm.instances` 선행을 코드가 삽입 |
| `apm.runtime` | `was_runtime` | `apm_runtime_health` | hostname | 5분 간격 추세 | 같음 |
| `apm.pool` | `was_runtime` | `apm_resource_pool` | hostname | 현재값 | 같음 |
| `apm.active` | `was_activity` | `apm_active_services` | hostname | 현재값 · N ≤ 20 | 같음 |

- 보기 어휘는 **벤더 중립**이다(`apm.*`). 본체에 제니퍼 경로·필드명을 두지 않는다(D-274 ③ · 87 수용 기준 "`src/`에 제니퍼 토큰·URL 0건").
- **창 밖 요청**("지난주 WAS 응답시간 추이")은 조회하지 않는다. 대신 "제니퍼 조회 창(10분·24시간) 밖 — 보존 기간 확인 필요"라는 사유를 소스 상태 행에 적는다(Q-9). **폴스타 값으로 조용히 대체하지 않는다.**
- **"전체 WAS 중 상위 N"**:
  - 지금은 `apm.instances`(≤ 200) → 호스트별 `apm.app_health` fan-out(상한 `max_bind_values`)만 가능하다. 인스턴스가 상한을 넘으면 상위 N은 **조회한 범위 안의 순위**라고 고지한다.
  - 게이트웨이 쪽에 도메인 단위 순위 도구를 요청한다(G-12 · 87 소유). 제니퍼 `realtime/instance`는 한 번 호출로 전 인스턴스 현재값을 준다(`apm_gateway/testdata/jennifer/recorded/local-docker/GET_api_realtime_instance__ok.json` 존재 — 응답 모양은 J0-L-b 뒤 확인).

### 4.3 의도 → 계층·영역 → 소스·처리기

121 §4.12(소스 판단 절차)를 그대로 따르되, **TP-2.2(`required_areas` — G-31 대기)를 기다리지 않는 첫 단계**를 둔다(G-3).

```
[LLM · 기존 분해 호출 1회 안에서 — 추가 LLM 0]
   task = {agent, sub_query, depends_on, input_from, (views[]) }
   · agent 어휘에 apm_query(·metric_query)는 그 소스가 활성일 때만 렌더된다(G-29 선례 — 비활성이면 프롬프트 바이트 불변)
   · views[]는 agent가 비SQL 처리기일 때만 · 닫힌 열거형(§4.2) · 비면 영역 기본 보기(was_performance → apm.app_health)
[코드]
   ① 어휘·DAG 검증(현행) — 목록 밖 agent는 general_inference가 아니라 "처리기 없음" 노트(B-3)
   ② 알람 키워드 교정은 agent ∈ {data_query}에만(현행) + views에 apm.events가 있으면 건너뜀(B-1)
   ③ 필수 입력 판정: views의 필수 입력(hostname)이 선행 단계로 충족되지 않으면
        - 사용자 질의에 대상 식별자가 있으면 그것으로 · 없으면 apm.instances 선행 단계 삽입(E-3과 같은 기제)
   ④ 간선 판정(§4.5): 선행 결과 패싯 ≠ 후속 필수 패싯이면 패싯 변환 단계 삽입
   ⑤ 인가: allowed_sources(G-9) — 권한 밖이면 조회하지 않고, 안내에도 노출하지 않음(D-264)
```

- **왜 영역 대신 처리기부터인가**:
  - WAS 영역 5종은 **소유 소스가 제니퍼 하나뿐**이다. 그래서 "영역 → 유일 소유 → 처리기"와 "처리기 직접 선택"의 결과가 같다(추적).
  - 현행 2단은 이미 처리기를 LLM이 고르는 구조다(`process_query` 선례). 신규 슬롯이 `views` 하나라 활성이 아닌 배포의 분해 출력 스키마를 바꾸지 않는다.
  - **121 TP-2.2가 랜딩하면 `required_areas` → 소유표 → 처리기로 이행**하고 동등성을 잰다(D-161). 이 순서는 121 P-12(소스 결정은 코드가)와 목적이 같다. 겹치는 속성(§4.1 대체 열)은 TP-2.2 뒤에 소유표가 가른다.
- **명시 소스**("제니퍼에서", "프로메테우스로"):
  - 레지스트리 시스템 항목의 표시명·별칭을 **등록 표면어**로 인식한다. 위치 힌트(D-246)와 같은 방식이다.
  - 시스템이 활성이면 그 처리기로 고정하고, 비활성·미연결이면 `source_unavailable` 노트를 단다(B-2 · R-2).
  - **D-004 해석은 G-7에서 확인**받는다. 이 방식은 "등록된 고유명사의 결정적 인식"이지 의도 분류가 아니라는 입장이다.

### 4.5 교차 계층 엔터티 연결

**원칙**:
- 중앙 엔터티 저장소를 새로 만들지 않는다. **간선마다 이미 있는 소유자**가 결정적으로 대응을 준다(Q-3).
- 본체는 간선 표만 가지고 경로를 고른다.
- 본체에 인스턴스 정합 로직을 **재구현하지 않는다**(D-274 ⑤).

| 간선 | 소유자 · 수단 | 판정 등급 | 상태 |
|---|---|---|---|
| **E1** 제니퍼 인스턴스 → OS hostname | 게이트웨이 resolver(`apm_instance_map`) — overrides → `hostName` → 규칙 | high / medium / 미연결 | 있음(게이트웨이) |
| **E1′** OS hostname → 제니퍼 인스턴스(역방향) | 같은 도구의 hostname 인자 | 같음 | 있음 |
| **E2** OS hostname ↔ 폴스타 `server_name` | 폴스타 `entity_keys` 매니페스트 기반 고정 조회(LLM 0 · 스키마 리터럴은 `db_adapters`·매니페스트에만) | 1:1 / 0건 / 다건 | **신설(E-3)** |
| **E3** 폴스타 호스트 → ITAM 자산 | 102 키 브리지(`src/nodes/key_bridge.py`) + ITAM `entity_keys`(104 승인본) | 1:1 / 0건 / 다건(자동 조인 금지) | 부품 있음 · 기본 off · ITAM 매니페스트 없음 |
| **E4** 폴스타 `server_name` → Prometheus `nodename` | `mcp_server` 서버측 셀렉터 조립(D-119 ③) | 시리즈 있음 / 없음 | 부품 있음 · 운영 라벨 규약 미확정 |
| **E5** OS hostname → ITAM(직접) | E3과 같은 브리지(hostname 패싯) | 같음 | 제니퍼 → ITAM을 폴스타 경유 없이 |

- **패싯 변환 단계 자동 삽입**(E-3):
  - 후속 단계 처리기 계약의 `required_inputs` 패싯이 선행 결과의 `key_facets_out`에 없으면, 코드가 **간선 표에서 최단 경로**를 찾아 변환 조회를 삽입한다.
  - 예 1: 제니퍼 → Prometheus는 `hostname`만 있고 `server_name`이 없다 → E2 조회를 삽입한다.
  - 예 2: ITAM → 제니퍼는 `sevrHostName` → E3 역방향 → `hostname` → E1′ 순으로 간다.
  - 삽입은 **교차 시스템 간선에서만** 한다. 같은 시스템 간선(폴스타 → 폴스타)은 바이트 불변이다(121 G-26 · D-272 ⑦ · `tests/test_cross_system/test_key_bridge_same_system_regression.py`의 xfail 3건 재발 금지).
- **연결 장부**(E-4):
  - 구동 집합의 키마다 `연결(high|medium|1:1)` · `미연결(0건)` · `모호(다건)` · `조회 안 함(상한·타임아웃·권한)`을 기록한다.
  - 장부는 121 §4.6 ③ 체크리스트의 브리지 커버리지 항목과 **같은 구조**다(새 장치가 아니라 APM·E2 간선을 추가하는 것이다).
  - 응답에는 "WAS 12개 중 호스트 연결 10(high 8 · medium 2) · 미연결 2"처럼 드러낸다(Q-4 · Q-9).
- **식별 규칙 개선 제안(87 통지)**:
  - 제니퍼 `GET /api-v2/manage/instance?processId=&hostname=`(hostname + PID → 인스턴스)는 결정적 1차 정합 후보다(§3.6). 폴스타 프로세스 결과의 PID와 결합하면 **이름 규칙보다 강한 연결**이 된다.
  - 게이트웨이 domain의 몫이다. 버전 요건(서버 5.6.0.21+)을 J0-O에서 확인한다.
- **`TargetRef` 확장**(E-1): APM 패싯(`apm_domain_id` · `apm_instance_id` · `apm_instance_name`)과 자산 패싯(`asset_key`)을 추가하고, 소스별 로컬 ID를 모두 보존한다(DM-7 CMDBf). 기존 필드와 폴스타 → 폴스타 동작은 불변이다.

### 4.7 Prometheus · ITAM — 121 설계 그대로, 확인된 공백만

  - **확인된 공백**: 121이 92에 요청한 **메트릭 템플릿 도구가 92의 Wave O0~O6에 없다**(`plans/92-WIP-prometheus-openmetrics-integration.md:584-623`). 121·92 양쪽에 통지한다(G-12와 함께 처리).
- **ITAM**: 121 TP-10(키 패싯 · 브리지)·102·95를 그대로 따른다. 이 계획이 더하는 것은 두 가지다.
  - ① 엔터티 프로필(P-B)·보강(P-C)의 **담당자 열**
  - ② `asset_software` 보류(G-11): 제공 스키마 전사본에 설치 SW 표가 없다. SW 관련 칼럼은 지원 종료일뿐이다(`testdata/itam/schema.yaml`). 운영 ITAM의 표 존재는 104 관리자 흐름으로 확인한다. 사용자에게 묻지 않는다(D-227 ⑨).

### 4.8 시간 정렬

- 기간 해석은 **122 해석기 소유**다(D-275 ⑭). 계획 LLM은 기간을 계산하지 않는다.
- 이 계획이 소유하는 것:

  - ② 열 그룹마다 **기준 시각·창** 표기(폴스타 시 통계 · Prometheus step · 제니퍼 분 단위 · ITAM 원장 기준일)

### 4.9 조합 응답 계약

**골격**(121 §4.6 순서를 유지하고, 4소스 요소를 더한다):

```
① 해석 한 줄       — 대상 · 기간 · 사용 소스와 선택 사유(코드)                         [121 §4.6 ⑦ · 106 H2]
② 소스 상태 행     — 폴스타 12건 · 제니퍼 10건(창 14:00~14:10) · ITAM 9건 · Prometheus 사용 불가(미연결)   [C-2 · B-8 대체]
③ 엔터티 표        — 행 = 구동 집합 · 열 그룹 = 계층(L3 | L2 | L1) · 그룹 머리에 소스·기준 시각   [C-1]
④ 연결 장부 요약   — 호스트 연결 10/12(high 8 · medium 2) · 자산 연결 9/10 · 모호 1                [E-4]
⑤ 불일치 각주      — "svr-web-03 OS 버전: 폴스타 실측 RHEL 8.8 ≠ ITAM 원장 RHEL 7.9"             [C-3 · G-5]
⑥ 요약 2~3줄       — LLM · 입력은 표 사실 목록만(121 G-25) · 숫자 대조(121 TP-4.4)               [C-4]
⑦ 경과 노트        — 창 절단 · 조회 안 함 사유 · 상한 도달                                      [현행 dependency_notes]
```

- **구동 집합 기준 left join**:
  - 보강 단계에서 짝이 없는 행은 **지우지 않고** `미연결`·`미등록`으로 표시한다.
  - 현행의 "가장 작은 쪽 기준 축소"(§2.5)는 이 형식과 충돌한다. 교정은 123 G-13 경로(121 TP-11.6 ④ + D-234 ③ 개정)가 소유하고, 이 계획은 **교차 시스템 보강 사례를 그 테스트에 공급**한다(G-6).
- **출처**:
  - 열 그룹 머리와 각주에 **실행 기록**을 쓴다. 실행 기록은 SQL 해시 또는 도구·보기, 조회 시각, 창으로 이뤄진다(Q-7).
  - LLM 요약은 출처를 만들지 않는다.
  - UI 출처 칩(Grafana형)은 후속으로 둔다. 첫 릴리스는 텍스트 각주다.
- **상충**:
  - 표에는 권위 소스 값만 넣는다.
  - 같은 응답에서 **이미 조회된** 대체 소스의 같은 속성이 정규화 뒤에도 다르면 불일치 각주를 단다. 정규화는 대소문자, 공백, 버전 표기, 단위 환산이다.
  - **추가 조회·LLM 판정·다수결은 하지 않는다**(Q-6 · G-19 유지).
  - 비교 대상 속성은 권위 소스 지도(§4.1)에서 대체 소스가 선언된 속성으로 한정한다. 첫 릴리스는 OS명·버전, CPU 코어, 메모리 용량이다.
- **합의/단독(P-D)**: "두 계층 모두 이상"과 "한 계층만 이상"은 **코드가 계산한 사실**로 요약 입력에 넣는다. 이상 판정 기준은 게이트웨이 `was_signals`와 폴스타 임계값이다(GALA+ · TrioXpert 방향 · 선택 — C-5).
- **2단 `composite_answer="steps"`와의 관계**: 엔터티 표는 병합이 성립할 때 단계별 표 **대신** 나온다. 불성립(구동 집합 없음 · 영역이 독립)이면 현행 단계별 표가 유지된다. D-062 개정 방향("표는 코드 · 한 문장")과 같다.
- **부분 결과(D-265)**: 시간 상한에 걸리면 **마감까지 모인 열 그룹으로** 엔터티 표를 낸다(B-6 — 원 소유 통지 후 C트랙 테스트).

### 4.10 인가 · 감사 · 안전

- **인가**: `allowed_sources`(G-9)는 DB가 없는 소스(Prometheus·OpenMetrics·APM)에 적용하고, SQL DB는 D-232 그대로다. 권한 밖 소스는 소스 상태 행에도 "권한 밖"으로만 적고 **소스 존재를 드러내는 안내는 하지 않는다**(D-264 선례).
- **감사**: `apm_query`·`metric_query`·패싯 변환 조회를 본체 감사에 남긴다(121 N-14 계열).
- **읽기 전용**: 게이트웨이는 GET + 경로 허용목록이다(D-195 ①). 본체는 쓰기 도구를 부르지 않는다(D-003). L2 조치(87 G-6)는 이 경로와 무관하다.
- **프롬프트 주입**: 트랜잭션명·실행 텍스트·자산 비고는 다음 단계의 **값**으로만 쓰고, 처리기·소스·보기를 바꾸지 못한다(121 P-10).
