### 벤치마크 퀵 가이드

**무엇인가** — 설정 파일이 멀쩡한지 전수로 검사하고, 설정을 바꿔가며 어느 쪽이 빠르고 정확한지 잰다.
**내가 할 일** — 명령 하나 실행하고, 끝나면 나온 폴더를 전달한다. 그게 전부다.

#### 1. 준비 (처음 한 번)

```bash
cd /path/to/collectorinfra && source .venv/bin/activate
python -m scripts.bench --preflight
```

`→ 실행 가능합니다` 가 나오면 준비 끝. 경고가 있어도 대부분 그대로 진행된다(건너뛸 항목을 알려준다).

#### 2. 실행 — 셋 중 하나

| 언제 | 명령 | 걸리는 시간 |
|---|---|---|
| **평소 점검** · 설정이 이상할 때 | `python -m scripts.bench` | 1.5~3시간 |
| **아주 빠르게** 정합성만 | `python -m scripts.bench --quick` | 10초 |
| **성능 비교까지** (본 실행) | `python -m scripts.bench --sweep --mode run --scale full` | 10~30시간 |
| **처분 제안서** | `python -m scripts.bench --propose` | 2~5분 |

처음이라면 **본 실행 전에 한 번**:

```bash
python -m scripts.bench --sweep --mode mock --scale smoke   # 무과금 파이프라인 확인
python -m scripts.bench --sweep --mode run  --scale smoke   # 30분 — 실 확인
```

내부망에서는 **아무것도 묻지 않고 바로 시작한다.** 승인 절차는 없다.

**인증이 켜진 서버(`AUTH_ENABLED=true`)는 전용 벤치 계정이 있어야 돈다.** 계정이 없으면 스위프는
서버를 띄우기 전에 멈추고 계정 주는 법을 출력한다 — 인증을 끄고 재지 않는다(`plans/94` G-3 · 사용자
확정 2026-09-15). 인증을 끄면 인증 미들웨어와 사용자별 DB 범위가 빠져 운영과 다른 경로를 재기 때문이다.
인증이 꺼진 서버는 계정 없이 그대로 돈다.

**질의용 벤치 계정**을 주는 방법은 둘 중 하나다 *(2026-09-14 보강)*:

| 방법 | 예 | 주의 |
|---|---|---|
| 플래그 | `--user <ID> --password <PW>` | — |
| OS 환경변수 | `export BENCH_USER_ID=<ID>` · `export BENCH_USER_PASSWORD=<PW>` (PowerShell: `$env:BENCH_USER_ID="<ID>"`) | **`.env`·`.encenv`에 적으면 읽히지 않는다**(OS 환경변수로만 읽는다). 시나리오 CLI(`python -m scripts.scenario`)는 이 변수를 읽지 않는다 |

설정 에코에 쓰는 **운영자 크레덴셜은 입력하지 않는다** — `ADMIN_USERNAME`(`.env`)·`ADMIN_PASSWORD`(`.encenv`)를
설정에서 자동으로 읽는다(OS 환경변수로 줘도 읽힌다). 다른 값을 쓰려면 `--admin-user`/`--admin-password`.
설정 키 정의·계정 준비는 `docs/03_setup_guide.md` §3.5, 로그인 실패 메시지별 대응은 `plans/94` 「▶ 실행 가이드」 ⑨가 정본이다.

#### 3. 오래 걸리는 실행은 백그라운드로

```bash
nohup python -m scripts.bench --sweep --scale full > results/bench/nohup.log 2>&1 &
tail -f results/bench/nohup.log
```

**끊겨도 괜찮다.** 같은 명령을 다시 치면 하던 데서 이어진다. 지운 폴더만 없으면 된다.

#### 4. 끝나면

화면 마지막에 폴더 경로가 나온다. **그 폴더를 통째로 전달한다.**

```
results/bench/20260911-01/
├── SUMMARY.md          ← 먼저 이것만 봐도 된다
├── config_health.md      설정에 문제가 있으면 여기
├── report.md             어느 설정이 나은지
└── proposals/            바꿀 것 제안 (반영은 다른 사람이)
```

`SUMMARY.md` 맨 위 다섯 줄에 결과 요약과 **다음 할 일**이 적혀 있다.

#### 5. 막혔을 때

| 화면에 나온 말 | 뜻 | 할 일 |
|---|---|---|
| `ibm-db 미설치` | 은행존 DB만 못 본다 | 그대로 진행해도 된다 |
| `tier 불일치` | 설정과 설치된 패키지가 안 맞는다 | `SUMMARY.md` 즉시 조치 절을 전달 |
| `가림(shadowed)` | 셸 환경변수가 설정 파일을 덮고 있다 | 그 키는 자동으로 빠진다. 그대로 진행 |
| `판정 불가`가 대부분 | 테스트 케이스가 적다 | 그대로 전달. 워크로드 확장은 다른 사람 몫 |
| `판정을 내지 않습니다 — …오류다` | 서버에 제대로 붙지 못했다 | 바로 위에 찍힌 `INVALID` 사유·오류 표지를 전달. **10시간을 태우기 전에 멈춘다** |
| `접속: 인증이 켜진 서버…인데 벤치 계정이 없습니다` | 인증 on 서버에 계정을 안 줬다 | `--user`/`--password` 또는 OS 환경변수 `BENCH_USER_ID`/`BENCH_USER_PASSWORD`(위 표). 인증을 끄고 돌리지 않는다(G-3) |
| `※ 운영자 크레덴셜을 찾지 못했습니다` | `ADMIN_USERNAME`/`ADMIN_PASSWORD`를 설정에서 못 읽었다 | 인증 on 서버에서만 뜬다 — 설정 에코가 실패해 arm이 전부 `INVALID`. `.env`·`.encenv` 확인(`docs/03` §3.5) |
| `INVALID` 사유에 `로그인 실패` · `http 401` · `ConnectError` | 서버 로그인·계정 문제 | `plans/94` 「▶ 실행 가이드」 ⑨-5의 메시지별 표 |
| 디스크 부족 | 결과 폴더가 쌓였다 | 오래된 `results/bench/*` 삭제 |
| `.env`가 바뀌어 있다 | **버그** | 중단하고 보고. 이 도구는 설정 파일을 고치지 않는다 |

#### 6. 하지 않아도 되는 일

- 축이나 항목을 고르는 일 — **코드가 고른다**
- YAML·설정 파일 편집 — **없다**
- 통계 해석 — **리포트가 결론을 써 준다**
- 중단 복구 판단 — **다시 실행하면 된다**
- 승인 요청 — **내부망은 불요**

#### 7. 맥북 로컬 MLX로 돌릴 때 *(2026-09-17 추가 · D-222 · `plans/100`)*

- 준비·기동은 `docs/03_setup_guide.md` §7.2(`scripts/mlx_server.sh` · 9B). mlx는 내부망과 같이 승인 없이 실 실행된다.
- `--sweep --mode run`은 arm 서버를 띄우기 전에 **MLX 서버 도달·1토큰 생성**을 확인하고, 실패하면 멈춘다(exit 2).
- **로직 확인용으로만 쓴다.** arm 1개 × 시나리오 1건이 27B에서 약 10분(583초·618초 실측)이라 smoke(9 arm × 31건)도 수십 시간이다. 규모를 줄이는 CLI 옵션은 없다.
- **지연 비교를 결론으로 쓰지 않는다.** MLX 프롬프트 캐시는 arm마다 재기동되는 앱 서버 밖에 있어 arm 사이에 남는다 — 실행 순서가 지연에 섞일 수 있다(2026-09-17 두 arm 실측에서는 가장 긴 약 2만 토큰 프롬프트가 두 arm 모두 약 200초 콜드였다). 성능 결론은 내부망 결과로만 낸다.
- 오케스트레이터가 안 떠서 1단이 내려간 arm은 INVALID로 빠진다(`plans/94` ⑪).

## 실행 가이드 ② 상세 — 개발자 실행 참조본 *(v2 신설 · v6에서 문서 앞으로 이동)*

> 사용자 지시: *"개발자가 벤치마크 테스트 코드를 실행하는 방법을 가이드하고"* ·
> *"개발자의 역할은 단지 벤치마크 테스트를 실행시키는 것 뿐이다."*
>
> **이 절만 읽으면 실행할 수 있어야 한다.** 뒤따르는 §0~§13은 설계 근거이고, 실행자는 여기까지만 본다.

### A.1 30초 요약

```bash
cd /path/to/collectorinfra
source .venv/bin/activate

python -m scripts.bench            # ① 전수 설정 검증 (기본 동작 · LLM 호출 0)
python -m scripts.bench --sweep    # ② 성능 스위프까지 (내부망이면 승인 프롬프트 없음)
```

끝나면 화면이 **산출 폴더 경로 하나**를 알려준다. 그 폴더를 전달하면 개발자 일은 끝이다.

- 중간에 끊겨도 **같은 명령을 다시 치면 이어서 간다.** `--resume` 같은 것을 기억할 필요 없다.
- YAML을 열거나 고칠 일은 없다. 축은 코드가 고른다.
- 통계를 읽을 일은 없다. 리포트가 판정 문장으로 끝난다.

### A.2 사전 준비 (설치당 한 번)

| # | 할 일 | 확인 명령 | 실패하면 |
|---|---|---|---|
| 1 | 루트 venv 활성화 | `python -c "import src.config"` | `pip install -e ".[dev,document]"` |
| 2 | `.env`가 이 설치의 실제 값인지 | `python -m scripts.bench --show-env` | 운영 `.env`를 배치. **벤치마크는 `.env`를 수정하지 않는다** |
| 3 | DB 도달성 | `python -m scripts.bench --preflight` | 아래 A.7 표 |
| 4 | (스위프만) LLM 도달성 | 동일 | 폐쇄망 FabriX 접속 정보 확인 |

**3번 하나로 1·2·4가 함께 점검된다.** 실제로 개발자가 치는 준비 명령은 `--preflight` 하나다.

### A.3 표준 절차 3종

#### 절차 1 — 설정 건강 점검만 (LLM 호출 0 · 수 분 ~ 2시간)

가장 자주 쓰는 절차다. **LLM을 한 번도 부르지 않는다.**

```bash
python -m scripts.bench                    # L1~L4 전수 (기본)
python -m scripts.bench --quick            # L1·L3만 (초 단위)
python -m scripts.bench --quick --ci       # 위와 같되 문제가 있으면 exit 1 (CI용)
```

산출: `results/bench/<날짜>-<n>/config_health.md` · `coverage_ledger.md`

#### 절차 2 — 소규모 확인 (30분 내외)

본 스위프 전에 파이프라인이 도는지만 본다. **본 스위프에 들어가기 전에 반드시 한 번.**

```bash
python -m scripts.bench --sweep --scale smoke
```

축 3~4개 · 워크로드 20건 · 반복 없음. 예상 호출 수와 소요 시간을 먼저 보여준다.

> 내부망(`LLM_PROVIDER=fabrix`)이면 **확인을 묻지 않고 바로 실행**한다. 외부 프로바이더가 설정돼 있으면
> 그때만 승인 프롬프트가 나온다(§4.4) — 개발자가 구분할 필요는 없고, 화면이 어느 쪽인지 알려준다.

#### 절차 3 — 내부망 본 스위프 (10~30시간)

```bash
python -m scripts.bench --sweep --scale full
```

- 실행 전 **예상 LLM 호출 수·소요 시간·종료 예정 시각**을 표로 보여준다. 내부망이면 묻지 않고 진행한다.
  이 표는 승인용이 아니라 **운영 시간대를 피할 판단 재료**다(§A.8 6번).
- 끊기면 같은 명령을 다시 친다. 이어서 간다.

```bash
nohup python -m scripts.bench --sweep --scale full --yes \
      > results/bench/nohup.log 2>&1 &
tail -f results/bench/nohup.log       # 진행 상황
```

### A.4 명령이 내부에서 하는 일 (참고 · 개발자가 실행하지 않는다)

```
1. preflight      환경 점검 · 이전 미완 실행 탐지
2. 트랙 T (L1~L4) 전수 설정 검증          ← 기본 동작은 여기까지
   ─────────────────────────────────── --sweep 이 없으면 여기서 리포트 쓰고 종료
3. 축 자동 선별   카탈로그 → F1 → F2 → axes.yaml 생성 (가림 키 자동 제외)
4. 예상치 산출    arm 수 · LLM 호출 · 소요 시간 → 표로 고지(내부망은 프롬프트 없음)
5. 스위프         S0 기준선 → S1 노이즈 → S2 OFAT → S3 쌍 → S4 확인
                  arm마다 subprocess 기동·검증·측정·종료, 실패는 INVALID로 격리
6. 리포트         성능 리포트 + 건강 보고서 + 커버리지 장부 + 판정 문장
7. 제안서         권고 프로파일 · 노브 처분 · D-161 4항
```

**3번이 자동이라는 것이 v1과의 핵심 차이다.** 개발자가 축을 고르지 않는다.

### A.5 내부 명령 (개발·디버깅 시에만 · 평소엔 쓰지 않는다)

단일 진입이 실패해 원인을 좁힐 때만 쓴다. 운영 절차에는 등장하지 않는다.

```bash
python -m scripts.bench.validate --layer l1            # 카탈로그 정합만
python -m scripts.bench.validate --layer l2 --key TEXT2SQL_CANDIDATE_COUNT   # 한 키만
python -m scripts.bench.axes --explain                 # 축이 왜 그렇게 뽑혔는지 근거 출력
python -m scripts.bench.runner --arm S2-X2-n3 --mock   # arm 하나만 LLM 없이 재현
python -m scripts.bench.report results/bench/20260911-01/   # 리포트만 다시 생성
```

`--explain`은 축 선별 결과에 이의가 있을 때 쓴다. 각 키가 어느 필터(F1/F2)에서 어떤 사유로
포함·제외됐는지 한 줄씩 출력한다.

### A.6 산출물 — 무엇을 전달하나

## 0. 요약 — 이 계획이 실제로 푸는 문제

### 0.1 해석 정정 — 요청은 3종, 실체는 "선행 1 + 트랙 4"

사용자 지시를 그대로 읽으면 만들 것은 세 개다. 그런데 실측하면 **③이 ②에 의존하고, ②가 ①에 의존하고,
①이 성립하려면 워크로드가 지금보다 커야 한다**. 순서를 뒤집으면 전부 헛돈다.

| # | 이름 | 한 줄 | 산출 코드 | 없으면 생기는 일 |
|---|---|---|---|---|
| **선행 P** | **워크로드 확보** *(v4 정정)* | ~~골드셋 26건 → 80건 신규 작성~~ → **`plans/94` 시나리오 카탈로그(145건)를 소비**하고 축 비교에 쓸 정상 군만 선별 | `testdata/scenarios/`(94 소유) | 리포트가 *"차이 없음"*만 낸다 — 노브당 유의 차이를 검출할 검정력이 없다(§2-②) |

L3(주입 실효성)이 실패하는 키를 먼저 걸러내지 않으면 그 키를 축으로 삼은 스윕이 통째로 무효가 된다(§2-③·R3).

**개발자가 이 순서를 외울 필요는 없다.** 단일 명령이 순서·의존·재개를 전부 안다(§0.4·「실행 가이드 ② 상세」).

### 0.2 이 계획의 한 문장

**노브를 줄이는 근거를 "정적 감사"(참조 수·수명)에서 "측정"(정확도·지연·비용)으로 한 축 넓히고,
그 측정을 재현 가능한 코드로 고정한다.** 삭제 자체는 본 계획의 산출물이 아니라 `plans/70` P1의 입력이다.

### 0.3 ★ 실측이 바꾼 것 3건

1. **정적 감사표는 이미 있다 — 없는 것은 측정이다.** `docs/flag_audit.md`가 플래그 **43개**를 전수 판정했고
   (기한부 5·상수화 3·존치 35), 판정 규칙 5조는 D-162 §6으로 고정돼 있다. 그런데 **다섯 규칙 중 성능을 보는
   것이 하나도 없다** — 참조 수·`.env` 실제값·생성일만 본다. 본 계획은 **규칙 6조(측정 근거)** 를 추가하는 것이지
   감사표를 다시 만드는 것이 아니다.
2. **A/B 비교 인프라가 이미 있다.** `scripts/eval_text2sql.py:75`의 `AB_AXES` 5축(`synonym_fuzzy`·`value_retrieval`·
   `candidate_count`·`selection`·`semantic_compose`)과 `FLAG_ENV` 매핑(`:65-74`), `build_ab_report`(`:1038`),
   `_run_meta`(`:1194` — 커밋·dirty·벽시계 provenance)가 **2팔 비교까지는 이미 동작한다**. 트랙 A는 신규 하네스가
   아니라 **이것을 N팔로 일반화하고 subprocess 격리를 씌우는 것**이다. 지표도 이미 있다(`aggregate:984` — `ex_rate`·
   `avg_latency_ms`·`total_tokens`·`avg_llm_calls`·`avg_retries`).
3. **"간소화"의 값싼 답은 삭제가 아니라 프로파일이다.** 환경변수 151개(`.env` 실측) 중 운영자가 실제로 만지는 것은
   소수인데, 어느 것이 소수인지가 문서화돼 있지 않다. 삭제는 D-161 4항 실측을 노브마다 요구하는 비싼 경로다.
   **검증된 프리셋 몇 개 + 나머지는 "건드리지 마시오" 등급**이 같은 체감 효과를 훨씬 싸게 낸다(§6.3, G-6).

### 0.4 자동화 책임 경계 — 개발자가 하는 일은 "실행"뿐 *(v2 · 사용자 지시)*

> 사용자 지시: *"개발자의 역할은 단지 벤치마크 테스트를 실행시키는 것 뿐이다."*

이 한 줄이 설계 제약이다. 개발자가 축을 고르거나, 명령을 순서대로 여러 개 치거나, 통계를 해석하거나,
중단된 스윕을 손으로 복구하는 일이 **하나라도 남아 있으면 이 계획은 요건을 못 맞춘 것이다.**

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **개발자(실행자)** | ①내부망 접속·`.env` 준비 확인 ②**명령 하나 실행** ③끝나면 산출 폴더 전달 *(v5: 승인 단계 삭제 — 내부망은 프롬프트 없이 진행)* | 축 선별 · YAML 편집 · 단계별 명령 나열 · 통계 해석 · 실패 arm 복구 · 재개 판단 |
| **코드(자동)** | 환경 사전점검 · 축 자동 선별 · arm 전개 · 격리 기동·검증 · 실패 격리 · **자동 재개** · 통계·검정 · 리포트 · 제안서 생성 · 결론 문장 작성 | `.env`·`config.py` 수정(V5) · 폐기 제안 자동 반영 |
| **의사결정자(설계자·운영자)** | 제안서 검토 후 **반영 여부 결정** · 게이트 G-1~G-13 확정 | 벤치마크 실행 |

**개발자 표면의 전부**(자세히는 문서 앞 「실행 가이드 ② 상세」):

```bash
python -m scripts.bench            # 이것 하나. 점검 → 계획 제시 → 실행 → 리포트 → 제안서
```

이 요건이 v1 설계에서 바꾼 것 4가지:

1. **`axes.yaml`은 "사람이 고치는 파일"에서 "자동 생성물"로 바뀐다**(§3.2·§7.1). 카탈로그 인트로스펙션과
   영향 경로 규칙으로 코드가 만들고, 사람 검토는 **선택**이다(`--axes-review`로 열람·동결 가능).
2. **단계별 명령을 나열하지 않는다.** 트랙 T·P·A·B·C는 내부 단계이지 개발자가 아는 이름이 아니다.
   단일 명령이 의존 순서를 알고, 앞 단계 산출물이 있으면 건너뛴다.
3. **중단·재개가 개발자 판단을 요구하지 않는다.** 같은 명령을 다시 치면 이어서 간다(`--resume` 불요 ·
   기본 동작). 폐쇄망 며칠짜리 스윕이 전제이므로 이것이 편의가 아니라 요건이다(R2).
4. **리포트가 결론을 낸다**(§5.5). "축 X2는 p=0.03"이 아니라 *"후보 수 3이 기준선보다 정확도 +9%p,
   지연 +2.1s. 권고: 채택"* 까지 코드가 쓴다. 개발자가 통계를 읽고 판단하지 않는다.

**경계의 반대쪽도 명시한다** — 자동화하지 **않는** 것은 셋뿐이고, 전부 근거가 있다.

| 자동화 제외 | 이유 |
|---|---|
| `.env`·`config.py` 실제 수정 | D-161 폐기 절차 우회 · `.env`는 git 미추적이라 복구 근거 소실(§6.1·V5) |
| **외부 프로바이더**(`gemini` 등) 실행 | D-127. 내부망은 면제지만 외부 경로는 승인이 산다 — 코드가 `LLM_PROVIDER`로 자동 판정한다(§4.4 · v5) |
| 게이트 G-1~G-13 확정 | 설계 판단이지 실행이 아니다 |

## 2. 먼저 인정해야 할 네 가지 제약 (설계가 여기서 갈린다)

### ① 조합 폭발 — "조합을 벤치마크한다"는 문장은 그대로는 실행 불가능하다

2^110은 탐색 불가다. 실행 가능한 것은 **축을 좁힌 뒤의 부분 설계**뿐이다. 본 계획은 3단으로 좁힌다.

```
231 노브
  └─(F1) 성능에 닿을 수 없는 것 제거 ─────────→ 후보 **148** (v7 실측 · 초안 추정 40~60은 과소였다)
        · UNCONSUMED_KEYS(미소비) 20 · 크레덴셜 14 · 접속·저장 정책 20 · 비질의 그룹 133
  └─(F2) 영향 경로 판정 ──────────────────────→ **1차 축 28 · 2차 축 22** (v7 실측)
        · 1차 = 동작 모드를 바꾼다 / 2차 = 상한·예산(정상 경로에서 발동하지 않는다)
        · "존치 35" 중 LLM 호출 수·DB 왕복·프롬프트 길이·재시도 예산을 바꾸는 것만
  └─(F3) 실험 설계 ───────────────────────────→ 실행 arm 20~40회
        · OFAT 주효과 → 상위 효과 축만 2-way 교호작용
```

**전수(full factorial)는 어느 단계에서도 쓰지 않는다.** 축 12개만 해도 4096 arm이고, arm당 워크로드
80건 × LLM 호출 수를 곱하면 폐쇄망에서 며칠 단위다.

### ② 검정력 — 골드셋 26건으로는 정확도 차이를 구분할 수 없다 ★이 계획의 가장 큰 위험

EX 골드셋은 gp 15 + yd 6 + b0 5 = **26건**이다. 1건이 3.8%p다. 두 arm의 EX가 각각 20/26과 22/26이면
차이는 7.7%p지만, 이 표본에서 **통계적으로는 구분되지 않는다**(쌍체 McNemar 기준, 불일치 쌍이 2~3건이면 p≫0.05).

| 목표 검출력 | 필요 워크로드 규모(쌍체·불일치율 가정) | 확보 가능? *(v4)* |
|---|---|---|
| 5%p 차이를 80% 검정력으로 검출 | 대략 **150~250건** | △ 145건으로 하한 근접 |
| 10%p 차이를 80% 검정력으로 검출 | 대략 **60~90건** | ✅ 여유 |

**v4 정정**: `docs/29` **113건** + `docs/synonym_test_cases.md` **32건 = 145건**이 이미 문서로 존재한다
(실측 2026-09-11). 이 중 축 비교에 쓸 수 있는 **정상 군**만 골라도 80건을 넘으므로, v1이 잡았던
*"80건을 새로 만든다"* 는 불필요하다 — **만드는 것이 아니라 기계 판독본으로 옮기는 것**이고 그 소유는
`plans/94`다(§1.5).

→ **판정 대상은 10%p급을 확실히, 5~7%p급을 조건부로 잡는다.** 그 아래는 여전히 `판정 불가`다.
그 아래 차이는 리포트가 **`판정 불가(underpowered)`** 로 표기하고, 그 축은 "성능 근거 없음 = 정적 규칙으로
판정"으로 넘긴다. **없는 유의성을 만들어내지 않는 것이 이 항목의 핵심이다.**

### ③ LLM 비결정성 — 같은 설정도 흔들린다

D-035·Known Mistakes가 반복 기록한 사실이다. 대응 3종:

- **쌍체(paired) 설계** — arm 간 비교는 항상 **같은 질의 id 단위 쌍**으로 한다. 집계 평균 비교보다 분산이 훨씬 작다.
- **반복 n회** — 기본 `--repeat 3`. 정확도는 다수결이 아니라 **건별 성공률(0/⅓/⅔/1)** 로 다룬다.
- **온도 고정** — 벤치마크 중 `LLM_FABRIX_LLM_CONFIG`의 temperature는 arm이 명시적으로 바꾸지 않는 한 고정값을
  주입한다. 고정하지 않으면 모든 축의 효과에 온도 분산이 섞인다.

### ④ 재기동 비용 — 플래그는 기동 시 1회 해석된다

`CLAUDE.md`·D-135 실측: 즉시 반영 7키 / 리로드 78키 / **재시작 148키**. 사다리 단은 `build_graph()` 안에서
**빌드 타임에 배타 확정**된다(D-162 ①). 따라서:

- **arm 1개 = 프로세스 1회 기동.** 인프로세스에서 config만 갈아끼우는 것은 사다리·노드 등록을 바꾸지 못해
  **측정값이 거짓이 된다**.
- 러너는 `subprocess`로 자식 프로세스를 띄우고 **env로만** 설정을 주입한다(`.env` 파일을 수정하지 않는다 — 병행
  세션·작업 트리 오염 금지).
- 자식의 기동 로그에서 `오케스트레이션 사다리 확정: tier=…`(`ladder.py:114`)를 파싱해 **의도한 단으로 떴는지
  검증**하고, 다르면 그 arm을 `INVALID`로 버린다(조용한 강등이 측정에 섞이는 것을 막는다).

| **S2 OFAT** | 축 1개씩만 기준선에서 이동 | 12~18 | 주효과. 각 축의 부호와 크기 |
| **S3 교호작용** | S2 상위 효과 축 중 상호작용이 의심되는 **쌍만** | 6~10 | 예: X2(후보 수) × X3(선택 전략), X7(캐시) × X1(사다리 단) |
| **S4 확인** | S2·S3이 지목한 후보 프로파일 2~3개 | 6~9 (반복 포함) | 권고안이 기준선을 실제로 이기는지 |

**실측 62 arm**(2026-09-11 · 1차 축 28개 · bool은 2수준·수치는 3수준). 초안 추정 28~41은 수치 축의 3수준을 세지 않은 값이다.
arm당 워크로드는 94 카탈로그의 정상 군 32건 → **1984회 실행 · 내부망 10~30시간 규모**(G-13에서 실행 창 확정).
`--scale smoke`(축 4개 · 9 arm)로 파이프라인을 먼저 확인하고 `--scale full`로 넘어간다 — 명령이 규모와 예상 시간을 먼저 고지한다.

**S1을 건너뛰지 않는다.** 같은 설정을 3번 돌려 얻은 편차가 곧 *"이 벤치마크가 구분할 수 있는 최소 차이"*다.
이 값 없이 S2의 차이를 해석하면 노이즈를 효과로 읽는다(E1 A/B 사고 2026-08-04와 같은 유형).

### 3.5 트랙 T — 전수 설정 검증: 스윕이 닿지 않는 317개를 덮는다 *(v2 신설 · 사용자 지시)*

> 사용자 지시: *"전체적인 설정 파일을 테스트하고 보고서를 만들 수 있는 계획을 수립해야 한다."*

#### 3.5.1 "전체 설정 테스트"는 두 가지로 갈린다 — 하나는 전수 가능하다

§2-①이 보인 대로 **성능 스윕의 전수는 불가능**하다(2^110). 그런데 지시를 실측 관점에서 다시 읽으면
*"전체 설정 파일을 테스트한다"* 는 **성능 측정만을 뜻하지 않는다.** 운영자가 겪는 *"설정이 어렵다"* 의 실체는
성능보다 앞선 곳에 더 많이 있다.

| 실제 질문 | 어느 층이 답하나 | 전수 가능? |
|---|---|---|
| *"이 키가 먹기는 하나?"* | L4 소비 실증 | **✅** |
| *"값 범위가 뭐지? 이렇게 넣으면 뜨나?"* | L2 기동 안전성 | **✅** |
| *"분명 바꿨는데 왜 안 바뀌지?"* | L3 주입 실효성 | **✅** |
| *"`.env.example`에 있는데 코드엔 없는 키 아닌가?"* | L1 카탈로그 정합 | **✅** |
| *"어느 값이 빠른가?"* | L5 성능 효과 | ❌ 축 12~18만 |

→ **L1~L4를 335필드 전건으로 돌리고, L5만 축으로 좁힌다.** 이러면 *"전체 설정 파일을 테스트했다"* 가
빈말이 아니게 되고, **L1~L4는 LLM을 한 번도 호출하지 않아** 환경 준비만으로 지금 시작할 수 있다.

#### 3.5.2 5층 구조

| 층 | 검증 내용 | 대상 | 실 LLM | 실행 시간(추정) | 산출 |
|---|---|---|---:|---|---|
| **L1** | **카탈로그 정합** — `.env` / `.env.example` / `config.py` / `settings_catalog` **4자 대조**. 고아 키(파일에만 있음)·누락 키(코드에만 있음)·타입 불일치·설명 부재·`.encenv` 가림 대상·중복 등재 | 335 + 파일 키 전건 | **0** | 초 | 정합 표 |
| **L2** | **기동 안전성** — 각 키를 경계값(bool 2종·enum 전 값·int min/max/0/음수·빈 문자열)으로 주입하고 **config 로드가 성공하는가**. 실패는 `ValidationError` 메시지까지 기록 | 335 × 1~5 값 | **없음** | **3~5분**(대표값 1개 · v7 실측 0.5s/건) | 값역 표 + 실패 목록 |
| **L3** | **주입 실효성** — 주입값 = **자식이 실제로 읽은 값**인가. OS env·`.encenv` 가림, `AliasChoices` 순서 함정(D-162 실측), 인라인 주석 파손을 전수로 잡는다 | 335 | **0** | L2에 편승 | 가림 목록 |
| **L4** | **소비 실증** — 값을 바꾸면 **동작이 실제로 달라지는가**. mock 워크로드로 프롬프트 렌더·생성 SQL·`node_path`의 해시가 변하는지 본다. 안 변하면 *노브 환상* 후보 | 축 밖 키 포함 가능한 범위 | **0** | 1~2시간 | 무효 노브 후보 |
| **L5** | **성능 효과** — 정확도·지연·비용 | 축 12~18 | **있음** | §3.3 | 축별 효과표 |

#### 3.5.3 L2를 **경량 모드**로 도는 이유 (실측 근거 있는 함정 회피)

`config.py:1188-1191` 주석이 못박은 실측이 있다 — **nested config를 인스턴스 기본값으로 두면 모듈 임포트
시점의 env로 고정되어, 이후 `os.environ` 변경 + `load_config.cache_clear()`가 반영되지 않는다**(2026-07-15
E1 하네스 A/B 무효화 실측). 그래서:

- **같은 프로세스에서 env를 바꿔가며 335필드를 도는 방식은 쓰지 않는다.** 값이 반영되지 않아 전 항목이
  거짓 통과한다. §2-④와 같은 이유다.
- **경량 모드** = 필드마다 자식 프로세스를 새로 띄워 **config 로드까지만** 하고 자기 config를 JSON으로
  에코한 뒤 종료한다. 서버·그래프 빌드를 하지 않아 1~2초면 끝난다.
  ```
  python -c "from src.config import load_config, ...; print(json.dumps(<실효 설정 전체>))"
  ```
- **서버 모드**는 그래프 배선에 영향을 주는 키에만 쓴다 — 카탈로그 `apply_mode`가 `restart`이면서 사다리·
  노드 등록에 관여하는 것(사다리 3키·`ACTIVE_DB_IDS`·`DB_BACKEND` 등 20개 내외). 전수 335를 서버로 돌면
  기동 비용이 수 시간이고 얻는 것이 없다.

L3는 L2의 에코 산출물을 그대로 재사용한다 — **주입값 사전 vs 에코 사전의 차집합**이 곧 가림 목록이다.
별도 실행이 필요 없다.

#### 3.5.4 L4 소비 실증 — `UNCONSUMED_KEYS`를 사람 손에서 떼어낸다

현재 "미소비" 판정은 `settings_catalog.py:350`의 `UNCONSUMED_KEYS` **손으로 관리하는 frozenset**이다
(D-129가 16개로 시작해 현재 20개). 손 관리는 필연적으로 낡는다 — 소비가 생겨도 목록에서 안 빠지고,
소비가 사라져도 안 들어온다.

L4는 이것을 **동적으로 반증**한다.

```
기준 렌더 : mock 워크로드 N건 → (프롬프트 해시, 생성 SQL 해시, node_path, 호출 계획) 수집
키별 렌더 : 키 하나만 기본값과 다른 값으로 → 같은 수집
판정      : 네 해시가 전부 동일 → "동작 불변(노브 환상 후보)"
            하나라도 다름        → "소비 실증됨"
```

- **판정 방법은 `scripts/prompt_render_diff.py`가 프롬프트에 쓰는 기법과 같다**(렌더 결과 해시 비교).
  다만 그 스크립트는 프롬프트 정본 전환 전용이라 **도구를 재사용하는 것이 아니라 방식을 차용**한다.
- **"동작 불변"은 "삭제해도 된다"가 아니다.** mock 워크로드가 그 키의 경로를 지나지 않았을 뿐일 수 있다.
  리포트는 `노브 환상 후보`로만 적고, `UNCONSUMED_KEYS`와 **대조표**를 낸다:
  | 대조 결과 | 의미 | 조치 |
  |---|---|---|
  | 목록에 있고 L4도 불변 | 일치 — 미소비 확인 | 유지 |
  | 목록에 없는데 L4가 불변 | **목록이 놓친 후보** | 참조 grep으로 확인 후 등재 검토 |
  | 목록에 있는데 L4가 변함 | **목록이 낡음** — 소비가 생겼다 | 목록에서 제거 |

세 번째 칸이 이 층의 진짜 값어치다. 손 관리 목록의 거짓을 **자동으로** 드러낸다.

#### 3.5.5 패키지 경계 — 어디까지가 "전체 설정"인가

본체 `AppConfig` 밖에도 설정 원천이 있다(D-139 패키지 경계). v2는 **범위를 명시하고 나머지는 미포함을
밝힌다**(침묵 제외 금지).

| 원천 | 위치 | 트랙 T 범위 | 사유 |
|---|---|---|---|
| 본체 `AppConfig` 23그룹 | `src/config.py` | **포함**(L1~L5) | 본 계획의 대상 |
| `mcp_server` | `mcp_server/config.toml` · `mcp_server/mcp_server/config.py` | **L1만**(존재·정합 확인) | 별도 프로세스·별도 cwd. 타임아웃·max_rows는 **MCP 서버가 관리**(CLAUDE.md 보안 절)라 본체 스윕의 축이 아니다 |
| `sre_agent` | `sre_agent/sre_agent/settings.py` `AgentSettings` | **제외** | 별도 venv·별도 프로세스. 조사 경로는 워크로드 밖 |
| `.encenv`(시크릿) | 루트 | **L1·L3만** | 값은 읽지 않는다. **가림 대상 키 목록**으로만 쓴다 |
| `noise_gate` 관련 키 | `AppConfig.noise_gate` 등 | **L1~L4 포함 · L5 제외** | 알람 워크로드는 성격이 달라 별도 벤치마크(G-4) |

→ **L5(성능)는 질의 경로만, L1~L4(검증)는 본체 전체.** 이 비대칭이 *"전체 설정 파일을 테스트"* 의 실행
가능한 정의다.

### 4.2 arm 실행 계약

한 arm의 생애는 다음과 같다. **모든 단계가 실패 시 그 arm을 `INVALID`로 표시하고 다음으로 넘어간다(스위프 중단 금지).**

```
1. env 조립   : os.environ 사본 + arm의 축 값 오버라이드 (.env 파일 미수정)
2. 기동       : subprocess.Popen([python, -m, src.main, --server, --port <free>])
                또는 --query 단발 모드(G-8에서 택일)
3. 기동 검증  : stdout/stderr에서 `오케스트레이션 사다리 확정: tier=X` 파싱
                → 의도한 단과 다르면 INVALID(degraded_reason 기록)
                → 헬스 엔드포인트 200까지 대기(상한 90초)
4. 워밍업     : 워크로드 앞 2건은 버린다(캐시·연결 풀 예열 — 측정 대상 아님)
5. 측정       : 워크로드 전건 순차 실행. 건별로
                {id, ok, ex_pass, latency_ms, llm_calls, tokens, retries, node_path, error}
6. 종료       : SIGTERM → 5초 후 SIGKILL. 포트 회수 확인
7. 적재       : results/bench/<run_id>/raw.jsonl 에 append (arm 1건당 워크로드 건수 줄)
```

**재개(resume)**: `raw.jsonl`에 이미 있는 `(arm_id, workload_id, repeat_idx)`는 건너뛴다.
폐쇄망에서 며칠짜리 스위프가 중간에 끊기는 것을 전제한다.

| `env` | 그룹 | 건수 | 내용 |
|---|---|---:|---|
| `closed` | A~K | **107** | 실 질의 워크로드 — 라우팅·조회·성능통계·알람·복합·HITL·멀티턴·폼필·가드·부하 |
| `sandbox` | L | 32 | 유사어·용어(SYN A~I) — 로컬 도커 샌드박스 전용 |

**종전 기본값이 `sandbox` 여서 실 스위프가 유사어 32건만 재고 실 질의를 한 건도 건드리지
않았다**(실측 2026-09-14 · 두 런 3968턴). 폐쇄망이 이 계획의 전제이므로(§1.4) 기본을
`closed` 로 바꾸고, 활성 DB로 자동 판정한다 — 로컬 샌드박스(`polestar`)만 활성이면 `sandbox`,
폴스타 실 DB가 하나라도 활성이면 `closed`. `--env` 로 덮어쓸 수 있다.

**실행 첫 화면에 워크로드 구성을 적는다.** 필터가 조용히 걸리면 결과가 비어도 "원래 그런 것"으로
읽힌다 — 그 한 줄이 없어서 두 번의 런이 끝나도록 아무도 알아채지 못했다.

```
  환경: closed — 실 관측 DB 활성(polestar_cm_gp) — closed
  워크로드: 시나리오 107건 — 그룹 A(12), B(12), C(13), … · 프롬프트 미작성 21건은 건너뛴다
```

#### 4.3.0-1 단언 이관 — 정확도를 잴 수 있게 만들었다 *(v9 · 2026-09-14)*

정상군 107건 중 **기계 단언이 있는 시나리오는 1건**이었다. 나머지는 기대값이 전부
`manual_review` 산문이라 정확도 쌍이 언제나 0쌍이다 — 인증을 고쳐도 성공한 런과 실패한
런이 같은 문장으로 나온다. 산문을 단언으로 옮겼다.

| 군 | 전체 | 기계 단언 | 비고 |
|---|---:|---:|---|
| A 라우팅 | 12 | 10 | `intent` 는 응답에 없어 **`db_ids`** 로 본다. 비조회 질의는 "SQL 을 만들지 않았는가"로 |
| B 조회(EAV) | 12 | 12 | `r.name` vs `r.hostname` · `stringvalue` vs `_short` · NUMERIC 캐스트(D-160) · DB2 `FETCH FIRST` |
| C 성능통계 | 13 | 11 | **절대 기간만 값을 못박고** 상대 기간("지난달")은 모양(`'20\d{4}'`)만 — 값을 박으면 다음 달에 전건 거짓 불합격 |
| D 알람 | 6 | 5 | `cmm_alarm_active` · `alarmseverity` · 명시 건수 LIMIT |
| E 복합 | 7 | 7 | 복합 경로는 `executed_sql` 에 마지막 태스크만 남아 태스크 연결은 사람이 본다 |
| F 존 HITL | 8 | 8 | 미작성 3건을 2턴 HITL 로 작성 · 존 누수(D-154) 부정 단언 |
| G 멀티턴 | 4 | 4 | **승계의 증거** — 2턴 질의에 호스트명이 없는데 SQL 에는 있어야 한다 |
| H 폼필 | 17 | 16 | 17건이 전부 같은 샘플을 올리고 있었다 → 양식별 실 픽스처로 교체(없던 3종은 생성) |
| I 폼필 HITL | 8 | 8 | 표현 불가였다 → `turns[].endpoint` 신설로 해소(아래) |
| J 가드 | 10 | 5 | DML·다중문 부정 단언 · LIMIT. 마스킹·PII·업로드 한도는 픽스처/설정 의존 |
| K 부하 | 10 | 3 | 나머지는 반복·동시성 프로토콜이라 단일 시나리오로 표현되지 않는다 |
| **계** | **107** | **89** | 러너가 실제로 돌리는 98건 기준 **87건(89%)** — A-05·A-10 은 teardown 미지원으로 건너뛴다(v10 정정) |

**막고 있던 것 셋을 먼저 고쳤다.**

1. **`intent` 는 관측되지 않는다** — `done` 페이로드에 없어 그대로 대조하면 전건 거짓
   불합격이다. 사유를 남기고 라우팅은 `db_ids` 로 본다.
2. **모의 실행이 canned 응답을 판정한다** — `mock:` 블록이 없으면 모의 서버는 고정 SQL 을
   돌려준다. 여기에 내용 단언을 걸면 **모의 서버를 판정한 결과**가 불합격으로 쌓인다.
   블록이 없을 때만 내용 단언을 보류한다.
3. **턴마다 엔드포인트를 못 바꾼다** — 폼필 답변 턴은 `form_fill_answers` 를 JSON 으로
   보내야 하는데 `/query/file` 은 그 필드를 받지 않는다. `turns[].endpoint` 를 신설했다.

**실행 전에 판정 가능 비율을 적는다.** 이 비율이 보이지 않으면 1건과 107건이 구별되지 않는다.

```
  워크로드: 시나리오 107건 — 그룹 A(12), B(12), … · 9건은 러너가 건너뛴다(프롬프트 미작성·teardown 미지원)
            정확도 판정 가능 87/98건(89%) — 나머지는 완주율·지연만 잰다
```

#### 4.3.1 판정 신호 2순위 — 완주율·SQL 생성률 *(v8 신설 · 2026-09-14 실측 대응)*

**정확도만으로는 아무것도 재지 못하는 상태였다.** 94 카탈로그의 정상군 시나리오 32건은 기대값이
전부 `manual_review` 산문뿐이라 **기계 단언이 0개**다(실측 2026-09-14). 판정기는 단언이 없으면
`manual`을 주고 93은 `manual`을 정확도 비교에서 제외하므로, 정확도 쌍은 **항상 0쌍**이다.
이 상태에서는 성공한 런과 전건 401인 런이 같은 문장(`판정 불가`)으로 나온다.

그래서 판정 신호를 2단으로 둔다.

| 순위 | 신호 | 어디서 오나 | 사람 손 |
|---:|---|---|---|
| 1 | **정확도** (`passed`) | 시나리오에 옮겨진 기계 단언 | 필요 — 단언을 옮겨 적어야 한다 |
| 2 | **완주율** (`completed`) | `func_verdict`·`response_mode` (오류·크래시·행이 아닌가) | 불요 |
| 2 | **SQL 생성률** (`sql_generated`) | `executed_sql` 비었는가 | 불요 |

- 1순위 쌍이 0쌍일 때만 2순위로 내려간다. **이름을 바꿔 적는다**(`정확도` → `완주율`) — 무엇으로
  판정했는지 문장이 숨기지 않는다.
- 2순위는 `manual` 건도 센다. "정답인지 모른다"와 "끝까지 돌지 않았다"는 다른 사실이다.
- 2순위는 설정 축이 실제로 흔드는 값이다 — 재시도 폭주·생성 실패·조기 종료가 전부 여기 찍힌다.
- **1순위를 대체하지 않는다.** 단언을 옮겨 적으면 자동으로 1순위로 복귀한다(코드 변경 없음).

#### 4.3.2 건전성 관문 — 판정 이전의 질문 *(v8 신설)*

판정을 내기 전에 **이 런이 판정할 자격이 있는가**를 먼저 묻는다. 셋 중 하나면 통계를 내지 않고
사유와 대표 오류 표지를 출력한 뒤 `exit 1` 한다.

| 조건 | 뜻 |
|---|---|
| 유효 프로파일 0개 | 어떤 arm도 기동 검증을 통과하지 못했다 |
| 실행 턴 0건 | 아무것도 돌지 않았다 |
| 오류율 ≥ 50% | 측정이 아니라 사고다 |

근거: 2026-09-14 실 스위프에서 1984턴이 **전량 HTTP 401**이었는데도 산출된 `axis_verdicts.md`는
62개 arm에 대해 "판정 불가 — 실 모드에서 정확도를 다시 잰다"만 찍었다. 오류율은 통계의 입력이
아니라 **통계를 낼지 말지를 정하는 선행 조건**이다.

### 4.4 실행 게이트 — 내부망 면제 · 외부 프로바이더 유지 *(v5 개정 · 사용자 확정)*

> 사용자 확정: *"내부망에서 밴치마크 테스트를 진행할 예정이라 과금 승인은 필요 없다."* → **G-7 해소.**

**승인 게이트를 지우는 것이 아니라 조건부로 만든다.** 지시를 *"승인 로직 전부 삭제"* 로 읽으면 개발망에서
Gemini로 스모크를 돌릴 때 무승인 외부 호출이 되고, 그것은 D-127 위반이자 사용자 의도도 아니다.

| `LLM_PROVIDER` | 승인 프롬프트 | 옵트인 env | 근거 |
|---|---|---|---|
| **`fabrix`**(내부망 KBGenAI) | **없음** | **없음** | 사내 인프라 — 외부 과금 API가 아니고 데이터가 밖으로 나가지 않는다(D-120과도 정합). **사용자 확정 2026-09-11** |
| `gemini` · 기타 외부 | **유지**(예상치 제시 후 1회) | `RUN_BENCH=1` | **D-127 존속** — 내부망 면제는 내부망에만 적용된다 |
| `ollama`(로컬) | 없음 | 없음 | 로컬 프로세스 |

- **판정은 코드가 한다.** 개발자가 어느 쪽인지 알 필요도, 플래그를 외울 필요도 없다(§0.4).
  `preflight`가 프로바이더를 읽어 *"내부망 FabriX — 승인 없이 진행합니다"* 를 한 줄로 알린다(침묵 금지).
- `--dry-run`(arm 전개·검증만) / `--mock`(주입형 예측기)은 **디버깅 수단으로 남는다.** 더 이상 "과금을 막는
  기본 동작"이 아니라, 파이프라인을 LLM 없이 확인하는 용도다.
- **`--estimate`는 유지한다.** 승인 근거가 아니라 **소요 시간·서버 부하 예고**로 쓴다 — 내부망에서도 10~30시간
  스위프가 언제 끝날지는 알아야 하고, 운영 시간대를 피할 근거가 된다(§A.8 6번).

**여전히 유효한 안전 제약**(과금과 무관한 것들):

- DB는 **읽기 전용만**(D-003). 벤치마크가 쓰기를 하는 경로는 없다.
- 결과 JSONL은 `trace_writer._sanitize`(`:125`)와 같은 마스킹을 거친다 — PII는 내부망에서도 남기지 않는다.
- 동시성 1 · 운영 부하 시간대 회피(R6). **승인이 없어진 것이지 부하가 없어진 것이 아니다.**
- DB는 **읽기 전용만**(D-003). 벤치마크가 쓰기를 하는 경로는 없다.
- 결과 JSONL에 PII가 섞이지 않도록 `trace_writer._sanitize`(`:125`)와 같은 마스킹을 거친다.

### 4.5 신뢰성 장치 (E1 A/B 사고 재발 방지)

`_run_meta`(`eval_text2sql.py:1194`)가 기록하는 provenance를 **run 단위와 arm 단위 양쪽에** 남긴다.

- run: 커밋 sha·dirty 여부·시작 벽시계·호스트명·python 버전·설치 패키지 해시
- arm: **실효 설정 전체 스냅샷**(자식 프로세스가 기동 직후 자기 config를 직렬화해 에코 — 우리가 주입했다고
  믿는 값이 아니라 **자식이 실제로 읽은 값**)

주입값과 에코값이 다르면 그 arm은 `INVALID`다. `.encenv`·OS env 우선순위(D-129 실측: OS env > `.encenv` > `.env`)
때문에 **주입이 조용히 무시되는 경우가 실재한다** — 이 장치가 없으면 "효과 없음"으로 오독한다.

## 5. 트랙 B — 리포트 생성기 (산출물 ②)

### 5.1 입력·출력

```
입력 : results/bench/<run_id>/raw.jsonl  (+ 이전 run들 — 회귀 비교용)
출력 : results/bench/<run_id>/report.md     사람이 읽는 정본
       results/bench/<run_id>/report.html   표·차트 포함(선택 · G-8)
       results/bench/<run_id>/summary.json  트랙 C의 입력
```

### 5.2 리포트 구성 (섹션 순서 고정)

1. **실행 요약** — run_id·커밋·기간·arm 수·유효/INVALID·총 LLM 호출·총 토큰
2. **측정 노이즈 상한(S1)** — 기준선 반복 간 EX 편차와 지연 편차. **이 절이 맨 앞에 온다.**
   이후 모든 차이는 이 값과 대비해 읽어야 하기 때문이다.
3. **축별 주효과(S2)** — 축마다 한 행:
   | 축 | 값 | ΔEX (95% CI) | Δp50 지연 | Δp95 지연 | ΔLLM 호출 | Δ토큰 | 판정 |
   판정은 `유의(+)` · `유의(−)` · **`판정 불가(underpowered)`** · `무효(INVALID arm)` 넷 중 하나.
4. **교호작용(S3)** — 쌍별 표. 주효과 합과 실제 차이의 괴리를 명시.
5. **Pareto 전선** — 정확도 vs 지연 vs 비용 3축. 지배당하는 arm은 접어둔다.
6. **목표치 대조** — `docs/29` 목표(단순 ≤10s·복합 ≤30s·문서 ≤60s·라우팅 ≤5s) 대비 arm별 달성률.
7. **노드별 지연 분해** — 효과가 큰 축에 한해, 어느 노드의 `elapsed_ms`가 움직였는지. **기전 설명 없는 효과는
   신뢰하지 않는다**는 원칙의 장치다.
8. **INVALID 사유 목록** — 버린 arm과 이유(조용한 강등·주입 무시·타임아웃). **비우지 않는다.**
9. **재현 명령** — 이 리포트를 다시 만드는 정확한 명령줄.

### 5.3 통계 처리 (과소·과대 주장 금지)

- 정확도: **쌍체 McNemar 검정** + Wilson 신뢰구간. 표본이 부족하면 p값 대신 `판정 불가`.
- 지연: 분포가 치우치므로 평균 t검정이 아니라 **부트스트랩 신뢰구간**(건별 쌍 차이 재표본).
- 다중비교: 축이 12~18개이므로 **Benjamini–Hochberg** 보정을 적용하고, 보정 전/후를 둘 다 표기한다.
- **효과 크기를 항상 함께 적는다.** "유의하지만 0.5%p"는 운영 판단에서 무의미하다.

### 5.4 설정 건강 보고서 + 전건 커버리지 장부 *(v2 신설 · "전체 설정 파일" 요건의 산출물)*

| 3 | 값역 표(L2) | 필드별 허용 범위와 **실제로 거부된 값**. `ValidationError` 원문 | 낮 |
| 4 | 가림 목록(L3) | OS env·`.encenv`가 `.env`를 덮고 있는 키. **"바꿨는데 안 바뀜"의 원인 목록** | **높음** |
| 5 | 노브 환상 후보(L4) | 동작 불변 키 + `UNCONSUMED_KEYS` 대조표(§3.5.4) | 중 |
| 6 | 등급 제안 | A 환경결속 / B 운영레버 / C 내부상수급(§6.3) 초안 배정 | — |
| 7 | 전건 커버리지 요약 | 아래 장부의 집계 | — |

#### 5.4.2 전건 커버리지 장부 — **미측정을 숨기지 않는다**

335필드 **전건**이 한 줄씩 들어간다. 이 장부가 *"전체 설정 파일을 테스트했다"* 의 증거이자,
동시에 *"어디까지만 했는지"* 의 정직한 고백이다.

| 키 | 그룹 | 타입 | L1 | L2 | L3 | L4 | L5 | 등급 | 미측정 사유 |
|---|---|---|---|---|---|---|---|---|---|
| `TEXT2SQL_CANDIDATE_COUNT` | text2sql | int | ✅ | ✅ | ✅ | ✅ | ✅ X2 | B | — |
| `OBS_TRACE_RETENTION_DAYS` | observability | int | ✅ | ✅ | ✅ | ⚪ | ⚪ | C | 보존 정책 — 질의 경로 무관(F1 제외) |
| `NOISE_FLAPPING_ENABLED` | noise_gate | bool | ✅ | ✅ | ✅ | ✅ | ⚪ | C | 알람 파이프라인 — 별도 벤치마크(G-4) |
| `LLM_FABRIX_API_KEY` | llm | secret | ✅ | ⚪ | ✅ | ⚪ | ⚪ | A | 시크릿 — 값 미취급 |

기호: ✅ 검증됨 · ❌ 실패(조치 필요) · ⚪ **미측정 + 사유 필수** · ⏭ 해당 없음

> **규칙: ⚪에 사유가 비어 있으면 리포트 생성이 실패한다.** 침묵 제외 금지 원칙의 기계적 강제다.
> 이 한 줄이 *"전체를 테스트했다"* 가 빈말이 되는 것을 막는 유일한 장치다.

#### 5.4.3 CI 게이트로 쓸 수 있다 (선택 · G-9)

L1·L3는 초 단위이고 LLM을 부르지 않아 **평소 게이트로 상시 실행**할 수 있다.

```bash
python -m scripts.bench --quick --ci     # L1·L3만. 고아 키·가림·타입 충돌이 생기면 exit 1
```

`.env.example`에 키를 추가하고 `config.py`에 안 넣는(혹은 그 반대) 드리프트를 **커밋 시점에** 잡는다.
D-129가 카탈로그를 SSOT로 만든 뒤에도 `GROUP_ORDER` 미등재로 UI에서 그룹이 통째로 탈락한 전례가 있다
(D-184 부기 — 카운트 테스트가 실패 상태로 방치돼 있었다). 그 유형을 자동으로 막는다.

### 5.5 리포트가 결론을 낸다 — 개발자는 통계를 해석하지 않는다 *(v2 · §0.4 요건)*

각 표의 마지막 칸은 숫자가 아니라 **문장**이다. 판정 어휘는 다섯 개로 고정한다.

| 판정 | 뜻 | 트리거 조건 |
|---|---|---|
| **채택 권고** | 기준선보다 낫고 부작용이 목표치 안 | 효과가 노이즈 상한 초과 + 보정 후 유의 + 목표치 위반 없음 |
| **조건부 권고** | 한 지표는 좋아지고 다른 지표는 나빠짐 | Pareto 비지배이나 트레이드오프 존재 → **무엇과 무엇을 맞바꾸는지 문장으로 명시** |
| **기각** | 기준선보다 나쁨 | 유의하게 악화 |
| **차이 없음** | 효과가 노이즈 상한 이하 | → 처분 규칙 6조 대상(§6.2) |
| **판정 불가** | 검정력 부족 또는 arm 무효 | → **성능 근거 없음. 정적 규칙으로 판정** |

**리포트 맨 앞 "한 눈에" 블록**(개발자가 그대로 전달할 수 있는 형태):

```
run 20260911-01 · 커밋 9e73cc9(clean) · 폐쇄망 FabriX · 소요 11h20m
설정 건강 : 즉시 조치 2건(가림 키 TEXT2SQL_SELECTION · 고아 키 OBS_LEGACY_DUMP)
성능      : 채택 권고 3 · 조건부 1 · 차이 없음 7 · 판정 불가 2 · 무효 arm 1
권고 요약 : 후보 수 3 채택(+9%p 정확도 / +2.1s) · 스키마 캐시 redis 유지 · 2단 라우팅 기각
다음 할 일: proposals/ 폴더를 설계자에게 전달 (자동 반영 없음)
```

**`다음 할 일` 줄이 항상 있다.** 개발자가 *"그래서 뭘 하죠"* 를 묻지 않게 하는 것이 이 블록의 목적이다.

## 6. 트랙 C — 최적화 제안기 (산출물 ③)

### 6.1 원칙 — 제안까지만, 적용은 사람이

`optimize.py`는 **`.env`·`config.py`를 수정하지 않는다.** 산출물은 세 가지 문서다.

| 산출물 | 내용 | 소비처 |
|---|---|---|
| `recommended.env.diff` | 기준선 대비 권고 설정 **diff 형식 제안** | 운영자가 검토 후 손으로 반영 |
| `knob_disposition.md` | 노브별 처분 제안 표 (존치/상수화/기한부/삭제) + **근거** | `plans/70` P1 입력 · `docs/flag_audit.md` 갱신 |
| `d161_evidence.md` | 삭제·상수화 제안 노브마다 **D-161 4항 실측 자동 수집** | 폐기 제안의 필수 첨부 |

**자동 적용을 하지 않는 이유**: 환경변수 삭제는 D-161이 정의한 *폐기 제안*이고, 4항 실측 첨부 없는 폐기 제안은
반려된다. 자동 반영은 그 반려 절차를 우회하게 된다. 또한 `.env`는 git 미추적이라 자동 수정은 복구 근거가 남지 않는다.

### 6.2 노브 처분 규칙 — D-162 §6의 5조에 **6조를 더한다**

기존 5조(`docs/flag_audit.md`)는 위에서부터 먼저 맞는 것을 적용한다. 본 계획은 그 **앞에** 한 조를 넣는다.

| # | 조건 | 판정 | 신설 여부 |
|---|---|---|---|
| **0** | **벤치마크에서 유의한 성능 효과(정확도 또는 지연 또는 비용)** | **존치 + 권고값 명시** | **신설(D-211)** |
| 1 | 프로덕션 참조 0건 | 기한부 | 기존 |
| 2 | `.env` 실제값이 코드 기본값과 다름 | 존치(상수화 금지) | 기존 |
| 3 | 프로덕션 참조 3건 이상 | 존치 | 기존 |
| 4 | 참조 1~2건 · 기본값 ON | 상수화 | 기존 |
| 5 | 참조 1~2건 · 기본값 OFF | 기한부 | 기존 |
| **6** | **벤치마크에서 효과가 노이즈 상한 이하 + 규칙 2~3으로 "존치"** | **"존치하되 운영자 비노출"**(§6.3 등급 C) | **신설(D-211)** |

**규칙 0을 맨 위에 두는 이유**: 규칙 2가 `.env`에 값이 있다는 이유만으로 존치를 강제하는데, 그 값이 **성능에
무해하다는 측정이 있으면** 존치의 근거가 "누군가 켜뒀다"뿐이다. 규칙 0과 6은 그 경우를 갈라준다.

**규칙 6이 "삭제"가 아니라 "비노출"인 이유**: 효과 없음은 삭제 근거가 못 된다 — 측정하지 않은 워크로드에서
효과가 있을 수 있고(우리 워크로드는 질의 경로 중심이다), 안전·감사 목적 노브는 성능 효과가 0인 것이 정상이다.

### 6.3 간소화의 실물 — 노브 3등급 + 프로파일

**"151개를 줄인다"의 실행 가능한 정의**는 삭제 수가 아니라 **운영자가 보는 수**다.

| 등급 | 정의 | 목표 수 | 노출 |
|---|---|---:|---|
| **A. 환경 결속** | 그 설치에서 반드시 정해야 함(접속 정보·활성 DB·프로바이더) | 15~25 | `.env` 상단 · 웹UI 기본 화면 |
| **B. 운영 레버** | 벤치마크에서 효과가 확인돼 **권고값과 함께** 제공 | 10~15 | `.env` · 웹UI · **권고값 주석 필수** |
| **C. 내부 상수급** | 효과 없음 또는 안전·감사 목적. 기본값 사용 | 나머지 | `.env.example`에서 **접기** · 웹UI 고급 섹션 |

**프로파일 프리셋**(G-6에서 채택 여부 확정):
`config/bench/profiles.yaml`이 정의한 검증된 조합을 `.env.example`에 **주석 블록으로** 제공한다.
예: `# --- 프로파일: 폐쇄망 운영(정확도 우선) --- ` 아래에 등급 B 키의 권고값만 나열.

> **주의(D-162)**: *"플래그 부채를 정리하면서 플래그를 늘리는 것은 자기모순"*이다.
> 따라서 **`CONFIG_PROFILE` 같은 신규 설정 키는 만들지 않는다**. 프로파일은 문서·주석·웹UI 프리셋 버튼으로만
> 존재하고, 실체는 여전히 개별 env 키다. 이 제약을 뒤집으려면 G-6에서 사용자 확정이 필요하다.

### 6.4 D-161 4항 실측 자동 수집

`d161_evidence.md`는 삭제·상수화 후보마다 네 항을 **코드로** 채운다.

| 항 | 수집 방법 |
|---|---|
| ① 운영 설정 실제값 | `.env`·`.encenv` 파싱(카탈로그의 alias 우선) — **코드 기본값이 아니라** |
| ② 런타임 가용성 | 관련 패키지 `importlib.metadata` 조회 · 관련 엔드포인트 설정 유무 |
| ③ 최근 개발 활동 | `git log -1 -S'<키>' -- <참조파일들>` + **`git merge-base --is-ancestor`로 현 브랜치 소속 확인** |
| ④ 역방향 의존 | 워드 경계 grep(`-w`)으로 참조 파일 전수 — `.venv` 제외(flag_audit 측정 오염 1번 사례) |

**`.venv` 제외를 기본값으로 넣는다.** `docs/flag_audit.md`가 기록한 실사례: 벤더 venv 오염이 `trace_enabled`를
52건(실제 5건)으로 부풀렸다.

### 6.5 리포트 → 처분 결정 파이프라인 *(v3 신설 · "레포트를 어떻게 분석하나")*

리포트가 나온 뒤 노브 하나하나를 어느 처분으로 보낼지는 **순서가 정해진 결정 절차**다.
`optimize.py`가 이 절차를 코드로 실행하고, 사람은 그 결과를 검토한다.

#### 6.5.1 입력 신호 — 리포트에서 뽑아 쓰는 것

| 출처 | 신호 | 값역 |
|---|---|---|
| L1 | 정합 상태 | `정상` · `고아 키` · `누락 키` · `타입 충돌` · `설명 부재` |
| L2 | 값역·기동 | `전 값 성공` · `일부 거부` · `기본값도 실패` |
| L3 | 주입 실효 | `실효` · **`가림`**(OS env·`.encenv`가 덮음) |
| L4 | 소비 실증 | `변함` · `불변` · `미검사` |
| L5 | 성능 판정 | `채택 권고` · `조건부` · `기각` · `차이 없음` · `판정 불가` · `측정 안 함` |
| 정적 | 참조 수 · `.env` 실제값 · 생성 경과일 | `flag_audit` 방식 재수집 |

#### 6.5.2 결정 절차 — 위에서부터 먼저 맞는 것을 적용한다

**0단계(간소화가 아니라 결함 수정)가 맨 앞에 온다.** 깨진 설정을 안고 간소화를 논하면
"줄였더니 안 된다"가 된다.

| 순 | 조건 | 처분 | 성격 |
|---:|---|---|---|
| **0-a** | L2 = `기본값도 실패` | **즉시 수정** — 기동 불가 결함 | 결함 |
| **0-b** | L1 = `고아 키`(파일에만 있음) | **파일에서 제거** — 코드가 읽지 않는다 | 결함 |
| **0-c** | L1 = `누락 키`(코드에만 있음) | **`.env.example`에 등재** | 결함 |
| **0-d** | L3 = `가림` | **즉시 조치 + 축에서 제외** — 이 키는 측정 자체가 불가 | 결함 |
| **1** | L4 = `불변` **AND** 참조 0건 | **삭제 제안**(D-161 4항 첨부 · §6.4) | 간소화 |
| **2** | L4 = `불변` **AND** 참조 1~2 **AND** 기본값 ON | **상수화 제안** | 간소화 |
| **3** | L5 = `채택 권고` | **기본값을 권고값으로 변경** + **등급 B** + 권고값 주석 | 최적화 |
| **4** | L5 = `조건부` | **등급 B 유지 + 트레이드오프 문장 병기** — 기본값은 바꾸지 않는다 | 최적화 |
| **5** | L5 = `기각` | **기본값 유지 + "권장하지 않음" 주석** | 최적화 |
| **6** | L5 = `차이 없음` **AND** 참조 3건 이상 | **등급 C 강등**(존치·비노출 — 처분 규칙 6조) | 간소화 |
| **7** | L5 = `판정 불가` | **보류** — 정적 규칙(1~5조)으로 폴백, 재측정 대기 목록에 등재 | 보류 |
| **8** | L5 = `측정 안 함`(축 밖) | **등급 C 기본 배정** + L1~L4 결과만 반영 | 간소화 |
| **9** | `.env` 실제값 ≠ 코드 기본값 **AND** 위 어디에도 안 걸림 | **존치**(규칙 2 — 살아있는 레버) | 존치 |

**규칙 1·2가 L5보다 위에 있는 이유**: 동작이 변하지 않는 키는 성능을 볼 것도 없다.
반대로 **규칙 6이 규칙 1보다 아래인 이유**: 성능 차이가 없어도 참조가 많으면 그 코드가 실제로
그 값을 읽고 있다는 뜻이라 삭제가 아니라 비노출이 맞다.

#### 6.5.3 처분별 산출 형식

각 처분은 `proposals/knob_disposition.md`에 한 행으로 쌓이고, **실행 가능한 형태**를 함께 낸다.

| 처분 | 함께 내는 것 | 반영 단계(§6.6) |
|---|---|---|
| 즉시 수정(0-a~0-d) | 수정할 파일·줄·전후 값 | **R0** |
| 삭제 제안 | `d161_evidence.md` 4항 + 제거 대상 파일 목록 + 그 값을 단언하는 **테스트 목록** | R4 |
| 상수화 제안 | 남길 상수값 + 제거할 분기 위치 + 테스트 목록 | R4 |
| 기본값 변경 | `config.py` 전후 값 + **마이그레이션 필요 여부**(§6.7) | R3 |
| 등급 배정 | A/B/C + `.env.example` 배치 위치 | R1·R2 |
| 보류 | 재측정에 필요한 워크로드 규모(검정력 역산) | — |

### 6.6 간소화 실행 — 위험도 순 5단계 롤아웃 R0~R4 *(v3 신설)*

> **기호 주의**: §3.3의 실험 설계 단계(S0 기준선·S1 무결성·S2 OFAT·S3 교호작용·S4 확인)와 구분하려고
> 롤아웃은 **R**을 쓴다. S는 *측정하는 순서*, R은 *바꾸는 순서*다.

**한 번에 다 바꾸지 않는다.** 되돌리기 쉬운 것부터, 런타임 위험이 없는 것부터 간다.

| 단계 | 바꾸는 것 | 런타임 위험 | 되돌리기 | 체감 간소화 기여 | 승인 |
|---|---|---|---|---|---|
| **R0 결함 수정** | 고아 키 제거 · 누락 키 등재 · 가림 해소 · 기동 실패 값 교정 | **0**(오히려 복구) | 1커밋 | — | 낮음 |
| **R1 문서 재편** | `.env.example` 3등급 재배치 · C등급 접기 · **권고값 주석** · 프로파일 주석 블록 | **0** — 런타임 무영향 | `git revert` | **큼** | 낮음 |
| **R2 노출 재편** | 웹UI 기본/고급 분리 · 카탈로그 등급 메타 · 미소비 뱃지 갱신 | **0** — 값 불변 | 1커밋 | **큼** | 낮음 |
| **R3 기본값 변경** | 코드 기본값을 권고값으로 | **중** — 미명시 설치의 동작이 바뀐다 | 1커밋 + `.env` 명시로 무력화 | 중 | 중간 |
| **R4 삭제·상수화** | env 키 제거 · 분기 제거 · 테스트 갱신 | **높음** | 어려움 | 작음 | **높음** · D-161 4항 |

#### ★ 이 표가 말하는 것 — 체감 간소화의 대부분은 무위험 구간에서 나온다

*"설정하기 너무 어렵다"* 는 **운영자가 보는 수**의 문제다. R1·R2는 런타임을 전혀 건드리지 않으면서
그 수를 줄인다. 반대로 R4(삭제)는 위험이 가장 크면서 운영자 체감에는 거의 기여하지 않는다 —
이미 접혀서 안 보이던 것이 사라질 뿐이다.

→ **권고: R0~R2를 먼저 완주하고, R3·R4는 별건으로 판단한다.** R4는 본 계획의 산출물이 아니라
`plans/70` P1의 입력이다(§13).

#### 6.6.1 단계별 커밋 규율

- **처분 1건 = 커밋 1건**(R3·R4). `docs/flag_audit.md`가 이미 *"플래그당 1커밋"* 규율을 쓴다.
- 커밋 메시지에 **근거 run_id와 처분 규칙 번호**를 적는다: `config(bench): X2 기본값 n1→n3 (run 20260911-01 · 규칙 3)`
- R1·R2는 묶어도 된다(런타임 무영향).

### 6.7 회귀 방어 — R3·R4가 조용히 동작을 바꾸지 않게 *(v3 신설)*

#### 6.7.1 R3(기본값 변경)의 진짜 위험

`.env`에 명시되지 않은 키는 코드 기본값을 쓴다. 그 기본값을 바꾸면 **이미 배포된 설치의 동작이
말없이 바뀐다.** 폐쇄망에 여러 설치가 있으면 어느 설치가 영향받는지도 알기 어렵다.

**방어: 기본값을 바꾸기 전에 현재 기본값을 `.env`에 박는다.**

```
① 마이그레이션 생성   현재 실효값을 그대로 .env에 명시하는 블록을 만든다(값 변화 0)
② 배포·확인           설치들이 그 블록을 반영. 이 시점에 동작 변화 0
③ 코드 기본값 변경     .env가 명시하고 있으므로 기존 설치는 불변, 신규 설치만 새 기본값
```

`optimize.py`는 R3 제안마다 **①의 블록을 함께 생성**한다(`proposals/migration_pin.env`).
이 블록 없이 기본값을 바꾸는 제안은 내지 않는다.

#### 6.7.2 비트 동일성 가드 (기존 관행 재사용)

이 저장소는 이미 *"OFF 골든 + sha256 동일"* 방식을 쓴다(D-134 · D-128). 그대로 쓴다.

| 대상 | 가드 | 기존 자산 |
|---|---|---|
| 프롬프트 렌더 | 변경 전후 sha256 동일 | `tests/test_semantic_routing/test_prompt_byte_identity.py` · `tests/test_prompt_render_matrix.py` |
| 생성 SQL | 골든 스냅샷 동일 | `tests/text2sql/test_semantic_golden.py` |
| 카탈로그 | 그룹 집합·필드 집합 등가 | `tests/test_api/test_settings_catalog.py:204-205` |
| 경로 대칭 | 단일/멀티 동일 | `tests/test_nodes/test_path_parity.py` |

**R1·R2는 이 가드가 전부 그린이어야 한다** — 문서·노출만 바꾸는 단계에서 렌더 해시가 움직이면
그건 문서 변경이 아니라 동작 변경이다.

#### 6.7.3 R4(삭제)의 테스트 연쇄

Known Mistakes가 기록한 함정: *"결정적 상수·매트릭스 값 변경 시 그 값을 단언하는 테스트를 repo 전체
grep으로 일괄 갱신. 기존 테스트가 버그를 정답으로 굳혔는지도 점검."*

→ 삭제·상수화 제안에는 **그 키를 단언하는 테스트 목록**을 반드시 붙인다(§6.5.3). 목록이 비어 있으면
"테스트가 없다"가 아니라 **"수집에 실패했다"로 간주하고 제안을 보류**한다.

또한 **카운트 단언은 낡는다** — `test_settings_catalog.py`가 스스로 *"이 숫자 단언은 본질적으로
취약하다"* 고 적어둔 그 지점이다. 키를 지우면 335가 깨지므로 같은 커밋에서 갱신한다.

### 6.8 정량 목표와 완료 판정 *(v3 신설)*

*"간소화했다"* 를 느낌이 아니라 숫자로 판정한다. **줄이는 대상은 코드 노브 수가 아니라 운영자가
보는 수**다(§6.6 ★).

| 지표 | 현재(실측 2026-09-11) | 목표 | 측정 방법 |
|---|---:|---:|---|
| `.env.example` **기본 노출** 키 | 216 | **≤ 45** | 접기(C등급) 밖 키 수 |
| 신규 설치가 **반드시 채우는** 키 | 미정(빈 값 17개는 하한) | **≤ 25** | §6.8.1 시나리오 검증 |
| 웹UI **기본 화면** 항목 | 335 | **≤ 45** | 고급 섹션 밖 항목 수 |
| `.env` 현재 등재 키 | 151 | 강제하지 않음 | 기존 설치는 그대로 동작해야 한다 |
| 카탈로그 필드(코드 노브) | 335 | **목표로 삼지 않음** | 삭제는 결과이지 목표가 아니다(§13) |

**마지막 두 행이 중요하다.** 기존 `.env` 151키를 강제로 줄이면 배포된 설치가 깨진다.
간소화는 *"새로 설정하는 사람이 보는 것"* 을 줄이는 것이지 기존 파일을 정리하는 것이 아니다.

#### 6.8.1 완료 판정 — 신규 설치 시나리오

가장 직접적인 수용 시험이다. **빈 `.env`에서 시작한다.**

```
1. .env를 비운다(빈 파일)
2. .env.example의 A등급 블록만 복사해 값을 채운다
3. python -m scripts.bench --preflight   → 전 항목 통과해야 한다
4. python -m scripts.bench --sweep --scale smoke 의 워크로드 20건 → 기준선과 동등한 성공률
```

3·4가 통과하면 *"A등급만 채우면 동작한다"* 가 실증된다. 이것이 **간소화 완료의 정의**다.
실패하면 그 키는 A등급으로 승격되어야 한다 — 즉 이 시나리오가 **등급 배정의 최종 심판**이다.

#### 6.8.2 재측정 루프 — 간소화가 성능을 깨지 않았는지

R3 적용 후 반드시 한 번 돌린다.

```bash
python -m scripts.bench --sweep --scale smoke --compare results/bench/<직전 run>
```

리포트가 회귀 비교표를 낸다(§5.1). **기준선 대비 유의한 악화가 있으면 그 R3 커밋을 되돌린다.**
되돌림 판단도 리포트의 판정 어휘(§5.5)로 나오므로 사람이 통계를 읽지 않는다.

(가림 목록)와 고아 키가 드러난다 — 사용자가 말한 *"설정하기 너무 어렵다"* 의 즉효 처방에 가장 가깝다.

**B5를 마지막 LLM 미호출 Wave로 둔 이유**: 단일 진입은 T1~B4가 다 있어야 감쌀 것이 생긴다. 다만 B5 이전에도
각 모듈은 개별 실행이 가능하므로(「실행 가이드 ② 상세」 A.5 "내부 명령") 개발 중에는 막히지 않는다.

## 13. 이 계획이 하지 않는 것

- **환경변수를 삭제하지 않는다.** 삭제 제안서까지가 범위다 — 실행(R4)은 `plans/70` P1 소관이다(G-12).
  본 계획이 직접 수행하는 간소화는 **R0 결함 수정 · R1 문서 재편 · R2 노출 재편**이며, 셋 다 런타임 위험 0이다.
- **기존 `.env` 151키를 줄이지 않는다.** 배포된 설치가 깨진다. 줄이는 대상은 *새로 설정하는 사람이 보는 수*다(§6.8).
- **`src/`를 수정하지 않는다.** 벤치마크는 운영 경로 밖이다. 단 B7에서 `.env.example`·웹UI 노출 등급은 바꾼다.
- **알람 파이프라인의 성능을 측정하지 않는다**(G-4 (a) 권고 시) — 다만 **설정 검증(L1~L4)은 포함**한다(§3.5.5).
  성능 벤치마크는 워크로드 성격이 달라 별도 계획이 필요하다.
- **`sre_agent` 설정을 다루지 않는다** — 별도 venv·별도 프로세스라 본 하네스의 격리 모델 밖이다(§3.5.5).
- **내부망 면제를 외부 경로로 확대하지 않는다** — 승인 불요는 `LLM_PROVIDER=fabrix`에만 적용되고,
  외부 프로바이더에서는 D-127이 그대로 산다(§4.4 · v5).
- **개발자에게 판단을 요구하지 않는다** — 통계 해석·축 선별·재개 여부는 전부 코드 몫이다(§0.4). 반대로
  **제안서를 자동 반영하지도 않는다** — 그것은 설계자의 판단이다.
- **LLM 프롬프트를 튜닝하지 않는다.** 축은 설정이지 프롬프트가 아니다.
- **HITL 경로의 지연을 측정하지 않는다**(X18) — 사람 응답 시간이 섞여 재현 불가.
