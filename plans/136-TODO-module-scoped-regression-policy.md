## 2. 정책 (D-303)

1. **기본 = 모듈 단위.** 코드를 구현하거나 교정한 뒤에는 바꾼 모듈과 관련된 테스트만 돌린다. 범위는 §3의 선택 규칙으로 정하고, 결과는 모듈별로 나눠 보고한다.
2. **전체 회귀는 사용자가 요청할 때만 돌린다.** 계획 완료·Wave 종료·커밋 직전에도 자동으로 돌리지 않는다. 에이전트가 전체가 필요하다고 판단하면(공용 계약 변경·대규모 이동 등) 실행하지 않고 이유를 적어 제안한다. **(v1.1)** 도구가 §3.1 조건으로 필요를 판정하면 `[전체 회귀 권고]` 블록을 내고, 에이전트는 그 블록을 사용자 보고에 그대로 옮긴다. 권고는 실패가 아니라 종료 코드에 영향이 없다. 도구를 못 쓰는 수동 절차에서도 같은 조건으로 판단해 권고한다.
3. **병렬이 기본이다.** 본체는 xdist 워커로, 독립 패키지(apm_gateway·mcp_server·sre_agent)는 별도 프로세스로 동시에 돌린다. 병렬로 돌릴 수 없는 테스트만 `@pytest.mark.serial`로 표시해 따로 직렬 실행한다. 선택 건수가 적으면 워커 기동 비용이 더 크므로 직렬로 돈다 — 임계는 W1 실측으로 **정적 테스트 함수 100건**으로 확정했다(초기값 300 · §11).
4. **정적 게이트는 매번 돌린다.** `arch_check --ci`·`overfit_check --ci`(합계 5초). ruff·mypy는 **바꾼 파일만** 검사하고, 위반이 이번 diff 줄에 걸린 것만 신규로 본다(worktree 전체 대조는 하지 않는다).
5. **실패가 나면 실패한 테스트만 재대조한다.** 세션 시작 커밋의 격리 사본에서 실패 ID만 다시 돌려 「원래 실패 / 이번 변경 탓 / 새 테스트」로 판정한다. 기준선 전체를 다시 돌리지 않는다.
6. **교정 라운드에서는** 실패했던 테스트와 그 모듈 선택분만 다시 돌린다.
7. **보고 문구에 범위를 적는다.** 모듈 단위 결과를 「회귀 0」처럼 전체 결과로 쓰지 않는다. 형식: *"모듈 단위 회귀 — 대상 모듈 3 · 테스트 412건 통과 · 정적 게이트 통과 · 전체 미실행"*.
8. **LLM·하네스 검증은 바꾸지 않는다.** MLX는 대표 소수 1회(기존 정책), 내부망 측정은 사용자 몫이다. 시나리오·벤치·매뉴얼 캡처는 회귀에 자동으로 넣지 않는다. 매뉴얼은 D-255대로 하되, 매뉴얼·화면 파일을 바꾸면 `tests/test_manual`이 §3 규칙 ③으로 선택된다.

## 3. 모듈 단위 선택 규칙

**입력**: 세션 시작 커밋 이후 바뀐 파일(커밋분 + 작업 트리 + 추적되지 않은 새 파일). `--files`로 내가 바꾼 파일만 줄 수도 있다(병행 세션 변경을 빼고 싶을 때).

| # | 바뀐 것 | 선택되는 테스트 |
|---|---|---|
| ① | 테스트 파일 | 그 파일 |
| ② | Python 모듈(`src`·`noise_gate`·`scripts`) | 그 모듈을 **직접 import**하는 테스트 파일. 함수 안의 import, `patch("src.x.y")`·`import_module("src.x")`처럼 문자열로 적은 모듈 경로도 포함한다 |
| ③ | Python이 아닌 파일(`config/*.yaml`·`src/static/*`·`testdata/*`·`scripts/manual/*`) | 그 파일의 경로나 파일명을 문자열로 적은 테스트 파일 |
| ④ | 독립 패키지(`apm_gateway`·`mcp_server`·`sre_agent`) 안의 파일 | 그 패키지의 테스트 전체. mcp_server 2초·sre_agent 16초라 패키지 단위가 가장 단순하다. apm_gateway(직렬 113초)는 xdist 병렬로 돈다 |
| ⑤ | (항상) | 저장소 전역 가드 — 소스 트리를 통째로 훑는 테스트에 `@pytest.mark.repo_guard`를 달아 항상 넣는다(W2 확정 — 6노드 · §11) |
| ⑥ | 위 결과가 비었을 때 | 「선택된 테스트 없음」을 보고하고, 바뀐 파일이 속한 테스트 폴더를 돌린다 |

**왜 「직접 import」인가 — 최근 커밋 24건(2026-09-15 이후 `src`·`noise_gate`를 바꾼 커밋)으로 실측**

| 선택 깊이 | 커밋당 선택 비율(테스트 건수 기준) 중앙값 | p75 | 최대 |
|---|---|---|---|
| 전이 import 전부 | 57.9% | 63.3% | 73.2% |
| 2단계까지 | 51.8% | 56.6% | 70.9% |
| 1단계까지 | 41.2% | 51.9% | 67.4% |
| **직접 import (채택)** | **12.9%** | **28.2%** | **54.5%** |

- 모듈 하나만 바꿨을 때 직접 import 선택은 중앙값 **0.4%**(p90 3.1%)다.
- 전이 import는 `src.graph`·앱 조립을 import하는 통합 테스트가 거의 모든 모듈에 걸려 전체의 절반을 넘는다. 이것으로는 「모듈 단위」가 성립하지 않는다.
- **과거에 좁은 검증이 놓친 두 사례는 둘 다 직접 import로 잡힌다.**
  - D-176 검증 정정: 놓친 `tests/test_nodes/test_multi_db_executor_body.py`·`test_multi_db_failure_audit.py`는 수정 모듈 `src.nodes.multi_db_executor`를 직접 import한다(`:17`·`:13`).
  - `docs/18:347`: 놓친 `tests/test_orchestration/test_plan123_disclosures.py`는 수정 모듈 `src.domain.time_spec`을 **함수 안에서** import한다(`:327`). 그래서 규칙 ②가 함수 안의 import까지 보게 했다.
  - 두 사례 모두 사람이 「수정 모듈의 테스트 폴더」를 고르다가 빠뜨렸다. 선택을 사람이 아니라 import 관계로 정하면 이 유형은 구조적으로 막힌다.
- **남는 위험**: 중간 모듈을 거쳐서만 닿는 테스트는 빠진다. 공개 함수의 시그니처나 반환 형태를 바꿨다면 `--wide`(1단계 확장)로 넓힌다. 그래도 놓친 회귀는 사용자가 요청하는 전체 회귀가 잡는다. 놓친 사례가 나오면 `docs/18`에 기록하고, 그 사례를 근거로 규칙을 보강한다(근거 없는 규칙 추가 금지).

### 3.1 전체 회귀 권고 조건 (v1.1 — 요청 ③)

도구가 아래 조건 중 하나라도 걸리면 출력 끝(마지막 범위 줄 바로 앞)에 블록을 낸다. 판정은 결정적이다(그래프·AST·git만 쓴다). 권고는 종료 코드에 영향이 없고 `--plan`에서도 나온다. `--full` 실행에서는 내지 않는다.

```
[전체 회귀 권고] 사유: <조건별 사유>
  → 사용자가 요청하면: python scripts/regress.py --full
```

| # | 조건 | 임계·판정 |
|---|---|---|
| 1 | 테스트 기반 파일 변경 | 루트 `pyproject.toml`·`uv.lock`·`pytest.ini`·`setup.cfg`·`tox.ini`·루트 conftest 3종. 독립 패키지의 pyproject·conftest는 제외 — 규칙 ④가 그 패키지 전체를 돈다 |
| 2 | 허브 모듈 변경 | 바꾼 모듈에 **전이 import**로 닿는 테스트가 전체의 **85% 이상**(정적 테스트 함수 수 기준 · 그래프로 매번 계산 · 하드코딩 목록 없음). 현재 해당: `src`·`src.config`·`src.utils` 등 |
| 3 | 공개 시그니처·반환 형태를 깨는 변경 | `--base` 버전과 AST 비교 — 공개 심볼 삭제 · 매개변수 삭제·이름·순서·종류 변경 · 기본값 제거 · 기본값 없는 새 매개변수 · 반환 주석 변경. 기본값 있는 매개변수 추가·새 심볼 추가는 세지 않는다. 걸리면 `--wide`도 자동 적용 |
| 4 | Python 모듈 이동·삭제 | `git diff --name-status`의 R·D(테스트가 아닌 `.py`) |
| 5 | 직접 import 선택 비율 | 선택이 전체의 **40% 이상** — 전체와 차이가 작다 |

**임계 보정**: 최근 커밋 24건(§3 표와 같은 집합) 재생에서 허브 임계 0.50이면 권고가 16/24(67%)로 거의 항상 떠 무의미했다. 0.85에서 **5/24(21%)**다. 사유 분포(중복 포함): 허브 5 · 직접 비율 3 · 테스트 기반 1 · 이동·삭제 1 · 시그니처 1. 0.90이면 조건 2가 사실상 `src/__init__.py`에만 걸려 죽은 조건이 된다(커밋별 표는 §11).

## 4. 병렬 실행

- **도입**: `pytest-xdist`를 `dev` extra에 추가한다. 루트 venv에는 W1에서 설치한다. 이번 실측은 scratch 폴더에만 설치해 공유 venv를 건드리지 않았다.
- **본체**: `-n auto`로 돌리되 워커는 최대 8개로 제한한다. 병행 세션과 MLX 서버가 CPU를 함께 쓰는 맥북이라 코어 10개를 모두 쓰지 않는다.
- **직렬 분리**: 병렬로 돌릴 수 없는 테스트는 두 번 나눠 돌린다. 먼저 `-m "not serial" -n N`, 다음 `-m serial`. 이번 실측에서 대상은 0건이었다. 새로 생기면 마커로 피하기 전에 원인(전역 상태 미원복 등)부터 고친다 — `tests/conftest.py`의 `_restore_sql_file_logger_globals` 선례(2026-09-21)처럼.
- **패키지 동시 실행**: 선택된 패키지(본체 · apm_gateway · mcp_server · sre_agent 자체 venv)를 별도 프로세스로 동시에 띄운다. 각자 cwd와 venv로 돌고 서로 import하지 않는다(D-139 경계). 본체와 apm_gateway는 각자 xdist 워커를 쓰고, 두 쪽 워커 합이 8을 넘지 않게 나눈다.
- **공유 자원**: 컨테이너 DB(5433·5434·3307 등)를 쓰는 테스트는 읽기 전용이라 동시 접속해도 문제가 없다. 고정 경로에 쓰는 테스트는 기존 conftest 원복 장치가 막는다. 위반이 드러나면 위의 직렬 분리 규칙대로 처리한다.

## 5. 실패 귀속 자동화

손으로 하던 기준선 대조를 **실패분만** 자동으로 한다.

1. 작업 트리에서 실패·에러가 난 테스트 ID만 모은다(`tail`로 자르지 않고 파일로 저장).
2. `git worktree add --detach <scratch>/regress-<pid> <base>`로 격리 사본을 만든다. `<base>`는 세션 시작 커밋이다(`--base` · 생략하면 `HEAD`를 쓰고, 병행 세션이 커밋했으면 틀릴 수 있다고 경고한다).
3. 사본에 `.env`·`.encenv`를 **심링크**하고 `PYTHONPATH=<사본>`으로 같은 명령을 돌린다. 각각 `docs/18:305`와 `:284`·`:312`의 재발을 막는다.
4. 판정은 셋 중 하나다.
   - 사본에서도 실패 → **원래 실패**
   - 사본에서 통과 → **이번 변경 탓**(내 변경 또는 병행 세션 변경)
   - 사본에 그 테스트가 없음 → **새 테스트 실패**
5. 사본을 지우고(`git worktree remove --force` · 자기 경로만), 판정표를 출력한다.

**종료 코드**: 「이번 변경 탓」이나 「새 테스트 실패」가 있으면 1, 원래 실패뿐이면 0.

## 6. 명령

```bash
python scripts/regress.py                     # 기본: 모듈 단위 · 병렬 · 정적 게이트 · 실패 귀속
python scripts/regress.py --files src/a.py …  # 내가 바꾼 파일만 기준으로
python scripts/regress.py --base <sha>        # 세션 시작 커밋 지정(변경 목록·실패 귀속 기준)
python scripts/regress.py --wide              # 공개 시그니처를 바꿨을 때 — 1단계 확장
python scripts/regress.py --plan              # 무엇을 돌릴지 목록만 출력(실행 안 함)
python scripts/regress.py --full              # 사용자가 요청할 때만 — 전 패키지 전체 · 병렬
```

출력은 다섯 덩어리다(v1.1 — ④ 추가).
1. 모듈별 표(모듈 → 선택 테스트 파일 수·건수 → 통과·실패)
2. 실패 귀속 판정표
3. 정적 게이트 결과
4. `[전체 회귀 권고]` 블록(§3.1 조건에 걸릴 때만)
5. 마지막 한 줄 범위(`범위: 모듈 단위 — 전체 미실행` · `범위: 전체(사용자 요청)` · `범위: 계획만 — 실행 안 함`)

실행 산출물(로그·junit·`failed_ids.txt`·`summary.txt`)은 `logs/regress/<시각>-<pid>/`(gitignore)에 남는다. `Makefile`의 `make regress`는 기본 명령, `make test`는 `--full`이다.

### 6.1 도구를 쓸 수 없을 때(대체 절차 — v1.1에서 「도구 전 수동 절차」를 바꿈)

1. 바꾼 모듈마다 직접 import하는 테스트를 찾는다: `grep -rlE "(from|import) src\.<패키지>\.<모듈>\b|['\"]src\.<패키지>\.<모듈>['\".]" tests noise_gate/tests`. `from src.<패키지> import <모듈>` 형태도 grep한다.
2. 찾은 파일과 바꾼 테스트 파일을 한 번의 `pytest`로 돌린다(100건 이상이면 `-n 8`).
3. 독립 패키지를 바꿨으면 그 패키지 테스트를 따로 돌린다.

5. 실패가 나면 그 ID만 세션 시작 커밋 worktree에서 다시 돌린다(§5의 2~4).
6. §3.1 조건을 손으로 판단해 하나라도 걸리면 같은 형식의 `[전체 회귀 권고]` 블록을 보고에 적는다.
7. 보고에 범위를 적는다(정책 ⑦).
