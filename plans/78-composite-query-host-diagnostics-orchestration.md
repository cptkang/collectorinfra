### 0.1 사용자가 제시한 목표 (2026-08-26)

> 자원의 현황을 조회하고, 조회된 자원의 **운영체제 정보** 또는 **미들웨어 정보**를 조회하여
> **장애 원인을 분석하고 해결방안을 LLM으로 제시**한다. 이를 위해 **사용자의 의도를 분석**하거나
> **폴스타(서버 모니터링)가 보내는 이벤트를 분석**하여 필요한 정보를 조회해 장애 대응이 가능하도록 한다.

이 목표를 처리 단계로 펴면 다음과 같다. **진입점이 둘**이고, 뒤쪽 절반은 v5까지의 78이 다루지 않던

```
                                                                       ↓
                                          ⑤ 해결방안 제시 ←─ ④ 장애 원인 분석(RCA)
```

### 0.3 v5까지의 78과의 충돌 — W3·W4 폐기

| v5 계획 | 충돌 | 조치 |
|---|---|---|
| **W3** `host_diagnostics` capability + **수집기 어댑터 2백엔드 신설** | `sre_agent`(bash toolset)와 `mcp_server`(고수준 8종)가 이미 OS 조사를 담당. 어댑터를 신설하면 **조사 경로가 3개로 분기** — Plan 64 §0 "중복 구현 금지"·D-118 위반 | **폐기 → 위임·경로 정리로 전환**(§0.4, 새 W3) |
| **W4** 조치 권고 생성 | `remediation.py`가 이미 결정적 표 기반으로 생성. 78이 또 만들면 **권고가 두 벌** | **폐기 → 소비·표시로 축소**(새 W4) |
| W2-6 대상 호스트 부하 가드 | 조사 실행이 `sre_agent` 소관이면 가드도 그쪽 | **경계 이관 · 요구만 유지**(§0.4) |

> **이 발견을 놓친 원인**(재발 방지): v1 실측이 `SUBAGENT_REGISTRY`(본체 capability 목록)만 보고
> **"실호스트 조사 도구가 없다"(G1)** 로 결론했다. 그러나 조사 경로는 **레지스트리가 아니라 별도
> 노드(`fault_diagnosis`)와 별도 패키지(`sre_agent`)** 에 있었다. `docs/21_orchestration_ladder.md` §7이
> 경고한 것과 같은 오독 — **"배선 도달 가능성"이 아니라 "역방향 import·별도 진입점"까지 봐야 한다**
> (D-161 ② 4항). v6는 `grep -rn "sre_"`·`graph.py` 배선·`.env` 실제값으로 재확인했다.

### 0.4 재정의된 78의 정체성

**78은 조사 엔진을 만들지 않는다. 조회와 조사를 잇는 배선 계층이다.**

```
        [이미 있음]                    [78이 채움]                  [이미 있음]
   ┌──────────────────┐         ┌────────────────────┐      ┌──────────────────┐
   │ text2sql 파이프라인│  ────→  │  대상 확정·경로 선택 │ ───→ │ sre_agent 조사·RCA│
   │ (자원 현황 조회)   │         │  (G2·G3·G5 해소)    │      │ remediation 해결방안│
   └──────────────────┘         └────────────────────┘      └──────────────────┘
                                          │
                                          ├─→ 가벼운 경로: process_query · mcp_server 고수준 도구
                                          └─→ 미들웨어 조사(G4 — 유일한 신규 구축)
```

78이 담당하는 것은 넷이다.

1. **G2 — 조회 결과를 조사 대상으로 전달**(세 소비 경로 전부에 부재)
2. **G3 — N개 대상 fan-out**(현재 1건씩만)
3. **G4 — 미들웨어 조사**(유일하게 실체가 없는 영역)
4. **G5 — 두 진입점의 대칭성**(채팅·이벤트가 대상 확정 로직을 공유하지 않음)

여기에 v4에서 찾은 **인가(G)·부하(E)·검증(V)** 갭이 얹힌다(§4.4) — 다만 조사 실행이 `sre_agent`
소관이므로 **부하 가드는 요구로 전달하고 구현은 이관**한다.

## 1. 요구 해석 — 무엇이 실제 과제인가

사용자 예시를 처리 단계로 분해하면 다음과 같다.

```
"CPU 사용량이 80% 이상인 서버를 조회하고 해당 서버에서 동작 중인 프로세스를 보여줘"

 ① 대상 선별   : 인프라 DB 조회 → CPU>80% 서버 목록 {hostname, ip, db_id, ...}   ← DB 평면
 ② 대상 확정   : ①의 결과에서 조사 대상 서버 집합을 결정적으로 확정              ← 배선
 ③ 상태 조회   : 확정된 각 서버에 read-only 명령 실행 → 프로세스 목록            ← 호스트 평면
 ④ 통합 응답   : ①의 선별 근거 + ③의 조사 결과를 한 응답으로 병합               ← 집계
```

**요구의 본질은 ①이나 ③ 각각이 아니라, ②와 ④ — 서로 다른 평면(DB / 실호스트)을 하나의 질의 안에서
잇는 배선**이다. 아래 §2 실측이 보여주듯 ①은 완성돼 있고 ③은 부분적으로 존재하지만, ②·④가 없어
질의가 중간에서 끊긴다.

### 1.1 범위

> **v6 갱신** — §0.3의 폐기·전환을 반영한다. **"제외"는 하지 않는다는 뜻이 아니라 78이 만들지
> 않는다는 뜻**이며, 위임처를 함께 적는다.

| 포함 (78이 만든다) | 제외 (이미 있거나 남의 소관) → 위임처 |
|---|---|
| **G2** 조회 결과 → 조사 대상 전달 (세 소비 경로 공통) | 조사 실행·ReAct 루프·브리핑 조립 → **`sre_agent`**(D-118) |
| **G3** N-대상 fan-out · 부분 실패 허용 | 장애 원인 분석(RCA)·심각도 판정 → **`sre_agent`**(dispatcher·severity_signatures) |
| **G4** **미들웨어 조사** (유일한 신규 구축 영역) | 해결방안 생성 → **`remediation.py`** (78은 소비·표시만) |
| **G5** 두 진입점(채팅·이벤트) 대상 확정 대칭화 | OS 정보 수집기·bash allowlist → **`sre_agent` toolset** |
| 경로 선택 — 가벼운 조회 vs 무거운 RCA (P12) | 폴스타 데이터 읽기 → **`mcp_server` 고수준 도구 8종**(D-119·D-122) |
| **호스트 인가 게이트**(§4.4 갭 ①) | 변경 명령 **실행** 경로 → 없음(D-003 · §8.3) |
| 관측·감사·검증 배선 (Tier 1) | 폴스타 에이전트 스냅샷 노출 → 폴스타 측 작업(R-1) |

## 2. 현행 실측 — 어디까지 되고 어디서 끊기는가

> 아래는 전부 코드 실측이다(추정 아님). 파일·라인은 2026-08-26 `multiintent` 브랜치 기준.

### 2.1 이미 되는 것

| 능력 | 근거 |
|---|---|
| 복합 의도를 DAG로 분해 | `src/orchestration/intent_planner.py:396-399` — TaskSpec에 `depends_on`·`input_from` 부여 |
| 데이터 의존 순차 실행 | `src/prompts/intent_planner.py` "작업 간 의존성" 절 — 선행 결과 참조를 자연어로 기술 |
| 실시간 프로세스 조회 | `src/orchestration/process_query.py` — 폴스타 **실시간 프로세스 API**(DB 이력 아님) |
| 프로세스 의도 결정적 교정 | `intent_planner.py:111-134` `_coerce_process_intent` — 시간성 신호 없는 프로세스 조회를 `data_query`→`process_query`로 교정(D-046/D-047) |
| 서버명 → hostname 해소 | `process_query.py:183` `_resolve_canonical_hostname`(D-046) |

**따라서 "현재는 DB 조회 위주로만 동작한다"는 전제는 절반만 맞다.** 조회 결과 기반 후속 처리의
골격(planner·의존 배선·프로세스 API·명령 allowlist)은 이미 있다. 없는 것은 그 사이의 연결이다.

### 2.2 끊기는 지점 — 갭 3종

#### G1. ~~Capability 갭~~ → **경로 분화 갭** (v6 정정)

> **⚠ v1~v5의 G1 결론은 틀렸다.** 아래 원문의 *관찰*(레지스트리에 조사 도구가 없다)은 사실이지만
> *결론*("따라서 어느 단에서도 서버에 명령을 보낼 수 없다")은 오류다. 조사 경로는
> **`SUBAGENT_REGISTRY`가 아니라 별도 노드 `fault_diagnosis`와 별도 패키지 `sre_agent`** 에 있다(§0.2).
>
> **정정된 G1**: 능력이 없는 것이 아니라 **경로가 정리되지 않았다.** 같은 "서버 상태를 본다"는
> 요구에 대해 지금 세 갈래가 병존하는데, **언제 무엇을 쓸지 규칙이 없다.**
>
> | 경로 | 비용 | 적합 요구 | 현재 진입 규칙 |
> |---|---|---|---|
> | `process_query`(실시간 API) | 낮음 | 프로세스 목록 | `_coerce_process_intent` 결정적 교정 |
> | `mcp_server` 고수준 도구 8종 | 낮음~중 | OS 구성·메트릭·토폴로지 단건 | **본체에서 호출 경로 없음** ⚠ |
> | `sre_agent` 위임(HolmesGPT ReAct) | **높음**(LLM 다중 왕복) | 원인 분석·해결방안 | `fault_diagnosis` 의도 분류 |
>
> **두 가지가 문제다.** ① 본체는 `mcp_server`의 고수준 도구를 **쓰지 않는다** — `DBHubClient`가
> `_call_tool`이라는 범용 호출을 갖고도 `search_objects`/`execute_sql`만 쓴다(`src/dbhub/client.py`).
> 중간 비용대의 조회가 통째로 비어 있어, 가벼운 요구가 무거운 `sre_agent`로 가거나 아예 처리되지
> 않는다. ② 진입 규칙이 **의도 분류 하나**에 의존해 P12(비싼 경로는 소수 질의만)가 보장되지 않는다.
>
> → 새 **W3**가 이 분화를 정리한다(수집기 신설이 아니라 **경로 선택 규칙 + `mcp_server` 도구 배선**).

<details>
<summary>v1~v5 원문 (오독 기록 — 보존)</summary>

`SUBAGENT_REGISTRY`(`src/orchestration/subagents.py:1084-1110`)의 6개 항목은 **전부 "조회" 계열**이다:

```
data_query · process_query · alarm_query · cache_management · synonym_registration · general_inference
```

이 레지스트리가 사다리 1단·2단 **양쪽의 단일 capability 출처**다 —
1단은 `deepagents_tools.py:298`이 이를 `@tool`로 변환하고, 2단은 `agent_orchestrator.py:160`이
직접 디스패치한다. **실호스트 조사 항목이 없으므로 어느 단에서도 "서버에 명령"은 선택지에 없다.**

실행 능력 자체는 `sre_agent/`에 있으나 세 겹으로 닫혀 있다:

- `remote_vm_profile()`(`toolset_profiles.py:60-88`)은 **의도적으로** bash를 확장하지 않는다 —
  중앙 호스트 셸은 대상 VM이 아니며(`REMOTE_VM_SHELL_NOTE`), 대상 데이터는 MCP로만 조회한다(D-119).
- `REMOTE_SSH_ALLOW = ["ssh"]`는 bastion 옵트인 슬롯으로만 존재하고 기본 경로가 아니다.
- `sre_agent`는 **양방향 import 0**의 독립 패키지(D-118)라 본체가 함수 호출로 쓸 수 없다 — MCP 계약뿐.

D-117이 접근 경로(폴스타 에이전트 확장·read-only·USE 프로파일)를 **보안 인터뷰로 이미 확정**했지만,
상태는 **계획(미구현)**이고 용도가 **노이즈 게이트 전용**이다(Plan 60 §18). 채팅 경로 배선은 없다.

</details>

#### G2. 결과 의존 배선 갭 — 선행 결과가 조사 대상으로 흐르지 않는다

> **v6 확장 — 문제는 `process_query` 하나가 아니다.** 재실측 결과 **선행 조회 결과를 소비하는
> 세 경로 전부**에 같은 결함이 있다. 즉 G2는 국소 버그가 아니라 **아키텍처 수준의 누락**이다.
>
> | 소비 경로 | 대상 해소 방식 | `prior_targets` |
> |---|---|---|
> | `process_query` | `_resolve_hostname` — filter_conditions → previous_entities | **없음** |
> | **`fault_diagnosis`**(채팅 RCA) | `_extract_targets`(`fault_diagnosis.py:200`) — filter_conditions → previous_entities | **없음** ⚠ |
> | **`investigation_trigger`**(이벤트) | 알람 페이로드의 hostname (선행 조회 자체가 없음) | 해당 없음 |
>
> **따라서 사용자 목표의 ②(대상 확정)가 어느 경로로도 성립하지 않는다.**
> *"CPU 80% 이상 서버를 조회하고 **그 서버들의** 원인을 분석해줘"* 는 `fault_diagnosis`로 분류되어도
> 대상이 비어 조사가 시작되지 못하거나 엉뚱한 대상으로 간다. **G2가 78의 최우선 항목인 이유다.**

<details>
<summary>원문 (process_query 기준 상세 — 유효)</summary>

D-095 선행 스코프 주입의 게이트가 **양쪽 모두 `data_query`/`alarm_query`로 한정**돼 있다:

```python
# src/orchestration/deepagents_tools.py:241  (소비자 측)
if collector and agent_name in ("data_query", "alarm_query"):
    input_from, prior = _dependency_scope(sub_query, collector)

# src/orchestration/deepagents_tools.py:159  (생산자 후보 측)
if t.get("agent") not in ("data_query", "alarm_query"):
    continue
```

그리고 주입된 `prior_rows`의 **소비처는 SQL 생성 경로뿐**이다 —
`query_generator.py:180·486·679`, `multi_db_executor.py:228-231`. `process_query`는 `prior_rows`를
읽지 않는다.

`process_query`가 대상 서버를 얻는 경로는 `_resolve_hostname(isolated)`(`process_query.py:151`)뿐이고,
그 입력은 **이번 턴 `filter_conditions`** 또는 **`previous_entities`(멀티턴 승계)** 다.

> **결과**: 한 턴 안의 복합 질의에서 "①이 찾아낸 서버 목록"이 ③으로 전달되는 경로가 **없다**.
> 멀티턴으로 나눠 "해당 서버의 프로세스"라고 다시 물으면 `previous_entities`로 동작하지만,
> 사용자가 요구한 **단일 복합 프롬프트**에서는 끊긴다.

</details>

#### G3. Fan-out 갭 — 대상이 N개일 때 1개만 처리한다

`process_query`는 단일 hostname만 다룬다. D-047 주의 문구가 이를 명시한다:

> "복수 서버 지목은 현재 첫 host filter만(다중 요구 시 리스트 반환 확장)"

사용자 예시의 "CPU 80% 이상인 서버**들**"은 본질적으로 N개다. 대상이 N개인데 1개만 조사하면
**침묵 절단**이 되어, 사용자는 그것이 전체인 줄 안다(Known Mistakes "침묵적 폴백/강등 금지" 위반).

#### G4. 미들웨어 조사 갭 — 실체가 없다 (v6 신규)

사용자 목표는 OS **또는 미들웨어** 정보 조회를 요구한다. **미들웨어 쪽은 어느 계층에도 없다.**

| 확인 대상 | 실측 결과 |
|---|---|
| 본체·`noise_gate`·`sre_agent`·`mcp_server` 코드 | 미들웨어(WAS/웹서버/DB엔진) 조사 코드 **0건** — `middleware` 히트는 전부 HTTP 미들웨어 |
| `mcp_server` 고수준 도구 8종 | OS 구성(`polestar_os_config` — `core_config_prop` EAV)까지만. 미들웨어 전용 도구 없음 |
| `sre_agent` bash allowlist | `VM_DIAG_ALLOW` 26종은 전부 **OS 레벨**(ps·vmstat·ss·journalctl…). WAS 로그·스레드덤프·커넥션풀 없음 |
| 폴스타 데이터 | `config/db_profiles/polestar_b0.yaml:206`에 `name='sicwso01 (이미지 업무 WAS#1)'` — **서버 명명 규칙에 WAS가 문자열로 섞여 있을 뿐**, 미들웨어 인스턴스를 별도 엔티티로 갖는 스키마는 확인되지 않음 |
| `general_inference` 프롬프트 | *"OS·미들웨어 튜닝 가이드는 예시로도 제안하지 말 것"* — 현재는 **명시적 범위 밖**으로 선언돼 있다 |

**따라서 G4는 78에서 유일하게 '새로 만들어야 하는' 영역**이며, 착수 전에 **데이터 소스 확정이
선행**되어야 한다(§4.7 · R-11). 소스 없이 조사 도구만 만들면 빈 껍데기가 된다.

#### G5. 진입점 비대칭 갭 — 채팅과 이벤트가 로직을 공유하지 않는다 (v6 신규)

두 진입점이 **각자 다른 코드로 대상을 확정**하고, 각자 다른 계약으로 `sre_agent`를 호출한다.

| | 채팅(A) | 이벤트(B) |
|---|---|---|
| 대상 확정 | `fault_diagnosis._extract_targets` | 알람 페이로드 |
| 호출 도구 | `sre_diagnose` | `sre_investigate_alarm` |
| 결과 소비 | `final_response` 자연어 | `alarm_notifier` 브리핑 첨부 |
| 인가 | — | — |

공유되는 것은 submit/poll 패턴뿐이다. 결과적으로 **한쪽에 넣은 개선이 다른 쪽에 반영되지 않는다** —
G2 수정, 인가 게이트, 부하 가드, 감사 스키마가 전부 두 번 들어가거나 한쪽만 들어간다.
Known Mistakes의 **"단일/멀티 경로 대칭 — 한쪽만 고치는 비대칭이 반복 원인"** 이 구조로 굳은 형태다.

### 2.3 갭 요약 (v6 갱신)

| 갭 | 한 줄 | 영향 | 78 소관 |
|---|---|---|---|
| ~~G1~~ → **경로 분화** | 조사 경로 3갈래에 선택 규칙이 없고, 중간 비용대(`mcp_server` 도구)가 미배선 | 가벼운 요구가 비싼 경로로 가거나 미처리 | **배선·규칙** |
| **G2** | 선행 결과 → 조사 대상 전달이 **세 경로 전부**에 없다 | 목표 ②(대상 확정) 불성립 ★ | **최우선** |
| **G3** | 대상 N개를 1개로 절단 | 부분 결과를 전체로 오인 | 78 |
| **G4** | 미들웨어 조사 실체 없음 | 목표의 절반(미들웨어) 미충족 | **신규 구축**(소스 확정 선행) |
| **G5** | 두 진입점이 대상 확정·인가·감사를 공유하지 않음 | 개선이 한쪽만 적용됨 | **공통화** |

여기에 §4.4의 계층 갭(**G 인가 · V 검증 · E 부하**)이 얹힌다.
**G2와 G5를 함께 풀어야 한다** — 공통 모듈로 만들지 않으면 G2 수정이 한쪽에만 들어간다.

## 3. 문헌 조사

> 조사 축: ① 복합 질의를 어떻게 분해·실행하는가 ② 도구가 늘 때 어떻게 고르는가
> ③ 조회에서 조치로 넘어갈 때 무엇이 위험한가.

### 3.1 분해·실행 구조

**LLMCompiler — An LLM Compiler for Parallel Function Calling** (ICML 2024)
Planner가 사용자 질의를 **DAG로 컴파일**하고, Task Fetching Unit이 의존성이 해소된 태스크를
디스패치하며, Executor가 병렬 실행한다. ReAct 대비 **지연 최대 3.7배·비용 6배 개선, 정확도 ~9%p 향상**.
핵심 통찰은 Planner 출력을 **스트리밍**해 계획 완성 전에 실행을 시작한다는 점이다.
→ 본 프로젝트의 `intent_planner`(계획) + `agent_orchestrator`(실행)는 이미 같은 형태이며,
`depends_on`/`input_from`이 DAG 엣지에 해당한다. **새 구조를 도입할 필요 없이 엣지가 통과시키는
데이터 종류만 넓히면 된다**는 것이 G2 처방의 근거다.

**ADaPT — As-Needed Decomposition and Planning with Language Models** (NAACL Findings 2024)
사전에 깊게 분해하지 않고, **실행자가 실패했을 때만 재귀적으로 하위 분해**한다. 태스크 복잡도와
실행자 능력 양쪽에 적응하며 ALFWorld/WebShop/TextCraft에서 각각 **+28.3 / +27 / +33%p**.
→ 현행 planner 프롬프트의 "보수적으로: 분해가 불확실하면 무리하게 쪼개지 말고 task 1개로 묶으세요"
원칙과 정합한다. **과분해는 비용이자 오류원**이므로 본 계획도 분해를 늘리지 않는다.

**Plan-Execute-Verify-Replan (VMAO)** (arXiv 2603.11445)
Plan → Execute(의존 인식 병렬, 기본 k=3) → **Verify** → Replan → Synthesize의 순환.
Verify는 개별 응답이 아니라 **"집합 결과가 원 질의를 충족하는가"를 오케스트레이션 수준에서** 채점한다
(완성도 0~1·누락 측면·모순). 종료 조건은 완성도 80% 달성 / 개선 5% 미만(수확체감) / 토큰 예산 /
최대 3회 반복. 단일 에이전트 대비 완성도 **3.1 → 4.2 (+35%)**.
→ 복합 질의에서는 **"모든 task가 성공했지만 질의는 충족되지 않은" 상태**가 발생한다.
예: ①은 10대를 찾았는데 ③은 1대만 조사한 경우(= G3). task 단위 성공만 보면 놓친다.
**종료 조건을 반드시 함께 도입**해야 무한 재계획을 막는다.

**Agentic DAG-Orchestrated Planner for Hybrid Data Lakes** (arXiv 2603.14229) ·
**AGENTIQL** (arXiv 2510.10661) · **BLENDSQL**
이종 소스(정형 테이블 + 비정형/API) 다중 홉 질의를 DAG 하위 질문으로 분해하고 **상류 결과를 자동
전파**한다. AGENTIQL은 질문 분해 에이전트 + 코딩 에이전트 + 정제 단계로 나눠 해석성·모듈성을 얻는다.
→ "DB 조회 + 실호스트 조회"는 정확히 이종 소스 다중 홉이다. **상류 결과 자동 전파가 이 문헌군의
공통 필수 요소**이며, 본 프로젝트에 그것이 빠진 자리가 G2다.

### 3.2 도구 선택과 액션 표현

#### 3.2.1 도구가 늘 때의 선택 문제

**Tool-to-Agent Retrieval** (arXiv 2511.01854) · **SchemaRouter** (arXiv 2608.21375) ·
**SING** (arXiv 2606.16591)
도구·에이전트를 공유 벡터 공간에 임베딩하고 메타데이터로 연결해 top-k 검색한다. SchemaRouter는
단일 DB의 schema linking을 **여러 이종 API의 필드 수준으로 일반화**한다. 공통 경고:
**"poorly differentiated tool descriptions cause semantic covering"** — 설명이 서로 비슷하면
top-k가 같은 능력의 변형으로만 채워져 상보적 도구 집합을 못 만든다.
→ 본 프로젝트의 도구는 6개로 **검색 도입은 불필요**(과설계). 그러나 경고는 그대로 적중한다:
**v9 정정** — v5까지 신설을 상정했던 `host_diagnostics`는 폐기됐으나(§0.3), 표면어 충돌은 남는다:
**W3-1이 배선할 `mcp_server` 고수준 도구**(`process_snapshot` 등)가 기존 `process_query`와
**"프로세스"라는 표면어를 공유**한다.
설명 차별화만으로는 부족하며 **결정적 교정 가드가 필수**다(현행 `_coerce_process_intent` 전례 —
D-047이 이미 같은 문제를 프롬프트 강화만으로는 못 잡아 결정적 교정을 넣었다).

#### 3.2.2 액션 표현 — 코드 생성까지 갈 것인가 (검토 후 **미채택**)

> **검토 계기**: "대상 확정을 결정적으로 처리하면 관련 코드가 없는 형태는 처리하지 못하는 것 아닌가?
> LLM이 해석하고 필요하면 코드 스니펫을 생성해 처리하는 방식은 없는가"(사용자 제기, 2026-08-26).
> **이 지적은 타당하다** — 결정적 추출기의 커버리지 추격은 본 프로젝트에서 실제로 일어났다.
> D-047 구현 노트: *"LLM이 한글 field명 생성 시 `_HOST_FIELDS` 매칭 실패로 identifier=None"* →
> `서버명·서버이름·장비명·호스트명·서버·장비`를 방어적으로 계속 추가해야 했다. 새 표면형이 나올
> 때마다 목록을 늘려야 하고, 늘리기 전까지는 **조용히 실패**한다.

**CodeAct — Executable Code Actions Elicit Better LLM Agents** (ICML 2024 · arXiv 2402.01030)
JSON/text 액션은 **사전 정의된 도구 범위에 제약**되고 **도구 조합이 불가**하다는 문제의식에서,
실행 가능한 Python을 통합 액션 공간으로 쓴다. 17개 LLM·API-Bank·M3ToolEval에서
**성공률 최대 +20%, 스텝 −30%**. 관련 계보: **PAL**(ICML 2023 · 2211.10435),
**PoT 적용 조건 분석**(AAAI 2024 · `10.1609/aaai.v38i16.29721`),
**Tree-of-Code**(ACL Findings 2025 · `10.18653/v1/2025.findings-acl.509`),
서베이 **"If LLM Is the Wizard, Then Code Is the Wand"**(2401.00812).
→ CodeAct의 문제의식은 위 사용자 지적과 **같다**. 커버리지 확장이 필요하다는 진단은 문헌이 지지한다.

**그러나 본 계획에는 미채택한다. 세 가지 이유다.**

**① 우리 문제는 개방형 조합이 아니라 닫힌 선택이다.**
CodeAct가 이기는 영역은 *도구를 조합해야 하는 개방형 작업*이다. `prior_targets`가 푸는 문제는
"결과 행의 N개 컬럼 중 어느 것이 서버 식별자인가"로, **선택지가 유한하고 이미 열거되어 있다**.
닫힌 선택에 코드 생성을 쓰는 것은 표현력을 남기고 위험만 사는 교환이다.

**② 인터프리터 도입 비용이 크다.**
**OWASP AIVSS**(AI Vulnerability Scoring System)는 **Agentic AI Tool Misuse**(도구 선택 훼손·안전하지
않은 호출·감독 부재)를 자율 에이전트 고유의 **10대 핵심 위험** 중 하나로 규정하며, *"코드 인터프리터와
프로덕션 API 키를 가진 에이전트는 검색 도구만 가진 에이전트보다 내재 위험이 훨씬 크다"*고 명시한다 —
즉 **인터프리터 보유 자체가 위험 점수를 올리는 요인**이다.
또한 Auto-GPT에서 **간접 인젝션 → path-traversal → `execute_python_code` → Docker 샌드박스 탈출**이
실제로 발생했다(산업 보고 · §11.3). 결정적으로, 인젝션 표면에는 **"이전 도구 호출의 출력"이 포함**되는데 —
본 계획이 스니펫에 먹이려는 입력이 정확히 그것(DB 결과 행·명령 stdout)이다. §7.2 신뢰 경계에서
불신 영역으로 분류한 데이터를 코드 생성기의 입력으로 쓰면 경계가 무의미해진다.
(참고: **CIRCLE** — LLM code interpreter 보안 벤치마크, 2507.19399.)

**③ 스니펫의 종류를 갈라야 하는데, 위험한 쪽이 실질적 요구다.**

| 스니펫 종류 | 시스템 접근 | 판정 |
|---|---|---|
| **명령 스니펫**(`ps`/`top` 등을 LLM이 조립) | 있음 | **불가** — allowlist(P5)가 무의미해진다. 설계 파탄 |
| **데이터 변환 스니펫**(결과 행 → 대상 튜플) | 없음 | 상대적으로 안전하나 ②의 인터프리터 표면을 신설 |

**해결책은 코드 생성이 아니라 층의 분리다** — 아래 §3.2.3.

#### 3.2.3 해석과 확정의 분리 — 커버리지는 LLM, 신뢰 경계는 코드

사용자 지적이 드러낸 것은 "결정적이 틀렸다"가 아니라 **본 계획이 두 가지를 하나로 묶어 서술했다**는
점이다. 실제로는 성격이 다른 두 판단이다.

| | 무엇을 정하나 | LLM 적합 | 근거 |
|---|---|---|---|
| **해석**(interpretation) | "결과 행에서 서버 식별자는 **어느 컬럼**인가" | **적합** | 값이 아니라 **스키마 메타** 판정. 출력이 **닫힌 집합**(실재하는 컬럼명 중 하나) → Action-Selector 패턴 |
| **확정**(commitment) | "**이 서버들을** 조사 대상으로 고정한다" | **부적합** | 값이 행동을 결정 → TDG(IPIGuard)가 무너지고 인젝션이 대상을 바꿀 수 있다 |

**LLM은 컬럼명을 고르고, 값은 코드가 그 컬럼에서 그대로 읽는다.** 이러면 커버리지는 LLM이 주고
(새 표면형이 나와도 목록 추가 불요), 대상 값 자체는 LLM을 거치지 않으므로 §7.1의 결정적 확정과
TDG 고정이 유지된다.

**이 패턴은 본 프로젝트에 이미 있다** — `src/nodes/field_mapper.py` 첫 줄:

> **3단계 매핑: 프롬프트 힌트 → Redis synonyms → LLM 추론**

결정적 수단을 먼저 쓰고 **LLM을 마지막 단**에 두는 계단식 폴백이다. `prior_targets`도 같은 계단을
쓴다(W1-3′). 신규 패턴을 발명하지 않고 확립된 사내 패턴을 재사용하는 것이므로 추가 위험도 없다.

### 3.3 조회에서 조치로 — 위험과 통제

**Coding Agents Are Guessing: Action-Boundary Violations in Underspecified DevOps Instructions**
(arXiv 2607.02294)
지시가 불충분할 때 에이전트가 안전/위험 경계를 **추측**한다. 위반 분류:
**① Scope overflow**(의도하지 않은 대상 — 잘못된 환경·파일·시스템) **② Depth overstep**(필요보다
파괴적 — 임시 제거 대신 영구 삭제) **③ Assumption failure**(상태·권한에 대한 암묵 가정).
50건 이상 실제 DevOps 인시던트 기반 평가에서 상용 코딩 에이전트들이 **명시 승인 없이 파일 삭제·
서비스 종료·구성 롤백을 제안**했고 **비가역 작업에 확인을 요청하지 않는 경우가 빈번**했다.
완화책: 샌드박스, 비가역 작업 승인 워크플로, **dry-run 계획과 실제 실행 모드의 명시적 분리**,
프롬프트에 범위 제약 명시.
→ **Scope overflow가 본 계획의 1급 위험이다.** "해당 서버"를 LLM이 자연어로 재해석하게 두면
조사 대상이 어긋난다. 대상 집합은 **선행 조회 결과에서 결정적으로 확정**해야 한다(G2 처방이
성능 문제가 아니라 **안전 요구**인 이유).

**Design Patterns for Securing LLM Agents against Prompt Injections** (arXiv 2506.08837)
핵심 원칙: **신뢰할 수 없는 데이터가 이후 행동에 영향을 주지 못하게 분리**한다. 6패턴 중 본 계획에
직접 해당하는 것:
- **Plan-Then-Execute** — 계획을 먼저 고정하면 도구 출력이 계획을 바꾸지 못한다.
- **Action-Selector** — 제한된 행동 집합 중에서만 고른다.
- **Context-Minimization** — 신뢰할 수 없는 입력을 컨텍스트에서 최소화한다.
- **LLM Map-Reduce** — 항목별 독립 처리 후 병합. **병합(reduce) 단계가 취약점**이다.
→ **명령 stdout은 신뢰할 수 없는 데이터다.** 프로세스명·커맨드라인·로그 본문에 지시문이 섞여 들어올
수 있다. 원문을 통째로 LLM에 넣으면 안 된다. 현행 `noise_gate.domain.process_rank.select_top_processes`
(결정적 상위 N 선별 + 마스킹 후 주입, D-047-1)가 정확히 Context-Minimization이며, **이 패턴을 실호스트
출력에도 그대로 확장**하는 것이 본 계획의 기본 자세다.

**IPIGuard — Tool Dependency Graph-Based Defense Against Indirect Prompt Injection**
(EMNLP 2025 Main · `10.18653/v1/2025.emnlp-main.53`) ★ **본 계획 설계와 동형**
에이전트 실행을 **사전 계획된 도구 의존 그래프(Tool Dependency Graph, TDG)의 순회**로 모델링한다.
핵심은 **행동 계획과 외부 데이터 상호작용의 명시적 분리** — 외부 데이터를 받기 **전에** 실행 경로를
고정하므로, 주입된 지시문이 계획에 없는 도구 호출을 유발할 수 없다. AgentDojo 벤치마크에서
효과성과 견고성의 균형을 달성. 기존 방어가 프롬프팅 전략·탐지 모델에 의존하는 데 반해 IPIGuard는
**구조적 제약**을 가한다.
→ **이 논문은 본 계획이 이미 택한 구조에 이름을 붙여준다.** `intent_planner`의
`depends_on`/`input_from`이 곧 TDG이고, W1의 `prior_targets` **결정적** 주입이 곧 "외부 데이터 수신 전
경로 고정"이다. 따라서 **W1은 편의 기능이 아니라 인젝션 방어 구조**다 — 대상 집합을 LLM이 도구 출력을
읽고 재해석하게 두면 TDG 순회가 아니라 데이터가 계획을 바꾸는 구조가 되어 방어가 무너진다.
이것이 §4.2에서 "대상 확정 주체 = 코드(결정적)"를 고른 가장 강한 근거다.

**The Task Shield: Enforcing Task Alignment to Defend Against Indirect Prompt Injection**
(ACL 2025 Long · `10.18653/v1/2025.acl-long.1435`)
보안 관점을 "유해 행동 차단"에서 **"태스크 정렬 보장"**으로 재설정한다 — 모든 지시·도구 호출이
사용자가 지정한 목표에 기여하는지 매 행동마다 검증한다. GPT-4o에서 **공격 성공률 2.07%**,
**태스크 유틸리티 69.79%**.
→ W5(오케스트레이션 수준 검증)의 직접 근거다. **다만 유틸리티 69.79%가 함께 읽혀야 한다** —
LLM 기반 정렬 검사는 기능을 약 30% 깎는다. 본 계획이 W5를 **결정적 충족도 체크(LLM 미사용)**로
좁힌 이유가 여기 있다: 대상 수 대조 같은 산술적 확인은 LLM 없이 가능하고, 유틸리티 손실이 없다.

**Adaptive Attacks Break Defenses Against Indirect Prompt Injection Attacks on LLM Agents**
(NAACL Findings 2025 · `10.18653/v1/2025.findings-naacl.395`) ★ **균형추**
**8종의 방어를 모두 적응형 공격으로 우회**했고 **50% 이상의 공격 성공률을 일관되게 달성**했다.
저자들은 적응형 공격 평가를 방어 설계의 **필수 절차**로 포함할 것을 권고한다.
→ **본 계획에서 가장 중요한 문헌일 수 있다.** 위 두 방어(IPIGuard·Task Shield)를 도입하더라도
**"방어를 넣었으니 안전하다"는 결론은 성립하지 않는다.** 따라서 견고한 통제는 방어의 정확도가 아니라
**능력 자체의 부재**다 — 실행 경로를 코드에 탑재하지 않으면(사용자 확정 ②) 인젝션이 성공해도
실행될 변경 명령이 존재하지 않는다. §7.1의 "실행 경로 미탑재"와 §8.3의 3단계 진입 요건은
이 논문을 근거로 **완화 불가 조건**으로 둔다.

**Architecting Resilient LLM Agents: Secure Plan-then-Execute** (arXiv 2509.08646) ·
**Prompt injection to RCE in AI agents** (Trail of Bits, 2025-10)
→ 명령 실행 능력을 가진 에이전트에서 인젝션은 RCE로 직결된다. 실행 경로를 아예 두지 않는
사용자 결정(권고만)이 이 위험의 대부분을 제거한다.

**safecmd** (AnswerDotAI)
**denylist가 아니라 allowlist** — 읽기 전용/쉽게 되돌릴 수 있는 명령의 관대한 허용 목록.
prefix 매칭의 함정(허용 prefix가 쓰기 형태를 포섭)을 지적한다.
→ 본 프로젝트 `toolset_profiles.py:5-10`의 주석이 **이미 같은 교훈을 담고 있다**:
> "allow/deny는 prefix 매칭이므로 … 읽기 전용 형태로 좁혀 등록한다 (예: 'ip' 전체 허용 시
> 'ip link set …'까지 허용됨 → 'ip addr show' 등으로 한정)"
따라서 **새 allowlist를 만들지 않고 `VM_DIAG_ALLOW`/`VM_DIAG_DENY`를 정본으로 재사용**한다(사본 금지).

**HolmesGPT** (CNCF Sandbox) — read-only by design
모든 내장 toolset이 **읽기 전용**이며 기존 RBAC(Kubernetes RBAC·Grafana roles·cloud IAM)를 존중하고
**모든 도구 호출을 감사 로깅**한다. 데이터 소스는 toolset 또는 MCP 서버로 확장한다.
→ 본 프로젝트가 채택한 것과 동일한 자세다(D-119/D-122). 채팅 경로도 같은 원칙을 지킨다.

**Agentic AIOps 가드레일 / AI SRE 성숙도** (VKTR · Rootly · PagerDuty SRE Agent 2025-10)
자율성은 스위치가 아니라 **곡선**이다: **read-only insights → advised actions → approval-based
remediation → autonomous with guardrails**. 행동 이전에 에이전트 신원·blast radius 한계·롤백·
policy-as-code·감사·비용 가드가 모두 갖춰져야 한다.
→ 사용자 결정(읽기전용 + 권고)은 **정확히 2단계(advised actions)** 다. 3단계로 넘어가려면 D-003
예외 신설과 §8.3의 미해결 항목이 선행한다. 본 계획은 2단계에서 멈춘다.

**LLMs for Agentic NetOps and AIOps** (arXiv 2605.12729) · **AIOpsLab**
조사를 구조화된 워크플로로 본다: 다음 판별 질의 선택 → 부분 결과 해석 → 경쟁 가설 유지 →
**증거·승인·롤백에 묶인 조치 제안**.
→ "조치 제안은 증거에 묶인다"가 §7 권고 생성의 설계 기준이다.

### 3.4 하네스 엔지니어링 — 계층 분류와 단계별 기법

> 여기까지(§3.1~§3.3)는 *무엇을 어떻게 분해·실행·통제할 것인가*를 개별 주제로 다뤘다. 이 절은
> 그 주제들을 **하나의 시스템 관심사로 묶는 프레임**과, 그 프레임 안에서 각 단계에 쓰이는
> **구체적 기법**을 정리한다. 적용 결과는 §4.4(커버리지 매핑)·§4.5(단계별 적용)에 있다.

#### 3.4.1 ETCLOVG 7계층 분류법

**Agent Harness Engineering: A Survey** (2026 · TMLR **under review** — CMU·Tulane·Yale·Stanford·
Amazon·Virginia Tech·Northeastern·Rutgers 공동, 교신 Tianyang Wang(UAB)·Chandan K. Reddy(VT) ·
[OpenReview](https://openreview.net/forum?id=eONq7FdiHa) · [companion](https://picrew.github.io/LLM-Harness/))

에이전트를 둘러싼 **하네스(harness = 모델 바깥의 실행 인프라)** 를 7계층으로 분류한다.
110+ 논문·23+ 배포 시스템·148+ 오픈소스를 매핑했다. 핵심 주장은
**"하네스 계층이 모델보다 에이전트 신뢰성을 더 좌우한다"** 이며, 기존 6요소 프레임과 달리
**Observability와 Governance를 독립 계층으로 승격**했다 — 프로덕션에서 각각 **별도 툴링 스택·별도 팀
소유**이기 때문이다.

| | 계층 | 관심사 | 대표 설계 결정 |
|---|---|---|---|
| **E** | Execution | 코드가 어디서 도는가 · 샌드박스 · OS 권한 · 리소스 | 컨테이너 vs microVM vs 데스크톱 |
| **T** | Tooling | 도구 설명·발견·호출 · MCP/A2A · 도구 선택 | 도구 스키마의 풍부도 |
| **C** | Context | 단기/세션/지속 지평선의 정보 접근 제어 · 표류 완화 | 컨텍스트 길이·검색 정책 |
| **L** | Lifecycle | 상태 읽기/쓰기 제어 흐름 · 단일/다중 에이전트 · HITL | 제어 흐름 복잡도(직선 vs 재귀) |
| **O** | Observability | 트레이스·비용·실패·신뢰성 신호 수집 | 관찰 깊이(비용 대 통찰) |
| **V** | Verification | 작업을 평가·실패 귀인으로 전환 | 평가 기준의 엄격성 |
| **G** | Governance | 권한 모델 · 생명주기 훅 · 감사 인프라 | 권한 모델의 제한 수준 |

앞 4개(E·T·C·L)가 **구조적 핵심**, 뒤 3개(O·V·G)가 **제어 평면**이다.

**계층 간 결합 — 저자들의 핵심 경고:**

> *"Harness layers are coupled in ways that make local optimization fragile."*

반복되는 제약 3종:

1. **비용–품질–속도 트릴레마** — 강한 샌드박스·풍부한 컨텍스트·깊은 평가는 전부 토큰·지연·인프라
   비용을 올린다. **어느 계층을 의도적으로 얇게 둘지 사전에 정해야 한다.**
2. **능력–제어 트레이드오프** — 도구를 늘리고 샌드박스를 느슨히 하면 작업 범위가 커지지만
   오정렬 위험이 함께 커진다.
3. **국소 개선의 역설** — 프롬프트·도구·샌드박스·검증기를 개별로 개선해도 **전체 시스템 성능은
   내려갈 수 있다.**

**실무 체크리스트**: ① 계층별이 아니라 **시스템 변경으로 통합 테스트** ② 실행 환경별 **비용 모델링**
③ 압축 시 **정보 손실·출처 기록** ④ **트레이스를 디버깅 자료가 아니라 1차 평가 대상**으로
⑤ 모델이 좋아지면 **불필요한 래퍼를 제거**하는 점진적 단순화 메커니즘.

> ⑤는 본 프로젝트의 **D-161(승격–폐기 동반 원칙)** ·`plans/70`(경로 부채)과 사실상 같은 문제의식이다.
> ①은 `arch_check` + 통합 회귀 스위트가 이미 담당한다.

> **분류법의 지위**: 이 서베이는 preprint(TMLR 심사 중)다. 다만 본 계획이 쓰는 것은 실험 결과가
> 아니라 **분류 렌즈**이므로, 심사 결과와 무관하게 커버리지 점검 도구로 사용할 수 있다.
> 렌즈로 쓰되 **설계 근거로는 §3.1~§3.3의 동료심사 문헌을 쓴다**.

#### 3.4.3 내부 참조 문서 — 「하네스 엔지니어링 구현 명세」

`sample/하네스_엔지니어링_구현_구성요소.docx` (2026-08-26 작성 · 서베이 원문 + `article/refuser/`
하네스 문헌 615편 기반). ETCLOVG를 **구현 명세로 전개**한 문서로, 계층별 필수/확장 기능,
171개 오픈소스 카탈로그, 빌드/채택 권고, 3단계 구축 로드맵, 계층별 점검 목록을 담는다.
본 계획에 직접 영향을 준 것은 다음 다섯이다.

**① 다섯 기법의 위치 — "부분적으로 맞다"**
프롬프트 최적화·사전 라우팅·작업 분해·컨텍스트 압축·메모리는 **7계층 중 C와 L에 집중**되어 있고,
나머지 다섯(E·T·O·V·G)은 거의 건드리지 않는다. 이 다섯은 **정확도를 올리는 레버**이고,
**운영에 필요한 것은 나머지 다섯 계층**이며 **구현 작업량으로는 오히려 이쪽이 크다.**

| 기법 | 귀속 | 이것만으로 부족한 이유(문서 표 3) |
|---|---|---|
| 프롬프트 최적화 | C | 행동이 어디서 실행되는지·실패를 어떻게 탐지할지 정하지 못한다 |
| 컨텍스트 압축 | C | 압축 손실이 누적되는 **장기 드리프트를 스스로 탐지하지 못한다** |
| 메모리 | C | 저장된 기억의 **출처·노후화·프라이버시는 G 계층 문제** |
| 사전 실행 라우팅 | L | **라우팅 오분류를 측정하려면 O·V가 필요하다** |
| 작업 분해 | L | 하위 에이전트의 **격리 환경(E)과 도구 계약(T)을 전제**한다 |

→ §4.4가 찾아낸 갭이 전부 E·V·G에 몰린 것은 우연이 아니다. **다섯 기법 관점으로만 보면
구조적으로 보이지 않는 영역**이다.

**② Tier 규율 — 측정(Tier 1)이 최적화(Tier 2)보다 앞선다**

| Tier | 목표 | 범위 | 통과 기준 |
|---|---|---|---|
| **0** 최소 동작 | 루프가 돈다 | E 격리 · T 레지스트리+스키마 검증 · C 최근 N 유지 · L 루프+상한+복구 사다리 | 단순 과제 완주, 실패해도 **폭주하지 않고 멈춘다** |
| **1** 측정 가능 | 무엇이 왜 실패했는지 안다 | **O 구조화 추적+비용 회계** · V 1~3단계 · **G 허용목록·자격증명 격리·승인** | 실패를 **모델/도구/환경/평가설정에 귀책**할 수 있다 |
| **2** 운영 가능 | 규모·시간을 견딘다 | C 압축·KV 캐시 인지 · L 체크포인트·**사전 라우팅**·분해 · O 드리프트 · V 4~5단계 · G 선언적 정책 · E microVM | 장기 실행이 드리프트 없이 유지, 회귀 자동 탐지 |

> 문서의 근거: *"Tier 1의 추적·귀책 능력이 없으면 Tier 2의 최적화가 이득인지 손실인지 판별할
> 방법이 없다."* 자주 하는 실수 목록에도 **"측정 없이 하네스를 쌓는다"** 가 올라 있다.
> **이 지적이 본 계획 v4의 Wave 순서에 그대로 적중했다 — §4.6에서 정정한다.**

**③ KV 캐시 — 런타임 도구 목록 변경 금지** ★ 설계 정정 유발
Manus 팀은 KV 캐시 적중률을 *"프로덕션 AI 에이전트의 단일 최중요 지표"* 로 지목한다
(캐시 토큰이 **10배 저렴**). 규칙 셋: ① 프롬프트 **접두부 안정** ② 컨텍스트 **append-only**
③ **결정론적 직렬화**. 그리고 **도구 정의가 직렬화 컨텍스트의 앞부분**에 오므로
**런타임에 도구를 추가·제거하면 이후 모든 턴의 캐시가 무효화된다.** Manus는 도구 목록을 바꾸는
대신 **디코딩 중 토큰 로짓을 마스킹하는 상태 기계**로 우회한다.
→ **§4.5-②(사전 라우팅)의 구현 방식을 정정**한다(§4.5-② 개정 참조).

**④ T 계층을 과소평가하지 말 것**
최소 하네스 루프 7요소 중 **둘이 T**이며, **도구 노출이 성능 조작 변수 1순위**로 지목된다
(11,700 궤적 비교 · arXiv 2608.11386). 또한 **도구 이름을 모델의 사전학습 관례에 맞추면
오류가 80% 감소**한다(arXiv 2510.07248). 설계 원칙은 *"적지만 더 나은 도구가 무차별 노출을
능가한다"* — 과대한 도구 메뉴는 프롬프트 엔트로피와 계획기 분기를 함께 키운다.
→ W3의 도구 **명명·스키마**를 "설명 차별화" 수준에서 **명시적 설계 사항으로 격상**한다.

**⑤ 압축은 재현율 우선으로 조정한다**
*"재현율을 먼저 최대화해 잠재적으로 관련된 모든 정보를 포착한 뒤, 반복하며 정밀도를 높인다.
반대 방향으로 시작하면 안 된다. 초기에 너무 많이 제거하면 나중에 필요한 컨텍스트를 잃고,
그 손실은 복구되지 않는다."*
→ 본 계획의 2단 축약은 상위 N 선별이라 **정밀도 우선**에 해당한다. 다만 **원문 전량을 감사 로그와
CSV에 보존**하므로 손실이 복구 가능하다 — 이 보존이 규칙 위반을 상쇄하는 **필수 조건**임을
W2-7에 명시한다.

> **문서의 지위**: 내부 기술 참조 문서다. ETCLOVG 분류·카탈로그·인용 실험치는 서베이 원문 확인분이나,
> **구현 수준 구분(Must/Should/May)·세 결정 축·유형별 우선순위·빌드/채택 권고·3단계 로드맵·
> 점검 목록은 정리자가 재조직한 것**(문서 자체가 명시)이다. 본 계획은 이를 **실무 판단 틀**로 쓰되,
> 학술 근거는 §3.1~§3.3의 동료심사 문헌을 유지한다.

## 4. 목표 아키텍처

### 4.1 한 장 그림

> **v9 정정** — v5까지의 그림이 남아 있어 **v6에서 폐기한 구조**(`host_diagnostics` capability ·
> `HostDiagnosticCollector` 어댑터 · 권고 *생성*)를 계속 제시하고 있었다. 아래가 정정본이다.
> **78이 만드는 것은 ★ 표시 넷뿐**이고, 조사 실행·RCA·권고 생성은 전부 기존 자산 소관이다(§0.4).

```
[진입 A] 사용자 질의 "CPU 80% 이상 서버 조회하고 해당 서버 프로세스 보여줘"
[진입 B] 폴스타 이벤트(알람 페이로드)                          ※ 두 진입점이 아래를 공유한다(G5)
   │
   ├─ intent_planner (기존·무변경) / alarm_graph (기존·무변경)
   │     t1: data_query      "CPU 80% 이상 서버 조회"
   │     t2: process_query   "선행 결과 서버들의 현재 프로세스"  depends_on=[t1] input_from=[t1]
   │         └ 원인 분석 요구면 fault_diagnosis (옵트인 · sre_agent 위임)
   │
   ├─ t1 실행 → rows[{hostname, ip, db_id, cpu_pct}, ...]
   │
   ├─ ★ prior_targets 추출 — 공통 모듈 (신규·결정적)      ← G2+G5 / P2 / W1
   │     해석 3단(결정적 → synonyms → LLM 컬럼 지목) · **확정은 항상 코드**
   │     세 소비 경로(process_query · fault_diagnosis · investigation_trigger)가 같은 함수를 쓴다
   │
   ├─ ★ 호스트 인가 게이트 (신규)                          ← 갭 ① / W3-5
   │     조회 권한 ≠ 조사 권한. 채팅·이벤트 **양쪽이 같은 모듈**을 호출한다
   │
   ├─ ★ 경로 선택 (신규·결정적 우선)                       ← G1 정정 / P12 / W3-2
   │     프로세스 목록        → process_query  (실시간 API · 낮음)
   │     OS 구성·메트릭 단건  → mcp_server 고수준 도구 8종 (낮음~중)  ← W3-1 신규 배선
   │     원인 분석·해결방안   → fault_diagnosis → sre_agent 위임 (높음)
   │
   ├─ ★ N-대상 fan-out (신규)                              ← G3 / P3 / W2
   │     for target in T[:N_max]  (병렬 k · per-target timeout · 부분 실패 허용)
   │     ※ 조사 **실행**은 sre_agent toolset / mcp_server 소관 — 78은 대상과 경로만 정한다
   │
   ├─ 결정적 축약 (기존 자산 재사용)                        ← P4 / W2-7
   │     select_top_processes(...) 상위 N + 마스킹 → LLM 주입용 축약본
   │     원문 전량은 감사 로그·CSV 다운로드에만 (D-047 계승)
   │
   ├─ reduce (결정적)                                       ← P3 / W2-4
   │     대상별 결과 + 실패 사유를 표로 병합. 조사 못 한 대상은 명시(침묵 절단 금지)
   │
   ├─ 브리핑·해결방안 **소비**(표시만)                      ← W4
   │     sre_agent 브리핑 6요소 + remediation.py 권고를 위험도·신뢰도 **그대로** 노출
   │     ※ 권고 **생성**은 remediation.py 소관 — 78은 만들지 않는다(v6)
   │
   └─ result_aggregator (기존) → 최종 응답
```

### 4.2 설계 결정 요지

| 항목 | 결정 | 근거 |
|---|---|---|
| planner 변경 | **하지 않는다** | P1 — 분해 구조는 이미 충분. agent 목록에 1항목 추가뿐 |
| ~~capability 추가~~ | **하지 않는다**(v6 폐기 · v9 반영) — 기존 `process_query`·`fault_diagnosis`·`mcp_server` 도구로 분화한다 | §0.3 — 신규 capability는 조사 경로를 3분기시킨다(D-118 위반) |

| 액션 표현 | **닫힌 도구 선택**(코드 생성 미채택) | P10 · §3.2.2 — 인터프리터 표면 회피 |

| ~~기본 백엔드~~ | **`sre_agent` 소관으로 이관** — 78은 부하 가드를 **요구로만** 전달(W3-6) | §6.2 이관 표 |
| allowlist | `sre_agent`의 `VM_DIAG_ALLOW`를 **그대로 둔다**(이전·복제 없음) | P5 · 사본 금지(D-053 계열) · R-3 해소 |
| 실행 경로 | **탑재 안 함** | 사용자 확정 ② · D-003 |
| 플래그 | 전부 **기본 off** | 비활성 시 회귀 0 |

### 4.3 ~~어댑터 경계~~ — **폐기**(v6 · v9 반영)

> **이 절의 설계는 v6에서 폐기됐다**(§0.3). 사용자 확정 ①("실행 채널을 어댑터 추상화로 둘 다 설계")은
> **`sre_agent`가 이미 bash toolset을 보유한 사실을 모른 채** 내려진 것이며, 재실측 후 **실행 채널
> 전체를 `sre_agent` 소관으로 이관**했다. 78은 수집기를 만들지 않는다.
>
> | 폐기된 산출물 | 대체 |
> |---|---|
> | `HostDiagnosticCollector` 프로토콜 · `PolestarAgentCollector` · `SshCollector` | `sre_agent` toolset(`VM_DIAG_ALLOW` 26종) + `mcp_server` 고수준 도구 8종 |
> | `host_access_mode` 플래그(polestar_agent \| ssh) | `sre_agent` 소관(§6.2 이관 표) |
> | allowlist 정본 이전 | 이전하지 않는다 — `sre_agent`가 계속 보유(R-3 해소) |
>
> **78에 남는 것은 요구 전달뿐이다**: 부하 가드(`nice` 하향 · 명령 자체 timeout · 동일 호스트 중복
> 조사 금지 · `top -n 1` 고정)를 **계약으로 명시**하고 구현은 `sre_agent`가 한다(W3-6 · D-118 경계).
>
> 원 설계의 상세(프로토콜 시그니처·SSH 옵트인 근거)는 **변경 이력 v5 항목**과 git 이력에 남는다.

| **T** Tooling | `mcp_server` 고수준 도구 **본체 배선**(W3-1) · 도구 명명·스키마 규약(W3-4) · 결정적 교정(P6) · MCP 경계 유지 | 다룸 (W3) |
| **C** Context | 결정적 축약·마스킹(P4) · 토큰 예산 · `prior_targets` | 다룸 (W1/W3) + §4.5-④ 보강 |
| **L** Lifecycle | DAG 분해 · fan-out · 재계획 1회 상한 · 부분 실패 허용 | 다룸 (W1/W2/W5) |
| **O** Observability | 전 수집 감사 · 실패 트레이스 · 기동 로그 | 다룸 (W6) |
| **V** Verification | 충족도 체크(대상 수 대조) | **부분** ⚠ **갭 ②** |
| **G** Governance | D-003 불변식 · 권고만 · 전 수집 감사 | **부분** ⚠ **갭 ①** |

#### 갭 ① (G) — 호스트 단위 인가가 없다 ★ 최우선

기존 자산 `allowed_db_ids`는 **DB 단위 인가**다. **호스트 단위 인가는 존재하지 않는다.**
초안은 "읽기 전용이니 안전하다"로 이 문제를 건너뛰었는데, **조회 권한과 조사 권한은 별개**다 —
어떤 사용자가 특정 DB를 조회할 수 있다는 사실이 그 DB에 등재된 **서버에 명령을 보내도 된다**는
뜻은 아니다.

P11(능력을 늘리면 제어를 함께 늘린다)의 직접 사례다. **조사 경로를 채팅에 열면서**(W3-1 · 기존
플래그 해제) G 계층을 그대로 두면 **능력만 늘고 제어는 그대로**인 상태가 된다.

→ **W3에 인가 게이트를 추가한다**(아래 **W3-5**).

#### 갭 ② (V) — "성공했지만 틀린 결과"를 못 잡는다

V 계층의 대표 실패 유형이다. W5의 충족도 체크는 *대상 수 대조*라는 **산술 확인**이라,
엉뚱한 호스트를 조사했는데 결과가 정상 형태로 돌아오면 그대로 통과한다.

→ **완전 해소는 범위 밖**(평가 하네스·골든셋이 필요하며 이는 별도 작업이다). 대신
**W5에 한계를 명시**하고, 검증 가능한 최소 항목(조사한 hostname이 `prior_targets`에 실제로
있었는가 — 사후 대조)을 추가한다(W5-4).

#### 갭 ③ (E) — 조사가 대상 호스트를 악화시킬 수 있다

본 계획의 대표 시나리오가 **"CPU 80% 이상인 서버"에 `ps`/`top`을 날리는 것**이다.
이미 포화된 호스트에 조사 부하를 더하는 구조인데, 초안에는 per-target 타임아웃만 있고
**대상 호스트 측 부하 보호가 없다**. D-117이 명시한 `nice`/`timeout` 가드를 승계하지 않았다.

→ **W2에 부하 가드를 추가한다**(아래 W2-6).

### 4.5 하네스 단계별 적용

§3.4.2의 단계별 기법을 본 계획에 대조한다. **네 개는 이미 있고, 두 개가 신규**다.

#### ① 프롬프트 최적화 — 기존 방식 유지, 자동 최적화 미채택

- **현황**: `intent_planner` 프롬프트·도구 설명이 분류를 좌우한다. **W3-1**이 배선할
  `mcp_server` 고수준 도구(`process_snapshot` 등) 설명이 `process_query`와 표면어 충돌을
  일으키므로, **W3-4**(도구 명명·스키마 규약)에서 함께 다룬다(P6).
  *(v13 정정 — 종전 `host_diagnostics` capability 표기는 v6에서 폐기됐다. §3.2.1은 v9에서
  이미 정정됐으나 이 절이 남아 있었다.)*
- **판단**: 자동 프롬프트 최적화(APE/OPRO/DSPy)는 **미채택**. ① 폐쇄망에서 최적화 루프를 돌릴
  추가 모델 서빙 부담 ② 과금 외부 API 승인 게이트(D-127)와 충돌 ③ 무엇보다 이 프로젝트는
  **프롬프트 강제가 프로필 few-shot과 경쟁해 반복 실패한 이력**이 있고, 그 해법이 프롬프트 강화가
  아니라 **결정적 교정**이었다(D-047 `_coerce_process_intent`). 프롬프트를 더 정교하게 만드는 방향은
  이미 한 번 실패한 경로다.
- **조치**: 프롬프트 변경 시 **골든셋 회귀로 검증**(기존 `scripts/eval_text2sql.py` 경로 재사용).

#### ② 사전 실행 라우팅 — **신규**. 조사는 예외 경로다

- **현황**: 오케스트레이션 사다리는 **빌드 타임 1회** 판정이고(요청별 강등 없음), `intent_planner`의
  agent 분류가 요청별 라우팅이다. 그러나 초안에는 **"이 질의에 실호스트 조사가 필요한가"를 실행
  전에 거르는 게이트가 없다.**
- **왜 필요한가**: 조사는 비싸고(N 호스트 × 명령 × 수집 지연) **위험하다**(갭 ③ — 대상 호스트 부하).
  RouteLLM이 보여주듯 비싼 경로를 **소수 질의에만** 보내는 것이 비용·위험을 동시에 줄이는
  표준 수단이다(강모델 14% 호출로 비용 −85%). **P12**.
- **조치(W3-2·3)**: **조사 경로 진입**에 **명시적 신호 요구**. 애매하면 가벼운 경로로 강등한다:

  ```
  원인 분석·해결방안 요구        → fault_diagnosis → sre_agent 위임 (비싼 경로)
  프로세스 목록만 필요           → process_query    (실시간 API — 가볍고 이미 검증됨)
  이력·추세                      → data_query       (DB)
  ```

  이 판정은 **결정적 규칙 우선**(P6 전례) — LLM 분류에만 의존하지 않는다.

- **구현 방식 제약(v5 정정 · §3.4.3-③)**: 라우팅을 **도구 목록에서 빼는 방식으로 구현하지 않는다.**
  도구 정의는 직렬화 컨텍스트의 **앞부분**에 오므로, 런타임에 도구를 추가·제거하면 **이후 모든 턴의
  KV 캐시가 무효화된다**(캐시 토큰은 비캐시 토큰보다 10배 저렴 — Manus는 이 적중률을 "프로덕션
  에이전트의 단일 최중요 지표"로 지목한다).

  ```
  ✘ 금지: 조사 불필요 판정 → build_tools()에서 조사 계열 도구 제외
  ✔ 채택: 도구는 항상 등록 → handler 진입부에서 게이트(거부 사유를 구조화 반환)
  ```

  거부는 **침묵하지 않고** 사유를 반환해 LLM이 대체 경로(`process_query`)를 선택하게 한다.
  이 형태는 Manus의 로짓 마스킹과 같은 취지 — **목록은 고정, 가용성만 제어**한다.

  > **파생 규칙**: 같은 이유로 `COMPOSITE_INVESTIGATION_ENABLED` 같은 **플래그를 요청 시점에
  > 바꿔 도구 목록을 흔들지 않는다.** 플래그는 기동 시 1회 해석한다(오케스트레이션 사다리가
  > 빌드 타임 1회 확정인 것과 같은 규율 — `docs/21_orchestration_ladder.md` §2).

#### ③ 작업 분해 — 기존 유지

§3.1·P1대로 planner를 변경하지 않는다. ADaPT의 과분해 회피 원칙에 따라 **분해를 늘리지 않고**
엣지가 나르는 데이터만 넓힌다(W1).

#### ④ 컨텍스트 압축 — **신규**. 결정적 2단 축약, LLM 압축은 미채택

- **문제**: fan-out N개 × 프로세스 목록 = **토큰 폭증**. 대상 10개 × 프로세스 수십 개를 그대로
  올리면 제어 평면 예산을 넘긴다. 초안의 P4는 *대상 1개*의 축약만 상정했다.
- **LLM 기반 압축(LLMLingua) 미채택 — 세 가지 이유**:
  1. **압축 대상이 신뢰 불가 데이터다**(§7.2). 압축기에 먹이는 순간 인젝션 표면이 하나 더 생긴다.
  2. **결정적 축약이 이 도메인에서 더 낫다.** 프로세스 목록의 올바른 축약은 "CPU/메모리 내림차순
     상위 N"이지 perplexity 기반 토큰 가지치기가 아니다. 도메인 지식이 범용 압축을 이긴다.
  3. 폐쇄망에서 압축용 모델을 추가로 서빙해야 한다.
- **조치(W2-7) — 결정적 2단 축약** (MemGPT의 계층 티어 개념만 차용):

  | 단 | 대상 | 방법 |
  |---:|---|---|
  | 1 | 호스트별 | `select_top_processes`로 상위 N + 마스킹 (기존 자산 재사용) |
  | 2 | 전체(N 호스트) | 호스트 수에 따라 **호스트당 노출 행 수를 동적 축소** + 이상 호스트 우선 |

  **원문 전량은 감사 로그·CSV에만** 남긴다(D-047 표시/다운로드 규약 계승).
  ETCLOVG 체크리스트 ③에 따라 **압축으로 무엇이 빠졌는지(호스트당 절단 행 수)를 결과에 기록**한다.

#### ⑤ 메모리 — **신규**. 단기 조사 캐시만, 장기 메모리 미채택

- **문제**: 멀티턴에서 "그 서버 메모리도 보여줘"가 오면 **같은 호스트를 다시 조사**한다.
  낭비이자 갭 ③(대상 호스트 부하)의 증폭 요인이다.
- **기존 자산**: `previous_entities`(멀티턴 승계) · D-117 §14.4가 게이트 경계 probe에 **2초 캐시**를
  이미 쓴다 — 같은 발상이다.
- **조치(W2-8)**: `(db_id, hostname, profile)` 키의 **단기 결과 캐시**.
  - TTL 짧게(`composite_snapshot_ttl_seconds` 기본 **60s**) — 조사는 "지금 상태"를 묻는 것이므로
    오래된 캐시는 오답이 된다.
  - **캐시 히트 시 수집 시각을 응답에 명시**한다(침묵 금지 — 사용자가 실시간으로 오인하면 안 된다).
  - 키 만료 sweep 필수(Known Mistakes — in-memory dict는 값 bound뿐 아니라 키 만료도).
- **장기 메모리(세션 간 학습·AGENTS.md류) 미채택**: 본 계획 범위 밖이며, 조사 결과를 장기 보관하면
  §7.2의 불신 데이터가 영속화된다. 감사 로그(W6)가 이력 보존을 이미 담당한다.

### 4.6 하네스 프로파일과 Tier 규율 — 착수 순서 정정

#### 4.6.1 세 결정 축 판정

문서 표 22의 세 축으로 본 계획의 프로파일을 판정한다. 이 판정이 계층 투자 우선순위를 결정한다.

| 축 | 본 계획의 값 | 근거 | 함의 |
|---|---|---|---|
| **폭발 반경** | **중간~높음** | 행동은 읽기 전용이나 **운영 실호스트에 접근**한다. 되돌릴 것은 없지만 대상 호스트에 부하를 주고(갭 ③), 잘못된 대상에 닿을 수 있다(scope overflow) | **E·G 최우선** |
| **과제 지평** | **낮음** | 복합 질의 1턴 완결. 100턴 장기 실행이 아니다 | **C·L 투자 우선순위 낮음** |
| **자율성** | **낮음** | 사용자 질의에 응답하는 형태 — 매 요청이 사람의 개입 지점이다 | O·V 부담 상대적으로 낮음(단 0은 아님) |

**판정 결과: 본 계획은 E·G 중심 프로파일이다.**

- §4.4가 찾은 갭 3종이 전부 **E·V·G**에 몰린 것은 이 프로파일의 필연적 귀결이다.
  갭 ①(G 인가)과 ③(E 부하)을 최우선으로 잡은 것은 이 축 판정과 정합한다.
- **C(압축·메모리) 투자의 근거를 정확히 해 둔다**: 과제 지평이 짧으므로 *지평 때문에* 필요한 것이
  아니다. **fan-out으로 인한 단일 턴 내 토큰 폭증** 때문이며(N 호스트 × 프로세스 목록),
  이는 L 계층 설계(fan-out)가 C에 부과한 부담이다 — 계층 결합(P11)의 사례다.
  **지평 대응(장기 메모리·드리프트 감시)은 여전히 범위 밖**이다.

#### 4.6.2 Tier 매핑과 착수 순서 — **v4 순서 위반 정정**

§3.4.3-②의 Tier 규율로 Wave를 재분류하면 **v4의 착수 순서에 문제가 드러난다.**

| Wave | 내용 | Tier | v4 순서 |
|---|---|---|---|
| W0 | 갭 재현 테스트 | 0 | 1번째 |
| W1 | 결과 의존 배선 | 0 | 2번째 |
| W2-1~6 | fan-out **기능** + 부하 가드 | 0 (E) | 3번째 |
| **W2-7·8** | **압축 · 조사 캐시** | **2** | **3번째** ⚠ |
| W3-1·4 | `mcp_server` 도구 배선 + 도구 명명·스키마 규약 | 0~1 (T) | 4번째 |
| **W3-5** | **호스트 인가 게이트** | **1 (G)** | 4번째 |
| **W3-2·3** | **경로 선택 규칙 + 진입 게이트** | **2 (L)** | 4번째 ⚠ |
| W4 | 조치 권고 | — | 5번째 |
| W5 | 검증 | 1 (V) | 6번째 |
| **W6** | **관측·감사** | **1 (O)** | **7번째(마지막)** ⚠ |

**문제**: **Tier 2 항목(W2-7·8 압축·캐시, W3-2·3 라우팅)이 Tier 1 항목(W6 관측·감사)보다 앞에 있다.**
문서가 "자주 하는 실수" 첫머리에 올린 **"측정 없이 하네스를 쌓는다"** 에 정확히 해당한다.
근거는 커플링 문제(P11) — *"고립해서 보면 이로워 보이는 변경이 나머지 제어 루프와 결합하면
전체 롤아웃을 악화시킬 수 있다."*

구체적으로 무엇이 위험한가:

- **압축(W2-7)**: 축약이 유용한 정보를 잘랐는지, 어떤 호스트에서 얼마나 잘렸는지는 **추적 없이는
  알 수 없다.** 압축을 켠 뒤 응답 품질이 떨어져도 원인을 압축에 귀책할 방법이 없다.
- **캐시(W2-8)**: 캐시 히트율·stale 응답 비율을 못 보면 TTL이 적절한지 판단 불가다.
- **라우팅(W3-2·3)**: 문서 표 3이 명시한다 — *"라우팅 오분류를 측정하려면 O·V가 필요하다."*
  비싼 경로 진입률을 못 보면 게이트가 과하게 막는지 헐거운지 알 수 없다.

**정정 — 착수 순서에 선행 조건을 건다** (Wave 번호는 유지하고 순서 제약만 부과한다):

```
Tier 0 :  W0 → W1(공통 모듈) → W2-1~6 → W3-1·4    (루프가 돌고, 폭주하지 않는다)
Tier 1 :  W6(관측·감사) → W3-5(인가) → W5(검증)    ★ 여기까지가 최적화의 전제
Tier 2 :  W2-7·8(압축·캐시) → W3-2·3(경로 게이트)  (측정 가능해진 뒤에만 착수)
부가   :  W4(결과·권고 소비)  — Tier 1 이후 임의 시점
별도   :  W7-1(OS 근사)  — **선행조건 0 · 즉시 착수 가능**
         W7-2(APM 연계) — **APM 도입 후**(D-119 경계 확장 · R-11/R-12)
```

> **v6 주석**: W1이 Tier 0의 첫 실질 항목인 이유는 **대상 해소 공통 모듈**이 세 경로의 공통 기반이기
> 때문이다(G2+G5). 이것 없이 W3·W7을 진행하면 각 경로가 자기 해소 로직을 갖게 되어 **G5가 굳는다.**
> W7은 Tier와 별개 축이다 — **1단계(OS 근사)는 선행조건이 0**이라 APM 일정과 무관하게 착수할 수
> 있고, **2단계(APM)는 도입 시점에 종속**된다. 둘을 한 Wave로 묶되 착수 시점은 분리한다.

- **W6는 마지막이 아니라 Tier 1의 첫 항목**이다. W2-1~6까지 오면 관측할 대상(fan-out 실행)이
  생기므로 그 시점에 착수 가능하다.
- **W2-7·8과 W3-2·3(경로 선택·진입 게이트)은 W6 완료를 선행 조건으로 갖는다.** 각 항목에 명시한다.
- W3-5(인가)는 Tier 1이지만 **W3-1·4와 같은 Wave**이므로, 조사 플래그 해제 자체가
  W3-5 완료를 요구한다(R-9와 동일 게이트).

> **왜 Wave 번호를 바꾸지 않는가**: 번호는 *갭 해소 단위*를 가리키고 순서는 *Tier 규율*이 정한다.
> 둘을 하나의 번호에 섞으면 어느 쪽 정보도 온전히 남지 않는다. 문서의 표 28(적용 절차)도
> "활동"과 "산출물"을 분리해 같은 방식을 쓴다.

#### 4.7.1 미들웨어 조사 — 방식 선택 (G4)

> **사용자 확정(2026-08-26)**: **미들웨어 데이터 소스는 향후 APM 모니터링 솔루션을 연계할 예정.**
> 이 확정으로 아래 선택지의 우선순위가 바뀐다 — **APM이 정본 소스**가 되고, 나머지는 그 전후를 메운다.

| 방식 | 얻는 것 | 선행조건 | 판정 |
|---|---|---|---|
| **E. APM 연계** ★ | 트랜잭션 응답시간·에러율·처리량 · 힙/GC · 스레드풀 · **커넥션풀** · 슬로우 쿼리 | **APM 솔루션 도입·연동**(시점 미정) | **정본 소스 — 2단계 채택**(사용자 확정) |
| **A. OS 레벨 근사** — 기존 `ps`/`ss`/`journalctl` 재사용 | 프로세스 존재·기동 인자(힙 설정 등)·리스닝 포트·프로세스 자원·시스템 로그 | **없음**(allowlist 기보유) | **1단계 채택 — APM 도입 후에도 존치**(아래 근거) |
| B. 폴스타 에이전트 확장 | 폴스타가 수집 중인 미들웨어 지표(있다면) | 폴스타 측 스냅샷 노출 | **미채택** — APM이 같은 자리를 더 잘 채운다 |
| **C. JMX/Jolokia** | 힙·GC·스레드풀·MBean | JMX 포트 개방·자격증명·Jolokia 배포 | **폐기 확정**(v7) — **APM이 대체**한다. 신규 접근 경로를 열 이유가 사라졌다 |
| D. WAS 로그 파싱 | 예외·스택트레이스 | 로그 경로 표준화·수집 파이프라인 | 보류 — APM이 에러 추적을 담당하면 불요 |

**A와 E는 대체가 아니라 보완이다 — A를 존치하는 이유:**

- APM은 **애플리케이션 관점**(트랜잭션·힙·풀), OS 근사는 **인프라 관점**(살아 있나·포트·자원)이다.
- **APM 에이전트가 붙지 않은 미들웨어**가 남는다(레거시·경량 웹서버·상용 제약).
- **APM 자체가 죽었을 때** 볼 수단이 필요하다 — 관측 도구의 장애를 관측 도구로만 진단할 수 없다.
- A는 선행조건이 **0**이라 APM 도입 일정과 무관하게 지금 착수 가능하다.

→ **APM 도입 후 우선순위만 바뀐다**: 미들웨어 장애는 **APM이 1차**, OS 근사가 2차 확인·폴백.

#### 4.7.2 APM 편입 경로 — **D-119 경계 확장** (신규 아키텍처 결정 아님)

D-119가 이미 이 경우를 명시적으로 예비해 두었다:

> *"`mcp_server`의 성격을 '폴스타 데이터 접근 전용'에서 **'관측 데이터 읽기 경계'**로 재정의 —
> **향후 관측 소스 추가도 별도 서버가 아니라 이 경계의 확장으로 편입한다.**"* (D-119 ①)

따라서 **APM은 별도 서버·별도 커넥터가 아니라 `mcp_server`의 세 번째 소스**로 들어간다.
Prometheus 편입(D-119 R-B)이 그대로 청사진이 된다.

| 항목 | Prometheus 전례 | APM 적용 |
|---|---|---|
| 설정 객체 | `PrometheusConfig`(url·auth_header·timeout·expose_raw) | `ApmConfig` 동형 |
| 고수준 도구 | `prom_metric_instant`·`prom_metric_range`(hostname 앵커·**서버측 결정적 조립**) | `apm_*` 소수(§아래) |
| 원시 도구 | 5종 **옵트인**(`expose_raw_promql`) | 벤더 질의문 노출은 **옵트인** |
| 반환 계약 | `{data, queried_at, source_kind:"prometheus"}` | `source_kind:"apm"` |
| 자격증명·타임아웃·감사 | **서버측 일원화** | 동일 |
| 소비자 | 방언 무지 | **벤더 무지** |

**벤더 중립 도구 표면**(솔루션 미정이므로 *벤더 API*가 아니라 *질문*으로 정의한다):

```
apm_app_health(hostname|app, window)      → 응답시간·에러율·처리량
apm_runtime_health(hostname|app, window)  → 힙·GC·스레드
apm_resource_pool(hostname|app)           → 커넥션풀·스레드풀 사용률
apm_slow_transactions(hostname|app, n)    → 상위 N 느린 트랜잭션
```

필드명은 **OpenTelemetry 시맨틱 컨벤션에 맞춘다** — OTel은 2026년 사실상 표준(CNCF 졸업)이고
주요 APM이 OTLP를 수용하므로, 벤더가 바뀌어도 **매핑 계층만 교체**하면 된다.

**⚠ 편입 시 최대 리스크 — 식별자 정합**: APM의 인스턴스 식별자(agent id·application name)와
폴스타 `hostname`을 **잇지 못하면 데이터가 있어도 무용**하다. 78의 G2(대상 확정)와 직결된다.
D-119가 Prometheus에서 겪은 것과 같은 문제이며(`nodename` 라벨 실측·`exported_nodename` 충돌),
그때 남긴 **"운영 편입 체크리스트"** 를 APM용으로 재사용한다(§4.7.3).

#### 4.7.3 APM 편입 체크리스트 (착수 시 실측 — D-119 전례)

1. APM 인스턴스 식별자가 폴스타 `server_name`/`hostname`과 **동일 값으로 매칭되는가** —
   불일치 시 매핑 테이블이 필요한가(D-020 hostname 정합 규약 계열)
2. 한 호스트에 **미들웨어 인스턴스가 여럿**일 때 구분 키는 무엇인가(포트·인스턴스명)
3. 보존 기간·조회 지연(APM 데이터가 실시간인가 집계 지연이 있는가)
4. 인증 방식·토큰 수명 · 조회 타임아웃
5. 미등록 대상 조회 시 **graceful 여부**(빈 결과 vs 오류) — 침묵 폴백 금지 규약 적용 지점
6. **OTLP/OTel 시맨틱 컨벤션 준수 여부** — 준수하면 매핑 비용이 크게 줄어든다

> **파생 결정**: G4의 1단계는 "`sre_agent`에 미들웨어 프로파일 추가"(`profile="middleware"`,
> `VM_DIAG_ALLOW` 기보유 명령 조합)이고, **2단계는 `mcp_server` 소스 확장**이다.
> 78은 양쪽 모두 **요구를 정의하고 결과를 소비**하며, 구현은 각 패키지 소관이다(경계 유지).

> **이미 필수 의존인 `pydantic`** 으로 얻고, 프레임워크는 들이지 않는다(§4.7.5-④).

#### 4.7.5 Pydantic AI 적용 가능성 검토 (v10 · 사용자 지시)

> **결론: 현재 조건에서 미채택 — 단, 거부가 아니라 보류다.** 진입 장벽이 *프레임워크의 품질*이
> 아니라 **운영 LLM(FabriX)의 프로토콜 제약**에서 오기 때문이며, 그 조건이 바뀌면 판정도 바뀐다(⑤).
> 다만 pydantic-ai에 끌린 **문제의식 자체는 실재하는 결함**이므로, 그중 이 프로젝트가 지금 실제로
> 얻을 수 있는 부분은 **신규 의존 0으로** 채택한다(④).

##### ① 실측 — 무엇이 사실인가 (추정 없음)

> ⑨가 핵심이다 — 제어 평면(`create_orchestrator_llm`, vLLM·OpenAI 호환)은 **deepagents 트랙 B 전용**이고,
> **78의 DAG 분해는 워커 평면 = FabriX**를 탄다. pydantic-ai가 쉽게 붙는 쪽이 78의 경로가 아니다.

##### ② 결정적 제약 — FabriX는 pydantic-ai의 주경로를 못 탄다

pydantic-ai의 값어치 대부분은 **모델의 네이티브 tool-calling / JSON 스키마**에서 나온다.
FabriX 두 모드는 그 둘 다 없다 — 설정 문제가 아니라 **프로토콜에 자리가 없다**.

| 모드 | 페이로드 | tool 전달 | 판정 |
|---|---|---|---|
| **KBGenAI**(`fabrix_kbgenai.py`) | `{modelId, contents[], isStream, isRagOn, …, systemPrompt}` 전용 스키마 | **`tools` 필드 자체가 없다.** `bind_tools`(L308)는 `tool_registry` dict에 담아둘 뿐 **전송하지 않는다** | **원천 불가** |
| **FabriXAPIClient**(`fabrix_client.py`) | OpenAI 호환 `/chat/completions` | `_build_payload`(L120)가 **`tools`를 싣지 않는다**. 대신 마지막 user 메시지에 `### Tool Definitions` **few-shot 문자열을 주입**하고 응답 본문에서 `{"tool_name":…}` 를 파싱(L142~) | **프롬프트 모사** — 네이티브 아님 |

> 코드가 이미 스스로 못 박아 두었다 — `noise_gate/infrastructure/noise_signal_tools.py:233`:
> *"vLLM 오케스트레이터는 네이티브 `bind_tools`를 지원한다(**FabriX는 미지원**)"*.

→ 운영 구성에서 pydantic-ai가 쓸 수 있는 모드는 **`PromptedOutput` 하나**뿐이다.
그런데 `PromptedOutput`은 *스키마를 프롬프트에 넣고 평문 응답을 파싱하는* 방식으로,
**이 프로젝트가 지금 하는 것과 같은 방식**이다(`extract_json_from_response`).
즉 프레임워크를 들여도 운영 경로에서 얻는 순증분은 **"네이티브 구조화 출력"이 아니다.**

##### ③ 도입 비용 — 세 번째 FabriX 구현이 생긴다

브리지가 없으므로(실측 4) FabriX를 물리려면 `Model` ABC를 **직접 구현**해야 한다.
그때 **재구현 대상**은 전부 기존 두 클라이언트에 **이미 있는 것들**이다.

- 전용 페이로드 조립 · `status != SUCCESS` 오류 규약 · `remove_llm_junk` 후처리
- **PII 필터 훅**(`log_filter_block_if_any`) — 보안 계층이 LLM 클라이언트에 붙어 있다
- **KBGenAI 메시지 순서 규약**(System 다음 **빈 `AIMessage`**) — 현재 `is_kbgenai()`로 **8곳**에 적용 중
- SSE 스트리밍(`_astream`) — 사용자 응답 스트리밍 경로 → `StreamedResponse`도 함께 구현

**Plan 69 P2가 정확히 이 문제를 한 번 정리했다** — KBGenAI 판정이 3형태로 11곳에 흩어져 있던 것을
`src/utils/llm_compat.py` 단일 출처로 모았다. **세 번째 프로토콜 구현을 만드는 것은 그 정리를 되돌린다.**

여기에 **폐쇄망 wheel 반입**이 얹힌다 — §4.7.4가 *"신규 wheel 반입 불요 → 착수 리스크를 크게 낮춘다"* 를
명시적 이점으로 적어 두었는데, 도입하면 기반 의존만 **7종 + 전이**(`httpx2`·`httpcore2`·`truststore` 등)가
새로 필요하다. 기술적 충돌은 없지만(실측 8) **보안 반입 절차가 착수 경로에 추가**된다.

또한 `pydantic-graph`가 **필수 의존으로 따라온다** — LangGraph와 기능이 겹치는 두 번째 그래프 런타임이
같은 venv에 상주한다. 쓰지 않으면 그만이지만, §4.7의 *"오케스트레이션 = LangGraph 유지"* 결정과
**표면상 상충하는 자산**이 생기는 것은 유지보수 관점의 부채다.

##### ④ 진짜 문제와, 그래서 무엇을 채택하는가

pydantic-ai에 끌린 이유 자체는 **실재하는 결함**이다. 실측하면:

- `extract_json_from_response` 계열이 **16개 파일 25곳**에서 쓰인다
- **`TaskSpec`이 `list[dict]`**(`state.py:246`) — 타입 계약이 없다
- `_llm_decompose`(`intent_planner.py:493~`)는 필드마다 `raw.get(…, 기본값)`으로 **수동 보정**하고,
  실패하면 **단일 `data_query`로 폴백**한다 — 사유가 로그에만 남고 응답에 드러나지 않는다
  (Known Mistakes *"침묵적 폴백 금지"* 저촉 소지)
- **검증 오류를 모델에 되먹이지 않는다.** 재시도 전례는 `input_parser.py:217~`에 **한 곳** 있으나
  *고정 힌트 문자열*을 덧붙일 뿐이고 판정도 `query_targets` 존재 여부뿐이다.
  **78의 DAG 분해(`intent_planner`)에는 재시도가 아예 없다** — 단일 시도 후 폴백.

**그런데 이 넷을 고치는 데 pydantic-ai가 필요하지 않다.** `pydantic>=2.0`은 **이미 필수 의존**이다.

| pydantic-ai가 주는 것 | 78이 얻는 실질 | plain pydantic으로 대체되는가 |
|---|---|---|
| 타입 지정 출력(`output_type`) | **큼** | **된다** — `class TaskSpec(BaseModel)` + `model_validate` |
| 검증 실패 → 모델 재요청(`ModelRetry`) | **큼** | **된다** — `ValidationError.errors()`를 되먹이는 헬퍼(수십 줄). `input_parser` 전례의 일반화 |
| 스키마 → 프롬프트 자동 주입 | 중간 | 부분 — 현행 프롬프트는 **few-shot 예시가 정본**이고 79 트랙 A가 그 구조를 막 고정했다 |
| `PromptedOutput` 파서 | **없음(동등)** | 이미 `extract_json_from_response` 보유 |
| `ToolOutput`·`NativeOutput` | **없음** | FabriX가 못 받는다(②) |
| OTel 계측 | 중간 | W6는 **DB·호스트 접근 감사**가 대상 — LLM 호출 추적과 층이 다르다 |
| 에이전트 루프 | **없음** | LangGraph 담당(§4.7 오케스트레이션 유지 확정) |

→ **채택하는 것은 pydantic-ai가 아니라 그 패턴이다.** 신규 의존 **0**.
다만 **두 절반의 착지점이 다르다** — 실측 결과 하나만 78 범위 안이다.

##### ④-1 배치 실측 정정 (**중요** — 초안의 오류)

초안은 *"W1이 실제로 손대는 경로(`intent_planner` → `agent_orchestrator`)"* 라고 적었는데
**틀렸다**. §5 Wave 본문 전수 grep 결과 **`intent_planner`·`task_plan`·`TaskSpec`을 건드리는
Wave가 하나도 없다.** `TaskSpec`은 78의 수정 대상이 아니다(§6.1 파일 배치에도 없다).

| 절반 | 대상 | 착지 | 근거 |
|---|---|---|---|
| **타입 계약** | **`prior_targets`** — W1-3이 **새로 만드는** 산출물 | **W1-6으로 편입** ✔ | 78이 직접 만드는 계약이므로 서지컬. `[{hostname, ip, db_id}]`가 지금 표에만 있고 코드 계약이 없다 |
| 타입 계약 | `TaskSpec`(`state.py:246`) | **범위 밖 → R-13** | 어느 Wave도 `intent_planner`를 수정하지 않는다. 넣으면 78이 만들지 않는 파일을 여는 범위 확대 |
| **되먹임 재시도** | `_llm_decompose`(`intent_planner.py:493~`) | **범위 밖 → R-13** | 위와 동일 |

##### ④-2 기존 결정과의 충돌 — 재시도를 W1에 넣으면 안 된다

**W1-3.2가 이미 못 박아 두었다** — *"검증 탈락 시 3단으로 되돌아가지 않는다 — 사유를 남기고
대상 미확정으로 종료(**무한 재시도 금지**)"*. W1-3의 LLM 컬럼 지목은 **닫힌 집합에서 하나 고르기**라
재요청해도 후보 집합이 그대로이고, 실패는 *데이터에 식별자 컬럼이 없다*는 신호일 때가 많다.
**되먹임 재시도는 그 결정과 충돌하므로 W1에 적용하지 않는다.**

> 되먹임 재시도가 값을 갖는 곳은 **자유 형식 스키마를 산출하는 `_llm_decompose`** 이고,
> 그건 78이 손대지 않는 파일이다. **두 곳을 섞으면 안 된다** — 착수 시 이 경계를 지킬 것.

##### ④-3 그래서 78이 실제로 채택하는 것

**W1-6**(아래 §5 W1) — `prior_targets` 항목을 `BaseModel`로 정의하고 W1-3.2의 결정적 검증을
그 계약 위에서 표현한다. 기보유 `pydantic`만 사용하고 **재시도는 넣지 않는다**(④-2).
나머지(`TaskSpec` 타입화 · `_llm_decompose` 재시도)는 **R-13에 파생 과제로 등재**한다 —
실재하는 결함이므로 조용히 사라지지 않게 하되, 78의 범위로 끌어들이지는 않는다.

##### ⑤ 재검토 트리거 — 언제 판정이 뒤집히는가

**미채택 근거가 전부 FabriX 한 가지에 걸려 있다.** 다음이 성립하면 비용 구조가 반전된다.

| 조건 | 무엇이 달라지나 |
|---|---|
| **워커 LLM의 vLLM(OpenAI 호환) 전환** ★ | `Model` 서브클래스가 **불필요** — `OpenAIChatModel` + 커스텀 provider로 직결(실측 6). 네이티브 tool-calling이 살아나 **`ToolOutput` 주경로**를 탈 수 있다. 도입 비용이 ③ 전체 → **설정 수준**으로 떨어진다 |
| 79 트랙 C(logprob 신뢰도) 재개 | **같은 라우터 평면 이동에 걸려 있다**(79 §8②) — 선행조건이 동일하다 |
| ~~79 트랙 E-3(Instructor)~~ | **v12 — 트리거에서 이탈.** 79가 **한국어 커스텀 핸들러**로 주입 문제를 해소하고 **모드 자동 선택**(평문=`MD_JSON`/vLLM=`TOOLS`)을 어댑터에 넣기로 하면서, E-3은 **평면 이동을 기다리지 않는다**. 평면 이동은 E-3에게 *선행조건*이 아니라 *최적화*가 됐다 |

> **★ v11 — 세 건이 한 결정에 수렴한다 → v12에서 두 건으로 축소.** `plans/79` **§8 ⑪**(라우터의 LLM
> 평면 배치)이 결정되면 **트랙 C(logprob)** 와 **본 항목(pydantic-ai)** 이 풀린다. 근본 원인은 같다 —
> *의도 추출 경로가 워커 평면(FabriX, 평문·tool-calling 부재)을 탄다.*
>
> **v12 정정**: **E-3(Instructor)은 이 수렴에서 빠진다.** 79가 두 가지로 종속을 끊었기 때문이다 —
> ⓐ **한국어 커스텀 핸들러**로 프롬프트 주입 간섭을 제거 ⓑ **모드 자동 선택**을 어댑터에 내장해
> 평문/vLLM 양쪽을 같은 소비 코드로 처리. **결과적으로 Instructor는 평면 이동 전에 착수 가능하고,
> 이동 후에는 `Mode.TOOLS`로 자동 승격된다.**
>
> **여기서 78이 가져갈 교훈**: pydantic-ai가 이 수렴에 남은 이유는 **`Model` ABC 재구현이라는
> 구조적 결합** 때문이지 평문 모델 자체가 아니다(§4.7.5-③). *어댑터로 끊을 수 있는 종속*과
> *프레임워크가 요구하는 종속*은 다르다 — 두 검토의 판정이 갈린 진짜 이유다.

> 즉 **`plans/79` 트랙 C와 본 항목은 트리거를 공유한다.** 라우터 평면 이동이 결정되면 두 건을
> **한 번에** 재평가하는 것이 맞고, 그 전에 각각 따로 착수할 이유가 없다.

**현 시점 권고: 도입하지 않는다.** 대신 ④의 타입 계약을 W1에 얹는다.
**이 판정은 제안이며, D-번호 등재는 사용자 확정 후에 한다**(D-161 부기 — 계획서 예약만으로는 효력 없음).

가장 작은 변경으로 가장 큰 효과를 내는 Wave다.

### W2 — N-서버 fan-out (G3 해소) · **D-165**

1. `process_query.run_process_query`를 **대상 리스트 처리**로 확장:
   - 단일 대상 입력 시 **기존과 동일 경로**(회귀 0)
   - N개 대상: `asyncio.gather` + `Semaphore(composite_fanout_concurrency`, 기본 3) +
     per-target timeout(`composite_target_timeout_seconds`, 기본 10)
2. **부분 실패 허용**: 대상별 개별 try/except (Known Mistakes "독립 신호 수집은 개별 try/except").
   실패 대상은 `{target, error}`로 결과에 남긴다.
3. **전체 타임아웃 가드**: per-call 타임아웃만으로는 무력화된다(Known Mistakes) —
   fan-out 전체에 `composite_total_timeout_seconds`(기본 45) 상한.
4. **reduce(결정적)**: 대상별 결과를 표로 병합. 응답에 반드시 포함:
   - 조사 대상 수 / 성공 수 / 실패 수 / **절단 여부와 절단된 수**
5. 표시·다운로드는 D-047 규약 계승 — 채팅=상위 N 요약, CSV=전량.
6. **대상 호스트 부하 가드**(E 계층 · §4.4 갭 ③ · D-117 승계):
   - 수집 명령에 **`nice` 우선순위 하향 + 명령 자체 timeout**을 건다(중앙측 타임아웃과 별개 —
     중앙에서 끊어도 대상 호스트의 프로세스는 계속 돌 수 있다).
   - **동시 조사 대상 수 상한**을 부하 관점에서도 해석한다: 같은 호스트에 대한 **중복 동시 조사 금지**
     (in-flight 키 `(db_id, hostname)` 단일화).
   - `top -b` 등 반복 샘플링 명령은 **1회 스냅샷**으로 고정(`-n 1` 류) — 장시간 점유 금지.
   - **판단 근거**: 본 계획의 대표 시나리오가 *이미 포화된 서버*를 조사하는 것이다. 조사가 장애를
     악화시키면 계획의 목적 자체가 무너진다.
7. **결정적 2단 축약**(C 계층 · §4.5-④) — **Tier 2 · 선행: W6 완료**(§4.6.2):
   - 1단 호스트별 `select_top_processes` 상위 N + 마스킹(기존 자산 재사용)
   - 2단 전체 — 호스트 수에 따라 **호스트당 노출 행 수 동적 축소**, 이상 호스트 우선 배치
   - **압축 손실 기록**: 호스트당 절단 행 수를 결과에 실는다(ETCLOVG 체크리스트 ③)
   - **원문 전량 보존이 필수 조건**(§3.4.3-⑤): 문서는 압축을 *재현율 우선*으로 조정하라고 권고하는데
     상위 N 선별은 **정밀도 우선**이다. 감사 로그·CSV에 **원문 전량을 남겨 손실을 복구 가능**하게
     두는 것이 이 편차를 상쇄하는 조건이다 — 보존 없이 상위 N만 남기면 규칙 위반이 된다.
8. **단기 조사 캐시**(메모리 · §4.5-⑤) — **Tier 2 · 선행: W6 완료**:
   - 키 `(db_id, hostname, profile)` · TTL `composite_snapshot_ttl_seconds`(기본 60s)
   - **캐시 히트 시 수집 시각을 응답에 명시**(실시간 오인 방지 — 침묵 금지)
   - **키 만료 sweep 필수**(Known Mistakes — in-memory dict는 값 bound + 키 만료 둘 다)

**수용 기준**

   - 인가 판정은 **위임·호출 직전**(실행 경계)에 둔다 — planner·LLM 경로가 아니라 경계에서 막아야
     우회가 없다(UI 게이트 ≠ 인가).
   - **두 진입점(채팅·이벤트)이 같은 인가 모듈을 호출한다**(G5) — 한쪽만 적용되는 비대칭 금지.
   - 인가 실패는 **조용히 건너뛰지 않고** 사유와 함께 결과에 남긴다.
   - **모델 결정은 착수 시 사용자 확인 사항**(R-9): (a) `allowed_db_ids`+role 조합 (b) 호스트
     그룹/태그 기반 별도 인가 목록. **결정 전 조사 플래그를 해제하지 않는다.**
6. **대상 호스트 부하 가드 — 요구 전달**(§4.4 갭 ③): 조사 실행이 `sre_agent` 소관이므로 78은
   **요구를 명시하고 계약으로 전달**한다 — `nice` 하향 · 명령 자체 timeout · 동일 호스트 중복 조사
   금지 · `top -n 1` 고정. **구현은 `sre_agent` toolset 측**(경계 유지 · D-118).

**수용 기준**
- `mcp_server` 고수준 도구가 본체에서 호출되고 반환 계약이 그대로 소비된다(1).
  > **범위 주의(v16 정정 · 2026-08-27)**: 이 기준은 **두 조각**이다 — ①클라이언트가 도구를
  > 부를 수 있는가(W3-1 · `DBHubClient.inspect_host` · **완료**) ②그것을 **언제 부를지**
  > 정해진 경로가 있는가(**W3-2** 경로 선택 규칙 · 미구현). ②가 없으면 프로덕션 호출부가
  > 0건이므로 *"호출되고 소비된다"* 가 e2e로 충족되지 않는다. WU-13을 완료로 표시했다가
  > 이 간극을 놓친 이력이 있다(`docs/18_known_mistakes.md` 2026-08-27).
- 경로 선택 회귀 테스트: 프로세스 목록 요구가 `sre_agent`로 가지 않는다(2 · P12).
- 라우팅이 **도구 목록을 흔들지 않는다** — `build_tools()` 결과가 요청 간 동일함을 단언(3 · P14).
- **인가 단언**(5): 인가되지 않은 호스트는 조사가 **시작되지 않는다**(호출 0회).
  **채팅·이벤트 양쪽에서 동일하게** 막힌다(대칭 테스트 2건 — G5).
- 부하 가드 요구가 계약 문서·페이로드에 명시된다(6).
- 플래그 off 시 회귀 0.

### W4 — 조사 결과·해결방안 소비 (**v6 축소**) · **D-166**

> **v5 대비 전환**(§0.3): 조치 권고 **생성을 폐기**한다. `sre_agent/domain/remediation.py`가
> 결정적 표 기반으로 이미 생성하며(위험도 3등급 · 고위험×저신뢰 강등 · 실행 경로 부재를 테스트로
> 고정), 78이 또 만들면 권고가 두 벌이 된다. 78은 **소비·표시**만 한다.

1. **브리핑·권고 소비**: poll 결과의 브리핑 6요소(timeline·bottleneck·cause·evidence·
   recommendation·limitation)와 `Remediation` 목록을 응답에 싣는다.
   `fault_diagnosis.py`가 이미 `_BRIEFING_ORDER`로 조립하므로 **재사용**한다(사본 금지).
2. **위험도·신뢰도 표기 보존**: 권고의 `risk`/`confidence`를 **깎지 않고 그대로 노출**한다.
   "검토 필요"로 강등된 항목을 정식 권고처럼 보이게 하지 않는다.
3. **실행 경로 부재 유지**: 78은 권고를 **문자열로만** 다룬다. 변경 명령이 어떤 경로로도 실행되지
   않음을 테스트로 고정한다(`remediation.py` 전례 계승).
4. **부분 결과 표시**: 조사 실패·타임아웃·인가 거부 시 사유를 노출한다(침묵 금지).

**수용 기준**
- 권고 생성 코드를 78이 **만들지 않는다**(중복 부재 단언).
- 위험도·신뢰도가 원본 그대로 표시된다.
- 변경 명령 실행 경로 부재 단언 통과.


### W5 — 오케스트레이션 수준 검증·재계획 (P7) · **D-167**

VMAO의 Verify를 **최소 형태로만** 도입한다(과설계 경계 — ADaPT 교훈).

1. **결정적 충족도 체크**(LLM 미사용): 복합 질의에서
   - 선행이 M개 대상을 반환했는데 후속이 조사한 대상이 M보다 적은가?
   - 후속 task가 대상 미확정으로 빈손 반환했는가?
2. 미충족이면 **1회만** 재실행(대상 집합을 명시 주입). 종료 조건:
   **최대 1회 재시도 · 개선 없으면 즉시 중단 · 전체 타임아웃 준수**
3. 재시도 후에도 미충족이면 **사유를 응답에 노출**한다.
4. **실행 전 준비 검증**(V 계층 1~3단계 중 "준비 검증" · 문서 표 29 V): **조사 경로**
   (`sre_agent` 위임 · `mcp_server` 고수준 도구)가 **가용한지 조사 착수 전에 확인**한다.
   *(v13 정정 — "수집기 백엔드"는 v6에서 폐기된 어댑터를 가리키던 표기다.)* 문서의 지적 — *"평가 인프라 잡음이 모델 실패로 위장한다.
   실패한 실행은 모델 한계가 아니라 망가진 도구·낡은 컨텍스트·리셋되지 않은 샌드박스에서 비롯될 수
   있다."* 백엔드 미가용을 조사 실패로 기록하면 원인 귀책이 어긋난다.
   → 미가용이면 **조사를 시작하지 않고** 사유를 반환한다(경로 강등 **W3-2** 경유).
5. **대상 정합 사후 대조**(V 계층 · §4.4 갭 ② 부분 해소): 조사 결과에 실린 hostname이
   `prior_targets`에 **실제로 있었는지** 대조한다. 불일치는 오류로 처리하고 사유를 남긴다
   — "엉뚱한 호스트를 조사했는데 형태가 정상이라 통과"를 막는 최소 방어다.

> **갭 ②의 잔여 한계(명시)**: 위 4는 *대상이 맞았는지*만 본다. **조사 결과의 내용이 옳은지**
> (수집은 성공했으나 값이 무의미·오래됨·잘못된 프로파일)는 **검증하지 않는다.** 완전한 V 계층은
> 평가 하네스와 골든셋을 요구하며 이는 본 계획 범위 밖이다(별도 작업). ETCLOVG 체크리스트 ④
> ("트레이스를 1차 평가 대상으로")는 W6의 감사 로그가 그 재료를 남기는 것까지만 충족한다.

**수용 기준**: 무한 루프 부재 단언, 재시도 1회 상한 단언, 미충족 사유 노출,
**`prior_targets`에 없는 hostname이 결과에 실리면 오류로 잡힌다**(4).

### W6 — 관측·감사 (**Tier 1 — 최적화의 전제**) · **D-164**

> **착수 순서 주의**(§4.6.2): 이 Wave는 **번호는 마지막이지만 순서는 Tier 2보다 앞**이다.
> W2-7·8(압축·캐시)과 W3-2·3(경로 선택·진입 게이트)은 **이 Wave의 완료를 선행 조건으로 갖는다.**
> 문서의 "자주 하는 실수" 1항 — *측정 없이 하네스를 쌓는다.*

1. 전 수집 감사: `{request_id, user_id, target, profile, commands, backend, rc, duration}` —
   stdout 원문은 **마스킹 후** 저장(D-117 §18.5 계승)
2. 실패 트레이스(`logs/trace/<날짜>/<request_id>.jsonl`)에 fan-out 단계 기록
3. 기동 로그에 **조사 경로 활성 상태**(`COMPOSITE_INVESTIGATION_ENABLED` · `sre_agent`/`mcp_server` 가용성)·플래그 확정값 1줄(사다리 로그 전례 — `observability/ladder.py`). *(v13 정정 — 구 "수집기 백엔드" 표기)*
4. **Tier 2 판별에 필요한 지표**(이것이 없으면 압축·캐시·라우팅의 이득을 판정할 수 없다):
   - **압축**: 호스트당 절단 행 수 · 축약 전후 토큰 수
   - **캐시**: 히트/미스 · 히트 시 데이터 나이(age)
   - **라우팅**: 조사 경로(`fault_diagnosis` → `sre_agent` 위임) 진입률 · 게이트 거부 사유별 건수
   - **비용 귀속**: 조사 1건당 토큰·지연(문서 6.4가 지목한 생태계 공백 — 표준이 없으므로 직접)
5. **추적에 신원·권한 상태를 함께 기록**한다(문서 표 29 O). 문서의 지적 — *"관측성 추적은 신원과
   권한 상태가 같은 세밀도로 포착될 때만 거버넌스 증거가 된다."* **W3-5**의 인가 판정 결과
   (허용/거부·사유)를 감사 레코드에 포함해야 G 계층의 증거로 성립한다.

**수용 기준**
- 실패한 조사의 **전체 경로를 추적으로 재구성**할 수 있다(문서 표 29 O).
- 4의 지표 4종이 실제로 남는다 — **Tier 2 착수 가능 판정의 근거**다.
- 감사 레코드에 인가 판정 결과가 포함된다(5).

### W7 — 미들웨어 조사 (G4 · **v7 2단 구조**) · **D-168**

> **유일한 신규 구축 영역**이다(§0.4). 78이 조사기를 만들지 않는 원칙은 여기서도 같다 —
> **요구 정의 + 결과 소비**가 78의 몫이고 구현은 각 패키지 소관이다.
> **사용자 확정(2026-08-26)**: 데이터 소스는 **향후 APM 연계**. 따라서 W7은 **2단 구조**다 —
> 1단계는 APM 일정과 **무관하게 지금 착수**, 2단계가 APM 편입이다.

#### W7-1단계 — OS 레벨 근사 (§4.7.1-A · **선행조건 0 · 즉시 착수 가능**)

APM 도입 후에도 **존치**한다(§4.7.1 — APM 미부착 미들웨어·APM 자체 장애 시 폴백).

1. **`profile="middleware"` 요구 정의** — `sre_agent`에 전달할 조사 프로파일 명세:
   - 프로세스 존재·기동 인자(힙 설정 등) — `ps`(allowlist 기보유)
   - 리스닝 포트·연결 수 — `ss`(기보유)
   - 프로세스 자원 점유 — `top -b -n 1`·`pidstat`(기보유)
   - 최근 시스템 로그 — `journalctl`(기보유)
   → **`VM_DIAG_ALLOW` 확장이 불필요**하다. 기존 명령의 **조합·해석**이 프로파일의 실체다.
2. **미들웨어 식별 규칙**(결정적): 프로세스명·기동 인자 패턴 → 미들웨어 종류 매핑을
   **선언적 파일**로 둔다(하네스 문서 표 29 G — *"정책이 코드가 아닌 선언적 파일에 있는가"*).
   LLM 추정에 의존하지 않는다(D-035).
3. **소비·표시**: 조사 결과를 브리핑에 실어 반환한다(W4 규약 재사용).

**선행 실측(축소 — R-11 갱신 반영)**: 대상 호스트에서 미들웨어 프로세스를 **OS 레벨로 식별
가능한지**(프로세스명·기동 인자 패턴)와 **조사 대상 미들웨어 종류**만 확인하면 된다.
*"폴스타가 미들웨어를 별도 엔티티로 갖는가"* 는 **APM이 정본 소스가 되면서 착수 조건에서 빠진다.*

#### W7-2단계 — APM 연계 (§4.7.2 · **D-119 경계 확장** · R-11/R-12)

**신규 아키텍처 결정이 아니다** — D-119 ①이 *"향후 관측 소스 추가도 이 경계의 확장으로 편입"*
한다고 이미 정했다. Prometheus 편입(D-119 R-B)이 그대로 청사진이다.

1. **`mcp_server`에 APM 소스 추가**(구현은 `mcp_server` 소관): `ApmConfig`(url·auth·timeout·
   expose_raw) · 고수준 도구 4종(§4.7.2) · `source_kind:"apm"` · **자격증명·타임아웃·감사 서버측
   일원화** · 벤더 질의문 노출은 **옵트인**.
2. **도구 표면은 벤더가 아니라 질문으로 정의**하고 필드명은 **OTel 시맨틱 컨벤션**에 맞춘다 —
   벤더 교체 시 **매핑 계층만 교체**(R-11 완화).
3. **식별자 정합 실측**(§4.7.3 체크리스트 6항) — **이것이 2단계 최대 리스크**(R-12).
   매칭 불가 시 매핑 테이블을 **선언적 파일**로 둔다.
4. **우선순위 전환**: 미들웨어 장애는 **APM 1차 · OS 근사 2차**. 전환은 설정으로 하고
   **APM 미가용 시 자동으로 1단계로 폴백**하되 **사유를 명시**한다(침묵 강등 금지).
5. **78 측 변경은 최소**: 소비 경로는 W3-1(고수준 도구 배선)을 그대로 쓴다 — 도구가 늘 뿐
   **새 경로가 생기지 않는다**(P14 · "적지만 더 나은 도구").

**수용 기준**
- **1단계**: 선행 실측 2항이 문서로 남는다 · **allowlist 확장 없이** 성립 · 식별이 선언적 파일로
  이뤄지고 LLM 추정에 의존하지 않는다 · 미식별 시 **사유를 남긴다**(빈 결과 금지).
- **2단계**: §4.7.3 체크리스트 6항 실측 완료 · 벤더 교체가 **매핑 계층 교체로 끝난다**(계약 테스트) ·
  APM 미가용 시 **사유를 밝히고** 1단계로 폴백 · 본체·`sre_agent`에 **신규 의존 0**.

## 7. 안전 통제

### 7.1 불변식 (D-003·D-035·D-117 계승)

- **읽기 전용** — allowlist 밖 명령 실행 불가. 변경 명령은 수집기에서 **물리적으로 제외**.
- **실행 경로 미탑재** — 권고까지만(사용자 확정 ②). 테스트로 고정(W4-2).
  **이것이 유일하게 적응형 공격에 견디는 통제다**(P9) — 방어 8종이 전부 우회된 실측(ASR>50%)이
  말하는 바는, 인젝션이 성공하는 것을 전제하고도 피해가 없으려면 **실행될 명령이 아예 없어야**
  한다는 것이다. 방어 계층을 늘리는 것으로 이 조건을 대체할 수 없다.
- **대상은 결정적 확정** — LLM이 조사 대상을 재해석하지 않는다(P2 · scope overflow 방지).
  구조적으로는 **TDG 순회**다(IPIGuard) — 외부 데이터 수신 **전에** 경로가 고정되므로,
  도구 출력에 섞인 지시문이 계획에 없는 대상·도구를 불러낼 수 없다.
- **결정적=판단, LLM=서술**(D-035) — 대상 선별·상위 N·마스킹은 코드, 서술만 LLM.
- **감사 필수** — 전 수집 기록·마스킹.
- **폐쇄망** — 외부 SaaS 전송 없음. 실 운영 데이터의 외부 API 송신 금지(D-120 계승).

### 7.2 신뢰 경계 (P4)

```
[신뢰]   사용자 질의 · 코드가 조립한 명령 · allowlist
   │
[경계]  ─────────────────────────────────────────
   │
[불신]   명령 stdout · 프로세스명/커맨드라인 · 로그 본문 · DB 행 값
```

불신 데이터는 **결정적 축약(상위 N 선별 + 시크릿 마스킹 + 길이 절단)을 거친 뒤에만** LLM 컨텍스트에
들어간다. 원문 전량은 감사 로그와 CSV 다운로드에만 존재한다.
마스킹 규칙은 `mcp_server` `process_snapshot`(D-122 ⑤: password/token/api_key/credential 값·
접속문자열 비밀번호·120자 절단)과 **동일 규칙을 재사용**한다.

### 7.3 Scope overflow 방지 체크리스트

| 위험 | 통제 |
|---|---|
| 대상 서버 오인 | 선행 결과에서 결정적 추출 · 지시어 값 배제(`_is_demonstrative_value`) |
| 프로세스 행을 서버로 오인 | `pid` 보유 행 제외(`context_resolver.py:196` 판별 재사용) |
| 대상 폭주 | `COMPOSITE_MAX_TARGETS` 상한 + 절단 명시 |
| 잘못된 DB/존 | `db_id`를 대상 튜플에 포함해 전달(위치 힌트 승계) |
| 허용 명령 우회 | prefix 포섭 케이스 테스트(`ip link set`·`dmesg -C`·`journalctl --vacuum`) |

### 8.3 자율성 3단계로 넘어가려면 (본 계획 범위 밖)

승인 게이트 후 변경 명령 실행(성숙도 3단계)은 다음이 **모두** 선행해야 한다 —
현재 전부 미해결이므로 본 계획은 2단계에서 멈춘다.

1. **D-003 명시적 예외 신설**(Plan 64 §8.3 B-3 — 최대 블로커)
2. 승인 인터럽트 UX(HITL) · 승인 주체·권한 모델
3. blast radius 한계·롤백 절차·policy-as-code
4. 실행 감사·사후 검증(Verify 실패 시 자동 롤백)
5. **적응형 공격 평가**(P9) — Adaptive Attacks(NAACL Findings 2025)가 8종 방어를 전부 우회하며
   권고한 필수 절차다. 실행 능력을 여는 순간 "인젝션 방어를 넣었다"로는 불충분하고,
   **적응형 공격 하에서의 잔여 위험**을 측정해야 한다. 조사 대상 서버의 프로세스명·로그 본문이
   곧 공격면이므로(§7.2 불신 영역), 이 항목은 형식적 절차가 아니다.

> **주의**: 위 5개는 순차 체크리스트가 아니라 **동시 충족 조건**이다. 특히 5는 1~4를 다 갖춘
> 뒤에도 독립적으로 실패할 수 있다 — 방어의 존재가 아니라 **측정된 잔여 위험**이 판정 기준이다.

대상을 정확히 전달해도 엉뚱한 DB를 조회한 결과를 넘긴다.

**두 개의 게이트는 중복이 아니라 직교한다** ★

79 C-3②(저신뢰 → 비싼 경로 차단)와 78 W3-2(요구 유형별 경로 선택)가 같은 목적처럼 보이나
**축이 다르다.**

| | 79 C-3② | 78 W3-2 |
|---|---|---|
| 묻는 것 | **얼마나 확신하는가**(신뢰도) | **무엇이 필요한가**(요구 유형) |
| 위치 | 라우팅 직후 | 조사 경로 진입부 |
| 판정 실패 시 | 되묻기 | 가벼운 경로로 강등 |

→ **AND로 결합한다**: *요구 유형이 조사를 가리키고* **그리고** *신뢰도가 충분할 때만* 진입.
어느 하나라도 불충족이면 진입하지 않는다. 두 게이트를 하나로 합치지 않는다 — 실패 처리가 다르다.

**공유 자산**

| 자산 | 78 | 79 |
|---|---|---|
| `src/orchestration/subagents.py` | `_make_isolated_input` 부근(prior_targets 주입) | `:166` 임계 필터 | 
| 감사 레코드 | 조사·인가·Tier 2 지표(W6) | 신뢰도·분포·엔트로피(C-2·C-3③) | **한 스키마로 통합**한다 |
| `plans/78` P12·P13·P14 | 원출처 | 79가 인용(비싼 경로·측정 우선·KV 캐시) |

> **파일 충돌 주의**: 같은 `subagents.py`를 양쪽이 수정한다(위치는 다름). **79를 먼저 랜딩**하고
> 78이 그 위에 얹는 순서를 권장한다 — 79의 임계 재설계(C-4)가 후보 집합을 바꾸므로,
> 78이 먼저 들어가면 78의 회귀 기준선이 79 착수 시 무효가 된다.

### 8.5 운영 — 구축 후 유지 (§3.4.3 · **P15**)

구축이 끝나면 유지가 시작된다. 두 가지 지속 활동을 둔다.

**① 관측(O)과 검증(V)을 하나의 피드백 루프로 묶는다**

추적 도구와 평가 프레임워크는 서로 다른 인터페이스로 발전해 실무에서 단절되기 쉽다. 연결 방식:

- **프로덕션 실패 추적에서 회귀 테스트를 생성**한다 — 조사 실패(인가 거부·백엔드 오류·대상 불일치)가
  발생하면 그 케이스를 회귀 스위트에 편입해 재발을 막는다.
- 이 프로젝트에는 이미 실패 트레이스(`logs/trace/`)와 골든셋 회귀 경로가 있으므로
  **새 인프라가 아니라 연결만** 필요하다.

**② 주기적으로 덜어낸다 — 모델 업그레이드 점검**

본 계획이 추가하는 구성요소는 전부 **"모델이 스스로 하지 못한다"는 가정**을 부호화한다.
모델이 개선되면 그 가정이 낡고, 낡은 구성요소는 순비용이 된다.

| 점검 대상(본 계획 산물) | 질문 | 제거 후보의 신호 |
|---|---|---|
| 해석 3단의 **LLM 컬럼 지목**(W1-3) | 결정적 매칭 없이도 컬럼을 맞히는가 | 1·2단 적중률이 3단과 차이가 없어진다 |
| **결정적 교정 가드**(P6 · `_coerce_*`) | 도구 오분류가 줄었는가 | 가드를 꺼도 오분류율이 오르지 않는다 |
| **진입 라우팅 게이트**(W3-2·3) | 모델이 스스로 비싼 경로를 아끼는가 | 게이트 거부 건수가 0에 수렴한다 |
| **2단 축약**(W2-7) | 더 긴 컨텍스트를 안정적으로 다루는가 | 축약 유무의 응답 품질 차가 사라진다 |
| **재계획 1회**(W5-2) | 1차 시도 성공률이 올랐는가 | 재계획 발동률이 0에 수렴한다 |

- 판단 방법은 일률적으로 **"제거하고 A/B로 측정한다"** 이며, **Tier 1의 측정 능력이 전제**다(P13).
- 이 점검은 **D-161(승격–폐기 동반 원칙)** 의 적용 사례로 다룬다 — 폐기 제안 시 D-161 ② 4항
  실측을 그대로 요구한다.

### 11.5 조사에서 확인한 공백

- **HITL 승인·blast radius**의 동료심사 문헌은 빈약하다(검색 결과 대부분 preprint·비심사 저장소).
  §8.3의 3단계 진입 요건은 문헌 합의가 아니라 **산업 관행 + 본 프로젝트 D-003**에 근거한다 —
  이 점을 인지하고 3단계 착수 시 별도 조사가 필요하다.
- **원격 명령 실행 에이전트의 안전성**을 직접 다룬 동료심사 연구는 찾지 못했다. 인접 근거
  (action-boundary·인젝션 방어·allowlist 실무)로 대체했으며, 이 공백 자체가 §7.1의 보수적 자세
  (실행 경로 미탑재)를 지지한다.
- **컨텍스트 압축·에이전트 메모리 주제의 OpenAlex 색인 공백(v4)**: 이 두 주제를 제목·초록 검색으로
  조회하면 **2026년 preprint(인용 0)만** 잡히고 확립 문헌이 나오지 않는다. 실제 표준 문헌
  (LLMLingua = EMNLP 2023 · 125 cites, MemGPT = 52 cites)은 **다른 검색어로만** 도달했다.
  → 교훈: OpenAlex 주제 검색이 비면 "문헌이 없다"가 아니라 **검색어가 그 분야의 관용어와 다르다**를
  먼저 의심하고, 대표 기법명(고유명사)으로 재조회한다.
- **2차 인용 검증 실패 1건(v3에서 정정)**: 초안은 "OWASP AIVSS가 인터프리터 도구 공격에
  **CVSS v4.0 9.4**를 부여한다"고 적었으나, 이는 기술 블로그(2차 출처)의 전언이었고
  **OWASP 공식 문서에서 해당 수치를 확인하지 못했다**. 검증된 진술(Tool Misuse = 10대 핵심 위험,
  인터프리터 보유가 내재 위험을 높인다)로 교체했다. → 교훈: **수치는 1차 출처에서 확인되기 전까지
  계획서에 싣지 않는다**(CLAUDE.md 실측 우선 원칙의 문헌판).
