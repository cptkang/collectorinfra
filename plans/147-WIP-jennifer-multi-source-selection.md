## 1. 결론

### 1.1 한 줄

소스 N개를 붙이는 게이트웨이와 이름 지목의 기반은 이미 있다(`plans/87` J8 · `plans/134` M-5). 이 계획은 **채팅에서 고른 소스만 조회**하는 선택 규칙을 완성한다 — ① 레지스트리 소스 행마다 **사전 정의 단어**(위치어·이름)를 두고 제니퍼는 그 목록만 본다 ② 단어가 소스 둘 이상에 걸리거나 **아무 지목이 없으면 조회 전에 되묻는다**(선택지 = 걸린 소스 / 전 소스 + 「전체」) ③ 되묻기 답·말 지목·화면 선택은 **같은 대화에서 승계**한다 ④ 화면 스코프 칩에 「제니퍼 소스」 축(보조) ⑤ 소스 추가는 **게이트웨이 `.env` + 레지스트리 한 행**으로 끝나고, 두 정본의 불일치는 기동 점검이 잡아 선택지에서 뺀다. 소스가 1개인 배포 · APM 비활성 배포는 바이트 불변이다.

|---:|---|---|
| 1 | **이번 턴 화면 선택·되묻기 답**(요청 본문의 제니퍼 소스 선택 — §4.3) | 그 소스(들) · 승계 갱신 |
| 2 | **이번 턴 원문의 소스 단어**(§4.2) ∪ 분해 LLM `sources`(기존 칸 · 보조) | 걸린 소스가 1개 → 그 소스 · 2개 이상 → **되묻기**(선택지 = 걸린 소스) · 승계 갱신 |
| 3 | **승계** — 같은 대화의 직전 선택(단 1·2의 결과) · 지시어 후속이면 직전 대상 행의 `apm_source_id`(130 M-5) | 그 소스(들) · 「승계 중」 고지 |
| 4 | 없음 | 소스 ≥2면 **되묻기**(선택지 = 사용 가능 소스 + 「전체」) · 소스 1개면 그 소스(현행) |

- **되묻기는 조회 0**이다 — 그 task는 「조회 안 함 + 되묻기」로 끝나고, 같은 질의의 다른 task(폴스타 등)는 그대로 진행한다(부분 답 + 되묻기). 재계획 대상에서 뺀다(D-293 ⑤ 소스 불가 종결과 같은 결).
- **「전체」** 답은 「전 소스」 선택으로 승계된다(다음 턴부터 되묻지 않음).
- **분해 LLM `sources`와 단어가 다르면**: 단어(결정적)가 이긴다 · LLM만 냈으면 그 값을 쓴다(기존 `_plan_sources` 검증 재사용). LLM `sources`만으로 2개 이상이면 단 2와 같이 되묻는다.
- **모르는·미연결 소스**: 레지스트리에 없는 id는 버린다(기존). 기동 점검에서 미연결로 판정된 소스만 걸리면 조회하지 않고 안내만 한다(넓히지 않음 · D-290 ⑥).
- **대상 해석과의 순서**: 소스를 먼저 정하고, 대상 텍스트(인스턴스·업무명 — 130) 검색은 정한 소스 안에서만 한다(현행 `apm_query.py:2667` 규칙). 되묻기면 검색도 0이다.
- **배치**: 순수 함수는 `src/routing/`(infrastructure — 레지스트리와 같은 층)에, 호출은 `apm_query`(application). `arch_check` 방향 위반 0.

### 4.2 소스별 사전 정의 단어(레지스트리 `sources[].terms`)

```yaml
sources:
  - {id: bank,   label: 은행존 제니퍼, zone: bankjon,
     terms: ["은행존", "은행", "K리전", "은행존 제니퍼"]}
  - {id: common, label: 공동존 제니퍼, zone: gongjon,
     terms: ["공동존", "공동", "김포", "여의도", "운영", "개발", "스테이징", "DR", "공동존 제니퍼"]}
  - {id: legacy, label: 레거시 제니퍼, zone: bankjon,
     terms: ["은행존", "은행", "레거시", "레거시 제니퍼"]}
```

(값은 예시 — 확정 목록은 W1에서 사용자 확인. 운영 용어 「운영」·「개발」 등은 D-271 제외어 규칙을 그대로 따른다.)

- **정본 = 레지스트리 한 곳.** 소스를 추가할 때 이 칸을 함께 적는다. 제니퍼는 이 목록만 본다(폴스타 `locations` 비참조 — R-2).
- **같은 단어의 여러 소스 등재 허용**(R-3) — 로드 검증은 형식(빈 문자열·중복 단어 같은 행 안)만 거부한다. 「한 단어가 두 소스」는 정상이며 되묻기로 처리된다.
- **매칭**: 기존 `term_in_text`(라틴 단어 경계·대소문자 무시) · D-271 제외어(「운영체제」·「운영 중」·「운영자」·「운영팀」) 재사용 · 긴 단어 우선(「은행존 제니퍼」가 걸리면 그 안의 「은행존」은 따로 세지 않음).
- **D-293과 분리**: 이 단어는 **시스템 유사어가 아니다** — `source_alias_terms()`·`target_db_hints`에 넣지 않는다(넣으면 「김포」가 APM 처리기 고정(D-293 ③)을 일으킨다). APM task가 생긴 뒤 `apm_query` 안에서만 쓴다. 시스템 지목(「제니퍼」·「APM」)은 종전대로 D-293이 처리한다.
- **원문 범위**(W0 실측 · 검증 교정 2026-10-08로 확정): **task 질의(`sub_query`)에 소스 단어가 걸리면 그것만** 본다 · task 질의에 단어가 0건일 때만 턴 원문(`original_user_query`)을 본다 — 복합 질의에서 폴스타 task의 위치어(「김포 서버 CPU와 레거시 WAS」의 「김포」)가 APM task 판정에 섞이지 않게 한다. W0 실측(MLX 2문항)에서 분해는 위치어를 APM task 질의에 남겼다.

### 4.3 되묻기·화면 — 스코프 칩 「제니퍼 소스」 축

- **되묻기 UI**: 존 선택 역질문(`renderZoneClarification`)과 같은 체크박스 블록 — 선택지 = 걸린 소스(또는 전 소스 + 「전체」) · 확인 → 같은 질문을 선택과 함께 다시 보낸다. 사용자가 「공동존」처럼 **글로 답해도** 단 2(소스 단어)로 성립한다.
- **요청 칸**: `selected_apm_source_ids`(신규 · 요청 스코프) — 시스템 단위 `selected_sources`(plans/132 N-10)와 의미가 달라 섞지 않는다. 서버는 레지스트리 ∩ 사용 가능 소스로 검증한다.
- **스코프 칩 축**: `/scope/options`에 축 `apm_source`(옵션 = 사용 가능 소스 · 라벨 · 존)를 **APM 활성 ∧ 사용 가능 소스 ≥2 ∧ 사용자 `apm` 권한**일 때만 더한다(`scope.py:3` 주석이 예정한 축 추가 · 엔드포인트 불변). 칩 텍스트: 「제니퍼: 공동존 제니퍼 · 선택/승계 중」 · × 해제 = 승계 끊기(다음 질문부터 다시 되묻기).
- **승계 저장**: 스레드 상태에 `apm_source_scope`(소스 id 목록 · 근거 `selected|named|answered|all`) — 체크포인터는 델타만 병합하므로 **라우트에서 요청 스코프 칸을 명시 초기화**하고, 승계 값은 별도 키로 둔다(Known Mistakes 멀티턴). 응답 메타에 현재 값을 실어 칩이 그린다.
- **매뉴얼 동반(D-255)**: 사용자편(소스 고르기 · 되묻기 · 승계·해제 · 고지 읽기) · 관리자편(소스 추가 절차 · 단어 목록 · 정합 점검 카드).

### 4.4 소스 추가 = 설정만 + 정합 점검

**추가 절차(코드 0)** — `docs/31` §4.2·§4.4를 체크리스트로 고쳐 쓴다:
1. 게이트웨이 `apm_gateway/.env`: `JENNIFER_SOURCES`에 id · `JENNIFER_<ID>_API_URL`·`_API_TOKEN`(AIOps 전용 토큰) · 선택 키
2. 루트 `config/db_registry.yaml` `solutions[apm].sources[]`에 `{id, label, zone, terms}` 한 행
3. 게이트웨이 → 본체 재기동 → 기동 로그·관리 화면 정합 결과 확인 → 「〇〇 제니퍼 인스턴스 목록」으로 확인
4. (선택) `apm_gateway/config/instance_map.yaml`의 `per_source`·`overrides`

**정합 점검(신규)**:
- 본체 기동 시 APM 활성이면 `gateway_health`를 1회 부른다(짧은 타임아웃 · 실패해도 기동 계속). 결과: `레지스트리∖게이트웨이`(미연결 — **선택지·화면 축에서 뺀다** · R-7) · `게이트웨이∖레지스트리`(존·단어 미상 — 선택 불가 · 알람은 전 존 구독자만) · 소스별 도달·도메인 수. 로그 1줄(비밀 값 0).
- **점검 실패(게이트웨이 다운)** 시에는 레지스트리 전 소스를 사용 가능으로 본다(선택지를 비우지 않는다 — 조회 시 게이트웨이 오류는 종전 실패 고지).
- 분해 프롬프트의 소스 칸(`render_source_line`)은 **레지스트리 기준 그대로** 둔다 — 기동 시점 게이트웨이 상태에 프롬프트가 흔들리지 않게(렌더 지문 결정성). 미연결 소스는 단 2·4에서 걸러진다.
- 관리 화면 대시보드 「제니퍼 소스」 카드(id·라벨·존·단어 수·게이트웨이 설정·도달·도메인 수 · 불일치 강조) + 관리 API 1개 · CLI `scripts/apm_source_check.py`(배포 전 — 레지스트리와 게이트웨이 `.env`의 `JENNIFER_SOURCES`를 파일로 대조 · 토큰 값은 읽지 않음). 주기적 재점검은 하지 않는다(재기동 시 갱신 — 필요해지면 별도).

### 4.5 답 표시

- 소스 ≥2 배포의 결과 표에 「소스」 칸을 **레지스트리 라벨**로(모르는 id는 원문) · 소스 상태 행(`plans/125` C-2)에 소스별 「조회 n건 / 실패(사유) / 선택 밖」.
- 좁힌 근거 고지 1줄(의무·중립): 「공동존 제니퍼만 조회했습니다(근거: 「김포」)」 · 「… (이전 선택 승계)」 · 「… (화면 선택)」.
- W0에서 현행 표시를 먼저 실측한다 — 이미 라벨이면 상태 행만 더한다.

### 4.6 소스 수 증가 대비

- 「전체」 선택은 전 소스 fan-out — 소스 N에 비례(`plans/130` B2 콜드 캐시). 되묻기·단어 선택이 일상 질의를 1~2소스로 줄인다.
- W4에서 목 게이트웨이 소스 5개(지연 1 포함)로 응답 시간·부분 실패 고지를 잰다(로직 확인 — 지연 결론은 내부망).
- 되묻기 선택지·칩 축은 소스 수만큼 늘어난다 — N ≤ 10 가정에서 배치만 확인.

### 4.7 플래그

신규 `enable_*` 없음(R-8). 활성 = APM 활성 ∧ 레지스트리 소스 ≥2. 그 밖의 배포는 바이트 불변(D-162 · `render_source_line` 전례). **「신규 기능 기본 off」 원칙의 예외**이고, 소스 ≥2 배포에서는 「지목 없음 = 전 소스」가 「되묻기」로 바뀌는 **동작 변경**이다 — 근거는 D-322 본문과 레지스트리 `sources` 주석에 적는다.
