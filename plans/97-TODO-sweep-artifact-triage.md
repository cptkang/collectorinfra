## 0. 한 줄 결론

**7GB를 다 분석할 필요가 없다 — 다 반출할 필요도 없다.**
config 처분에 실제로 쓰이는 것은 **arm 당 `raw.jsonl` + `summary.json` + 서버 로그 머리 20줄**이고,
동형 산출물 기준 **전체의 0.1% 미만**이다. 나머지 99.9%는 **체크포인트 DB(용량의 98.6%)**와
**`schema_analyzer` 디버그 덤프(서버 로그의 65%)**이며, **축 판정 코드는 그 둘을 한 줄도 읽지 않는다**
(`scripts/bench/sweep.py:303` `read_observations(raw_path)`가 유일한 입력 경로).

그리고 분석보다 먼저 답해야 하는 질문이 하나 있다 — **이 스위프가 판정 자격이 있는가**.
`plans/96`이 확정한 대로 직전 run 은 **383턴 중 103턴(26.9%)이 러너 JWT 만료로 무효**였다.
다만 그 원인은 "실행이 길어서"가 아니라 **프로파일이 하나뿐이어서**다 — 러너는 프로파일(=arm)마다
서버를 새로 띄우고 **새로 로그인**하며(`runner.py:507`·`532`), 그 run 은 `baseline` 단일 프로파일로
**연속 7.52시간**을 돌아 8시간 수명에 닿았다(실측 2026-09-16: 첫 401이 **281번째 턴 · 누적 7.52시간**,
`run.json`의 `profiles[].reasons`는 비어 있고 `echo_ok=true`).
**따라서 62 arm 스위프는 arm 당 10~30분이면 구조적으로 안전하다** — 만료 위험이 남는 경로는 둘뿐이다:
**①`--token`/`--admin-token` 주입**(`runner.py:420-421`이 런 전체에서 그 토큰 하나를 재사용한다)
**②단일 arm 이 6.4시간(8h의 80%)을 넘는 워크로드**. 그럼에도 Phase 0 에서 무효율은 잰다 —
401·INVALID 는 만료 말고도 기동 실패·계정 미지정·에코 불일치에서 나오고, 확인 비용이
**로그 본문을 열지 않고 10분**이기 때문이다.

## 2. config 개선에 필요한 파일 — 3등급

`plans/93` §6.5.1의 입력 신호 6종을 출처로 되짚으면 이렇게 갈린다.

| 신호 | 출처 | 7GB 안에 있나 |
|---|---|---|
| L1 정합 · L2 값역·기동 · L3 주입 실효 · L4 소비 실증 | `python -m scripts.bench`(트랙 T) 산출물 — `config_health.md`·`coverage_ledger.md` | **아니다** (별도 실행 · 총 120 KB) |
| **L5 성능 판정** | **`raw.jsonl`** | 그렇다 (arm 당 ~1 MB) |
| 정적(참조 수·`.env` 실제값·경과일) | `optimize.py`가 코드·git에서 수집 | **아니다** |

→ **§6.5.2의 처분 규칙 13행 중 7행(0-a~0-d·1·2·9)은 7GB를 한 줄도 읽지 않고 확정된다.**
L5가 필요한 것은 3~8행뿐이고, 그 입력은 `raw.jsonl`이다.

### Tier A — 반드시 확보 (arm 당 ~1.2 MB)

| 파일 | 왜 |
|---|---|
| `raw.jsonl` | L5의 유일 입력. 턴별 `func_verdict`·`wall_ms`·`node_elapsed_ms`·`node_path`·`executed_sqls`·`failed_assertions`(expected/actual 전문 포함)를 이미 담는다 |
| `summary.json` | 집계 · `failures` · `scenario_verdicts` · `silent_wrong_total` · `meta`(커밋·dirty·provider·platform) |
| `run.json` / `run_meta.json` | 어느 커밋·어느 설정으로 쟀는지. **없으면 어떤 판정도 근거가 되지 못한다**(D-161 ①) |
| 서버 로그 **머리 20줄** | `src.graph: 그래프 빌드 완료(orchestration=…)` · `src.observability.ladder: 사다리 확정 tier=…` — **arm 의 설정이 실제로 먹었는지의 유일한 증거**. 93 v8 사고("설정 에코 미확인"이 통과로 집계돼 62 arm 전부 `valid=true`)가 정확히 이 줄을 안 본 결과다 |

### Tier B — 원인 분류용 (grep 추출 · arm 당 수십 KB)

- 서버 로그 `[ERROR]` **전량**(동형 기준 28줄) — SQL 실행 실패·방언 오류·FabriX 상한 초과가 여기 다 있다
- `[WARNING]` 중 `SQL 검증 실패|폴백|강등|만료|타임아웃` 매칭 라인
- `artifacts/*.xlsx` — 폼필 H·I군 판정 (96 C-2: 미리보기 금지, 전 칼럼 판독)
- `axis_verdicts.md` — 스위프가 스스로 낸 축 판정(대조용)

### Tier C — 반출하지 않는다

- **`checkpoints-*.db` 원본** — 용량 98.6%. 판정 코드가 읽지 않고, `raw.jsonl`에 `thread_id`가 없어
  **직접 조인할 키조차 없다**(scenario_id 경유 매핑 필요). 필요한 건 §1.3의 9개 키뿐
- 서버 로그의 `schema_analyzer DEBUG[N]` 라인 — 65%

## 3. 단계 계획 — Phase 0~6

> **원칙 3가지**: ①**축소는 서버에서** 한다(반출량이 곧 절차 비용) ②각 Phase 는
> **조기 종료 조건**을 갖는다 ③**앞 Phase 의 산출물만** 입력으로 쓴다(뒤로 갈수록 대상이 줄어든다).

### Phase 0 — 판정 자격 선별 *(서버 · 로그 본문 미열람 · 10분)*

| # | 확인 | 방법 | 불합격 시 |
|---|---|---|---|
| 0-1 | arm 인벤토리 | 폴더별 파일 수·크기 집계 | — |
| 0-2 | provenance | `run.json`·`summary.json:meta`의 commit·dirty·provider·host | dirty면 재현 불가로 표기 |
| 0-3 | **401 무효율** | arm별 `raw.jsonl`의 `error`에 `401` 포함 턴 비율 + `run.json`의 `profiles[].valid`·`reasons`(`로그인 실패`·`http 401`) + **arm 당 연속 실행 시간**(`wall_ms` 누적 vs 6.4h) + `--token` 사용 여부 | **>5%면 조기 종료 A** |
| 0-4 | **설정 에코** | arm별 서버 로그 `head -20`의 `tier=`·`orchestration=` | 에코 없는 arm은 판정 대상 제외 |
| 0-5 | 완주율·SQL 생성률 | `raw.jsonl`의 `response_mode`·`executed_sql` (93 §4.3.1 2순위 신호) | 기준선 대비 급락이면 arm 무효 |

**조기 종료 A** — 무효율 5% 초과: **분석을 시작하지 않는다.** `plans/96` T-1(토큰 수명 관리)을
먼저 반영하고 재측정한다. 7GB 는 삭제하지 말고 서버에 보관한다(재측정 후 대조용).
**조기 종료 B** — 유효 arm 이 축당 2개 미만: 그 축은 「판정 불가」로 고정하고 §6.5.2 7행(보류)으로 보낸다.

> **이 Phase 가 계획의 핵심이다.** 무효 표본을 유효로 세면 **없는 신호를 해석하게 된다** —
> 96 §1 에서 리포트의 「과잉 거부 의심」 26건이 **전건 401 구간**이었던 것이 그 실물이다.
> 스위프의 만료 위험 자체는 §0 의 두 경로로 한정되지만, 이 10분은 *만료를 의심해서*가 아니라
> **판정 자격을 세지 않은 채 7GB 를 파지 않기 위해** 쓴다.

### Phase 1 — 축소본 추출 *(서버 · 10~20분 · 산출 ~30 MB)*

`scripts/bench/triage.py`(신규 · §6) 한 번 실행으로 반출 패키지를 만든다.

| 추출 | 방법 | 예상 크기(62 arm) |
|---|---|---:|
| `raw.jsonl` 전량 | 그대로 복사 | ~60 MB → **gzip ~8 MB** |
| `summary.json`·`run.json`·`axis_verdicts.md`·`report.md` | 그대로 | ~10 MB |
| 서버 로그 머리 40줄 + `[ERROR]` + 지정 WARNING | grep | ~2 MB |
| 체크포인트 9키 축소본 | thread별 최종 1건 디코드 → `state_digest.jsonl` | ~40 MB |
| `artifacts/` | H·I군 우선(전량이어도 130 MB) | 선별 시 ~10 MB |

**제외**: 체크포인트 원본 · `schema_analyzer DEBUG` 라인. **검증**: 패키지에 arm 수 × Tier A 4종이
빠짐없이 들어갔는지 매니페스트로 확인(누락은 침묵 폴백이 아니라 실패로 보고 — Known Mistakes).
**반출**: 기존 폐쇄망 반출 절차를 따른다. `raw.jsonl`에는 **질의문과 생성 SQL 전문**이 들어간다(93 A.6).

### Phase 2 — 건전성 관문 *(반출 후 · 30분)*

93 §4.3.2 관문 + 96 §1 방식으로 **arm별 유효 표본을 재산정**한다. 산출은 표 하나 —
「판정 자격 있는 arm 목록」. 이후 Phase 는 이 목록 밖을 보지 않는다.

### Phase 3 — L5 축 판정 *(1시간 · 입력은 `raw.jsonl`뿐)*

`read_observations` → 축별 `채택 권고`·`조건부`·`기각`·`차이 없음`·`판정 불가` 5값.
93 §5.3대로 **노이즈 상한과 검정력을 함께 적는다**(26건 골드셋으로는 10%p 미만이 안 잡힌다).
**여기까지가 config 최적값 결정에 필요한 전부다.** 로그 본문은 아직 한 줄도 열지 않았다.

### Phase 4 — 실패 원인 분류 *(2시간 · Tier B)*

**순서를 지킨다** — 96 §3의 허위 불합격 필터를 **먼저** 적용하고(I군 픽스처 미매핑 열·
`filled_rows`·`row_count` 합산·리터럴 단언 4종), 남은 불합격만 `[ERROR]` 라인과 대조한다.
거꾸로 하면 판정 계약 버그를 제품 결함으로 오분류한다.

### Phase 5 — 선택적 심층 *(조건부 · 체크포인트 축소본)*

조용한 오답 후보와 수동 검토 잔여 **한정**으로 `state_digest.jsonl`의 `final_response`를 읽는다.
**전량 판독은 하지 않는다** — 96이 이미 "수동 검토 66%"를 구조적 결함으로 확정했고,
그 해소는 러너 개선(D-218 ⑤)이지 로그 정독이 아니다.

### Phase 6 — 처분 결정과 롤아웃

93 §6.5.2 결정 절차에 Phase 3·4 결과를 넣고, §6.6 R0~R4 순서로 반영한다.
**R0(결함 수정)이 간소화보다 앞이다.** 이 Phase 의 정본은 93이며 이 계획은 입력만 공급한다.

## 4. "전체를 다 분석해야 하는가"에 대한 답

**아니다.** 근거 넷 — 전부 실측이다.

1. **판정 경로가 하나다** — 축 판정의 입력은 `raw.jsonl` 뿐이다(`sweep.py:303`).
2. **용량과 신호가 반비례한다** — 용량 98.6%인 체크포인트의 판정 기여는 0이고,
   0.08%인 `raw.jsonl`이 L5 전부를 담는다. 로그도 65%가 디버그 덤프이고 `[ERROR]`는 0.16%다.
3. **처분 13행 중 7행은 로그와 무관하다** — L1~L4·정적 신호는 트랙 T 와 코드 grep 에서 나온다.
4. **필요한 정보는 이미 구조화돼 있다** — `raw.jsonl`은 노드별 경과시간·노드 경로·실행 SQL·
   실패 단언의 expected/actual 을 행마다 담는다. 로그를 풀어 재구성할 것이 없다.

**다만 "다 분석하지 않는다"가 "일부만 본다"는 아니다** — `raw.jsonl`은 **전 arm 전량**을 본다.
버리는 것은 **동일 정보의 원시 중복본**(체크포인트·디버그 덤프)이지 표본이 아니다.

## 9. 신규 결정 예약 — D-219

**벤치 스위프 산출물의 분석·반출 계약**:
①**판정 입력 단일화** — 축 판정의 입력은 `raw.jsonl`이며, 체크포인트 DB 와 노드 디버그 로그는
판정 경로가 아니다(실측: 용량 98.6%가 기여 0) ②**축소는 서버에서** — 폐쇄망 산출물은 원본이 아니라
축소본을 반출한다(≤50 MB · 체크포인트 원본 반출 금지 · 원본은 재측정까지 보관) ③**판정 자격 관문 선행** —
무효 표본률(401 등) 5% 초과 run 은 분석 대상이 아니라 재측정 대상이다(D-218 T-1 연계). 만료 위험은 arm 수가 아니라
**①토큰 주입(`--token`) ②단일 arm 연속 6.4시간 초과** 두 경로에 한정된다 — 러너는 프로파일마다 재로그인한다(실측) ④**설정 에코가
arm 유효성의 정본** — 기동 로그의 `tier=`·플래그 에코가 없는 arm 은 판정에서 제외한다(93 v8 재발 방지)
⑤**축소 사실의 기록 의무** — 제외 규칙과 제외량을 매니페스트에 남긴다(침묵 폴백 금지).
대안(기각): 전량 반출 후 분석 · 표본 추출(arm 일부만) · 체크포인트 상시 비활성화.
