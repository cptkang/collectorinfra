## 0. 요약

### 0.1 결론

| 질문 | 답 | 근거 |
|---|---|---|
| 왜 「제니퍼의 인스턴스 리스트」가 DB 조회로 가나 | **소스를 고르는 단계가 따로 없다.** 처리기(agent) 선택이 곧 소스 선택이고 기본값은 `data_query`(SQL)다. 제니퍼 처리기는 ① 2단 경로 ② `MCP_SOURCE_ENDPOINTS`에 `apm` ③ 사용자 소스 권한이 **모두** 맞을 때만 계획 LLM에 보인다. 하나라도 빠지면 LLM은 제니퍼의 존재를 모르고 `data_query` → SQL DB 분류 → 첫 활성 DB(폴스타)로 간다 | §3 C2·A·D · §4 S-1~S-5 |
| 사용자 보고가 재현되나 | **재현된다(2단 · APM 끔 — C2).** 「제니퍼의 인스턴스 리스트」 → 폴스타 SQL(제니퍼를 값으로 취급 · 211초). 더 위험한 것은 「WAS 인스턴스 목록」 → 폴스타 등록명에 「WAS」가 든 서버 2대를 **「WAS 인스턴스 2건」으로 답한 그럴듯한 오답**(고지 없음 · 255초) | §3 C2-1·C2-2 · O-10 |
| 제니퍼를 연결하면 해결되나 | **아니다(실측).** 2단 + 제니퍼 연결 상태에서도 ① 계획 LLM이 보기(`views`)를 비워 **응답시간 보기**로 갔고(목록 보기 아님) ② 제니퍼가 인스턴스 0건(`source_unavailable`)을 돌려주자 **재계획 LLM이 「다른 도메인(인프라 DB)」으로 재조회 task를 3회 추가**해 폴스타 SQL을 만들었다(SQL 오류 4회 · 314초) | §3 B arm · §4 S-6·S-7 |
| 폴스타가 최우선인가 | 하드코딩된 기본 DB는 채팅 경로에 **없다**. 대신 「분류 실패 → `ACTIVE_DB_IDS` 첫 항목」 폴백, 분류 예시의 폴스타 편중, 입력 파서 어휘의 폴스타 전제, 승계 신호어 부재가 겹쳐 **결과적으로 폴스타로 수렴**한다 | §4 S-8·S-9 |
| 기존 계획이 덮나 | **설계는 있다**(121 P-12 「LLM은 영역·명시 소스만, 소스 결정은 코드」 · 125 B-2 명시 소스). 그러나 ① 4개 계획에 흩어져 있고 ② 핵심 항목이 측정 게이트 뒤에 묶여 있으며(125 B-2·B-3·B-7 = R7 · 121 TP-2.2 = G-31 · TP-9 = G-32) ③ **「소스 불가 → 다른 소스로 대체하지 않음 · 재계획하지 않음」(125 §4.6)은 계약만 있고 재계획기에 구현이 없다** | §5 |
| 사용자에게 소스를 물어야 하나(의견 ③) | **모호할 때만 묻는다.** 잘못 추측한 비용(실측 164~314초 · 엉뚱한 소스의 답)이 선택 질문 1턴(결정적 칩 · LLM 0)보다 훨씬 크다. 그러나 사용자가 소스를 이미 말했거나(「제니퍼의 …」) 그 정보를 가진 소스가 하나뿐이면(WAS 영역 = 제니퍼 — 의견 ④) 묻는 것은 같은 답을 두 번 받는 셈이다. 존 되묻기와 겹치면 한 질문으로 합친다 | §6.3 N-10 · G-8·G-9 |
| 소스 선택을 기억해 두었다가 참고하나(요청 ⑤) · 저장소는 | **기억한다 — 사용자가 확인한 선택만.** 소스 선택 칩에서 고른 결과·정정·관리자 정리 사례만 저장하고(시스템이 스스로 고른 소스는 저장 금지 — 오염 자기강화 차단), 「소유 소스 2개+ · 명시 없음」일 때 되묻기 **전에** 참고한다. 명시 소스·단독 소유 판정은 뒤집지 않는다. **저장소는 Redis(현행) + 인프로세스 검색(어휘 → 선택적 임베딩 numpy)** — 예상 규모가 수천 건이라 벡터 DB가 풀 문제가 없고, 양식 기억(D-151)·질의 이력(D-133)·유사어 임베딩(D-084)과 같은 모양이다. 수만 건·다중 인스턴스·공용 벡터 인프라(`plans/129`) 중 하나가 생기면 옮긴다 | §6.5 · G-10~G-12 |
| 유사어는 소스마다 따로인가(요청 ⑦) | **지금은 아니다(실측).** 소스 이름(유사어 1층)만 레지스트리 항목별로 따로 있고, 컬럼·값 유사어는 **소스 귀속 없는 전역 사전**이 있어 컬럼 이름만 같으면 다른 DB에 붙는다. 채팅 등록은 항상 전역에도 쓰고, DB를 못 정하면 활성 DB 전부로 퍼진다. 제니퍼·문서·Prometheus는 유사어 저장소가 없다. 「인스턴스·이벤트·담당자·업무」는 소스마다 뜻이 다르다. **권고: 유사어를 4층(소스 이름 · 소스 어휘 · 스키마 · 대상)으로 나누고 층마다 소스(시스템) 귀속 네임스페이스에 둔다 — 「전역」은 같은 시스템 안 공유로 좁히고, 소스가 정해진 뒤에만 그 소스의 유사어로 해석한다** | §6.6 · G-13~G-17 |
| 권고 | **소스 선별 단계를 계획 호출 안에 명시적으로 세운다(추가 LLM 0).** 명시 소스 인식(결정적) → 영역 선별(LLM) → 소유·활성·권한 판정(코드) → 선별된 소스 안에서만 처리기·보기 선택. 소스 불가는 **안내로 끝내고 대체·재계획하지 않는다** | §6 |

| R-2 | ITAM · 제니퍼 · RAG 등 소스별로 맞는 조회 | 소스마다 처리기가 있다(ITAM = `data_query`의 DB · 제니퍼 = `apm_query` · 문서 = `doc_query` · Prometheus = 처리기 없음). 문제는 처리기 부재가 아니라 **처리기 앞의 소스 결정**이다 |
| R-3 | DB 쿼리 우선 · 폴스타 최우선 해소 | 불확실·실패·빈 분류의 기본값이 전부 SQL·첫 활성 DB다. 기본값을 「소스 미정 → 안내」로 바꾸는 것은 기본 경로 변경이라 측정이 필요하다(D-251 ⑦) |
| R-4 | 1차로 소스를 선별 | 계획 호출 **안에서**(추가 LLM 0) 소스 선별 결과를 구조화해 내고, 코드가 판정한 뒤 처리기를 고른다. 키워드 분류기는 만들지 않는다(D-004) |
| R-5 | 도커 제니퍼·ITAM을 설정하고 직접 테스트 | §2 설정 · §3 실측. 로컬 제니퍼는 **라이선스가 없어 도메인 0건**이라 성공 경로(인스턴스 행 표시)는 실측하지 못했다 — 코드 추적으로 보완(§4 S-6) |
| R-6 | (의견 ③) 프롬프트를 분석해 조회할 내용·소스를 사용자에게 묻고 선택을 유도 | 소스 판정이 **모호할 때만**(소유 소스 2개 이상 · 명시 없음) 선택 칩으로 묻는다. 명시 소스·단일 소유는 묻지 않는다. 선택은 스레드에 기억한다(N-10) |
| R-7 | (의견 ④) WAS 인스턴스 목록은 제니퍼에서 | WAS 영역(`was_instance`·`was_performance`·`was_runtime`·`was_activity`·`apm_event`)은 레지스트리상 **제니퍼 단독 소유**다. 묻지 않고 제니퍼로 보내고, 제니퍼를 쓸 수 없으면 안내만 한다 — 폴스타는 대체 후보가 아니다 |
| R-8 | (요청 ⑤) 유사 사례를 정리해 「질의 → 소스」를 기억하고 다음 유사 질문에 참고 · 벡터 DB vs Redis 검토 | §6.5 — 확인된 선택만 저장 · 판정 순서 안 위치 · 검색 계단 · 만료·무효화 · 저장소 비교와 권고 |
| R-9 | (요청 ⑦) 유사어는 데이터 소스마다 다르게 관리 | 유사어 레코드마다 **소스(시스템) 귀속**을 두고, 등록·조회·관리가 소스를 먼저 정한다. 한 소스의 유사어가 다른 소스의 해석에 끼어들지 않는다. 같은 말이 소스마다 다른 뜻을 가져도 된다(소스 이름만 예외 — 한 이름은 한 소스) — §6.6 |

## 6. 개선 방향 — 소스 선별 단계

### 6.1 원칙

1. **소스 선별 → (선별된 소스 안에서) 처리기·보기 선택 → 실행·조합**으로 단계를 나눈다.
2. **추가 LLM 호출 0** — 소스 선별은 기존 분해 호출의 구조화 출력 칸과 결정적 코드로 한다.
3. **키워드 분류기를 만들지 않는다**(D-004). 결정적 인식은 **레지스트리에 등록된 시스템 표시명·별칭**뿐이다(D-004 부기 · D-281 ⑦ — 위치 힌트 D-246과 같은 방식).
4. **소스 불가는 정상 결과다**(125 Q-9) — 조회하지 않고 사유를 알린다. 다른 소스로 대체하지 않고, 재계획으로 되살리지 않는다.
5. 신규 `enable_*` 0(D-162). 기본 경로 변경은 기준선 → 수정 → 재측정(D-251 ⑦).

### 6.2 흐름

```
input_parser (기존 · target_db_hints = LLM이 뽑은 시스템·DB 표면어)
  ↓
[소스 선별]  ── 분해 호출 1회 안 + 코드
  ① 명시 소스 해소(결정적 · LLM 0)
       target_db_hints → 레지스트리 전 시스템(databases + solutions)의 표시명·별칭
       → requested_sources = [{system, kind: db|non_db, active, allowed}]
  ② 영역 선별(LLM · 분해 출력 칸)  ※ W2
       task.areas = 닫힌 어휘(레지스트리 capabilities) · task.requested_source(선택)
  ③ 판정(코드 · 질문 여부도 코드가 정한다)
       명시 소스 > 영역 소유 소스(소유표 — DB 없는 시스템 포함) > 스레드에 기억된 선택
       · 명시 소스 · 활성 · 허용      → 묻지 않고 그 소스로 고정       예) 「제니퍼의 인스턴스 리스트」
       · 소유 소스 1개                 → 묻지 않고 그 소스로            예) 「WAS 인스턴스 목록」(제니퍼 단독) · 「자산 담당자」(ITAM 단독)
       · 소유 소스 2개+ · 명시 없음    → 정본 규칙으로 갈리면 그대로, 남으면 **소스 선택 칩으로 묻는다**(N-10 · 존 질문과 한 번에)
       · 소유 소스 0개                 → 범위 밖 안내(조회 0)
       · 요청 소스 비활성(연결 안 됨)  → 조회하지 않고 「요청하신 ‘제니퍼’는 현재 연결되어 있지 않습니다」(사용자 표현만 · D-264)
                                          — **안내만**(G-1 확정 · 다른 소스 선택지도 내지 않는다 · 활성 판정은 시스템 단위)
       · 권한 밖                       → 조회하지 않고 종전 거부 문구(소스명 비노출 · D-264 ②)
  ↓
처리기·보기 선택(선별된 소스의 처리기만 · 보기는 닫힌 어휘)
  ↓
실행 → [재계획: 소스 불가·권한 거부·창 밖 task는 평가 대상에서 제외 · 다른 처리기로 대체 금지]
  ↓
조합 응답(125 C) · 소스 상태 행
```

### 6.4 하지 않는 것

- 원문 키워드로 소스를 고르는 규칙(「WAS」 → APM 등) — D-004. 소스 어휘·스키마·대상 유사어(S2~S4 — §6.6)도 소스 선택에 쓰지 않는다. 소스 선택에 쓰는 유사어는 소스 이름(S1)뿐이다.
- 비활성 소스를 프롬프트에 노출해 LLM이 고르게 하는 것(W1 기준) — 비활성 바이트 불변(D-283 ②) 유지. 명시하지 않은 질의(「WAS 응답시간」)의 불가 안내는 W2의 영역 판정(N-6)으로 한다.
- 소스 선별 전용 LLM 호출 추가 · 학습형 라우터 · 전 소스 무조건 조회(125 §4.11).
- 제니퍼 인스턴스 이름 검색·업무명 해석(130 소유).

### 6.5 소스 선택 기억 — 확인된 사례로 다음 질문을 돕는다(요청 ⑤)

**목적**: 사용자가 소스 선택 칩(N-10)에서 고른 결과, 「다른 소스로 보기」 정정, 관리자가 정리한 사례를 「질의 → 소스」 사례로 저장해 두었다가, 비슷한 질의가 오면 **되묻기 전에** 참고한다. 1차 효과는 같은 사용자가 같은 종류의 질문에서 같은 선택 질문을 반복해 받지 않게 하는 것이다. 쌓인 사례는 소스 선별 골드와, 125 §4.11이 「골드가 쌓인 뒤 재검토」로 미룬 학습형 라우터의 데이터가 된다.

**판정 순서 안의 위치**(§6.2 ③): `명시 소스 > 단독 소유 > [기억 사례] > 소스 선택 칩`

- 기억은 「소유 소스 2개+ · 명시 없음 · 정본 규칙으로 안 갈림」에서만 쓴다. 명시 소스·단독 소유 판정을 뒤집지 않는다 — 예: WAS 영역은 제니퍼 단독 소유라 기억과 무관하다(R-7).
- 쓰면 응답에 한 줄 고지 + 바꾸기 칩을 붙인다: 「이전에 비슷한 질문에서 ‘○○’를 고르셔서 그 기준으로 조회했습니다 [다른 소스로 보기]」. 바꾸기를 누르면 그 사례를 정정(`feedback`)으로 갱신한다.
- 현재 권한·활성 상태로 다시 거른다 — 기억이 권한 밖·비활성 소스를 가리키면 쓰지 않고 칩으로 묻는다(D-232 · D-264).
- **분해 프롬프트에 few-shot으로 넣지 않는다**(G-12): 요청마다 프롬프트 접두가 달라져 KV 캐시가 무효화되고(CLAUDE.md 「플래그는 기동 시 1회 해석」과 같은 이유), 9B가 예시를 과신할 위험이 있다. 코드 판정의 동점 해소 재료로만 쓴다.

**사례 1건의 칸**

| 칸 | 내용 |
|---|---|
| `text` | 정규화한 질의 — 민감값 마스킹(`data_masker`) · 식별자 일반화(「web01 CPU 사용률」 → 「<서버> CPU 사용률」 — 입력 파서가 뽑은 식별자 자리만) |
| `areas` | 판정에 쓰인 영역 코드(W2 N-5) |
| `sources` | 고른 소스 코드(복수 가능) |
| `origin` | `user_choice`(칩 선택) · `feedback`(「다른 소스로 보기」 정정) · `curated`(관리자 정리·시드) |
| `scope` | `user:<id>`(개인) · `org`(관리자 승인 공용) |
| `registry_fp` | 레지스트리 지문 — 소스 등록이 바뀌면 그 소스를 가리키는 사례 무효 |
| `created_at` · `last_used_at` · `use_count` | sliding TTL·정리 근거 |

**쓰기 게이트**(오염 자기강화 차단 — Known Mistakes 「LLM 자동 등록은 쓰기 지점에서 결정적 차단」 · D-151 C3 · D-133 「자동 편입 금지」)

- 쓰는 곳은 ① 소스 선택 칩에서 사용자가 고른 순간 ② 「다른 소스로 보기」 정정 ③ 관리자 정리(시드·화면) — 셋뿐이다. **시스템이 스스로 고른 소스(LLM 판정·폴백)는 저장하지 않는다**(테스트로 고정).
- 개인 사례는 그 사용자에게만 쓴다. 조직 공용(`org`)은 관리자 승인으로만 승격한다(유사어 승인 루프 D-012와 같은 모양 · G-11).
- **유사 사례 정리(시드)**: `config/source_memory_seeds.yaml`(git 정본 · D-131) — 4소스 골드(FS)·라우팅 골드(`testdata/routing_gold/routing.yaml`)에서 정답 소스가 확정된 문항과 관리자 정리 사례를 둔다. 기동 시 읽어 `org` 사례로 쓴다. 런타임 사례만 Redis에 둔다.

**검색 계단**(D-084·D-133 선례): ① 정규화 일치 → ② 어휘·퍼지(토큰·문자 n-gram — 질의 이력 검색과 같은 방식) → ③ (선택) 임베딩 코사인 — 로컬 다국어 모델(유사어 의미 검색과 같은 오프라인 반입 모델) · **인프로세스 numpy**. 임계 미만은 「기억 없음」(칩으로 묻는다). **임베딩 단독으로 확정하지 않는다**(D-084) — 임베딩 단계 결과는 개인 사례 일치이거나 어휘 단계와 같은 소스를 가리킬 때만 채택하고, 아니면 칩으로 묻는다. 임베딩 승격은 ①② 단계의 적중률을 잰 뒤 정한다(D-133 「측정 선행」).

**만료·관리**: sliding TTL(기본값은 W5에서 측정으로 정함 — 양식 기억 선례 · 0이면 기능 off = 현행과 비트 동일 · 신규 `enable_*` 없이 TTL 값으로 켠다 — D-162 · 「신규 기능 기본 off」) · 레지스트리 지문 변경 시 무효 · 관리자 화면 조회·삭제·승격 · 사용자 채팅 명령 「소스 기억 보여줘 / 삭제」(양식 기억 명령 선례) · 감사 이벤트(쓰기·사용·삭제).

**저장소 검토 — 벡터 DB vs Redis**

| 기준 | **A. Redis(현행 7.4 · 모듈 없음) + 인프로세스 검색** | B. Redis 벡터 인덱스(Redis Stack 또는 Redis 8 Query Engine) | C. 전용 벡터 DB(Qdrant — `plans/129` 후보) |
|---|---|---|---|
| 예상 규모 | 사용자 수 × 수십 + 시드 수백 → **수천 건**. 384차원(e5-small)이면 1만 건 ≈ 15MB, 전수 코사인은 수 ms 수준(추정 — W5에서 실측) | 같은 규모에서 이점이 거의 없다 | 같은 규모에서 이점이 거의 없다 |
| 운영 부담 | **추가 0** — 이미 운영 중(스키마 캐시·알람 스트림·양식 기억·질의 이력) | 폐쇄망 Redis 교체·모듈 반입(운영은 OS 패키지 Redis ≥7.0 — `docs/03_setup_guide.md` §5 · 로컬 `redis:7-alpine` 7.4.8 모듈 0 실측) | 새 서비스(배포·백업·감시·인증) — `plans/129` 코드 0 |

| 필터(사용자·권한·활성) | 키 공간 + 인프로세스 필터 | TAG 필터 | payload 필터 |

**권고: A.** 지금 규모와 쓰임새(사용자별 선택 기억 · TTL · 수천 건)에는 벡터 검색 엔진이 풀 문제가 없고, 폐쇄망 반입·운영 부담만 생긴다. 검색 계층은 인터페이스(`SourceMemoryIndex.search(text, scope) -> [(case, score)]`)로 감싸 두고, 다음 중 하나가 되면 B 또는 C로 옮긴다 — ① 사례가 수만 건을 넘어 인프로세스 검색·적재가 응답 예산(단순 질의 <10s)에서 의미 있는 몫을 차지 ② 다중 프로세스·인스턴스가 같은 인덱스를 중복 적재하는 메모리가 문제 ③ `plans/129`가 Qdrant를 들여와 공용 벡터 인프라가 생김(그때는 C 합류가 자연스럽다).


### 6.6 데이터 소스별 유사어 — 소스마다 따로 둔다(요청 ⑦ · v1.2 · **v1.3 G-13으로 축소**)

> **v1.3 확정 범위(2026-10-01 · G-13~G-17 · D-295)** — 사용자 *"폴스타와 ITAM은 유사어를 같이 사용해도 되고 나머지 제니퍼, RAG등은 각각 분리하라."* 권고((a) ITAM도 분리)와 다르다. 그래서 이 절의 설계는 이렇게 줄어든다:
>
> | 구분 | 항목 | 처분 |
> |---|---|---|
> | **없어짐** | 시스템별 네임스페이스로의 전역 사전 분할(N-12a) · 전역 폴백 → 시스템 폴백(N-12c 앞부분) · 시스템별 정본 파일 분할(N-12e) · 전역 사전 이관(N-12f · G-14) · O-7 「시드 로드」 전역 적재 가드(ITAM이 DB 공용이라 막을 대상 아님 — `plans/133`에 통지) · 통합 관리 화면(N-12g) | 폐기 — 현 전역 사전 = **「DB 공용 사전」**(폴스타 4 DB + ITAM 공유) |
> | **남음(W6)** | ① G-15 채팅 등록 가드(비DB 맥락이면 DB 사전 미등록 + 안내) ② 비DB 처리기(`apm_query`·`doc_query`)의 DB 사전 비소비·G-16 근거 계약 테스트 ③ S1 한 이름 = 한 소스(기존 테스트) ④ N-12d 비DB 유사어 = 소유 패키지 정본(계약) ⑤ Y-8 실측·교정 ⑥ 매뉴얼 | §14.3 랜딩 |
>
> Y-1~Y-5는 **DB 공용 사전 안의 공유**라 G-13 아래에서는 결함이 아니라 의도된 동작이다(폴스타 등록어가 ITAM 컬럼에 붙는 것 = 같이 써도 된다). 비DB 소스와의 경계만 지킨다(Y-6 · G-15).

**원칙**: 유사어는 **소스(시스템) 귀속 네임스페이스**에 둔다. 한 소스의 유사어는 다른 소스의 해석·조회에 끼어들지 않는다. 같은 말이 소스마다 다른 뜻을 가질 수 있음을 전제로 한다 — 그래서 유사어는 **소스가 정해진 뒤에** 그 소스의 것으로 해석한다(§6.2 흐름의 「처리기·보기 선택」 이후). 소스를 정하는 데 쓰는 유사어는 1층(소스 이름)뿐이다(D-004).

#### 6.6.1 유사어의 네 층 × 소스

| 층 | 뜻 | 폴스타 | ITAM | 제니퍼 | 사내 문서 | Prometheus |
|---|---|---|---|---|---|---|
| **S1 소스 이름** | 이 소스를 부르는 말 — **소스 선택에 쓰는 유일한 층** | `databases[].aliases` · 위치·제품 표면어 | `databases[itam].aliases` | `solutions[apm].aliases` | `solutions[doc].aliases` | `solutions[prometheus].aliases` |
| **S2 소스 어휘** | 이 소스 안에서 그 말이 가리키는 영역·보기 | 답변 영역 라벨(`capabilities`) | 답변 영역 라벨 | 보기 라벨(`views` — 「인스턴스」 = `apm.instances`) | 문서군 `surface_terms`(`rag_collections.yaml`) | (없음 — 92) |
| **S3 스키마 유사어** | 질의어 → 컬럼·속성·값 | `synonym_seeds/{db}.yaml` + `schema:{db}:synonyms` + **전역 사전**(아래 결함) | **없음**(시드 생성 = `plans/133`) | 해당 없음(도구 인자) | 해당 없음 | 메트릭 이름 유사어(없음 — 92) |
| **S4 대상 유사어** | 질의어 → 대상 식별자 | 등록명 ↔ hostname(간선 E2) | 자산명·호스트명 | **업무명 → 인스턴스**(`business_map` — `plans/130` · 미구현) · 인스턴스 이름 검색(130 N-1) | 문서명 | `nodename` |

- **S1**은 D-293으로 이미 소스 항목마다 따로 있다. 인식은 소스 전체를 한 번에 훑지만(`source_alias_terms`), **한 이름은 한 소스만** 가리킨다(테스트 고정).
- **S2~S4는 같은 말이 소스마다 달라도 된다** — 네임스페이스가 다르기 때문이다. 대신 S2~S4로 소스를 **고르지 않는다**(원문 키워드 소스 분류 금지 — D-004). S2는 소스 카탈로그 설명으로 계획 LLM에 렌더되는 재료일 뿐이다(121 TP-9.4 · 판정은 LLM 구조화 출력).

## 8. 수용 기준

- 「제니퍼의 인스턴스 리스트를 보여줘」:
  - APM 활성 · 허용 → `apm_query` 단일 task · `views=["apm.instances"]` · 성공이면 인스턴스 행(이름·호스트·도메인), 소스 불가면 「연결되어 있지 않음/인스턴스 0건」 안내 **1건으로 종료**(SQL 0 · 재계획 0 · 로컬 10초 이내 목표).
