## 1. 실측 — 지금 화면이 가진 것과 없는 것

### 1.1 결정 레코드가 이미 담는 것 (`noise_gate/infrastructure/decision_store.py::record`)

`logs/alarm_decisions.jsonl` 1줄 = 판단 1건. 세부 리스트가 **추가 기록 없이** 쓸 수 있는 필드:

| 필드 | 내용 | 비고 |
|---|---|---|
| `ts` · `alarm_id` · `tier` · `reason` · `priority` · `fingerprint` | 판단 시각·식별·결과·사유(한국어)·우선순위·지문 | `reason`은 단계별 고정 문구 + 일부 변수(침묵 규칙 ID·부모 가용 상태·매트릭스 산식) |

| `alarm_name` · `server_name` | 사람이 읽는 식별자 | D-196에서 추가(빈 값이면 키 없음) |

| `recurrence` | 재통보 시 직전 창 재발 메타(`count`·`first_seen`) | 있을 때만 |
| `semantic_annotation` | 의미적 근접중복 후보 주석(감사 전용) | 있을 때만 |

### 1.2 기록에 없는 것 — "왜"의 구체 근거

`decide_notification`(`noise_gate/domain/notification_policy.py:251-627`)과 워커 탐지 함수(`noise_gate/application/alarm_worker.py`)는
판단 순간 **구체 근거를 알고 있지만 기록하지 않고 버린다**. 사유 문구는 단계 수준("동일 서버 상위 심각도 발생 중")에 머문다.

| 단계 | 판단 순간 알고 있는 것 | 현재 기록 | 버려지는 위치 |
|---|---|---|---|
| 비운영 알람 | 걸린 비알람 마커 단어 | 사유 고정 문구 | `is_operational_alarm` → bool만 반환 |

| 침묵 규칙 | 걸린 규칙 전체(매처·만료·생성자) | 사유에 `침묵 규칙(<id>) — <사유>` | `match_rules` 결과를 사유 문자열로만 |

| 인히비션 | **억제한 상위 알람** · 그 심각도 · 경과 초 | `inhibited`는 signals에도 없음 | `_detect_inhibition`(`:1236`) → bool |

### 1.3 드로어 가림 — 원인 확정

- 관제 화면의 상단 바는 `<header class="noise-top">`이라 이 규칙을 그대로 상속한다(`.noise-top`은 position·z-index를 재정의하지 않는다).
- 결정 추적 드로어 `.drawer { position: fixed; top: 0; z-index: 41 }` · `.scrim { z-index: 40 }`(원래 `noise.html` 인라인 → 현재 `noise-console.css:214-220`).
- 결과: 드로어가 열려도 **헤더(z 100)가 드로어 상단 약 70px를 덮었다** — ✕ 닫기 버튼(`top: 14px`)·알람명 제목이 가려지고, 스크림이 헤더를 어둡게 하지 못했다.
  스크롤 전(헤더 y≈20px)·후(헤더 y=0) 모두 겹쳤다.
- **현재(D-245 부수 수정)**: `noise-console.css:9-18`의 `.noise-top`에 `z-index: 1`만 명시 — `position`은 건드리지 않아 전역 `header`의 sticky를 그대로 물려받는다. 상단 바는 여전히 스크롤을 따라오고, 쌓임 순서만 스크림(40)·드로어(41) 아래로 내려갔다.
  두 화면이 같은 CSS를 쓰므로 함께 해소된다. **코드 수준 수정이며 브라우저 실화면 확인은 D-245 쪽에서도 하지 않았다**(서버 미기동 — 피어 통지).
- (D-245는 처음에 `position: static; z-index: auto`로 고쳤다가 상단 바 고정이 사라지는 부수 변화 때문에 `z-index: 1`만 남기는 쪽으로 정정했다 — 이 계획 v2의 G-6은 그 정정으로 소멸.)

### 1.4 티어 분포 추이 그래프 — 판독을 막는 것 (`noise.js::loadTimeseries`)

1. **축이 없다** — y 눈금·단위·x 시각 라벨 0개. 막대가 몇 건인지, 몇 시인지 화면에서 읽을 수 없다.
2. **수치가 없다** — 네이티브 `title` 툴팁뿐(마우스 hover 1~2초 대기, 키보드·터치 불가).
3. **높이가 비례가 아니다** — `Math.max(2, (count / max) * 120)`: 1건짜리 구간도 2px로 올려 그리므로 작은 구간이 부풀고, 구간이 많은 막대는 합이 120px를 넘어 128px 영역을 넘칠 수 있다.
4. **빈 버킷은 아무것도 그리지 않는다** — 0건과 "데이터 없음"을 구분할 기준선이 없다.
5. **버킷이 UTC 고정 격자**(`decision_store.timeseries` — `floor(ts/bucket)*bucket`) — KST(UTC+9)에서 2시간 구간은 **홀수 시(09·11·13시…)** 에, 1일 구간은 **매일 09시**에 시작한다. 라벨 없이 쓰이던 동안엔 드러나지 않았지만 시각 라벨을 붙이면 바로 보인다(→ G-3).
6. 범례에 **스택 순서·기간 합계가 없다**(아래 회색이 SUPPRESS, 위 빨강이 PAGE라는 것을 알 방법이 범례 색뿐).

## 2. 설계

### 2.1 세부 리스트 패널 (공용 컴포넌트)

모든 드릴다운이 **한 패널**을 쓴다. 항목별 차이는 **필터 + 열 프로파일**뿐이다(패널을 항목마다 만들면 한쪽만 고쳐지는 비대칭이 생긴다).

```
┌───────────────────────────────────────────────── 세부 리스트 패널 (우측, min(1080px, 96vw)) ─┐
│ SUPPRESS — 억제된 알람   (!)                                                 24H · 1,284건  ✕ │
│ 통보하지 않고 기록만 남긴 판단입니다. 어떤 단계가 무슨 근거로 억제했는지 봅니다.              │
│ ┌ 단계 ┐ [전체 1,284] [자가복구 상관 612] [스톰 301] [유지보수 188] [침묵 규칙 97] …        │
│ [ 알람명·서버명·사유 검색              ] [조회]                                              │
│ 시각         알람              서버        억제 단계     억제 사유                 근거       │
│ 09-22 10:41  CPU 사용률 경고   WEB-03      스톰          동일 서버 다발, 대표 1건… 창 9/5건 │
│ 09-22 10:40  /fsapp 사용률     AP-11       침묵 규칙     월간 배포 점검            ~12:00 만료│
│ …                                                                                            │
│                                                      ‹ 이전  1 / 26  다음 ›   (50건/쪽)      │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **진입점**: KPI 6카드 · 퍼널 머리의 "수신"·"PAGE" 수치 · 퍼널 단계 행(14종 + 있을 때 미분류) · 퍼널 아래 티어 카드 4종 · (S7) 상위 억제 알람 행 · (S7) 추이 막대.
  진입점은 전부 `<button>` 또는 `role="button" tabindex="0"` + Enter/Space(피드 항목과 같은 방식) — 마우스 전용 금지.
- **헤더**: 제목(항목명) · (!) 설명 · 범위(현재 `state.range`) · 총 건수 · 한 줄 설명(§2.7 문구의 첫 문장) · 비율 항목이면 **산식 줄**(`SUPPRESS 1,284 ÷ 수신 3,020 = 42.5%`).
- **분포 칩**: 티어 항목이면 **단계 분포**, 단계 항목이면 **티어 분포**를 칩으로(각 건수). 칩 클릭 = 필터 추가(AND). 건수는 같은 목록 응답에서 센다 — 별도 집계 API를 만들지 않는다(목록 페이지와 무관하게 전체 분포가 필요하므로 응답에 `facets`를 더한다 · §2.5).
- **행 클릭 → 결정 추적 드로어**를 패널 **위에** 연다(F-5 해소: 행 데이터로 그리고, 타임라인은 `summary.stages` 순서로 클라이언트가 계산 — 서버 `/decisions/{id}`는 SSE 피드처럼 레코드가 없는 경우의 폴백으로만).
- **닫기**: ✕ · 스크림 클릭 · Esc — **맨 위 층 하나만** 닫는다(드로어가 열려 있으면 드로어만).
- **범위 전환**(헤더 1H/24H/7D/30D) 시 열린 패널은 같은 필터로 다시 조회한다.
- 페이지 50건 고정(서버 상한 200 이내). 빈 결과는 "이 조건의 판단이 없습니다" + 현재 필터 요약.
- 기존 "결정 이력" 관리 탭은 **그대로 둔다**(범용 검색 도구). 패널은 항목 맥락의 드릴다운이다.

### 2.2 항목별 열 프로파일 — KPI · 티어 카드 (요구 1)

공통 열: `시각 · 알람 · 서버`. 각 프로파일은 **"이 목록이 답하는 질문"** 하나에 맞춰 열을 고른다.

| 진입 | 필터 | 답하는 질문 | 전용 열 (현재 기록으로) | S6 뒤 추가 |
|---|---|---|---|---|
| **수신 알람** | 없음 | 무엇이 들어와 어디로 갔나 | 실효 심각도 · 중요도 · **티어** · 결정 단계 · 사유 + 티어 칩·단계 칩 | 존(`db_id`) · 자원명 |
| **PAGE** | `tier=page` | 왜 즉시 불렀나 | 결정 경로(심각도3 단락 / 수집 실패 보수화 / 매트릭스) · 심각도(폴스타 → AI 상향 → 실효, 상향이면 표시) · 중요도 · 승격 근거(사유의 `승격:` 뒤) · 재발(`recurrence.count`) | 승격 목록(구조화) · 울린 값(`condition_log`) |
| **TICKET** | `tier=ticket` | 어떤 산식으로 대기열에 갔나 | **매트릭스 산식**(심각도×중요도 → 기본 티어 → 최종) · 조정(승격/강등 근거) · 폴스타 통보 정책(`noti_policy`) · 일상 패턴(`is_routine`·`pattern`) | 기본 티어·승격·강등 구조화 |
| **DASHBOARD** | `tier=dashboard` | 왜 통보 없이 화면에만 남았나 | **강등 경로**(단계) · 경로별 근거(독립 해소 설정 / 근본원인 미통보·`root_resource` / 주석 코로보레이션 / 매트릭스 산식) · 심각도 · 중요도 | 근본원인 자원명 · 코로보레이션 출처 |
| **SUPPRESS** | `tier=suppress` | **어떤 알람을 왜 억제했나** | **억제 단계** · **억제 사유** · **단계 근거**(§2.3의 해당 단계 열을 한 칸에 요약) · 실효 심각도(억제 상한 이하임을 확인) · 동작(결정 추적 · 이 패턴 침묵) + 단계 칩 | 단계별 구체 근거(§2.4) |
| **억제율** 수치 | `tier=suppress` | (= SUPPRESS) | SUPPRESS 프로파일 + 산식 줄 | |
| **액션가능** 부제 | `tier=page,ticket` | 사람이 움직여야 했던 것 | PAGE 프로파일 + 티어 열 | |
| 퍼널 아래 **티어 카드 4종** | 해당 티어 | KPI와 같음 | KPI와 같은 프로파일 | |

억제율/액션가능 KPI 카드는 **클릭 영역이 둘**이다 — 큰 숫자(억제율) → SUPPRESS, 부제(액션가능) → PAGE+TICKET.
"이 패턴 침묵"은 기존 드로어 동선을 재사용한다(값만 채우고 저장은 사용자가 · 심각도3 행에는 버튼을 숨긴다 — 서버가 어차피 막지만 헛된 동선을 주지 않는다).
**운영자 화면에서만** 보인다(사용자 화면에는 침묵 API가 없다 — D-245). 두 화면의 열 프로파일은 같고, 동작 열만 모드에 따라 다르다.

### 2.3 퍼널 단계별 열 프로파일 (요구 2)

진입: 퍼널 단계 행 클릭 → `stage=<키>` 필터. 헤더에 **단계 설명**(§2.7 — 도메인 정본)과 **활성 여부**(꺼진 단계면 "이 단계는 꺼져 있어 판단을 내리지 않습니다 · 켜는 설정 `NOISE_…`")를 보인다.

### 2.4 근거 기록 `stage_evidence` (S6 · G-1)

**원칙**: 판정(tier·reason·priority·signals·fingerprint·stage)은 **비트 동일**. 레코드에 **최상위 필드 하나**를 더한다 —
D-196이 `alarm_name`·`server_name`을, Plan 60이 `correlation_meta`·`recurrence`를 더한 것과 같은 패턴이다. **`signals` 동결 스키마는 건드리지 않는다.**

```jsonc
// 결정 단계의 근거만 담는다(다른 단계의 탐지값은 담지 않는다). 빈 dict면 키를 넣지 않는다.
"stage_evidence": {
  // non_alarm   {"markers": ["승인", "요청"]}
  // self_heal   {"heal_seconds": 184.2, "fired_severity": 2}
  // silence     {"rule_id": "…", "matcher_summary": "server=WEB-* · alarm=*", "expires_at": "…", "created_by": "…"}
  // dependency  {"mode": "multi_hop" | "one_hop", "root_notified": true, "root_resource_name": "…"}
  // inhibition  {"inhibitor": "<상위 알람명>", "inhibitor_severity": 3, "age_seconds": 42, "window_seconds": 300}
  // flapping    {"flap_percent": 62.5, "high": 50.0, "low": 25.0, "samples": 12}
  // storm       {"window_count": 9, "threshold": 5, "window_seconds": 300}
  // annotation  {"corroborated_by": ["resolution", "change_nearby"]}
  // matrix      {"base_tier": "ticket", "promote": ["폴스타 통보 정책(notify)"], "demote": []}
}
```

- **도메인이 아는 것**(비운영 마커·침묵 규칙·의존성 모드·주석 코로보레이션·매트릭스 조정)은 `NotificationDecision`에 **맨 뒤 기본값 필드** `evidence: dict = field(default_factory=dict)`로 싣는다 — D-196이 `stage`를 더한 방식 그대로(위치 인자 호출 무영향).
  비운영 마커는 `is_operational_alarm`을 바꾸지 않고 같은 정규식으로 **걸린 단어만 뽑는 순수 함수**를 옆에 둔다.
- **워커만 아는 것**(자가복구 소요·인히비터·플래핑 %·스톰 창)은 탐지 함수의 **반환형을 바꾸지 않고**(직접 호출하는 기존 테스트 보호) `_last_self_heal_duration`처럼
  `_last_<단계>_evidence` 속성에 남기고, 워커가 그래프 입력에 `detection_evidence: {stage: dict}`로 싣는다.
- **`AlarmState`(`noise_gate/orchestration/alarm_graph.py`)에 `detection_evidence`를 반드시 선언**한다 — 미선언 키는 LangGraph가 노드 반환 시 버린다(D-203 `sufficiency_shortfalls` 사례).
- 게이트 노드(`notification_gate.py`)가 `decision.evidence`와 `detection_evidence.get(decision.stage)`를 합쳐 `store.record(stage_evidence=…)`로 넘긴다. 저장소는 빈 dict면 키를 넣지 않는다.
- **식별 필드**(G-2): `db_id`·`resource_name`을 최상위로 더한다(D-196과 같은 근거 — 침묵 매처가 쓰는 필드를 목록이 못 보여준다).
  `condition_log`(울린 실제 값)는 값이 섞이므로 **200자 상한 + `_view` 마스킹 대상 추가**(현재 마스킹 키는 `alarm_name`·`server_name`·`reason`뿐 — `resource_name`·`condition_log`·`stage_evidence`의 문자열도 넣는다).
- **플래그를 두지 않는 것을 권고**한다: 판정 무영향의 감사 전용 가산 필드이고 D-196 식별 필드도 플래그 없이 더했다. 다만 기본 설정에서도 자가복구·매트릭스 레코드에는 키가 생기므로
  "기본 off = 비트 동일"(`plans/80` §5.4-③)의 **레코드 바이트** 관점 예외가 된다 → G-1에서 확정받는다.
- 크기: 레코드당 약 60~200바이트 증가. 조회 상한은 줄 수(`max_lines`)라 응답 시간 영향은 무시할 수준이다.

### 2.6 오버레이 층 체계 (S1 · 요구 3 후속)

가림 자체는 D-245가 헤더의 쌓임 순서를 `z-index: 1`(sticky 유지)로 내려 해소했다. 112는 **기존 값(스크림 40·드로어 41)을 바꾸지 않고**, 새로 생기는 오버레이를
그 표 안에 끼운다. 세부 리스트 패널 위에 결정 추적 드로어가 열려야 하므로 패널이 드로어보다 낮아야 한다.

| 층 | 요소 | z-index |
|---|---|---|
| 상단 바(sticky · D-245) | `.noise-top` | 1 |
| 세부 리스트 스크림 | `.scrim--panel` (신규) | 30 |
| 세부 리스트 패널 | `.detail-panel` (신규) | 31 |
| 결정 추적 스크림 | `.scrim` (현행) | 40 |
| 결정 추적 드로어 | `.drawer` (현행) | 41 |
| 설명 팝오버 · 차트 툴팁 | `.info-pop` · `.chart-tip` (신규) | 50 |

- 표는 `noise-console.css` 머리 주석에 두고, **모든 오버레이가 헤더 z 1보다 위여야 함**을 적는다 —
  누가 헤더를 다시 100 이상(전역 `header` 기본값)으로 올리면 표 전체를 그 위로 올려야 한다(예: 200·210·220·230·240). 전역 스플래시(z 2000)·앱 툴팁(z 9999)보다는 늘 아래.
- 새 오버레이는 전부 `position: fixed`로 **body 직계**에 둔다 — 헤더의 쌓임 맥락 안에 넣지 않는다.
- 전역 CSS(`style.css`) 안의 다른 sticky 요소(z 9·20)는 관제 화면에 없는 선택자라 겹치지 않는다(구현 시 두 화면 DOM에서 재확인).
- 정적 자산 캐시 무효화: `noise-console.css?v=` · `noise.js?v=` 번호를 올린다(**두 화면 모두** — 한쪽만 올리면 다른 화면이 옛 파일을 쓴다).

### 2.7 항목 설명 — 느낌표(!) 팝오버 (S4 · 요구 4)

**컴포넌트**
- 항목 라벨 옆 `<button type="button" class="info-btn" aria-label="〈항목〉 설명" aria-expanded="false" aria-controls="infoPop">!</button>`.
  글리프는 **지시대로 느낌표**, 모양은 원형 외곽선·중립색(`--text-muted`) — 경고 pill(`pill--warn`)의 채운 주황과 **다르게** 보여 "경고"로 읽히지 않게 한다(G-4 대안: 관례 ⓘ).
- 클릭/Enter/Space로 열고, 같은 버튼·Esc·바깥 클릭으로 닫는다. 한 번에 하나만 연다. 열면 `aria-expanded="true"`, 팝오버에 포커스 이동 없음(읽기 전용 · 스크린리더는 `role="dialog" aria-label`).
- 팝오버는 body 직속 1개(`#infoPop`)를 버튼 근처에 배치하고 화면 가장자리에서 뒤집는다. 폭 최대 360px · 모바일 폭에서 좌우 16px 여백. 색은 `--tooltip-bg`·`--tooltip-text` 토큰(라이트/다크).
- **호버 툴팁을 쓰지 않는 이유**: 기존 `#appTooltip`(`app.js`)은 hover 전용·`nowrap`·`pointer-events: none`이라 여러 줄 설명·키보드·터치를 못 받고, 관제 화면은 `app.js`를 싣지 않는다.
- **선례와의 관계**: 설정 화면은 `?` 버튼 → 오른쪽 설명 패널(D-191 · 원천 `config/settings_help/`)이다. 관제 화면은 **지시대로 느낌표**를 쓰고, 설명이 짧은 항목 단위라 패널 대신 팝오버로 둔다.
  "관련 설정" 줄은 env 키를 **글자로만** 보인다 — 설정 화면 딥링크는 해시를 받는 코드가 없어(F-2) 링크를 걸어도 해당 키로 가지 않는다.
- 두 화면 공통이되, 운영자 전용 카드(억제율 감시·워치독·관리 탭 3)의 (!)는 운영자 화면에만 있다.

**콘텐츠 형식**(항목마다 같은 순서): **무엇을 세나(정의)** · **산식** · **어떻게 읽나(높으면/낮으면)** · **주의** · **관련 설정**(있을 때 env 키).
문구는 `src/static/js/noise-help.js`(데이터만 — `window.NOISE_HELP = {…}`)에 모으고, 단계 설명만 API(`summary.stages[].description`)에서 받는다 — 판정 코드와 떨어지면 안 되는 문구와 화면 문구를 나눈다.

**대상**: KPI 6 · 퍼널 카드 · 퍼널 단계 15(단계 행마다 — 단, 행 전체 클릭은 드릴다운이므로 (!)는 라벨 옆 별도 버튼) · 티어 카드 4 · 추이 그래프 · 실시간 피드 · 억제율 감시 · 워치독 · 상위 억제 알람 유형 ·
관리 탭 3(침묵·결정 이력·정책) · 결정 추적 드로어의 "타임라인"·"신호 스냅샷"(신호 키 16종은 표 행마다 한국어 설명 — 현재 영문 키가 그대로 보인다) · 세부 리스트 패널 헤더.

**문구 초안**(구현 시 수치·키를 코드와 재대조한다)

| 항목 | 초안 |
|---|---|
| 수신 알람 | 선택한 기간에 노이즈 게이트가 **발송 판단을 내린** 알람 수입니다. 판단은 PAGE·TICKET·DASHBOARD·SUPPRESS 중 하나이므로 네 카드의 합과 같습니다. **주의**: 같은 알람의 재발생 중복과 최소 심각도 미달은 게이트 앞에서 걸러져 판단이 없으므로 세지 않습니다. 결정 기록 파일의 최근 N줄(`NOISE_DECISION_STORE_MAX_LINES`) 안에서 셉니다 — 긴 기간(30D)은 앞부분이 빠질 수 있습니다. |
| PAGE | **즉시 통보**한 판단입니다. 경로는 셋입니다 — 심각도 3(항상 · 어떤 억제도 거치지 않음), 부가 신호 수집 실패(보수적으로 호출), 우선순위 매트릭스(예: 심각도2×중요도 높음, 또는 한 단계 승격). **읽는 법**: 운영자가 곧바로 대응해야 했던 양입니다. 급증은 실장애 또는 오탐 폭주 신호입니다. **주의**: 즉시 경로라 실시간 스트림에 실리지 않아 피드는 30초마다 재동기화됩니다. |
| TICKET | 즉시 호출 없이 **대기열·기록**으로 넘긴 판단입니다. 대부분 매트릭스(심각도2×중요도 보통, 심각도1×중요도 높음)나 한 단계 승격·강등의 결과입니다. |
| DASHBOARD | **통보 없이 화면에만** 남긴 판단입니다. 경로: 독립 해소(설정 시) · 의존성 연쇄(근본원인 미통보) · 계획-무해 주석 · 매트릭스(심각도1×보통/낮음, 심각도2×낮음). 퍼널에서는 통보되지 않았으므로 **캔슬**로 셉니다. |
| SUPPRESS | 통보하지 않고 **기록만 남긴** 판단입니다(삭제가 아닙니다 — 결정 추적에서 근거를 볼 수 있습니다). 어느 단계가 억제했는지는 퍼널과 세부 리스트에서 봅니다. 심각도 3은 어떤 단계·규칙으로도 억제되지 않습니다. |
| 억제율 / 액션가능 | **억제율** = SUPPRESS ÷ 수신 알람. **액션가능** = (PAGE + TICKET) ÷ 수신 알람. DASHBOARD는 둘 어디에도 들지 않아 합이 100%보다 작을 수 있습니다. **주의**: 아래 "억제율 감시" 게이지는 메타경보용 **별도 창**(`NOISE_META_ALERT_WINDOW_SECONDS`)으로 계산해 이 값과 다를 수 있습니다. |
| 노이즈 캔슬링 퍼널 | 게이트는 단계를 **위에서 아래로** 차례로 평가하고 **처음 걸린 단계에서 판단을 확정**합니다. 막대의 채운 부분 = 이 단계를 지나 다음으로 간 비율, 빗금 = 이 단계에서 통보 없이 끝난 비율(SUPPRESS·DASHBOARD). 오른쪽 수 = 이 단계에서 확정된 건수(괄호는 그중 캔슬). 흐린 행 = 이 기간 0건(꺼진 단계 포함 — 단계 (!)에서 켜짐 여부 확인). 행을 누르면 그 단계의 판단 목록이 열립니다. |
| 티어 분포 추이 | 막대 1개 = **한 구간(예: 2시간) 동안 게이트가 내린 판단 수**. 색 = 판단 결과, 아래에서 위로 SUPPRESS → DASHBOARD → TICKET → PAGE(위로 갈수록 시급). **읽는 법**: 막대 높이 변화 = 알람 유입량 변화, 회색 비중 변화 = 억제 비율 변화. 빨강(PAGE)이 튀는 구간을 먼저 보십시오. "비율" 보기로 바꾸면 구간마다 100%로 맞춰 비중 변화만 봅니다. |
| 실시간 결정 피드 | (운영자) 최근 판단(최대 60건). 실시간 스트림으로 즉시 들어오고 30초마다 결정 기록과 다시 맞춥니다(PAGE 포함). 항목을 누르면 결정 추적이 열립니다. · (사용자 화면 "최근 결정") 실시간 스트림 없이 **30초마다** 결정 기록에서 새로 읽습니다 — 문구는 `IS_ADMIN`으로 가른다. |
| 억제율 감시 | 메타경보 창 안의 SUPPRESS 비율과 임계(`NOISE_META_ALERT_SUPPRESS_RATIO`). 임계를 넘으면 **과억제**(진짜 장애를 묻을 위험)를 점검하라는 뜻입니다. |
| 워치독 | 마지막 판단 이후 경과 시간. 창 안 판단 수가 최소치(`NOISE_META_ALERT_MIN_EVENTS`) 미만이면 **무수신** — 수집·게이트 경로가 멈췄을 수 있습니다. |
