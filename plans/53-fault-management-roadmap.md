# 53. 장애관리 기능군 구현 로드맵 (Fault-Management Capability Roadmap)

> 작성일: 2026-06-26
> **대상 계획**: Plan 50(장애진단·원인분석), Plan 51(OS 데이터 수집·진단 기법), Plan 52(알람 노이즈 캔슬링)
> **목적**: 세 계획의 **구현 우선순위·순서·의존성·선행 결정**을 일원화하여 착수 순서를 확정한다.

## 1. 개요

장애관리 기능군은 세 계획으로 구성된다:

| 계획 | 기능 | 한줄 요약 |
|------|------|----------|
| **50** | 장애진단·원인분석(RCA) | 사건 구간 다중신호 상관 → 인과 추론 → 진단 리포트 (진단 **아키텍처**) |
| **51** | OS 데이터 수집·진단 기법 | 무엇을·어떻게 수집/분석 (50의 **데이터·기법 계층**, 3계층 L1/L2/L3) |
| **52** | 알람 노이즈 캔슬링 | 중요도·심각도 기반 발송 판단(PAGE/TICKET/DASHBOARD/SUPPRESS) |

본 로드맵은 "무엇부터 만들 것인가"를 의존성·가치·비용·리스크·선행 블로커로 판단하여 **5개 Wave**로 묶는다.

## 5. 권장 구현 순서 (5 Wave)

### Wave 1 — 노이즈 게이트 MVP `[Plan 52 E1]` · 비용 S
**가장 먼저.** 알람피로는 *상시·전건* 통증 → 즉시·광범위 ROI. 전부 L1, 옵트인, 기존 파이프라인+Plan 47 재사용.
- 산출: 4-티어 라우팅 + 중요도×심각도 매트릭스 + 유지보수 억제 + 핑거프린트 dedup 교정 + 자가복구 상관 +
  `polestar_noise_context` 컬렉터(중요도·유지보수·의존성).
- **시너지**: 이 컬렉터를 Wave 2가 재사용(노이즈 게이트가 진단의 토대도 깐다).
- 선행 결정: `IMPORTANCE_ID` 값코드 매핑, 억제 적극성 정책 (작음 — 즉시 해소 가능).

### Wave 2 — 진단 MVP(pull) `[Plan 50 PhaseA + Plan 51 L1]` · 비용 M
50과 51 L1은 분리 불가에 가깝다(51=50의 데이터·기법 층). 전부 L1 → 보안 결정 없이 착수.
- 산출: 진단 서브그래프(pull) + L1 증거 소스(알람타임라인·메트릭추이·프로세스·토폴로지) +
  결정적 상관엔진(USE·이상탐지·시그니처) + LLM 인과추론(근거 인용·신뢰도).
- Wave 1 컬렉터(토폴로지·중요도) 재사용.
- 선행 결정: pull 우선(이미 권장), 메트릭 `_h` 보존기간 확인.

### Wave 3 — 완성·통합 `[Plan 52 E2~E3 + Plan 50 PhaseB]` · 비용 M
- 52 E2(의존성/인히비션/스톰/플래핑) + E3(메타모니터링·운영지표)로 노이즈 게이트 완성.
- 50 PhaseB(push 진단)는 50A+52 위에서 동작.
- **통합 지점**: 진단된 근본원인 알람은 PAGE, 연쇄 자식은 52가 억제 → 두 기능 결합.

### Wave 4 — 심층·외부 게이트 `[Plan 51 L2/L3 + Plan 50 PhaseC]` · 비용 L~XL
- 51 L3(원시 syslog/dmesg/OOM·프로세스 추이) = 최대 비용·리스크. **호스트 수집 보안정책 결정이 선행 블로커.**
- 51 L2는 벤더(폴스타) 협의 의존. 50 PhaseC(다중서버 연쇄·문서·이력)도 여기.
- 보안 결정·벤더 협의 완료 후 착수 → 명백히 마지막.

### Wave 5 — 선택/지속 `[Plan 52 E4]` · 비용 L
- ML 액션가능성 랭킹. Wave 1~3로 운영자 피드백 데이터가 축적된 뒤 도입.

## 7. 전제 및 뒤집힐 조건

- **전제**: 현재 최대 운영 통증이 "알람 과다(피로)"라는 점 → Wave 1(노이즈) 우선이 명확.
- **뒤집힐 조건**: 즉시 목표가 *알람 감소가 아니라 RCA 자체*라면 **Wave 2(진단)를 Wave 1로 승격**.
  단, 그 경우에도 **51 L3는 여전히 마지막**(보안 게이트 불변).
- **공통 원칙(전 Wave)**: 읽기전용·결정적수치+LLM해석·옵트인·기존 경로 무변경(회귀 없음).

## 9. 아키텍처 분리 판단 (별도 AI 에이전트로 분리할 것인가)

### 9.0 명시적 결론 — 별도 프로젝트를 생성하는가?

> **결론: 아니오. 별도 프로젝트(별도 레포·독립 에이전트)를 생성하지 않는다.
> 50/51/52는 모두 현행 `collectorinfra` 프로젝트 내부에 구현한다.**

분리 수위는 3단계로 구분되며, 권고는 **(1) 동일 프로젝트 내 모듈**이다:

| 분리 수위 | 설명 | 권고 |
|----------|------|:---:|
| **(1) 동일 프로젝트·모듈** | `collectorinfra` 내 `src/diagnosis/` 모듈 + `diagnosis_graph` 서브그래프 | **✅ 채택(현재)** |
| (2) 동일 프로젝트·별도 프로세스 | 같은 레포 내 별도 실행 프로세스 (예: `alarm_server/` 선례) | ⏸ 미래 트리거 시 (§9.5) |
| (3) **별도 프로젝트·별도 레포** | 독립 코드베이스·독립 에이전트·독립 배포 | **❌ 불채택** |

**별도 프로젝트(3)를 만들지 않는 이유** (별도 프로세스보다도 더 강하게 반대):

1. **인프라 대량 재사용** — 50/51/52는 collectorinfra의 폴스타 도메인 자산(알람 이력 repo·메트릭 쿼리·
   프로세스 API·DBHub/DBRegistry·스키마캐시·LLM 팩토리·config·마스킹·감사·notification_bus)을 그대로
   쓴다. 별도 레포는 이 전부를 **중복하거나 공유 라이브러리로 추출하는 대규모 리팩터**를 강제한다.
2. **51·52는 애초에 독립 프로젝트가 될 수 없다** — 52는 기존 **알람 파이프라인 내부 노드**, 51은 50이 쓰는
   **공유 라이브러리**. 빼내면 알람 파이프라인이 파편화된다.
3. **동일 도메인 코드베이스** — 폴스타 스키마·EAV·DB 프로필·query_guide를 50/51/52가 공유한다. 레포를
   가르면 도메인 지식이 이중 관리된다.
4. **프로젝트 관례** — collectorinfra는 별도 **프로세스**(`alarm_server`)조차 **동일 레포 안**에 둔다.
   **별도 레포로 분리한 선례가 없다.**
5. **운영 과투자** — 소규모 운영에서 2번째 레포·CI·배포·버전 관리는 비용만 크고 이득이 없다(YAGNI).

> 미래에 §9.5 트리거(독립 스케일링·L3 보안 격리·독립 릴리스·전용 LLM)가 **실측**되면, 그때도 1순위는
> **별도 레포가 아니라 (2) 동일 레포 내 별도 프로세스**(alarm_server 패턴)로의 추출이다. 별도 레포는
> 그 이후에도 조직·소유권 분리가 실제로 필요할 때만 고려한다.

### 9.1 "별도 AI 에이전트"의 4가지 의미 구분

| 수준 | 의미 | 프로젝트 사례 |
|------|------|--------------|
| L-a | 오케스트레이션 **서브에이전트**(논리) | `SUBAGENT_REGISTRY`(data_query 등) |
| L-b | 독립 **서브그래프/모듈**(논리, 동일 프로세스) | `src/alarm/` + `alarm_graph` |
| L-c | 독립 **배포 서비스/프로세스**(물리) | `alarm_server/`(TCP 수신 전용) |
| L-d | 빌드타임 `.claude/agents/` | team-lead 등 (런타임 무관) |

핵심 질문은 **L-b(모듈/서브그래프) vs L-c(별도 프로세스)**. L-d 무관, L-a는 이미 반영.

### 9.2 셋은 "동급 에이전트 3개"가 아니다

| 계획 | 실제 성격 | 에이전트성(LLM 추론) | 분리 후보? |
|------|----------|:---:|:---:|
| **50 진단** | LLM 인과추론 **서브그래프** | **높음**(유일) | 검토 대상 |
| **51 수집·기법** | **데이터·기법 라이브러리**(50에 종속) | 없음 | ❌ (라이브러리) |
| **52 노이즈 게이트** | 알람 파이프라인의 **결정적 게이트 노드** | 거의 없음(규칙 판단) | ❌ (`src/alarm/` 잔류) |

→ 진짜 분리 검토 대상은 **50뿐**이며, 질문은 *"진단을 별도 프로세스로 뺄 것인가"* 로 좁혀진다.

### 9.3 판단 (Plan 50 기준)

| 분리 유리 요인 | 분리 불리 요인 |
|----------------|----------------|
| (미래) 독립 스케일링 | 알람 이력·메트릭·프로세스 API·DBHub·스키마캐시·LLM 팩토리·마스킹·감사·notification_bus **대량 재사용** |
| (미래) LLM 모델 차등 — 단 LLM 팩토리로 프로세스 분리 없이 해결 가능 | 모든 증거가 **동일 폴스타 DB**(분리해도 같은 DB) |
| **L3 호스트 수집 보안 격리** | pull(메인 그래프)+push(알람 워커) **2개 진입점** → 분리 시 네트워크 경계 2개 |
| | 실패/비동기 격리는 graceful degradation + Redis Stream으로 **이미 확보** |
| | 별도 프로세스 정당화 사유(ingress) 부재 — `alarm_server`만 TCP 때문에 별도 |
| | 소규모 운영: 배포·모니터링 단위 증가 부담 |

### 9.4 결론

1. **논리적 분리(L-a/L-b)는 적절 — 현 계획안이 이미 올바름.** 50을 독립 모듈 `src/diagnosis/` +
   `diagnosis_graph`로 두고, pull=`fault_diagnosis` 서브에이전트, push=알람 워커 훅 (alarm과 동일 패턴).
2. **물리적 분리(L-c, 별도 프로세스)는 현재 부적절(YAGNI·과투자)** — 재사용·동일 DB·2진입점·소규모 운영에서
   비용만 크고 이득 미미.
3. **51·52는 분리 대상 아님** — 51=공유 라이브러리, 52=알람 파이프라인 노드(`src/alarm/` 잔류).
4. **"추출 가능한 모듈러 모놀리스"로 설계** — `src/diagnosis/` 경계를 clean architecture+arch_check로 깨끗이
   유지하여, 필요 시 별도 서비스 추출이 싸지도록. = *논리적 분리, 물리적 통합, 필요 시 추출.*
5. **유일한 즉시 분리 후보: Plan 51 L3 호스트 수집기** — 채택 시 **그 수집기만** 최소권한·별도 자격증명·
   네트워크존·감사가 적용된 제약 컴포넌트로 격리(진단 에이전트 전체가 아님). Wave 4 보안 결정과 연동.

### 9.5 물리적 분리(L-c) 전환 트리거 (미래)

아래가 **실측 확인되면** 그때 `src/diagnosis/`를 별도 서비스로 추출:
- 진단 LLM 부하/비용의 **독립 스케일링** 필요 · **L3 호스트 수집** 보안 격리 필요 ·
  **독립 릴리스 주기** 필요 · **전용 LLM 프로바이더/인프라** 필요(우선 LLM 팩토리 차등으로 해결 시도).
