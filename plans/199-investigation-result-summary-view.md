## 0. 요약

- **문제의 본질은 정보량이 아니라 순서와 층이다.** 결론(1순위 원인·지금 할 일)이 화면 중간의 표·칩·아코디언 사이에 묻혀 있고, 같은 결론이 4~5곳에 형태만 바꿔 반복되며, [서술 보기]는 HolmesGPT 답변 원문(최대 8,000자 마크다운)을 **렌더하지 않은 평문**으로 보인다.
- **화면의 주 사용자는 관제 요원이고, 그 일은 「원인 영역을 보고 담당자에게 넘기기」다**(§0.1). 그래서 첫 화면 맨 위는 원인보다 **원인 영역**(WAS·DB·외부 연계·서버 자원)이고, 첫 화면의 출력물은 **담당자에게 넘길 전달문**이다.
- **3단 구조**: ① **한눈에 보기**(모든 화면 맨 위 · 펼침) → ② **근거 요약**(접힘 · 담당자가 펼침) → ③ **상세**(접힘). 관제 요원과 담당자 모두 일반 사용자 계정이라 계정으로 나누지 않고 **누구나 펼칠 수 있게** 하며, 펼침 선택은 브라우저에 기억한다. 관리자(admin)는 지금처럼 운영자 전용 항목만 더 본다.
- **요약·전달문은 결정적으로 조립한다.** 새 LLM 호출을 만들지 않는다. 브리핑에 이미 있는 구조화 필드(`engine_agreement.playbook.layer` · `synthesis.hypotheses`·`actions`·`followups` · `deep_dive.cause`·`recommendation`·`limitations` · 단계 상태 · `known_errors`)만 읽는다(D-035 · Known Mistakes 「LLM 출력에 정합성을 의존하지 않는다」).
- **노출 범위는 넓히지 않는다.** 사용자 뷰는 지금도 마스킹을 거친 상세를 받는다. 이 계획은 *무엇을 먼저·펼쳐서 보이는가*만 바꾼다. 백엔드 변경은 플래그 전달 1필드뿐이다(§5 W1).
- **장애 진단 진행 중 화면의 「실행 기록」은 맨 아래 접힘 섹션으로 내린다**(§3.10 · Q6). 지금은 「실행 기록」 탭을 열면 화면 폭 60%의 왼쪽 칸이 비어 있고(조사 서비스 실행 기록 기본 꺼짐), 쓸모 있는 「중간 결과」는 그 탭 오른쪽 칸에 갇혀 있다.

### 1.3 같은 결론의 반복

`diagnosis-tab.png` 한 화면에서 「WAS 요청 처리 부하(CPU 주인 = WAS)」가 ① 조사 흐름 「지금까지」 줄 ② 종합 가설 표 1행 ③ 종합 AI 소견 ④ 엔진 비교 플레이북 칸 「1순위 원인」 ⑤ 플레이북 [서술 보기]로 다섯 번 나온다. 반복 자체보다 **어느 것이 정본 결론인지 표지가 없다**는 것이 문제다.

### 1.4 [서술 보기] — 원문 평문

- `engineColumn`(`briefing-view.js:1175`)이 `escapeHtml(narrative)`를 줄바꿈 보존으로 넣는다. HolmesGPT 답변은 마크다운(`### 장애 분석 결과 보고서`·`- 원인: …`·`**…**`·표)이라 기호가 그대로 보인다.
- 원문은 `deep_dive.narrative` 최대 8,000자(`sre_agent/sre_agent/application/investigation_dispatcher.py:450` `DEEP_NARRATIVE_MAX_CHARS`). 같은 답변에서 뽑은 `cause`·`root_cause_hypotheses`·`recommendation.items`·`limitations`·`timeline`이 이미 있다 — 원문은 **이 필드들의 출처 확인용**이지 첫 읽기 대상이 아니다.
- 플레이북 칸 [서술 보기]는 `synthesis.narrative`(AI 소견 한 문단)로, 종합 블록의 AI 소견과 같은 문장이다.

### 1.5 비플레이북 브리핑(`renderBody` · `investigation-conversation.png`)

`briefing_lines`(중요도·요약·타임라인·원인 가설·권고·한계 — 라벨 정본 `noise_gate/domain/investigation_briefing.py:29`) + 두 소스 타임라인 표. 줄 구조는 이미 요약형에 가깝지만 **결론 강조가 없고 원인 영역이 없다**. 이 갈래도 같은 한눈에 보기 카드를 얹는다(§3.1 출처 열 「비플레이북」).

### 1.6 원인 영역의 출처 — 이미 있다 (2026-10-29 실측)

- sre_agent `_finish_playbook`(`investigation_dispatcher.py:2015`)이 **모든 플레이북 브리핑**에 `engine_agreement`를 싣고(심층 조사 생략·실패여도 `compare_engines`가 플레이북 쪽 계층은 계산한다), 그 안의 `playbook.layer`가 플레이북 판독(`readings`)에서 결정적으로 뽑은 **지배 계층**이다 — 값 `db`·`external`·`cpu`·`gc`·`host_resource`·`unknown`(`sre_agent/sre_agent/domain/engine_agreement.py:23` · 판독 → 계층 표 `READING_LAYERS`). 심층 조사 쪽 계층은 `holmesgpt.layers`.
- 사용자 뷰도 `engine_agreement`를 싣고(`PLAYBOOK_VIEW_KEYS` · `investigation_store.py:313`) `layer`는 마스킹 제외 enum이다(`_PLAYBOOK_ENUM_KEYS`). → **원인 영역은 백엔드 변경 없이 화면에서 읽는다.** 화면은 enum → 문구 표만 가진다(계층 판정의 정본은 sre_agent에 그대로).
- 「네트워크」 계층은 현재 없다(`LAYERS`에 미정의) — 추가는 sre_agent 판독 변경이라 범위 밖. 네트워크 원인은 당분간 「원인 영역 미확정」으로 나온다(§6 위험).

### 1.7 장애 진단 진행 중 「실행 기록」 — 큰 빈 칸 (v0.3 · 2026-10-29 실측)

- **비는 이유**: 실행 기록은 조사 서비스 설정 `SRE_ACTIVITY_LOG_ENABLED`가 켜져야 쌓인다. 코드 기본값이 꺼짐이고(`sre_agent/sre_agent/settings.py:388` `sre_activity_log_enabled: bool = False`) 로컬 `sre_agent/.env`도 `false`다. *(2026-10-29 개정: 코드 기본값 on · D-341 부기 23 — 로컬 `sre_agent/.env`는 실제로는 파일 없음 · §1.8 ⑤)* 장애 진단 탭 자체는 본체 설정(`src/config/alarm.py:500` `investigation_live_view_enabled`)으로 따로 켜지므로, **본체만 켜고 조사 서비스 기록을 끈 조합**이면 탭은 보이지만 실행 기록은 종결 때까지 비어 있다. 화면은 빈 칸 위에 안내 1줄(`TEXT.logEmpty` — 「…꺼져 있으면 종결 때까지 비어 있습니다」)만 낸다. 켜져 있어도 조사 대기·첫 단계 전에는 잠시 빈다. (내부망 두 설정 값은 W0에서 확인한다 — 코드 기본값이 아니라 운영 `.env` 값으로 판단.)
- **부수 문제**: ① 진행 중에 가장 쓸모 있는 「중간 결과」(끝난 단계의 판정·표)가 **「실행 기록」 탭 오른쪽 칸에만** 있어 기본 「조사 흐름」 탭에서는 보이지 않는다. ② 실행 기록은 도구 호출·캐시 적중·응답 발췌·AI 메모 같은 **원시 기록**이라 관제 요원의 판단 자료가 아니다 — §2의 ③ 상세 단에 해당한다. ③ 조사 흐름의 결과 한 줄·왜·건너뜀(`finding`·`because`·`step_skip`)도 같은 설정 아래에서만 붙는다(`plans/187` §5.6.4 계약) — 설정이 꺼져 있으면 조사 흐름 카드도 단계 섹션에서 만든 한 줄로만 채워진다.

## 3. 설계

### 3.1 한눈에 보기 카드 — `summaryModel(view)` 순수 함수 + `summaryCardHtml`

```
┌ 한눈에 보기 ───────────────────────────────────── [완료] 2026-10-26 13:19 ┐
│ 원인 영역  WAS 애플리케이션(CPU 처리)              [확정]                 │
│ 결론       WAS 요청 처리 부하 — CPU 주인은 WAS 인스턴스 A1                │
│ 대상       svr-was-01 · 증상 CPU 사용률 95% · 발생 13:15                   │
│ 영향 범위  같은 사건 알람 2건(WAS 응답 지연 — 제니퍼) · 이상 인스턴스 1/2  │
│ 할 일      A1 /order/submit 의 ORDER_ITEM 조회 실행계획 확인               │
│ 꼭 확인    ⚠ S1 WAS 골든 시그널 수집 결손 — 이 근거 없이 판정             │
│            ⓘ 알려진 문제 KE-012 「배치 겹침 CPU 포화」 일치 · 우회 있음   │
│                          [전달문 복사] [전달문 보기 ▾] [근거 보기 ▾] [자세히 ▾] │
└──────────────────────────────────────────────────────────────────────────┘
```

- `briefing-view.js`에 `summaryModel(view) → {status, area:{layer,label,certainty,alt?}, conclusion:{text,source}, target, scope[], actions[], mustSee[], owner:null}`을 순수 함수로 두고, `renderPlaybook`·`renderBody` 양쪽 맨 앞(머리 바로 아래)에 같은 카드를 얹는다. **요약형·상세형 공통**이다 — 요약형의 기존 「종합(플레이북)」 블록은 이 카드로 대체한다.
- **원인 영역 문구 표**(화면 표시 전용 · enum 정본은 sre_agent `engine_agreement.py`):

  | `layer` | 화면 문구 |
  |---|---|
  | `db` | DB(SQL·커넥션 풀) |
  | `external` | 외부 연계(외부 호출) |
  | `cpu` | WAS 애플리케이션(CPU 처리) |
  | `gc` | WAS JVM(GC·힙) |
  | `host_resource` | 서버 자원(OS·메모리·디스크) |
  | `unknown`·없음 | 원인 영역 미확정 |

  표에 없는 새 enum이 오면 원문 그대로 보인다(침묵 금지). enum 집합 동기화는 W1 테스트가 `engine_agreement.LAYERS`를 읽어 화면 표와 대조한다.
- `owner`(담당자)는 **모델 키만 두고 그리지 않는다** — 별도 담당자 조회 기능(ITAM 등)이 들어올 자리다(§0.1 범위 밖).
- 결론 출처(`플레이북` / `심층 조사`)를 작은 표지로 단다. 카드 밖의 같은 결론 반복 블록(1.3)은 **삭제하지 않고** ②·③단으로 내려 접는다 — 「정본 결론은 카드」 한 곳만 강조한다.
- 진행 중이면 결론 자리에 「지금까지: …」(부분 브리핑)와 진척 S n/m을 보이고, 꼭 확인 첫 줄이 「조사 진행 중」이 된다. 종결 시 카드가 결론으로 바뀐다.

### 3.2 확실성 규칙 — 결정적 · 단정 금지

| 배지 | 조건(위에서부터 먼저 맞는 것) |
|---|---|
| **미확정** | 원인 영역 `unknown`이고 가설도 없음 · 또는 조사 실패·시간 초과 |
| **추정** | 1순위 가설이 판단 보류 · 결론이 심층 조사에서만 나옴 · 엔진 비교 `different_layer`(이때 원인 영역 줄에 「다른 분석은 ○○ 영역」 병기 — 넘길 곳이 둘일 수 있음) · 결론 근거 단계에 결손 · 비플레이북 브리핑의 원인 가설 · 진행 중 부분 결과 |
| **확정** | 1순위 가설 「지지」 + 위 조건 해당 없음 |

「확정」은 「판독 규칙의 근거가 지지함」의 뜻이다 — 매뉴얼에 그렇게 적는다. 198 I-3 근거량 점수가 들어오면 이 표의 조건으로 편입한다(점수 함수는 198 소유).

### 3.3 꼭 확인 규칙 — 관제용(첫 화면) / 담당자용(근거 요약) 분리

| 첫 화면(관제용 · 최대 3줄 + 「외 n건」) | 근거 요약 단(담당자용) |
|---|---|
| ① 조사 미완료·실패·부분 결과(「S4까지의 결과입니다」) | 엔진 불일치 상세(두 엔진 칸) |
| ② 결론 근거 축의 결손·미연동 단계(「S4 호스트 자원 결손 — 폴스타 서버 미확정」) | `limitations` 전부 |
| ③ 알려진 문제 일치·후보 **한 줄**(ID · 제목 · 「우회 있음/없음」) | 알려진 문제 상세 조건·우회 절차·피드백 |
|  | 검토 기한 지난 런북 |

해당 없으면 줄 자체를 그리지 않는다(빈 경고 칸 금지). 원인 미확정·영향 범위는 경고가 아니라 각각 확실성 배지·영향 범위 줄로 보인다.

### 3.4 전달문 — 양식 미리보기 + [전달문 복사]

- `handoffText(model)` 순수 함수가 고정 양식을 만든다. 없는 항목의 줄은 뺀다.

  ```
  [장애 전달] svr-was-01 · CPU 사용률 95% · 발생 2026-10-26 13:15
  원인 영역: WAS 애플리케이션(CPU 처리) — 확정
  결론: WAS 요청 처리 부하 — CPU 주인은 WAS 인스턴스 A1
  영향 범위: 같은 사건 알람 2건(WAS 응답 지연) · 이상 인스턴스 1/2
  확인 요청: A1 /order/submit 의 ORDER_ITEM 조회 실행계획 확인
  주의: S1 WAS 골든 시그널 수집 결손 · 알려진 문제 KE-012 일치(우회 있음)
  조사: inv-… · 2026-10-26 13:19 · 포털 「장애 진단」에서 근거 확인
  ```

- [전달문 보기]는 읽기 전용 미리보기(선택해 직접 복사 가능), [전달문 복사]는 클립보드 복사 — 실패하면 기존 `copyKb`와 같은 안내(「내용을 직접 선택해 복사하세요」)를 보인다.
- **마스킹**: 사용자 뷰 문자열은 이미 서버에서 가려져 있으므로 전달문도 가려진 값으로 만들어진다. 운영자 뷰(원문)에서 복사하면 원문이 나간다 — 운영자 화면의 복사 버튼 옆에 「원문 포함」 표지를 단다.
- 시스템이 메신저·문자로 직접 보내지 않는다(§0.1 범위 밖). 담당자 줄은 담당자 조회 기능이 들어오면 `owner`로 채운다.

### 3.5 근거 요약(②단) — 표·그림

1. **단계 판정 스트립** — S번호 순 정렬 · 칩 문구를 사람 말로(「호스트 자원 이상」) · S번호는 칩 꼬리 작은 글씨 · 클릭하면 ③단 해당 단계로 스크롤(기존 `data-bv-step` 재사용).
2. **미니 타임라인** — 알람 시각을 0으로 두고 두 레인(인프라 · APM)에 이벤트 점을 찍는 인라인 SVG(외부 라이브러리 없음 — 기존 원칙 유지). 입력은 이미 있는 시각 필드만. 시각이 2개 미만이면 그리지 않는다.
3. **가설 표** — 지지/보류/반박 3칸 정렬. 198 I-3(W4)가 들어오면 그 카드로 교체한다 — 이 계획은 I-3의 **자리만 만든다**(중복 구현 금지 · §7).
4. **엔진 비교** — 기존 2칸 4행 표를 여기로 내린다(관리자는 4택 선택 포함).
5. **담당자용 꼭 확인**(§3.3 오른쪽 열).

### 3.6 [서술 보기] — 4줄 요약 먼저 · 원문 서식 정리 접힘

1. 펼치면 먼저 **원인 · 근거(핵심 수치) · 대응 · 한계 4줄**(이미 있는 `deep_dive.cause`·`hgSide.basis`·`recommendation.items`·`limitations`)을 보인다.
2. 그 아래 원문은 **다시 접어 둔다**. 펼치면 **안전 마크다운 렌더러**(`briefing-view.js` 내부 50줄 이내)로 서식을 정리한다 — **escape 먼저, 화이트리스트 변환 나중**: 제목(`#`~`####` → 굵은 소제목) · 목록(`-`·`*`·`1.`) · 굵게 · 인라인 코드 · 파이프 표. 링크·이미지·HTML은 변환하지 않는다(텍스트 그대로). 제목이 3개 이상이면 소제목 목차를 단다. 8,000자 생략 표지는 그대로 보인다.
3. 플레이북 칸 [서술 보기]는 종합 AI 소견과 같은 문장이므로 **제거하고 「종합의 AI 소견 참조」 링크로 바꾼다**(반복 1곳 감소).
4. sre_agent 쪽 HolmesGPT 답변 형식을 프롬프트로 고정하는 안은 **채택하지 않는다**(LLM 출력 형식에 화면이 의존하게 됨 — Known Mistakes). 렌더러는 형식 무관하게 동작한다.

### 3.7 펼침 정책 — 계정 구분 없음

| 단 | 모든 사용자 기본 | 관리자(admin) 추가 |
|---|---|---|
| ① 한눈에 보기 | 펼침 | 전달문 「원문 포함」 표지 |
| ② 근거 요약 | 접힘 [근거 보기] | 가설 코드 · 엔진 4택 · 알려진 문제 피드백 |
| ③ 상세 | 접힘 [자세히] | AI 중간 서술 · KB 초안·포스트모템 · 플레이북 id·버전(종전 조건 그대로) |

- 펼침 선택은 **브라우저 저장소에 사람별 편의로 기억**한다(`localStorage` 키 `bv.expand.evidence`·`bv.expand.detail` · 읽기·쓰기 모두 try/catch · 실패하면 기본 접힘으로 그린다). 재조회 중 유지는 기존 `keepOpenState`(`data-bv-key`)를 그대로 쓴다.
- 서버 응답·인가는 바꾸지 않는다 — 관리자 추가 항목은 지금처럼 **서버가 뷰에 넣을 때만** 그린다(D-325 ③). 클라이언트 값으로 노출 범위를 정하지 않는다.

### 3.8 장애 진단 탭 배치

- 종결된 조사: **한눈에 보기 → 근거 요약 → 「조사 흐름」(접힘) → 상세 → 「실행 기록」(접힘)** 순서로 뒤집는다. 진행 중에는 **진척형 한눈에 보기 → 조사 흐름(펼침) → 중간 결과(접힘 [근거 보기]) → 「실행 기록」(접힘)** 순서다 — 실행 기록 배치는 §3.10.
- 머리 「조사 이유」 중복 줄(1.2)은 1줄로 접는다(196 결함 목록과 겹치면 196에서 처리 — 착수 시 확인).

### 3.9 용어 정리(표시 문구만)

`COLUMN_LABELS`에 단계 표 원문 열(`prev_day`·`ratio_prev_day`·`minutes_over_90` 등 — W0 픽스처에서 전수 추출)을 추가하고, 「지표」 열의 원문 값(`cpu_pct`·`process_cpu_pct` 등)은 표시 사전을 따로 둔다. 「단계 판정 — 공통(엔진 선택과 무관)」→「단계별 판정」, 「평가 high」→「신뢰도 높음」처럼 사용자 면 문구만 바꾼다. 내부 키·저장값은 그대로. 문구 단언 테스트는 repo 전체 grep으로 함께 갱신한다.

### 3.10 장애 진단 「실행 기록」 — 전환 탭 대신 맨 아래 접힘 섹션 (v0.3 · Q6 확정 A안)

**검토한 선택지**

| 안 | 내용 | 빈 칸 해소 | 중간 결과 노출 | 기존 결정 |
|---|---|---|---|---|
| **A(확정)** | 「조사 흐름 / 실행 기록」 전환 탭을 없애고 한 화면 세로 배치. 실행 기록은 **맨 아래 접힘 섹션** 「실행 기록 (n건) ▸」. 중간 결과는 조사 흐름 아래 [근거 보기] 접힘 | 접힌 머리 한 줄만 남음 | 기본 화면에서 펼치면 보임 | G-50 개정(D-341 ㊳ 원 권고안으로 회귀) |
| B | 전환 탭 유지 · 실행 기록 0건이면 왼쪽 칸을 한 줄 안내로 줄이고 중간 결과를 전체 폭으로 · 중간 결과를 조사 흐름 탭에도 복제 | 0건일 때만 해소 | 두 곳에 같은 렌더 | G-50 유지 |
| C | 실행 기록을 관리자 화면에만 | 사용자 화면에서 해소 | 별도 조치 필요 | D-341 ㉘(사용자·관리자 모두) 개정 · **담당자도 일반 사용자 계정이라 담당자가 기록을 못 봄**(§0.1) — 비권고 |

**A안 배치(확정)**

```
[머리] 대상 · 조사 이유(1줄) · 진척 S3/8 · ● 실시간
[한눈에 보기 — 진척형]  지금까지 … · 원인 영역(추정) · 꼭 확인
[조사 흐름]             단계 카드(펼침 · 진행 중)
[근거 보기 ▸]           중간 결과 — 끝난 단계 판정·표(접힘)
[실행 기록 (0건) ▸]     조사 서비스 실행 기록이 꺼져 있어 종결 때까지 비어 있습니다   ← 접힌 머리 한 줄
```

- **접힌 머리 한 줄에 상태를 싣는다**: 건수(「실행 기록 (37건)」) · 0건 사유(「아직 기록 없음」 / 「조사 서비스 실행 기록 꺼짐」 — 구분 가능한지는 W0 실측, 불가하면 지금 안내 문구를 그대로 한 줄로) · 잘림·보관 요약 표지(`truncated`·`clipped`·`archive`). **펼쳐도 0건이면 큰 빈 칸 없이 안내 한 줄**만 그린다.
- 펼치면 지금 실행 기록 화면(엔진·AI 메모 필터 · 자동 스크롤 · 최신이 위 · 300행 상한 · 행 클릭 발췌)을 **그대로** 쓴다 — 목록 렌더·필터·가림 규칙 무변경. 2칸 그리드(`dv-grid`)는 실행 기록 한 칸이 되므로 목록이 전체 폭을 쓴다.
- 접힘 상태는 §3.7과 같이 브라우저에 기억한다(`dv.expand.log` · try/catch). 접혀 있는 동안에도 스트림·병합·건수 갱신은 계속한다(연결·커서 하나 — 무변경). 자동 스크롤은 펼쳤을 때만 적용한다.
- 「조사 흐름」 섹션은 진행 중 펼침, 종결 뒤 접힘(§3.8). 전환 탭 버튼(`dv-modes`)은 플래그 on일 때 그리지 않는다 — 플래그 off면 종전 전환 탭 그대로(비트 동일).
- **설정 조합 안내**: 본체 장애 진단 화면은 켜져 있는데 조사 서비스 실행 기록이 꺼진 조합은 실행 기록뿐 아니라 조사 흐름의 결과 한 줄·건너뜀 표시도 빠진다(§1.7 ③). 이 계획은 화면만 고치고 설정은 바꾸지 않는다 — 내부망 두 설정 값을 W0에서 확인해 결과를 보고하고, 조사 서비스 실행 기록을 켤지는 사용자 결정으로 남긴다.
- 기록: 착수 Wave에서 **D-341 부기(G-50 개정)**를 등재한다. 매뉴얼 U-70(`scripts/manual/features.yaml:104` — 앵커 「실행 기록」·「자동 스크롤」·「조사 흐름」)과 캡처 `diagnosis-tab`을 갱신한다.
