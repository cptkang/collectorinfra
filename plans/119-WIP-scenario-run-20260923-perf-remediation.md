  - **집계 보강**: *"김포·여의도 평균·최대 비교 집계가 없음"*. 정당한 후속일 수 있다.
- 평가 LLM만 돌고 후속을 내지 않은 단일 호출 턴도 318턴이다(p50 2.8초 · 합계 1,036초). 이는 CU-4(D-251 ⑤)의 대상이다.
- `replanner` 무의미 재시도 제거(`_filter_futile_retries`)가 26회 발동했다. 이 경우 LLM 평가(p50 8.5초)를 **다 쓴 뒤에** 버린다.

## 5. 수정 단위

### 5.1 트랙 N — 확정·미구현 항목의 이행 (이 run = 기준선)

#### N-1 ★ 응답 표 결정적 렌더 + 요약만 LLM (D-251 ④ · CU-5 · 114 P-3)

- **범위**: D-251 ④ 그대로다. 표가 있는 조회 응답 전체(2·3단 공통 `output_generator._generate_text_response`)와 폼필·파일 응답 서술이 대상이다.
- **이 run이 보태는 명세**
  1. **표는 코드가 `_preview_rows`·`_display_row` 결과로 렌더한다.** 기존 D-187 `_normalize_markdown_tables`가 필요 없는 형태로 만든다. 표 컬럼 규칙(D-100 "전부")은 코드 렌더에서 지킨다. LLM 프롬프트에는 표 규칙을 넣지 않는다.
  2. **LLM 입력**: 질의 · 데이터 요약 · 수치 요약(코드 계산) · 미리보기 **소수 행**(예: 5행)만 넣는다. 출력은 **2~3줄 요약**이다. 출력 상한은 프롬프트 지시와 `max_tokens` 둘 다로 건다. 지시만 걸면 LLM 비결정성에 기댄다(Known Mistakes).
  3. **스트리밍 순서**: 요약 토큰을 먼저 내고 표를 뒤에 붙일지, 표를 먼저 내고 요약을 뒤에 붙일지 정해야 한다. 표 먼저가 첫 화면 도달이 빠르다. 다만 강조·해석이 표 아래로 간다. 현 UI의 토큰 스트리밍(D-009)과 `done` 교체 동작을 확인한 뒤 정한다(구현 착수 시 실측).
  4. **폼필·파일 응답**: 파일 생성 뒤의 서술(§2.6 약 43초)도 같은 규칙을 따른다. 폼필 역질문(D-151)이 있으면 **역질문을 먼저 발행**하고 서술은 생략한다. 답변 턴에서 최종 서술을 1회 한다.
  5. **후처리 덧붙임 10종**(`_append_*` · `output_generator.py:121-133`)은 순서와 내용을 그대로 둔다.
- **영향 테스트**: 응답 표 형태를 단언하는 테스트와 시나리오 단언(`response_must_contain`)을 repo 전체에서 grep해 일괄 갱신한다(Known Mistakes "결정적 상수 변경 시 단언 테스트 일괄 갱신").
- **매뉴얼(D-255)**: 응답 화면 형태가 바뀌므로 `scripts/manual/content/user.md`의 응답 예시·캡처 갱신 대상인지 확인한다.
- **검증**: 단위(20행 초과·59열·복합 필드명 `|`·빈 결과·수치 요약 동반) + 로컬 MLX 스모크(D-240) + 재측정(§7).

### 5.2 트랙 Q — 신규 제품 항목

#### Q-1 존 역질문 조기 판정 (§2.6 · D-143 후속2 개정 · G-2 확정 — 동등성 확인 조건부 · 플래그 없음)

- **문제**: 후단 게이트는 DB 분류 LLM 결과를 "폴스타 존으로 팬아웃되는가"에만 쓴다. 그런데 이 판정 때문에 분류 LLM(과 그 앞의 `intent_planner` 분해 LLM)을 모두 기다린다.
- **안**: 분류 **전에** 결정적 신호(위치어·서버 식별·승계·핀·스레드 스코프)를 평가한다. 신호가 전무하고 **활성 후보 DB가 전부 존 그룹 소속**이면 분류 없이 역질문한다.
  - 존 없는 DB가 하나라도 활성이면 종전대로 분류 뒤 판정한다. W-10(`_keep_zoneless_targets`)과 같은 경계다.
  - 활성 DB·존 그룹은 레지스트리에서 읽는다. 폴스타 리터럴을 코드에 두지 않는다.
- **동등성 조건**: "신호 없음 + 전부 존 소속"이면 현재도 분류 결과와 무관하게 역질문으로 끝나는지를 코드로 확인해야 한다. 분류가 존 없는 대상이나 비폴스타 대상을 낼 여지가 있으면 동등하지 않다. 착수 전에 이 확인이 선행된다.
- **추정 효과**: 역질문 136건 × 약 17초 ≈ 2,300초. 존 역질문 p50이 21.5초에서 약 5초(파싱만)로 내려간다. 파싱 전 앞단 게이트로 합칠 수 있으면 0.1초 미만이다.

#### Q-2 존 역질문 답변 턴의 파싱 재사용 (111 C-6의 좁은 조각 · G-3 확정 · 플래그 없음)

- **문제**: 존 선택 답변은 **대상 DB만 바꾸는** 턴이다. 그런데 `input_parser`(4~7초)부터 전부 다시 돈다. 216건 × 약 5초 ≈ 1,100초다.
- **안**: 역질문 턴의 `parsed_requirements`를 요청 스코프 페이로드(존 역질문 payload)에 실어 둔다. 답변 턴은 원 질의가 같고 이번 턴 입력이 존 선택뿐이면 파싱을 생략한다.
- **111 C-6과의 관계**: C-6은 `frame` 노드 신설(106 H1 선행)로 **모든 재진입**을 다룬다. Q-2는 **존 선택 재진입 하나**만 다루고 frame 없이 된다. C-6이 오면 흡수된다(G-3 확정 — 먼저 넣는다).
- **주의**: 체크포인터 델타 병합 때문에 요청 스코프 값은 라우트에서 명시 초기화해야 한다(Known Mistakes).

#### Q-3 검증 실패 재생성 위임 후속의 결정적 제거 (§2.5 · D-063 확장)

- **문제**: 내부 루프가 예산 3을 다 쓴 검증 실패 task에 대해, `replanner`가 *"올바른 SQL로 재조회"* 후속을 붙인다. 같은 프롬프트·같은 스키마로 다시 생성하므로 결과가 거의 같다. 한 턴에 생성이 최대 12회까지 간다.
- **안**: `_filter_futile_retries`에 규칙 하나를 추가한다. 선행 task가 **검증 실패로 재시도 예산을 소진**했고, 새 후속이 같은 에이전트·같은 대상 DB·같은 sub_query 계열(식별 리터럴 동일)이면 제거한다. 응답에는 마지막 검증 사유를 사용자 언어로 싣는다(침묵 강등 금지).
- **N-3·N-5와의 관계**: N-5는 산문 체인을 내부에서 끊는다. N-3은 시간이 모자랄 때만 끊는다. Q-3은 시간이 남아도 **무의미한** 위임을 끊는다. 셋은 겹치지 않는다.
- **더 싼 대안**: 후속 LLM 평가 **전에** 결정적으로 판정하면 평가 LLM(p50 8.5초)도 아낀다. 필터를 평가 앞에 둘 수 있는지는 착수 시 확인한다.

#### Q-4 폼필 매핑 Layer 1 완전 일치 (§2.6)

- `result_organizer` Layer 1이 이름이 완전히 같은 필드(`'상태'`↔`'상태'`)를 해석하지 못해 Layer 2 LLM(약 6초)으로 넘긴다. 52회 발동했다.
- 원인(표시용 키 치환·공백·정규화 차이)부터 확정한 뒤 Layer 1에 **정규화 후 완전 일치**를 넣는다. 추측으로 고치지 않는다 — 입력 shape를 로그에서 먼저 실측한다.

#### Q-5 스키마 테이블 선택 LLM 생략 — 프로필 선언 기본 집합 (§2.7 · G-4 확정 — 조사 먼저 · 플래그 기본 off)

- **조사 먼저**: 테이블 선택 LLM 결과를 결정적 보충 규칙이 덮어쓰는 비율을 코드 경로로 확정한다. 82%라는 값은 로그상 최종 집합 기준이다. LLM이 고른 테이블이 **빠지거나** 보충되지 않는 경우(11%)의 성격도 분류한다.
- **안(조사 결과가 뒷받침하면)**: `db_profiles`에 의도별 기본 테이블 집합을 선언한다. 질의의 테이블 신호(유사어 매칭 대상 테이블)가 그 집합 안에 있으면 LLM 선택을 생략한다. 신호가 집합 밖이면 종전대로 LLM을 호출한다.
- **리스크**: 결정적 경로가 틀리면 SQL 생성이 없는 테이블을 쓰려다 검증 실패로 재시도한다. 효과는 반드시 재측정으로 확인한다. 신규 동작이라 D-162대로 **플래그 기본 off**로 넣는다(G-4 확정).
- **추정 효과**: ≈290회 × 6~9초 ≈ 1,700~2,600초.

#### Q-6 광폭 `SELECT *` 억제 (§2.3 ② · N-1 뒤 재판정)

- R3-08·R2-09 유형: 사용자가 "모든 정보"를 묻자 `SELECT r.*`(59열 × 10,000행)가 나갔다. DB2 실행만 38.5초 걸렸다.
- N-1이 서술 비용을 없애도 **DB 비용과 59열 표**는 남는다. 코드 렌더 표의 표시 컬럼 상한(나머지는 CSV)은 **두지 않는다**(G-4 확정 · D-100 유지). N-1 재측정 뒤 광폭 표가 여전히 문제면 재판단한다.
- 프롬프트·검증기 쪽 `*` 경고는 N-1 재측정 뒤에도 문제가 남으면 착수한다.

**채택하지 않는 것 — hedged request(L-5)**: FabriX 호출은 비싸고 직렬이다. 병렬로 두 번 부르면 사내 LLM 게이트웨이 부하가 늘고, 비결정성 때문에 두 결과 중 하나를 고르는 규칙도 새로 필요하다. 꼬리의 원인은 간섭이 아니라 이 run에서 확인된 **서술 길이와 루프**다(§2.3·§2.5). 원인을 걷어 낸 뒤에도 파싱·분류성 짧은 호출의 p95 꼬리가 남으면 그때 다시 검토한다.

#### 5.4.2 설계 — 요청 하나를 세 개의 시계로 잰다

사용자 제안(단계를 나눠 측정 · 추가 타임아웃)을 문헌 L-1·L-6·L-7·L-8로 구체화한 것이다.

```
요청 t0 ──────────────────────────────────────────────── 전체 안전 상한(hang 방지 · 종전 값 유지)
   │  [조회 예산] 파싱 · 분해 · 스키마 · SQL 생성/재시도 · 실행 · 재계획
   │        └ 조회 마감 = 처리 마감 − 서술 예약            ← T-2
   │  [서술 예약] 결정적 표(0초대) → 요약 LLM(자기 예산 안)   ← T-4
   │        └ 처리 마감 = 첫 답변 표·토큰이 나가야 하는 시각  ← T-5 ①
   │  [전달] 첫 토큰 이후: 토큰 간 idle 상한 + 전달 연장 상한 ← T-5 ②③
```

- **처리 마감**(`processing_deadline`): 요청 후 **첫 답변(표 또는 첫 토큰)** 까지의 상한이다. 운영 설정 `API_QUERY_TIMEOUT`의 의미를 이것으로 옮긴다(G-7 확정).
- **조회 마감**(`retrieval_deadline`) = 처리 마감 − 서술 예약. 조회 단계는 이 시각을 자기 마감으로 본다.
- **전달 상한**: 첫 답변이 나간 뒤에는 토큰 간 idle 상한으로만 끊고, 여기에 **전달 연장 상한**(예: +60초)을 더한다. 요청 전체의 hang 방지 상한(CU-11 · D-242)은 그대로 둔다.

### 7.2 잔여 · 사용자 할 일

1. **재측정 R1**(§7 단계 3): 폐쇄망에서 `baseline` 프로파일 · 상한 240초 · 전 카탈로그. 코드 준비는 끝났다. 이 run부터 `timeline`·`ttft_ms`가 수집되고 리포트 머리에 상한 의미가 **첫 답변까지**로 찍힌다 — G-1 기준선(이 run · 상한 의미 "요청 전체")과 **타임아웃률을 직접 비교하지 않는다**(리포트가 경고한다). 계획서의 R1/R2 구분(N 트랙만 vs +Q·T)은 커밋을 나눠 배포해야 성립한다 — 한 번에 배포하면 R1이 곧 R2다.
