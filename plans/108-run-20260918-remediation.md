### 1.4 생성 실패 루프 — 근인 확정

`SQL 생성 완료` 424회 · retry 분포 `0:296 / 1:62 / 2:35 / 3:31`.

- 생성 결과가 SQL 이 아닌 **한국어 산문**이었던 횟수 **130회**. 검증 실패 유형
  `SELECT 문만 허용됩니다. 감지된 타입: UNKNOWN` 과 **정확히 130건으로 일치**한다(다른 유형:
  `dtime IS NULL` 누락 11 · 존재하지 않는 테이블 4 · 금지 키워드 2 · 한글 토큰 잔존 3).
- **산문은 프롬프트가 지시한 동작이다.** `_SYSTEM_TEMPLATE_SKELETON`
  (`src/db_adapters/polestar/prompts.py:123`) [Strict Constraints] 1 — *"사용자의 요청이 모호하거나
  스키마 범위를 벗어나는 경우, 쿼리를 생성하지 말고 추가 맥락을 요청하라."* 같은 템플릿의 4·5번은
  *"반드시 SQL 을 생성하라"* + *"알람/이벤트 데이터는 이 템플릿의 사용 가능 테이블에 존재하지 않는다 …
  해당 조건을 생략한 채 지표를 조회하며 SQL 주석으로 생략 사실을 남겨라"* 라 **서로 경쟁한다**.
- 실제 산문 3유형: ①알람 데이터가 스키마에 없다 ②"프로세스 이력"이 없다 ③조회 대상이 모호하니
  알려달라(=되물음).
- **재시도는 그 되물음을 버리고 같은 프롬프트를 다시 돌린다.** 체인 39건(retry=0 이 산문) 중
  회복은 **retry=1 에서 7건** · retry=2 1건 · retry=3 2건 · **끝까지 산문 29건**. 산문에 소모된
  생성 호출 **124회**(중앙값 ~9.6s). 소진 후 사용자가 받은 답은 `재시도 횟수가 최대(3회)에 도달하여
  처리를 중단합니다` 였다.

### 5.2e ★ 「단언 미평가」 턴이 **기능** 합격률 분모를 오염시킨다 (판정 계약 · 사용자 판단 G-6)

CU-H2 후속으로 드러났다. 타임아웃 199턴은 `func_verdict` 에서 **fail 100 · error 99** 로 갈리는데,
`fail` 100턴은 **기능 합격률의 분모에 들어간다.** 그 턴들의 단언은 60초에서 잘려 **평가된 적이 없다.**

| 집계 | pass | fail | error | manual |
|---|---:|---:|---:|---:|
| 전체 380턴 | 40 | 120 | 99 | 121 |
| 그중 타임아웃 | — | **100** | **99** | 0 |
| **타임아웃 제외** | 40 | **20** | **0** | 121 |

| 기능 합격률 | 값 |
|---|---|
| 타임아웃을 분모에 포함(현행) | 40 / 160 = **25.0 %** |
| 타임아웃 제외(평가가 성립한 턴만) | 40 / 60 = **66.7 %** |

**2.7배 차이다.** 현행 수치는 *"제품이 기능 질문 160개를 받아 40개를 맞혔다"* 고 말하지만, 실제로는
*"평가 가능한 기능 질문 60개 중 40개를 맞혔고, 그와 별개로 지연 예산을 199번 넘겼다"* 이다.

- 이것은 `plans/96` 이 세운 원칙(**측정이 성립하지 않은 턴을 합격률 분모에 넣지 않는다** — 401 무효
  T-c)이 **새로운 사유에 적용되지 않은** 경우다. 401 은 하네스 과실, 타임아웃은 제품 과실이라는
  차이는 있지만, **단언이 평가되지 않았다**는 점은 같다.
- 하네스는 이미 **두 축**(`func_verdict` / `perf_verdict`)으로 설계돼 있다. 타임아웃은 **성능 축의
  사건**인데 기능 축으로 새고 있다 — 이중 계상이다.
- **타임아웃을 감추자는 것이 아니다.** 성능 축(`perf_fail` 138건)과 단 무관 지표(§5.3)가 그대로
  드러낸다. 문제는 **기능 축 숫자가 성능 문제 때문에 읽을 수 없게 되는 것**이다.

### 5.4 회복 추정과 그 한계

타임아웃 199턴 중 **`replanner` 까지 완료한 117턴**의 그 시점 누적 노드 시간은 p50 **41.3s** ·
p90 **57.5s** · max 60.0s다. 여기서 2단 전용 몫(`intent_planner`+`replanner`)을 빼면
p50 **36.4s** · p90 **50.3s** 이고 **117/117이 60초 미만**이다.

| 구분 | 턴 수 | 3단 전환 시 전망 |
|---|---:|---|
| `result_aggregator`·`replanner` 안에서 사망 | **131** | 회복 유력 — 그 노드들이 없다 |
| `agent_orchestrator` 안에서 사망 | 67 | **회복 안 된다** — 실제 파이프라인이 아직 돌던 중이다 |
| 노드 기록 없음 | 1 | 판정 불가 |

**추정: 199턴 중 110~140턴 회복.** CU-A2 가 여기에 더해 끝까지 산문인 29체인에서 회차당 ~9.6s × 2를
덜어낸다.

**한계 3가지 — 이 추정은 보장이 아니다.**
1. 타임아웃 턴의 측정값은 **60초에서 잘린 값**이다. `result_aggregator` 는 완료 기록이 없어
   실제로 얼마나 더 필요했는지 모른다.
2. **3단은 이 run 에서 한 번도 측정되지 않았다.** 3단은 `semantic_router`(LLM 1회)를 새로 치르는데
   그 비용이 이 run 에 없다. 2단의 `intent_planner`(p50 0.0s)보다 비쌀 수 있다.
3. 노드 시간 합(41.3s)과 wall(60.6s) 사이 **약 19초가 귀속되지 않는다**(SSE·체크포인트·HTTP +
   중단된 집계기 부분 실행). 3단에서도 그 오버헤드 일부는 남는다.
