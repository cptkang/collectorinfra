## 1. 결론

> 30.5%는 제품 품질만 잰 값이 아니다. **카탈로그가 합격을 구조적으로 막고 있다.**
>
> **상한 문제.** 폐쇄망 정상군에서 실행 가능한 시나리오 104건 중 65건(62.5%)은 턴에 `manual_review`가 있다. 이런 시나리오는 기계 단언이 전부 통과해도 판정이 `manual`로 끝난다(`scripts/scenario/assertions.py:871-875`). 그래서 **제품이 완벽해도 시나리오 합격률의 상한은 37.5%(39/104)다.**
>
> **가드가 이 상한을 못 본다.** `tests/test_scenario/test_assertion_coverage.py:48-61`은 기계 단언이 하나라도 있으면 "판정 가능"으로 세어 89%로 통과한다.
>
> **정의 불일치.** 리포트 헤드라인은 `manual`을 분모에 남기지만(`scripts/scenario/report.py:386`), 벤치 정확도는 뺀다(`scripts/bench/compare.py:104`). 같은 run에 기능 합격률 정의가 둘이다.
>
> **기준선만 D-241 정의로 읽으면.** 2단 기준선의 자동 판정 합격률은 **67.2%(41/61)**다. 불합격 20턴은 전부 `plans/120`이 원인을 확정하고 수정했다(재측정 대기).
>
> 따라서 합격률과 커버리지를 올리는 주 수단은 제품 수정이 아니다.
> - ① **수동 검토 65건을 기계 판정으로 옮긴다**(§4 전수표 — 57건 이관 가능)
> - ② **헤드라인을 D-241 ③ 정의로 맞춘다**
> - ③ **커버리지 분모(plans/1~94에 멈춤)와 실행 범위(폐쇄망 45%)를 넓힌다**
>
> **v2 결론.**
> - **수동 판정은 실 DB 오라클로 상당 부분 자동화할 수 있다**(§9). 하네스는 이미 MCP 읽기 경로를 쓰고, 오라클 SQL은 감사 `query_executed`에 섞이지 않는다. 다만 시스템 결과 행 수집(H-1)이 선행이고, DB2는 DB 레벨 timeout이 없어 오라클을 집계·키 조회로 제한해야 한다. 정답 정의가 모호한 5건은 오라클로도 풀리지 않는다.
> - **시간 표현 정규화 계층은 이미 있지만 월 단위만 표현한다**(§10). 그래서 월로 표현할 수 없는 시간 표현 11턴 중 8턴이 오답이었고(시간 단위 최근 30일 → 월 통계 8월 · 알람 "어제"·"지난주" → 9월 전체), 그중 1턴은 `pass`, 나머지는 대부분 `manual`에 가려졌다. 처방은 "LLM에게 날짜를 맡기는 것"이 아니라 **LLM은 슬롯만 뽑고 코드가 반개구간·입도를 계산해 모든 경로에 리터럴로 주입하는 것**이다.

## 9. 트랙 O — 실 DB 오라클로 수동 판정 자동화 (v2 · 2026-09-29)

> **요청(2026-09-29)**: *"메뉴얼 리뷰도 실제 db에서 쿼리를 통해 조회하여 자동으로 판정할 수 있는지 검토하라."*
>
> **결론 — 가능하다. 단 조건이 셋이다.**
> - **경로는 이미 있다.** 러너 프로세스에서 `src.db.get_db_client(cfg, db_id)` → `DBHubClient` → MCP `execute_sql`로 읽기 전용 조회를 한다. preflight가 이 경로를 이미 쓴다(`scripts/scenario/preflight.py:497-502`).
> - **오라클 쿼리는 감사 `query_executed`에 섞이지 않는다.** 이 이벤트는 시스템 노드(`query_executor.py:46` · `multi_db_executor.py:509·545·985` · `realtime_usage.py:196`)만 남긴다. 러너는 서버 stdout에서 thread_id가 일치하는 줄만 모은다(`runner.py:1349-1366`). 그래서 SQL 단언이 오라클 SQL을 시스템 SQL로 오인하지 않는다.
> - 조건 ① **시스템 쪽 결과 행이 필요하다.** 러너가 받지 않는다. 받을 수 있는 채널은 `/query/{id}/download-csv` 하나다 → H-1이 선행이다.
> - 조건 ② **DB2는 DB 레벨 timeout이 없다**(`mcp_server/mcp_server/db.py:144-149` — PG는 `command_timeout`, MariaDB는 `max_statement_time`). `max_rows`도 전량을 가져온 뒤 메모리에서 자른다(`tools.py:146-150`). 오라클은 집계·키 조회로 제한하고 대형 스캔은 금지한다.
> - 조건 ③ **정답 정의가 모호한 건은 오라클이 풀지 못한다**(§9.4). 오라클 SQL도 틀릴 수 있다. DB2 방언은 로컬에 POLESTAR 스키마가 없어 **폐쇄망에서만 검증된다**(`db2/init`에 `cmm_resource` 0건).
>
> §3.3 H-7(환경 오라클)은 이 트랙으로 흡수한다. H-7은 "기동 시 값 몇 개"였고, O는 "턴별 정답 조회"다.

### 9.2 설계

| 요소 | 내용 | 근거 |
|---|---|---|
| **명세** | 턴 `expect.oracle: {id, compare: count\|keyset\|rowset\|argmax\|value, key: [...], tol, snapshot: once\|pre_post}`. SQL은 카탈로그가 아니라 **정본 파일** `testdata/scenarios/oracles/{id}.{pg,db2}.sql`에 둔다(엔진별) | 골드셋 형식(`testdata/text2sql_gold/` · `known_fail` · 0행 가드)을 재사용한다 |
| **상대 기간** | 오라클 SQL에 `CURRENT_DATE`를 쓰지 않는다. 러너가 턴 송신 시각(KST) 앵커로 `:anchor_month`·`:prev_month`·`:today` 자리표를 **리터럴로 치환**한다 | 월말 run에서 시스템과 오라클이 다른 달을 보는 것을 막는다. §10 해석기와 같은 함수를 쓴다(T-2) |

| **안전** | ① 러너 측 `is_select_only`(`eval_text2sql.py:225-246`) 선검사 ② MCP readonly(`security.py:60-102`) ③ 집계·키만 · `LIMIT`/`FETCH FIRST` 필수 ④ 러너 측 전체 타임아웃 ⑤ `DB_BACKEND=direct`면 오라클 비활성 + 사유 기록(direct 클라이언트는 db_id를 무시하고 readonly 검사가 없다 — `src/db/__init__.py:38-43` · `src/db/client.py:201-207`) | D-003 |
| **감사 공백 보완** | 오라클 SQL은 운영 감사에 남지 않는다(MCP `logs/sql/`에만 `-- 호출: mcp_server`로 남아 시스템 SQL과 구별되지 않는다 — `mcp_server/sql_log.py:24·101-106`). 모든 오라클 SQL에 주석 태그 `/* scenario-oracle run=<id> scn=<id> */`를 붙이고, run 디렉터리에 `oracle_log.jsonl`(SQL·db·행 수·ms·태그)을 남긴다. readonly 검사는 주석을 제거한 뒤 하므로 태그가 거부되지 않는다(`security.py:60-65`) | G-9 |
| **비교** | `eval_text2sql.execution_match`·`column_subset_match`를 재사용한다(`plans/94` §1.2 재구현 금지). 어댑터 셋을 더한다 — ① CSV 문자열 → 숫자 강제(정규화가 `"12.34"`와 `12.34`를 다르게 본다 · `eval_text2sql.py:292-315`) ② **마스킹 대칭**: 오라클 행에도 `DataMasker(cfg.security).mask_rows`를 적용한다(시스템 CSV는 마스킹돼 있다 · `query.py:3633-3635`) ③ `_source_db` 태그 분리 | |

## 10. 트랙 T — 시간 표현 정규화 (제품 변경 · v2 · 2026-09-29)

> **요청(2026-09-29)**: *"날짜 관련하여서도 사용자가 요청한 "지난달", "반년" 등의 요청등은 LLM을 통해 기간을 정규화시켜 조회쿼리로 변경한다던가 하는 방식으로 성능을 개선하는 방안을 조사하여 처리할 계획을 검토하라. 이러한 사용자 프롬프트의 용어를 LLM을 통해 분석하고 정규화시키는 로직을 넣어 쿼리의 성능을 높이는 식으로 처리하는 방식을 면밀히 조사하여 개선 계획을 업데이트하라."*
>
> **결론.** 정규화 계층은 이미 있다. 정규식 1순위 → input_parser LLM의 `time_range` 폴백 → SQL 생성 프롬프트에 「기간 조건(시스템이 결정적으로 해석)」 블록 주입(D-136·D-185·D-201). **문제는 이 계층이 월(YYYYMM) 단위만 표현한다는 것이다.** 그래서 LLM이 "최근 30일"·"어제"·"지난주"를 정확한 ISO 날짜로 뽑아도, 해석기가 그것을 **월로 뭉개고 완결 월로 잘라** 오답을 만든다.
>
> 따라서 처방은 "LLM 정규화를 새로 넣는 것"이 아니다.
> - ① **정규화의 표현력을 넓힌다** — 단위(시·일·주·월·분기·반기·연) · 입도(grain) · 반개구간 `[start, end)`
> - ② **LLM은 날짜를 계산하지 않고 슬롯만 뽑게 한다.** 계산은 코드가 한다(§11 문헌 근거)
> - ③ **모든 경로가 한 번 해석한 결과를 쓴다.** 단일·멀티·2단·3단·폼필·알람·시맨틱·검증기
> - ④ **SQL에는 리터럴 경계만 들어가게 한다**

### 10.1 실측 — 시간 표현 질의의 SQL (2단 기준 경로 · 두 run의 서버 감사 로그)

### 10.3 설계 — 「LLM은 슬롯, 코드는 계산」

```
원문 ─┬─ ① 결정적 인식기(한국어 규칙 · 확장) ──────────────┐
      │      매칭 → TimeSpec(source=rule, span=원문 구간)   │
      └─ ② 미매칭이면 LLM 슬롯 추출(input_parser 호출에 통합) │
             {relation, n, unit, completeness, anchor,        │
              abs(Y/M/D/H), display_grain, span}  ← enum JSON │
             → span이 원문에 실제 있는지 대조 · 값 범위 검사   │
             → 실패하면 폐기(환각 기간 차단)                    │
                                                              ▼
③ 결정적 해석기  TimeSpec + 기준 시각(KST · 요청 수신 시각) → TimeResolution
      · 반개구간 [start, end)  · 해석 정책 표(§10.3.1 · G-15)로 완결성·주 시작·연 넘김 고정
      · 입도 = f(display_grain, 구간 경계 정렬) → 통계 테이블(h/d/m)
      · 기간 없음 = 직전 완결 월(source=default · 고지 대상)
                                                              ▼
④ 단일 출처 state `time_resolution` (요청 스코프 · 라우트에서 초기화)
      → 단일·멀티·2단 subagents·3단·폼필 월 시리즈·알람·시맨틱·검증기·도구가 전부 이것만 읽는다
                                                              ▼
⑤ SQL 주입 = 리터럴 경계만   stat_h: stat_date >= '2026082400' AND < '2026092400'
                             stat_d: '20260824' ~ '20260923'(반개구간) · 알람: ctime >= TIMESTAMP … AND < …
⑤' 생성 후 검증기   실행 SQL의 시간 조건을 파싱해 TimeResolution과 대조 · 불일치나
                    CURRENT_DATE·NOW()·CURRENT DATE·INTERVAL이 있으면 재생성(검증 실패 사유 동반)
⑥ 응답 고지(결정적 문구)   [조회 기간] 2026-08-24 ~ 2026-09-23 · 시간 단위(최근 30일)
```

| 요소 | 결정 | 이유 |
|---|---|---|

**성능 효과를 어떻게 기대하는가**
- **정확도가 주 효과다.** §10.1 오답 8건은 전부 해석기 표현력 문제다.
- **지연·비용은 부수 효과다.**
  - ① 입도를 바로잡으면 조회량이 맞아진다(시간 단위 30일 요청이 월 통계로 가면 오답, 반대로 월 요청이 시간 통계로 가면 대용량)
  - ② 결정적 해석이 맞으면 replanner의 "기간 불충족" 재시도가 줄어든다(K-09는 같은 오답으로 재시도했다 — `server-baseline.log:6415-6417`)
  - ③ LLM 호출은 늘지 않는다(input_parser 통합)
- **리터럴 대 `CURRENT_DATE` 상수식의 인덱스 사용 차이는 작다.** PostgreSQL의 `CURRENT_DATE` 식은 STABLE이라 인덱스 조건에 쓸 수 있다. 성능을 해치는 것은 **컬럼에 함수를 씌우는 것**(`TO_CHAR(col)` · Db2 11.5 「컬럼 식 회피」)이다 — 이 절은 그 둘을 섞지 않는다(§11). 리터럴화의 주 이득은 재현성 · 판정 가능성 · 방언 이식성이다.

- **정량 근거는 전부 영어다.** 한국어 질의 + text-to-SQL에 대한 동료심사 문헌은 0건이다(공백). 그래서 T-0 자체 골드셋이 1차 근거가 된다.
- **SCATE 절대 정확도가 약 0.5다.** 슬롯 추출이 병목이 될 수 있다 → 규칙 커버리지를 먼저 넓히고(T-2), LLM 슬롯은 스팬 대조로 거른다(T-3).
- **반개구간이 유일한 업계 표준은 아니다.** Cube·MetricFlow는 끝 포함이다. 반개구간을 고르는 이유는 월말 일자 계산이 없어진다는 것이다(추정).
- **한국어 기성 도구가 없다**(Duckling KO · dateparser · Recognizers-Text · Chrono · HeidelTime 모두 부적합 — 확인). 그래서 규칙은 자체 구현이고, `dateparser`의 `RELATIVE_BASE`·`PREFER_DATES_FROM` 같은 설정 개념만 참고한다.
- **LLM 날짜 산술을 쓰지 말라는 결론은 최신 모델에서 직접 재지 않았다**(공백). T-3에서 로컬 MLX로 현행 ISO 폴백과 슬롯 폴백을 골드셋에 나란히 돌려 확인한다(무과금 · D-240).
