### CU-2. 전체 조회 질의에도 행 상한을 건다 (P-7)

**앵커** — `src/sql_validation.py:187-192`

```python
is_all_query = has_all_scope_keyword(user_query)
if not _has_limit_clause(sql):
    if is_all_query:
        # 모든/전체 결과 조회 질의의 경우 LIMIT 자동 추가 생략
        logger.info("모든/전체 결과 조회 질의이므로 LIMIT 자동 추가를 건너뜁니다.")
    else:
        auto_fixed_sql = _add_limit_clause(sql, default_limit, db_engine)
```

**두 경로가 서로 반대로 말한다.**

| 경로 | 전체 조회 질의에서 | 앵커 |
|---|---|---|
| `resolve_query_limit` | **`_ALL_QUERY_LIMIT` = 10,000 으로 상향** | `src/utils/query_gen_common.py:487-488` · 상수 `:409` |
| `query_validator` | **LIMIT 자동 추가를 통째로 생략** | `src/sql_validation.py:189-191` |

LLM 이 LIMIT 을 빼고 생성하면 **아무도 되돌려 놓지 않는다.** J-03 실측: 생성 SQL 이 `-- 전체 서버 목록 조회 (LIMIT 없음)` 주석을 달고 무제한으로 실행돼 1,668행을 반환했다.
`spec.md` 의 *"최대 반환 행 수 10,000행"* 과도 어긋난다(`query_gen_common.py:409` 주석이 그 근거를 적고 있다).

**수정** — `is_all_query` 분기를 **생략이 아니라 상향**으로 바꾼다.

```python
if not _has_limit_clause(sql):
    limit = _ALL_QUERY_LIMIT if is_all_query else default_limit
    auto_fixed_sql = _add_limit_clause(sql, limit, db_engine)
```

`_ALL_QUERY_LIMIT` 은 `query_gen_common` 의 **기존 상수를 재사용**한다(새 설정 필드 0). 경고 문구도 상향분을 구별해 적는다.

**검증**
- J-03 → `sql_must_match: (?i)\blimit\s+10000\b` 통과.
- `_has_limit_clause` 가 이미 `LIMIT` / `FETCH FIRST` 양쪽을 보므로(`:862-870`) 방언 분기는 `_add_limit_clause` 가 그대로 처리한다 — **DB2 경로도 같이 테스트에 넣는다.**
- **회귀 주의**: 기존 테스트 중 "전체 조회는 LIMIT 없음"을 정답으로 굳힌 것이 있는지 repo 전체 grep 으로 확인하고 일괄 갱신한다(`CLAUDE.md` 「기존 테스트가 버그를 정답으로 굳혔는지도 점검」).

### CU-13. LOB 속성의 `stringvalue` 선택 (P-2 · **게이트 G-5**)

**앵커** — `src/semantic/coverage.py:145-148`

**G-5 로 올린다. 실데이터에서 LOB 속성의 `stringvalue` NULL 비율을 먼저 재고 결정한다** — 추정으로 정하지 않는다.

### CU-14. 스키마 부재 오판 후 조건 침묵 삭제 (P-5)

E-07 의 생성 SQL 선두:

> `-- 알람 데이터가 스키마에 존재하지 않으므로, "심각 알람이 발생한 적이 있는" 조건은 적용하지 못합니다.`

알람 테이블은 **존재한다**(같은 run 의 D군이 `cmm_alarm` 을 정상 조회했다). 즉 **스키마 노출이 그 턴에 닿지 않았고**, 모델은 조건을 버린 뒤 결과를 **정상 답변으로** 냈다.

**수정 2단**
1. **왜 스키마가 안 보였는지**를 먼저 잡는다 — 복합 질의의 task 격리(`_make_isolated_input`)가 알람 테이블을 sub_query 스코프에서 떨어뜨렸는지 확인한다.
2. **SQL 주석에 적힌 자기 고백을 결정적으로 감지**해 답변으로 승격시킨다. *"조건을 적용하지 못했다"* 는 SQL 주석은 응답에 드러나지 않으면 조용한 오답이다 — **요청 조건이 SQL 에 반영되지 않았음을 코드가 판정**해 사유를 응답에 싣는다(`CLAUDE.md` 「침묵적 폴백 금지」).

### CU-15. 멀티턴 호스트명 승계 (P-15 · **조사 J-3**)

G-01 턴3 의 SQL 에 승계 호스트명 `cocm-hdkapp01` 이 없다. `CLAUDE.md` 의 알려진 실수 「승계 신호(hostname/db_id)는 top-level 승격 경로가 대칭인지 + 이번 턴 파싱이 승계값을 덮어쓰지 않는지(우선순위) 확인」이 그대로 해당한다.
**조사 J-3 선행** — 승격 경로 부재인지 이번 턴 파싱이 덮어썼는지를 로그로 가른다. 둘은 수정 위치가 다르다.

### CU-16. 멀티 DB 경로의 LIMIT 가드 (P-7 후속 · **CU-2 가 닿지 않는다**)

**앵커** — `src/nodes/multi_db_executor.py:2304`(`_validate_sql`) · `src/config.py:349` `multi_full_validation: bool = False`

**CU-2 를 랜딩했는데 멀티 DB 조회에는 효과가 없다.** 실측 두 가지:
1. `multi_db_executor._validate_sql` 은 `validate_sql` 을 부르지만 **`outcome.errors` 만 쓰고 `auto_fixed_sql` 을 버린다** — LIMIT 을 붙여줘도 그 SQL 이 실행되지 않는다.
2. 애초에 기본 경로는 `_validate_sql_simple` 이라 **코어 검증기를 타지도 않는다**(`multi_full_validation` 기본 `False`).

즉 **J-03 형 무제한 SQL 이 멀티 DB 조회에서는 여전히 실행될 수 있다.** 이 run 에서 3-DB 팬아웃은 유효 280턴 중 **66턴(24%)** 이었다(P-6).
`CLAUDE.md` 「단일/멀티 경로 대칭 — 한쪽만 고치는 비대칭이 반복 원인」의 교과서 사례이고, **CU-1 과 같은 유형의 결함이 한 계획서 안에서 두 번 나온 것**이다.

**수정** — `_validate_sql` 이 `auto_fixed_sql` 을 채택하게 한다. `multi_full_validation` 기본값 변경은 **별도 판단**(§5 게이트)이며, 기본 경로(`_validate_sql_simple`)에도 LIMIT 가드가 필요한지가 핵심 질문이다.

> **✅ 랜딩 (2026-09-16 · D-220)** — 핵심 질문의 답은 **"필요하다"** 다. 근거는 코드가 스스로 적어 뒀다:
> `_check_row_limit_dialect` 독스트링이 *"행 제한 절 **부재는 문제로 보지 않는다**(기존 동작 보존 — 상향은 별 관심사)"* 라고
> 명시한다 — D-176 이 방언 그물을 놓으며 의식적으로 남긴 자리이고, CU-2 가 단일 경로에서 닫은 것과 **같은 구멍**이다.
> 구현: `_validate_sql` 반환을 `(에러, 보정된 SQL)` 튜플로 바꾸고, **기본 경로에도** `_auto_limit_or_none` 으로
> 단일 경로와 **같은 함수(`_add_limit_clause`)·같은 경계값(`_ALL_QUERY_LIMIT`)** 을 적용했다. 호출부 3곳이 보정본을 채택한다
> (후보 파이프라인은 `validate` 계약이 `Optional[str]` 이라 에러만 넘긴다 — 옵트인 경로·범위 밖).
> `multi_full_validation` 기본값(False)·`query.default_limit` 은 **건드리지 않았다**.
> 검증: `tests/test_nodes/test_multi_full_validation.py::TestCU16RowLimitParity` 6건(기본 경로·전체 조회 상향·DB2 `FETCH FIRST`·
> 기존 절 불변·거부 SQL 미보정·full ON 보정 채택).

**부수 — 동작과 반대를 말하는 독스트링 2곳**: `src/utils/query_gen_common.py:422`(*"LIMIT 자동 추가 스킵(`query_validator`)"*) · `src/tools/validation.py:32`(*"「모든/전체」 조회면 행 제한 자동 추가 생략"*). CU-2 로 사실이 아니게 됐다. → **둘 다 2026-09-16 정정 완료**(「스킵」→「상향」).

### CU-18. 결정적 알람 조립이 사용자 건수를 버린다 (2026-09-16 신규 · D-02·D-04)

**앵커** — `src/db_adapters/polestar/assembler.py:1474 build_alarm_history_sql(..., limit: int)` · 호출부 `:1562`

결정적 조립을 켜고 뽑아 보니 **"100건"·"상위 10개" 같은 사용자 명시 건수가 사라지고 `LIMIT 1000`(설정 상한)이 붙는다.** 시그니처는 `limit` 을 받는데 호출부가 **파싱된 사용자 건수가 아니라 설정 기본값**을 넘긴다.

**요건 침묵 누락**이라 `CLAUDE.md` 「침묵적 폴백 금지」 대상이다. `spec.limit` 전달 여부는 **G-10**.

### CU-17. 네 프로필 공통 반례 — `WHERE parent.hostname = '서버명'` (P-1 후속)
