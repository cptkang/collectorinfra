# 55. 멀티소스 관측 확장 로드맵 — APM·DPM 연동 에이전트 (Multi-Source Observability Roadmap)

> 작성일: 2026-06-29
> **상위/선행 계획**: Plan 53(장애관리 로드맵 — 폴스타 단일소스 5-Wave), Plan 50(RCA), Plan 51(데이터 수집·3계층), Plan 52(노이즈 게이트), Plan 54(노이즈 대시보드)
> **관련 결정**: D-003(읽기전용), D-005(멀티 DB 순차·부분실패), D-037(deepagents 멀티에이전트), 착수 시 **D-043(멀티소스 관측)** 등재 예정
> **목적**: 현재 **폴스타(SMS, 인프라 계층) 단일 관측원**의 한계를 넘어, **APM(애플리케이션)·DPM(DB)·미들웨어** 관측원을 별도 연동 에이전트로 추가하여 *미들웨어·DB의 이벤트와 영향도*까지 분석하는 **확장 단계의 우선순위·의존성·통합지점**을 일원화한다.
> **상태**: 로드맵 (방향·순서 권고, 미구현)

## 1. 개요 및 목표

### 1.1 배경 — 단일 관측원(폴스타)의 구조적 사각지대

현재 collectorinfra의 모든 신호는 **폴스타(SMS) 한 소스**에서 온다. 폴스타는 **인프라 계층**
(CPU/메모리/디스크/네트워크/프로세스/OS 로그)을 관제하지만, 그 **위(애플리케이션)와 옆(DB 내부)** 은 보지 못한다.
Plan 52 직전 검토(노이즈 게이트의 심각도·영향 정밀화 한계)에서 확인된 사각지대가 이를 그대로 드러낸다:

| 사각지대 | 폴스타로 가능? | 필요한 관측원 |
|----------|:---:|----------|
| **실제 사용자 영향**(트랜잭션 에러율·레이턴시·Apdex) | ✕ (인프라 메트릭은 *대리지표*) | **APM** |
| **미들웨어 자원 영향**(WAS 스레드풀·커넥션풀·JVM 힙/GC·큐 적체) | ✕ (`server.*`만, JVM 테이블 0건) | **APM/미들웨어 모니터링** |
| **DB 내부 영향**(세션·락 경합·슬로우쿼리·대기이벤트·실행계획) | ✕ (호스트 CPU↑까지만) | **DPM** |
| **end-to-end 인과**(앱 지연 → DB 슬로우쿼리 → 호스트 IO) | ✕ (계층 단절) | 3소스 교차 상관 |

> 폴스타 스키마(`schema/polestar-schema.md`)·DB 프로필 실측: `transaction`·`jvm`·`thread_pool`·`slow`·`session`·`lock`
> 관련 테이블이 **전무**하다. 이는 폴스타의 결함이 아니라 **SMS의 관측 범위(scope)** 자체가 인프라 계층이기 때문이다.

### 1.2 목표

1. 폴스타(인프라) + **APM(애플리케이션)** + **DPM(DB)** + **미들웨어**를 **읽기전용으로 연동**하는
   **소스별 커넥터 에이전트**를 정의하고, 그 신호를 기존 자산(노이즈 게이트·RCA·대시보드)이 **보조 입력**으로 소비한다.
2. **52 노이즈 게이트**에 "실제 사용자 영향(APM)·DB 영향(DPM)" 축을 더해 *증상 기준 통보*를 정밀화한다(사각지대 해소).
3. **50 RCA**의 `evidence_collector`에 APM/DPM 증거를 추가하여 **인프라↔앱↔DB end-to-end 상관**을 구현한다.
4. **54 대시보드**에 멀티소스 영향도·교차 타임라인을 표시한다.
5. 폐쇄망·읽기전용·옵트인·기존 경로 무변경 원칙(전 계획 계승)을 유지한다.

### 1.3 설계 원칙

- **어댑터는 분리, 두뇌는 통합** — 소스 연동(수집)은 **격리된 커넥터**(벤더·자격증명·네트워크존 분리), 분석·상관·판정·
  LLM 추론은 **기존 오케스트레이션에 통합**(서브에이전트/모듈). = 53 §9 "논리 분리·물리 통합, 필요 시 추출"의 멀티소스 적용.
- **폴스타는 SSOT 베이스라인, 타 소스는 보강** — APM/DPM은 폴스타 신호를 *대체*하지 않고 *영향도·인과 정밀화*로만 얹는다
  (52 §3.11 "상향 전용·SSOT 보존" 철학 계승).
- **읽기전용·결정적 수치 + LLM 해석** — 각 소스 SELECT/조회 API만, 수치·상관은 Python(결정적), 인과 해석만 LLM(D-003·52·50 계승).
- **공통 데이터 평면 재사용** — 멀티 DB 프로필(D-005)·deepagents 서브에이전트(D-037)·진단 evidence 모델(50)을 확장하고
  새 프레임워크를 만들지 않는다.

## 2. 관측 계층 모델 (무엇을 어떤 소스가 보는가)

```
        ┌──────────────────────────────────────────────────────┐
  영향  │  사용자 / 비즈니스 트랜잭션                            │  ← APM (골든시그널)
   ▲    ├──────────────────────────────────────────────────────┤
   │    │  애플리케이션 / 미들웨어 (WAS·JVM·스레드풀·커넥션풀)   │  ← APM / 미들웨어
   │    ├──────────────────────────────────────────────────────┤
   │    │  데이터베이스 내부 (세션·락·슬로우쿼리·대기이벤트)     │  ← DPM
   │    ├──────────────────────────────────────────────────────┤
  원인  │  인프라 (CPU·메모리·디스크·네트워크·프로세스·OS로그)   │  ← 폴스타(SMS) [현재 유일]
        └──────────────────────────────────────────────────────┘
```

| 소스 | 계층 | 대표 신호 | 연동 방식(후보) | 예시 제품군 |
|------|------|----------|----------------|------------|
| **폴스타(SMS)** | 인프라 | 알람·메트릭추이·프로세스·OS로그·토폴로지 | 기존 DBHub 읽기전용 + 프로세스 API | (현행) |
| **APM** | 앱·미들웨어 | 처리량·에러율·응답시간·Apdex·서비스맵·JVM/GC·스레드풀 | 벤더 DB 읽기전용 또는 REST API | 제니퍼·핀포인트·와탭 등 |
| **DPM** | DB 내부 | 활성세션·락/블로킹·슬로우쿼리·대기이벤트·실행계획 | 벤더 DB 읽기전용 또는 REST API | 맥스게이지·InterMax 등 |
| **미들웨어** | WAS | 스레드풀·커넥션풀·큐·세션 | 다수는 APM이 커버(중복 시 통합) | (APM 내포) |

> **폐쇄망 정합**: APM/DPM/미들웨어 솔루션은 모두 **사내 설치형**이므로 외부 egress가 없다. 각 솔루션 접근 자격증명·
> 네트워크 도달성만 추가 관리하면 된다(외부 SaaS 아님 — Plan 52 §3.1.2 폐쇄망 원칙과 정합).

## 3. 기존 계획(50~54)에 보태는 가치 — 통합 지점

본 로드맵은 **새 기능군이 아니라, 기존 50/52/54에 "소스 축"을 더하는 확장**이다. 각 계획에 정확히 어디서 꽂히는지:

| 대상 | 현재(폴스타 단일) | 멀티소스 추가 후 | 통합 코드 지점 |
|------|------------------|-----------------|---------------|
| **52 노이즈 게이트** | 심각도×중요도(인프라) + 억제신호 | **+ 사용자 영향(APM)·DB 영향(DPM)** 축 → "트랜잭션 에러 급증 → 승격"(기본) / "사용자 영향 0 → 강등"은 **옵트인·승격 비대칭** | **52 §6.4·§8.6에 확장점 예약됨** · step 8 보조 입력 · `notification_policy` |
| **50 RCA** | evidence: 알람·메트릭·프로세스·토폴로지(인프라) | **+ APM 트레이스·DPM 슬로우쿼리** 증거 → 인프라↔앱↔DB 교차 상관·근본원인 | `evidence_collector`에 소스 추가, `correlation_engine` cross-source |
| **51 데이터 수집** | L1/L2/L3 (폴스타 호스트 축) | **새 소스축 추가**(APM-L1=벤더DB, DPM-L1=벤더DB) | 3계층 모델에 *소스 차원* 추가(§5.4 매핑 확장) |
| **54 대시보드** | 노이즈 게이트 결정 추적(폴스타 신호) | **+ 영향도 패널·교차 타임라인**(앱/DB 신호) | `signals` 스냅샷에 apm/dpm 필드, 결정추적 드로어 확장 |
| **53 로드맵** | 폴스타 5-Wave(인프라 완성) | **본 로드맵이 53의 후속 멀티소스 Wave** | 53 Wave 1~3 완료를 선행으로 가정 |

> **53과의 관계(중복 아님)**: 53은 *폴스타 단일소스로 장애관리 기능군을 완성*하는 로드맵. 55는 *그 위에 관측원을
> 늘리는* 로드맵. 53 §9는 폴스타 도메인(자산 재사용)이라 "별도 레포 불채택"이었으나, **APM/DPM은 새 도메인·새 벤더라
> 분리 판단을 재적용**한다(§4).

## 4. 아키텍처 — 멀티소스 통합 패턴

### 4.1 "별도 에이전트"의 분리 수위 (53 §9 재적용)

사용자 요구의 "별도 에이전트로 APM/DPM 연동"을 53의 분리 모델(L-a~L-c)로 정합화한다:

| 구성 요소 | 분리 수위 | 근거 |
|----------|----------|------|
| **APM/DPM 커넥터(수집·연동)** | **L-c 후보**(격리 어댑터/별도 프로세스) | 별도 벤더 자격증명·네트워크존·장애 격리 → 53 §9.5 트리거("전용 인프라·보안 격리") 충족 가능 |
| **소스별 신호 정규화·카탈로그** | L-b 모듈 (`src/sources/apm/`, `src/sources/dpm/`) | 도메인 라이브러리, clean architecture 경계 |
| **멀티소스 상관·영향도·진단** | L-a/L-b 통합 (기존 오케스트레이션) | RCA·노이즈게이트가 *모든 소스 신호를 함께* 봐야 함 → 통합이 본질 |
| **APM/DPM 조회 서브에이전트** | L-a (`SUBAGENT_REGISTRY` 등록) | pull 질의("DB 슬로우쿼리 보여줘") = data_query 패턴 재사용(D-037) |

→ **결론: 수집(커넥터)은 분리, 분석(두뇌)은 통합.** 사용자의 "별도 에이전트"는 *커넥터/연동 계층*에 해당하고,
미들웨어·DB 이벤트의 **영향도 분석은 기존 RCA·노이즈게이트에 통합**되어야 가치가 난다(교차 상관이 핵심이므로).

### 4.2 재사용 자산 (신규 프레임워크 금지 — D-001/D-005/D-037 계승)

- **멀티소스 프로필** — `config/db_profiles/*.yaml`(폴스타 멀티인스턴스) 패턴을 그대로 확장하여 `apm_*.yaml`·`dpm_*.yaml`
  소스 프로필 추가. DBRegistry·읽기전용 방어(D-003)·DBHub 경로 재사용(벤더가 RDB 노출 시).
- **deepagents 오케스트레이션** — `intent_planner→agent_orchestrator→result_aggregator`에 `apm_query`·`dpm_query`
  서브에이전트 등록(D-037). 멀티 의도("앱 성능 + DB 상태")는 기존 멀티인텐트 처리로 자연 분해.
- **진단 evidence 모델(50)** — `DiagnosisState`/`evidence_collector`/`correlation_engine`을 소스 무관(source-agnostic)
  하게 일반화하여 apm/dpm evidence를 동일 타임라인에 병합.
- **노이즈 게이트(52)** — `noise_context`에 `app_impact`·`db_impact` 필드 추가, `decide_notification` 보조 입력.

### 4.3 런타임 토폴로지(목표)

```
[APM 솔루션] ──(읽기전용 커넥터, 격리)──┐
[DPM 솔루션] ──(읽기전용 커넥터, 격리)──┤   소스 정규화 → 공통 신호 모델
[폴스타 SMS] ──(기존 DBHub/프로세스 API)─┘            │
                                                     ▼
        ┌──────────── collectorinfra (통합 두뇌) ────────────┐
        │  pull: apm_query/dpm_query 서브에이전트(D-037)     │
        │  push: 알람 워커 → 52 노이즈게이트(+app/db 영향)   │
        │  진단: 50 evidence_collector(멀티소스) → 교차상관  │
        │  관제: 54 대시보드(영향도·교차 타임라인)           │
        └────────────────────────────────────────────────────┘
   ※ 커넥터만 보안 격리(벤더 자격증명·네트워크존), 분석은 통합
```

## 6. 멀티소스 상관 · 영향도 분석 (50/52 확장 핵심)

- **교차 상관(cross-source correlation)**: 동일 (엔티티, 사건창)에서 인프라·앱·DB 신호를 **하나의 타임라인**에 병합하고
  선후/연쇄를 결정적으로 판정(50 §6 확장). 예: `APM 레이턴시↑(t0) → DPM 슬로우쿼리·락대기(t0) → 폴스타 호스트 IO await↑(t0+)`
  → 근본원인 = DB 쿼리, 인프라/앱은 증상.
- **영향도 점수(impact score)**: "사용자 영향"을 **APM 골든시그널로 정량화**(에러율·레이턴시 SLO 위반·영향 트랜잭션 수)하여
  52 우선순위 매트릭스의 보조 축으로 사용 → *증상 기준 통보* 정밀화(사각지대 해소).
- **결정적 우선·LLM 보조**: 수치·시그니처·선후는 Python, 인과 서술만 `causal_reasoner` LLM(50 §7·52 §4.1 불변).

## 8. 권장 구현 순서 (멀티소스 Wave)

> **전제**: Plan 53 Wave 1~3(폴스타 노이즈 게이트 + 진단 MVP) 완료. 본 로드맵은 그 **후속 또는 53 Wave 4(L2/L3)와 병렬**.
> 53 Wave 4(호스트 직접 수집)와 본 로드맵은 **서로 독립**(다른 소스축)이라 병렬 가능.

| Wave | 내용 | 단독 가치 | 의존성 | 비용 |
|------|------|----------|--------|------|
| **M0** 선행 설계 | 관측 계층 모델·대상 제품·연동 방식·**엔티티 매핑** 확정, 공통 신호 모델 정의 | (블로커 해소) | — | S |
| **M1** APM 커넥터 + 신호 카탈로그 | APM 읽기전용 어댑터 + 골든시그널/서비스맵 정규화 + `apm_query` 서브에이전트(pull) | 사용자 영향 *가시화*(단독으로도 가치) | M0 | M |
| **M2** APM → 52·54 통합 | 노이즈 게이트에 `app_impact` 축(증상 기준 통보 정밀화) + 대시보드 영향도 패널 | 노이즈 정밀도↑(사각지대 B 해소) | M1, 53 W1~3 | M |
| **M3** DPM·미들웨어 커넥터 | DPM 어댑터(세션·락·슬로우쿼리·대기) + 미들웨어(WAS/JVM) + `dpm_query` 서브에이전트 | DB·미들웨어 이벤트 가시화 | M0 (M1과 병렬 가능) | M |
| **M4** 멀티소스 교차 상관 → 50 RCA | `evidence_collector` 멀티소스화 + cross-source 상관(인프라↔앱↔DB end-to-end) | end-to-end 근본원인 분석 | M1·M3, 53 W2 | L |
| **M5** 통합 영향도·양방향 트리거 | 통합 영향도 모델 + 멀티소스 진단 리포트 + APM/DPM 이벤트도 진단/게이트 트리거 | 완성형 멀티소스 AIOps | M2·M4 | L |

**의존성 그래프**:
```
M0 ──┬─► M1(APM) ──► M2(APM→52/54) ──┐
     └─► M3(DPM/미들웨어) ───────────┤
                  M1+M3 ──► M4(교차상관→50) ──► M5(통합영향도·양방향)
```

**한 줄 권고**: *엔티티 매핑·제품을 먼저 확정(M0) → 사용자 영향이 큰 APM부터 연동·노이즈게이트 통합(M1→M2) →
DPM/미들웨어(M3) → 셋을 교차 상관해 RCA를 end-to-end로(M4) → 통합 영향도·양방향 트리거로 완성(M5).*
