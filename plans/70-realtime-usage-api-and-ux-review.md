## 1. CPU/메모리 실시간 사용률 API 조회

### 1.1 결론

**찬성 → 사용자 확정(2026-07-23): 2안(dashboard/measurement) 채택.** 읽기전용 HTTP GET이므로 D-003과 정합하고, Plan 47-1(실시간 프로세스 API)로 이미 검증된 인프라 패턴(httpx 클라이언트 + `db_id=base_url` CSV 설정 + graceful degradation)을 그대로 재사용할 수 있다. 다만 **신규 데이터 평면(DB 우회 경로) 추가**라는 점에서 라우팅 게이트·폴백·감사로깅 설계가 필요하므로, **별도 구현 계획서(Plan 71 후보)로 분리**하여 구체화한다.

### 1.2 API 선택: 2안(dashboard/measurement) — 확정

| 비교 | 1안 lastdata | 2안 dashboard/measurement |
|---|---|---|
| 식별자 | **CPU/MEM 리소스 ID** (서버 ID 아님 — 별도 해석 단계 필요) | **서버 ID** (`cmm_resource`에서 SQL로 즉시 확보 가능) |
| 다중 서버 | 서버당 1콜 × 리소스 ID 해석 선행 | 1콜에 콤마 구분 다수 |
| 응답 | 최소 (min/max/avg/time) | resourceName·targetId 등 포함, 무거움 |

- "ㅇㅇ존의 모든 서버" 시나리오(수백 대)에서는 **호출 횟수가 지배 변수**다. 2안의 응답이 무거운 것은 파싱 후 필요 필드만 취하면 되므로 실질 비용이 아니다(§1.3-4 실측: 200대 응답 ~37KB — 무리 없음). 1안은 서버당 1콜 + 리소스 ID 사전 해석이 필요해 대량 조회에 부적합하다.
- **주목**: 2안 응답의 `targetId`(예시에서 465050)가 바로 1안이 요구하는 리소스(CPU/MEM) ID다(`resourceId`=서버 464399와 구분됨). 즉 **2안을 기본으로 쓰고, 특정 서버 1대 드릴다운·기간별 조회가 필요해지면 2안 응답에서 확보한 targetId로 1안을 호출**하는 하이브리드가 가능하다. 1안을 위해 별도 리소스 ID 매핑 테이블을 만들 필요 없음.
- CPU(`Utilization`/`server.Cpus`)와 메모리(`UsedPercent`/`server.Memory`)는 `type` 파라미터가 다르므로 **동시 요청 시에도 2콜**(지표별 1콜)이 필요하다.

### 1.3 실측 결과 — 전 항목 해소 (사용자 실측, 2026-07-23)

초판에서 "추정 금지 원칙"에 따라 실측을 요구했던 5건이 모두 확인되었다. **아래 값을 구현 계획서의 확정 입력으로 사용한다.**

1. **파라미터명**: `timeSelector`가 맞음 (기획서 본문의 `timeSelecotr`는 수기 오타).
2. **2안 응답 shape (확정)** — 실 환경이 내부망이라 원본 반출이 어려워, 사용자가 형식을 교정한 아래 shape를 파서 기준으로 사용한다. 최상위 `date`(호출 시각, `"YYYY-mm-DD HH:MM:SS"`) + `data.measurement[]` 배열 + `id` 문자열:

   ```json
   {
     "date": "2026-07-23 09:11:15",
     "data": {
       "measurement": [
         { "resourceId": 464399, "targetName": "CPU", "min": 0.55, "avg": 0.55,
           "targetId": 465050, "max": 0.55, "resourceName": "cob0-bnoapd05",
           "definition": "Utilization", "targetType": "server.Cpus", "time": 1784765400000 },
         { "resourceId": 464541, "targetName": "CPU", "min": 2.066666666666667, "avg": 2.066666666666667,
           "targetId": 465274, "max": 2.066666666666667, "resourceName": "cob0-bnoapd07",
           "definition": "Utilization", "targetType": "server.Cpus", "time": 1784765460000 }
       ]
     },
     "id": "dashboard - measurement"
   }
   ```

   파서 주의: ① 요청한 서버가 응답에 **누락**될 수 있음을 전제(수집 중단 서버 등) — 요청 ID 집합과 응답 `resourceId` 집합을 대조해 누락분을 "미수집"으로 표기. ② `avg` 값의 긴 소수(2.0666…)는 표시 시 반올림하되 **집계 전 캐스트 규칙과 무관**(API 값은 최종값). ③ 최상위 `date`는 호출 시각, 항목별 `time`은 수집 시각 — 신선도 판정에는 `time`을 사용(§1.4).
3. **`count` 파라미터**: 반환 샘플 수(시도 횟수)로 확인 — `count=2`면 동일 자원에 대해 연속 두 시점(`time` 1784770860000 → 1784770920000, 60초 간격)이 반환됨. **`count=1` 고정 사용**으로 확정.
4. **성능·크기 실측 (Postman)** — URL 길이·응답 크기·지연 모두 200대 단일 콜까지 문제 없음:

   | 존 | 10대 | 20대 | 100대 | 200대 |
   |---|---|---|---|---|
   | 여의도(yd) | 198ms | 486ms (9.99KB) | 620ms (20.33KB) | 814ms (37.7KB) |
   | 김포(gp) | 506ms | 655ms (4.08KB) | 1,774ms (20.24KB) | **2,460ms** (36.31KB) |

   설계 반영: ① **청크 크기 200대/콜**로 확정(URL ~1.6천 자, 일반 한계 내). 존 서버 수가 200을 초과하면 청크 분할 + 병렬 호출, 전체 타임아웃 가드 유지(Known Mistakes: per-call 타임아웃만으론 무력화). ② **김포가 여의도 대비 ~3배 느림**(200대 2.46s) — Plan 47-1의 `process_api_timeout_seconds=3`을 재사용하면 김포 대량 조회가 타임아웃 경계에 걸린다. **measurement 전용 타임아웃을 별도 설정**(예: 10s)할 것. ③ 존별(김포/여의도/은행) 콜은 병렬화.
5. **존별 base_url — 은행존 지원 확인**: 은행존(b0)에도 API 존재, `http://10.37.16.51:9010` (**포트 9010 주의** — 기존 gp/yd base_url과 달리 포트 명시 필요, CSV 값에 포트 포함 그대로 기입).
   - **설정명 제네릭화(사용자 제안) — 찬성**: 현행 `process_api_base_urls_csv`는 이름만 프로세스 API 전용일 뿐 실체는 **폴스타 REST API의 base_url**이며, measurement API도 동일 base를 쓴다. `polestar_rest_base_urls_csv` 등 제네릭 명으로 통합을 권장한다. 단 3가지 조건: ① **하위호환** — 기존 `.env` 키를 pydantic `AliasChoices`로 폴백 유지(설정 유무 판단에 `os.getenv()` 금지 — Known Mistakes). ② base_url은 통합하되 **기능별 옵트인 플래그는 분리** 유지(`process_enrich_enabled` 등). b0 프로세스 API 부재/미등재 논점은 **"미등재"로 확정**(2026-07-24 실측: `10.37.16.51:9010`의 listByhostname 호출 200 OK·프로세스 배열 수신 — 동일 솔루션이라 동일 API 지원). 따라서 **통합 CSV에 b0를 포함**하며, 부수 효과로 알람 프로세스 보강(Plan 47-1)의 은행존 확장도 가능해짐(확장 여부는 별도 결정). ③ rename 시 참조부 전수 grep(정의만 고치고 호출부 누락 금지).

### 1.4 설계 시 권고 사항

- **라우팅 게이트는 결정적으로**: "실시간 현황"(API)과 "지난달 통계"(DB `cmm_metric_stat_m`)의 분기를 LLM 의도 분류에 맡기지 말 것(D-035). 표면어 범위는 **B안 권고**(§5.1 항목 1): *기간 표현(`resolve_stat_month_range` 결과) 없음 + "실시간/현재/지금" 명시*일 때만 API 경로 — "현황" 단독은 기존 DB 경로 유지. 오분기하면 통계 질의에 실시간 스냅샷으로 답하는 사고가 되며, 이 비용이 반대 방향(실시간 의도가 몇 분 낡은 DB 값으로 답변)보다 훨씬 크다. 옵트인 플래그로 시작해 비활성 시 기존 경로 무변경(회귀 0).
- **흐름은 2단계 하이브리드**: 서버 목록·서버 ID는 어차피 DB(`cmm_resource`)에서 SQL로 확보해야 하므로, "①SQL로 존 내 서버 ID 목록 → ②API로 측정값 → ③병합"의 결정적 조립. 기존 오케스트레이션 다중 task 흐름(선행 task 결과 스코프 전달, D-099 패턴)과 정합.
- **신선도 표기**: `time`(Unix ms)은 **마지막 수집 시각**이지 호출 시각이 아니다(호출 시각은 최상위 `date`). 수집이 중단된 서버의 낡은 값이 "실시간"으로 오인될 수 있으므로, KST 변환한 수집 시각을 결과에 노출하고 임계(예: 10분) 초과 시 "수집 지연" 플래그를 달 것. 요청 대비 응답 누락 서버는 "미수집" 표기(§1.3-2).
- **폴백은 침묵 금지**: API 실패(타임아웃/비200/파싱 실패) 시 DB 마지막 수집값으로 폴백하되, 응답에 "실시간 조회 실패 — DB 마지막 수집값(수집 시각 포함)"을 명시(Known Mistakes: 침묵적 폴백 금지).
- **감사로깅**: 스펙의 "모든 쿼리 실행 감사로깅"은 이 API 호출에도 적용해야 일관적이다(호출 URL·대상 서버 수·소요 시간).
- **계층**: 클라이언트는 `PolestarProcessApiClient`([polestar_process_api.py](src/alarm/infrastructure/polestar_process_api.py)) 패턴으로 infrastructure 계층에, 존→base_url 매핑은 기존 CSV 패턴 재사용(§1.3-5 제네릭 rename 포함). arch_check 통과 확인.

## 3. "모든 서버" 질의의 LIMIT 절단

### 3.1 결론 — 신규 기획이 아니라 **기존 가드(D-066)의 우회 버그**

"모든/전체/모두" → LIMIT 100,000 상향 가드는 이미 존재한다:

- 공용 함수 `resolve_query_limit` ([query_gen_common.py:136-168](src/utils/query_gen_common.py#L136-L168)) — 명시 건수("100건"/"상위 N") > "모든/전체/모두"(100,000) > 기본값(1,000) 우선순위.
- 단일 DB 경로([query_generator.py:266](src/nodes/query_generator.py#L266))와 멀티 DB 경로([multi_db_executor.py:134](src/nodes/multi_db_executor.py#L134)) 양쪽에 주입되어 있고, 트랙 C 컴파일에도 `default_limit=limit_value`로 전달된다.

그런데도 LIMIT 1000이 재발한다면, 가드에 **원문이 도달하지 않는 경로**가 있다는 뜻이다.

### 3.2 원인 — **실측 확정(2026-07-24)**: 단일 DB 경로의 `sub_query_context` 대체 (단일/멀티 비대칭)

초판(v2)은 intent_planner의 sub_query 재작성을 유력 가설로 세웠으나, 실측 3건(§3.3)과 코드 대조로 **정확한 탈락 지점은 그 다음 단계**로 확정됐다. 원문 훼손은 두 겹으로 일어난다:

1. **(공통) 오케스트레이션 진입 시** `user_query`가 intent_planner의 `sub_query`로 대체된다([agent_orchestrator.py:162](src/orchestration/agent_orchestrator.py#L162), [process_query.py:269](src/orchestration/process_query.py#L269), [subagents.py:782](src/orchestration/subagents.py#L782)). 실측 질의 2에서 보듯 이 단계는 "모든"을 대체로 보존한다("모든 데이터들"→"모든 서버들").
2. **(결정적 탈락 지점, 단일 DB 경로 한정)** [subagents.py:817-820](src/orchestration/subagents.py#L817-L820)에서 단일 DB로 라우팅되면 `user_query`를 sub_query가 아니라 **semantic_router가 정제한 `sub_query_context`로 다시 교체**한다. 이 정제는 위치어의 SQL WHERE 누출 방지가 목적(§4.9.6 디멘전 7)이지만, 라우터 프롬프트의 few-shot 예시([semantic_router.py:43-45](src/prompts/semantic_router.py#L43-L45): "여의도 개발 폴스타에서 서버 리스트 출력" → "서버 목록 조회")가 **위치어 제거가 아니라 문장 전체 압축**을 시연하고 있어, "모든" 같은 수량 한정어까지 함께 탈락한다. 실측 질의 1·3의 축소 문자열("OS 종류 및 버전 조회")이 정확히 이 정제 스타일이다.
3. **멀티 DB 경로는 `sub_query`를 유지**하므로([subagents.py:819](src/orchestration/subagents.py#L819) 주석 명시) "모든"이 살아남아 `multi_db_executor`의 `resolve_query_limit`이 100,000을 반환한다 — 실측 질의 2와 일치.

즉 이 버그는 질의별 LLM 비결정성이 아니라 **단일/멀티 경로의 구조적 비대칭**이다(Known Mistakes "단일/멀티 경로 대칭" 원칙의 전형 사례): 같은 "모든" 질의라도 존이 단일 DB로 풀리면(은행존→b0, 공동존 김포→gp) 반드시 절단되고, 멀티 DB로 풀리면(공동존→gp+yd) 보존된다.

### 3.3 실측 결과 (사용자, 2026-07-24) — 원인 경로 확정 완료

v2의 테스트 가이드(계측→재현→판정표→mock 고정)에 따라 3건이 실측되었다:

| # | 질의 원문 | 경로 | `resolve_query_limit` 입력(관찰된 축소 문자열) | LIMIT |
|---|---|---|---|---|
| 1 | "은행존에 등록된 모든 데이터들에 대해 OS 종류 및 버전을 확인" | **싱글**(b0) | "OS 종류 및 버전 조회" — "모든"·존 표현 모두 탈락 | **1,000 (절단)** |
| 2 | "공동존에 등록된 모든 데이터들에 대해 OS 종류 및 버전을 확인" | **멀티**(gp+yd) | "공동존에 등록된 모든 서버들에 대해 OS 종류 및 버전을 확인" — "모든" 보존 | 100,000 (정상) |
| 3 | "공동존 김포에 등록된 모든 데이터들에 대해 OS 종류 및 버전을 확인" | **싱글**(gp) | "OS 종류와 버전 조회" — "모든"·존 표현 모두 탈락 | **1,000 (절단)** |

판정: **싱글=절단 / 멀티=정상**으로 경로에 따라 100% 갈렸다 — §3.2의 구조적 비대칭(단일 경로의 `sub_query_context` 교체)과 정확히 일치하며, 질의별 우연이 아니다. 질의 1·3의 축소 문자열이 존 표현까지 제거된 형태인 것도 semantic_router 정제(위치어 제거 + 문장 압축)의 산물로 설명된다. 재시도 경로·트랙 C 가설(v2 판정표의 나머지 행)은 기각 — 추가 계측 불요.

**사고 영향도 확정 (추가 실측, 2026-07-24)**:

- **존 정합 — 문제 없음.** 질의 1·3 모두 요청한 존(은행 폴스타 / 공동존 김포 폴스타)의 데이터만 반환됐다. 존 표현이 SQL 생성 입력에서 사라진 것은 의도된 설계(위치는 DB 라우팅 전용, WHERE 누출 금지)이며, 라우팅은 정상 — 결함은 절단 하나로 국한된다.
- **행 절단 — 실피해 확정.** 감사 로그 `row_count=1000`, 존 서버 총수는 은행존 **2,328대**·공동존 김포 **1,820대**. 즉 질의 1은 **1,328대(57.0%)**, 질의 3은 **820대(45.1%)** 누락된 채 응답됐다. 두 존 모두 총수가 기본 LIMIT(1,000)을 초과하므로 이 버그는 간헐 결함이 아니라 **존 전체 조회에서 상시 발현되는 결함**이다. 수정 후 LIMIT 100,000이 적용되면 두 존 모두 `max_rows=10,000` 이내라 전량 반환 가능하다.

### 3.5 "LIMIT 제거" 안은 비권장

- LIMIT 절 자체를 없애는 것은 스펙의 안전 제약(최대 10,000행, 30s 타임아웃)과 충돌하고, 검증기의 LIMIT 요구 규칙과도 어긋난다.
- 현행 상향값 100,000은 이미 충분히 높으며, 실질 상한은 DB 클라이언트의 `max_rows=10000`([db/client.py:45](src/db/client.py#L45))에서 한 번 더 잘린다. 존 전체 서버는 수백~수천 대 규모이므로 **LIMIT 100,000 + max_rows 10,000 이중 안전망 유지**로 충분하다. 즉 이 항목의 실작업은 "LIMIT 정책 변경"이 아니라 **§3.2 전파 버그 수정**이다.
- 만약 향후 1만 행 초과 추출이 실제로 필요해지면(월보 등) 그때 `max_rows` 정책을 별도 결정(D-번호)으로 다룰 것 — 대화형 응답이 아니라 파일 산출 경로에서만 완화하는 것이 안전하다.

## 4. 존 모호 시 역질문 (전 존 폴백 → 사용자 선택)

### 4.1 결론

**찬성 — 단, 발동 조건은 결정적 게이트로 좁게.** → **구현 완료 (2026-07-24, D-140).** 최종 구현은 LLM `clarification_needed` 방출을 기다리지 않고 **라우트 진입 시 결정적 게이트로 파이프라인 실행 전 반환**하는 stateless 설계를 채택했다(`api/routes/query.py::_zone_clarification_or_none` — 서버측 보류 상태 없음, 재개는 프론트가 원문+`selected_db_ids`를 재전송). 배선: /query·/query/stream 대칭 조기 반환 → 프론트 체크박스 3개 UI([app.js](src/static/js/app.js) `renderZoneClarification`, 미선택 시 확인 버튼 비활성, 새 질의 시 보류 블록 자기정리) → `selected_db_ids` 구조화 재전송 → [semantic_router](src/routing/semantic_router.py)(우선순위 2.5)·[intent_planner](src/orchestration/intent_planner.py)(②.5 pre-check)가 mapped_db_ids 선례 동형으로 LLM 우회 고정 → 복합 계획 개별 task까지 [subagents](src/orchestration/subagents.py) raw_targets 폴백으로 커버. 테스트 12종(`tests/test_orchestration/test_zone_selection.py`).

### 4.2 발동 조건 — LLM 방출에 의존하지 말 것

Known Mistakes 원칙(LLM 분류에 정합성 의존 금지)에 따라, 역질문 트리거는 결정적으로:

- **발동**: (질의가 존 단위 대량 조회 의도 — "모든/전체 서버" 등 표면어) AND (존 식별 불가 — `LOCATION_HINT_TERMS`([input_parser.py:35](src/nodes/input_parser.py#L35)) 미포함 또는 "ㅇㅇ존" 리터럴 포함).
- **비발동(기존 폴백 유지)**: 서버명 지목 질의(존이 결과에 영향 없음 — hostname으로 어차피 특정됨), 멀티턴에서 직전 턴 존 승계 가능한 경우(`previous_entities` 폴백), 존 무관 질의.
- LLM의 `clarification_needed` 방출은 보조 신호로만 취급(방출돼도 결정적 게이트 미충족이면 무시).

**과잉 역질문이 최대 리스크다.** 존이 없는 모든 질의에 되물으면 "물어보면 다 해주던" 현재 UX보다 후퇴한다. 존별 데이터 격리가 실질적 의미를 갖는 대량 조회에서만 발동해야 한다.

### 4.3 배선 설계 권고

1. **응답 형식**: API 응답에 `type="clarification"` + `question` + 선택지를 내리고 UI가 렌더(선택 UI 방식은 §4.4). **전 존 조회 경로를 막지 않을 것** — 체크박스 3개를 모두 선택하면 기존 폴백(전 존 조사)과 동일하게 동작한다(별도 "전체" 항목·단축 버튼은 사용자 결정으로 두지 않음 — §4.4).
2. **후속 턴**: 선택 시 동일 `thread_id`로 이어 보내고, 서버는 보류된 원 질의에 존을 결합해 재개. **멀티턴 검증은 요청 본문에 thread_id가 실제 실리는지 프론트까지 확인**(Known Mistakes). LangGraph 체크포인터 사용 시 보류 상태(pending_clarification)는 요청 스코프이므로 라우트에서 명시 초기화 대상에 포함할 것.
3. **비대화 경로 분기**: API 직접 호출·배치(월보 추출 등)처럼 역질문이 불가능한 경로는 기존 전 존 폴백을 유지하되, 응답에 "존 미지정 — 전 존 조회함"을 명시(침묵적 확대 해석 금지).
4. **타임아웃/이탈**: 역질문 후 사용자가 응답하지 않고 새 질의를 보내면 보류 상태를 폐기하고 새 질의로 처리(보류 상태가 다음 턴을 오염시키지 않도록 자기정리).
5. §2의 "ㅇㅇ존" 프리필 버튼과 같은 릴리스로 묶어, 무수정 전송 → 역질문 → 존 선택의 흐름을 완결시킬 것.

### 4.4 존 선택 UI 방식 — 체크박스 3개 단독 **확정** (사용자, 2026-07-24)

사용자 지적 두 가지를 반영해야 한다: ① 공동존은 김포센터/여의도센터를 **분리 지정**할 수 있어야 하고, ② "은행존 + 공동존 김포"처럼 **존을 조합**하는 조회가 실사용에 존재한다. 따라서 단일 선택 버튼으로는 부족하다.

**선택지 입도는 DB 라우팅 입도와 일치**시킨다 — 은행존(b0) / 공동존 김포(gp) / 공동존 여의도(yd)의 3개 체크 항목([domain_config.py](src/routing/domain_config.py) 등재 단위와 동일). "공동존 전체"는 gp+yd 두 항목 체크와 동치다. 초안은 단축 버튼(전체/공동존)을 보조 편의로 함께 제안했으나, **사용자 확정(2026-07-24): 단축 버튼 없이 체크박스 3개 단독**으로 간다(UI 단순화 — 전체/공동존 선택은 해당 항목을 직접 체크). 구조화 전송(ⓒ)·자유 텍스트 폴백(ⓓ)은 동의됨.

| 방식 | 평가 |
|---|---|
| ① 단일 선택 버튼 | **탈락** — 다중 조합(은행존+김포) 불가 |
| ② **체크박스 + 확인 버튼** | **채택(확정)** — 다중 조합 충족, 선택 결과가 구조화 값으로 확정되어 결정적 라우팅 가능, 오타 없음. 전체 선택 = 3개 모두 체크(단축 버튼 없음) |
| ③ 존 리스트 제시 + 자유 텍스트 입력 | 보조 폴백으로만 — 자유 입력은 오타·모호 표현("김포쪽")으로 **다시 모호성으로 회귀**해 역질문의 취지가 반감된다. 단, 별도 구현 없이도 자연 폴백으로 동작: 사용자가 체크박스 대신 채팅으로 "은행존이랑 김포"라고 답하면 다음 턴이 일반 질의로 흘러 기존 위치 힌트 결정적 보강(D-065)이 처리한다 |

UX 보강(2026-07-24, 사용자 피드백): 존 선택 대기 중 입력창이 비어 있으면 **전송 버튼(Enter 포함)도 "선택한 존으로 조회"와 동일 동작** — 체크 후 습관적으로 전송을 누르는 흐름 수용. 체크가 없으면 "조회할 존을 선택해주세요"로 안내(기존 "질의를 입력해주세요" 오류 대체). 입력창에 새 질의를 치고 전송하면 기존대로 보류 블록 자기정리 후 새 질의 처리.

구현 시 핵심 원칙 — **선택 결과를 자연어로 재조합해 재질의하지 말 것.** 체크 결과는 구조화 필드(예: `selected_db_ids: ["polestar_b0", "polestar_cm_gp"]`)로 백엔드에 전달해 `target_db_hints`/`priority_db_ids`에 결정적으로 주입한다. 자연어 재조합 후 재파싱하면 LLM 재해석이 개입해 "은행존 알람"→"김포 은행 공동존…" 오라우팅 실측 사례(2026-07-16)와 같은 오염 경로가 열린다. 화면에는 사용자 메시지로 "선택: 은행존, 공동존 김포"를 에코해 대화 이력의 가독성만 확보한다.

  3. **좁게 → 넓게가 안전한 확장 방향** — 신규 데이터 평면은 옵트인·회귀 0 원칙으로 시작하고, 운영 후 감사 로그에서 "현황" 질의의 실시간 의도 비율을 관찰해 필요 시 A안으로 확장하면 된다. 반대 방향(넓게 시작 후 축소)은 사용자 습관 파괴라 어렵다.
