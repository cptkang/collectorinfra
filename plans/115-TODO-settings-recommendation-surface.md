## 1. 결론

### 1.1 한 줄

**권고는 이미 만들어지고 있는데 파일 안에서만 산다.** 벤치는 축마다 최적 레벨을 정해 `recommended.env.diff`·`knob_disposition.md`로 쓰지만(`scripts/bench/optimize.py`), 관리자 설정 화면(`GET /admin/settings/schema`)은 그 존재를 모른다. **둘을 잇고, 적용은 사람이 누르게 한다.**

### 1.2 사용자 확정 (2026-09-23)

| 물음 | 확정 |
|---|---|
| 화면에서 권고값을 어떻게 다루나 | **표시 + 버튼으로 적용.** 키마다 권고값·근거·출처를 배지로 보여주고, 「권고값 적용」(개별)과 「권고 일괄 적용」(N건)으로 **사용자가** 저장한다. 기존 저장 경로(.env 기록 → 재시작·리로드 안내)를 그대로 쓴다 |
| 권고 출처를 어디까지 | **벤치 측정 + 분석 근거 둘 다.** 단 화면에서 **「측정됨」과 「분석 근거」를 구분 표기**한다 |

**기동 시 강제 적용은 하지 않는다**(사용자가 고르지 않은 안). 근거: ①설정이 사람 모르게 바뀌면 `.env` 실측값으로 판단하라는 D-161 규율이 무너진다 ②사다리 단처럼 실행 경로를 바꾸는 키가 포함돼, 강제 적용은 곧 "다른 제품을 돌리는 것"이다 ③되돌릴 지점이 화면에 남지 않는다.

### 1.3 설계 요지 셋

1. **권고의 단일 계약은 파일 하나다** — 벤치가 `recommendations.json`을 쓰고, 서버는 그것만 읽는다. `src/`가 `scripts/`를 import하지 않는 현행 경계를 지킨다(실측: `src/`에서 `import scripts` 0건).
2. **분석 근거 권고는 저장소 정본에 둔다** — `config/recommendations.yaml`. 측정 없이도 근거가 선 항목(예: `API_QUERY_TIMEOUT=60`)을 사람이 적고, 화면이 같은 자리에서 보여준다.
3. **적용은 기존 저장 흐름 위에 얹는다** — 새 저장 경로를 만들지 않는다. 버튼은 입력칸을 채우고 기존 `PUT /admin/settings`로 간다(마스킹·재시작 안내·준비도 경고가 그대로 돈다).

## 3. 설계

### 3.1 W-1 · 권고 계약 파일 — 벤치가 쓰고 서버가 읽는다

- **산출**: 캠페인·스위프가 끝날 때 `recommendations.json`을 함께 쓴다(기존 4종 옆).
- **형식**(키마다 1건 · 다중 키 축은 `keys`로 함께 싣는다):

  ```json
  {"generated_at": "...", "run_id": "...", "campaign": "...", "qualified": true,
   "caveats": ["사다리 단 축이 「판정 불가」다 — 기준 경로로 고정했다"],
   "items": [{"env_key": "TEXT2SQL_SELECTION", "recommended": "hybrid",
              "current_effective": "llm", "action": "존치 + 권고값", "rule": "§6.5.2-3",
              "verdict": "레벨 우세", "reason": "...", "axis": "TEXT2SQL_SELECTION",
              "keys": null, "segment_id": "text2sql-3", "measured_at": "..."}]}
  ```
- **자격 없는 run의 권고는 싣지 않는다**(D-219). `qualified: false`면 파일은 쓰되 `items`를 비우고 사유만 남긴다 — 조용히 사라지면 "권고가 없는 것"과 구별되지 않는다.
- **조건부 표기를 함께 싣는다**: 사다리 단이 기준 경로가 아니거나 판정 불가로 고정됐으면(D-250 ②) 그 문장을 `caveats`에 넣는다. 화면이 그대로 보여준다.
- 앵커: `scripts/bench/optimize.py`(`write_proposals` 옆에 `write_recommendations_json`) · `scripts/bench/__main__.py` 호출부.

### 3.2 W-2 · 분석 근거 권고 정본 — `config/recommendations.yaml`

- 측정 없이 근거가 선 항목을 사람이 적는다. 필드: `env_key`·`recommended`·`reason`·`evidence`(문서·run id)·`source: analysis`·`applies_when`(선택 — 예: 폐쇄망만).
- **측정 권고와 충돌하면 측정이 이긴다**(D-161 「실측 우선」). 화면은 둘 다 보여주되 적용 버튼은 측정값에 붙이고, 분석 권고는 "측정이 대체함"으로 접는다.
- 초기 내용은 §2.3 표.

### 3.3 W-3 · API — 스키마에 권고를 얹는다

- `SettingSchemaItem`에 `recommendation` 필드 1개 추가(없으면 `null`):
  `{value, source: "measured"|"analysis", action, reason, evidence, run_id, measured_at, keys, caveats, applicable: bool, blocked_reason}`
- **적용 불가 판정을 서버가 낸다**(화면이 추측하지 않게): `override`가 `os`·`encenv`면 `.env`를 고쳐도 실효값이 안 바뀐다 → `applicable: false` + 사유. 시크릿·`is_sensitive`도 제외.
- 일괄 적용용 목록: `GET /admin/settings/recommendations` — 적용 가능한 것만, 다중 키 축은 묶음 1건으로.
- 앵커: `src/api/settings_catalog.py`(모델·조립) · `src/api/routes/admin.py`(엔드포인트 1개 추가).

### 3.4 W-4 · 화면 — 배지·근거·버튼

- 행에 배지: `권고 120` + 출처 칩(`측정됨`/`분석 근거`). 클릭하면 근거(사유·run id·판정 어휘)를 도움말 패널에 띄운다(기존 `openSettingHelp` 재사용).
- 버튼 둘: 행의 **[권고값 적용]**(입력칸을 권고값으로 채움 · 저장은 기존 버튼) · 상단 **[권고 일괄 적용 (N건)]**(적용 가능한 것만 채움 · 저장 전 확인).
- 필터 하나 추가: `권고 있음`. 기존 필터(등급·미소비)와 같은 자리.
- **적용 불가 항목은 배지만 두고 버튼을 비활성**하며 사유를 보여준다(OS 환경변수·`.encenv`가 덮는 키).
- 앵커: `src/static/js/admin.js:356` `renderSettings`·`buildGroup`·`openSettingHelp` · `src/static/admin/dashboard.html` 필터 영역.

### 3.5 W-5 · 다중 키 축(사다리 단)은 묶음으로만

- 사다리 단 권고는 3키를 **함께** 바꿔야 그 레벨이다(`optimize.py`가 이미 경고 문구를 쓴다). 화면도 3행을 한 묶음으로 표시하고, 개별 적용 버튼 대신 **묶음 [권고값 적용]** 하나를 둔다.
- 부분 적용 시도(사용자가 한 키만 직접 고침)는 막지 않되, 저장 응답에 "이 키는 묶음 권고의 일부다 — 나머지 2키가 권고와 다르면 그 레벨이 아니다"를 경고로 싣는다.

### 3.6 W-6 · 안전장치

| 장치 | 이유 |
|---|---|
| 자격 없는 run의 권고 미표시(사유는 표시) | D-219 — 무자격 측정으로 설정을 바꾸면 이번 사고의 재연 |
| 조건부 표기(사다리 단·타임아웃률) 상단 배너 | D-250 ② — "이 권고는 그 단에서 잰 값" |
| `override`(os·encenv) 키는 적용 불가 + 사유 | `.env`를 고쳐도 실효값이 안 바뀐다(`settings_catalog` 실측 필드) |
| 시크릿·민감값 제외 | 권고 대상이 아니다 |
| 적용 뒤 반영 시점 안내는 기존 응답 그대로 | `apply_mode` 3분류(D-068 계열)를 새로 만들지 않는다 |
| 권고 파일이 없거나 낡았으면 그 사실을 표시 | 조용히 "권고 없음"으로 보이면 벤치가 안 돈 것과 구별되지 않는다 |

### 3.7 하지 않는 것

- **기동 시 강제 적용**(§1.2) · `.env` 자동 수정 · 권고를 근거로 한 런타임 자동 스위치.
- 권고 생성 규칙 변경 — 처분 어휘·규칙 번호는 `plans/109` 소유다. 이 계획은 **전달과 표시**만 한다.

| **G-1** | 권고 파일(`recommendations.json`)을 **어디서** 읽나 — ①`results/bench/campaigns/<최근>/`를 서버가 직접 읽는다 ②운영자가 관리자 화면에서 **업로드**한다 ③설정으로 경로를 준다(`RECOMMENDATIONS_PATH`) | **③ + ①의 기본값.** 폐쇄망에서 벤치와 서버가 같은 기계가 아닐 수 있다(측정은 `nclago01`). 경로 설정을 두되 기본은 최근 캠페인 폴더로 본다. ②는 W-1 이후 필요하면 더한다 |
| **G-2** | 「권고 일괄 적용」이 재시작 필요 키를 포함할 때 — ①저장만 하고 안내 ②저장 후 재시작을 유도하는 문구·버튼 | **①.** 재시작은 운영 행위다. 기존 응답의 `requires_restart_keys`를 그대로 보여주고, 재시작은 사람이 한다 |

## 6. 성공 기준

- 관리자 「환경변수 설정」에서 **권고가 있는 키를 필터 하나로 모아 볼 수 있다**(측정·분석 구분 표시).
- 「권고값 적용」이 기존 저장 경로를 그대로 타고, 재시작·리로드 안내가 종전과 같이 나온다.
- OS 환경변수·`.encenv`가 덮는 키는 **적용 버튼이 없고 사유가 보인다**.
- 사다리 3키는 **묶음 1건**으로 뜬다 — 부분 적용하면 경고가 뜬다.
- 자격 없는 캠페인의 권고는 화면에 **뜨지 않고**, 대신 "측정이 자격을 얻지 못했다"가 뜬다.
- 유효 캠페인이 없는 현재 상태에서도 §2.3의 분석 근거 권고가 화면에 선다.
