### 0.2 권고 한 줄

**자유 분해를 "작업 루틴 선택 + 슬롯 채우기"로 바꾸고, 어느 DB·시스템인지는 정본에서 파생한 소스 카탈로그와 소유표로 코드가 정하며, 시스템을 넘을 때는 식별자를 결정적으로 변환해 배치로 넘기고, 결과는 계획이 약속한 항목을 코드가 대조한 뒤 출처와 함께 짧게 쓴다.**
순서: TP-0(측정) → TP-1(결함) → TP-2(루틴)·TP-9(소스 카탈로그) → TP-10(다중 소스 연쇄) → TP-4(결과 작성) → TP-5(재계획). 각 단계는 D-251 ⑦에 따라 기준선 → 수정 → 재측정.

## 1. 배경과 범위

### 1.1 용어

| 용어 | 이 문서에서의 뜻 | 현행 대응물 |
|---|---|---|
| **작업 유형**(request type) | 요청 전체의 **구조** 분류 — "선별 후 상세", "비교", "교차 도메인" 같은 단계 골격의 종류 | **없음**. 비슷한 신호가 5곳에 흩어져 있다(§2.2) |
| **작업 루틴**(task routine) · 지침 | 유형 하나에 대한 **선언적 절차** — 단계 목록 · 단계별 답변 영역 · 입출력 타입 · 0행/오류 시 처리 · 응답 골격 · 완결성 체크리스트. 문헌의 SOP·Routine·rule library | 없음. 분해 프롬프트의 규칙·예시 6건이 유일한 지침 |
| **주단계** | 루틴의 단계 = 처리기 1회 호출(task) | `task_plan`의 task(`TaskSpec`) |
| **세부 단계** | 처리기 안의 고정 단계 — 스키마 분석 → SQL 생성 → 검증 → 실행 → 정리 | `_run_single_db_pipeline`에 코드로 고정 |
| **결과 작성 계획** | 응답 골격 + 완결성 체크리스트 + 요약 방식(템플릿/짧은 LLM) | 없음 |
| **바인딩** | 단계를 기존 처리기(LangGraph 노드 함수·도구)에 연결 | `SUBAGENT_REGISTRY` 7종 디스패치 |
| **처리기 계약**(handler contract) | 처리기의 목적 · 입력 슬롯 타입 · 출력 타입 · 부작용 없음 · 선행조건 · 지연 등급 · (v2) 필수 입력·키 패싯·바인드 상한 | `SubAgentSpec.description` 1줄 |
| **(v2) 데이터 소스 · 시스템** | 조회가 실제로 일어나는 곳 — 폴스타 존 DB · ITAM DB · Prometheus · 폴스타 REST · OpenMetrics exporter | 레지스트리 `databases`·`solutions`(SQL만 · 비SQL 미등재) |
| **(v2) 답변 영역**(capability) | "무엇을 답할 수 있는가"의 코드 — 자산 계약·서버 사용률·알람 등. **소유 소스**가 레지스트리에 선언된다(D-224 ①) | `db_registry.yaml` `capabilities` 10종 · 소유표는 플래그 뒤 |
| **(v2) 소스 카탈로그** | 소스별 "보유 데이터"의 정리본 — 답변 영역·속성·입도·단위·신선도·커버리지·정본/대체·필수 입력. **정본 파일에서 파생**하고 사본을 두지 않는다(D-131) | 없음 — 설명이 7곳에 흩어짐(§2.8) |
| **(v2) 엔터티 집합 · 키 패싯** | 단계 사이로 넘기는 대상 집합(서버 등)과 그 식별자 여러 형태(hostname · server_name · IP · FQDN) | 서버 식별자 IN 목록 1종(`prior_rows`) |
| **(v2) 키 브리지** | 한 시스템의 식별자를 다른 시스템의 식별자로 결정적으로 변환·판정(1:1 / 0건 / 다건) | `key_bridge.py`(D-224 ②③④ · 기본 off) |
| **(v2) 바인드 조인** | 선행 결과의 키로 다음 소스 조회를 매개하는 것(bind join · 분산 semijoin) — 배치·상한·장부 포함 | `input_from` → `prior_rows` IN 목록(100 상한) |
| **(v2) 출처**(provenance) | 응답의 각 값이 어느 소스·어느 단계에서 왔는지 | `_source_db`(한 task 안 멀티 DB만) |

> "작업 루틴"은 알람의 `is_routine`(일상 반복 알람)과 무관하다. 코드 식별자는 `task_routine`으로 구분한다.

### 2.1 흐름과 LLM 호출

```
context_resolver → input_parser [LLM ①: parsed_requirements 10키]
 → field_mapper
 → intent_planner
     ├ 사전 처리 계층 A — 결정적 10종(유사어·양식 기억·존 재진입 ②.5·mapped_db_ids ③·양식 업로드·사용법 …)
     │   → 단일 task 즉시 반환 (LLM 0)                                   intent_planner.py:298-417
     └ _llm_decompose [LLM ② 1~2회: 원문만 읽는다 — parsed_requirements 미참조]   :766-782
         → tasks[{task_id, agent, sub_query, depends_on, input_from, order}]
         → _normalize_plan_exit(알람·프로세스 교정, 무조건 · D-250 ⑤) → DAG 검증(코드 기본 on)

     task → SUBAGENT_REGISTRY 7종 → 기존 노드 함수 직접 호출                subagents.py:1660-1695
       data_query: classify_dbs [LLM ③ — DB 설명 문장만 보고 DB 선택] → schema_analyzer [LLM ④ 테이블 선택]
                   → query_generator [LLM ⑤] ⇄ query_validator → query_executor → result_organizer
 → replanner — 결정적 조기 종료 → LLM 평가 [⑥] → 결정적 필터 6종 → task **추가만**   replanner.py:236-242

```

#### 2.7.3 시스템별 식별자 — 같은 서버를 부르는 이름이 다르다

| 시스템 | 식별자 | 상태 |
|---|---|---|
| 폴스타 | `hostname`(OS 호스트명) · `name`(등록 서버명) — **둘이 다르다**(D-036·D-061) | 매니페스트 `entity_keys` 있음(`polestar_cm_gp.yaml:648-653`) |

#### 2.7.4 한계와 결과 종합

- **상한**: 선행 행 주입 100행 · 스코프 값 100개 · 조사 대상 10(`process_query`만) · 같은 레벨 task **동시성 상한·task별 타임아웃 없음** · PromQL 시리즈 상한 없음.
- **부분 실패**: task 예외 → 실패 표기 · 의존 후속 skip + 노트. **소스 부재(Prometheus 미연결·ITAM 운영 미연결)를 계획 단계에서 알리는 장치가 없다.**
- **인가**: ITAM은 `db_id`라 D-232가 적용된다. **Prometheus·OpenMetrics에는 사용자 단위 인가 축이 없다.**
- **감사**: `inspect_host`·`process_query`는 본체 감사 호출 0건 · PromQL은 mcp_server 로그 줄뿐.
- **출처 표기**: `_source_db`는 한 task 안 멀티 DB에만 붙는다 — **task를 넘는 병합에는 시스템 출처가 없다**. LLM 합성 입력은 `[조회 i]` 번호뿐이다.
- **단위·시점**: 폴스타 사용률은 %, ITAM `sevrCPUUseRt`는 연계 스냅샷(**같은 이름 · 다른 의미** — `plans/95` T5), Prometheus는 counter/0~1. **정규화·표기 계층이 없다.**

#### 2.8.2 라우터가 실제로 보는 것

- **DB당 설명 한 덩어리**: 표시명 · 별칭 · 레지스트리 설명 · (Redis에 있으면) LLM 생성 `상세` 한 줄(`src/routing/semantic_router.py:1263-1297`). **테이블·지표·시간 입도·존별 커버리지 차이·비SQL 시스템은 없다.**

- 관련도 임계 0.3 · 통과 0건이면 **첫 활성 DB로 폴백**(노트는 소유 플래그 on에서만 — `subagents.py:193-215`).
- few-shot 예시에 db_id가 하드코딩돼 있고, **예시 한 줄 교정만으로 교차 시스템 케이스 r-073이 결정적으로 회귀**했다(9B · `plans/113` 부록 C) — 프롬프트 예시가 사실상의 소스 지식원이며 민감하다.
- DB 안의 테이블 선택 LLM은 **테이블명 + 앞 15개 컬럼명**만 보고 설명은 보지 않는다(`schema_analyzer.py:949-1034`).

#### 2.8.3 비SQL 시스템은 데이터 보유가 아니라 원문 키워드로 고른다

- 실시간 프로세스 API · 실시간 사용률 REST · `host_inspect` MCP 도구 · OpenMetrics `metrics_live` — **네 경로 모두 원문 키워드 교정**으로 진입한다(`intent_planner.py:106-226` · `host_inspect.py:52-69` · `query_gen_common.py:637`). 소스가 늘 때마다 이 방식으로 넓히면 D-004가 금지한 키워드 사전 분류에 가까워진다.
- Prometheus는 **본체 채팅 경로에 진입점이 없다**.
- **데이터 가용성으로 소스를 고르는 유일한 기존 구현**은 mcp_server의 PromQL ↔ OpenMetrics 소스 사다리(`metric_source.py`)다 — 메트릭 채널 내부에만 있다. 본체에서는 양식 업로드 턴의 field_mapper가 컬럼 매핑으로 `mapped_db_ids`를 정하는 것이 유일하다.

#### 2.8.4 같은 속성이 여러 소스에 있다

| 속성 | 소스 | 차이 |
|---|---|---|
| CPU 사용률 | 폴스타 통계(`cmm_metric_stat_h/d/m`) · 폴스타 REST 순간값 · Prometheus(`node_cpu_seconds_total` counter) · ITAM `sevrCPUUseRt`(연계 스냅샷) | 입도(시간/일/월 · 순간 · 초 · 스냅샷) · 단위(% · 0~1) · 신선도 · 의미 |
| 서버 사양(CPU 코어·메모리·디스크) | 폴스타(현재 구성 실측) · ITAM(자산 원장) | `server_spec`만 `ambiguous_owner: true` 불리언 하나 |

- 경계는 **"ITAM 설명문에서 사양·사용률 어휘를 뺀다"**로 푼다(D-214 ③). 새 소스마다 문구 조정이 필요하고 취약하다.
- **입도·단위·신선도·커버리지·정본 여부를 담을 구조화 필드가 없다** — 산문(`query_guide`)·주석에 흩어져 있다.

#### 2.8.5 "스키마나 기초자료로 정리"의 현재 품질

- `plans/104` 관리자 흐름의 LLM 컬럼 설명이 **ITAM에서 의미를 오독**했다(실측 — 벤더 시트 전사본과 대조):

| `hWSportEndYmd` | "서버 종료 날짜" | HW 지원 종료일(EOS/EOL) |

- 정합성 검사 `catalog_diff`는 폴스타 시맨틱 모델 사본만 본다. 레지스트리 설명 ↔ 프로필 ↔ capabilities 대조는 없다. `description_locked`를 쓰는 DB가 없어 LLM `상세`가 레지스트리 설명과 모순돼도 덧붙는다.

### 3.10 v1 조사에서 확인한 공백

- 계획에서 체크리스트를 자동 도출해 **온라인 게이팅**하고 지연을 보고한 연구가 없다.
- **task plan + answer plan 결합** 연구가 없다(TP-4는 설계상 추론).
- 운영 관측에서 **0행이 유효한 답**인 경우의 재계획 처리 문헌이 없다.
- 7~14B **로컬 양자화 모델**·**한국어**에서 루틴 추종·유형 분류·데이터 서술 오류율을 잰 연구가 없다.
- 가장 직접적인 근거(Routine · TDP · StepFly · Blueprint First)는 preprint이고 단일 조직 자가 보고다.

### 3.15 (v2) 조사에서 확인한 공백

- **이종 DB 엔진 + 시계열·메트릭 API를 연쇄 조회**하는 NL 벤치마크·동료심사 시스템이 없다(TACO는 단일 엔진 SQL).
- **교차 시스템 엔터티 매핑을 명시 과제로 넣은 AIOps 에이전트 벤치마크가 없다** — 공개 벤치마크는 키를 미리 통일해 둔다.
- hostname·자산 시리얼·IP 같은 **IT 식별자 문자열의 LLM 매칭** 연구가 없다.
- **fan-out(전달 키 수) 크기에 따른 정확도·지연 곡선**을 보고한 연구가 없다.
- **소스 10개 미만 + 짧은 설명 + LLM 선택** 형태를 직접 평가한 연구, **TSDB를 DB와 같은 카탈로그**에 넣고 라우팅을 비교한 연구, 다중 소스 라우팅의 **기권 평가**가 없다.
- 관계형 집계 테이블 ↔ TSDB **시간 해상도 정렬·단위 정규화**의 학술 평가가 없다.
- 운영 중 **스키마 드리프트를 감지해 LLM용 설명을 자동 갱신**하는 과정의 학술 평가가 없다.
- NL → PromQL 동료심사 문헌은 사실상 PromCopilot 1편이다.

→ 공백이 크다. 그래서 v2 설계는 **LLM 자유도를 줄이고 결정적 표·규칙·장부에 기대는 쪽**을 택하고, 효과는 **자체 교차 소스 골드(TP-0.6)**로만 판정한다.

## 4. 목표 설계

### 4.1 요청 계획 객체 — 사용자 모델의 칸을 한 객체로

```
RequestPlan (요청 스코프 · 턴마다 초기화)
├─ request_type      작업 유형 — 닫힌 열거형(§4.2) · LLM이 고르고 코드가 검증
├─ routine_id        작업 루틴 — request_type에서 결정적으로 결정(없으면 free_composite)
├─ frame             확정 의도 슬롯 — plans/107 IntentFrame 재사용(D-131 단일 출처)
├─ required_areas    (v2) 필요한 답변 영역·속성·기간·입도·명시 소스 — LLM 구조화 산출
├─ steps[]           주단계 = 루틴 단계 인스턴스
│    ├─ area         (v2) 이 단계가 답할 답변 영역 — 루틴 선언 또는 LLM 산출
│    ├─ owner_source (v2) 소유표로 코드가 결정한 소스(시스템·DB) + 결정 사유(정본/명시/대체)
│    ├─ capability   처리기(SUBAGENT_REGISTRY 키) — 소스 종류(backend)에서 결정적으로
│    ├─ slots        단계별 슬롯(전역 필터·기간을 단계 범위로 좁힌 값)
│    ├─ consumes     선행 단계의 타입 있는 출력 — (v2) entity_set(키 패싯) · db_set · time_window · scalar
│    ├─ bind         (v2) 키 패싯 · 브리지 결과(1:1/0/다건) · 배치 크기 · 상한 · 장부
│    ├─ on_empty / on_error   stop_with_notice · continue · fallback_step
│    └─ sub_steps    세부 단계 — 처리기가 선언한 고정 단계(관측 전용)
├─ answer_plan       결과 작성 계획
│    ├─ skeleton     응답 골격(해석 한 줄 · 표/스칼라 · 요약 · 경과 노트 · (v2) 출처·정의 차이)
│    ├─ checklist    완결성 항목(단계 종결 · 요청 컬럼 · 기간·대상 일치 · (v2) 브리지 커버리지 · 속성 커버리지)
│    └─ summary_mode template | llm_short(2~3줄) | none
└─ limits            단계 수 · 재계획 · 시간 예산(P-1) · (v2) 소스별 바인드 상한·동시성
```

- 저장은 기존 `task_plan`과 **병행**한다 — `steps[]`를 `task_plan` 호환 dict로 **렌더**해 넣고 `RequestPlan` 요약은 새 상태 키 하나에 싣는다(추정 — 키 이름은 TP-2 설계 검토에서 확정).
- **새 그래프 노드는 만들지 않는 것이 기본이다.** 네 노드의 함수 계층만 바꾼다. 3단 `tier3_plan.py`는 같은 함수를 재사용한다.

바뀐 흐름(**계획 LLM 호출 수는 늘리지 않는다**):

```
input_parser [LLM ①] ─ parsed_requirements
 → intent_planner
     ├ 사전 처리 계층 A (현행 유지 · 단 ②.5 존 재진입은 저장된 계획 복원 — TP-1.2)
     └ 유형·영역·슬롯 산출 [LLM ② 1회 · 입력 = 원문 + parsed_requirements
                           + 유형 카탈로그 + (v2) 소스 카탈로그 요약(고정 접두)]
         → {request_type, required_areas, step_slots, requested_source?, (free_composite일 때만) tasks}
         → (v2) 소스 결정 (코드: 소유표 — 0 기권 · 1 진행 · 2+ 규칙 → 역질문/가정 표기)   ← P-12
         → 루틴 인스턴스화 (코드: 단계 · 간선 · 처리기 · 키 패싯 · 한도)          ← P-1 · P-5 · P-14
         → 계획 검증 (코드: 닫힌 어휘 · DAG · 완결성 슬롯 대조 · 필수 입력 충족 순서 · 상한)
             불합격 → 결정적 수리 1회 / LLM 피드백 1회(기존 예산) → 그래도 불합격 → 현행 경로 + 사유
 → agent_orchestrator  단계 → 처리기 계약 바인딩 · (v2) 키 브리지 · 배치 바인드 · 소스별 동시성·타임아웃
 → replanner           결정적 트리거만 → 루틴 fallback_step 또는(자유 복합만) LLM 국소 재계획
 → result_aggregator   병합 판정 먼저 → 사실 목록 → 체크리스트 → 표(코드) + 출처 + 요약(모드) + 경과 노트
```

### 4.2 작업 유형 체계(G-2 확정 — 초안 채택 · D-270 ②)

유형은 **구조**를 말하고 소스를 말하지 않는다. **교차 시스템은 유형이 아니라 "단계들의 소유 소스가 다른 것"**이다 — 모든 유형에서 생길 수 있고, §4.11~4.13이 처리한다.

| 코드 | 유형 | 단계 골격 | 현행 대응 | 결과 형태 | 교차 시스템 예 |
|---|---|---|---|---|---|
| `lookup` | 목록·상세 조회 | 1단계 | 단일 조회 | 표 | "ITAM에서 EOS 지난 서버" |
| `rank` | 상위·하위 N | 1단계(정렬·상한 필수) | 같음 | 표 + 최댓값·최솟값 사실 | — |
| `aggregate` | 집계·통계 | 1단계(집계 필수) | 같음 · 멀티 DB 스칼라 | 스칼라/표 | — |
| `trend` | 기간 추이 | 1단계(기간 필수) | 같음 | 시계열 표 + 증감 사실 | "Prometheus 1시간 CPU 추이" |
| `compare` | 비교(존·DB·기간·시스템) | 비교 축마다 1단계 병렬 → 결정적 병합 | 멀티 DB 팬아웃 | 비교표(출처 열) | "폴스타 서버 수 vs ITAM 자산 수" |
| `select_then_detail` | 선별 → 상세 | s1 선별(entity_set) → s2 상세 | D-203 경로 | 선별 기준 + 상세 표 | "폴스타 CPU 80% 이상 → ITAM 계약 만료일" · "ITAM 노후 서버 → 폴스타 사용률" |
| `cross_domain` | 교차 도메인 | s1 한 영역(entity_set) → s2 다른 영역 | 복합 분해 + 교정 | 서버 키 병합 표 | "심각 알람 서버 → Prometheus CPU 추이" |
| `realtime_inspect` | 실시간·호스트 점검 | 1단계 | 교정 + 핸들러 | 표 | — |
| `document_fill` | 양식 산출 | 사전 처리 ③(현행 유지) | `mapped_db_ids` | 파일 | — |
| `admin_op` | 캐시·유사어 관리 | 1단계 | 사전 처리 · 교정 | 결정적 안내 | — |
| `usage_help` | 사용법·일반 | 1단계 | 코드 조립 | 텍스트 | — |
| `free_composite` | 루틴 미매칭 복합 | **현행 LLM 자유 분해** | `_llm_decompose` | 현행 | 3홉 이상 등 |

- 분류는 **LLM이 닫힌 열거형에서 고른다**(D-004). 루틴 선택은 유형에서 결정적 매핑이다.
- 필수 슬롯이 비면 루틴을 쓰지 않고 `free_composite`로 내린다(P-3). 되묻기로 바꿀지는 `plans/106` H1 소관이다.

### 4.3 작업 루틴 레지스트리(G-3 확정 — YAML 구조화 필드 · D-270 ③)

위치 후보 `config/task_routines.yaml`(런타임 정본 · 기동 시 1회 로드·검증). **v2: 단계는 처리기가 아니라 답변 영역(`area`)을 선언**하고, 소스·처리기는 소유표가 결정한다 — 같은 루틴이 폴스타 → ITAM과 폴스타 → Prometheus를 모두 덮는다.

```yaml
# 초안 — 필드 이름은 G-3에서 확정. 스키마 리터럴 금지(영역·슬롯·타입만).
version: 1
routines:
  - id: select_then_detail
    type: select_then_detail
    summary: "조건으로 대상을 선별한 뒤, 선별된 대상의 상세·추이를 조회한다"
    steps:
      - id: s1
        name: 대상 선별
        area: from_request                # LLM이 산출한 required_areas[0] — 예: server_usage
        slots: [filters, aggregation, limit, targets]
        output: entity_set                # 키 패싯 투영은 소스 카탈로그가 정한다(§4.13)
        on_empty: stop_with_notice        # D-203 선행 게이트와 같은 의미
      - id: s2
        name: 선별 대상 상세
        area: from_request                # 예: asset_contract(→ itam) · metric_series(→ prometheus)
        slots: [metrics, time_range]
        consumes: {s1: entity_set}        # 간선은 여기서 유도 — LLM이 쓰지 않는다
        output: rows
    answer:
      skeleton: [interpretation_line, selection_basis, bridge_coverage, table, provenance, summary, notes]
      checklist:
        - step_terminated: [s1, s2]
        - bridge_coverage: {s2: reported}   # 1:1 / 0건 / 다건 건수 표기
        - has_columns: {s2: metrics}
        - slot_matches: {s2: time_range}
      summary_mode: llm_short
    limits: {max_steps: 3, max_replan: 1}
```

- 프롬프트에는 **유형 카탈로그(유형당 1줄 + 필수 슬롯)와 소스 카탈로그 요약**만 고정 접두로 싣는다. 요청마다 프롬프트 접두가 바뀌지 않는다(KV 캐시 원칙).
- 한 줄 카탈로그로 분류시키는 것이 9B에서 정확한지는 U-2에서 측정한다.

### 4.4 처리기 계약 — 바인딩의 단일 출처(P-6 · v2 확장)

| 필드 | 내용 | 소비처 |

### 4.5 타입 있는 단계 의존과 단계 슬롯(P-5 · P-10 · P-14)

- 현재 데이터 의존은 **서버 식별자 집합 한 종류**다. v2에서 이것을 **`entity_set`**으로 일반화한다 — 값 목록이 아니라 **키 패싯 묶음**(hostname · server_name · ip · fqdn · asset_key 중 소스가 줄 수 있는 것)이다. 폴스타 → 폴스타 경로는 동작이 같다.
- 추가 타입: `db_set` · `time_window`(절대 구간 + 타임존) · `scalar`(임계값).
- 타입은 선행 단계의 **출력 스키마에서 코드가 뽑는다**(LLM은 값을 옮기지 않는다 — NESTFUL 28%).
- 선행 결과는 **값**만 바꾼다. **처리기·소스 선택은 바꾸지 못한다**(P-10 — 알람 문구·자산 비고 등 DB 내용 경유 주입 차단).
- **단계 슬롯 한정**: `_scope_parsed_requirements`가 전역 필터·기간·집계를 모든 task에 넘기는 것을 단계 슬롯으로 좁힌다.

### 4.6 결과 작성 계획(P-8)

순서: **병합 가능 판정 → 사실 목록 → 체크리스트 → 렌더 → (필요 시) 요약 LLM → 숫자 대조**.

1. **병합 판정을 task 마감 앞으로**(N-6).
2. **사실 목록**(코드) — 최댓값·최솟값·건수·임계 초과·증감·0행 사유 · 단위 포함.
3. **체크리스트 대조**(코드) — 미충족은 "미충족 하위 목표" 경과 노트(`dependency_notes` 재사용). **(v2)** 브리지 커버리지(1:1 n · 0건 m · 다건 k)와 속성 커버리지를 항목에 포함.
4. **요약 숫자 대조**(코드 · LLM 0회) — 불일치면 템플릿 요약으로 대체 + 로그.
5. **복합 합성 경로** — 의도(단계)별 표 + 단계별 한 문장(**G-7 ① 확정 — D-062 의미 개정 예정 · 랜딩 시 부기**).
6. **템플릿 요약**(**G-7 ② 보류** — TP-4.4 숫자 대조 측정 뒤 재상정 · D-251 ④ 유형 한정 개정 사항).
7. **해석 한 줄**(코드) — 대상·기간·지표·집계·제외 조건 + **(v2) 사용한 소스와 선택 사유**. UI 소유는 `plans/106` H2.
8. **(v2) 출처 열·정의 차이 각주** — task를 넘는 병합 표에도 값마다 소스를 붙이고, 같은 속성이 다른 소스에서 왔으면 정의 차이(입도·단위·시점)를 각주로(K-5 · L-6).

### 4.7 재계획 정책(P-7)

| 트리거(결정적) | 현행 | 목표 |
|---|---|---|
| 처리기 예외·검증 소진 | LLM 평가 후 재생성 위임 | **재계획하지 않는다** — task 안에서 사유와 함께 종결 |
| 0행 | 첫 0건 재조회 허용 · 연속 0건 중단 | 0행 원인 분류 — 식별자 미해결이면 1회 재조회, **데이터 없음이면 정답으로 종결** · (v2) **브리지 0건이면 재조회가 아니라 미매칭 보고** |
| 체크리스트 미충족 | 없음 | 루틴 누락 단계를 **결정적으로 추가** |
| 정체 — 같은 SQL 해시 반복 | LLM 평가 **뒤** 필터 | LLM 평가 **전** 판정 |
| (v2) 소스 불가 | 없음(침묵 대체) | 부분 답변 + 남은 작업(재계획하지 않음) |
| 자유 복합 후속 | LLM 평가 | 유지 — 새 task는 **계획 검증 통과 필수**(N-5) |

### 4.8 요청 시점 코드 생성 경로(G-8 확정: 필요 질의 비율 측정 뒤 판단 — 기본 범위 밖)

1. **진입 조건(결정적)**: 루틴 미매칭 + "이미 조회한 결과끼리의 계산" 필요 + 사용자 승인.
2. **표현**: **제한 연산 DSL**(JSON) — `filter`·`sort`·`join_by_key`·`group_by`·`derive(식 화이트리스트)`·`top_n`. 실행은 코드.
3. **입력**: 이미 조회해 마스킹을 거친 행만 · DB·외부 호출 없음.
4. **검증**: 스키마·상한·결과 합의.
5. **승격**: 골드 통과 + 사람 승인 뒤 루틴 단계로. 자동 등록 없음.
6. **채택하지 않는 것**: 임의 Python·셸 실행.

> v2 참고: 다중 소스 결합(폴스타 행 ⋈ ITAM 행)은 **결정적 병합(§4.13 ⑧)**으로 처리하고 DSL이 필요 없다. DSL은 파생 지표·재집계가 필요할 때만이다.

### 4.11 (v2) 소스 카탈로그 — 보유 데이터를 스키마·기초자료로 정리

**목적**: "어떤 데이터가 어느 DB·시스템에 어떤 입도·의미로 있는가"를 한 형식으로 정리해 ① 계획 LLM이 필요한 영역을 말할 재료 ② 코드가 소유 소스를 정할 표 ③ 응답의 출처·정의 차이 표기 ④ 관리자 점검 화면의 근거로 쓴다.

**정본과 파생(D-131 · G-15 확정 (a) — D-270 ⑭)**: 카탈로그를 **새 사본 파일로 만들지 않는다.** 정본에 필드를 더하고 기동 시 1회 파생·렌더한다.

| 카탈로그 층 | 정본(어디에 적나) | 파생 내용 |
|---|---|---|
| 시스템 | `db_registry.yaml` — `solutions`(다중 존) · `databases`(단일 DB) + **(v2) 비SQL 시스템 항목**(Prometheus · 폴스타 REST · OpenMetrics — `backend: mcp`/`rest`, plans/82 Wave 7 선언 형식) | 시스템 목록 · 활성 여부 · 인가 대상 여부 |
| 답변 영역 | 레지스트리 `capabilities` + **(v2) 신규 영역**: `metric_series`(메트릭 시계열) · `metric_instant` · `os_config` 등 | 영역 → 정본 소스 · 대체 소스 |
| **속성**(v2 신설) | 영역별 속성 레코드 — 프로필(`known_attributes` 등)·지식(`measures`)·메트릭 템플릿 목록에 **구조화 필드로** | 아래 레코드 |
| 스키마 | `db_profiles` · 104 승인본 · Redis 컬럼 설명 | 테이블·컬럼(소스 결정 **뒤** 해당 소스 것만 노출 — K-1) |

**속성 레코드(초안)**:

```yaml
# 예시 — 필드 초안. 값은 정본(프로필·지식·레지스트리)에 두고 여기서는 형식만 보인다.
- area: server_usage
  attribute: cpu_usage
  sources:
    - system: polestar          # 정본
      role: canonical
      granularity: [hour, day, month]      # 통계 테이블 입도
      unit: percent_0_100
      freshness: "수집 지연 최대 15분"
      coverage: "폴스타 에이전트 설치 서버 · 은행존은 일부 지표 미수집"   # LC 진술(K-5 · J-5)
    - system: prometheus        # 대체 — 명시 요청 또는 정본 불가 시
      role: alternate
      granularity: [raw_15s]
      unit: ratio_0_1
      derivation: "1 - rate(idle) — 템플릿 cpu_usage"
      coverage: "node_exporter 설치 호스트만"
      required_inputs: [entity_set.server_name]   # nodename 라벨(D-119)
    - system: itam
      role: not_for_this        # 같은 이름 · 다른 의미(연계 스냅샷 — plans/95 T5)
      note: "자산 원장 스냅샷 — 사용률 답변에 쓰지 않는다"
```

**설명 렌더 — 형제 소스와의 차이 중심(P-11 · K-3)**: 라우터·분해 프롬프트의 소스 목록을 "각 소스가 무엇을 가졌나"가 아니라 **"비슷한 소스와 무엇이 다른가"**로 렌더한다. 예: 폴스타 3존은 위치·엔진·미수집 지표 차이 · ITAM은 "사양·사용률은 정본 아님"을 **어휘 삭제가 아니라 명시 규칙으로**(D-214 ③의 취약성 해소). 렌더는 기동 시 1회(KV 캐시).

**생성·승인 흐름(P-20 · D-227 · D-228 · G-16)**:

1. **SQL 소스**: 104 흐름(MCP 수집 → LLM 초안 → 관리자 승인)을 확장 — 레지스트리 조각에 `capabilities`·속성 레코드 초안 포함 · 준비도 C3를 "설명 존재"에서 "영역·속성 선언 + 형제 차이 기술 존재"로 강화.
2. **설명 근거 강화**: 스키마 이름만이 아니라 **값 프로파일(분포·카디널리티)·쿼리 이력(질의 이력 저장소)·기초자료(관리자 제공 데이터 사전)**를 초안 근거로(K-2). ITAM 오독(§2.8.5) 재발 방지.
3. **비SQL 소스**: Prometheus는 **메트릭 템플릿 목록**(mcp_server 소유 · §4.14)이 속성 레코드의 원천 · 커버리지는 mcp_server의 `nodename` 커버리지 캐시(`metric_source.py`)를 **점검 화면에서만** 읽는다(질의 경로는 카탈로그만).
4. **승인 전 초안은 라우팅 재료가 아니다**(D-228). 승인은 사람.
5. 기초자료 업로드 채널은 **질의 사용자에게 묻는 것이 아니라 관리자 입력**이다 — **G-16 확정(D-270 ⑮)**: D-227 ⑨("신규 DB 구조 조사는 사용자에게 묻지 않는다 — MCP로 수집")의 "사용자"는 **질의 사용자**로 해석하며, 구조 조사는 계속 MCP로 수집하고 기초자료는 **설명 초안의 근거**로만 쓴다(승인 필수 · 샌드박스 자료 정본화 금지).

**정합성·드리프트(P-19 · TP-9.6)**: 레지스트리 영역 ↔ 프로필 속성 ↔ 템플릿 목록 교차 대조(`catalog_diff` 확장) · 스키마 스냅샷 diff에 **변경 등급**(테이블 추가·삭제 = 상 · 컬럼 = 중 · 설명 = 하) → 상이면 설명 재생성 요청 + 소스 판단 골드 재실행 · LLM `상세`가 레지스트리 규칙과 모순되면 경고(`description_locked` 활용).

### 4.12 (v2) 소스 판단 절차 — 어느 DB·시스템을 조회할지

```
[LLM · 계획 호출 안에서] required_areas = [{area, attribute?, time_window?, granularity?}]
                         requested_source = "prometheus" | null   ← 사용자가 소스를 명시했을 때만
[코드] 영역마다 소유표 조회
   ├─ 후보 0개            → 기권: "보유 소스 없음" 안내 + 가능한 영역 제시(K-6) · 조회하지 않음
   ├─ requested_source 있음 → 그 소스가 영역을 가지면 사용 / 없으면 "요청 소스에 해당 데이터 없음" + 정본 제안
   │                          / 비활성·미연결이면 "요청 소스 사용 불가" 사유(N-11 침묵 대체 금지)
   ├─ 후보 1개            → 진행
   └─ 후보 2개 이상        → 규칙: 정본(role=canonical) → 요청 입도·신선도 적합 → 커버리지
                             → 남으면 역질문(존 역질문 카드 형식) 또는 가정 표기("정본 폴스타 기준")
[코드] 시스템 안의 DB 결정: 폴스타 존은 현행 위치 힌트 고정(D-246) → 없으면 LLM 분류(classify_dbs)
       · 단일 DB 시스템(itam)은 분류 생략 · 교차 시스템 task에는 다른 시스템의 위치 힌트를 적용하지 않는다(N-10)
[코드] 필수 입력 판정: 선택된 소스의 required_inputs가 선행 단계로 충족되는지 — 아니면 "첫 홉 불가"
       (예: 실시간 프로세스 REST는 호스트가 먼저 필요)
```

- **D-004 준수**: 원문 키워드로 소스를 고르지 않는다. 결정적 코드의 입력은 **LLM 구조화 출력(영역 코드·명시 소스)**뿐이다(D-224 ① 방식). 기존 키워드 교정(알람·프로세스·호스트 점검)은 지우지 않고, 영역 산출이 안정되면 **동등성 측정 뒤** 영역 기반으로 옮긴다(D-161 — 폐기 전 실측).
- **소유 판정의 2단 기본화**(**G-13 확정 — D-270 ④**): 현행 `ROUTER_CAPABILITY_OWNERSHIP_ENABLED`(기본 off) 경로를 신규 플래그 없이 **섀도 → 측정 → 2단 기본 동작**으로 옮긴다(D-251 ⑥ 방식). 기본값 변경은 측정 통과 뒤 D-224 ⑥ 부기.
- **DB 안의 테이블 선택**(TP-9.4 부속): `schema_analyzer`가 테이블명만이 아니라 **카탈로그의 테이블 설명·속성**을 보게 한다 — 알람 힌트의 폴스타 테이블명 하드코딩(`schema_analyzer.py:998-1005`)은 카탈로그 렌더로 대체 후보(공용 계층 리터럴 제거).

### 4.13 (v2) 다중 소스 연쇄·병렬 실행

① **키 패싯 투영**: 선행 단계가 `entity_set`을 낼 때, **후속 단계의 소유 소스가 요구하는 키 패싯을 모두 SELECT**하도록 코드가 강제한다(카탈로그의 `required_inputs`). 폴스타 → ITAM은 `hostname`, 폴스타 → Prometheus는 `server_name` — 둘 다 필요하면 둘 다(§2.7.3). SQL은 LLM이 쓰더라도 **투영 요구를 프롬프트 계약 + 결과 검증**으로 확인하고, 빠지면 결정적 보충 조회(키만) 또는 사유.

② **키 브리지**(D-224 ②~④ 재사용 · **G-14 확정 — 패싯 병행 · D-270 ⑬**): 결정적 정규화(casefold · FQDN 단축 · IP 정규형 · 다중 IP 분해) → 대상 시스템 매니페스트(`entity_keys`)로 조건 확정 → **1:1 / 0건 / 다건(모호)** 등급. 다건은 **자동 조인하지 않고** 보고(L-2 · L-3). ITAM 매니페스트는 104 승인본에 `entity_keys`를 추가하는 경로로 공급(N-16). **Prometheus 패싯**(`nodename=server_name`)을 매니페스트 형식에 추가.

③ **바인드 조인 배치와 장부**(P-15): 후속 소스의 `max_bind_values`·`bind_block`으로 나눠 조회하고, **키별로 "결과 있음 / 데이터 없음 / 조회 안 함(상한·타임아웃·블록 실패)"**을 장부에 기록 → 체크리스트·응답에 노출. PromQL은 `nodename=~"a|b|…"` 정규식 목록 길이 상한(서버측 조립 · 값 이스케이프 D-119).

④ **bind ↔ ship 전환**(J-2): producer 결과가 상한을 넘으면 ⓐ 후속을 시간·존 필터만으로 조회해 코드가 키로 거르기 ⓑ 상위 N으로 줄이고 고지 ⓒ 역질문(대상 좁히기) — 루틴 `limits`로 선택. 선행 행 100 상한과 판정 스코프가 어긋나는 현행 문제(§2.7.4)도 장부로 드러낸다.

⑤ **같은 소스 안의 결합은 한 질의로**(P-13): 연속 단계가 같은 DB·같은 엔진이면 앱 레벨 IN 전달 대신 한 SQL(JOIN/서브쿼리) — TP-3.3 과분해 병합과 같은 규칙. 교차 전달은 이종 소스 경계에서만.

⑥ **병렬 예산**: 같은 레벨의 독립 단계(폴스타 ∥ ITAM ∥ Prometheus)는 병렬이되 **소스별 동시성·타임아웃**(계약 `concurrency`·`timeout_sec`)을 두고, 넘치면 부분 답변(P-17). 현행 레벨 병렬에는 상한이 없다.

⑦ **시간창·입도·단위**(P-18): 자연어 기간은 **계획 단계에서 한 번** 절대 구간 `[start, end)` + KST로 해석해 모든 소스에 같은 값으로 전달 · 입도 매핑(폴스타 h/d/m ↔ Prometheus `step`) · rate 창 = `max(step + 수집 간격, 4 × 수집 간격)` · 단위는 카탈로그 기준으로 정규화해 표기(% vs 0~1). "알람 발생 시각 기준인지 질의 시각 기준인지"를 슬롯에 명시.

⑧ **결정적 병합과 출처**: 브리지 결과 키로 병합(D-234 정규화 확장 — FQDN 단축 포함) · **값마다 소스 열** · 같은 속성이 여러 소스에서 오면 병기하지 않고 정본을 쓰되 대체 사용 시 각주 · **이종 집계 합산 금지**(N-13 — 같은 시스템·같은 영역일 때만 합산).

⑨ **보안·인가·감사**: 계획은 사용자 질의로만(P-10) — ITAM 비고·알람 문구 같은 DB 내용은 다음 단계의 **값**으로만 쓰이고 처리기·소스를 바꾸지 못한다 · **소스 단위 인가**(**G-18 확정 — D-270 ⑰**: D-232를 비SQL 소스로 확장한 `allowed_sources` 신설) · `inspect_host`·`process_query`·PromQL 호출을 본체 감사 로그에 기록(N-14).

⑩ **소재 프로브의 2단 배치**(N-15 · TP-10.8): 소유 모호 영역(`server_spec` 등)에서 식별자가 어느 시스템에 있는지 **고정 조회로** 확인하는 `entity_locator`를 2단 계획 검증 직후(또는 `agent_orchestrator` 진입부)에 배치 — **함수 호출 배치 우선**(G-11 확정 · 노드 추가는 필요성이 실측될 때만).
