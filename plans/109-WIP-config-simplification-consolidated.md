### ① 퀵 — 단계표와 멈춤 기준

**무엇인가** — 설정 파일이 멀쩡한지 전수로 검사하고, 설정을 바꿔가며 **축마다 어느 값이 최적인지** 잰다.
**내가 할 일** — 아래 단계를 **순서대로** 돌리고, 단계마다 「통과 기준」을 본 뒤 다음으로 간다. 끝나면 폴더를 전달한다.

> **왜 단계인가.** run `20260914-185540` 은 62 arm · 6,567턴 · **93.4시간**을 돌고 **통째로 폐기**됐다 —
> 역질문 56%·SQL 관측 0건 상태였는데 그걸 멈출 기준이 없었다. 단계는 새 명령이 아니다.
> **같은 명령을 점점 크게 돌리되, 다음으로 넘어가도 되는지 매번 판정한다.**
>
> **한 번 구동은 10시간을 넘지 않는다**(2026-09-21 사용자 지시 · D-239). 4·5단계는 전 축을 설정 카테고리별 **구간**으로 나눠
> `--segment next` 로 하나씩 돈다. 진행은 캠페인 상태 파일이 기억한다.

| 단계 | 명령 | 걸리는 시간 | 통과 기준(한 줄) |
|---:|---|---|---|
| **0** | 사전 결정·코드 준비 (명령 없음 — 아래 확인 4건) | — | 사다리 단 결정 · 벤치 계정 · **깨끗한 원격 커밋** · 하네스 수정 포함 |
| **1** | `python -m scripts.bench --preflight` → **실행할 서버에서** `python -m scripts.bench --segment next --mode dry` | 약 2초 → 약 40초 | 마지막 줄 `→ 실행 가능합니다.` · 그 서버의 구간 계획표를 떠 둔다(A.3 1단계) |
| **2** | `python -m scripts.bench --quick` → `python -m scripts.bench` | 91초 → 약 5분 | `즉시 조치  : 0건`(종전 L2 허위 6건은 2026-09-21 해소 · CS-10) |
| **3** | `python -m scripts.bench --sweep --mode mock --scale smoke` | 약 6분 | 건전성 블록에 `판정을 내지 않습니다` 없음 · 산출 4종 생성 (**exit 1 은 정상**) |
| **4** ★ | `python -m scripts.bench --segment next --mode run` — **첫 구간 = 관문**(보정 구간) | **1회 ≤ 10시간**(개발 PC 예시 5.6시간) | **차단 0 · 멈춤 주의 0** (아래) — 어기면 그 구간이 「실패」로 기록되고 `next` 가 멈춘다 |
| **5** | 같은 명령을 **구간 수만큼 반복** — 한 번에 한 구간 | 1회 ≤ 10시간 · 개발 PC 예시 20구간 · 합계 약 153시간(추정) — **첫 구간 뒤 다시 본다** | 구간마다 4단계와 같은 기준 |
| **6** | 결과 읽기 (명령 없음) | — | 캠페인 합산 리포트 → 구간별 건전성 → 축 최적 레벨 → arm 판정 순서 |
| **7** | 처분 제안 확인 (`--sweep` 이 이미 만든다) | — | `recommended.env.diff` 는 **제안일 뿐** |
| **8** | 산출 폴더 전달 — 구간 폴더 전부 + 캠페인 폴더 | — | 체크포인트 DB 제외 |

**4단계(첫 구간)가 핵심 관문이다 — 아래 중 하나라도 보이면 코드가 그 구간을 「실패」로 기록하고, 다음 `--segment next` 는 거기서 멈춘다.**
5단계의 모든 구간에 같은 기준이 걸린다(판정 코드 `sweep.RunHealth.stop_reasons()`).

| 화면에 나온 것 | 뜻 | 할 일 |
|---|---|---|
| `판정을 내지 않습니다 — …SQL 이 관측된 턴이 0건이다` | **차단**. 파이프라인이 SQL 에 못 닿았거나 하네스가 SQL 을 못 읽었다 | 멈춤. `raw.jsonl` 을 전달 |
| `판정을 내지 않습니다 — …전부 무효다` · `…오류다` · `유효한 프로파일이 0개다` | **차단** | 멈춤. `INVALID` 사유를 전달 |
| `주의: 그래프 진입률 NN%` (80% 미만) | 턴 상당수가 노드를 하나도 안 밟았다 | **멈춤** |
| `주의: 역질문 종료율 NN%` (30% 이상) | 역질문에서 멈춘 턴이 많다 — **이 런이 폐기된 이유** | **멈춤** |
| `주의: 무효 턴 N건(NN%)` | 러너 인증 실패 등 측정 불성립 | **5% 넘으면 멈춤**(D-219 ③) |
| `주의: 기준선 arm 이 N개 중 M번째로 실행됐다` | 기준선이 맨 앞이 아니다 — 커밋에 R-6 수정이 없다 | **멈춤**(0단계 커밋 확인) |
| `판정표를 무효로 표시했습니다 — … 불일치 쌍 합 0건` | 설정을 바꿔도 결과가 한 건도 안 바뀌었다 | **멈춤**(run 모드면 구간 「실패」) — 다른 구간도 워크로드는 같다 |
| `주의: 자동응답 N건(NN%)` | 하네스가 역질문에 대신 답했다 | **멈춤 사유 아님** — 그 턴의 라우팅·매핑 판정은 해석에서 뺀다(6단계) |

> **벤치 판정표의 기능 합격률은 단언이 평가되지 않은 턴을 분모에서 뺀다**(D-241 · 사용자 결정 ①) — 무효·타임아웃·역질문 차단
> 3사유의 턴 수가 건전성 블록에 따로 찍힌다(완주율·지연에는 남는다). **94 리포트(`report.md`)의 합격률은 아직 그 턴을
> 포함한다** — 러너 쪽 반영은 `plans/110` `108·G-6` 소관이고 36 사용자도 승인했다(2026-09-21) — 36이 구현할 때까지 두 숫자가 다를 수 있다. 두 숫자가 다르면 이 차이다.

**인증이 켜진 서버(`AUTH_ENABLED=true`)는 전용 벤치 계정이 있어야 돈다**(`plans/94` G-3 · D-215). 계정이 없으면 스위프는
서버를 띄우기 전에 멈추고 계정 주는 법을 출력한다 — 인증을 끄고 재지 않는다. 계정은 `--user <ID> --password <PW>` 또는
OS 환경변수 `BENCH_USER_ID`·`BENCH_USER_PASSWORD`(**`.env`·`.encenv`에 적으면 읽히지 않는다**). 운영자 크레덴셜은
설정에서 자동으로 읽는다(`--admin-user`/`--admin-password` 로 덮을 수 있다). 계정 준비는 `docs/03_setup_guide.md` §3.5.

**내부망(`fabrix`)·로컬(`mlx`)이면 승인을 묻지 않는다.** 외부 프로바이더(`gemini` 등)면 `--mode run` 이 시작하지 않고 멈춘다 —
여는 방법은 코드상 **`--yes` 하나**다(`__main__.py:407-410` `run_sweep` · §4.4 의 `RUN_BENCH=1` 은 구현되지 않았다).
**외부 프로바이더(gemini 등)는 과금이다. `--yes` 는 사용자가 이번 실행을 승인했을 때만 붙인다(D-127).**

### ② 상세 — 개발자 실행 참조본

#### A.1 30초 요약

```bash
cd /path/to/collectorinfra && source .venv/bin/activate

python -m scripts.bench --preflight                        # 1단계
python -m scripts.bench --quick && python -m scripts.bench # 2단계 — 설정 검증 (LLM 0)

python -m scripts.bench --segment next --mode dry          # 1단계 — 실행할 서버의 구간 계획표
python -m scripts.bench --segment next --mode run          # 4단계 — ★ 첫 구간 = 관문
python -m scripts.bench --segment next --mode run          # 5단계 — 같은 명령을 구간 수만큼 반복
```

- **단계를 건너뛰지 않는다.** 특히 4단계의 「멈춤」 신호(①퀵 표)가 하나라도 보이면 5단계를 돌리지 않는다.
- **한 번 구동은 10시간을 넘지 않는다** — 축을 설정 카테고리별 **구간**으로 나눠 `--segment next` 로 하나씩 돈다(D-239).
  진행은 캠페인 상태 파일이 기억한다. 구간 **안**에서 끊겨도 다음 `--segment next` 가 **같은 run 을 잇는다**(성공한 턴은 건너뛴다 · CS-04).
- `scripts.bench --segment next|<구간id>` 는 `scripts.scenario --segment N`(D-221 · 시나리오 N건마다 토큰 재발급)과 **다른 옵션**이다.
- YAML을 열거나 고칠 일은 없다. 축은 코드가 고르고, 판정표가 결론 문장을 쓴다.

  - **기준선과 실효 설정이 같은 arm 은 돌리지 않는다**(표의 `생략 N`). 설정 스냅샷 지문(`probe.config_fingerprint` · 비결정 키 제외)이
    기준선과 같은 arm 은 기준선을 한 번 더 도는 것(A/A)이라, 그 레벨은 **같은 구간의 기준선 관측**을 쓴다. 판정표에는
    `기준선과 동일 설정 → 기준선 관측 사용(실행 생략)` 으로 남는다. 지문으로만 정하고, 스냅샷을 뜨지 못하면 생략하지 않는다.
    **이 생략은 선택이 아니라 10시간 제약의 필요조건이다** — 생략이 없으면 arm 이 4개인 3레벨 축(`COMPOSITE_FANOUT_CONCURRENCY` 등 6개)이
    구간 하나(arm 당 2.78시간 → 최대 3개)에 들어가지 못한다.
  - **첫 구간은 가장 작은 구간(기준선 + 축 1개)이다 — 보정 구간.** 관문이라 실패해도 버리는 시간이 가장 적다. 그다음은 짧은 구간부터 돈다.
  - 추정 근거는 표 머리에 찍힌다. 시작 전 기본값은 **턴당 77.4초**(run 20260914 의 그래프 진입 턴 평균 — 전체 평균 51초는
    pre-gate 역질문으로 곧바로 끝난 턴 34%가 끌어내린 값이다) × **arm 당 129턴**(카탈로그) + 기동 30초 = **arm 당 2.78시간**이다.
- **보정 구간의 뜻** — 첫 구간(run 모드)이 끝나면 그 구간의 **실측 초/턴과 실측 턴/arm** 으로 남은 구간이 다시 짜인다
  (mock 구간은 반영하지 않는다 · 이미 끝난 구간은 다시 짜지 않는다). **그래서 구간 수와 구성이 바뀔 수 있다.**
  - 턴당 약 62.6초 이하로 재지면 구간당 arm 이 4개가 되어 구간 수가 준다.
  - 턴당 83.5초를 넘으면 구간당 arm 이 2개로 줄어, 생략 뒤에도 arm 이 3개인 3레벨 축 6개가 「구간 불가」(미측정)로 남는다.
    10시간 상한은 코드가 넘기지 않는다 — 그때는 사용자 판단이다.
  - **달력 추정(5단계)은 첫 구간이 끝난 뒤 `--segment next --mode dry` 로 다시 본다.**
- 실행: `nohup python -m scripts.bench --segment next --mode run > results/bench/nohup.log 2>&1 &`.
  끝나면 `구간 <id>: **완료**` 또는 `구간 <id>: **실패**`(이어서 `실패 사유:` 줄)가 찍히고 상태 파일·합산 리포트 경로가 이어진다.
- **통과 기준**: ①퀵의 「멈춤」 표 — **차단 0 · 멈춤 주의 0**. 어기면 코드가 그 구간을 「실패」로 기록하고(`campaign.json` · 사유 포함)
  다음 `next` 가 멈춘다. run 모드에서는 **전 arm 판정 불가 · 불일치 쌍 합 0건**도 실패다(mock 은 설계상 늘 그래서 제외한다).
  계정·프로바이더·MLX 관문에서 시작하지 못한 것은 구간을 돈 것이 아니므로 기록하지 않는다.
- 무과금 리허설(선택): `--segment next --mode mock` — 같은 계획의 첫 구간을 모의 서버로 돈다(2026-09-21 로컬 실측 **2분 01초**).
  상태 파일은 `mock-closed` 로 따로 쌓여 run 캠페인과 섞이지 않는다.
- 건전성 블록 읽는 법 — run 20260914 원시 로그에 **현재 코드**를 적용한 결과(실제 값):

```
건전성 — 유효 프로파일 62/62 · 턴 6567건 · 판정 {'error': 52, 'fail': 4268, 'manual': 1630, 'pass': 617}
  워크로드 도달 — SQL 관측 0% · 그래프 진입 66% · 역질문 종료 56%
  주의: 그래프 진입률 66% — 턴 2235건이 노드를 하나도 밟지 않았다(pre-gate 역질문·요청 거부). …
  주의: 역질문 종료율 56% — 워크로드가 역질문에서 멈췄다면 축이 아니라 역질문 응답 경로를 재고 있다
  주의: 기준선 arm 이 62개 중 62번째로 실행됐다 — 쌍체 지연 비교가 실행 시각과 교란된다. …
```

  그 런이 실제로 찍은 것은 첫 줄과 `오류 표지 314건: status=error http=422` 뿐이었다(`sweep_console.log:13-14`) —
  **오류율 0.8% 라 종전 관문을 통과했고 93시간을 돌았다.** 지금 코드는 위처럼 **차단**하고 주의 3줄을 낸다.
- **검정력을 올리는 것은 구간을 더 도는 것이 아니라 `--repeat` 다.** 축 비교는 (시나리오, 반복) 쌍으로 하므로 구간을 늘려도
  축당 표본은 같다. 단 `--repeat 2` 는 arm 시간을 두 배로 늘려 구간 구성이 바뀐다 — `--mode dry` 로 먼저 본다.

##### 5단계 — 나머지 구간을 하나씩 (1회 ≤ 10시간)

```bash
nohup python -m scripts.bench --segment next --mode run > results/bench/nohup.log 2>&1 &
tail -f results/bench/nohup.log
```

- **같은 명령을 구간 수만큼 반복한다.** 한 번에 구간 하나만 돈다. 남은 구간은 `--segment next --mode dry` 가 언제든 보여준다.
- **실패 구간이 있으면 `next` 는 멈춘다** — 건너뛰면 같은 원인으로 다음 구간도 버린다. 원인을 고친 뒤
  `--segment <구간id> --mode run` 으로 그 구간을 다시 돈다(같은 축·같은 생략 · 시도 횟수가 기록된다). 완료된 구간 id 를 주면 돌지 않는다.
- 진행 상태: `results/bench/campaigns/<캠페인>/campaign.json` — 구간별 상태 · run id · 건전성 · 실측 시간·턴 수.
  캠페인 이름 기본값은 `<mode>-<env>`(`run-closed`)라 mock 리허설(`mock-closed`)과 섞이지 않는다. 새 캠페인은 `--campaign <이름>`.
- **규모 — 개발 PC 기준 예시**(2026-09-21 기본 속도 · 생략 29 arm 반영): **20구간 · 합계 약 153시간(추정)** · 한 번 구동 5.6~8.3시간.
  구간마다 기준선이 한 번씩 돌아 실행 arm 은 55개(기준선 20 + 변이 35)다. 전 축 한 번(65 arm · 약 98시간 추정)보다 총량은 늘지만
  한 번 구동이 10시간을 넘지 않는다. 달력으로는 **하루 1구간이면 20일 · 야간·주간 2구간이면 10일**이다.
  **이 달력은 첫 구간(보정 구간)이 끝난 뒤 다시 본다** — 실측 속도로 남은 구간이 다시 짜여 구간 수와 구성이 바뀔 수 있다(4단계).
  운영 서버의 수치는 그 서버에서 뜬 계획표가 정본이다(1단계).
- **구간 안에서 끊기면 같은 run 을 잇는다**(CS-04 · 2026-09-21). 구간을 시작하기 전에 run_id 가 「진행」 기록으로 상태 파일에
  남고, 다음 `--segment next`(또는 `--segment <id>`)가 그 기록을 만나면 94 러너 이어쓰기(`resume_from`)로 넘긴다 — **성공한 턴은
  건너뛰고 무효 턴은 다시 돈다.** 완료된 arm 도 서버는 다시 띄운다(arm 당 약 30초). 기록된 pid 가 살아 있으면 멈춘다 — 같은 run 에
  두 프로세스가 쓰지 않게 한다. 이어 돈 구간의 경과는 마지막 시도분뿐이라 속도 실측(재계획)에 쓰지 않는다.
  실무 대책은 그대로 둔다: ①`nohup … &` ②원격이면 `tmux`/`screen` ③실행 창 합의(A.8 6번).
- **디스크는 구간마다 쌓인다.** 구간마다 `results/scenario/<run_id>/` 폴더와 arm 별 `checkpoints-<arm>.db` 가 새로 생긴다.
  체크포인트 크기는 run 20260914 가 arm 당 약 0.23GB(62 arm · 약 14GB), run 20260918 기준선이 한 파일 804MB 였다.
  **캠페인 전체 추정 = 구간 수 × 구간당 arm 수 × arm 당 크기** — 개발 PC 예시(55 arm)면 **약 13~44GB** 다. 끊긴 구간은 같은 폴더를 이어 쓰지만, 실패 구간 재시도는 새 폴더라 옛 폴더가 남는다.
  - **체크포인트 DB 는 재분석에 쓰지 않는다** — 판정의 유일한 입력은 `raw.jsonl` 이다(D-219). **그 구간의 `axis_verdicts.md` 와 합산 리포트가
    생긴 뒤에는 그 구간의 `checkpoints-*.db` 를 정리해도 된다.** 반출(8단계)에서도 뺀다.
  - 디스크를 검사하는 코드는 없다. 구간을 시작하기 전에 `df -h` 로 여유를 사람이 본다(구간 하나 = arm 3개 × 최대 약 0.8GB + 산출물).
- 전 축 한 번에 도는 `--sweep --mode run --scale full`(약 98시간)도 명령은 남아 있지만 **10시간 제약을 어기므로 쓰지 않는다**.
  `--sweep` 은 추정이 10시간을 넘으면 `--segment next` 로 나눠 돌리라는 경고를 낸다.

#### A.4 명령이 내부에서 하는 일 (참고 · 개발자가 실행하지 않는다)

```
--sweep
 1. 축 자동 선별   카탈로그(D-129) → F1 → F2 → 1차 축 (smoke 는 앞 4개)
 2. arm 전개       기준선 + 축마다 레벨별 arm(OFAT). 기준선이 맨 앞에 선다(D-238)
 3. 설정 스냅샷    서버를 띄우기 전에 arm 마다 자식 파이썬으로 실효 설정을 읽는다 → 대조군 식별(D-237)
 4. 실행           94 러너 — arm 마다 서버 기동·설정 에코·로그인·시나리오 실행·원시 적재·종료
 5. 94 리포트      report.md · summary.json (D-238)
 6. 건전성 관문    차단이면 여기서 exit 1 — 판정표를 만들지 않는다(D-219)
 7. 판정           노이즈 바닥(대조군 실측) → arm↔기준선 판정 → 축별 레벨↔레벨 판정(D-237)
 8. 후단 관문      전 arm 판정 불가면 판정표에 「무효」를 박고 exit 1
 9. 처분 제안      축 최적 레벨 → §6.5.2 처분 → proposals/ 4종(D-238)
```

- **실제로 도는 실험 설계는 S0(기준선)·S2(OFAT)뿐이다.** 93 §3.3 의 S1(노이즈 반복)·S3(교호작용)·S4(확인)는 구현되지 않았다 —
  노이즈 바닥은 S1 대신 **대조군 arm**(주입값 = 기준선 실효값)으로 잰다(D-237).
- 트랙 T(`python -m scripts.bench`)는 스위프와 **별개 명령**이다 — `--sweep` 은 트랙 T 를 돌리지 않는다.

```
--segment next   (D-239)
 1. 계획     전 축 arm 전개 → 설정 스냅샷(기준선 동일 arm 판정) → 카테고리별 구간 짜기(끝난 구간 제외 · 실측 속도)

 3. 실행     그 구간의 기준선 + 생략하지 않은 arm 으로 위 --sweep 2~9 (생략 arm 의 레벨은 기준선 관측으로 판정)
 4. 기록     구간 상태·건전성·실측 시간·턴 수 → campaign.json → 남은 구간 재계획 → 합산 리포트
```

##### 6단계 — 결과 읽기 순서

0. **캠페인 합산 리포트** `results/bench/campaigns/<캠페인>/campaign_verdicts.md` — 구간이 끝날 때마다 다시 쓰인다.
   끝난 구간의 「축 최적 레벨」을 모은 표이고, **미완·실패 구간의 축은 `미측정(구간 <id> 미완)` 으로 표에 남는다**(빠뜨리지 않는다).
   구간마다 기준선이 한 번씩 돌았으므로 **기준선 반복으로 노이즈 바닥**을 잰다. 같은 기준선이 구간마다 다르게 나오면
   *「구간 간 시간 교란이 크다」* 가 붙는다 — 그때는 **구간이 다른 축끼리 효과 크기를 비교하지 않는다**(축 판정은 구간 안에서만 내려진다).
   캠페인 단위 `proposals/`(`recommended.env.diff` 포함)도 같은 폴더에 있다.
1. **건전성 블록**(콘솔 · `nohup.log`) — 차단·주의부터. 4단계 기준을 다시 적용한다.
2. **`axis_verdicts.md` 「축 최적 레벨」 표** — *"이 축의 최적 레벨은 무엇인가"*. 판정 3종:
   `최적 레벨`(그 값이 유의하게 낫다) · `레벨 간 차이 없음`(**재서 같다**) · `판정 불가`(**측정이 안 됐다**).
   **「불일치 쌍이 전부 0건」이면 「차이 없음」이 아니다** — 레벨을 바꿔도 결과가 한 건도 안 바뀐 것은 워크로드가 축에
   닿지 않았다는 뜻일 수 있다.
3. **「arm 판정 — 기준선 대비」 표** — 근거다. `(대조군)` 표기가 붙은 arm 은 **주입값이 기준선 실효값과 같다** —
   그 줄의 델타는 축 효과가 아니라 **노이즈 바닥**이다. 머리말의 `실측 노이즈 바닥 — 지연 ±Nms` 를 넘지 못하는 지연 차이는 효과로 읽지 않는다.
   (run 20260914 는 설정이 같은 대조군 3개가 **-2.1초·+2.1초·+5.8초**를 냈다.)
   구간 캠페인에서는 대조군을 돌리지 않으므로 이 줄이 `(기준선과 동일 설정) · 실행 생략` 이고, 노이즈 바닥은 0번의 기준선 반복으로 본다.
4. **자동응답 주의가 있었다면** 그 턴의 라우팅·매핑·거부 판정은 하네스가 정한 값 위에서 내려진 것이다.
5. **벤치 판정표의 기능 합격률은 단언 미평가 턴(무효·타임아웃·역질문 차단)을 뺀 값이다**(D-241) — 건전성 블록·판정표 머리·합산 리포트에
   사유별 턴 수가 있다. 94 리포트(`report.md`)의 합격률은 아직 그 턴을 포함한다(러너 쪽은 36 승인 완료 · 구현 예정).
6. **D군(알람) 8건** — 커밋된 판의 벤치 스위프에서는 `TEXT2SQL_ALARM_DETERMINISTIC` 이 빠져 **LLM 경로의 결과**다(A.7). 결정적 알람 경로의
   효과로 읽지 않는다. 병합 교체(`110·N-2`)는 작업 트리에만 있고 36 `merge_arm_profiles` 커밋과 함께 들어간다 — 그 커밋 이후의 run 부터
   D군이 결정적 경로를 잰다(`raw.jsonl` D군 행이 `profile=optin_alarm+<arm>` · `base_profile=optin_alarm` 이면 교체된 판이다).

##### 7단계 — 처분 제안 (`--sweep` 이 이미 만들었다)

- **`--sweep` 이 끝나면 `proposals/` 4종이 이미 있다** — 축 최적 레벨을 93 §6.5.2 처분 절차에 넣은 결과다(D-238).
- **대조군 레벨이 이기면 `기각`(현행 유지)** 이다 — 현행이 최적이라는 뜻이라 기본값을 바꾸자는 제안이 아니다.
  이 구분이 없으면 현행 유지가 기본값 변경 제안으로 둔갑한다.
- `recommended.env.diff` 는 권고가 있는 축만 키를 쓰고, 없으면 사유만 주석으로 남긴다(`# **권고 변경 0건.**`).
- **어떤 파일도 자동 반영하지 않는다.** 반영은 93 §6.6 R0~R4 순서로 사람이 한다(이 문서 §3.4) — R3(기본값 변경) 전에 `migration_pin.env` 를 먼저 배포한다(93 §6.7.1).
- `python -m scripts.bench --propose` 는 **실 캠페인(`run-<env>` · 다른 캠페인은 `--campaign <이름>`)의 끝난 구간 축 최적값**을
  처분 입력으로 읽고 `recommended.env.diff` 도 쓴다(2026-09-21 · CS-34 부분). 캠페인이 없거나 끝난 구간이 없으면 종전처럼 트랙 T
  신호만으로 처분한다(`results/bench/<id>/proposals/`). 구간·캠페인 폴더의 `proposals/` 는 그대로 만들어진다.

##### 8단계 — 전달

- **전달할 것**: `results/scenario/<run_id>/` 폴더 — **단 `checkpoints-*.db` 는 빼고**(run 20260914 는 14GB 였고 판정 코드가
  읽지 않는다 · `plans/97` §1). 트랙 T 를 돌렸다면 `results/bench/<id>/` 도.
- **구간 캠페인이면 구간 폴더 전부 + 캠페인 폴더**를 보낸다. 구간 폴더 목록은 `campaign.json` 의 구간별 `run_id` 이고, 캠페인 폴더는
  `results/bench/campaigns/<캠페인>/` 다. `campaign.json` 에 없는 폴더(재시도 전 실패 시도)는 판정에 쓰이지 않았다 — 끊긴 구간은 같은 run 폴더를 이어 쓴다.
  체크포인트는 구간마다 쌓여 캠페인 전체로 수십 GB 가 된다(5단계 「디스크」) — 반출하지 않는다.
- **크기**: run 20260914 축소본이 **56MB** 였다(`plans/97` §5 목표 ≤50MB 와의 차이는 미정).
- **반출 스크립트는 없다** — `scripts/bench/triage.py`(`plans/97` §6 · R-8 → 이 문서 CS-06)는 미구현이다. 지금은 손으로 묶는다:

```bash
cd results/scenario && tar czf <run_id>-triage.tar.gz --exclude='checkpoints-*.db' <run_id>/

# 구간 캠페인 — 구간 폴더 전부 + 캠페인 폴더 (2026-09-21 mock 캠페인으로 확인 — 체크포인트는 묶이지 않는다)
cd results/scenario && tar czf ../<캠페인>-triage.tar.gz --exclude='checkpoints-*.db' \
  $(python -c "import json,sys; print(' '.join(r['run_id'] for r in json.load(open(sys.argv[1]))['records'] if r['run_id']))" \
      ../bench/campaigns/<캠페인>/campaign.json) \
  -C ../bench/campaigns <캠페인>
```

- **주의**: `raw.jsonl` 에는 질의문과 생성 SQL 이 들어간다. 폐쇄망 산출물을 내보낼 때는 기존 반출 절차를 따른다.

## 1. 장부 규칙

1. **행 키는 `CS-NN`이다.** 93의 잔여 대부분은 원본에 ID가 없어서 새로 매겼다. 원 ID가 있으면 `원 ID` 칸에 적는다(예: `97·R-8`).
   - 게이트에는 원 계획 번호를 붙인다(`93·G-5` · `97·G-3`).
   - 93 §11의 G-1~G-3과 97 §11.5의 G-1~G-3은 **서로 다른 항목**이다.
2. **항목마다 원 계획 절 · 소재지 · verify를 적는다**(D-208).
3. **한 항목은 한 곳에만 둔다.** 110과 겹치는 것은 §3.7에 참조만 둔다.
4. **완료는 이 문서의 행을 닫는 것으로 추적한다.** 상태 칸을 고치고 §7에 1줄을 추가한다. 원본은 고치지 않는다. D-번호 상태가 바뀌면 `docs/02_decision.md`를 갱신한다.
5. **run 결과를 인용할 때는 출처 4종을 같이 적는다**: run id · 커밋(저장소에 있는가) · 사다리 단 · dirty 여부. 하나라도 불명이면 처분 근거로 쓰지 않는다(97 §0.5.8 · D-161 ①).

## 2. 계속 유효한 계약 (요약 — 설계 정본은 원 절)

### 2.1 동작 경계와 측정 (93)
- **자동 반영은 없다.**
  - 신규 config 필드와 신규 `enable_*`는 0개다.
  - `src/`를 수정하지 않는다. `.env`·`.encenv`·`config.py`에도 쓰지 않는다.
  - 제안까지만 하고 적용은 사람이 한다(93 §4.1 · §6.1 · D-211).
- **arm 1개 = 프로세스 기동 1회**다. 설정 주입은 env로만 하고, 인프로세스 교체는 하지 않는다(93 §2 ④).
- **INVALID 조건.** 주입값과 자식 에코가 다르면 INVALID다. 사다리 단이 다른 arm도 INVALID다. 대조군 판정은 스냅샷이 없으면 하지 않는다(93 §4.5 · §5.3.2).
- **워크로드**는 `closed`가 기본이다. 활성 DB로 자동 판정하고, 첫 화면에 고지한다.
  - **건수의 정본은 `sweep.workload_summary()`·`judgeable_count()`의 동적 계산이다. 산문은 파생이다**(93 v11.1 · D-238 ⑨).
  - 2026-09-21 실측: closed 103건 · 판정 가능 92/103 · sandbox 31건.
  - 카탈로그 L군은 32건인데 워크로드는 31건이다. SYN-F-05가 러너 동작이라 빠지는 것이고, 드리프트가 아니다.
- **인증 on 서버는 전용 벤치 계정으로만 잰다.** 계정은 OS 환경변수나 CLI로만 받는다(D-215). 110 하네스는 계정이 없으면 내장 계정으로 폴백하는데, 이 차이는 **의도된 것**이다.
- **판정 신호는 2순위다**: 정확도 → 완주율 → SQL 생성률(93 §4.3.1). `llm_calls`·`tokens`는 추정치를 넣지 않는다(D-221).
- **없는 유의성을 만들지 않는다.** 불일치 쌍이 5 미만이면 판정 불가다. 효과 크기를 병기하고 BH 보정을 한다(93 §5.3).
  - **검정력을 올리는 것은 `--scale full`이 아니라 `--repeat`다.** full은 축을 늘릴 뿐 축당 표본은 smoke와 같다(가이드 4단계).
- **노이즈 바닥의 정본은 D-237 ⑥ 대조군 실측값이다**: 지연 **±4,009 ms** · 정확도 **2.0 %p**.
  - 97 §0.5.4의 ±5.8 s(그래프 진입 턴 부트스트랩)는 계산 방식이 달라 병존하던 값이다. 시점 기록으로만 본다.

### 2.2 판정 자격과 반출 (97 · D-219)
- **판정 입력은 `raw.jsonl` 하나다**(`sweep.read_observations`). 체크포인트 DB(용량의 98.6%)와 디버그 덤프는 판정 경로가 아니다.
- **반출은 서버 측에서 축소한다.**
  - Tier A: raw · summary · run.json · 로그 머리 20줄.
  - Tier B: ERROR 전량 · 지정 WARNING · artifacts · axis_verdicts.
  - 체크포인트 원본은 반출하지 않는다. 원본은 재측정이 끝날 때까지 보관한다(97 §2 · §5).
- **자격 관문이 먼저다.**
  - 오류율·무효율은 필요조건일 뿐이다. SQL 관측이 0건이면 판정하지 않는다.
  - 진입률·역질문률·기준선 순서는 **고지만 하고 차단하지 않는다.** 임계가 워크로드의 함수이기 때문이다.
  - 전 arm이 판정 불가인 표는 무효로 표시하고 **처분 규칙의 입력으로 보내지 않는다**(D-219 ③⑥).
  - 사람 쪽 멈춤 기준은 가이드 4단계의 「멈춤」 표다.
- **Phase 4 실패 원인 분류는 110 §2.2의 허위 불합격 필터를 먼저 적용한다.** 순서를 거꾸로 하면 판정 계약 버그를 제품 결함으로 잘못 분류한다(97 §3).
- **재현성.** 커밋이 저장소에 없거나 dirty인 런은 어떤 처분의 근거도 되지 않는다(97 §0.5.8).

### 2.3 비교·처분·롤아웃 (93 §6 · D-237 · D-238)
- **비교 단위는 둘이다**: arm↔기준선(마이그레이션 입력)과 레벨↔레벨(최적값).
  - 두 비교의 어휘를 섞지 않는다.
  - 3레벨 이상이면 축 안에서 BH 보정을 한다.
  - 우세 레벨이 갈리면 최적을 만들지 않는다(D-237).
- **대조군이 최적이면 `기각`이다.** 현행 유지가 기본값 변경 제안으로 둔갑하는 것을 막는다(D-238 ①). `decide()`는 정본이라 건드리지 않는다.
- **처분 규칙**: 0조·6조를 더한다(93 §6.2). 10순위 결정 절차의 0단계는 결함 수정이다(§6.5.2).
- **롤아웃은 R0 → R4 순서다.**
  - 체감 간소화는 R1·R2에서 나온다.
  - 처분 1건 = 커밋 1건이고, 커밋 메시지에 run_id와 규칙 번호를 적는다(93 §6.6).
- **회귀 방어**(93 §6.7):
  - R3 전에 `migration_pin.env`를 먼저 배포한다.
  - 비트 동일성 가드 4종을 둔다.
  - 테스트 목록이 없는 R4는 보류한다.
- **정량 목표는 노출 수다. 코드 노브 수가 아니다.**
  - 기존 `.env`는 줄이지 않는다.
  - 최종 판정 기준은 빈 `.env` + A등급만으로 기동·질의가 되는가다(93 §6.8 · §6.8.1).
- **축 선별의 한계**:
  - ①이름 신호로 고른다.
  - ②`AppConfig` 밖 상수는 축이 되지 않는다(`scripts/bench/axes.py` 독스트링 · §3.5 CS-60).
