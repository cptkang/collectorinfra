## 1. 배경과 범위

### 1.1 용어

| 용어 | 이 문서에서의 뜻 |
|---|---|
| **하네스(harness)** | 모델 바깥에서 모델의 입력·출력·실행 흐름을 조립·검증·제어하는 코드 전체. 문헌 G-1(ETCLOVG)은 Execution·Tooling·Context·Lifecycle·Observability·Verification·Governance 7층으로 나눈다. 의도 파악은 주로 **Context·Lifecycle** 층이다 |
| **의도 파악** | 사용자 발화를 **실행 가능한 목표**(대상·지표·기간·집계·산출 형식)로 바꾸는 일. 분류(intent) + 슬롯 채우기(slot filling) + 모호성 처리 |
| **명확화 게이팅** | 실행 전에 "물을지 / 가정하고 진행할지 / 거절할지"를 판정하는 단계 |
| **슬롯** | 의도를 실행하는 데 필요한 구조화 인자. 이 저장소에서는 `input_parser` 10키와 라우터 산출(`db_id`·`required_capabilities` 등)이 사실상의 슬롯이다 |

### 1.2 범위

- **대상**: 사다리 전 단 공통 전단(`context_resolver → input_parser → field_mapper`)과 3단 `semantic_router`·2단 `intent_planner`의 **의도 해석 부분**.
- **비대상**: SQL 생성 품질(`plans/61`·`67`·`69`) · 라우터 지시문 문구(`plans/79` 트랙 A — 이미 소유자 있음) · 신뢰도 logprob(`plans/79` 트랙 C — 이월 확정).
- **소유 경계**: 이 계획은 **"슬롯 기반 트리거 · 해석 표시 · 평가 확장"** 을 소유한다. 라우터 **신뢰도 기반 트리거**는 계속 `plans/79` C-3 ①의 소관이며 여기서 다시 설계하지 않는다(§7.2).

### 3.2 되묻기 트리거 전수 — **둘뿐이다**

| 트리거 | 성격 | 판정 입력 | 한계 |
|---|---|---|---|
| 존 역질문 | **결정적** | 채널·턴·위치/식별/지정 신호·팬아웃 | 슬롯 **하나**(존)만 본다 |
| `unknown` | **LLM 자기선언** | 라우터 LLM 출력 | 문헌 A-5: LLM은 거의 스스로 묻지 않는다. 기본 off |

`plans/79` C-3 ①(저신뢰 → 되묻기)은 **트리거 후보**지만 logprob 부재로 이월됐고, S-2(자기보고 분포 실측)가 정산 근거다(`plans/79` v17).
→ **"필요한 슬롯이 비었다 / 값이 실존하지 않는다 / 여러 대상에 걸린다"를 이유로 묻는 트리거가 없다.** 이것이 §4의 핵심 공백이다.

### 3.3 재작성(rewrite)의 위험 전례 — 이 저장소 고유 사정

문헌 B-1·B-2는 재작성으로 이득을 보고하지만, 이 저장소에는 **LLM 재작성이 의도를 오염시킨 실측 사례**가 코드 주석으로 남아 있다.

| 일자 | 사례 | 조치 | 위치 |
|---|---|---|---|
| 2026-07-16 | "은행존 알람"이 직전 위치와 병합돼 "김포 은행 공동존…"으로 재작성 → gp 오라우팅 | 이번 턴에 위치 표면어가 있으면 직전 위치/DB 줄을 **입력에서 제거** | `src/orchestration/intent_planner.py:585-590` |
| 2026-08-04 | 전량 조회 뒤 "OS 종류…확인" 후속이 직전 샘플 4개 서버로 **축소 재작성** | 지시어가 있을 때만 직전 엔티티 주입(D-153 후속1) | `src/orchestration/intent_planner.py:607-613` |

→ 교훈: **재작성의 오염원은 입력에서 결정적으로 제거**해 왔다. 문헌의 Mediator를 그대로 넣으면 이 방어선을 우회하는 새 재작성 경로가 생긴다. **H3은 조건부·후순위**로 둔다.

### 트랙 H1 — 슬롯 기반 결정적 명확화 게이트 (**1순위**)

**H1.1 배치**

```
context_resolver → input_parser → field_mapper → semantic_router ─┬─(기존 분기)
                                                                  │
                                           [신규] clarification_gate  ← 라우터 결과 + 파서 슬롯
                                                                  │
                                    ask → status="clarification" (기존 규약) / pass → 기존 분기
```

- **노드로 둘지, 기존 존 역질문 후단 게이트(`semantic_router.py:402`)를 일반화할지**는 G-3. 권고는 **후자**(추정 근거: 존 역질문이 이미 "라우터 결과 + 파서 슬롯 → 결정적 판정 → clarification 페이로드"의 완성형이다. 신규 노드는 `_INTENT_ROUTE_MAP`·`build_graph()`·conditional_edges 3곳 수정(D-004 주의사항)이 필요하다).
- 2단(`intent_planner`) 경로에는 `subagents._zone_clarification_or_none_task`와 **대칭 배선**한다(단일/멀티·레거시/오케스트레이션 대칭 실측 원칙).
- 계층: 판정 함수는 **domain**(순수 함수, `src/domain/clarification_policy.py` 가칭), 부품 호출(`entity_locator`·값 인덱스)은 기존 계층 그대로. `arch_check --ci` 통과가 수용 조건.

**H1.2 판정 유형 — AwN 4유형을 이 도메인에 매핑**

| 유형 | 트리거(결정적) | 판정 입력 | 부품 | 기본 동작 |
|---|---|---|---|---|
| ① `missing_slot` | intent별 **필수 슬롯 표**(H1.5)의 슬롯이 비었고, **기본값 정책이 없는** 경우 | `input_parser` 10키 · 라우터 `db_id` 집합 | 없음(순수 함수) | 묻는다 |
| ② `invalid_value` | 명시 식별자·지표명이 **어느 시스템에도 실존하지 않음** | `filter_conditions` 식별자 · `query_targets` | `entity_locator`(고정 조회) · 값 인덱스 | 후보 제시와 함께 묻는다(유사 후보 = `flex_match_score`) |
| ③ `out_of_capability` | 쓰기·변경 의도 · 미연동 시스템 · 권한 밖 존 | 라우터 intent · `required_capabilities` · RBAC | D-003 · `host_sweep.authorized_zones` | **묻지 않고** 사유와 대안을 돌려준다 |
| ④ `multi_reference` | 한 식별자가 **2개 이상 시스템/존**에 실존 | `decide_systems` 결정표 결과 | `entity_locator` | 선택지로 묻는다(존 역질문 페이로드 재사용) |

- ②·④는 `entity_locator`가 **3단 + `CROSS_SYSTEM_PROBE_ENABLED`** 에서만 등록된다(실측 — 모듈 docstring). 1·2단 경로에서의 가용성은 **§10 U-3 확인 필요**.
- ③은 **"묻지 않는" 유형**이다 — 되묻기가 아니라 조기 설명 반환이다. 문헌 D-1(레일)의 역할.

**H1.3 질문 선택 — EVPI의 결정적 근사**

문헌 A-3은 EVPI로 "가장 값어치 있는 질문 하나"를 고른다. 이 저장소에는 logprob이 없으므로(`plans/79` §3.1③) **후보 수 축소량**으로 근사한다(**추정** — 문헌이 제시한 방식이 아니라 이 계획의 설계다).

```
각 미해소 슬롯 s에 대해:
    before(s) = 현재 실행 시 팬아웃될 대상 수 (존 수 × DB 수 × 호스트 후보 수 …)
    after(s)  = s가 가장 흔한 값으로 확정될 때의 대상 수 (결정표로 계산)
    gain(s)   = before(s) − after(s)
질문 = argmax gain(s)   (동률이면 H1.5 표의 우선순위)
```

- 계산에 쓰는 값은 전부 레지스트리(`config/db_registry.yaml`)·결정표·고정 조회 결과다 — **LLM 0회**.
- **한 턴에 질문 1개**(선택지 여러 개 가능). 여러 슬롯이 비어도 한 번에 다 묻지 않는다(문헌 A-3 중복 질문 벌점 · A-4 1.3턴).

|---|---|---|
| `data_query`(사양·목록) | 대상 범위(존/DB 또는 식별자) | 존: 기존 존 역질문 규약 유지 · 식별자 없음 + 전량 = 허용(LIMIT 1000) |

**H1.7 (v2) 비용 등급별 적용 — ChatGPT Deep Research 패턴(P-6)**

상용 챗봇은 명확화 단계를 **모든 요청이 아니라 고비용 기능 앞에만** 붙였다. 같은 원칙으로 H1의 **개입 강도를 경로 비용 등급에 연동**한다. 등급은 **라우터·파서 산출물과 레지스트리로 결정적으로** 매긴다(원문 키워드 금지 — D-004).

| 등급 | 해당 경로(예) | 게이트 동작 | 근거 |
|---|---|---|---|
| **T0 저비용** | 단일 DB · 식별자 명시 · 단순 조회 | **묻지 않는다.** 빈 슬롯은 기본값 + **H2 해석 표시** | Model Spec "사소한 질문 회피 · 안전한 추정 + 가정 명시" |
| **T1 중비용** | 멀티 존/멀티 DB 팬아웃 · 대량 전량 조회 · 교차 시스템(`plans/102`) | H1 **`missing_slot`·`multi_reference`** 적용(현행 존 역질문이 이 등급의 부분 구현) | AwN · SAGE |
| **T2 고비용** | 실호스트 조사(`host_sweep`) · `sre_agent` 위임 · 문서(Excel/Word) 생성 · 순차 의존 복합 | H1 전 유형 + **H8 실행 브리프 확인** | Deep Research(명확화 → 재작성 → 실행) · Model Spec "비용 큰 행동 전 확인" |

- 등급 판정 함수는 H1과 같은 domain 순수 함수(`classify_cost_tier(route, parsed, registry) -> Tier`)로 두고, 등급별 활성 유형은 설정으로 둔다: `CLARIFY_TIER_POLICY=T0:none,T1:missing_slot|multi_reference,T2:all+brief`(형식은 G-8에서 확정).
- `plans/78` **P12**(저신뢰 상태로 위험 경로 진입 금지)와 **같은 자리**다 — P12가 신뢰도로 막는다면 H1.7은 **슬롯 충분성과 비용 등급**으로 막는다. 두 조건은 OR로 결합(어느 한쪽이라도 걸리면 확인).

**H5.2 (v2) 암묵 피드백 신호 — GPT-5 라우터 패턴(P-5)의 이식형**

GPT-5 라우터는 *사용자의 모델 전환 · 선호율 · 정답률* 로 **지속 학습**한다. 이 저장소는 학습하지 않는다(폐쇄망 · FabriX · 결정적 판정 원칙). 대신 **같은 종류의 신호를 모아 오프라인 평가와 골든셋 후보로만** 쓴다.

| 신호 | 의미 | 수집 지점(실측 · 신설) |
|---|---|---|
| 스코프 칩 해제(`reset_db_scope=true`) | 직전 턴의 스코프 승계가 **의도와 달랐다** | 요청 필드 존재(`src/api/schemas.py:73`) · **감사 기록 없음 → 신설** |
| 해석 표시(H2) 후 다음 턴 슬롯 정정 | 기본값 가정이 틀렸다 | H2 도입 시 신설 — 직전 `assumed_slots`와 이번 턴 파서 슬롯 diff(결정적) |
| 되묻기 무응답 이탈 | 질문이 과했거나 부적절 | H5 `clarification_decision` + 스레드 다음 턴 부재 |
| 단시간 재질의(같은 스레드 · 슬롯 대부분 동일) | 응답이 의도를 못 맞췄다 | 파서 슬롯 비교(원문 키워드 비교 금지) |
| 알람 노이즈 피드백 | (참고) 이미 존재하는 사용자 피드백 경로 | `plans/83` — 스키마 재사용 검토 |

- 저장: 감사 로그에 `event="intent_signal"` 신설(`AuditEntry` 확장 · 기존 `log_user_request` 옆). **원문은 저장하지 않고** 슬롯 diff·신호 유형·`thread_id`만 남긴다(D-183 저장 원칙 · PII 필터 정책 `docs/pii_filtering_rules.md` 준수).
- 사용처: ①H0 골든셋 후보 추출(사람 검수) ②H1.5 기본값 정책 재조정 근거 ③H4 가이드라인 증류 입력. **라우터·게이트 파라미터를 자동 갱신하지 않는다.**

| 암묵 기준 | background desiderata | 읽기 전용(D-003) · 존 권한(RBAC) · 은행존 → 공동존 조회 순서 · 민감값 마스킹 · 명시 위치 최우선·승계 금지(`intent_planner.py:585-590`) · 지시어 없으면 직전 엔티티 미주입(D-153 후속1) | 기존 코드 가드(이관 아님 — **명세가 인용**) |

**H7.2 명세의 사례 = 골든셋** — Model Spec이 원칙마다 사례를 붙이듯, 명세의 각 원칙에 **입력 → 기대 판정** 사례를 달고 그 사례를 H0 `clarification.yaml`에 그대로 넣는다(사례 id를 명세에서 역참조). 명세와 테스트가 **같은 사례를 공유**하므로 한쪽만 바뀌면 드러난다.

**H7.3 프롬프트 투영** — 명세 중 LLM이 알아야 하는 부분(암묵 기준 일부)만 **공용 프롬프트 블록 1개**로 렌더링해 `input_parser`·라우터·`intent_planner`가 공유한다(D-053 사본 금지). **프롬프트 텍스트 변경은 "Ask first" 항목**이며 `plans/79` S-1 측정 기준을 흔들므로 **S-1 이후 착수**, 렌더 결과는 `scripts/prompt_render_diff.py --ci`로 고정한다.

**H7.4 운영 원칙** — 명세는 **결정 문서(`docs/02_decision.md`)를 대체하지 않는다.** 결정은 "왜 이렇게 정했나", 명세는 "해석할 때 무엇을 적용하나"를 소유하며, 명세의 각 조항은 근거 D-번호를 인용한다.

### 트랙 H8 — (v2) 고비용 경로의 실행 브리프 확인 — Deep Research 패턴

**목적**: T2 등급(H1.7) 경로에 진입하기 전에, **해석된 요청을 구조화 브리프로 보여주고 1회 확인**받는다. Deep Research가 "명확화 → 상세 지시문 재작성 → 실행"으로 나눈 것을 옮기되, **재작성을 LLM 자유 서술이 아니라 슬롯 템플릿 렌더링**으로 한다(§3.3 재작성 오염 전례 회피).

**H8.1 브리프 스키마(초안)**

```python
class ExecutionBrief(BaseModel):          # src/domain/ 순수 모델(가칭)
    goal: str                # 최종 목표 등급(H7) — 템플릿 문구
    targets: list[str]       # 존/DB/식별자 — 파서·라우터·entity_locator 결과
    time_range: str | None   # 원문 슬롯 또는 기본값(assumed 표시)
    metrics: list[str]
    output: str              # 응답 / Excel / Word / 조사 리포트
    cost_hint: str           # 예: "은행존·공동존 3개 DB · 호스트 12대 조회"
    assumptions: list[str]   # 기본값으로 채운 슬롯(H2와 같은 원천)
    constraints: list[str]   # 읽기 전용 · 권한 밖 존 제외 등(H7 암묵 기준)
```

**H8.2 흐름**

```
T2 판정 → ExecutionBrief 렌더(결정적) → status="clarification"(kind="brief_confirm") 응답
        → 사용자: 확인 / 수정(슬롯 단위) / 취소
        → 확인 시 브리프를 그대로 실행 입력으로 사용(sub_query_context · sre_agent 위임 페이로드)
```

- **UI**: 기존 `status="clarification"` 규약을 재사용하되 `kind` 1개 추가 — 신규 화면 대신 존 역질문 카드의 변형(G-10). 프론트 영향은 **§10 U-9 확인 필요**.
- **`sre_agent` 위임**: 현재 조사 결과 쪽에는 브리핑 계약(`SPEC-briefing-contract.md` — *출력* 브리핑)이 있다. H8 브리프는 그 반대편인 **입력 브리프**다. 이름 충돌을 피하기 위해 코드에서는 `ExecutionBrief`/`investigation_request`로 구분한다.
- **LLM 사용**: 기본 0회(템플릿). 문구 다듬기가 필요하면 기존 라우터 평면(FabriX) 1회 — Deep Research의 "경량 모델" 역할이며 **신규 모델 도입 없음**.
- **예산**: 브리프 확인은 요청당 1회. H1 되묻기와 합산해 H1.4 예산(최대 2회)을 넘지 않는다 — 넘으면 브리프만 남긴다.
- 플래그: `EXECUTION_BRIEF_CONFIRM_ENABLED=false`. 비대화형 채널(시나리오 러너·API 일괄)에서는 **자동 확인 + 브리프를 감사에만 기록**.

- **(v2)** `plans/78` P12: H1.7 T2 판정과 OR 결합(§5 H1.7). 판정 함수를 공유하지 않고 **결과만 합친다** — 신뢰도(79/78)와 슬롯·비용(106)의 소유를 섞지 않기 위해서다.
